## Why the fallback exists, and why it stays

The fallback is not compatibility code, and removing it is not an option. Keep it, and add the clone arm.

- **Its job is sessions no launcher started, and most of those run in the main checkout.** It has been in the corpus since the initial commit (`2c01123c`), when every run copy was a linked worktree and the first `worktree ` line was right from anywhere. `feat_clone_per_run_anchor` (#120) put `HARNESS_MAIN_REPO` in front of it and kept it on purpose. `harness-runs/task_prompts/feat_clone_per_run_anchor_task_prompt.md`, goal 2: "When the anchor is absent (a supervised session in the main checkout, or any session no launcher started), the reader falls back to today's first `worktree ` line, so the main checkout resolves exactly as today." Every supervised command run in the main checkout depends on it.
- **The clone case without the anchor was left open, not decided.** The same prompt notes that inside a clone the first line "silently resolves to the clone itself". The anchor closed that for watcher-launched sessions. An operator's interactive session inside a clone was not considered. This branch closes that gap.
- **It is not there for adopters or for live worktrees.** No run copy has been created as a linked worktree since the clone switch (#122): `create-worktree.sh`, `--existing` included, only clones. The only `git worktree add` calls left are the maintainer scripts `scripts/release.sh` and `scripts/measure-suite.sh`, whose short-lived trees no plugin session runs in. The watcher and library still carry legacy-worktree support for runs started before clones. Removing it is a separate cleanup, and this branch must not depend on it in either direction.
- **It is not there for GitHub runs.** A `harness-run.yml` job checks the branch out as its own main checkout, and `autonomous-watcher.sh job` launches the session through `spawn_engine`, which sets the anchor unconditionally. Every way of starting a remote run reaches that same job: the local watcher's `remote-run.sh dispatch`, and `@sdlc-harness` comments on the run's issue through the trigger. The `profile-main-anchor` doctor comment already records that the fallback "answers the same directory there".
- **What the `git worktree list` form gives over a plain show-toplevel.** In a linked worktree a person adds by hand, it answers the main checkout, not the worktree. That costs nothing to keep, so goal 1's "keeps today's answer" covers it.

## Why it matters

The operator's natural move after a run finishes is to open a session in that run's copy, and every operator command misreads the state there:

- `branch-status` reports no run.
- `branch-answer`, `branch-pause` and `branch-resume` cannot find the record they act on.
- `branch-prompt`'s collision guard checks an empty registry and inbox.
- `branch-user-review` would drop its round into the clone's inbox, which no watcher reads.

The read paths fail quietly, with a confident wrong answer, not an error. The write paths put files where nothing will ever pick them up. The same applies to an autonomous instruction document whenever a session reaches it without the variable: the `AUTONOMOUS_STOP` kill-switch check would read the clone's state directory and miss a stop set in the main checkout.
