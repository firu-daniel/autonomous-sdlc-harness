## What `feat_unattended_bash_sandbox` already changed

- **Sandboxed Bash no longer sees the tokens.** The unattended profile's `sandbox.credentials.envVars` unsets `GH_TOKEN`, `GITHUB_TOKEN`, `HARNESS_PR_TOKEN`, `NPM_TOKEN`, `ANTHROPIC_API_KEY` and `CLAUDE_CODE_OAUTH_TOKEN` before every sandboxed command, and `sandbox.credentials.files` read-denies `~/.ssh`, `~/.aws`, `~/.config/gh`, `~/.gnupg`, `~/.netrc`, `~/.git-credentials`, `~/.docker/config.json`, `~/.kube`, `~/.config/gcloud`, `~/.azure` and the shell startup files, mirrored by `Read` denies for the file tools. This reaches **sandboxed Bash only**: the `claude` process itself, hooks, local MCP servers and the two excluded wrappers keep the whole environment (the profile's `CREDENTIALS ARE DENIED ON BOTH SIDES` note: "the excluded wrappers above keep the environment an HTTPS push needs. The gate launcher, also excluded, keeps it too").
- **The network is denied by default.** `network.strictAllowlist` with a shipped domain list that is empty, `WebFetch`/`WebSearch` and `curl`, `wget`, `nc`, `ssh`, `scp`, `rsync` and similar in `deny`. A credential a sandboxed command reads therefore has fewer ways out: an allowed domain, a commit that gets pushed, or text the run posts (a PR body, a park question).
- **Four commands run unsandboxed, each in one spelling** (`sandbox.excludedCommands`, the profile's `FOUR COMMANDS RUN OUTSIDE THE SANDBOX, EACH IN ONE SPELLING` note): the main checkout's own `commit-on-branch.sh`, `push-branch.sh`, `refresh-branch.sh` and `launch-sandboxed-gates.sh`, each as `bash <main checkout>/<scriptsDir>/<name>.sh:*`. The push runs every git call as `git -C <main>` with an explicit refspec, reads its configuration from the main checkout, and still **always exits 0**. The gate launcher starts the gate worker under its own `bwrap` (`--unshare-all`, no network) and unsets every `sandbox.credentials.envVars` name and masks every `files` path for it. None of the four reads `GH_TOKEN`/`GITHUB_TOKEN` or calls `gh` (checked 2026-11-08).
- **Not changed:** `.git/config` (and the persisted `extraheader` in it) is write-protected but still **readable**, by `Read(//<repoRoot>/**)` and by a sandboxed `cat`; job mode runs the session in the job's own checkout (`docs/remote-execution.md`: "Job mode runs exactly one run, in the job's own checkout"), so that is the file with the `extraheader`. `harness-run.yml`'s credential handling is untouched; `spawn_engine` strips nothing (its launch subshell exports only `HARNESS_MAIN_REPO` and `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`).

## What is there today, and why

- **The `run` job sets `GH_TOKEN: ${{ github.token }}` at job level**, with `contents`, `actions`, `issues` and `pull-requests` all `write` (`cli/templates/github/workflows/harness-run.yml` → the `run` job's `env:`, and the header's `# THE PERMISSIONS.` table). The table justifies each grant by a step that needs it: `restore`, `open`, `deliver`, `continue`, the push. **Those grants are legitimate. The leak is that a job-level `env:` also reaches the `Run the harness` step's child processes.**
  - The watcher process in that step needs the token. `autonomous-watcher.sh` → `job_control_poll` runs `remote-run.sh pause-requested` (a `gh run list`), and the job's progress pass reports through `remote-run.sh`.
  - **Also at job level: `HARNESS_PUSH_URL: ${{ secrets.HARNESS_PUSH_URL }}`**, the optional notification webhook `autonomous-notify.sh` posts to. It reaches the `claude` session the same way. Only the watcher's notify path reads it; decide under goal 1 whether the launch strips it too.
  - **The `claude` session that `spawn_engine` launches does not appear to need it.** No agent may run `remote-run.sh` (the script-allowlist guard's deny list), and the profile allow-lists no `gh`. Confirm this by searching every agent, instruction and allow-listed wrapper for a `gh` call or a `GH_TOKEN` read. Today nothing strips it: there is no `env -u` or `unset` in `spawn_engine`.
- **The `run` checkout persists its credential** (`token: ${{ secrets.HARNESS_GIT_TOKEN || github.token }}`, with no `persist-credentials: false`). The header's `# THE CHECKOUT CREDENTIAL.` paragraph gives the reason: `push-branch.sh` pushes with it. **That reason is real, and it reaches the agent.** The orchestrators call `push-branch.sh` themselves after every commit point: ledger flips, plan commits, the committer's opt-in push (`push-branch.sh` header, `# WHAT IT IS FOR.`). So the agent's own process tree must be able to push, and the token sits in `.git/config` as a base64 `extraheader`.
  - That file is readable through `Read(//<repoRoot>/**)` and `Bash(cat:*)` in `cli/templates/claude/settings.autonomous.json`. The sandbox write-protects `<main>/.git/config` but does not read-deny it.
  - **There is also an end-of-job `Push the branch` step**, `if: always()`, after `Run the harness` and the placeholder sweep. It is a backstop on top of the per-commit pushes (it pushes what a cancelled or failed session left), it uses the same persisted credential, and it turns every `refusing to push` / `push failed for` line into an `::error::` annotation and a job-summary line while still exiting 0. Goal 3's design must keep it working; goal 4 can reuse its reporting.
  - `github.token` expires when the job ends, which limits the damage. **`HARNESS_GIT_TOKEN` is a personal or App token that does not expire with the job.** When it is set, it is the credential persisted.
- **Locally**, the watcher launches `claude` with the user's whole environment: cloud keys, registry tokens, whatever the shell exports, plus everything in the operator override file `<machine config dir>/watcher.env`, which the watcher sources under `set -a` so its children inherit it. Each local session now runs in a per-run clone with a per-run profile (`run_profile_render`), so goal 5's design applies to that layout.
- **The precedent to copy is already in the repository.** The mention reader unsets `GH_TOKEN`, `GITHUB_TOKEN` and `HARNESS_PR_TOKEN` before its session (`remote-run.sh`, the `unset GH_TOKEN GITHUB_TOKEN HARNESS_PR_TOKEN` line). It also refuses output that carries the job token raw or in the base64 form `actions/checkout` persists (`remote-run.sh`, the function documented with "The job's `GH_TOKEN` in the base64 form `actions/checkout` persists into the…").

## The goal

> **Which agent pushes is not the boundary; the OS user and the job are.** The committer, the orchestrators' ledger and plan pushes, and every other agent run in one `claude` process tree, as one OS user, on one runner. A credential that any of them can use for a push, any of them can read. Inside a single job, a credential that is "kept by the watcher only" is not out of reach either:
> - **A parent's environment is readable by its child.** On Linux, a same-user process can read `/proc/<pid>/environ` (for example `cat /proc/$PPID/environ`), and `Bash(cat:*)` is allow-listed. Yama's `ptrace_scope` restricts attaching to a process, not this read. Measure it on the runner rather than trusting this note.
> - **GitHub-hosted runners give the `runner` user passwordless `sudo`.** Code the agent runs (a `scratch-run.sh` probe, a test, a gate) can therefore read any process's memory, including the runner worker's, where the job's secrets are held. Dumping `Runner.Worker` memory is how the 2025 `tj-actions/changed-files` compromise took secrets.
>
> So goal 1 and the in-job routes below are **hygiene that blocks casual reads**. They become a real boundary only together with the sandbox `feat_unattended_bash_sandbox` shipped, and only if it has a separate PID namespace and no-new-privileges (no `sudo`). **Both are now measured `pass` for sandboxed Bash on the hosted `ubuntu-26.04` image** (`docs/sandbox-record.md` §5, PN1–PN3 and NN1–NN2; see the status note above); cite that record rather than re-arguing it, and state that it does not cover other images or self-hosted runners. What it does not cover on any image is everything outside the sandbox: the `claude` process itself, the file tools, hooks, local MCP servers and the four excluded commands. The only boundary Actions guarantees is **the job**: each job gets a fresh runner.

1. **The agent session gets no GitHub API token in its environment.** The profile already unsets them for sandboxed Bash; this closes the rest of the session: the `claude` process, and through it hooks, local MCP servers and the four excluded commands. In job mode, `spawn_engine` launches `claude` with `GH_TOKEN`, `GITHUB_TOKEN` and `HARNESS_PR_TOKEN` removed (and `HARNESS_PUSH_URL`, unless the plan finds a session-side reader). The watcher keeps them for its own passes. Confirm first that none of the four excluded commands needs one of them (the profile's note says they keep "the environment an HTTPS push needs"; a check on 2026-11-08 found no `GH_TOKEN`/`GITHUB_TOKEN` read or `gh` call in any of them, and no `gh` call anywhere under `plugin/`). A test pins that the launch line strips them. Record in the docs that this is hygiene, per the note above.
2. **Every commit is still pushed as it lands. That is a requirement, not a trade-off.** A run stops in many ways: pause, a usage limit, an API failure, a stall kill, a manual cancel, a runner that dies. Every commit made before the stop must already be on the remote. **No design may move pushing to the end of the job**, however well an end-of-job push is guarded.
3. **Shrink what a leaked push credential is worth, since some credential must be reachable in-job.** Inside one job, any credential that can hand commits off (a push token, an artifact/runtime token, an `actions: write` dispatch token) is readable by the agent, per the note above. So the goal is to make the reachable credential short-lived and narrow, not absent. Choose a design, say why, and measure it on a real GitHub run. Candidates:
   - **Baseline, required whatever else is chosen: `HARNESS_GIT_TOKEN` is never referenced in the `run` job.** Only the job's `github.token` pushes there. It is scoped to this repository, expires when the job ends, and cannot change `.github/workflows/` (it has no `workflows` permission; verify this). Move every step that uses `HARNESS_GIT_TOKEN` into jobs that run no agent: the checkout token, `Open the draft pull request` (a job before `run`) and `deliver` (a job after it). Do not just move it to step-level `env:`: verify whether a job's runner receives every secret the job references when the job starts. If it does, a step-level reference is still in the worker's memory while the agent runs.
     - Today's reason for the token in the `run` job is "so the job's pushes trigger your own CI, which GITHUB_TOKEN pushes never do". Find another way for the agent-free jobs to trigger CI on the final tip, for example the PR open or update made with that token, or a `workflow_dispatch` of the adopter's CI. Measure that CI actually runs.
   - **A staging remote.** The `run` job pushes each commit to a separate staging repository, using a fine-grained token scoped to that repository only. A follow-up job with no agent (`needs: run`, `if: always()`, on a fresh runner) verifies the commits and promotes them to the real branch: branch not protected, no credential in any commit, no change to `.github/workflows/` unless the task allows it. Per-commit durability holds because the commits are on a remote the moment they land. A leaked token can damage only the staging repository. Weigh the extra repository every adopter must create, and what happens to a run whose follow-up job never runs.
   - **The watcher pushes, inside the same job.** `push-branch.sh` called from inside the session records that a push is wanted, and the watcher (`autonomous-watcher.sh job`, the parent of the `claude` session on GitHub too) pushes with a credential that is not in `.git/config`. Note that the agent's push call is already an unsandboxed process (the excluded main-checkout spelling), so whatever it can reach, the session can reach. It is a boundary only if the sandbox hides the watcher's process and denies `sudo`, per the measurement branch's Linux runner section. **That has now measured true on the hosted `ubuntu-26.04` image** (PN1–PN3, NN1–NN2), so this route is open there; it is still unverified on other images and on self-hosted runners, and the plan must say what the route assumes on those. Weigh it against the four unsandboxed commands, which can reach whatever the watcher's credential is reachable from.
   - **Rejected: handing commits to a separate, concurrently running pusher.** That job can be a parallel job in the same workflow, or one started through `workflow_dispatch`/`repository_dispatch`. The hand-off itself needs a credential in the `run` job: an artifact or runtime token, or an `actions: write` token to dispatch. That credential is just as readable, and `actions: write` can dispatch any workflow on any branch. Record this so it is not re-proposed, unless the plan finds a hand-off channel that needs no in-job credential.
4. **A pushed commit never carries a credential.** `push-branch.sh` refuses to push when the commits it would send contain the job token, `HARNESS_GIT_TOKEN` or the persisted `extraheader` value, raw or base64. Reuse the mention reader's check rather than writing a second one. A refusal parks or fails the run visibly. It never pushes a redacted copy silently. **`push-branch.sh` always exits 0 and every caller is told never to gate on its exit**, so "visibly" needs a channel other than the exit status (for example a marker the watcher acts on); choose one and keep the wrapper's exit contract. In a job, the end-of-job `Push the branch` step already turns a `refusing to push` line into an `::error::` annotation and a job-summary line; a push from inside the session still needs its own channel. Fit the scan into the wrapper's existing order (environment drop, main and target checks, main-checkout configuration) rather than ahead of it.
5. **Local runs scrub the environment.** The profile's `sandbox.credentials.envVars` is already a six-name deny-list for sandboxed Bash; this goal is about the `claude` process and everything that runs outside the sandbox. Decide between an allow-list (`env -i` plus the variables the run needs: `PATH`, `HOME`, the Claude credential, locale, `TMPDIR`, the harness's own variables, and what the excluded wrappers' SSH or HTTPS push needs, such as `SSH_AUTH_SOCK` and `GIT_SSH_COMMAND`) and a deny-list of known secret patterns, and say how it relates to the profile's list so there are not two owners of the same names. State what breaks under each. `docs.retrieval`'s server, `run-test-suite.sh` and the adopter's own gate commands run inside the session, so the allow-list must cover what they need. That probably means an adopter-configurable pass-through list, which is a schema change. Make it with its negative fixture.
6. **Docs.** Rewrite `# THE CHECKOUT CREDENTIAL.` and the `GH_TOKEN` reasoning in `harness-run.yml`'s header to the new design. Update `docs/remote-execution.md` (the zizmor `artipacked` paragraph and the bullet above it, which now name five credential-keeping checkouts: `run`, `collect`, `trigger`, `control` and `poll`) and `plugin/docs/AUTONOMOUS_FLOW_WHITEBOARD.md`'s containment paragraph.
