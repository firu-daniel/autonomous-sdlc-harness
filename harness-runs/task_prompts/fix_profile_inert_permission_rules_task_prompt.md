`fix_profile_inert_permission_rules` removes two kinds of permission rule that Claude Code ignores, from the generated unattended profile. `chore_sandbox_manual_verification` found them in the `--debug` log of every sandboxed session on Claude Code 2.1.299 (`<home>/Work/harness-sandbox-tests/sandbox-verification-issues.md` #3 and #4):

- **`Write(...)` rules, allow and deny:** `Write(//…) is not matched by file permission checks — only Edit(path) rules are. Use Edit(…) instead (Edit rules cover all file-editing tools).` The write protection held in every probe, because each protected path also has an `Edit` deny. But `doctor`'s `profile-write-protection` requires "an Edit and a Write deny rule", so it grades a rule the runtime ignores.
- **`Bash(bash <work_root>/<project_name>-*/scripts/<x>.sh:*)` allow rules:** `mixes * with the trailing :* prefix syntax, so it is matched as a literal prefix (the * is not expanded)`. So no wrapper is ever allowed under the absolute path of a run copy, which is a run's clone or a legacy worktree. That covers `typecheck.sh`, `test.sh`, `commit-on-branch.sh`, `push-branch.sh`, `refresh-branch.sh`, `scratch-run.sh`, `flow-walker.sh` and `run-test-suite.sh`.

## What the Claude Code permissions page says (checked 2026-10-21)

- "Claude Code checks file permissions against `Edit(path)` and `Read(path)` rules only. If you write a path rule for `Write`, … Claude Code accepts the rule but never consults it, and warns at startup."
- In a Bash rule, `*` stands for any text, slashes and spaces included. The `:*` suffix is the same as a trailing ` *`, but only at the very end of the pattern. A trailing ` *` matches the bare command too, but only when it is the rule's only wildcard.

So the space-star spelling of the glob, `Bash(bash <work_root>/<project_name>-*/scripts/<x>.sh *)`, does not fix it. Its first `*` crosses `/`, so it allows `bash <work_root>/<project_name>-x/../../<anywhere>/scripts/<x>.sh`. With two wildcards, it also stops matching a wrapper called without arguments.

## The goal

1. Generate `Edit` rules only, and have `doctor` stop requiring a `Write` rule. A profile that still carries `Write` rules is not a failure. `Write` rules are emitted in three places: `writeProtection.ts`'s file-tool deny map, the `permissions.allow` and `permissions.deny` entries in `settings.autonomous.json` with that file's comment about `Read`, `Edit` and `Write` prefixes, and the watcher's per-run profile map (`run_profile_entries` and the jq map that follows it). That map is pinned against `writeProtection.ts` by `watcher-run-profile.test.mjs`, so the two change together.
2. Replace the glob wrapper rules with an exact-path form, or drop them and document the spellings that do match. The watcher already writes a per-run profile that names the run copy by its exact path. An exact `Bash(bash <copy>/scripts/<x>.sh:*)` there is one candidate, and a glob spelling in any form is not, for the reasons above. Two other places read these rules, so check them too. `doctor` parses wrapper rules in `absolutePathExpressions` and `expressionCoversRoot`, and the sibling-glob coverage check depends on them. The plugin's `autonomous-script-allowlist-guard.sh` accepts wrapper calls under `<worktree_glob>`. The profile and the guard must stay one statement.
3. Leave the `--debug` re-run of the write-protection rows of `docs/sandbox-verification.md` to a manual check after merge. The run itself cannot launch those sessions. Record what that re-run must show: the protected paths still refuse writes, a run copy's wrapper called by absolute path is allowed, and the `--debug` log carries no `is not matched by file permission checks` or `mixes * with the trailing :* prefix syntax` warning for any generated rule.
