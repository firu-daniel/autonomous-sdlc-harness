### 1. `## The query-log pass` compares against a retired reading of the generated region, and publishes the gap with the wrong sign

**Site.** `docs/retrieval-eval-results.md` → `## The query-log pass` — the latency table row *"Library-level arm E (`fused-rerank`), `docs/retrieval-eval-results.md` generated region"*, the paragraph **The gap, and its two causes**, the **Provenance** paragraph's sentence beginning *"This pass ran at its own corpus snapshot"*, and the closing **Repeatability** paragraph's clause *"the first run's server-side p50 sat 25.7 ms below that arm"*. The renderer that composed them is `evals/docs-retrieval/query-log-pass.mjs` → `renderQueryLogSection`, fed by `comparedArm` (*"read out of the file of record's generated region — the machine half, so the comparison is against the published numbers rather than against a transcription of them"*).

**The problem, and why it is reachable.** `comparedArm(repo)` reads arm E's latency, snapshot, threshold and timestamp **live** out of `docs/retrieval-eval-results.md`'s generated region at the moment the pass runs. The pass ran at `2026-09-21T18:18:03.552Z`, against the region as Task 4 had generated it. Task 9 then regenerated that region at `2026-09-21T19:00:20.828Z`. The section was never re-rendered, so every figure it took from the region is a reading of bytes that no longer exist in the file, while the section's own prose still asserts it is a live read of the region above it.

The four claims, against the region as this branch ships it:

| Claim in `## The query-log pass` | The shipped generated region (`### Corpus self-docs`) |
| --- | --- |
| Library-level arm E: p50 `600.7`, p95 `748.2` | p50 **`1145.3`**, p95 **`1263.5`** |
| arm E *"was taken at `{ files: 13, chunks: 173 }`"* | snapshot **`{ files: 13, chunks: 177 }`** |
| *"under threshold `0.3`"* | `"abstainScoreThreshold": **0.32**` |
| *"(2026-09-21T16:46:35.978Z)"* | `"generatedAt": **"2026-09-21T19:00:20.828Z"**` |

**The runtime symptom.** The published gap is not merely stale, it is **inverted**. The section states *"the gap is +218.3 ms at p50 and +207.8 ms at p95, and it is what the two things only this pass's calls carry cost: the per-call incremental refresh … and the MCP round trip"*. Against the shipped region the same subtraction is `819.0 − 1145.3 = −326.3` ms at p50 and `956.0 − 1263.5 = −307.5` ms at p95 — the server-side pass is **faster** than the library-level arm the file publishes, so there is no positive gap for the refresh and the round trip to explain, and the paragraph attributes a cost to a difference that runs the other way. The `Repeatability` paragraph inherits the error: *"the first run's server-side p50 sat 25.7 ms below that arm"* (`575 − 600.7`) understates it — against the shipped region every one of the five runs (`575`, `637`, `649`, `702`, `819`) sits below `1145.3`, so the paragraph's conclusion that *"the table above publishes … the widest of the five"* is drawn from the retired figure too.

A consumer decision turns on this. `docs/retrieval.md` → **Why `setup-worktree.sh` does not warm the index** and `docs/development.md` → roadmap item 17 both rest on what the agent-visible per-call cost is; this section is the file of record for the MCP-versus-library half of that cost, and it currently says the MCP path costs +218 ms more when the same file's own numbers say it costs 326 ms less.

**One further consequence, which the fix must not restate wrongly.** The provenance's own safeguard is void: *"different stamps, so the two latency rows are read as server-side against library-level and never as a before/after pair"*. The pass's snapshot is `{ files: 13, chunks: 177 }` and the shipped region's snapshot is also `{ files: 13, chunks: 177 }` — the stamps are now **equal**, so the sentence's stated reason for holding the rows apart no longer applies.

**The proof.** All of it is in one file, no run needed:

- `docs/retrieval-eval-results.md` → `### Corpus self-docs`, the arm E table row and the machine half's `snapshot`, `abstainScoreThreshold` and `generatedAt` fields.
- `docs/retrieval-eval-results.md` → `## The query-log pass`, the latency table and the three paragraphs named above.
- `evals/docs-retrieval/query-log-pass.mjs` → `comparedArm`, which reads those region fields at run time, and `renderQueryLogSection`, whose `signed(result.server.p50 - compared.latency.p50)` is where the published `+218.3` came from.

**The fix.** Edit the hand-written section only — it sits below `<!-- eval:generated:end -->`, so nothing here touches bytes the runner owns, and **do not re-run the pass**: a re-run today measures `self-docs` at `{ files: 14, chunks: 194 }` against a region stamped `{ files: 13, chunks: 177 }` and reintroduces the same mismatch one corpus later.
