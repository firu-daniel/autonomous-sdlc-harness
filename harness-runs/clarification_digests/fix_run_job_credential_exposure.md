## question_1 — How to continue past a task plan that hit its revision cap, and whether to accept two adopter-visible design choices
- **raised by:** planning phase — the task-plan writing loop (`task-plan-writer` ↔ `architecture-reviewer` / `task-plan-reviewer`), via the flow walker's `binding: <escalate>`, `reason: cap`; latest findings `harness-runs/architecture_reviews/fix_run_job_credential_exposure/review_2.md` (architecture gate, FAIL, 3 Must Fix)
- **asked:**
  - **Q1 — How should the run continue past the non-converged plan?** The cap is the flow's stop for a plan that did not converge, and the branch changes how credentials reach the agent and how pushes authenticate on GitHub. Options:
    - **(a) Revise again.** Hand the open findings back to the writer for another round of the full gate sequence (architecture, then task-plan review). The answer may name a round limit.
    - **(b) Accept the plan as it stands.** Treat the three open Must Fixes as ones the implementers fix while implementing Tasks 4 and 5, and go straight to implementation. The branch review at the end would still catch anything left over.
    - **(c) Stop here.** You take the plan over yourself (edit the drafts, or re-plan under a supervised command).

    The three open Must Fixes in `review_2.md`, as the reviewer summarised them:
    1. Task 4 would make the watcher a second writer of the job's step summary — `remote-run.sh` → `verb_save` already writes status/detail to `$GITHUB_STEP_SUMMARY`; the fix drops the watcher's own append and re-words Tasks 8 and 11.
    2. Task 5 adds a `push-credential` verb to `remote-run.sh` without updating that file's header lists (**THE VERBS AND THE EXIT MAP**, **WHAT IT NEVER DOES.**).
    3. Task 4 leaves a false sentence in the watcher header (values from `watcher.env` reaching "the engine" now depend on the base set / `sandbox.passEnv`).
  - **Q2 — Do you accept the two design choices the writer flagged as visible to adopters?** Options: accept both / accept with changes (say which) / reject (say the route you want instead).
    1. **The CI trigger.** Pushes made with `github.token` start no workflow, so the plan has a new agent-free `deliver` job mark the draft PR ready with `HARNESS_GIT_TOKEN`, which fires `ready_for_review`. An adopter's CI must add `ready_for_review` to its `pull_request` types to run on the final tip. This goes in the upgrade note, and `init`'s printed setup step changes to match (Task 13).
    2. **Workflow edits.** With `HARNESS_GIT_TOKEN` out of the `run` job, a task that edits `.github/workflows/*` can no longer push from a GitHub job: its first such commit makes every later push in that run fail. Such tasks would have to run locally.
- **answered:**

  > fix_run_job_credential_exposure Q1 — (b) Accept the plan as it stands and go to implementation. The implementers fix the three open Must Fixes of architecture_reviews/fix_run_job_credential_exposure/review_2.md while implementing the tasks they belong to: (1) drop the watcher's own append to the job step summary, leaving remote-run.sh verb_save as its only writer, and re-word Tasks 8 and 11 to match; (2) when Task 5 adds the push-credential verb to remote-run.sh, update that file's header lists THE VERBS AND THE EXIT MAP and WHAT IT NEVER DOES.; (3) in Task 4, correct the watcher header sentence about watcher.env values reaching the engine so it states the base set / sandbox.passEnv rule.
  >
  > Q2 — Accept both, with one change to each:
  > 1. CI trigger: accepted (deliver marks the draft PR ready with HARNESS_GIT_TOKEN, adopters add ready_for_review to their pull_request types, upgrade note and init's setup step say so). But ready_for_review fires once per PR, so a later run on a PR that is already ready (a user-review fix cycle, a resumed run) would start no CI. Either have deliver convert the PR back to draft and mark it ready again on every run so the event fires on each final tip, or state that gap explicitly in the plan and the upgrade note and add it to the post-release GitHub measurement (roadmap item 35). Prefer the re-toggle if it needs no extra permission.
  > 2. Workflow edits: accepted that a task editing .github/workflows/* cannot push from a GitHub job and must run locally. But a commit that makes every later push fail breaks goal 2 (every commit pushed as it lands) silently. In a GitHub job, push-branch.sh must detect that the commits it would send change a file under .github/workflows/ and refuse at that first push through the same refusal record the credential scan uses, so the watcher fails the run visibly at once with that reason (still exit 0). Document this limit in harness-run.yml's header, docs/remote-execution.md and the upgrade note. Templates under cli/templates/github/workflows/ are ordinary files and are not affected.
- **carries beyond this branch:** two standing decisions for the remote-execution design. (1) A task that edits `.github/workflows/*` cannot push from a GitHub job and must run locally; in a job, `push-branch.sh` refuses such commits at the first push through the push-refusal record, which fails the run visibly. (2) The harness's CI trigger on a run's final tip is `ready_for_review`, re-fired on every run by `deliver` turning the pull request back to a draft and marking it ready again with `HARNESS_GIT_TOKEN`; adopters must list `ready_for_review` among their `pull_request` types.
