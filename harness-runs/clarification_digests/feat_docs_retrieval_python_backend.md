## question_1 — How the Python toolchain (`uv`, and through it Python 3.11+) gets onto the machine that runs this branch
- **raised by:** Phase A (task-plan implementation), `layer-implementer`, layer `general`, **Task 1** — "Scaffold the `harness-docs-retrieval` package, its lockfile and the `scripts/python-service.sh` toolchain wrapper" (`harness-runs/task_plans/feat_docs_retrieval_python_backend/task_1_plan.md`)
- **asked:** Q1 — how `uv` should get onto the machine. `uv` was not on PATH, and the only interpreter was the system Python 3.9.6, below the package's 3.11+ floor. `bash scripts/python-service.sh lock` exited `3` with `python-service: not provisioned: uv is not on PATH; install uv, then run bash scripts/python-service.sh sync`. It is a park because the plan names installing `uv` as an operator pre-step and Task 1 forbids installing it or falling back to `pip` or the system `python3`. Installing a toolchain also changes the machine outside the repository and needs network access. Options: (1) the operator installs `uv`, then answers "installed", and the resumed run re-dispatches Task 1 to run `lock` and `sync` and commit `uv.lock`; (2) the operator authorizes the run to install `uv` with a named command; (3) something else, such as re-planning around a different toolchain or stopping the branch.
- **answered:** installed — `uv` 0.12.21 via `brew install uv`, at `/opt/homebrew/bin/uv` (on PATH). PyPI and the pytorch-cpu index (https://download.pytorch.org/whl/cpu) are reachable. A trial `uv lock` of an unchanged copy of `docs-retrieval-service/pyproject.toml`, run outside the worktree, resolved 88 packages on darwin-arm64: torch 2.14.1 from PyPI for macOS and 2.14.1+cpu from the CPU index for Linux. Note: with no `.python-version` pin, uv picked CPython 3.14.7 for that trial. Re-dispatch Task 1: run `bash scripts/python-service.sh lock`, then `sync`, and commit `uv.lock` with the scaffold.
- **carries beyond this branch:** Provisioning `uv` stays an operator pre-step: an unattended run neither installs it nor falls back to another interpreter. With no `.python-version` pin, `uv` chooses the newest CPython it can find (3.14.7 in the operator's trial).

## question_2 — How the untracked scratch probes and `__pycache__` directories get removed so gate 6a passes
- **raised by:** Phase G (Run gates), round 1, fix loop G.4, `layer-implementer`, layer `general`, **Finding 1** — "Leftover scratch probe and `__pycache__` bytecode carry the home directory (gate 6a)" (`harness-runs/test_fix_plans/feat_docs_retrieval_python_backend_task_round_1/finding_1.md`; gate log `harness-runs/test_run_logs/feat_docs_retrieval_python_backend/task_round_1.log`)
- **asked:** Q1 — how to remove them. `harness-runs/scratch/` held 28 untracked probe files besides its tracked `README.md`, and Python runs had created `docs-retrieval-service/src/harness_docs_retrieval/__pycache__/` and `docs-retrieval-service/tests/__pycache__/`. Gate 6a found the home directory in them. It is a park because the permission profile denied the implementer's `rm -rf` and `find … -delete`, the denial is the operator's to change, and deleting untracked files is irreversible. Options: (1) the operator deletes them, then answers "deleted", and the resumed run confirms the fix site is clean and closes the finding; (2) the operator authorizes the deletion in the run's profile; (3) something else, such as excluding `harness-runs/scratch/` and `__pycache__` from gate 6a.
- **answered:** deleted
- **carries beyond this branch:** The run's permission profile does not let an unattended run delete untracked scratch probes or `__pycache__` bytecode. Those leftovers fail gate 6a, so the operator has to remove them by hand before the gates can pass.
