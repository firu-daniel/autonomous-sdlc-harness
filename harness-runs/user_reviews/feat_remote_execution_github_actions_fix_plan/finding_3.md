## Problem (verified against the working tree)

**(a) Storage.** `## 10. What it costs` covers runner minutes and the poller only; there is no word on artifact or cache storage, and none on the hosted runner's disk.

**(b) Retention.** The `harness-state` artifact is the only remote copy of a run's clarifications, park-loop count, auto-resume count and walker state (`## 4.` → **Central state**). The `Upload the state bundle` step sets no `retention-days`, so the repository's setting applies — 90 days by default, as low as 1 day if lowered. `has_bundle` filters on "(.expired != true)", so an expired bundle is indistinguishable from a missing one: `restore` then prints "no previous bundle for $branch; this is its first job" under `--resume none|pause` and proceeds (silently losing every carried count), and exits 2 under `--resume answer` with a message about "no finished run … carries a state bundle", which does not say why. `sync` treats the expired case as a job that "ended with no state bundle (killed, cancelled or replaced)", and case 1 ("already applied") never re-checks expiry, so a parked record synced before expiry still looks answerable to `/autonomous-sdlc-harness:branch-answer` — whose answer then reaches a job whose `restore` refuses it.

## Fix — (a) storage, documentation only

- [ ] In `docs/remote-execution.md` → `## 10. What it costs`, after the reference-figure table's closing paragraph, add a short **Storage** paragraph with: artifact storage included per plan — Free 500 MB, Pro 1 GB, Team 2 GB, Enterprise Cloud 50 GB, then $0.25 per GB-month; cache storage 10 GB per repository, then $0.07 per GB-month; public repositories free; the harness's own use negligible — a `harness-state` bundle of a few KB per job and about 300 MB of retrieval cache when docs retrieval is on. Cite https://docs.github.com/en/billing/concepts/product-billing/github-actions and https://docs.github.com/en/actions/reference/limits. Record the retrieval date as the section does: fetch them if the implementing run has network access and write that date; otherwise write that the figures are carried from the user review of 2026-09-28 and were not re-fetched — never invent a date.
- [ ] In the same section (or `## 8. Choosing a runner`, with a pointer from §10), state the standard GitHub-hosted Linux runner's **14 GB SSD** (https://docs.github.com/en/actions/reference/runners/github-hosted-runners, same retrieval-date rule): the checkout, the toolchain, the plugin, the retrieval runtime and the adopter's own dependencies and build output all share it. Name a **self-hosted runner** (§8) as the route for a repository too large for that, and say the harness does nothing about repository size beyond saying so.

## Fix — (b) retention

- [ ] **Workflow.** On `Upload the state bundle` in `cli/templates/github/workflows/harness-run.yml`, add `retention-days: 400` beside "overwrite: true". Add a header block, `WHY retention-days IS SET`, stating: the bundle is the only remote copy of a run's clarifications and counters; a run parked or paused longer than the retention cannot be answered and loses its counts; `actions/upload-artifact` caps a `retention-days` above the repository's own maximum at that maximum (400 is the largest any repository can configure), so the value means "as long as this repository allows" — which is the same as the repository's own default, so the explicit value documents the choice and makes any later lowering a visible edit rather than changing the effective bound; the real bound is the repository's retention setting, which `doctor --check-github` reads. **Verify the clamp against the `actions/upload-artifact` v4 README's `retention-days` input** before relying on it; if the action rejects rather than caps a larger value, use `90` instead and say so in the header. Either way add a row to `## 6. What is not verified here` for it, and one sentence to Gate 12 in `docs/development.md` asking the run to record the `harness-state` artifact's `expires_at` from `gh api repos/<owner>/<repo>/actions/runs/<run id>/artifacts`.
- [ ] **`remote-run.sh`: tell expired from absent.** Add a helper beside `has_bundle` that reports a run's state artifact as `present`, `expired` (listed with `expired: true` and no unexpired copy) or `none`, and exposes `expires_at` for the message. Keep `has_bundle`'s callers' meaning intact.
- [ ] **`restore`.** In `previous_bundle_run`/`verb_restore`: walking the finished `harness run` runs newest first, a run whose bundle is **expired** stops the walk (never fall through to an older copy — that would restore staler state). Then: under `--resume answer`, exit 2 with a plain message — `refused: the state bundle of run <id> expired on <expires_at>, so its questions can no longer be answered here: resume from the committed ledger with /autonomous-sdlc-harness:branch-resume <branch>, or re-drop the task; nothing written`. Under `--resume none|pause`, proceed from the committed ledger (the flows resume from it) but say so plainly instead of "this is its first job": a `::warning::` line (it is read in a workflow step) naming the run, the expiry date, that the park-loop, auto-resume and stall counts and the clarification history were lost, and that the run continues from the committed ledger. A newest run with **no** artifact at all (killed before its upload) keeps today's behaviour.
- [ ] **`sync`.** Case 2/3: when the newest finished run's bundle is expired (not merely absent), set `status: paused`, a new registry-only `pause_reason: expired`, `remote_run_id` / `remote_run_url` at that run, and `remote_detail` = `the state bundle of run <id> expired on <expires_at>: resume from the committed ledger with /autonomous-sdlc-harness:branch-resume <branch>, or re-drop the task`; restore nothing and print that line. Case 1: when the record is `parked`, `park_loop` or `paused`, re-check the recorded run's bundle; if it has expired since, apply the same `paused` / `expired` update (the mirror's question files stay, but the job can no longer take an answer). Add `expired` wherever `killed` is documented as a registry-only `pause_reason` — the `remote-run.sh` header's `THE \`killed\` MAPPING`, the `autonomous-watcher.sh` header's `pause_reason` vocabulary ("plus `killed`, a registry-only"), and the `status.json` schema comment in `cli/templates/scripts/lib/harness-run-lib.sh` (its `pause_reason` row, "registry-only `killed` is never written here"), which becomes "registry-only `killed` and `expired`" — with its reason. That last comment is the bundle vocabulary `hr_remote_status_write` filters on. Before committing, run `grep -rn "registry-only" cli/templates cli/src docs plugin` and cover every hit. Nothing in the scripts keys on `killed` in code, so the new value needs no code consumer beyond these.
- [ ] **`status`** (read-only; stays write-free): after its runs list, when the newest finished `harness run` run's bundle is expired, print `remote-run.sh: the state bundle of run <id> expired on <expires_at>; ...` with the same way on. It may call the artifacts API (a read); the existing exit map already covers a gh failure as 3.
- [ ] **Update the header** of `remote-run.sh`: the exit map's `restore` line under 2, the `restore` SELECTS paragraph, the `sync` cases, `status`'s paragraph, and `REPRO` lines for an expired bundle.
- [ ] **Plugin commands.** `plugin/commands/branch-status.md` step 3's remote-record summary names the expired line when `status` prints it. `plugin/commands/branch-answer.md` → "Remote records sync first": a record `sync` has set to `paused` / `expired` is not a candidate; report the `remote_detail` sentence (the way on) instead of writing an answer. `plugin/commands/branch-resume.md`: beside the `pause_reason: killed` bullet, add that a record synced as `paused` with `pause_reason: expired` is resumable the same way, from the committed ledger, with its carried counts and clarification history lost. Keep each command's closing scope fence unchanged (they still invoke only the verbs they name).
- [ ] **`doctor --check-github`: a best-effort retention read.** In `REMOTE_GITHUB_CHECK`, after the variables read, ask `gh api repos/{owner}/{repo}/actions/permissions/artifact-and-log-retention` through the same `ask`. Answered: parse `days` (a positive integer; any other shape is the existing "answered in a shape this check does not read" warning). Below the threshold — **30 days** — `warn`: `the repository keeps artifacts for <n> days, so a remote run parked or paused longer than that loses its state bundle: raise it under Settings → Actions → General → Artifact and log retention`. Argue the 30 in the doc comment: a parked run waits on a human answer and a usage-paused one on a reset, the bundle is the only remote copy of either, and 30 days covers an ordinary absence — a holiday — while GitHub's own default (90) passes; below it, an ordinary absence can cost a parked run its question. `refused` (typically HTTP 403: the endpoint needs admin access) is a **note**, not a warning: `artifact retention not checked: <call> needs admin access (<why>)`. `unknown` follows the existing `cannotTell` warning. Update the doc comment's grade list and the pass text (append the retention figure when read). **Where the two constants live (decided at plan time):** both are `checks.ts`-local `const`s, declared beside the file's other local constants such as `REMOTE_RUN_SCRIPT`:
  - `ARTIFACT_RETENTION_ENDPOINT = 'repos/{owner}/{repo}/actions/permissions/artifact-and-log-retention'`. It is not a `githubActions.ts` export. That module owns the **names** that `cli/src` shares with the shell and YAML mirrors (workflow files, secrets, variables, artifact names), and it declares none of the `gh` call shapes `REMOTE_GITHUB_CHECK` already issues (its `['variable', 'list', …]` argv is local to `checks.ts`). This endpoint has one reader, `REMOTE_GITHUB_CHECK`, and no shell or YAML file spells it.
  - `ARTIFACT_RETENTION_WARN_DAYS = 30`. It is `doctor`'s grading policy, argued in that check's own doc comment, so it is local to `checks.ts` as well.
- [ ] **Docs.** In `docs/remote-execution.md` → `## 4.` → **Central state**, add the retention limit: the bundle lives as long as the repository's artifact retention (90 days by default, 1–400 configurable), what is lost when it expires, what `restore`, `sync`, `branch-status` and `branch-answer` then say, and that `doctor --check-github` warns below 30 days.
