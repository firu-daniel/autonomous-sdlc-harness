## Problem (verified against the working tree)

`poll_branch` returns 1 (not waiting) for any branch whose newest `harness run <branch>` run is not `completed` — "[ \"$state\" = completed ] || return 1". `continue_wait_poller`, the step that runs `gh workflow enable harness-resume.yml` for a usage-paused job, is the **last step of that very job** ("Continue, wait or stop" in `harness-run.yml`), so while it runs the job's run is still `in_progress`. The interleaving the user described is real:

1. The poller is enabled because branch B is usage-paused.
2. A tick lists the runs; branch A's job is still `in_progress`, so A is skipped (not waiting).
3. A's `continue` step enables the poller (a no-op: already enabled).
4. The tick finds nothing due or waiting (B was just dispatched, or its entry resolved) and `verb_poll` runs `gh workflow disable harness-resume.yml`.

A ends on `decision: wait-poller` with no poller left. Its `paused` notification promised an automatic resume at the reset, so it waits for a manual `/autonomous-sdlc-harness:branch-resume` that nobody knows is needed.

## Fix

**The ordering that closes the window.** In `harness-run.yml` the `Upload the state bundle` step runs **before** `Continue, wait or stop`. So by the time A's `continue` runs `workflow enable`, A's `harness-state` artifact already exists on A's still-in-progress run (`actions/upload-artifact@v4` makes an artifact available as soon as its step finishes; see the §6 row below). A tick that **re-checks after its own disable** therefore always sees the artifact of any job whose enable came before that disable, and a job whose enable comes after the disable leaves the poller enabled anyway. Re-checking in-progress runs *for an uploaded usage-paused bundle* (not merely "in progress") also meets the user's constraint: an ordinary long job carries no `harness-state` artifact until its final steps, so it never keeps the poller ticking.

- [ ] **A non-completed run carrying a usage-paused bundle counts as waiting.** In `poll_branch`, replace the bare "[ \"$state\" = completed ] || return 1" with: when `$state` is not `completed`, look up the run's artifacts **without exiting on failure** (the existing `has_bundle` calls `gh_fail`, which exits the whole tick with 3 — add a non-fatal variant, or a flag, that returns a distinct code on a gh failure). No `harness-state` artifact yet: skipped, not waiting — unchanged behaviour. Artifact present: download it (the existing download-directory reuse applies) and read `status` / `pause_reason`; `paused` + `usage` is **waiting** (return 0) and is **never dispatched from this arm**, even when its `usage_resume_at` has passed — its own `continue` step will enable the poller, and the next tick, seeing it `completed`, dispatches it through the normal arm with the chain limit. An artifact that is listed but cannot be downloaded (or an artifact lookup that fails) on an in-progress run counts as **waiting**, with one log line: it is conservative, and bounded to the job's last steps.
- [ ] **Re-check after the disable, and re-enable when a waiting run appeared.** In `verb_poll`, after `gh workflow disable "$WORKFLOW_RESUME_FILE"` succeeds: reset the listing cache (`ALL_RUNS_LISTED=0`), list again with `list_all_runs`, and re-evaluate each branch's newest `harness run` run with a **no-dispatch** evaluation — the waiting rules above and the existing reset-ahead rule, with no `redispatch` call and no notification (a run that is due now is still "waiting" for this purpose: the next tick dispatches it). If any branch is waiting, run `gh workflow enable "$WORKFLOW_RESUME_FILE"` and log `poll: <branch> became waiting during this tick; re-enabled <file>`. A failed re-list is a log line and the tick ends as it would have (disabled) — it cannot be worse than today. A failed re-enable sends one `paused` notification per waiting branch, naming gh's error and `/autonomous-sdlc-harness:branch-resume <branch>`, exactly the wording shape `continue_wait_poller` uses for a failed enable, and the verb still exits 0. Factor the evaluation so the first pass and the re-check share one function with a "may dispatch" switch, rather than two copies of the bundle-reading logic.
- [ ] **Update the header** of `remote-run.sh`: the `poll` paragraph ("Skipped, not waiting: … a run not yet `completed` (its own `continue` will decide)") must now state that a not-yet-completed run carrying a usage-paused bundle is waiting and never dispatched, and that after a disable the tick re-lists once and re-enables when a run became waiting; add the re-check to the exit map's "For poll" wording only if an exit changes (it should not); extend the `REPRO` `poll` lines with the interleaving case.
- [ ] **Docs.** In `docs/remote-execution.md` → `### Resuming without the local watcher`, after "**disables itself** once no run is left waiting", add one or two sentences: a job that ends on a usage pause uploads its bundle before it enables the poller, so a tick that disables re-checks once and re-enables when a job's usage-paused bundle appeared meanwhile; an ordinary running job carries no bundle until its final steps and never keeps the poller enabled. Add a row to the `## 6. What is not verified here` table: *An `actions/upload-artifact@v4` artifact is listed by `repos/{owner}/{repo}/actions/runs/<id>/artifacts` and downloadable with `gh run download` while its run is still in progress* — what rests on it: the post-disable re-check; source: the `actions/upload-artifact` v4 README (cite it with its retrieval date, or mark it not retrieved, per the table's existing convention); if it is wrong: the listing shows no in-progress artifact, the re-check finds nothing and the window stays open exactly as it is today — state that plainly, and that Gate 12 observation (v) records which it is. Extend Gate 12 (v) in `docs/development.md` → `## 5. ## Tests (`cli/test/remote-run.test.mjs`)

The stub today answers every `run list` and artifact query with one fixed value, so it cannot express "the world changed between the tick's first listing and its disable". Extend `STUB` minimally: when the stub's own log already contains a `workflow disable` call, it answers `run list` from `STUB_RUN_LIST_AFTER_DISABLE` and the artifact list from `STUB_ARTIFACTS_AFTER_DISABLE` (each falling back to its ordinary variable when unset). That models exactly "A uploaded and enabled after the first listing, before the disable". Update the suite header's `continue` and `poll` rule paragraph to name the new rule.

- [ ] **The interleaving case (the user's).** Branch B's newest `harness run` run is `completed` with a usage-paused bundle whose `usage_resume_at` has passed; branch A's newest run is `in_progress` with **no** artifact. After-disable answers: A still `in_progress`, now carrying `harness-state` whose bundle says `status: paused`, `pause_reason: usage`, `usage_resume_at` far ahead. Assert: B is dispatched (`workflow run … -f resume=pause`); `workflow disable harness-resume.yml` is recorded; a `workflow enable harness-resume.yml` is recorded **after** it (the poller ends enabled); no `workflow run` for A; no notification.
- [ ] **The constraint case.** Same, but after the disable A is still `in_progress` with **no** artifact (an ordinary long job). Assert the tick ends with `workflow disable` as its last enable/disable call — the poller is not kept enabled for a job that never paused.
- [ ] **In-progress, already uploaded, first pass.** A's run is `in_progress` and already carries a usage-paused bundle at the first listing: assert no `workflow disable` is sent at all and A is not dispatched.
- [ ] Existing `poll` cases stay green unchanged.
