## Problem (verified against the working tree)

When the due branch's re-dispatch fails, `poll_branch` logs "dispatching $branch failed ($REDISPATCH_ERR); still waiting" and returns 0, so `verb_poll` counts it as waiting and never disables the poller. Nothing bounds the retries and nothing notifies. A persistent cause — `harness-run.yml` removed from the default branch, the workflow disabled, `actions: write` withdrawn — keeps the poller ticking on every interval indefinitely (billed at least one minute per tick on a private repository), the run never resumes, and the only trace is a log line inside each tick's job.

## Fix

**Two bounds, either of which ends the retries for a branch:**
- a count: `HARNESS_POLL_MAX_DISPATCH_FAILURES` consecutive failed dispatches of the same paused run (default **3** — three ticks, 90 minutes at the shipped interval, is enough to ride out a transient GitHub error, and short enough that a persistent one costs at most three billed ticks for that branch);
- a deadline: the branch's `usage_resume_at` more than `HARNESS_POLL_GIVE_UP_AFTER_MINUTES` in the past (default **360**). This bound is stateless, so it still ends the loop when the carried count below is lost.

Each is a repository variable read through `harness-resume.yml`'s `env:`, with the default applied in the script when empty and the same "not a non-negative integer" refusal shape `HARNESS_MAX_CHAIN` has. Argue both defaults in the script's constants block beside `MAX_CHAIN_DEFAULT`.

**On reaching a bound:** send exactly one `paused` notification for the branch through the existing `notify` — detail: `The resume poller could not re-dispatch <branch> (<REDISPATCH_ERR>) after <n> attempts; automatic resume has stopped. Run /autonomous-sdlc-harness:branch-resume <branch>.` (use `$RESUME_HINT`), and from then on do **not** count that branch as waiting, so the poller can disable itself.

**Where the count lives (the user asked this be stated).** A tick's job starts from a fresh checkout and `GITHUB_TOKEN` can neither read nor write repository variables (the design already relies on that fact for pauses), so the count cannot live in the checkout or in a variable. It lives in a **poller state artifact**, `harness-poll-state`, uploaded by each tick of `harness-resume.yml` and read by the next:

- [ ] **The file.** `poll_state.json` under `<state_dir>/autonomous_logs/poll_state/current/` in the tick's checkout — one object keyed by branch: `{"<branch>": {"run_id": "<the harness run id whose bundle is being resumed>", "failures": "<n>", "notified": "1" | ""}}`. An entry whose `run_id` is not the branch's current newest `harness run` run id is discarded on read — a new run (a user's resume, a re-drop) resets the count. A successful dispatch removes the entry. A branch that has been notified keeps its entry with `notified: "1"` and is skipped silently (not waiting, no second notification) on every later tick while its `run_id` is unchanged.
- [ ] **Reading the previous tick's copy** is `poll`'s own job, through `gh` like every other call (so `remote-run.sh` stays the one shell-side producer): list `harness-resume.yml`'s runs newest first (bounded), skip `GITHUB_RUN_ID`, take the newest one carrying an unexpired artifact named `harness-poll-state`, and download it into `<state_dir>/autonomous_logs/poll_state/previous/`. The resume workflow's file name is already `WORKFLOW_RESUME_FILE` in `remote-run.sh`, so reuse it and do not retype it. The owner of each new name is fixed below under **Where each new name is owned**. Any failure to find or read the previous copy (first tick, expired, gh failure, unparseable JSON) is **one log line and an empty state**, never a failed tick; the stateless deadline bound still ends the loop.
- [ ] **Writing it.** `poll` always writes `current/poll_state.json` (an empty object when nothing is carried), including on its early `HARNESS_REMOTE_STOP` exit, so the next tick inherits the count unchanged.
- [ ] **Uploading it.** In `harness-resume.yml`, add after the poll step: `- name: Upload the poller state`, `if: always()`, `uses: actions/upload-artifact@v4`, `name: harness-poll-state`, `path:` the `current/` directory (compute it from `stateDir` in the existing `Read the configuration` step into `GITHUB_ENV`, the way `SCRIPTS_DIR` is), `overwrite: true`, `if-no-files-found: ignore`, and `retention-days: 7` (it only has to survive from one tick to the next; a week tolerates an edited long interval). Keep the header's two rules: every value through `env:`, every expression with a space after its braces. Update the header's `WHAT IT READS` with the two new variables and add a `WHAT IT WRITES` line for the artifact. The job's `permissions` (`actions: write`) already cover listing and downloading its own workflow's artifacts; say so in the header.
- [ ] **Where each new name is owned.** This was decided at plan time: `cli/src/remote/githubActions.ts` states "every remote-execution name has one owner", and a grep of `cli/src` finds no reader of `harness-poll-state`, `HARNESS_POLL_MAX_DISPATCH_FAILURES`, `HARNESS_POLL_GIVE_UP_AFTER_MINUTES` or, today, `HARNESS_MAX_CHAIN`.
  - **The artifact name `harness-poll-state`** is owned by `githubActions.ts`, as a new export `POLL_STATE_ARTIFACT_NAME` declared directly under `STATE_ARTIFACT_NAME`. The module's own doc comment lists "the state-artifact name" among the names it declares, and `STATE_ARTIFACT_NAME` sits there with no `cli/src` reader either, so artifact names are kept together with one owner. The shell and YAML copies are declared mirrors: add `POLL_STATE_ARTIFACT_NAME mirrors POLL_STATE_ARTIFACT_NAME` to `remote-run.sh`'s `MIRRORS OF \`cli/src/remote/githubActions.ts\`` list and set the shell constant `POLL_STATE_ARTIFACT_NAME='harness-poll-state'` beside `STATE_ARTIFACT_NAME='harness-state'`. Add `POLL_STATE_ARTIFACT_NAME` to the `cli/src/remote/githubActions.ts` line of `harness-resume.yml`'s `DECLARED MIRRORS` block, because its upload step spells the name. Extend the module comment's name list if it enumerates them.
  - **The two variables `HARNESS_POLL_MAX_DISPATCH_FAILURES` and `HARNESS_POLL_GIVE_UP_AFTER_MINUTES`** stay shell- and YAML-only, as `HARNESS_MAX_CHAIN` does. `remote-run.sh`'s constants block owns their defaults (`POLL_MAX_DISPATCH_FAILURES_DEFAULT=3` and `POLL_GIVE_UP_AFTER_MINUTES_DEFAULT=360`, beside `MAX_CHAIN_DEFAULT=24`, each argued in a comment). `harness-resume.yml`'s `env:` passes them through from `vars.`, and no `cli/src` constant is added. If a later `doctor` check reads them, that check moves them into `githubActions.ts` and adds the mirror entries.
- [ ] **Update `remote-run.sh`'s header**: the `poll` paragraph ("a dispatch that fails is one line and still waiting") now states the two bounds, the single notification and the carried state; the environment list gains the two variables; `WHAT IT NEVER DOES` gains the `poll_state/` writes; `REPRO` gains a failing-dispatch line.
- [ ] **Docs.** In `docs/remote-execution.md` → `### Resuming without the local watcher`, add a short paragraph: a re-dispatch that keeps failing is retried at most `HARNESS_POLL_MAX_DISPATCH_FAILURES` times (or until `HARNESS_POLL_GIVE_UP_AFTER_MINUTES` after the reset), then one `paused` notification names gh's error and `/autonomous-sdlc-harness:branch-resume <branch>`, and the poller stops counting that branch; the count travels between ticks in the `harness-poll-state` artifact. Add both variables to the `### Every secret and variable` table (read by `remote-run.sh poll`, defaults 3 and 360).

## Tests (`cli/test/remote-run.test.mjs`)

The stub needs two small extensions: `STUB_FAIL_TIMES=<n>` (fail the `STUB_FAIL_ON` prefix only for its first *n* matching calls, counted through the stub's own log), and answering `run list --workflow harness-resume.yml …` from its own variable (e.g. `STUB_RESUME_RUN_LIST`) so the previous tick's state artifact can be served through the existing `STUB_ARTIFACTS` / `STUB_BUNDLES` maps. Between ticks, the test copies the previous tick's `poll_state/current/` into the directory `STUB_BUNDLES` names for the resume run, which is what the upload-then-download does on GitHub.

- [ ] **A dispatch that always fails.** One usage-paused, due branch; `STUB_FAIL_ON='workflow run'`. Run `poll` `HARNESS_POLL_MAX_DISPATCH_FAILURES` times, carrying state between ticks. Assert: ticks 1 … n−1 send no notification and no `workflow disable`; tick n sends **exactly one** `paused` notification whose detail names the stub's error line and `/autonomous-sdlc-harness:branch-resume feat_x`, and records `workflow disable harness-resume.yml`. A further tick with the same state (the poller re-enabled by another branch, say) sends no second notification.
- [ ] **A dispatch that fails once, then succeeds.** `STUB_FAIL_TIMES=1`. Tick 1: no notification, no disable, state carries `failures: "1"`. Tick 2 with that state: `workflow run … -f resume=pause` recorded, no notification, the branch's entry removed from the written state, and the poller disabled (nothing else waiting).
- [ ] **The deadline bound, with no carried state.** `usage_resume_at` older than `HARNESS_POLL_GIVE_UP_AFTER_MINUTES`, dispatch failing, no previous state: one notification on the first tick and a disable.
- [ ] **A new run resets the count.** Carried state for `run_id` 700 with `failures` at the limit − 1, while the branch's newest `harness run` run is 701: the failure count restarts at 1 and nothing is notified.
