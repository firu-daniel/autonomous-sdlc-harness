### 1. The probe's launcher legs never record the per-run profile in the registry

**Severity:** Must Fix (user observation 1)

**Site:** `scripts/lib/sandbox-probe/session.sh` → `sp__render`, at the closing `SP__RENDERED="$out"`. Its readers are `scripts/launch-sandboxed-gates.sh` check 8 (`profile="$(hr_registry_peek "$registry" "$branch" run_profile)"`) and the two launcher calls the probe issues: `scripts/lib/sandbox-probe/legs-local.sh`, at `cmd="bash $SP_SCRIPTS/launch-sandboxed-gates.sh $SP_CLONE $SP_T2_LABEL"` (row T3), and `scripts/lib/sandbox-probe/legs-gate-sandbox.sh`, at `cmd="bash $SP_SCRIPTS/launch-sandboxed-gates.sh $SP_CLONE $SP_GS_LABEL"` (the `gate-sandbox` leg). The producer it must mirror is `scripts/autonomous-watcher.sh` → `spawn_engine`, at `registry_set "$branch" run_profile "$settings_file"`.

**The problem, verified in the current tree.**

- Round 1's Finding 2 moved the launcher off `hr_run_profile_file` and onto the registry. When the target is not the main checkout, `launch-sandboxed-gates.sh` check 8 now reads the profile path only from `.runs[<branch>].run_profile` in `<main>/<stateDir>/autonomous_logs/registry.json`. If the field is empty or not absolute, the launcher refuses with `the run registry records no per-run profile for '<branch>': …` (exit 2).
- The only writer of that field is `spawn_engine`, and it writes it only outside job mode: `if [ "$JOB_MODE" != "1" ] && ! registry_set "$branch" run_profile "$settings_file"`.
- The probe never goes through `spawn_engine`. `sp_setup` cuts the clone through `create-worktree.sh`. That writes the clone record through `hr_clone_create_var` (`hr_registry_set "$registry" "$branch" worktree "$dir" copy_kind clone`), and then `sp__render` calls the watcher's `run_profile_render` and `run_profile_check` in a child shell. The rendered path is returned in `SP__RENDERED`, but no `registry_set` / `hr_registry_set` call appears anywhere under `scripts/lib/sandbox-probe/` or in `scripts/sandbox-probe.sh` (grep-verified). So the clone record carries `worktree`, `copy_kind` and `branch`, and no `run_profile`.
- In the clone layout, both launcher calls aim at `$SP_CLONE`, whose branch is `SP_BRANCH`. Check 6's registry read is skipped, because the target is not the main checkout. Check 8 then finds no `run_profile` and refuses. T3's grader (`sp__t3_grade`) prints `not run` unless the launcher answered `pending`, and the gate-sandbox leg reports its rows `not run` on the quoted refusal. On Linux, every probe run would therefore lose T3 and GS1–GS4/WF5 to the probe's own setup, not to a sandbox result.

**Fix.**

1. **Record the rendered profile in `sp__render`, as `spawn_engine` does.** After `sp__render` has accepted `$out` (the child shell's `run_profile_render` and `run_profile_check` both passed) and before it sets `SP__RENDERED`, write the field into the main checkout's registry from the parent shell, with the library's own locked writer:

   ```bash
   if ! hr_registry_set "$SP_REGISTRY" "$1" run_profile "$out"; then
     SP__RENDER_REFUSAL="the per-run profile for '$1' was rendered at $out, but its path could not be recorded in the run registry '$SP_REGISTRY'"
     return 1
   fi
   SP__RENDERED="$out"
   ```

   - `SP_REGISTRY` is set by `sp_setup` (`hr_state_path "$SP_MAIN" autonomous_logs/registry.json`) before either `sp__render` call. It is the same file the launcher resolves (`hr_state_path "$main" …`, with `main` placed from `$SP_SCRIPTS`), so the field lands where check 8 reads it.
   - Write it from the parent shell, not through the sourced watcher's `registry_set` in the child. The parent's `SP_REGISTRY` is the probe's own resolved path, and the child's `REGISTRY` is whatever the sourced watcher derives.
   - A failed write is a refusal, as it is in `spawn_engine` (`cannot record the per-run profile's path in the run registry`). The existing callers already turn `SP__RENDER_REFUSAL` into `sp__setup_refuse` (in `sp_setup`) and `sp_refuse "sp_extra_clone: …"` (in `sp_extra_clone`), so they need no change.
   - Re-rendering through `sp_extra_clone --existing` overwrites the field. That is the same last-spawn-wins rule as `spawn_engine`'s.

   This covers every clone `sp__render` renders: the probe clone (`sp_setup`), every `sp_extra_clone`, and the wrappers leg's control clone (`controls.sh` → `sp_ctl_clone`, through `sp_extra_clone`).

2. **Update `sp__render`'s header comment.** It now records the rendered path as the clone record's `run_profile`, as `spawn_engine` does after its launch check, so that `launch-sandboxed-gates.sh` check 8 finds it. Name the refusal it sets when that write fails.

3. **Remove it at teardown.** `sp_teardown`'s clone loop already drops each clone's whole record (step `# 2. Its registry record.`, `hr_registry_drop "$SP_REGISTRY" "$b"`), and that removes `run_profile` with it. The guard on that step is `hr_registry_peek "$SP_REGISTRY" "$b" worktree`. It still holds for every record step 1 above writes to, because `sp__render` runs only after `sp__clone_path` has read a non-empty `worktree` from the same record. Amend the step-2 comment to say the drop also removes the `run_profile` field `sp__render` wrote. Add no separate unset, because a record left without its other fields would be a half-record that nothing else writes.

4. **Confirm the job-mode arm is not refused by the wrappers leg's control-clone record.** This was checked by reading the current tree, and it holds:
   - In job mode, `sp_job_setup` sets `SP_CLONE="$SP_MAIN"`. So the `gate-sandbox` leg (a job leg: `sp_job_declare gate-sandbox "GS1,GS2,GS3,GS4,WF5"`) aims the launcher at the main checkout, and check 6 runs `hr_registry_foreign_copy_var` over the main registry. (T3 is not a job row and is printed `not run` by `sp_job_skip_clone_rows`.)
   - The only clone record in job mode is the control clone `<SP_BRANCH>_ctl`. `sp_ctl_clone` cuts it through `sp_extra_clone` (wrappers job rows P1c, CW5, P1b, CW6). After step 1 its record carries `worktree`, `copy_kind clone`, `branch`, `updated_at` and `run_profile`, and **no `status`**. Neither `hr_clone_create_var` nor anything in the probe writes one.
   - `hr_registry_foreign_copy_var` counts a record only when its `status` is `running`, `parked`, `park_loop` or `paused` (`select($s == "running" or …)`, with `$s` defaulting to `""`). So the control-clone record is not live, and the job-mode arm accepts the main checkout whether or not the wrappers leg ran first.

   Record this ground in one comment line beside the control-clone note in `sp_teardown` (*"In job mode the only registered clone is the wrappers leg's control clone …"*) or in `controls.sh` → `sp_ctl_clone`'s header: the record it leaves carries no `status`, so `launch-sandboxed-gates.sh` check 6 never reads it as a live run copy. Pin it with the fixture in step 5 (d).
