**Problem.** The user declared the rename a breaking change with no backwards compatibility: a repository wired before it is adapted by hand (remove the old workflow files, run `init --force`, create the `devscene` label). The tree still carries a compatibility path for the trigger label of a repository wired before the rename. `LEGACY_TRIGGER_LABEL = 'harness'` is exported from `cli/src/remote/githubActions.ts`. Its shell mirror in `remote-run.sh` makes `trigger` accept `harness` whenever `HARNESS_TRIGGER_LABEL` is empty. `triggerFallbackLabel` reads an old trigger workflow's `(vars.HARNESS_TRIGGER_LABEL || '<label>')` fallback so that `doctor --check-github` grades the label an earlier release's workflow falls back to. When that label is `harness`, doctor adds a note saying the workflow "was written by an earlier release and falls back to `harness`". The suites `remote-names`, `remote-trigger` and `doctor` cover all of it. `triggerFallbackLabel` is removed with the constant: its own doc comment says it exists only because "its own fallback, not DEFAULT_TRIGGER_LABEL, is what starts a run in a repository wired by an earlier release", and the workflow `init` writes today always falls back to `DEFAULT_TRIGGER_LABEL`.
