1. **`task_10_plan.md` — the new plugin module would cite this adopter's ledger by its literal path, and lean on a rule that exists only in this repository's ledger.** Rule source: `.claude/context/conventions.md` → `## Configuration is the source of truth, and it is read at run time` (*"No branch name, no directory name and no command name from any one adopter appears as a literal in `plugin/`. The corpus writes `<state_dir>` …"*), and `.claude/context/plugin.md` → `## What this layer is` (*"No adopter's value is ever a literal here."*).
   Task 10's `## The writer's revision` bullet tells the implementer to write, into `plugin/instructions/plan_review_rounds.md`, *"apply or record each Should Fix (`harness-runs/lessons.md`'s Should Fix rule, cited, not restated)"*. That has two problems. First, `harness-runs` is this checkout's `stateDir` value. Today `git grep -n "harness-runs" -- plugin` finds no match, and every existing plugin reference to the ledger is spelled `<state_dir>/lessons.md` (`plugin/agents/architecture-reviewer.md`, `plugin/agents/branch-reviewer.md`). Second, the cited rule (*"In a revision round, a reviewer's Should Fix is applied or recorded under `## Rejected findings` with its reason"*) is a line in **this repository's** run-artifact ledger. An adopter's `lessons.md` starts as the `init` template and does not contain it. So the shipped module would cite a behaviour that does not exist in any other repository, and every adopter's writers would lose the Should Fix rule the module relies on. The ledger is also a run artifact: `.claude/context/conventions.md` → `## Documents of record` says *"A rule read off `harness-runs/` describes a run, not this project."* Scope register row 67 records the same plan (*"Task 10's writer section cites it rather than restating it"*), so the index carries the defect as well.
   **Fix:** In `task_10_plan.md` → `## The writer's revision`, state the Should Fix disposition as the module's own rule, in plugin prose: each Should Fix of the round is applied or recorded under `## Rejected findings` with its reason. Remove the `harness-runs/lessons.md` citation from the module's planned text. If provenance is wanted, put it in the plan's prose, outside the shipped wording. In the story index, restate Scope register row 67's reason to match, e.g. "still true; Task 10's module now states the rule as plugin behaviour."

2. **`task_25_plan.md` — `**Verification:**` asks for two Run-gates gates.** Rule source: `plugin/instructions/unit_loop_core.md` → `## The test-run rule`, point 4 (*"No `**Verification:**` bullet, finding fix or sub-step names `<test_cmd>`, a gate script, or a test file the unit neither creates nor edits"*).
   The bullets *"`npm run validate:flow-graph` exits 0 …"* and *"`npm run validate:flow-graph:negative` exits 0 …"* are gates 3c and 3d. `scripts/run-gates.sh` runs them (`gate "3c flow graph validates" npm run validate:flow-graph`, `gate "3d flow-graph negative fixtures are refused" npm run validate:flow-graph:negative`), and `commands.test` (`bash scripts/test.sh`) runs that script. Under the rule these runs happen only once per Run gates round, in Phase G. Editing `package.json`'s scripts does not make them the unit's own test file.
   **Fix:** In `task_25_plan.md` → `**Verification:**`, replace both `npm run` bullets with checks that run no gate. For example: `jq empty` on the schema and on each new or rebuilt fixture; a `grep -n` showing that `package.json`'s `validate:flow-graph` chain names `flow-graph-check-gate-in-round.json` and that `validate:flow-graph:negative` names `flow-graph-schema-round-without-gates.json --invalid`; and a `jq` check that `flow-graph-schema-round-without-gates.json` lacks `.nodes.plan_round.gates`. Keep the existing `grep -L '"formatVersion": 2'` bullet. Leave schema validation to Phase G.

State that the gate run, and the confirmation that each fixture fails with its own id, belong to Phase G gates 3e and 3f.
