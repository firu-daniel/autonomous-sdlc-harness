# Architecture review — iteration 0

Layer placement, readiness tags and dependency direction hold across all fifteen tasks. Tasks 1 to 12 land under `cli/` (`cli/templates/` and `cli/test/`) and are tagged `cli`. Tasks 13 to 15 land under `docs/` and are tagged `general`, which ships last. No task touches `plugin/`, and no task reaches across the `cli`/`plugin` boundary. The one new test suite, `cli/test/push-branch-retry.test.mjs`, follows the *CLI test suite* name pattern, opens with its rule and builds its fixture through `cli/test/helpers/fixture.mjs`. No `**Verification:**` bullet asks for a test run that `## The test-run rule` forbids: every test file named is one the task creates or edits, and `bash scripts/typecheck.sh` is `commands.typecheck`, which is not a test run.

There are two blocking findings. In each, a task changes behaviour that a module header or a single owner states as a rule, and the task does not amend that statement in the same edit.

## Should Fix

1. **Task 6's annotation read needs a token permission that no workflow grants.** `run_not_started_var` reads `repos/{owner}/{repo}/check-runs/<job id>/annotations`. The `permissions:` blocks of `harness-run.yml`, `harness-control.yml` and `harness-resume.yml` list `contents`, `actions`, `issues` and `pull-requests`, and no `checks`. `harness-run.yml`'s header (`THE PERMISSIONS.`) states that the block *"sets every permission it does not list to `none`, so each one the job uses is listed"*. Those are the jobs that reach the helper (`collect`, `control`, `poll`). Wherever `checks` is withheld from the token, the annotation read may always fail and fall back to the conclusion. Then the "GitHub's reason" this branch exists to surface would never appear. Either add `checks: read`, with its header line, to each workflow whose job reaches `run_not_started_var`, and drop Task 12's "changes no job" accordingly, or state in Task 6 that the annotation is read only where the token permits and that the fallback is the expected path under the shipped permissions.
2. **Task 8 sends `not_started` through `notify`, which passes it to `autonomous-notify.sh`.** That script's header says *"THE EVENT VOCABULARY IS A CONTRACT"* and lists seven words. `not_started` is not one of them, so the push notification arrives under the generic title `Run (not_started) — <branch>`. Today every `notify` call in `remote-run.sh` uses `paused` or `failed`. Either add `not_started` to the notifier's vocabulary and header within Task 8, or have Task 8 send the push under the label state (`paused` / `failed`) and call `forge_report not_started` separately.
3. **Task 4's fetch contradicts the push rule Task 14 keeps byte for byte.** Task 14 keeps the sentence *"A push that loses a race fails loudly, and is never fetched, rebased or retried."* Task 3 says the script "never fetches". After Task 4, a lost race is fetched, to name the commit the remote moved to. Task 14 should qualify the rule as written: fetched only to name what moved, never merged, rebased or retried. Task 13's `### When GitHub fails or lags` should match.
