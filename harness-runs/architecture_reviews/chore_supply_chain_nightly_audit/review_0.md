# Architecture review — iteration 0

Layer placement, dependency direction and ownership hold across the plan. The `cli` tasks (1, 2) touch only `cli/package.json`, `cli/src/retrieval/models.ts` and `cli/test/`. The `general` tasks touch only catch-all paths: the root manifest and lock, `schemas/`, `scripts/`, `.github/`, `docs-retrieval-service/`, `docs/` and `ROADMAP.md`. Dependencies point upward only, from `general` to `cli`. The pin constants have one owner per path (`models.ts`, `models.py`), and Task 9 reads them from those owners instead of retyping them. `RESIDUAL` keeps its single home in `scripts/check-rendered-workflows.mjs`. The blocking findings are all the same kind: a plan that asks a unit to run a gate script.

## Must Fix

1. **Task 8 runs the gate-14 script in its Verification** — `task_8_plan.md`, `**Verification:**`. Rule source: `plugin/instructions/unit_loop_core.md` → `## The test-run rule`, points 1 and 4.
   Two bullets ask the unit to run `scripts/check-rendered-workflows.mjs`: `node scripts/check-rendered-workflows.mjs --bogus` and `node scripts/check-rendered-workflows.mjs --zizmor-online`. That file is a gate script. `commands.test` → `scripts/test.sh` → `scripts/run-gates.sh` runs it as gates 14a–14d (`gate "14a rendered workflows parse as YAML" node scripts/check-rendered-workflows.mjs`). Point 4 says a `**Verification:**` bullet never names a gate script, and running it in a mode the gate does not use is still running the script. The unit edits the file, but that does not change this: point 3's exception covers test files only.
   **Fix:** Delete both run bullets. Verify the new mode with `node --check scripts/check-rendered-workflows.mjs` plus source reads instead. The usage string and the accepted-argument list name `--zizmor-online`. No argument array carries `--gh-token` (the existing grep bullet). Exit `4` is returned on a missing token and on a missing zizmor. Move the real online run to wherever Must Fix 2 places it, and leave 14d's offline result to Phase G (the existing last bullet).

2. **Task 13's work list runs the gate-14 script** — `task_13_plan.md`, `**Work:**`, the first sub-step's bullet `npm run build`, then `node scripts/check-rendered-workflows.mjs --zizmor-online`. Rule source: `plugin/instructions/unit_loop_core.md` → `## The test-run rule`, points 1 and 4 (a sub-step never names a gate script).
   This is the same gate script as in Must Fix 1. This sub-step is how the plan meets the acceptance line "the online zizmor leg … pass[es] on the branch's final tree, run locally". A unit may not run it, so as written the plan meets that acceptance line by breaking the rule.
   **Fix:** Remove the `check-rendered-workflows.mjs --zizmor-online` bullet from Task 13's run list. Move the run of the online leg against the rendered set out of the unit loop: add it to the story index's `**Manual setup required:**` as a hand-run before merge, with the command in a fenced block on its own line. Have Task 13's `### Measured on the branch's final tree` record that leg as *"not run by the flow — hand-run step, see the story index's Manual setup"*, never as a pass. If the own-repository half needs a flow-run measurement, the unit may run zizmor on its own over `.github` (for example `uvx zizmor@1.30.1 --no-config --format=plain .github` with `GH_TOKEN` set). That command is not a gate script, and it is the command shape Task 7 already uses offline. Change Task 13's first `**Verification:**` bullet ("a command that appears verbatim in … this task's work list") to match.

3. **Task 4 runs the validator that becomes gate 3's driver, against gate 3's own fixtures** — `task_4_plan.md`, `**Verification:**`, the five `node schemas/validate.mjs …` bullets. Rule source: `plugin/instructions/unit_loop_core.md` → `## The test-run rule`, points 1, 3 and 4.
   Once this task's `package.json` edit lands, every `validate:*` script runs `node schemas/validate.mjs`, and `scripts/run-gates.sh` runs those as gates 3a–3d. So `schemas/validate.mjs` is a gate script `<test_cmd>` runs. Three of the bullets replay gate 3's own assertions: `-d examples/harness.config.json`, `-d schemas/negative/layers-no-catch-all.json --invalid` and `-s schemas/flow-graph.schema.json -d schemas/negative/flow-graph-schema-unknown-outcome.json --invalid`. The unit creates the script, but that does not admit the run. Point 3's exception is for a test file the unit creates or edits, and this script is not a test file. The task's last bullet ("This task runs the validator it created directly rather than through a gate") is exactly the run point 1 forbids.
   **Fix:** Replace the five run bullets with `node --check schemas/validate.mjs` and a source read checking each row of the contract table. Each message string and exit code must appear in the source, and `--invalid` must be accepted only with `test`. Gate 3 at Phase G grades the passed-test and valid routes. If the plan wants behavioural evidence for the `failed test` and `Cannot find data file` routes, which no gate fixture reaches (the third `Top risks:` entry), the task can create a test file. That file builds its schema and data fixtures under the system temp directory, never in this checkout (`.claude/context/conventions.md` → `## The testing bar`). The unit then runs only that file through the single-file command (point 3). Add it to `### Targets`.
