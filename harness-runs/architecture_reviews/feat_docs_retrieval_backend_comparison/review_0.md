## Must Fix

1. **The Python database-URL default policy gets a second home in `python-backend.mjs` and `mcp-backend-pass.mjs`** — offending files: `task_3_plan.md` (Work → **Header and preconditions.**) and `task_5_plan.md` (Work → **Spawn and cold start.**). Rule source: `.claude/context/conventions.md` → `### Where a new responsibility goes` — *"A responsibility that already has a home does not get a second one"* and *"Before adding a copy of anything, grep for it."*, whose worked cost is `cli/src/core/repoPaths.ts`.
   Task 3 has the module work out the connection string itself: *"`process.env[PYTHON_DATABASE_URL_VARIABLE]` when non-empty, else `PYTHON_DEFAULT_DATABASE_URL`, which is the launcher's own default policy"*. Task 5 repeats that: *"`PYTHON_DATABASE_URL_VARIABLE`, defaulting to `PYTHON_DEFAULT_DATABASE_URL`, both imported"*. That policy already has an exported owner, `cli/src/retrieval/pythonBackend.ts` → `pythonDatabaseUrl(serverEnv)`. Its body is exactly that rule (a non-empty string under `PYTHON_DATABASE_URL_VARIABLE`, else `PYTHON_DEFAULT_DATABASE_URL`), and `cli/src/doctor/checks.ts` already consumes it. The plan imports the two constants the function is built from but not the function. So two eval modules each get a private copy of the decision, and they drift silently if the launcher's rule ever changes. That is the failure the `repoPaths.ts` header records.
   **Fix:** In `task_3_plan.md`, add `pythonDatabaseUrl` to the list of names imported from `cli/dist/retrieval/pythonBackend.js`. Replace the hand-built rule with "the database URL is `pythonDatabaseUrl(process.env)`", and keep the sentence that it is passed in the child environment only and never written into a message or return value. Make the same replacement in `task_5_plan.md` → **Spawn and cold start.**: the child env's `PYTHON_DATABASE_URL_VARIABLE` value is `pythonDatabaseUrl(process.env)`, imported. Drop the separate `PYTHON_DEFAULT_DATABASE_URL` import from both wherever it was only feeding the copied rule. Update the story index's first **Manual setup required** bullet, which says the runner *"defaults to exactly as the launcher does"*, so it cites `pythonDatabaseUrl` as the one place that default is decided.

2. **Task 7 copies `loadModels`'s embedder loading options into `vector-agreement.mjs` on a justification nothing authorizes** — offending file: `task_7_plan.md` (Work → **The fp32 embedder.**), with the story index (`feat_docs_retrieval_backend_comparison_story_plan.md` → `## Context`, *"Every task is in the `general` layer"*, and `## Phase 2 Readiness — Ordered Fix List`). Rule source: `.claude/context/conventions.md` → `### Where a new responsibility goes` (*"A responsibility that already has a home does not get a second one"*; *"Before adding a copy of anything, grep for it"*). Also `.claude/context/cli.md` → `## How a module in this layer is written` → *"One string, one producer"*.
   The work bullet builds `pipeline('feature-extraction', EMBEDDING_MODEL, { dtype: 'fp32' })` and embeds with a retyped `{ pooling: 'cls', normalize: true }`, *"`models.ts` → `loadModels`'s options with only the dtype changed"*. The embedder's loading parameters are owned by `cli/src/retrieval/models.ts`. Its `MODEL_VERSION` doc comment, *"Bumped by hand when any loading parameter above changes, so the embedder's `id` changes with it"*, makes those parameters part of the embedder's identity. The plan defends the copy with *"`MODEL_DTYPE` is not a parameter of `models.ts`, and this branch changes nothing under `cli/src`"*, plus a header note asking a future editor to carry changes across by hand. Neither the task prompt nor the story's own constraints forbid a `cli/src` change. The prompt's constraints are *"No change to the Python backend's search behaviour"* and *"The TypeScript path through the runner must produce the same results"*, and an export that leaves every value unchanged breaks neither. So the justification is self-imposed and does not waive the rule. A by-hand sync note is the drift the rule exists to prevent: if pooling or normalisation changes in `loadModels`, the matched-precision leg silently measures a different embedder from the one the TypeScript backend runs, and that would invalidate the very divergence-source measurement the write-up rests on.
   **Fix:** Add a new **`cli`-layer task** ahead of Task 7. In `cli/src/retrieval/models.ts`, it exports the embedder's extraction options as one constant (for example `EMBEDDING_EXTRACT_OPTIONS = { pooling: 'cls', normalize: true }`). `loadModels` uses that constant itself, so no value changes and the embedder `id` is unchanged. The task also amends the module's doc comment to say the constant exists for the eval's matched-precision leg. Rewrite `task_7_plan.md` → **The fp32 embedder.** to import that constant from `cli/dist/retrieval/models.js` beside `EMBEDDING_MODEL`. Only `dtype: 'fp32'` (and the scratch `env.cacheDir` / `env.allowRemoteModels = false`) is local to the leg. Delete the header sentences that justify the copy. Add the new task to `Depends on:`. In the story index, add the new entry to `## Phase 2 Readiness — Ordered Fix List` with `_(layer: cli)_`, renumbering as needed. Correct the `## Context` sentence that every task is in the `general` layer. List `cli/src/retrieval/models.ts` among the touched files wherever the story states what changes (it still changes neither backend's search behaviour).
