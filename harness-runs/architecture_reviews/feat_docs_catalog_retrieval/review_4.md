## Must Fix

1. **`docs serve` opens a second stdout writer beside `Reporter`, and the plan never declares the exception** — `task_8_plan.md` (the `server.ts` `serveDocs` bullet and the `docs.ts` `docs serve` bullet), with the story index `feat_docs_catalog_retrieval_story_plan.md` (`## Corpus staleness`).
   Rule: `.claude/context/conventions.md` → `## Output, logging and errors`: *"**The CLI has one output surface: `Reporter` (`cli/src/core/report.ts`).** Every command writes through it"*. The document gives three reasons this matters: *"`--quiet` behaves the same everywhere, the write engine's action log and the human-readable log are one log, and the output is plain ASCII"*. `cli/src/core/report.ts`'s header opens with *"The CLI's single output surface."* `.claude/context/cli.md` → `## How a module in this layer is written` says a module *"that needs to say something takes a reporter"*. The docs-retrieval carve-out in `## The stack…` covers optional **dependencies** only (*"The carve-out covers retrieval and nothing else"*). It does not cover the output surface.
   Task 8 has `serveDocs` start the MCP SDK's stdio transport, and that transport writes JSON-RPC frames straight to the process's stdout. Nothing in `cli/src` writes to stdout outside `Reporter` today: `grep -rn "process.stdout" cli/src` is empty, and only `cli.ts` and `report.ts` name `console`. `--quiet` cannot suppress those frames, and they are not plain ASCII, because they carry snippets. So this is a real second output surface. The plan handles it only as an operating rule inside the task (*"Nothing may write to stdout except the transport"*). Neither the monopoly's owner nor the plan records it as an exception. This is the same kind of gap iteration 0 raised for the writer monopoly, and the plan closed that one by declaring the exception in `cli/src/core/writer.ts`'s header (Task 5) and raising it in `## Corpus staleness`. Without a declaration, the Task 8 implementer (who reads only `task_8_plan.md`) ships an undeclared bypass. The Task 8 reviewer also has no header text to check `server.ts` against.
   **Fix:** In `task_8_plan.md`, add `cli/src/core/report.ts` to Targets. Add a Work bullet to extend that module's header with one named exception: while `docs serve` runs, the process's stdout belongs to the MCP stdio transport started by `cli/src/retrieval/server.ts` → `serveDocs`, and to nothing else. That module is the **one** place a transport writes to stdout. `Reporter` still carries every narration and warning line, on stderr only, and `--quiet` and the plain-ASCII guarantee do not apply to the protocol frames. Say in that bullet that `.claude/context/conventions.md` → `## Output, logging and errors` does not record the exception yet, and that it is raised for a supervised amendment. Have `server.ts`'s header point at that `report.ts` paragraph instead of arguing the exception itself. Add a Verification line: `grep -n "docs serve\|serveDocs" cli/src/core/report.ts` finds the header clause. In the story index's `## Corpus staleness`, add a `stale-rule` entry for `.claude/context/conventions.md` → `## Output, logging and errors`. It names the one module (`cli/src/retrieval/server.ts`) and the one sub-verb (`docs serve`) whose stdout is the MCP transport rather than `Reporter`, and it gives the restatement and the route (a supervised `/harness-analyze` re-run or a hand edit).
