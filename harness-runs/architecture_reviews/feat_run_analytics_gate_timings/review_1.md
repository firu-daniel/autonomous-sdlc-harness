That means building `<state_dir>/test_run_logs/<sanitized branch>` from three parts in `run-analytics.sh`. It names two callers, `run-test-suite.sh` and `launch-sandboxed-gates.sh`, and the function's own `Callers:` line names the same two. A third copy of the path in the driver is a second home for the lane path, and nothing would keep it in step with `hr_test_run_lane_dir`. The plan also adds a third reader of the lane and the label pattern without amending the lib header that lists the readers.
   **Fix:** In `task_3_plan.md`:
   - In **The header** → `GATE ROUNDS` → **The lane**, and in **Discovery** → *"Resolve the lane"*, resolve the lane with `hr_test_run_lane_dir "<state_dir>" "$branch"`. Take `<state_dir>` from the library's state-dir resolver, as `run-test-suite.sh` does (`hr_state_dir`), and anchor it to the checkout root the script already holds. A non-zero return means no rounds, silently. Do not assemble the path from `hr_state_path`, `HR_TEST_RUN_LOG_SUBDIR` and `hr_sanitize_branch`. Keep `HR_TEST_RUN_LABEL_PATTERN` as the label check.
   - Add `cli/templates/scripts/lib/harness-run-lib.sh` (comments only) to **Targets**, with a work bullet that amends `THE RUN GATES LANE` and `hr_test_run_lane_dir`'s `Callers:` line to name `run-analytics.sh` as a third caller. It is a read-only reader of finished rounds' `.verdict` and record files, and it takes the lane directory and the label pattern from here.
   - Add a **Verification:** text check that `run-analytics.sh` calls `hr_test_run_lane_dir`, and that both library comments name it.
