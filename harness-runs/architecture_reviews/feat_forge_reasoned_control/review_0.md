## Must Fix

1. **The mention agent's system prompt is scheduled into the `cli` layer, which the conventions documents bar from carrying agent prose** — offending files: `task_2_plan.md` (the whole task: target `cli/templates/scripts/prompts/mention-decision.md`, the new `prompts` subdir of `OUTER_LOOP_SCRIPTS`, tag `_(layer: cli)_`). The same placement is assumed by `task_3_plan.md` (`"$script_dir/prompts/mention-decision.md"` read as `--system-prompt`, step (c)), `task_10_plan.md` (the `docs/watcher.md` row) and the story index `<branch>_story_plan.md` → `## Context`, *Where the agent's prompt lives*, plus scope-register rows 31, 32, 34, 44 and 45.
   Rule sources:
   - `.claude/context/cli.md` → `## What this layer owns, and what it is not`: *"**Is not:** the process assets. Agent, command, instruction and hook contracts are the `plugin` layer's. A task that has drifted into writing prose an agent reads, or into changing a dispatch contract, has left this layer."*
   - `.claude/context/conventions.md` → `### Where a new responsibility goes`: *"a contract an agent or a flow reads → `plugin/agents/`, `plugin/commands/` or `plugin/instructions/`"*.

   `mention-decision.md` is an agent's system prompt. It holds the role, the trust boundary, the reading order and the decision contract, so it is exactly "prose an agent reads". The plan admits the conflict (story `## Context`; Task 2's *Why here and not in `plugin/`*; register row 45). Its answer is to schedule the placement anyway and raise a `stale-rule` entry in `## Corpus staleness`. A `stale-rule` entry is a recommendation for supervised follow-up, and it does not license an implementing run to break the rule it names in the meantime. No architecture check here carries an exception carve-out.

   The justification also does not hold against the tree. The plan says a plugin agent definition "would not be reachable" from the control job because that job "carries no version pin and installs no plugin". That describes the control job as it stands today, and Task 6 already edits that job to install Node and the `claude` CLI. The sibling workflow `cli/templates/github/workflows/harness-run.yml` already shows how a job reaches the plugin: its header's `THE PLUGIN PIN` paragraph and its `Install the pinned plugin` step (*"claude plugin marketplace add ./harness-marketplace && claude plugin install autonomous-sdlc-harness@autonomous-sdlc-harness"*), pinned through `HARNESS_CLI_VERSION`. The coupling that would result is the established contract one, where a shipped script hands a plugin asset to `claude` and nothing imports or sources across the boundary. It is not a new cross-half runtime import (`.claude/context/conventions.md` → `## The layers`, *"coupled by contract, not by import"*).

   **Fix:** Re-plan the prompt's home. Take one of the two routes below; do not keep the `cli`-layer placement with only a `stale-rule` note.
   - **(a) Relocate it to the `plugin` layer.**
     - Replace Task 2 with a `plugin`-layer task that adds `plugin/agents/<kebab-case-role>.md` as an agent definition. It needs the closed frontmatter set `name` (equal to the basename), `description`, `tools: Read, Grep, Glob` and `model: inherit`, plus the sections the `plugin` layer requires: `## Resolved values`, `## Invocation contract`, `## Output contract` and `## Read first` (`.claude/context/plugin.md` → `## Frontmatter`, `## The sections an asset carries`; `.claude/context/conventions.md` → `## What accompanies a new unit of each kind`, the agent-definition row).
     - Order it in the configured bottom-up order (`cli`, `plugin`, `general`) after the `cli` tasks it depends on and before `general`, re-numbering the readiness list.
     - Have Task 6 add the pinned-plugin install to the control job's comment path, mirroring `harness-run.yml`'s `Install the pinned plugin` step and its pin. Have Task 3 run that agent instead of `--system-prompt "<file content>"`.
     - Drop the `OUTER_LOOP_SCRIPTS` `prompts` row, the `subdir` widening and the README and `docs/watcher.md` enumeration edits (register rows 31, 32, 34 and 44 go back to `no-change` or are removed). Remove register row 45's `stale-rule` premise.
   - **(b) If the writer holds that the plugin cannot be made reachable from the control job, do not schedule the placement.** Raise it in `## Questions` to the maintainer: whether agent prose may ship under `cli/templates/scripts/`, against `.claude/context/cli.md` → `## What this layer owns, and what it is not` and `.claude/context/conventions.md` → `### Where a new responsibility goes`. State the evidence on both sides, including `harness-run.yml`'s pinned-plugin install, and leave Tasks 2, 3 and 10's dependent parts unscheduled until it is answered.
