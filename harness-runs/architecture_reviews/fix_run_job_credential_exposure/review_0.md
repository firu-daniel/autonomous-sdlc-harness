1. **The strip set's profile reader becomes a second, private copy of an answer the gate launcher already computes** — `task_4_plan.md` (and `task_2_plan.md`, which owns the shared library's new functions). Rule: `.claude/context/conventions.md` → `### Where a new responsibility goes` → *"A responsibility that already has a home does not get a second one"* and *"Before adding a copy of anything, grep for it"*. The library applies the same rule to profile reads: `cli/templates/scripts/lib/harness-run-lib.sh` → `hr_profile_deny_paths` is the one reader of a profile's `.sandbox.filesystem.denyWrite`, already called by `autonomous-watcher.sh` → `spawn_engine`, and `hr_json_single_object` is *"THE ONE HOME of the test, so a profile one caller accepts the other cannot refuse"*.
   Task 4's strip set is *"every `sandbox.credentials.envVars[].name` of `$settings_file` … read with `jq`"*, written inline in `spawn_engine`. The tree already reads exactly that list: `cli/templates/scripts/launch-sandboxed-gates.sh` → `lsg_bwrap_args_var`, the `jq -r '(.sandbox.credentials.envVars // []) | if type == "array" then .[] | objects | .name | strings | select(length > 0 and (contains("\n") | not)) else error("envVars is not a list") end'` read, which turns each name into a `--unsetenv`. With two copies, the two unsandboxed paths that unset the profile's credential names (the gate worker and the session) can disagree about which names those are, or about which profile shape they refuse. That divergence is the kind `cli/src/core/repoPaths.ts`'s header records. Task 2 says it is the one owner of what *"the later tasks share"*, but it does not take this reader.
   **Fix:** In `task_2_plan.md`, add to the contract table a library function in the `hr_profile_deny_paths` form, for example `hr_profile_env_var_names <profile>`. It prints every `.sandbox.credentials.envVars[].name` one per line, using the launcher's filter verbatim (objects only, string names, non-empty, no newline), and returns 1, printing nothing, when the profile is unreadable or `envVars` is not a list. Add a case for it to `cli/test/credential-scan-lib.test.mjs`, and move `launch-sandboxed-gates.sh` → `lsg_bwrap_args_var` onto it. Add that file to Task 2's `### Targets`: no other task edits it. List both callers in the function's header comment, as `hr_profile_deny_paths` does. In `task_4_plan.md`, make the strip set *"`hr_profile_env_var_names "$settings_file"`'s output minus `ANTHROPIC_API_KEY` and `CLAUDE_CODE_OAUTH_TOKEN`, plus `SESSION_ENV_STRIP_EXTRA`"*. Map a return of 1 to the `spawn_refuse` refusal. Remove the inline `jq` read, and add the function to Task 4's `**Depends on:**` list of Task 2 functions.

2. **`hr_session_pass_env` is planned as its own read of `harness.config.json`, beside the library's single configuration load** — `task_2_plan.md`. Rule: `.claude/context/conventions.md` → `### Where a new responsibility goes` (*"A responsibility that already has a home does not get a second one"*), and `.claude/context/cli.md` → `## What "done" means here` → *"A reviewer holds a change to its module's own header"*. The header of `cli/templates/scripts/lib/harness-run-lib.sh` states the home: *"`hr_config_load` runs ONE `jq` and holds the result in shell variables"* (THE CACHE IS PER PROCESS…). The load's own comment explains why that matters: a per-key read *"would have applied its filter to every document and silently unioned them"*. Every configuration reader in the file goes through `hr_config_load` and `hr_cfg_scalar_var` / `hr_cfg_list_var`, including the nearest neighbour, `hr_sandbox_opted_out`.
   The contract has `hr_session_pass_env` *"reading with `jq` the way the library's other configuration readers do"* and exiting 2 *"when the configuration cannot be read or parsed"*. Nothing in the plan names `hr_config_load`, so a direct `jq '.sandbox.passEnv[]' harness.config.json` meets the plan as written. That read would accept a multi-document or `defaultBranch`-less file that `hr_config_load` refuses. It would also skip the watcher's per-tick `hr_config_reset` cache, a second parse of the same file with its own refusal set.
   **Fix:** In `task_2_plan.md`, change the `hr_session_pass_env` row and its Work bullet so the function adds one `l("sandbox.passEnv"; try .sandbox.passEnv catch null)` line to `hr_config_load`'s single `jq` program. Build the function on `hr_config_load "$main_top"` (return 2 → exit 2; return 1, no configuration → exit 2 as well, since the watcher's main checkout must have one) and `hr_cfg_list_var "sandbox.passEnv"`, keeping the pattern filter on each element. State in its header that it reads through the cache like `hr_sandbox_opted_out`. Keep the `jq 1.5` floor note true: `l()` is already in the program, so no new construct is added. Add a test case showing that a two-document `harness.config.json` exits 2.
