Task 2 tells the implementer to build `forge_progress_stopped` with "the same paginated call `forge_progress` makes", the same newest-bot-comment-by-last-line pick, and the temp-file handling "as `forge_progress` does". That is a second copy of the selection rule — which login is the bot, how the marker line is found, how the newest one is chosen — and Task 3 then calls the copy once per pull request on the deletion path. When either copy changes (a different bot login under `HARNESS_GIT_TOKEN`, a CR-tolerant marker match, a different tie-break), the other drifts silently: the stop would rewrite a different comment from the one the progress pass edits, or none, and no compile step or existing test ties the two together.
   **Fix:** In `task_2_plan.md`, replace steps 2 and 3 with one shared lookup that both functions call. Add a function (for example `forge_progress_comment_var <pr> <marker-matcher>`, placed before `forge_progress`) that makes the paginated listing and the bot/last-line/`max_by(.id)` selection once and sets the picked comment's id and body (or empty, with `GH_ERR` on a refused listing). Change `forge_progress` to call it, keeping its observable behaviour byte-for-byte (the same warning lines and the same `same`/`differs` decision made by the caller), and have `forge_progress_stopped` call it with a matcher that accepts the bare marker or the ` round=<n>` form. Extend the task's `### Targets` to name the `forge_progress` edit, and its **Verification:** to state that `cli/test/remote-progress.test.mjs`'s existing `forge_progress` cases still pass unchanged (that file is already edited by this task, so running it stays within the test-run rule).
