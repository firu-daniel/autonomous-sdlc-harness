# Architecture review — iteration 0

## Must Fix

1. **Task 5 types the plugin name into a rendered template when the owner's constant is available as a `{{pluginName}}` token** — `task_5_plan.md` (and `task_2_plan.md`, which owns the render call in `cli/src/generators/claudeContext.ts`). Rule source: `.claude/context/conventions.md` → `## Configuration is the source of truth, and it is read at run time` → *"The shared constants have owners, and a value is imported from its owner rather than retyped"*, together with the owner's own header at `cli/src/generators/projectSettings.ts` → the `PLUGIN_NAME` doc comment.
   Task 5's work bullet for `cli/templates/claude/CLAUDE.md` changes the `/harness-analyze` placeholder lines and the `/branch-*` / `/harness-*` family names in the change-request fence to the literal `/autonomous-sdlc-harness:…`, and says "Change no `{{…}}` token". This template is rendered, not copied verbatim: `claudeContext.ts` renders it through `render('CLAUDE.md', { projectName, setupBanner, routingRows, stateDir })` with `assertNoneSurvive: true`. `PLUGIN_NAME` in `projectSettings.ts` owns the plugin name. Its header already says why the sibling template `harness-task-offer.md` gets `{{pluginName}}` instead of a literal: *"a shipped literal there would survive a rename in every adopter's checkout with nothing reporting it."* The same reasoning applies to `CLAUDE.md`, which lives in the same directory and is rendered by the same generator. As planned, Task 5 would add a second, unreported copy of the plugin name to a file every adopter receives. Meanwhile Task 2, Task 3 and Task 4 take the prefix from `PLUGIN_NAME`, so the plan disagrees with itself about who owns the name.
   **Fix:** In `task_5_plan.md`, spell every qualified site in `cli/templates/claude/CLAUDE.md` as `/{{pluginName}}:harness-analyze`, `/{{pluginName}}:branch-*` and `/{{pluginName}}:harness-*`. Replace "Change no `{{…}}` token" with "Add only the `{{pluginName}}` token; change no existing token". Add `cli/src/generators/claudeContext.ts` to Task 5's targets with a bullet that adds `pluginName: PLUGIN_NAME` to the `render('CLAUDE.md', …)` variables. `PLUGIN_NAME` is already imported there, and the every-token-has-a-value check needs the value. Alternatively, move that one-line edit into `task_2_plan.md`'s `claudeContext.ts` bullet and name the dependency in Task 5. Update Task 5's verification: the regex grep over the template must still print nothing, and `bash scripts/test.sh` must show that a generated `.claude/CLAUDE.md` in a fixture reads `/autonomous-sdlc-harness:…`.

2. **Task 2 leaves the owner of the plugin name unstated for `signals.ts`'s `flat` fallback warning** — `task_2_plan.md`. Rule source: `.claude/context/conventions.md` → `## Configuration is the source of truth, and it is read at run time` → *"a value is imported from its owner rather than retyped"*, and the `PLUGIN_NAME` doc comment in `cli/src/generators/projectSettings.ts`.
   The `cli/src/detect/signals.ts` bullet only says "Qualify the `flat` fallback warning". That warning is a module-level string constant, `'unrecognised layout — using the `flat` preset; run `/harness-analyze` to refine the layer profile'`, and an implementer following the bullet as written would retype `autonomous-sdlc-harness` inside it. Task 3 requires the same edit in the neighbouring `detect/presets.ts` to import `PLUGIN_NAME` from `../generators/projectSettings.js` *"so that `projectSettings.ts` stays the single owner of the plugin name"*. Task 4 requires it for `doctor/checks.ts`, and Task 2 itself does it for `init.ts` and `claudeContext.ts`. `signals.ts` is the only output-string site in the `cli` layer where the plan does not say where the prefix comes from.
   **Fix:** In `task_2_plan.md`, change the `signals.ts` bullet so the warning is built as a template literal from `PLUGIN_NAME`, imported from `../generators/projectSettings.js` exactly as Task 3 does for `presets.ts`. Comments may stay literal. Add a verification line: `grep -n "autonomous-sdlc-harness" cli/src/detect/signals.ts` prints only comment lines.

## Should Fix

1. **The watcher template would carry an undeclared mirror of `PLUGIN_NAME` if the route is `prefixed`** — `task_1_plan.md`. Rule source: `.claude/context/conventions.md` → `## Configuration is the source of truth, and it is read at run time`, the bullet on persisted keys: *"a mirror the header does not declare is a defect"*. That bullet is stated for machine-registry keys. It is applied here by analogy, which is why this is not a Must Fix.
   `cli/templates/scripts/autonomous-watcher.sh` is copied byte for byte with no substitution, so under route `prefixed` a literal plugin name is unavoidable. Nothing in the owner's header would record that this copy exists, so renaming the plugin would silently break the watcher's launch.
   **Fix:** If Task 1's measurement chooses `prefixed`, add a bullet that appends one sentence to the `PLUGIN_NAME` doc comment in `cli/src/generators/projectSettings.ts`. The sentence names `cli/templates/scripts/autonomous-watcher.sh` → the `ENGINE_COMMAND_*` assignments as the one verbatim-copied mirror of the name. The owner's header then records every copy it cannot substitute. Under route `bare`, add nothing.
