# architecture_user_review_reviews/

One `<branch>/review_{iteration}.md` per iteration, holding the architecture reviewer's plan-gate review of a hands-on-review fix plan rather than of a task plan: read by the fix-plan writer on the next iteration. One `<branch>` subdirectory holds one branch's set. The fix-plan index plays the role the story index plays at the task-plan gate, and its per-finding folder the role of the per-task files. `{iteration}` is the **next free** index: before each reviewer dispatch, `${CLAUDE_PLUGIN_ROOT}/instructions/user_review_fix_plan_writing_instructions_core.md` → `## Flow` step 8 lists `<branch>/` and passes one past the highest `review_<n>.md` already there, or `0` when the directory is absent or holds none. The gate's own counter only caps the loop and labels the heartbeat; it never names a file. A **re-entered** gate, and a later fix-plan round on the same branch, therefore adds files beside the earlier ones and writes over none of them.

The writer is the architecture reviewer, the same agent and the same layering lens that grades a task plan into `<state_dir>/architecture_reviews/`; it is told which of the two it is holding by the paths it is passed, never by a flag. The reader is the fix-plan writer, re-dispatched in revision mode with the path to the newest file and expected to apply its Must Fix items to the fix-plan index or to the per-finding files they name. The reviewer creates the branch directory itself and only when it has findings to write, so a fix plan whose architecture was clean leaves this directory empty.

A file appears only for a failed gate, and the gate sits early: the drafted fix plan is graded **before** anyone approves it and before a single one of its fixes is implemented. Files stop at convergence or at the fifth iteration, where the flow escalates with the latest path here. No file supersedes an earlier one, and the numbered set is the gate's **whole** history on the branch: step 7's FAIL path sends the revised plan back into this gate, and that re-entry, like every later fix-plan round, continues the series rather than restarting it. The whole directory is committed with the branch, since no ignore rule reaches it: the autonomous flow commits each round's new files at convergence, and the supervised flow names them for the human's commit.

The mistake worth naming is writing for the orchestrator. The flow deliberately does **not** read this file to judge the review's quality; it parses the verdict line, and on FAIL it hands the path straight to the fix-plan writer's revision dispatch. So the only consumer of the prose is that writer, and a finding stated as an observation rather than as a concrete change to a named plan file gives it nothing to apply — the gate fails again on the same point, and nothing in the loop notices why.
