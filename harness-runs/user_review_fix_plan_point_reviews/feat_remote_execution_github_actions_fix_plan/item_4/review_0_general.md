> File name note: the dispatched `findings_folder` already holds `review_0.md` and `review_1.md`, both written by the `plugin` layer's review loop for this same item. Writing this layer's iteration-0 findings to `review_0.md` would have overwritten the plugin layer's file. This file uses a `review_0_general.md` name so that nothing is overwritten. The per-layer loops share one folder and one `review_{iteration}.md` naming scheme, and that collision is the orchestrator's to settle.

Scope: the `general` (catch-all) layer's files in the uncommitted set, which are `docs/remote-execution.md` and `docs/development.md`. The `cli/` and `plugin/` files are cross-checked only where the docs quote them.

## Must Fix
1. **Gate 12 observation (x), as written, fails the job before the run starts, so the skip it is meant to record is never reached** — `docs/development.md` (`## 5. Verifying a change` → Gate 12, **(x) The interactive-test phase is skipped.**) — "npx --yes autonomous-sdlc-harness@<version> config set phases.qa true"
   The procedure is `config set phases.qa true`, then `git add harness.config.json`, commit, push, drop a task. `config set` writes only `harness.config.json` (`cli/src/commands/config.ts`, module header: "It writes nothing but `harness.config.json`"). With `phases.qa` true, `init` adds rules for the QA credentials file and the QA browser artifacts to its managed `.gitignore` block (`cli/src/generators/repoRoot.ts` → `writeRepoRootFiles`, `qaCredentialsPath` / `qaBrowserArtifacts`). The job runs `init --plugin-root-entries` and then fails on any tracked-file change (`cli/templates/github/workflows/harness-run.yml`: `git status --porcelain --untracked-files=no` → "::error::init … changed tracked files. Run '… init' locally and commit the result."). So a maintainer who follows (x) as written sees the job fail at the permission-profile step, and never sees the `E` `[-]` / `remote-skipped: qa` outcome. They would record a gate failure that comes from the procedure, not from the harness. The gate's own **Setup** already follows the correct pattern (`config set …`, then `init`, then `git add <each path the two init runs reported writing>`), and (x) leaves that pattern out.
   Confirmed by a probe: `bash scripts/scratch-run.sh harness-runs/scratch/gate12_qa_init_probe.mjs`. In a throwaway repository under `os.tmpdir()` it ran `init`, committed, ran `config set phases.qa true`, committed only `harness.config.json`, then ran `init` again. The result was `git status --porcelain --untracked-files=no` → `" M .gitignore\n"`, and `git diff --stat` → `.gitignore | 26 ++++++++++++++++++++++++++`. The probe ran plain `init`, not `init --plugin-root-entries`. That flag only changes the permission profile's entries (`cli/src/commands/init.ts`, `pluginRootEntries`). This was established by reading the code, not by running it.
   **Fix:** Between the `config set` block and the `git add` block, add a fenced `npx --yes autonomous-sdlc-harness@<version> init`. Replace `git add harness.config.json` with `git add <each path the init run reported writing>` plus `harness.config.json`, which is at minimum `.gitignore`, following the Setup's own wording. Optionally add one sentence saying why: the job fails when its own `init` changes a tracked file.
