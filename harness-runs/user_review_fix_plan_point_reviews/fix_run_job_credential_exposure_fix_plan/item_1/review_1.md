# general review — ### 1. `push-branch.sh` refuses a workflow-file change only in a GitHub job; a local unattended run still pushes it — iteration 1

## Must Fix
1. **`docs/github-issue-trigger.md` still sends a workflow-editing task to a local run** — `docs/github-issue-trigger.md` (bullet `**A task that edits `.github/workflows/*` cannot push that edit with the job's own token.**`) — "Such a task cannot push from a job at all, because the job pushes only with `github.token`, so it runs locally"
   The unit makes `push-branch.sh` refuse a workflow-file change in every unattended run, local or in a job (`cli/templates/scripts/push-branch.sh` → `NO UNATTENDED PUSH CHANGES A WORKFLOW FILE.`). This bullet still tells the operator to run such a task locally. An operator who follows it starts a local unattended run, and that run is now refused at its first push and marked `failed`. The bullet also cites `remote-execution.md` → `## 11. Security`, **The issue trigger**. This unit rewrote that bullet to say "supervised-only", so the two documents now contradict each other. The fix plan's "Other citations … job-only scope, which would otherwise be false" list did not name this file, but the defect is the one that list exists to remove. Found with `git grep -nE "locally" -- docs/github-issue-trigger.md`, line 198.
   **Fix:** Replace "Such a task cannot push from a job at all, because the job pushes only with `github.token`, so it runs locally" with something like "Workflow edits are supervised-only: `push-branch.sh` refuses such a commit's first push in every unattended run, local or in a job, and in a job `github.token` could not push it anyway; make the edit in a supervised session". Keep the citation, and keep the rest of the bullet (the `failed` marking, the annotation and the S1 citation).

2. **`docs/github-run-control.md` step 9 still says a workflow-editing task "runs locally"** — `docs/github-run-control.md` (step `9. Set `HARNESS_GIT_TOKEN` …`) — "It does not let a job push a `.github/workflows/*` edit: such a task runs locally"
   This is the same stale job-only scope. An operator setting up `HARNESS_GIT_TOKEN` reads it and moves a workflow-editing task to a local run, which `push-branch.sh` now refuses. Its cited target, `remote-execution.md` → **The job's credential design.**, no longer says anything about a local run. Found with `git grep -nE "locally" -- docs/github-run-control.md`, line 23.
   **Fix:** Change "such a task runs locally" to "workflow edits are supervised-only, refused by `push-branch.sh` in every unattended run; make them in a supervised session". Point the citation at `## 11. Security`, **The issue trigger**, which is where the bullet stating the rule now lives, or keep the current target and add that one.

## Should Fix
1. **Roadmap item 35 still frames a GitHub "accept" as grounds to narrow the refusal** — `docs/development.md` (`## 6.` roadmap table, row `| 35 |`) — "a result that GitHub accepts it is a follow-up fix narrowing that check"
   Before this unit, the merge case of the workflow-file refusal rested only on whether `github.token` could push it, so a GitHub "accept" really did justify narrowing the check. The unit makes the refusal supervised-only in every mode, for a reason unrelated to the job token: no unattended run may change CI. `docs/remote-execution.md`'s issue-trigger bullet was re-scoped to match ("whether GitHub would refuse that push from a job"), and this row was not. A maintainer who later measures item 35 and sees GitHub accept the merge would take the row's instruction and narrow the refusal. That would undo a decision the row does not mention. The row's wording also calls it "the first in-session push" with no mode, which still reads correctly.
   **Fix:** Rewrite the clause to: "a result that GitHub accepts it changes only the job's additional reason, not the supervised-only refusal". Alternatively, drop "is a follow-up fix narrowing that check".
