# cli review — 2. Adopter-facing surfaces say "docs retrieval" where adopters know "RAG" — iteration 0

## Should Fix

1. **The expansion of "RAG" landed in a string `doctor` never prints** — `cli/src/doctor/checks.ts` (`RETRIEVAL_DEPENDENCIES_CHECK`) — "The first of the three retrieval checks in registration order, and so the one that expands the term for the whole report: the other two say \"RAG\" alone"
   The comment states a rendering behaviour the report does not have. `cli/src/commands/doctor.ts` → the `runChecks(checks)` loop composes every line as `` `${STATUS_LABEL[result.status]}  ${result.id.padEnd(width)}  ${result.detail}` `` — status, **id**, detail. No check `title` reaches the output on any path: `runChecks` copies `title` onto `CheckResult` (`cli/src/doctor/checks.ts` → `runChecks`) and a grep over `cli/src` for `.title` finds no reader of that field, and the thrown-check path names the check by its id too. Confirmed by reading those two sites, not by running `doctor` against a retrieval-on fixture.
   Consequence: in the report an adopter actually reads, the term is never expanded — the three retrieval lines say `the RAG runtime is missing …`, `every model file RAG loads offline is cached in …`, `the RAG index did not build in memory: …` and `…so no RAG library is expected…`, all bare. The plan's rule ("expand it in the first of the three in registration order, so the other two can say RAG alone") is satisfied only in text nothing renders. The `title:` renames themselves are harmless and can stay.
   **Fix:** expand the term in the first *rendered* retrieval line instead — `RETRIEVAL_DEPENDENCIES_CHECK`'s own `pass`/`fail` details, which are first in `CHECKS` registration order: `the RAG (docs retrieval) runtime is installed at …` and `the RAG (docs retrieval) runtime at … is missing …`. Then correct the comment above the title to say what is true — that the titles are carried but not printed, and that the expansion lives in this check's detail because it is the first retrieval line of the report.

2. **The discarded-flag warning inverts the plan: the alias reaches the naming clause and not the re-invocation line** — `cli/src/commands/init.ts` (`discardedConfigFlagsWarning`) — "const named = option.aliases === undefined ? option.flag : `${option.flag} (or ${option.aliases.join(', ')})`"
   The plan's third consumer bullet reads "the discarded-flag / re-invocation derivation … — **so a re-invocation line carries the alias**". Here `invocation:` stays `option.flag` and `flag:` becomes `named`, so the `--reset-config …` line a reader pastes back carries only the canonical spelling, while the "X was given" clause names both on every run — including a run that typed `--docs-retrieval` and never saw `--rag`, which is the shape the same plan rules out one bullet later for the refusal message ("a reader is not told about a flag they did not use"). The trade-off is argued in the code comment beside it and is defensible — the pasteable half staying canonical is the better half to keep stable — but `harness-runs/user_reviews/feat_docs_catalog_retrieval_fix_plan/finding_2.md` carries no `**Deviations from plan:**` entry recording it, so the plan and the code now disagree with nothing saying which is intended.
   **Fix:** record it as a `**Deviations from plan:**` sub-bullet on that sub-step in `harness-runs/user_reviews/feat_docs_catalog_retrieval_fix_plan/finding_2.md` — the re-invocation stays canonical because that half is pasted back, and the alias is carried in the naming clause instead. (If the plan's literal wording is preferred instead, set `invocation` from the same `named`-style spelling and drop the parenthetical.)
