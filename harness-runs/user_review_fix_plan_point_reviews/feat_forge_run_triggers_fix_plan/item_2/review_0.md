# cli review — ### 2. `/autonomous-sdlc-harness:branch-status` cannot show a run started on GitHub until it is adopted — iteration 0

## Must Fix
1. **The exit map does not list a no-record `status` among the verbs that exit 2 for an unrecognised bundle** — `cli/templates/scripts/remote-run.sh` (header, exit-map entry `2`) — "working copy is missing, or a downloaded bundle is unrecognised\n#        (sync, restore)"
   A no-record `status` now calls `remote_state "$status_tmp"` (`status_from_github`). `remote_state` exits `$EXIT_REFUSED` (2) with "refused, nothing written: the bundle in '…' is unrecognised" when the downloaded `status.json` carries a status outside its enum. Before this change `status` never reached `remote_state`, so the header was accurate. Now the exit map gives only two exit-2 causes for `status`: a record without `execution: github-actions`, and no record with `execution.target` not `github-actions`. The header calls itself the exit map "stated once for every consumer (… the plugin commands that name this file)". The same finding's `branch-status` step 3 tells that command to report status exit 2 as "no run of that name is known locally or on GitHub". So a run whose bundle is corrupt would be reported to the user as not existing. Also, the `remote_state` doc comment ("`sync`, `fetch` and `review` all call it") no longer lists `status` among its callers. Confirmed by reading `remote_state` (the `case "$RS_STATE" in … *) … exit "$EXIT_REFUSED"` arm) and `status_from_github`; no probe was run.
   **Fix:** In the exit-map entry `2`, change "(sync, restore)" to "(sync, restore, and status with no local record)". Add `status` (no-record path) to the `remote_state` comment's caller list. Also tell the plugin-layer dispatch for this finding that `branch-status` must not read every exit 2 from a no-record `status` as "no run known". It should report the stderr message when that message is not the `execution.target` refusal.

## Nice to Have
1. **An expired bundle prints its expired line twice on the no-record path** — `cli/templates/scripts/remote-run.sh` (`status_from_github`) — "[ \"$RS_PAUSE_REASON\" != expired ] || [ \"$RS_BUNDLE\" -eq 1 ] || echo \"remote-run.sh: $RS_DETAIL\""
   In `remote_state`'s expired case, `RS_DETAIL` is already `expired_line "$RS_RUN_ID"`, and `status_from_github` prints it as `  detail: …`. The trailing line then prints the same text again. No consumer decision depends on it, but the output is redundant. There is also no test for the expired no-record path. Confirmed by reading `remote_state`'s "Case 2" block; no probe was run.
   **Fix:** Either drop the `  detail:` print when `RS_PAUSE_REASON` is `expired`, or drop the trailing echo and note in the header that the expired line is the `detail` value.
