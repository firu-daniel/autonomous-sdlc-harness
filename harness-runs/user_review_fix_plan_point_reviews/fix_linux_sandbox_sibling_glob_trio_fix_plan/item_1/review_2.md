Scope: `plugin/hooks/git-trust-file-guard.sh` (new), `plugin/hooks/hooks.json`, `plugin/hooks/README.md`, checked against the task file's steps 1–3 and `.claude/context/plugin.md` (plus `.claude/context/conventions.md`, which it defers to for guard rules). The task file's `**Deviations from plan:**` entries were treated as intended.

Executed: a probe, `bash scripts/scratch-run.sh harness-runs/scratch/layer-review-trust-guard-probe.mjs <repo>/plugin/hooks/git-trust-file-guard.sh`, ran the shipped guard under `/bin/bash` (3.2) against a throwaway `git init` fixture. Results: `deny` for a relative `commondir` with `.cwd` = `<repo>/.git`; a dangling leaf symlink → `.git/commondir`; a trailing-`/` trio path; `<repo>/sub/up/config.worktree` where `sub/up` → `../.git`; `<link-to-.git>/../.git/commondir`; and a relative trio path with no `.cwd` key. `SILENT` for `.git/commondir.lock`, an ordinary file, and paths carrying `$(echo PWNED >&2)` and a backtick form (stderr empty, so the `eval "set -- …"` hand-off did not execute either one). No defect found in the decision logic.

## Should Fix

1. **The REPRO block does not reproduce several of the outcomes in the guard's own fail-closed table, and the new suite's header says it does** — `plugin/hooks/git-trust-file-guard.sh` (header, `REPRO` block) — "A symlinked leaf: `ln -s .git/config.worktree /tmp/r/innocent`"
   The header's `FAIL-CLOSED TABLE` lists `deny` for an unknown `tool_name`; a path field that is missing, not a string, or empty; a payload that is not exactly one JSON value; `readlink` failing or a chain of more than 8 hops; and an ancestor `cd -P` cannot resolve. The REPRO block covers none of these. It covers only the trio, a path under one, `..`, a symlinked parent, the two silent cases, non-JSON, missing `jq` and a symlinked leaf. `.claude/context/plugin.md` → `## Guards, the shared library and the helper scripts` asks for a `REPRO` block "that reproduces each of its outcomes by hand". Also, `cli/test/git-trust-file-guard.test.mjs`'s header says "a `readlink` that fails or a symlink chain past the hop limit; the guard's own `REPRO` block reproduces those by hand". A maintainer who follows that pointer finds nothing to run. This was first raised from the `cli` side in iteration 1's Should Fix 2 and is still open.
   **Fix:** Add REPRO lines for at least these cases. Unknown tool: `tool_name "Read"` → `"deny"`. Empty path: `tool_input {"file_path":""}` → `"deny"`. Two JSON values: `printf '{}{}'` → `"deny"`. Hop limit: a 9-link chain built with `for i in 1 2 3 4 5 6 7 8 9; do ln -s l$((i-1)) /tmp/r/l$i; done` (after `touch /tmp/r/l0`), then `file_path /tmp/r/l9` → `"deny"`, with a reason naming "longer than 8 hops".

2. **The fail-closed table gives `deny` under "Configuration unresolvable" to a guard that reads no configuration** — `plugin/hooks/README.md` (`## Fail closed — and what that means for an allow-only guard`) — "| `git-trust-file-guard.sh` | `deny` | not applicable (reads no configuration) | **`deny`** |"
   In this table a cell says what the guard emits *because of* that column's condition. The protected-branch guard's `deny` in the first column means "denies everything it judges when the configuration will not resolve", and the next paragraph says so. Put this guard's `deny` in the same cell and an adopter reads it the same way: that a broken `harness.config.json` makes every `Edit`/`Write` refused. In fact the guard never reads the file, and its decision does not change under either configuration column. The second column's "not applicable" is correct, and the first column needs the same treatment.
   **Fix:** Make the row `| git-trust-file-guard.sh | not applicable (reads no configuration) | not applicable (reads no configuration) | **deny** |`, with the backticks kept as in the other rows.

3. **The guard ships without a top-level string filter, which the conventions list for a new guard requires, and the task file's Manual follow-up does not list that row** — `plugin/hooks/git-trust-file-guard.sh` (header) — "NO TOP-LEVEL STRING FILTER, DELIBERATELY"
   `.claude/context/conventions.md` → `## What accompanies a new unit of each kind`, row *A guard hook*, requires "its own self-verifying top-level string filter". The header argues the exception, as the plan asked, and `allow-qa-credentials-read.sh` is a precedent, so this is not graded as a missing required item. But the task file's **Manual follow-up** paragraph names the conventions sentences this guard makes untrue ("Exactly one guard … may answer `deny`", "it emits `allow` or nothing", "the only external binaries … `git` and `jq`", and the `plugin.md` row) and leaves this row out. A maintainer working through that list will not amend it. The next reviewer to grade this guard against that row will then flag a missing filter that was a deliberate choice.
   **Fix:** Add that row to the Manual follow-up list in `harness-runs/user_reviews/fix_linux_sandbox_sibling_glob_trio_fix_plan_2/finding_1.md`, e.g. "…and `.claude/context/conventions.md` → `## What accompanies a new unit of each kind`, row *A guard hook* — 'its own self-verifying top-level string filter' (argued away in the guard's header under **NO TOP-LEVEL STRING FILTER, DELIBERATELY**)".
