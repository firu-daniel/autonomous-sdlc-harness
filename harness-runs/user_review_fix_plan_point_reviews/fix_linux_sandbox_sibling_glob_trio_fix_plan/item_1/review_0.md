# cli review — ### 1. On a bubblewrap host the per-run copy still carries the run copy's own trio `Edit` rules, and on Linux they mount the placeholders that break git — iteration 0

Verified by running `npm test --workspace cli -- test/watcher-run-profile.test.mjs test/watcher-placeholder-host.test.mjs test/profile.test.mjs test/doctor-profile-sandbox.test.mjs` (build included): 126 tests, 126 pass, 0 fail. The `Deviations from plan:` entries (step 9 left to a `general` dispatch, the `*`-in-`<g>` reading, the structural seam-off assertion) were taken as intended and not flagged.

## Should Fix
1. **The adopter-facing text still says the file-tool side is what protects the trio on Linux, two clauses before saying the per-run copy drops it** — `cli/src/generators/writeProtection.ts` (`applyWriteProtection`) — "so on Linux only the file-tool side is relied on for the globbed entries: a run copy's hooks directory, MCP wiring and settings files, its ${COPY_GIT_PATHS.map("; and `cli/src/doctor/checks.ts` (`PROFILE_WRITE_PROTECTION_CHECK`'s pass message) — "so on Linux only the file-tool side is relied on for the globbed paths"
   Both sentences list `.git/commondir`, `.git/config.worktree` and `.git/objects/info/http-alternates` (the `_README` names them explicitly through `COPY_GIT_PATHS.map`) among the paths that the file-tool side protects on Linux. The sentence this unit appends then says that on a bubblewrap host the per-run copy also leaves out the run copy's own `Edit` rules for exactly those three. So for the run copy's trio on Linux, the profile now relies on neither side, only on the trust check and the launch check. A reader who stops at the first sentence takes the file tools to be refused on those three paths in the run copy, and they are not. The template's own `_README` (`cli/templates/claude/settings.autonomous.json`, "TWO RESIDUALS") has the same order, but its correction comes right after it in the same sentence, so it reads less badly.
   **Fix:** Qualify the earlier clause in both strings, e.g. "…so on Linux only the file-tool side is relied on for the globbed entries (and for the run copy's own `.git/commondir`, `.git/config.worktree` and `.git/objects/info/http-alternates`, not even that in the per-run copy: see below)". Or move the trio out of that list and into the new sentence. Then adjust the substring assertions in `cli/test/profile.test.mjs` and `cli/test/doctor-profile-sandbox.test.mjs` to match.

2. **The "kept glob rule" assertion for `.git/hooks` is vacuous** — `cli/test/watcher-placeholder-host.test.mjs` (the launch case "after a launch the manifest lists exactly the absent denyWrite paths…") — "assert.ok(deny.some((rule) => rule.includes('*') && rule.endsWith(kept))"
   The loop is meant to show that the base's sibling-glob `Edit` rules for the kept rows survive. For `kept = '/.git/hooks/**)'`, the clone's own exact rule `Edit(/<clone>/.git/hooks/**)` already contains a `*` (in `/**`) and ends with that suffix. The assertion therefore passes even if the base's `<project>-*/.git/hooks/**` glob rule were dropped. The `.git/config` and `alternates` iterations are sound, because their exact rules carry no `*`. Confirmed by reading the rule shapes from `fileToolDenyRules` (`directory` → `Edit(/<p>/**)`); no probe was run.
   **Fix:** Test the `*` against the part before the suffix, e.g. `deny.some((rule) => rule.endsWith(kept) && rule.slice(0, -kept.length).includes('*'))`.
