Verified on this pass: all five template/root-twin pairs are byte-identical. `cmp` ran on `lib/harness-run-lib.sh`, and the other four pairs show the same pre- and post-image blob hashes in `git diff HEAD`. The four edited suites pass when each is run alone with `npm test --workspace cli -- test/<name>.test.mjs`: `clone-trust-check` (65/65), `watcher-placeholder-host` (31/31), `profile` (49/49) and `doctor-profile-sandbox` (22/22). ## Should Fix
1. **The new `extensions.worktreeConfig` read opens `.git/config` before anything checks what kind of file it is, and blocks forever on a FIFO** — `cli/templates/scripts/lib/harness-run-lib.sh` (`hr_clone_target_check_var`) — "wtc_val=$(git -C / config --file \"$gd/config\" --bool --get extensions.worktreeConfig 2>/dev/null) || wtc_rc=$?"
   Before this change, condition 3 read no file. The library opens a clone's `.git/config` only through `hr_clone_config_check_var` (condition 5), which first refuses a symbolic link or a non-regular file (`if [ -L "$f" ] || [ ! -f "$f" ] || [ ! -r "$f" ]`). The new read runs before that guard, and only needs an empty `config.worktree`, which is now accepted. A probe showed that `git -C / config --file <fifo> --bool --get extensions.worktreeConfig` does not return. Command: `bash scripts/scratch-run.sh harness-runs/scratch/fifo_config_probe.py`, which printed `BLOCKED: no return within 3s on a FIFO .git/config` with this host's git on macOS. In that state the unsandboxed wrapper or the watcher's launch check would hang instead of failing closed. Reaching it would first take defeating `.git/config`'s own write protection, so this is defence in depth and not an open path. The same probe confirmed the other two branches: an absent file exits 1, and an invalid boolean exits 128, which is refused.
   **Fix:** Guard the read the way condition 5 does. For example, wrap it as `if [ -e "$gd/config.worktree" ]; then if [ -L "$gd/config" ] || [ ! -f "$gd/config" ]; then HR_TARGET_REFUSAL="… $gd/config is not a regular file …"; return 1; fi; …`. Alternatively, move the `extensions.worktreeConfig` arm after the `hr_clone_config_check_var` call, and keep case `(h2)`'s ordering assertion true by testing that arm before the allow-list's own refusal fires. Apply the same edit to `scripts/lib/harness-run-lib.sh` and re-run `cmp`.

2. **`docs/cli.md`'s manual remedy still names the `config.worktree` refusal as the one a leftover placeholder causes** — `docs/cli.md` (§6, **The manual remedy.**) — "The refusals that send an adopter here are that one, *\"is a clone, but <gd>/config.worktree exists, and a clone the harness made has none\"*"
   After this change, an empty regular `config.worktree` (or `http-alternates`) is accepted. So a leftover empty file at those paths no longer triggers that refusal, and the remedy's step "for each one that is an empty file, remove it" can no longer match it: the refusal now fires only for content, a link, a non-regular file or `extensions.worktreeConfig` on. An empty leftover `commondir` is still refused, with `"… commondir exists, and a clone the harness made has none"`, and the remedy does not list that sentence. An adopter who searches the docs for that refusal does not find the remedy. No finding in this fix plan edits this paragraph: Finding 4 owns `docs/cli.md` §6 residual 12's **Leftovers.** point, and its text does not touch the refusal list.
   **Fix:** Replace the quoted `config.worktree` refusal with the `commondir` one, `"is a clone, but <gd>/commondir exists, and a clone the harness made has none"`. Add one clause saying that an empty regular `config.worktree` or `http-alternates` is accepted by the trust check (`hr_clone_target_check_var`, condition 3) and needs no removal.
