# cli review — 3. Reviews collected during a run never start the next round on their own — iteration 0

## Must Fix
1. **The `collect` job checks out the run's branch, so its `review` child can never cut a working copy and every collected round fails** — `cli/templates/github/workflows/harness-run.yml` (`collect` job, step "Check out the run's branch for collecting") — "ref: ${{ inputs.branch }}"
   The job's checkout leaves the job's working copy on a local branch named `<branch>`. Then `remote-run.sh collect` runs `review <branch> … --repo "$root"`. With no remote record in a fresh job, `verb_review` takes the `create-worktree.sh --existing --no-bootstrap "$branch"` arm, which refuses a branch that is already checked out (`create-worktree.sh`: "branch '$branch' is already checked out at … — refusing", exit 2). So in the real workflow, every settled branch with a pending review ends in `review exited 4` plus the one failure comment, and no round is ever placed. That defeats the finding's whole purpose. `harness-control.yml`'s review job avoids this by checking out `${{ github.event.repository.default_branch }}`. The plan's YAML sketch did say "check out the run's branch", but this is the behaviour that sketch produces.
   The new suite misses it because `collectFixture` returns the fixture to `config.defaultBranch` before running `collect`.
   **Confirmed by probe:** I built a copy of `remote-collect.test.mjs`'s first case and changed one thing, so that the fixture stays on `feat_x` (`git checkout feat_x` instead of `config.defaultBranch`). I ran it with `bash scripts/scratch-run.sh harness-runs/scratch/collect_on_branch_probe.mjs`. Result: exit 0, stdout "collect: review exited 4; the pull request was told, and nothing is retried", stderr "create-worktree.sh: branch 'feat_x' is already checked out at … — refusing", and origin unchanged at `fixture: feat_x`. The unchanged copy (`collect_control_probe.mjs`) places the round and dispatches it.
   **Not confirmed by running:** that `actions/checkout@v5` with `ref: <branch name>` leaves a local branch of that name checked out. I took that from the action's documented behaviour (`git checkout -B <branch> refs/remotes/origin/<branch>`); nothing was run on GitHub.
   **Fix:** In the `collect` job, check out the default branch exactly as `harness-control.yml`'s review job does: `ref: ${{ github.event.repository.default_branch }}`, `fetch-depth: 0`. Rename the step to match, for example "Check out the default branch for collecting". `collect` already fetches the branch itself (`forge_fetch_branch`), and `review` cuts its own copy. Update the `THE COLLECT JOB` header if it describes the checkout. Then add a regression guard: in `workflow-templates.test.mjs`'s collect case, assert that the job's checkout `ref:` is the default branch and not `inputs.branch`. In `remote-collect.test.mjs`, either leave the fixture's main checkout on a branch other than `feat_x` and state why in the header (the job checks out the default branch, so `review` can cut `feat_x`), or add a case documenting that a checkout on the branch fails.
