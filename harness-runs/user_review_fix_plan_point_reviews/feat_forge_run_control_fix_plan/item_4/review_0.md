# general review — 4. The design of record still says a review in flight is refused and must be resubmitted, and the push-race question is undecided — iteration 0

## Should Fix
1. **"Two reviews submitted together become one round" is justified by a case that makes two rounds** — `docs/github-run-control.md` (`## 2. A review that requests changes starts a round`, **One writer at a time.**) — "the second job finds the first one's reviews recorded, or finds the round's run in flight and answers \"collected\""
   The second clause contradicts the first. In `cli/templates/scripts/remote-run.sh` → `control_review_in_flight`, a review job that finds the run in flight replies "part of round <n>" when a marker on origin's tip already records its review id. It replies "your review was collected" only when **no** marker records it. In that case the review was not in the first round, and the run's `collect` job places it as a later round. So "answers collected" is the two-round outcome. The sentence presents it as one of the ways the reviews become one round. The two reviews share a round only when the second is submitted before the first job's `round_collect` lists the pull request's reviews. The one-writer invariant still holds either way, since no round is doubled. A maintainer running Gate 12 (xiv)'s new simultaneous-review step in `docs/development.md` ("Passes when one round file carries both `## Review by` sections and only one new `chore: add user review for <slug>` commit appears") would take a two-round result for a defect, when the design allows it. Confirmed by reading `control_review_in_flight`, `round_markers_read` and `round_collect`. No probe was run.
   **Fix:** Reword it, for example: "So two reviews submitted together never make a double round. When the second is submitted before the first job lists the reviews, both go into one round, and the second job answers with that round's number. Otherwise the second job finds the round's run in flight and answers \"collected\", and that run's `collect` job takes it into the next round." Also qualify the Gate 12 step's pass criterion. One round file carrying both sections passes. A second review answered "collected" and then placed by `collect` as the following round is recorded as the race outcome, not as a failure.

2. **"Pending review" reads as GitHub's draft-review state, which is not what the code collects** — `docs/github-run-control.md` (`## 2…`, **Since the previous round, and never twice.**) — "An inline comment that belongs to a pending review is collected whatever its time, because a draft comment is created before its review is submitted."
   In GitHub's vocabulary, a *pending review* is an unsubmitted draft, whose state is `PENDING`. The code means something different. `round_collect` keeps a comment regardless of `created_at` when its `pull_request_review_id` is one of the reviews requesting changes that **this round collects** (the `$ids` selection). The doc never defines "pending" (and the bullet "every pending inline comment" uses the word the same way). The given reason, "a draft comment is created before its review is submitted", pushes the reader further toward the draft-state reading. Someone changing `round_collect` against this design of record could select on GitHub's `PENDING` state instead. Comments that `PENDING` state marks are not listed to other users anyway. Confirmed by reading `round_collect`'s jq filter and the `remote-run.sh` header's "Pending:" definition. No probe was run.
   **Fix:** Use the code's meaning: "An inline comment that belongs to a review this round collects is collected whatever its time, because a review's comments are created while it is still a draft, before it is submitted." Define "pending" once where the `## Inline comments` bullet first uses it, as not recorded by any earlier round and at or after the boundary, or replace it there with that phrase.
