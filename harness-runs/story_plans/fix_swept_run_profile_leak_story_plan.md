# Story: The sweep removes a merged run's per-run profile with its copy

## Context

`cleanup-merged-worktrees.sh` removes a merged run's copy (a clone through `hr_clone_remove_var`, a legacy worktree through `git worktree remove --force`) and deletes the merged branch. It leaves that run's per-run profile at `${XDG_STATE_HOME:-$HOME/.local/state}/autonomous-sdlc-harness/run-profiles/<repo slug>/<sanitized branch>.json` on disk. `docs/sandbox-verification.md` §7 row OR9 observed this. This branch makes the sweep delete that file right after it removes the run's copy, and before `git branch -D`. The deletion has three gates, and every one must pass:

- **The copy was removed by this sweep.** It happens only after `removed clone …` or `removed worktree …`. It does not happen after a refused `hr_clone_remove_var`, a skip line, a failed `worktree remove`, a record whose `worktree` is already gone, or a branch with no record.
- **The path is the one the watcher wrote.** It is `hr_run_profile_file "$slug" "$branch"`, where `slug` is `hr_repo_slug "$main_repo"`, worked out by the sweep itself. The sweep never reads the inherited `HARNESS_REPO_SLUG`: in job mode the watcher overwrites that with the remote slug, and the sweep inherits the watcher's environment. No glob is used and no path is built by hand.
- **No live run uses the file.** The registry is re-read right before the `rm`. The file is kept if any `running`, `parked`, `park_loop` or `paused` record maps to the same path through `hr_run_profile_file`. That covers the branch itself, and also a second branch that `hr_sanitize_branch` folds onto the same file name (`feat/x` and `feat-x` both write `feat-x.json`). These four statuses are the ones the watcher's `process_inbox_file` treats as owning a run copy. The sweep already skips them through its active-run filter. That filter becomes one function that the start-of-sweep read and the re-check share, so no second list exists. The re-check follows the ledger rule *"must check the enabling condition again after switching it off"*: a sweep run by hand can race a watcher launch.

`--dry-run` makes the same decision and prints `[dry-run] would remove run profile <file> for '<branch>'`. It deletes nothing.

**Leftovers from before this fix take the documented manual route, not a sweep arm.** The other route would enumerate `run-profiles/<slug>/`. That is a glob, which the prompt forbids for this script. It would also need to map a file name back to a branch, and `hr_sanitize_branch` cannot be reversed, so *"no registry record for that branch"* cannot be decided from a file name. And it would widen the most destructive script in the set to delete files it found by listing rather than by working the path out from a record. The leftovers are a one-off backlog, so a one-off command fits. The command is safe for one reason: the watcher re-renders a run's profile at every spawn, whether a launch, a park-resume or a pause-resume. So deleting every profile under the repository's slug while no run is `running` cannot take a profile from a session. `docs/watcher.md` → `### The per-run profile` documents the command (Task 4).

The work is four single-layer tasks, in ship order. Task 1 changes the sweep template and the library's comment about `hr_run_profile_file`'s callers. Task 2 adds the prompt's cases to the registry-driven sweep's suite. Task 3 points the two other suites that run a real sweep at a temp `XDG_STATE_HOME`. One of them proves end to end that a profile the real watcher rendered is the one the sweep removes. Task 4, the catch-all task, mirrors the changed templates into this repository's own `scripts/` byte for byte and updates `docs/watcher.md`, `docs/sandbox-verification.md` and `docs/outer-loop-verification.md` § 1.4's *What moved* paragraph. Job mode, `remote-run.sh start` / `review`, the profile's path and content, `run_profile_render` and `run_profile_check` are all left as they are. OR9's verdict cell is left as observed. The dated re-observation after the §7 table is owed once a real sweep has run after this branch merges, so this branch does not write it.

**Top risks:** The likeliest defect is a sweep that deletes a profile a live run still needs. That could come from deleting before the copy-removal result is known, from trusting the start-of-sweep active set alone, or from missing a sanitized-name collision. Task 1 orders the deletion after a successful removal and re-reads the live set at deletion time. Task 2's refused-clone, four-live-status and collision cases each guard one of those paths. The second risk is a path that does not match the watcher's. Using the inherited `HARNESS_REPO_SLUG`, or a slug derived from a run copy, would delete nothing, or delete another repository's file. Task 2's other-slug case passes a misleading `HARNESS_REPO_SLUG` on purpose. Task 3 checks the sweep against a profile the real watcher rendered. The third risk is a test that touches the real machine state directory. Tasks 2 and 3 give every sweep a temp `XDG_STATE_HOME` under the fixture root, so the `--dry-run` snapshot covers the profile files too.
