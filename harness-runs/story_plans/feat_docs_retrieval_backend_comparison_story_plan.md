# Story: Docs retrieval, second backend — measuring the Python backend against the TypeScript one, and writing the comparison up

## Context

This branch **measures** the Python docs-retrieval backend (`docs-retrieval-service/`, landed by `feat_docs_retrieval_python_backend`, made selectable by `feat_docs_retrieval_backend_selection`) against the TypeScript one (`cli/src/retrieval/`). It uses the same two committed corpora (`fixture-catalog`, `self-docs`), the same query sets and the same runner (`evals/docs-retrieval/`). Then it writes the comparison up. **The comparison is the deliverable.** It is the third of three branches. Nothing here changes either backend's search behaviour, the default backend, the default search mode, the abstention threshold, the corpus, or this repository's `harness.config.json`. No file under `plugin/` is touched. Twelve tasks are in the `general` layer, because their targets sit under `evals/`, `docs/`, `docs-retrieval-service/README.md` or `llms.txt`. One task, **Task 13**, is in the `cli` layer. It touches `cli/src/retrieval/models.ts` only to export the embedder's extraction options as one constant, `EMBEDDING_EXTRACT_OPTIONS`, which `loadModels` reads itself, so that Task 7's matched-precision leg imports them rather than copying them. No value changes, so the embedder id, every vector and both backends' search behaviour are unchanged.

**Preconditions, confirmed on this machine when the plan was written.** Docker is on `PATH`. Both weight caches are present: the Xenova q8 ONNX exports under `${XDG_CACHE_HOME:-$HOME/.cache}/autonomous-sdlc-harness/retrieval/models/Xenova/`, and the PyTorch originals with their `harness-docs-retrieval-models.json` manifest under `${XDG_CACHE_HOME:-$HOME/.cache}/harness-docs-retrieval/models/`. This worktree's Python environment is synced **with** the `models` extra (`torch`, `sentence-transformers` present). Per the task prompt, if any of these is missing when a task runs, the task **stops and returns a blocker naming it**. It never installs or downloads anything to work around it.

**The decisions this plan takes, stated once so every task inherits them.**

- **The runner gains a `--backend` flag, and the run without it is byte-for-byte the run it was.** `--backend` takes `typescript` or `python`. The vocabulary is declared once, in a new `evals/docs-retrieval/backends.mjs` (Task 2), so no second list exists. **With the flag absent** the run takes the existing in-process path and renders the existing unlabelled block (`<!-- eval:corpus:<id>:start -->`). Gate 11 (`check-floor.mjs`) and the eval branch's recorded blocks are therefore untouched. **With the flag given** the block is keyed `<id>@<backend>`, for example `<!-- eval:corpus:fixture-catalog@python:start -->`. Its machine half carries a `backend` key, and its provenance names the backend and the route. That is what lets the same-session TypeScript re-run (`--backend typescript`) sit beside the eval branch's recorded TypeScript block without destroying it. The recorded block is what `## Threshold calibration` and `## The query-log pass` cite.
- **The Python backend is driven over its HTTP app, `serve-http`, never re-implemented.** `POST /search` takes `{ query, k, mode }` and returns `hits`, `abstained`, `best_rerank_score` and `search_ms` (`docs-retrieval-service/src/harness_docs_retrieval/http_app.py` → `create_app`). Every figure is then scored by the same `evals/docs-retrieval/metrics.mjs` → `scoreArm` the TypeScript arms are scored by. The library-level latency for the Python arms is the server's own `search_ms`, timed in-process around `search_docs` alone. That is the README's **"Timing is exposed, never recorded."** contract, and what the task prompt's item 5 asks for. The HTTP hop is not timed.
- **The Python service reads a corpus through a throwaway mirror repository.** `load_service_config` (`docs-retrieval-service/src/harness_docs_retrieval/service.py`) refuses a `--repo` without a `harness.config.json`, and the `fixture-catalog` root (`evals/docs-retrieval/corpora/fixture-catalog`) carries none. Adding one there would change the corpus directory, which the task prompt forbids. So both backends' MCP passes and the Python runner path read the corpus through the mirror fixture `evals/docs-retrieval/query-log-pass.mjs` → `buildFixture` already builds under the system temp directory. That fixture copies every corpus file to the same repo-relative path, so every rendered `ref` is unchanged, and it carries the resolved `docs.root` and `layers[]`. Task 1 lifts it into a shared module rather than copying it.
- **Every wall-clock figure of record is taken by hand, outside any headless session.** `harness-runs/lessons.md` → *Evidence and measurement*: *"A wall-clock figure in a document of record is never one a run measured inside its own session … A plan never makes repeated in-run timing runs its acceptance evidence."* The `--out` runs whose blocks carry p50/p95 are therefore an **operator's hand run**, listed under **Manual setup required** below and specified, command by command, by Task 9. So are the MCP round-trip and cold-start passes and the footprint figures. The tasks build the tooling and verify it on stdout only. Tasks 10 and 11 write the record from the operator's captured outputs, and **return a blocker if those captures are absent**. Deterministic figures are measured in-session by Task 10: per-query hits, recall, MRR, abstention, and vector cosine.
- **Paired runs never straddle a corpus change.** `docs/retrieval-eval-results.md` is itself in `self-docs` (`docs/retrieval-eval.md` → `### Writing the results, and the corpus that grows when you do`). An `--out` into it between the TypeScript and Python `self-docs` runs would hand the second run a different corpus. So the hand run writes all four blocks into a **scratch copy**, `harness-runs/scratch/backend-comparison/results.md`, which is gitignored and outside `docs.root`. Task 10 then moves the four blocks into `docs/retrieval-eval-results.md` through `results.mjs` → `transplantCorpusBlock` (Task 2). That keeps `results.mjs` the generated region's one writer. `backend-comparison.mjs` (Task 8) **refuses** a pair whose `{ files, chunks }` snapshots differ.
- **The write-up is a new section of an existing document, not a new document.** The task prompt says *"no new committed documents"*. `.claude/context/conventions.md` → `### Where a new responsibility goes` sends a measured fact or a decision of record to `docs/` and nowhere else. Both hold if the write-up is `## The Python backend against the TypeScript one`, appended to `docs/retrieval-eval-results.md` below every existing section and outside the generated region. That file already carries this eval's verdict sections (`## The decision, applied to the real catalog`).
- **Divergence sources are checked in the prompt's order, and each is a measurement.** (1) **Quantization:** the two sides already differ, TypeScript q8 (`Xenova/bge-small-en-v1.5:q8:cls:384:v1`) against Python fp32 (`py-st/BAAI/bge-small-en-v1.5:fp32:cls:384:v1`, `docs-retrieval-service/README.md` → `## Weights, precision and ids`). (2) **ONNX against PyTorch at matched precision:** only the q8 ONNX export is cached (`onnx/model_quantized.onnx`), so this leg is **arranged only if the operator places the fp32 export in a scratch cache** (Manual setup, optional). Task 7 builds the leg, and it reports itself unarranged otherwise. Unarranged, (1) and (2) are measured jointly and the write-up says so. (3) **BM25:** arm B's per-query ordered refs, with no model in the path. Vector agreement is measured directly: the per-chunk cosine between the two embedders' vectors for the same chunk keys (Task 6).
- **The embedder id stays namespaced unless the number supports sharing, and a supportive number is a proposal, not a change.** Both committed corpora are fixture-sized. `harness-runs/lessons.md` → *Evidence and measurement*: *"A figure measured under a test stub or a fixture-sized corpus never justifies a design decision"*, and *"A decision rule's outcome is a proposal to the maintainer"*. So Task 10 records the decision as **keep namespaced**. If the cosine and arm C agreement would support sharing, it records that as a proposal that needs a real-shape figure, and writes no pending work into any other document.
- **The abstention threshold is read, never tuned.** `ABSTAIN_SCORE_THRESHOLD` (`0.32`, `cli/src/retrieval/search.ts` and `docs-retrieval-service/src/harness_docs_retrieval/search.py`) and `docs/retrieval-eval-results.md` → `## Threshold calibration` are unchanged. A mismatch in the abstention set is enumerated query by query with a stated cause, as a finding.
- **Shared files have one editor at a time, in ship order.** Tasks 1–8 each add or amend only their own rows of `evals/docs-retrieval/README.md`, and each depends on the previous task that edited it. `docs/retrieval-eval-results.md` is edited by Task 10 and then Task 11. Every other target has exactly one owning task.
- **What "same results" means for the TypeScript path (Acceptance 6).** Tasks 2 and 4 each capture the unlabelled run's per-query hits, abstentions and best rerank scores, plus the rendered block's non-latency bytes, before their first edit. After the edit they compare them and require them identical.

**Running a unit's own checks.** No task creates or edits a test file. The eval modules have no `cli/test` suite, and the task prompt adds none. Task 13's change to `cli/src/retrieval/models.ts` keeps every value, and no `cli/test` suite loads a real model. So no unit runs a test. Each verifies through a scratch launcher, `bash scripts/scratch-run.sh harness-runs/scratch/<file>.mjs`, which is the eval's documented route (`docs/retrieval-eval.md` → `### The two execution routes, and the one that stalls`). It never uses a bare `node evals/…`, which stalls an unattended run. `commands.typecheck` covers `cli/` only. It runs `npm run build`, so Task 13's run of it also refreshes the `cli/dist/retrieval/models.js` that Task 7 imports. Phase G's `scripts/run-gates.sh` is where Acceptance 6's "still passes with no Docker and no Python weights" is graded. No TypeScript-path module statically imports a Python-path module, because `run.mjs` loads `python-backend.mjs` through a dynamic `import()` only when `--backend python` is given.

**Top risks:** The likeliest failure is **the TypeScript path changing silently**: a refactor of `runArm`, the block key or the provenance that moves a figure or a byte of the recorded blocks. Tasks 2 and 4 guard it by keeping the flag-absent path on its existing code and comparing captured output before and after. The second risk is **an in-session timing leaking into a document of record**, or **a pair taken across a corpus change**. The hand-run protocol (Task 9), the scratch results copy, Task 8's snapshot-equality refusal, and Tasks 10 and 11's blocker when the captures are missing guard it together. A related risk is **the embedder's identity moving under the eval**. Task 13 guards it: it exports the extraction options without changing a value, and it leaves `MODEL_VERSION` and the id template untouched. The third risk is **papering over a divergence**, by tuning, by calling a gap noise before every source is checked, or by sharing the embedder id on a fixture-sized figure. Task 8 enumerates every per-query difference rather than averaging, and Task 10 must name one of the three cases and back each identified cause with a measurement. A fourth, practical risk is **an orphaned Python server** holding the port and a database connection after a refused run. Task 3 spawns it in its own process group and kills that group on every exit path.

**Manual setup required:**

- **Before Task 3's verification (and every later Python-path run):** start the database once, from `docs-retrieval-service/`, with `docker compose up -d --wait postgres`. The first run builds the `postgres/` image and may reach the network. Leave `HARNESS_DOCS_RETRIEVAL_DATABASE_URL` unset to use the compose default **for the eval's own modules**; the hand run's direct `bash scripts/python-service.sh run index` (the cold Python index) gets no default and sets the variable in its own fenced step first, as Task 9 writes it. The runner and the MCP pass take the URL from `cli/src/retrieval/pythonBackend.ts` → `pythonDatabaseUrl`, imported. That function is the one place the default is decided, for the launcher, `doctor` and this eval alike.
- **Optional, before the hand run, for the matched-precision leg (Task 7):** place the Xenova fp32 export of `bge-small-en-v1.5` (`onnx/model.onnx` with its `config.json`, `tokenizer.json` and `tokenizer_config.json`) under `harness-runs/scratch/backend-comparison/onnx-fp32/Xenova/bge-small-en-v1.5/`. This is a download, so it is the operator's to make or decline. Declined, the write-up records the leg as not arranged. Never place it in the machine-shared Xenova cache.
- **Before Task 10 — the hand-run measurement session**, by the operator at a terminal on an otherwise idle machine, outside any headless session, following `docs/retrieval-eval.md` → `### Measuring the Python backend against the TypeScript one` exactly as Task 9 writes it. It produces, under `harness-runs/scratch/backend-comparison/`: `results.md` (four `--out` blocks: `fixture-catalog` and `self-docs`, each `@typescript` and `@python`), `mcp-typescript.txt` and `mcp-python.txt`, `footprint.txt` and `host.txt`.
- **Before Task 11 — one real agent session through `.mcp.json` per backend**, by the operator, in a throwaway repository outside this checkout, per the same section of `docs/retrieval-eval.md`. It installs the package with `uv tool install` from this checkout's `docs-retrieval-service/` with the `models` extra, because `harness-docs-retrieval` is not on this machine's `PATH`. It produces `agent-session-python.jsonl`, `agent-session-typescript.jsonl` and `agent-session.md` in the same directory.
