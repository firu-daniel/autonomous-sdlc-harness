# Story: The Run gates phase runs the whole-tree type check as well as the test suite

## Context

Today the Run gates phase (Phase G) runs only `commands.test`, through `run-test-suite.sh`, so a branch can tick "Run gates passed" while its static checks (format, lint, type check) fail. The adopter's CI on the pull request is then the first place that failure shows up. The scenewise run that prompted this branch saw exactly that. Three dispatches each saw a failing whole-tree `typecheck.sh`, narrowed it to one file, and recorded the rest as "deferred to the Run gates phase", a phase that never ran it. This branch makes each Phase G round run the whole-tree `commands.typecheck` and then `commands.test`. It keeps the one wrapper call, the one verdict line and the one log per round. It also makes the implementer contract say what "deferred" may name.

**Decisions this plan takes. Every task restates the ones it needs, so no implementer has to re-decide them:**

- **One wrapper call runs both gates, and the script keeps its name.** `run-test-suite.sh` runs `commands.typecheck` with no path argument, then `commands.test`, under the one label, into the one log. The `<label>.running` / `<label>.verdict` files, the `--wait <label>` form, the label pattern and the verdict lines `pass`, `fail <log path>` and `pending` are unchanged. The script is not renamed. A rename would reach `OUTER_LOOP_SCRIPTS` (`cli/src/generators/outerLoopScripts.ts`), the name pins in `cli/test/outer-loop-scripts.test.mjs` and `cli/test/init.test.mjs`, and every adopter's permission profile. Keeping the name and changing the header contract costs none of that. Calling the wrapper twice with two labels was rejected because it would make the orchestrator handle two verdicts and two `--wait` loops per round.
- **Run both, report both.** The test command runs even when the type check failed. A round passes only when both pass. Effect on the cap: `MAX_GATE_ROUNDS = 5` counts gate runs. A branch broken both ways therefore spends **one** gate run and gets one fix plan covering both kinds of failure, where fail-fast would spend at least two runs before the second kind was even seen. The cost is a suite run on a round whose type check already failed. `MAX_GATE_ROUNDS` does not change.
- **`<none>` is not run and not a pass.** If `commands.typecheck` holds exactly `<none>` (trimmed, as `isNoneSentinel` in `cli/src/config/model.ts` reads it), the round runs only the test command. The log records that the type check was not run, and that never fails the round. If `commands.typecheck` is unset or empty, the wrapper refuses exactly as it does for an unset `commands.test`: exit 2 and one stderr line, `run-test-suite.sh: commands.typecheck is not set in harness.config.json`.
- **The log format is a wire between the wrapper (Task 1) and `test-fix-plan-writer` (Task 8).** The wrapper writes these marker lines, in this order. On the typecheck side it writes either the first pair or the first line plus the not-run line:
  - `== run-test-suite.sh: gate typecheck (commands.typecheck) ==`, then the command's output, then `== run-test-suite.sh: gate typecheck exited <status> ==`. With `<none>`, the header is followed by `== run-test-suite.sh: gate typecheck not run: commands.typecheck is <none> ==` alone.
  - `== run-test-suite.sh: gate test (commands.test) ==`, then the command's output, then `== run-test-suite.sh: gate test exited <status> ==`.
- **The supervised flows get the same behaviour without a change to their labels.** `task_supervised` and `review_<n>_supervised` call the same wrapper, so they now run both gates. Their prose changes only where it says what the gates are.
- **The implementer contract (Task 6): a failure outside the unit's change is a downgrade, not a blocker.** A unit still runs the whole-tree `<typecheck_cmd>`. If that run fails and the unit can show that every reported failure lies outside its own change, it records an **evidence downgrade** and does not block, because each Phase G round now runs that same whole-tree command. Outside its change means the failure names no file the unit created or edited and no symbol it defined or changed. A failure the unit's change caused is still the unit's to fix, and one it cannot fix stays a transient blocker. A path-narrowed run is supplementary evidence, never reported as the whole-tree result. "Deferred to the Run gates phase" may name only `<test_cmd>`, the whole-tree `<typecheck_cmd>`, or a test file the suite runs.
- **The ledger ids `G` and `RG` stay.** Only their wording changes, to exactly `Run gates passed (the Run gates wrapper printed pass for typecheck and test)`, in the templates and in both autonomous forks' flip rules together (Task 7).
- **Adopters' copies, and remote runs.** The outer-loop scripts are written `create-if-absent` (`cli/src/generators/outerLoopScripts.ts` → `writeOuterLoopScripts`; `docs/cli.md` §3's outer-loop row). An already-wired repository therefore gets the new wrapper only through `init --force`, which takes a `.bak` first. `doctor` grades no script content. Remote runs need no change. `cli/templates/github/workflows/harness-run.yml` sets up no toolchain of its own: it runs `setup-worktree.sh`, which runs `commands.depInstall` and then `commands.build`. A unit's `<typecheck_cmd>` already runs in that same environment, so the whole-tree run has what it needs wherever the unit run did. Phase G runs remotely as it does locally.
- **Adopters' rendered `typecheck.sh` and `test.sh` are not touched.** The change lives in the harness-owned outer-loop script and in the instructions. The repository's own `scripts/run-test-suite.sh` and its own `harness-runs/test_run_logs/README.md` are kept byte-identical to their templates (Task 12). Its `harness-runs/README.md`, an older and drifted copy of `cli/templates/state-dir/README-root.md`, takes only the one `test_run_logs/` clause Task 3 rewrites in the template, and keeps its drift (Task 12). `scripts/run-gates.sh` is not edited.

**Top risks:**

- **A wording drift between the wrapper's log markers and what `test-fix-plan-writer` is told to read.** That would leave the fix loop unable to tell a static failure from a test failure. Tasks 1 and 8 both quote the exact marker lines above, and Task 2 pins them literally.
- **A half-updated corpus**, where one core says the round passes on the test verdict while another says both gates. The `## Scope register` below enumerates every reached file, and each owning task's verification re-runs the register's derivation command against its own targets.
- **The implementer rule loosening into a licence to skip a type-check failure the unit caused.** Task 6 keeps the caused-by-this-change case a blocker and requires the downgrade to name every failing check and why each lies outside the change.
