# Story: Parallel plan reviews — a round's gates fan out, the round node joins

## Context

This branch makes the plan-review gates of a round run at the same time instead of one after another, in the task-plan loop and in the user-review fix-plan loop. Nothing in a round depends on the order of its gates any more: every gate runs every round, every gate writes `review_<round>.md` every round, the writer already reads every findings file of the round, and no gate reads another gate's file of the **same** round — verified for this plan: the plan-review modes of `plugin/agents/task-plan-reviewer.md`, `plugin/agents/architecture-reviewer.md` and `plugin/agents/business-parity-reviewer.md` name no other gate's folder, and the only cross-gate read is `plugin/instructions/plan_review_rounds.md` → `## Converging mode` item 4, which reads the **previous** round's file through the revision note. So the change is a fan-out and a join, with tokens, `FAIL` rounds and what each reviewer checks unchanged, and no agent definition is edited. The work is cut bottom-up in the configured layer order: the `cli` layer (the gate library, the planning graph, the walker, the walker's suites, run analytics, the commit-path suite), then the `plugin` layer (the round module, the two loop cores, their forks, the two entry commands, the pause module, the flow documents), then the catch-all `general` layer (the schema and its fixtures, the static checker, this checkout's self-adopted copies, the documents of record, the roadmap).

**Driver-neutral by design.** Two drivers will walk the planning graph: today's orchestrator session, and the script of the script-driven planning pilot (#159), which runs every dispatch as its own headless session. Everything about the fan-out lives in the graph and the walker; the orchestrator core keeps only what #159 moves into its script anyway — the safety contract, heartbeats, PAUSE, commits, and how several dispatches are sent at once. Every rule below is one a script can follow by reading the walker's output and calling the walker.

**The graph becomes format 3** (Task 2 produces it; Tasks 3, 19 and 20 consume it). Format 2 does not fit: its gates encode a sequence in their edges, the writer's `returned` edge targets the first gate, and arriving at a round node closes the round, so a writer edge into the round node would close an empty round. In format 3: `formatVersion` is `3`; every `round` node carries `"parallel": true` — the graph's declaration that the round's gates are independent and **may** run at the same time, whether a driver runs them at once or one by one; every gate's `PASS`, `FAIL` and every `skip[].to` name its round node (`plan_round`), the `PASS` edges keeping their `report`; the writer's `returned` edge names `plan_round`; and `entries` reads `["plan_writer", "plan_round", "ui_writer", "ui_review", "convergence"]`, so **review** of a task-plan draft enters at the round node. Arriving at a round node over any edge other than one of its own gates' outcomes **opens** the round; the round **closes** only at the **join**, once every dispatched gate has recorded an outcome. The round's outcomes, the counter, the cap, `onCap`'s `{open_gates}` and `convergingFrom` are unchanged.

**What the walker prints and accepts** (Task 3 produces it; Tasks 4–8, 12, 13, 22 consume it). These are the wire, spelled once here and restated by every consumer:

- **The set.** Opening a round prints one dispatch block per **due gate** — a gate its `skip` constructs do not pass, both `passedByExclusion` and `skipped` resolved before the fan-out — in `gates` order. Each block is the existing dispatch form: `action: dispatch` / `node: <gate>` / `agent: <agent>` / `arg.iteration: <round number>` (the same in every block) / `arg.review_mode: full|converging` / then, **in the first block only**, the `skip:` / `round:` / `ledger:` lines for what the walk passed through, a skipped gate's `skip: <gate> <skipped|passed-by-exclusion>` among them / `heartbeat: <template, {iteration} = the counter>  (#<total_dispatches>)`. A one-gate set is byte-identical to today's single dispatch. A gate skipped at the fan-out is in no block and counts as passed; a round whose every gate is skipped closes `PASS` at once.
- **Recording.** `next --flow <flow> --branch <branch> --node <node> --outcome <outcome> [--findings <path>] [--skipped <ids|none>]`. `--node` names the gate whose return this is; it is **required while a set is pending**, and otherwise, when given, must name the pending node. Outcomes may be recorded **in any order**. An outcome for a node that is not a pending gate of the current round, a second outcome for one gate, and a missing `--node` while a set is pending are each refused with exit 1 and one `flow-walker:` line, leaving the state file byte-identical.
- **Wait.** While gates of the set are still out, a recording call prints `action: wait` / `node: <round node>` / `recorded: <gate> <outcome>` / one `pending: <gate>` line per gate still out, in `gates` order. The set's **last** outcome prints the round's result exactly as a round closing prints it today (a writer revision with its `round: <n> FAIL` line, the UI-test writer with `round: <n> PASS` and `ledger: P1`, the hand-off, or the cap escalation).
- **The held binding.** A gate's `error` or `blocker` is recorded like a verdict and **held**: at the join the walker prints it once — `action: binding` / `binding: <escalate>` / `node: <the first held gate in gates order>` / `agent: <its agent>` / `reason: <error|blocker>` / one `held: <gate> <error|blocker>` line per held gate, in `gates` order — instead of closing the round. No `round:` line is printed, the counter does not move, and the files of the verdicts already recorded stand.
- **`current`** stays read-only. While a set is pending it prints the blocks of the gates **with no recorded outcome**, in `gates` order, the first carrying the fan-out's passed-through lines. A gate whose reviewer wrote its file but whose `next` never ran is therefore dispatched again and replaces its own file (`plan_review_rounds.md` → `## The round file`); only `start` reads files on disk.
- **`start`** entering a round (`--entry plan_round`) reads the round evidence. No round file: round 0, the whole set. A round with files missing whose evidence is **consistent** — every gate that has a round file holds exactly one verdict line, and no plan file postdates the round's earliest review file — records the present verdicts and dispatches only the gates without a file, at counter 0. Any other incomplete round restarts with the whole set, each gate replacing its file. A complete round keeps today's rules (all `PASS` or unreadable: the whole set again; a `FAIL` with the next revision note on disk: the next round's whole set; a `FAIL` without it: the round closes and the writer revises).
- **Concurrency.** `start` and `next` serialise their state writes on a lock directory, `<state_dir>/.flow_walker_state.lock`, taken with `mkdir` (atomic on macOS and Linux), kept empty so git never lists it, released on every exit path, treated as stale once `find <lock> -maxdepth 0 -mmin +1` prints it, and waited for at most 120 s before an exit 2 whose one line names the lock and the manual way on (remove it with `rmdir` once no walker call is running, then run `current`). Exactly one of several simultaneous recording calls prints the round's result. `current` reads without the lock: the state file is replaced by `mv`.

Task 22 records two decisions above, with their reasons, in `docs/flow-graph-walker.md`. The first the task prompt left to the planner: `--node` on `next`, because the walker can then refuse a non-pending or duplicate gate by name and a per-gate session can record its own outcome without knowing the others'. The second is a **deliberate departure from the prompt's wording** — its **Partial returns** bullet has *"the walker's `start` and `current` print only the gates without a valid round file"*: `current` is keyed on recorded outcomes rather than files, because `current` is read-only, so a gate whose file it skipped would never have its outcome recorded and the round could never close. In every case the prompt names the two rules give the same result; they differ only for a gate whose reviewer wrote its file but whose `next` never ran, which `current` dispatches again (the reviewer replaces its own file) while `start`, which reads files, records it.

**Schema after graph — a deliberate departure from contract-before-consumer.** `.claude/context/conventions.md` → `### The order files are created, so a half-built feature is still coherent` puts a contract ahead of its consumers; here the format-3 schema (Task 19, `general`) lands after the graph (Task 2) and the walker (Task 3) that consume it, so for the commits in between the branch carries a graph its own schema rejects. Layer order wins for three reasons: the plan ships a capability split across layers bottom-up in the configured layer order with the catch-all `general` layer last; Task 19 derives every fixture by copying Task 2's finished graph, so moving it first would make it author the format-3 shape a second time and invert that dependency; and no gate reads the graph against the schema or the static checks before Phase G (gates 3c, 3d and 3e, after every task), so no gate ever observes the gap. The format-3 shape itself is spelled once in this `## Context`, which both sides restate.

**The orchestrator side** (Task 12 states it in the task-plan core; Task 15 in the fix-plan core; the pause and overload mechanics of a set once, in `plugin/instructions/autonomous_pause_and_ledger.md` — Task 17 — which the autonomous forks, Tasks 13 and 16, cite and bind with their own values without restating). Before a set goes out, the STOP check, the `.dispatch_counter` increment and the heartbeat run once **per block**, in printed order; a halt at any block sends none of the set. A fork's PAUSE check runs **once**, before the set's first block. Then every dispatch of the set goes out in **one message**, as foreground `Agent` calls — never `run_in_background` — so they run concurrently; a run that sends them one at a time produces the same round, which is why that is a driver choice and changes neither the graph nor the walker. Each return is recorded with `next --node` as it is read. A PAUSE placed while a set is out is honoured at the join: every return is in and recorded, the walker printed the round's result, the autonomous fork's per-round commit landed, and the next dispatch's PAUSE check pauses with a partial commit that exits 3; resuming continues at the writer revision (a `FAIL` round) or at `ui_writer` (a `PASS` round). An overload that kills some dispatches of a set leaves the returned verdicts recorded and their files standing; only the dead gates are re-dispatched, `current` printing exactly those. `MAX_TOTAL_DISPATCHES` and the sizing sentence keep their numbers, because a round still dispatches exactly four agents.

**The user-review fix-plan loop keeps its routing in prose** (Task 15), stated in one place and in the walker's terms — **due gates**, **join**, **held binding** — so a later port to a graph translates it one-to-one. Steps 7 and 8 keep their numbers (they are cited from outside) and go out together once step 6 has cleared; the round close runs at the join. Its autonomous fork (Task 16) gets Part 2's pause and overload rules; its resume still restarts the whole round, both gates together, because its orchestrator reads no verdict line.

> Assumption: the task prompt's *"Verify headless concurrency in a `claude -p` orchestrator session"* cannot be settled inside this run: whether several foreground `Agent` calls in one message overlap is a timing observation, and the lessons ledger bars a run from making its own in-session timing its evidence. The cores state the one-message foreground form now, because it is correct whether or not the calls overlap — at worst the set runs serially, as today. Task 24 records the by-hand probe that settles it as `docs/sandbox-verification.md` row BG11, owed, and the maintainer takes it (`Manual setup required:` below). Reversible: if the probe shows no overlap, only the wall-time claim is wrong, and the forms and the walker stand.

> Assumption: the new `"parallel": true` is required and fixed to `true` on every round node, rather than a switch a graph may set to `false`. The prompt asks the graph to **declare** independence, and a sequential round would need a second walker mode no flow asks for. Reversible: a later format can widen the constant to a boolean.

**Top risks:** the first is a round that never closes or closes twice — a lost or duplicated outcome under concurrent `next` calls; Task 3's lock and refusals guard it, and Task 6 drives simultaneous calls through the CLI alone and asserts exactly one round result. The second is a resume that dispatches the wrong subset — Task 1 judges plan freshness against every present round file, Task 3 restates `start`'s evidence rule and `current`'s pending set, and Tasks 5 and 7 pin the partial-return and resume cases, including only the missing gate after an `error`. The third is drift between the walker's new output and the prose that acts on it, in two loops and their forks — the wire is spelled once above, Task 12 maps each printed line to an orchestrator act, Task 15 states the fix-plan loop in the same three terms, and Tasks 19–20 hold the graph to format 3 statically.
