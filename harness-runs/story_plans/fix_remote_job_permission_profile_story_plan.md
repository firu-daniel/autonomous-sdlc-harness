# Story: A remote job gets a permission profile that can read the plugin

## Context

Gate 12's first hand-run against 0.4.0 found that every remote run on a GitHub-hosted runner parks on its first read of a plugin instruction file, and that nothing in `init`, `doctor` or the job's preflight notices before the session launches. This branch closes the defects that run found: the job's profile grants nothing over the plugin root, `init` leaves the profile committable, the preflight lets an unusable profile through, `doctor` cannot see the missing grant, and four documents describe a setup that does not work (the committed `settings.json`, the default-branch push, the `workflow` token scope, and self-hosting). The version bump to 0.4.1 and the Gate 12 re-run are out of scope (task prompt → `## Out of scope`).

**The decisions this plan takes, and where it departs from the prompt's candidate approaches.**

- **The `Read` exemption is narrowed to the one shape that was measured, not dropped for the job alone.** The 2026-08-26 measurement (`cli/src/doctor/checks.ts` → `PLUGIN_PERMISSIONS_CHECK`'s header) was taken on a `directory`-sourced marketplace, where the install root is a cache snapshot that the runtime does *not* substitute; reads there succeeded while reads at the runtime root were refused. Gate 12 round 1 ran a GitHub-sourced marketplace, where the two roots are one directory, and reads there were refused. So the rule becomes: a `Read` grant is required at the **runtime root** — the root `machine/plugins.ts` → `pluginRuntimeRoot` answers, which is the install root itself wherever the two collapse — and is exempt only at an install root that is *not* also the runtime root. A job-only switch would leave a git-sourced adopter's local machine in the same unmeasured shape the runner just refused. One builder serves `init` and `doctor` (Task 2), so the two still cannot differ.
- **The shell-readable grant is two mechanisms, deliberately.** `init --plugin-root-entries` adds every resolved plugin root to the profile's `permissions.additionalDirectories` (Task 3), and the watcher, in job mode only, passes each of the profile's `additionalDirectories` entries as an `--add-dir` at launch (Task 7). Run 3 showed a committed `settings.json` `additionalDirectories` entry not taking effect for reasons nobody established, so the launch flag is the belt to the profile's braces — the same stance the watcher header already takes for the state directory.
- **The profile is gitignored for every adopter, not only a remote one.** It carries one checkout's absolute paths, the watcher reads it from the main checkout and never from a worktree, and this repository already ignores it by hand for that reason (root `.gitignore`, the `Added by hand in this repository` comment). Task 1 adds the rule to the managed block; Task 3 makes `init`'s note say so. **The consequence is a changed onboarding:** a teammate's fresh clone no longer carries a profile, so `doctor`'s `permission-profile` check would fail on it — the teammate now runs `npx autonomous-sdlc-harness init` once after cloning, which generates the machine-local profile, and then `doctor`. Task 3 rewrites the second `init` note that states the old onboarding (`cli/src/generators/projectSettings.ts`, *"There is no second init"*), and Task 10 the `README.md` → **F. A teammate clones** step list. **The second consequence is for worktrees:** `init`'s first commit (`cli/src/core/git.ts` → `commitAll`, `git add -A`) stops carrying the profile, so no `git worktree add` checkout — every run's working copy — has one. The watcher is unaffected (it loads `$MAIN_REPO/.claude/settings.autonomous.json`), but `doctor` read the profile from the checkout it runs in and would `FAIL permission-profile` in every worktree with a remedy that sends the operator to run `init` there. So **`doctor` in a linked worktree grades the main checkout's profile** — the one a run loads — against the worktree's own root, resolved through a new `cli/src/core/git.ts` → `mainWorktreeRoot` that mirrors the watcher's `hr_main_repo` (Task 12, which ships first so that Task 1 lands on it and `cli/test/doctor.test.mjs`'s sibling-worktree case never breaks). A remote job's checkout is a main checkout, so there it grades the job checkout's own profile, as before.
- **The setup push the code prints changes with the documents.** `init`'s remote-execution note (`cli/src/commands/init.ts` → `reportGithubSteps`) and `doctor`'s `remote-execution` remedy both print `git push origin <defaultBranch>`, which the `pre-push` hook `init` installs refuses. Task 11 makes them print `gh auth refresh -s workflow` then `git push --no-verify origin <defaultBranch>`, and Tasks 8 and 10 print the same commands in the documents. **In the code, those commands and their reasons have one producer:** a new `cli/src/core/defaultBranchPush.ts`, created by Task 4 with the push command and its `--no-verify` reason and extended by Task 11 with the `workflow`-scope command and its reason (`.claude/context/conventions.md` → `## Shared code, and where it lives`). Its three consumers — `cli/src/doctor/checks.ts` → `profileUntrackRemedy` (Tasks 4 and 5), `cli/src/commands/init.ts` → `reportGithubSteps` and `checks.ts` → `REMOTE_EXECUTION_CHECK` (Task 11) — import the values and spell none of them, so `grep -rn "no-verify origin" cli/src` finds the spelling in that module alone.
- **A profile committed by an earlier release is not rewritten by the job; the job stops.** The job's changed-tracked-files check forbids rewriting a tracked file, so the job cannot regenerate over one. Instead `doctor` gains a `--remote-job` switch (Task 4) under which `profile-paths` and `plugin-permissions` fail rather than warn, and a new `profile-tracked` check (Task 5) fails naming the untrack command; the job's preflight passes the switch (Task 6).
- **Finding 5 is corrected, not made true.** Nothing here can establish why Run 3's committed `settings.json` entries did not apply; the documents stop promising that they do, record Run 3 as the measured negative, and point at the two mechanisms above as the job's route (Task 8).

Task numbering is ship order, with two exceptions, both added in plan revision: **Task 12** ships **first**, before Task 1, and **Task 11** ships **ninth** — after Task 7 and before Tasks 8, 9 and 10 — as the readiness list below orders them. The nine `cli` tasks come first; the three `general` tasks document what they built and ship last. Six files are edited by more than one task, each time sequentially and under a `**Depends on:**` link or a shared-file note, with each task file stating which part it owns: `cli/src/core/git.ts` (Tasks 12, 5), `cli/src/core/defaultBranchPush.ts` (Tasks 4, 11), `cli/src/generators/permissionProfile.ts` (Tasks 2, 3), `cli/src/doctor/checks.ts` (Tasks 12, 2, 4, 5, 11), `cli/test/doctor.test.mjs` (Tasks 12, 2, 4, 5, 11) and `cli/test/init.test.mjs` (Tasks 1, 2, 3, 11).

**Top risks:** the likeliest failure is that a `Read` rule and an `additionalDirectories` entry in the `--settings` profile are refused on the runner exactly as the committed `settings.json` entries were in Run 3 — Task 7's launch-time `--add-dir` is the guard, and the Gate 12 re-run is the only thing that can prove either; nothing in this branch may claim it has. The second is a grading change that turns every git-sourced local adoption's `plugin-permissions` from pass to warn without saying why — Task 2 guards it by putting the measurement correction in the check's own report text and header, and Task 9 in `docs/cli.md`. The third is documents and printed notes that go on describing the old setup — the `## Scope register` below enumerates every corpus site the derivation reaches, Tasks 8–10 own the ones that change, and Tasks 3 and 11 keep `init`'s and `doctor`'s own printed text in step with them, with `cli/test/init.test.mjs` pinning the setup commands and `cli/src/core/defaultBranchPush.ts` (Tasks 4 and 11) the single place in `cli/src` that spells them.
