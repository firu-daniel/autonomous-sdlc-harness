# Story: Stop handing the task agent credentials it does not need

## Context

This branch narrows what credential the unattended session can reach, on GitHub and locally, without giving up per-commit pushing. The agent reads untrusted text (the task prompt, review files, answers), so every credential it can read is one an injected instruction can try to leak. `feat_unattended_bash_sandbox` already unsets six token names for **sandboxed Bash**. This branch covers the rest of the session — the `claude` process, and through it hooks, local MCP servers and the four excluded wrappers — plus the push credential itself, the commits that get pushed, and the local environment.

**What the code shows today (checked on this branch's base, `a819a1e8`).** `harness-run.yml`'s `run` job sets `GH_TOKEN: ${{ github.token }}` and `HARNESS_PUSH_URL` at job level. Its checkout persists `secrets.HARNESS_GIT_TOKEN || github.token` into `.git/config` as an `extraheader`. Its `Open the draft pull request` and `Open the pull request and report` steps carry `HARNESS_PR_TOKEN: ${{ secrets.HARNESS_GIT_TOKEN }}`. `autonomous-watcher.sh` → `spawn_engine` launches the agent with `exec "$AGENT_CLI" -p …` inside a `{ … }` group of its launch subshell. That subshell exports only `HARNESS_MAIN_REPO` and `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` and strips nothing. The outer `( … )` subshell then runs `record_run_analytics` and `classify_run_exit`, which still report through `remote-run.sh`, so they still need the token. **Nothing in the session reads the GitHub tokens.** A grep of `plugin/`, `commit-on-branch.sh`, `push-branch.sh`, `refresh-branch.sh`, `launch-sandboxed-gates.sh`, `lib/harness-run-lib.sh`, `run-test-suite.sh`, `docs-search-server.sh`, `scratch-run.sh` and `flow-walker.sh` for `GH_TOKEN|GITHUB_TOKEN|HARNESS_PR_TOKEN|HARNESS_PUSH_URL|HARNESS_GIT_TOKEN`, and of `plugin/` for a `gh` call, found none. `HARNESS_PUSH_URL` is read only by `autonomous-notify.sh`, which only the watcher runs. The mention reader's precedent is `remote-run.sh` → `control_mention_session` (`unset GH_TOKEN GITHUB_TOKEN HARNESS_PR_TOKEN`) and `mention_has_credential`, whose base64 form is computed from `GH_TOKEN` as `printf 'x-access-token:%s'`.

**The design, goal by goal.**

- **Goal 1 — the session's environment (Task 4).** The watcher strips a fixed set of names from the agent's environment, in both modes. `spawn_engine` reads the names, and refuses a launch whose names it cannot read, in its own shell before the launch subshell, as its existing pre-launch refusals do. The `{ … exec }` group only `unset`s that precomputed list, after `keep_awake_start` and before `exec`, so `record_run_analytics`, `classify_run_exit` and the watcher's own passes keep the tokens. The set is every `sandbox.credentials.envVars[].name` of the `--settings` file being passed, minus the agent's own credential (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`), plus two names the watcher owns: `HARNESS_PUSH_URL`, which has no reader in the session, and `HARNESS_GIT_TOKEN`. So the profile stays the single owner of the token names. This is **hygiene that blocks casual reads**, and the docs say so. It becomes a boundary only alongside the sandbox's PID namespace and no-new-privileges, which `docs/sandbox-record.md` → `## 5. The Linux runner's PID namespace and no-new-privileges` records as **pass** (PN1–PN3, NN1–NN2) on the GitHub-hosted `ubuntu-26.04` image `20261101.186.1` only. No self-hosted runner, `ubuntu-24.04` or other image is measured, and there the plan treats both as unverified.
- **Goal 2 — every commit is still pushed as it lands.** No design here moves pushing to the end of the job. The in-session `push-branch.sh` calls stay synchronous, and the end-of-job `Push the branch` step stays a backstop. **A workflow-file change fails the run visibly at its first push (Tasks 3, 4 and 5; clarification answer 1, Q2 item 2).** A job now pushes only with `github.token`, which cannot write `.github/workflows/`, so one such commit would make that push and every later one fail with nothing but a `push failed for` line. So `push-branch.sh` refuses it first. It refuses only while the main checkout carries the **job push-credential marker** `harness.pushCredential job-token`. Task 2 makes `lib/harness-run-lib.sh` the marker's one owner (`HR_PUSH_CREDENTIAL_KEY`, `HR_PUSH_CREDENTIAL_JOB_TOKEN` and the read-only `hr_push_credential_is_job_token`), Task 3's `push-branch.sh` reads it only through that predicate, Task 5's `push-credential store` sets it in the job only through those constants, and the session cannot write it. Neither script spells the key or the value, so the reader and the writer cannot drift (architecture review round 3, Must Fix 1). The refusal goes through the same push-refusal record the credential scan uses, the watcher fails the run at once with that reason, and the wrapper still exits 0. The mode comes from that record, never from `GITHUB_ACTIONS` (`harness-runs/lessons.md` → *Trust checks*). Paths match at the repository root only, so `cli/templates/github/workflows/` stays an ordinary directory. A merge's changes count against its first parent. Whether GitHub refuses a push whose only workflow change arrives through a default-branch merge is unmeasured, and roadmap item 35 measures it. Tasks 6, 11 and 12 document the limit in `harness-run.yml`'s header, `docs/remote-execution.md` with the upgrade note, and `docs/github-issue-trigger.md`.
- **Goal 3 — the push credential (Tasks 5, 6 and 13).** The baseline is required: **`HARNESS_GIT_TOKEN` is never referenced in the `run` job.** `Open the draft pull request` moves into a new agent-free `open` job before `run`, and `Open the pull request and report` into a new agent-free `deliver` job after it. Each job checks out and runs the **default branch's** scripts, as `collect` already does. That way a branch a previous session wrote never runs beside `HARNESS_GIT_TOKEN`. Only `github.token` pushes in `run`. It is scoped to the repository, expires with the job, and cannot write `.github/workflows/`, which `docs/github-integration-research.md` S1 already records as measured.
  - **On top of the baseline, the push credential leaves the checkout.** The `run` checkout sets `persist-credentials: false`. A new `remote-run.sh push-credential store` step writes `github.token` into `~/.git-credentials` through git's `store` helper, scoped to the repository's path, with the helper named in the checkout's local config as `store --file <absolute path>`. That config line is also where `push-branch.sh`'s scan finds the file (Tasks 2 and 3). In a job it is the only route by which the scan knows the job token, and the session cannot write it, so the path never comes from `HOME`. A final `push-credential erase` step removes exactly that entry. The read-deny on `~/.git-credentials` is **derived from the profile, not measured on this file**: `cli/templates/claude/settings.autonomous.json` names it in `sandbox.credentials.files` (read-denied to a sandboxed command) and so in its `Read` deny pair (the file tools), the same mechanism S1 (runner) and S2 (runner) measured **pass** on `~/.ssh`. S1/S2 (runner) are cited only as measuring that mechanism, never this file; the direct measurement — a sandboxed read and a `Read` of `~/.git-credentials` — is owed to roadmap item 35 (Task 10). So, by derivation, the cheapest read — `cat .git/config` or a `Read` of it — no longer yields a token, while every unsandboxed git (the excluded wrappers, the end-of-job push, `remote-run.sh`) still authenticates.
  - **What this route assumes.** It assumes what the "watcher pushes" candidate assumes — the read-deny, no `sudo` (NN1–NN2) and a hidden watcher `environ` (PN1–PN3), which still holds `GH_TOKEN` — without that candidate's hand-off. It is measured on the hosted `ubuntu-26.04` image only, and is hygiene elsewhere.
  - **Why not the other candidates.** The staging remote costs every adopter a second repository, and strands every commit of a run whose promoting job never runs. The concurrent pusher stays rejected: its hand-off needs an in-job credential that is just as readable. Task 11 records both.
  - **CI on the final tip.** The design also moves how CI is reached. `github.token` pushes start no workflow, so `deliver` makes the draft→ready flip with `HARNESS_GIT_TOKEN` when it is set. That gives the adopter's CI a `pull_request` `ready_for_review` event on the final tip, beside the `opened` event the `open` job's create already gives. **The event fires only on a draft→ready transition, so `deliver` re-toggles on every run** (Task 5; clarification answer 1, Q2 item 1, which prefers the re-toggle when it needs no extra permission). When `HARNESS_GIT_TOKEN` is set and the pull request is already ready (a person marked it ready, a round's own `--undo` was refused, a resumed run), `deliver` turns it back to a draft with the job's token (`gh pr ready --undo`) and then marks it ready with `HARNESS_GIT_TOKEN`. Both calls sit under the `pull-requests: write` grant `deliver` already holds, and `round` already runs `--undo` under that grant. `harness-control.yml` listens to `pull_request: closed` only, so the conversion starts none of the harness's own workflows. **The gap it leaves, stated in Task 11's decision block and upgrade note:** on a plan without drafts the conversion is refused, so a later run's final tip gets no `ready_for_review` and no CI. Roadmap item 35 measures both the re-toggle and this gap (Task 10). Close-and-reopen is rejected because it fires `harness-control.yml`'s `pull_request: closed` handler. A `workflow_dispatch` of the adopter's CI is rejected because it needs a new key naming the adopter's workflows.
  - **The cost.** An adopter's CI must list `ready_for_review` among its `pull_request` types to run on the final tip, and reviewers may see a *converted to draft* event at each run's end. A task that edits `.github/workflows/*` can no longer push from a job at all, and it must run locally (goal 2's refusal). Clarification answer 1, Q2 accepted both costs.
  - **The setup guidance `init` prints (Task 13).** `cli/src/commands/init.ts` → `reportGithubSteps`, step 3, tells every adopter today that `HARNESS_GIT_TOKEN` makes *"the job's pushes trigger your own CI"* — the reason this goal replaces. Task 13 rewords it: the token opens the draft pull request and flips it ready, so CI runs on `opened` and `ready_for_review`; pushes made by the job never trigger CI; the CI workflow must list `ready_for_review`. Its documentation mirrors are Tasks 11 and 12's.
- **Goal 4 — no pushed commit carries a credential (Tasks 2, 3, 4 and 5).** The mention reader's check moves into `lib/harness-run-lib.sh` as one predicate, and the mention reader calls it. `push-branch.sh` runs it over the commits it would send. It runs after the remote checks and before the push, so it fits the wrapper's existing order. On a hit the wrapper prints a `refusing to push:` line that never carries the value, and pushes nothing. It still exits 0, so it keeps its exit contract. It also writes a **push-refusal record** under the main checkout's `.git/`, which no sandboxed command and no file tool can write. The watcher acts on that record in both modes, whatever its reason: it stops the session, marks the run `failed` with detail `push refused: <reason>`, notifies, and in a job adds an `::error::` annotation and ends with decision `stop`. **The watcher writes nothing to the job summary.** The summary's row has one writer, `remote-run.sh` → `verb_save`, whose `### harness run <branch>` row carries that `failed` detail (architecture review round 2, Must Fix 1). The end-of-job `Push the branch` step already turns a `refusing to push` line into an annotation.
- **Goal 5 — local runs scrub the environment (Tasks 1, 2, 4 and 9).** Locally the watcher launches the agent under an **allow-list**. It keeps a fixed base set (`SESSION_ENV_BASE` in the watcher) plus the adopter's new `sandbox.passEnv` names, `spawn_engine` computes every other exported name before the launch subshell, and the launch group unsets them — never `env -i` with values on a command line. Goal 1's strip set is added on top, so the profile's token names are removed even when `sandbox.passEnv` lists one. The base set covers the excluded wrappers' SSH push and HTTPS push: the credential helpers' session-bus, `gh` config and `GCM_` names. A local HTTPS push that authenticated through `GH_TOKEN`/`GITHUB_TOKEN` stops working, and Tasks 4 and 8 give the way on. Job mode keeps goal 1's strip only, because a job's environment is the runner's, not a person's shell.
- **Goal 6 — docs (Tasks 6, 7, 8 and 10–12).** The decision is stated once, in `docs/remote-execution.md` (Task 11). Every other document cites it rather than restating it.

**The order, and one deliberate departure.** Ship order is the configured layer order: `cli`, then `plugin`, then the catch-all `general` last. That puts the `sandbox.passEnv` schema property (Task 9) after its model and check (Task 1), which reverses `.claude/context/conventions.md` → `### The order files are created, so a half-built feature is still coherent` for that one key. The branch is reviewed and merged as a whole, and no intermediate commit is released, so the merged tree carries all four places of the contract. Task 1's file says so. Within `general`, the documents that own a heading come before the documents that cite it: `docs/watcher.md` (Task 8) before `docs/config.md` (Task 9), and roadmap item 35 (Task 10) before `docs/remote-execution.md` (Task 11), before the documents that cite it (Task 12). No two tasks edit the same file. Task 13 was added in review round 0 and keeps its number so no other task's file is renumbered: it ships seventh, the last `cli` task, after Task 6 whose design its printed step restates and before the `plugin` task.

**What needs a release, not this branch.** A `harness-run.yml` job installs the plugin at the release tag and runs the CLI from npm. So this branch pins its GitHub-side behaviour **by test**: the launch-line strip (Task 4), the rendered workflow (Task 6) and the push scan (Task 3). It measures nothing on GitHub. The real-run measurement happens after this branch's own release, against a repository re-rendered with `init --upgrade-workflows`. It checks that per-commit pushes land with the stored `github.token`, that `GH_TOKEN` is absent from the agent's `environ`, that adopter CI runs on `opened` and on `ready_for_review` made with `HARNESS_GIT_TOKEN`, and whether a job's runner receives every secret the job references at start. That measurement is roadmap item 35, whose row Task 10 adds. A result that disagrees with the design is a follow-up fix, not a silent docs edit. This repository's own `scripts/` copies are protected outer-loop paths for this run and are re-rendered after merge, as `chore: re-render outer-loop scripts after #304 (#308)` was.

**Top risks:** The likeliest failure is a push that silently stops authenticating once the checkout no longer persists its credential, which would break goal 2 on every GitHub run. Task 5 guards it with a fixture test that `git credential fill` returns the stored token for the repository's URL and that an operator's own `~/.git-credentials` entry survives store and erase. Task 6 guards it by placing the store step before every step that reaches origin and the erase step after `Push the branch`. The second risk is an adopter's CI that quietly stops running on the harness's pull requests. Task 5 makes the `ready_for_review` flip with `HARNESS_GIT_TOKEN`, re-toggles a pull request that is already ready so the event fires on every run, and logs which token made it. Task 11 puts the one CI change an adopter must make, and the no-drafts gap, into the upgrade note, and roadmap item 35 (Task 10) measures it. A related risk is the workflow-file refusal failing runs whose only workflow change came in through a default-branch merge. Task 3 counts such merges conservatively, and roadmap item 35 measures whether GitHub would have refused that push. The third risk is the local allow-list stripping something a gate, the retrieval server or an excluded wrapper's SSH push needs. Task 4 guards it in three ways. It derives its base set from a grep of every session-side reader and from a walk of the HTTPS credential helpers. It refuses the launch rather than launching unscrubbed when the config cannot be read, from `spawn_engine`'s own shell, where a refusal reaches its caller. And a test grades that refusal on the registry and the notifier.
