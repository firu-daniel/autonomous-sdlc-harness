# Story: Improvement observations name every path repo-relative, and are checked for machine paths before they are committed

## Context

The improvement-observations intake (`plugin/instructions/improvement_observations_instructions.md`) is the one run artifact whose job is to quote what happened, and it quotes command output as written. When that output held an absolute path, the path went into the file, was committed, and reached `dev`: four intake files carried the running user's home path inside a quoted `gitdir:` line until `fix_gate_6a_worktree_git_file` (#26) removed it by hand. Nothing in the instructions stops it happening again. They say where the file is **written** (an absolute, `$REPO_ROOT`-anchored path) and nothing about the paths written **inside** it.

This branch closes that in the instructions themselves: a **content rule** in `## The entry format` that every path inside an entry is repo-relative, quoted command output included, and a **machine-path check** in `## Commit mechanics` that runs over the written file before the commit wrapper, rewrites any hit by that rule, and never commits a file that still carries one. Every other document that paraphrases the entry format or what happens between the intake write and its commit is brought into line. The work is cut into five single-layer tasks in the configured layer order — `cli`, then `plugin`, then the catch-all `general` last: the adopter-facing template README that describes the intake (Task 1), the content rule (Task 2), the check (Task 3), the plugin files that paraphrase the commit step (Task 4), and this repository's own init-written copy of the Task 1 template (Task 5).

**What this plan established, so no implementer re-derives it.**

- **What the check matches.** Two needle sources, both read as literals from a **bare**, allow-listed, single-statement command whose output the orchestrator reads — never a substitution, never a shell variable, per the checkout-root rule in `.claude/CLAUDE.md`: every line beginning `worktree ` in `git worktree list --porcelain` (the first is the main checkout, this run's own checkout is among them, and sibling worktrees are covered wherever they sit — `create-worktree.sh` accepts an override directory, so no prefix relationship between them is assumed), and the home directory from `jq -nr env.HOME`. The home directory is what gate 6a greps for (`scripts/run-gates.sh` → `machine_path_hits`), so the check is at least as strict as the gate it protects; the checkout roots cover an adopter whose checkouts sit outside the home directory, where a home-only needle would miss them. `jq` is chosen because it prints the home directory with no shell expansion in the command string at all, and it is already a prerequisite of the plugin's guards (`plugin/hooks/README.md` → `## Prerequisites`). The matcher is one `grep -nF -e <needle> … <absolute intake path>`: `grep`, `git worktree` and `jq` each have their own entry in the generated unattended profile (`cli/templates/claude/settings.autonomous.json` → `permissions.allow`), and the command carries no `$`, no pipe and no redirect. `grep`'s exit status is the verdict: `1` clean, `0` hit, `2` could not run.
- **Which files quote what happens between the intake write and its commit.** The forks' `Override I` **Commits + pushes** bullets (both autonomous forks) and the task fork's commit-point entries 5 and 8 (`plan_orchestration_instructions_autonomous.md` → **Autonomous-fork commit points — the clean-tree invariant**) describe the commit step's own behaviour, and change (Task 4). `plugin/docs/AUTONOMOUS_FLOW.md` → `## Improvement observations` summarises the entry format and the commit contract, and changes (Task 4). The sites that name the intake only as a **position** in Phase D's order — the `D` and `R5` ledger bullets, `autonomous_pause_and_ledger.md` `### 1.8`, both forks' `Override J` openings, `AUTONOMOUS_FLOW.md` step 5 and `AUTONOMOUS_FLOW_WHITEBOARD.md` — do not change: the check sits inside the intake step and moves nothing in that order. `clarification_digest_instructions.md` → `## Commit mechanics` imports "the reasoning plus the four wrapper exit codes" from the observations `## Commit mechanics` "unchanged"; the check is neither, and Task 3 says so in the check's own paragraph, so the digest neither gains the check nor needs an edit. The digest's `## Where it is written` also imports the observations **Write mechanics — absolute write, repo-relative commit.** paragraph by pointer, so no task edits that paragraph; Task 2's content rule, including its argument-versus-content sentence, lives only in `## The entry format`. The full enumeration is `## Scope register` below.
- **Whether another agent-written artifact class leaked a machine path into `dev`.** Measured with `git log dev -S"$HOME" --name-only --format='@@ %h %s'` and, for any user's home rather than this one's, `git log dev -G'(/Users/|/home/)[A-Za-z0-9._-]+/' --name-only --format='@@ %h' -- harness-runs`. Every commit either command reaches touches one of three artifact families only: `harness-runs/improvement_observations/` (the four files above, added in #4, #8, #9 and #14, cleaned in #26), `harness-runs/task_prompts/` (hand-written, out of scope by the task prompt), and `harness-runs/architecture_reviews/chore_gate_10_real_catalog_measurement/review_0.md` (out of scope by the task prompt: it names an external corpus outside the repository). **No other agent-written artifact class has carried a machine path in `dev`'s history.** Nothing outside improvement observations changes on this branch; the clarification digest, which also carries enumerated content verbatim, has not leaked and is not touched.
- **Gate baseline.** `bash scripts/run-gates.sh` on this branch's base, before any edit, fails exactly two gates: `1a plugin manifest` (`--strict` promotes the six unquoted-`${CLAUDE_PLUGIN_ROOT}` hook-command warnings in `plugin/hooks/hooks.json` to errors) and `11 docs-retrieval relevance floor` (the retrieval runtime's optional peers are not installed in this checkout). Gate 6a passes. "No new failure" means that set and no other.

**Cross-task names, fixed here so every task spells them the same.** Task 2's rule opens with the bold lead **`Every path in an entry is repo-relative.`** inside `## The entry format`; Task 3's check opens with the bold lead **`Machine-path check — before every wrapper call.`** inside `## Commit mechanics`. Every citer (Tasks 1, 3 and 4) names them by heading plus that lead, never by line.

**Top risks:** the likeliest failure is a check that an unattended run cannot issue — one needle spelled as `$HOME` or a `$(…)`, or the rule silently written as a compound — which would park every run at Phase D on a prompt nobody answers; Task 3 fixes the needle commands and the single-statement `grep` form, and its verification runs each command exactly as written. The second is the check leaking into a document that imports part of `## Commit mechanics` "unchanged" (the clarification digest) or, the other way, a paraphrasing fork left describing a commit step with no check in it; Task 3's scope sentence and Task 4's edits, both enumerated in `## Scope register`, guard that. The third is this branch doing what it forbids: the acceptance sample in Task 3 carries a real machine path by design, so it lives only in the gitignored `<state_dir>/scratch/`, is removed before any gate runs, and its recorded outputs are written with the machine prefix already rewritten; Task 5's full gate run is the backstop.
