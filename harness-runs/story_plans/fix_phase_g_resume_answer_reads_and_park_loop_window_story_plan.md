# Story: Keep the orchestrator out of Phase G answer files, and stop the park-loop guard holding a progressing run

## Context

#275 §2 took four real watcher runs over the answered `fixable: 0` park on a throwaway adopter (2026-11-06; `docs/sandbox-verification.md` §7 → *The answered `fixable: 0` park, on a throwaway adopter*, rows AP1 and AP6 and the paragraph **The park-loop guard on a fast adopter.**). They found two defects. This branch fixes both.

**Defect 1: the orchestrator reads Phase G answer files.** The contract is that only `test-fix-plan-writer` reads a Phase G park's answer. The orchestrator passes the paths in G.2's `Park answer:` clause and never opens either file (`plugin/instructions/plan_orchestration_instructions_core.md` → `### G.0 Resolve the round`, `### G.2 Write and review the test fix plan`, `## What you must NOT do`). In every observed Phase G resume, the orchestrator opened the answer file as soon as the engine launched, before G.0 ran. In runs B and C it also quoted earlier answers into the new question files it wrote. The cause is the watcher's resume prompt (`cli/templates/scripts/autonomous-watcher.sh` → `spawn_engine`, `resume_clause`), which tells the session to *"consume ALL of these answer files"*. That instruction suits the planning fork's Override 2(a), and it contradicts G.0 for a Phase G pair. The fix has three parts:

- **The watcher** still names every answer file, but no longer tells the session to consume them. It says a Phase G pair belongs to G.0 and to `test-fix-plan-writer` (Task 1).
- **The plugin** says the same at each place an orchestrator meets a Phase G pair. That is the core's G.2 and its must-not list, which gain a paths-only rule for question files (Task 3), plus the two planning forks' Override 2(a) and the user-review fix fork's **On resume** paragraph (Tasks 3 and 4).
- **The pins.** Task 5 pins those plugin strings in `cli/test/run-gates-park-answer.test.mjs`.

**Defect 2: the park-loop guard holds a run that is making progress.** `docs/watcher.md` §4 counts a park-resume as a no-progress cycle when either detector fires: no question file above the baseline index, or a re-park inside `PARK_LOOP_WINDOW_SECS` (300). In run B the window fired on its own, twice (98 s, then 215 s). Both resumes had raised a higher-indexed question, and the second had run and committed a whole gate round. Two honest answers put the run on hold. Task 2 makes the index detector the only one and retires the window. Task 6 updates `docs/watcher.md` §4 and the other documents that describe the window.

**Decision — the progress rule (the task prompt offers two forms; this plan takes the second).** A park-resumed session that parks again is a no-progress cycle **only** when it raised no `question_<n>.md` above the highest index present when it was resumed. A session that raised one made progress, however soon it re-parked. That is the prompt's *"the window counts only together with the index detector"*: once the window can no longer fire alone it decides nothing, so the knob is removed rather than kept as a no-op. The prompt's other form also counts a moved committed tip as progress. This plan does not adopt that half, for three reasons:

1. A session that parks again on a new question always raises the index, because the canonical format forbids reusing one (`plugin/instructions/task_plan_writing_instructions_autonomous.md` → `## Clarification channel — file format (canonical, single source of truth)`). So the tip adds nothing in that case.
2. In the only case left, a re-park with no question above the baseline, a moved tip would let an engine that commits a ledger or digest entry on every pass escape the bound. `harness-runs/lessons.md` → `## Unattended control loops` requires every retry in an unattended path to stay bounded.
3. Reading the tip would add a git call into the run copy, which `docs/watcher.md` §2 → `### Where the family runs git in a run's copy, and under what pins` governs.

The guard runs unchanged in job mode, because job mode calls the same `classify_run_exit`. `PARK_LOOP_MAX_CYCLES`, the `park_loop` status, `PARK_LOOP_CLEAR` and the `resume made no progress (cycle <c>/<max>: <reason>)` log line all keep their spelling. `plugin/commands/branch-status.md` greps that line.

**Decision — the Phase G `architecture-reviewer` does not open the answer file.** The task prompt asks whether the reviewer may follow the index's `Park answer consumed:` / `**Authorised by:**` pointer to the answer. It may not. The contract names `test-fix-plan-writer` as the only reader, and `**Authorised by:**` already quotes the authorising sentence for the reviewer to grade (`plugin/agents/test-fix-plan-writer.md` → `## Process`). Task 3 adds this rule to `plugin/agents/architecture-reviewer.md` → `## Process`, sub-case (c).

**Decision — Phase D's clarification digest stays the one later reader, and every no-read rule this branch writes stops before Phase D.** Both autonomous flows end Phase D with the clarification digest (`plugin/instructions/clarification_digest_instructions.md`, activated by `Override J` in `plugin/instructions/plan_orchestration_instructions_autonomous.md` and in `plugin/instructions/user_review_fixes_instructions_autonomous.md`). In `## What is digested` it reads every `question_<n>.md`, top level and `answered/`, and its `## The entry format` → **answered:** field quotes the answer file verbatim. It does not exclude Phase G pairs, and it should not: the digest is the record that survives the run copy, and a Phase G ruling is one the operator made. Both flows run Phase G before Phase D (the task fork runs the core's phases in the order `… → E → G → D`), so a Phase G resume that gets through its gates reaches the digest in the same session. That session carries W5 in its launch prompt and W3 in its fork. Unscoped, those two sentences would leave Phase D two bad choices: break them to quote the answer, or drop the answer, or record it as `no answer file on disk — resolved out of band`, which would be false. So this plan scopes the rules rather than changing the digest:

- **W3 and W5 open with "Before Phase D"** and name the digest as the one later step that reads the answer, quoting it into its committed record. W5 says `test-fix-plan-writer` is the answer's only reader *until* the digest quotes it.
- **W2 also opens its prohibition with "before Phase D".** The core's must-not list binds the whole session, Phase D included. At `HEAD` its bullet is unscoped and sits beside the digest only because `Override J` is a fork addition. This branch rewrites the bullet, so it states the scope itself rather than leaving the overlap implicit. The supervised flow runs no digest, and for it the scope changes nothing, because its Phase D opens no park file.
- **W1 and W4 are unchanged.** W1 governs what a question file says, and the digest writes no question file. W4 binds the `architecture-reviewer`, which the digest never dispatches.
- **The digest's file is unchanged** (`## Scope register`, row 23). Its source set and its **answered:** field already say what this decision needs, and no task edits it.

**Ship order: 1, 2, 3, 4, 5, 6.** The configured layer order is `cli`, `plugin`, `general`. Task 5 is a `cli` task, but it ships after the two `plugin` tasks because it reads the prose they write: *contract before consumer* (`.claude/context/conventions.md` → `### The order files are created, so a half-built feature is still coherent`). Shipped before them, it would fail its own unit run. This follows the `fix_run_gates_answered_park_resume` precedent, whose pin task also shipped after its plugin tasks. Task 1's watcher sentence points at G.0, which exists at `HEAD`, so Task 1 needs nothing from Tasks 3 and 4. The catch-all docs task ships last because it describes what Tasks 1–5 built.

**The wire strings, stated once here.** Each per-task file that writes or pins a string restates it byte-for-byte.

- **W1 — the core's G.2 paths-only rule.** Appended to the paragraph that opens `**The \`Park answer:\` clause**`, after its closing sentence *"…and the answer reaches no other agent."*:
  `A later park's question file names an earlier park by its question and answer paths alone, never by quoting or summarising either file.`
- **W2 — the core's must-not bullet.** In `## What you must NOT do`, the bullet that opens `Do NOT open a park's question or answer file` becomes exactly:
  ``- Do NOT open a park's question or answer file before Phase D, and never compose a dispatch or a question file from its content. Its paths travel only in G.2's `Park answer:` clause.``
- **W3 — the forks' rule, byte-identical in three files.**
  ``Before Phase D, never open, quote or summarise a Phase G pair's `answer_<n>.md`: tell the pair's origin from its `question_<n>.md` alone. Phase D's clarification digest is the one later step that reads it, and it quotes it verbatim into its committed record.``
- **W4 — the architecture reviewer's sub-case (c) rule.**
  ``Never open an answer file that the index's `Park answer consumed:` line or a finding's `**Authorised by:**` line names: grade the quoted sentence, because `test-fix-plan-writer` is the answer's only reader.``
- **W5 — the watcher's resume sentence.** The value of `resume_clause`, with `${resume_files}` expanded as today (a trailing space ends it, as now):
  ``This is a RESUME: every question file of this park has been answered. Its answer files, each paired by index with its question_<i>.md, are: ${resume_files}. Resume from the park point rather than restarting; each answer file is read only by the step your flow's instructions name for it. Before Phase D, never open or quote an answer file whose question file names an origin that opens Phase G: Phase G's G.0 finds that pair and passes its paths to test-fix-plan-writer, its only reader until Phase D's clarification digest quotes it. ``
  Its first sentence is unchanged from `HEAD`, because `cli/test/watcher-remote-job.test.mjs` → `PARK_RESUME` matches it.

**The self-adopted copy.** `scripts/autonomous-watcher.sh` is `init`'s output in this checkout and is not edited here. Like every self-adopted file, it is re-rendered from the template by a forced self-adopt run (`docs/development.md` → **Regenerating this repository's adoption after a `cli/templates/` change is one forced self-adopt run, read as a dry run first.**). The same ground covered `fix_run_gates_answered_park_resume`'s register row for this file. Until that chore lands, this repository's own daemon keeps the old prompt and the old window.

**Top risks:**

- **Breaking the parse of a prompt that tests and runs already key on.** Task 1 keeps the opening sentence and the `<state_dir>/clarifications/<branch>/answer_<i>.md` paths byte-identical. Its new case asserts the prompt still names every answer, now for both the task engine and the user-review engine.
- **Weakening the guard while fixing it.** Task 2 keeps the existing index-detector case, which still trips `park_loop` after two cycles and is cleared by `PARK_LOOP_CLEAR`. It adds the run-B pin: two fast re-parks that each raise a higher index, under shipped defaults, are never caught. The job-mode park-loop case in `cli/test/watcher-remote-job.test.mjs` uses the index detector and needs no change.
- **The plugin wording drifting between the files that must agree.** W3 is one two-sentence passage in three forks. Task 5 pins W1–W4, each in its named section, so a fork that loses its copy fails by name.
