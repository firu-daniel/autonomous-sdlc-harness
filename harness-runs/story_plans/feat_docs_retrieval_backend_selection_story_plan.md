# Story: Docs retrieval, second backend — selecting the Python backend: the config key, launcher routing, doctor checks and documentation

## Context

This branch makes the Python docs-retrieval backend that `feat_docs_retrieval_python_backend` landed in `docs-retrieval-service/` **selectable by an adopter**. It adds one config key, has the launcher route on it, adds three `doctor` checks that answer for the backend, and rewrites `docs/retrieval.md` to describe two backends. It is the second of three branches. The TypeScript backend stays the default. **With the key absent, nothing an adopter sees changes.** This branch calls the package's console entry point `harness-docs-retrieval` (`serve-mcp`, `self-check`) and re-implements none of it in TypeScript. `self-check` already answers in a shape a `doctor` check can grade: three lines, `packages`, `weights`, `index`, each `ok   <question>: …` or `FAIL <question>: …` (`docs-retrieval-service/src/harness_docs_retrieval/self_check.py` → `SELF_CHECK_QUESTIONS`, `CheckLine.render`). So no sub-command is missing.

**The decisions this plan takes, stated once so every task inherits them.**

- **The key is `docs.retrievalBackend`, an enum `"typescript" | "python"`, schema default `"typescript"`.** It is read only inside `retrievalApplies` (`cli/src/config/model.ts`), which is unchanged and still requires `phases.docs` and `docs.retrieval` both true. No generator writes the key, so `init`'s output and the generated `harness.config.json` are unchanged. It is set by hand or with `npx autonomous-sdlc-harness config set docs.retrievalBackend python`. It needs no `init --force`, because `.mcp.json`, the permission profile and the settings templates do not change. The launcher reads the key at run time.
- **Where the connection string comes from: a default that matches the compose file, and no second key.** The launcher exports `HARNESS_DOCS_RETRIEVAL_DATABASE_URL=postgresql://harness:harness@127.0.0.1:5432/docs_retrieval` when its environment carries no non-empty value. Those are the compose file's throwaway loopback values (`docs-retrieval-service/compose.yaml` → `postgres`). An operator who runs Postgres elsewhere overrides it the way `docs/retrieval.md` already documents for the query-log variable: an `env` entry on the `harness-docs` server in their `.mcp.json`. That entry is committed, so it carries a **password-free** URL, and libpq reads the password from `~/.pgpass`. There is no `docs.*` connection key for three reasons. `harness.config.json` is committed and shared across machines, while where a Postgres runs is a per-machine fact. A credential must never be committed. And an exported shell variable never reaches the server, because the agent runner passes only its fixed inherited set (`docs/retrieval.md` → **How the variable reaches the server, since an export does not.**). `doctor` resolves the URL the way the server sees it: the `.mcp.json` entry's value, else the default. It **ignores** a shell export, so the check and the server cannot disagree.
- **One database per repository, shared by its checkouts and worktrees.** The first branch left this open (`docs-retrieval-service/README.md` → `## The seam, as found`, items 3 and 8). It is settled by documentation here, with no package change. A second repository on the same machine gets its own database, created by hand, and names it in that repository's `.mcp.json` `env` entry. Worktrees of one repository share the index. Each call's refresh reconciles it to the calling checkout's corpus, and two servers refreshing at once can interleave. That is accepted, because a result is navigation and never evidence, and it is recorded as a cost, not hidden. A lost database connection is not reconnected. Every call fails until the server restarts, which the next agent session does. That is also recorded.
- **The launcher's new failure mode is exit `3`.** The Python backend is selected but cannot serve: either `harness-docs-retrieval` does not resolve on the launcher's `PATH` (interpreter or package missing), or the server exited non-zero. That covers the database not answering and a missing weight cache, which `serve-mcp` refuses before its transport starts with one `harness-docs-retrieval: …` line on stderr (`mcp_server.py` → `serve_mcp`, `store.py` → `open_postgres_store`). To report it, the Python branch runs the server as a child **with `TERM`/`INT` forwarded** rather than `exec`ing it. The TypeScript branch still `exec`s, unchanged. Stdout stays the transport's in both branches.
- **Three new `doctor` checks, `retrieval-python-dependencies`, `retrieval-python-model-cache` and `retrieval-python-index`, graded from one `self-check` run** (`packages`, `weights`, `index` respectively). They come after the three TypeScript checks. With retrieval off they pass with the existing `RETRIEVAL_OFF` sentence. With retrieval on and the TypeScript backend selected, they pass with a sibling "not selected" sentence. **The three TypeScript checks become "not applicable" when the Python backend is selected**, for the reason `retrieval-dependencies`' own doc comment already gives: grading a runtime the launcher never runs is a pass on a server that never starts. The `retrieval-python-index` check writes into the configured database, because `self-check`'s `index` question refreshes the real index. That is the first `doctor` check to write anything outside its temp probe, and the module header and `docs/cli.md` §7 record it rather than hide it.
- **`init` installs and downloads nothing for the Python backend, and still installs the TypeScript runtime and models when it is selected**, so switching back costs nothing. With the key set to `python` it adds one note saying so. With the key absent it says nothing new.
- **Reading Acceptance 1 against deliverable 4.** Deliverable 4 requires the three new checks to *pass with the existing "not applicable" message* when the backend is not selected. So with the key absent, `doctor` prints three more passing lines than before, all carrying `RETRIEVAL_OFF` or the sibling sentence, and every check that existed before reports exactly what it reported. Task 6 asserts exactly that on a fixture. Install, `init` output and `.mcp.json` are byte-unchanged, which Task 7 asserts.
- **The refresh-failure remedy reverts.** `docs-retrieval-service/src/harness_docs_retrieval/service.py` → `answer` carries the first branch's `TODO: @claude` marker: restore `server.ts`'s remedy byte for byte once `doctor` checks this backend. Task 9 executes it, because Task 5 is what makes `doctor` check it.
- **Out of scope, and kept out:** no file under `plugin/`; `cli/templates/repo/mcp.retrieval.json`, `cli/templates/claude/settings.autonomous*.json` and this repository's `harness.config.json` are not edited; no change to the package's search behaviour; `init` installs no Python, package, weight or container; no wall-clock or cost figure is recorded (the Python backend's measured costs are marked pending for `feat_docs_retrieval_backend_comparison`).

**Layers.** Tasks 1–7 are `cli`: the model and check, a constants module, the run library's reader, the launcher, `doctor` and `init`, each with its tests. Tasks 8–15 are `general`, in ship order after them. This departs from `.claude/context/conventions.md` → `### The order files are created, so a half-built feature is still coherent`, item 1, which orders the schema **first** and the model and check after it; the plan follows the task-plan writer's catch-all-last ship order instead (`plugin/agents/task-plan-writer.md` → the `## Phase 2 Readiness — Ordered Fix List` bullet), which puts the `general`-layer schema edit (Task 8) after the `cli` tasks. Until Task 8 lands, a configuration carrying `docs.retrievalBackend` passes `check.ts` and fails `npm run validate:config`-style schema validation, because `properties.docs` is `"additionalProperties": false`; no task before Task 8 commits a configuration carrying the key. The `general` tasks are: the schema, the package's own edits under `docs-retrieval-service/` (a directory no `layers[]` row but the catch-all covers, raised in the return's `## Corpus staleness`) and the documents of record. No task is `plugin`.

**Running a unit's own tests.** A `cli` task runs only the test file it creates or edits, with `npm test -- test/<name>.test.mjs` from `cli/`. No conventions document states a single-file Python command, so Tasks 9 and 10 **record the skip** for their Python test files, and Phase G's gate 13 runs them. Task 10's case is `container`-marked, so it runs only in 13d.

**Top risks:** The likeliest failure is a key-absent adopter seeing something change. Tasks 4, 6 and 7 guard it: they assert, on fixtures, that the launcher still `exec`s the TypeScript runtime, that every pre-existing `doctor` check reports what it did, and that `init`'s output and `.mcp.json` are unchanged. The second risk is the launcher, `doctor` and the compose file drifting apart on the command name, the database variable, the default URL or the `PATH` fallback list. Task 2 makes `cli/src/retrieval/pythonBackend.ts` the one owner and declares each mirror in its header. Task 2 asserts the `PATH` fallback list against `hr_path_with_fallbacks`, and Task 4 asserts the launcher template's literals; the `docs-retrieval-service/` mirrors are declared, not asserted. The third risk is that the database-scope decision surprises an operator running two repositories on one machine. It cannot be detected by `doctor`, so Task 13 states it in the turn-on section itself, beside the commands, rather than leaving it to `## Still open`.

**Manual setup required:**

- **For Acceptance 2 (Task 10's container case):** on a machine with Docker, run `HARNESS_GATES_CONTAINERS=1 bash scripts/run-gates.sh`, or `bash scripts/python-service.sh container-test`, after `bash scripts/python-service.sh sync` and `npm run build`. This machine has no Docker, so 13d reports `SKIPPED` here and the case is first executed by hand.
