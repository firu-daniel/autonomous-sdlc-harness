# Story: Turn the per-run clone on — every new run copy is a `git clone --shared`, each run gets a per-run profile with exact paths, and the main checkout's whole `.git` is write-denied

## Context

`feat_clone_per_run` taught the run library, the three excluded wrappers and the watcher's git family to trust, sync with, create and remove a clone (`cli/templates/scripts/lib/harness-run-lib.sh` → *THE CLONE ARM'S SYNC*, *CREATING AND REMOVING A RUN'S CLONE*, `hr_wrapper_target_check_var`'s clone arm). `feat_clone_per_run_anchor` gave every plugin reader a main-checkout anchor that holds inside a clone (`HARNESS_MAIN_REPO`, `docs/watcher.md` → `### The main-checkout anchor`). Nothing creates a clone yet. This branch turns the layout on, then closes what the layout makes closable.

**What ships, in five parts.**

1. **Every new run copy is a clone.** `create-worktree.sh` creates one in all three modes (default, `--no-bootstrap`, `--existing`) through `hr_clone_create_var`. It bootstraps through the **main** checkout's `setup-worktree.sh --target`. It pushes a new branch from the main checkout and syncs the clone's `origin/<branch>` mirror out to the pushed tip. On every failure exit after the branch exists it removes everything it created and nothing else, including, when the failure follows a successful push, the remote branch that push created (deleted under a lease on the pushed tip, Task 7). `remote-run.sh start` and `review` cut and remove clones through the library. `harness-run.yml`'s `run` job cuts no copy at all: the job's session runs in the job's own checkout, which is the main checkout there. The template says why, and a test over the rendered template holds it.
2. **Each run's trust surface is protected by a per-run profile.** Claude Code's `--settings` takes one file (re-checked on 2.1.304, not marked repeatable). So the watcher renders a **per-run copy** of the generated profile at every launch and resume, at `<lane dir>/run-profiles/<repo slug>/<sanitized branch>.json` under the machine state directory `hr_lane_dir` names. That path is outside every sandbox-writable root and every file-tool-writable root. The copy is the base profile with exact entries appended to `sandbox.filesystem.denyWrite` and `permissions.deny`, and to nothing else:
   - the run copy's own protected surface, re-rooted from the sibling glob to the exact path;
   - on a clone, its `.git/config`, `.git/hooks`, `.git/objects/info/alternates`, `.git/commondir`, `.git/config.worktree` and `.git/objects/info/http-alternates`;
   - on a legacy worktree, its `.git` pointer;
   - the `.git` pointer of every other live linked worktree.

   Before launching, the watcher checks four things, and refuses the launch if any fails:
   - the copy parses;
   - `sandbox.enabled` is `true`, with `failIfUnavailable` `true` and `allowUnsandboxedCommands` `false`, unless the profile carries the opt-out's own marker line;
   - removing exactly the appended entries gives back the base profile byte for byte, as JSON;
   - every appended entry is a plain path or rule string.

   So a per-run copy can fail Claude Code's schema validation only where the base profile itself does. That residual is stated in `docs/cli.md` §6 and measured by a manual row.

   **Job mode renders no per-run copy.** It runs the same check on the base profile and passes the base profile unchanged, writing nothing under the machine lane. The watcher's *JOB MODE* header keeps *"the machine lane (both halves)"* off, and a job copy would equal the base anyway: the copy is the main checkout, and the job's fresh checkout has no other linked worktree (Task 13; `cli/test/watcher-remote-job.test.mjs`, Task 26).
3. **The main checkout's whole `.git` is write-denied.** A `<main>/.git` directory entry replaces the per-file entries under it, because after this branch objects reach the main checkout only through sync-in's fetch. The sibling-glob `.git` entry, which on a clone covers the whole git directory (`docs/sandbox-verification.md` CL1–CL4), is replaced by six glob entries naming only the clone `.git` paths above. Those six keep every other clone's trust files closed to the file tools. The run's own copy gets the exact form from its per-run profile, because Linux may skip a `*` entry (`docs/cli.md` §6, residual 2).

   **The remote job is settled by reading the flows, not by keeping `.git` writable.** In a job the session's cwd is the main checkout. The flows issue no sandboxed git write there:
   - every commit and push goes through the excluded `commit-on-branch.sh` / `push-branch.sh`, which run unsandboxed;
   - a revert is done with the file tool, and `git restore` / `git checkout` sit in `ask` (`plugin/instructions/dispatch_discipline_instructions.md`, `plugin/instructions/improvement_observations_instructions.md`);
   - `git status`'s opportunistic index refresh fails silently and is harmless.

   A manual row measures a job-mode-shaped session.
4. **What git gave for free is replaced.**
   - **One branch, one checkout.** The library's one-live-copy rule (`hr_run_copy_live_var`, extracted from `hr_clone_create_var`) backs `create-worktree.sh`'s refusals in every mode and `branch-prompt.md`'s collision guard.
   - **Branch visibility.** The main checkout's ref is moved by every wrapper commit, push and refresh, and the watcher syncs in at every run exit. Where it can still lag is documented.
   - **The flows' push-state read.** A clone's configuration carries no `branch.<branch>.*` upstream keys (the clone allow-list does not widen), so a bare `git status -sb` in a clone always reports no upstream. The two Phase D cores read push state from `git rev-list --count origin/<branch>..HEAD` instead (Task 28). The remote-tracking ref it reads is current in both layouts: `create-worktree.sh` syncs the clone's mirror out after the creation push (Task 7), and `push-branch.sh` already does after every later push.
   - **Cleanup.** `cleanup-merged-worktrees.sh` finds run copies from the registry and removes a clone through `hr_clone_remove_var`.
   - **Alternates lifetime.** The clone is never dissociated, because that copies the whole history. Instead it holds only refs the main checkout keeps alive for the run's life: its branch, which sync keeps equal to the main checkout's, plus `origin/<defaultBranch>` and `origin/<branch>`. The residual (clone-only reflogs and stash entries) is stated in `docs/cli.md` §6.
   - **One compare-and-swap.** Every operation that moves a branch on a clone now moves the **clone's** ref first, by compare-and-swap against the tip sync-in read, and then the main checkout's. A failed main-checkout swap rolls the clone back by compare-and-swap (`hr_copy_ref_swap_var`).
   - **Healing.** Sync-in now heals a clone that is strictly behind by fast-forwarding it, and still refuses a diverged one.
5. **Migration: both layouts are supported until no worktree run is left. No run is migrated on resume.**
   - A parked or paused legacy worktree run resumes in its worktree. Its per-run profile protects its pointer. It commits through the existing worktree arm of the wrappers, and `cleanup-merged-worktrees.sh` sweeps it from its registry record, which carries no `copy_kind`.
   - The existing worktree-arm suites stay as the legacy layout's coverage. Every suite that runs `create-worktree.sh`, the watcher's payload paths or the remote verbs moves to the clone layout.
   - A dedicated migration suite drives a legacy run from resume to sweep.

**Constraints every task holds.**
- Every protection that exists today stays, or is replaced, never just removed: the wrappers' target and configuration refusals, the pinned hooks, the `pre-push` hook, the write protection and the guards.
- No `--local` clone and no hardlinks; the object store is borrowed (`--shared`).
- `allowWrite` is not widened, and how the run loads the plugin does not change.
- The script names, `<worktree_glob>`, the registry field `worktree` and the `doctor` check id `worktrees` stay.
- Scripts stay bash 3.2 compatible. The git floors stay: 2.23 for the wrappers, 2.38 for `refresh-branch.sh`.
- No test is ever aimed at this repository's own main checkout. Every fixture lives under the system temp directory, and a suite that drives the watcher points `XDG_STATE_HOME` into its fixture, so a per-run profile is never written under the real home directory.
- This repository's own `scripts/` and `.claude/settings.autonomous.json` are `init`'s output in this checkout (`.claude/context/conventions.md` → `## Documents of record`). No task edits them: every script change lands in `cli/templates/scripts/`, and the main checkout picks it up through the manual re-render below.
- The test-run rule (`plugin/instructions/unit_loop_core.md` → `## The test-run rule`) binds every `Verification:` bullet. A task runs only the test files it creates or edits, through `npm test --workspace cli -- test/<name>.test.mjs` from the repository root, as one plain foreground command.

**Why the tasks are cut this way.** Every task is single-layer and owns its files outright: no two tasks edit the same file. `cli/templates/scripts/lib/harness-run-lib.sh` is therefore one task (Task 1), and the suites that lock its behaviour in are separate tasks that depend on it. Script changes and their suites are split the same way where one task would pass the ceiling. The `cli` tasks come first, in dependency order. The two `plugin` tasks come next, and the `general` (catch-all) documentation tasks come last, because they describe what the earlier tasks built. Tasks 26–28 were added in revision and keep their numbers; the readiness list places each at its ship position (Task 27 after Task 12, Task 26 after Task 14, Task 28 after Task 20).

**Top risks:**
- **The clone-first reorder leaves a state the old order never could.** A failed main-checkout swap followed by a failed rollback leaves the clone ahead of the main checkout. Task 1 defines the one helper every operation goes through, with a distinct exit for that state. Task 2 and Task 4 drive a commit landing in the clone between sync-in and the update for all four operations, and expect a refusal with nothing moved on either side.
- **The per-run launch check refuses every launch, or accepts a profile Claude Code would silently ignore.** Task 13 writes the check against the base profile structurally. Task 14 drives it with a valid profile, a `sandbox.enabled: false` profile with and without the opt-out marker, an empty file and a tampered delta. Task 26 drives the same check in job mode, where the base profile itself is checked and the lane stays untouched. Task 23 owes the manual row that launches on a deliberately invalid profile.
- **Removing the sibling-glob `.git` entry could silently reopen another run's trust files.** Task 5 replaces it with six narrower glob entries, which keep the file tools out of every other clone's `.git/config`, hooks and alternates. Task 13 adds every other live worktree's pointer by exact path. Task 23 owes the rows that measure both from a real sandboxed session.

**Manual setup required:**
1. **After merge, re-render this checkout's adoption and restart the watcher**, so the main checkout runs the new scripts and profile. The outer-loop scripts are `create-if-absent`, so only a forced `init` replaces them. Run `HARNESS_SELF_ADOPT=1 node cli/dist/cli.js init --force --no-analyze` from the main checkout, restore the hand-kept files that run rewrites (`docs/sandbox-verification.md` → `## 0. Method` lists them), then run `bash scripts/restart-watcher.sh`. Tasks 1, 4, 7, 9, 11, 13 and 5 depend on it reaching the main checkout.
2. **Take the owed sandbox rows by hand** (Task 23): the per-run protection, `<main>/.git` refused as a whole, the three wrappers on a real clone, a legacy worktree run's commit, the job-mode-shaped session, the per-run profile file's own protection, the launch on a deliberately invalid profile, and the full flow. A run cannot launch a sandboxed session under the profile it measures.
3. **Migration check, before and after the re-render.** List the legacy worktree runs with `jq -r '.runs | to_entries[] | select(.value.copy_kind != "clone") | .key' harness-runs/autonomous_logs/registry.json` from the main checkout. Let each one finish under the supported worktree arm (Task 18 proves it can). The worktree arm itself is removed in a later branch, once that list is empty.
4. **The real GitHub `run` job is a post-release follow-up.** It needs a published CLI carrying Task 19's template and a re-run of gate 12 against the standing repository. No task here performs it.
