# Story: Docs-retrieval relevance eval

## Context

This branch builds the measurement half of the roadmap row *Docs-catalog retrieval*: a relevance eval that decides the retrieval tool against the index-first navigation agents use today. `feat_docs_catalog_retrieval` shipped the tool off by default with a provisional abstention threshold and nothing measured; this branch ships the runner, the two committed corpora, the numbers for arms B–E on the real models, the calibrated threshold, a regression gate, and the written procedure for the one arm that is deliberately not run here.

**Where the work lands, and why.** The eval runner is **not** shipped CLI surface. `cli/src/retrieval/session.ts` refuses to open a session unless `retrievalApplies(config)` — `phases.docs` **and** `docs.retrieval` both true — and this repository's `harness.config.json` has `phases.docs: false` and no `docs` key, which the task prompt settles as not to be flipped. The runner therefore **supplies `docs` and `phases` itself** and drives `corpusFiles` → `refreshIndex` → `searchDocs` directly, which `cli/src/retrieval/corpus.ts`'s own header licenses (*"the gate … is its callers' to check, not this module's"*). That licence is scoped to the gate and nothing else: `retrievalApplies` reads `phases.docs` and `docs.retrieval` alone, so the runner **reads `layers[]` and `stateDir` out of the real `harness.config.json`** at the resolved `--repo` root and overrides only `docs: { root }`. The same header's first sentence forbids a copy of the conventions list anywhere, and a hand-written copy in an `.mjs` file no compiler checks would silently stop covering a layer added later, with no gate failing. A `docs` sub-verb doing that would contradict `session.ts`'s stated rule, so the runner is a set of ES modules under **`evals/docs-retrieval/`** — the `general` layer — that import the compiled retrieval code at `cli/dist/retrieval/*.js`. They are the retrieval code's own interfaces, never a copy of them. **`harness.config.json` is left alone.**

**Two committed corpora, with stable ids the whole plan uses.** `fixture-catalog` is a made-up docs catalog under `evals/docs-retrieval/corpora/fixture-catalog/docs/`, carrying its **own `INDEX.md`** because arm A navigates from one and this repository's `docs/` has none. `self-docs` is this repository's own `docs/` plus every conventions document `layers[]` names — read from the configuration at run time rather than listed anywhere in the runner, and today three of them, roughly 166 chunks, confirmed by the provisioning pre-step.

**`self-docs` moves under this branch, and every figure taken over it is stamped rather than pinned.** `corpusConfig('self-docs')` sets `docs.root: 'docs'`, so the corpus is **every** `*.md` under `docs/` — including the documents this branch itself adds there. The branch moves it three times: Task 3 measures it at **12 files / ~166 chunks**; Task 4 creates `docs/retrieval-eval-results.md`, so from entry 4 on the eval's own file of record is **inside** the corpus it measures (13 files); Tasks 10 and 12 add `docs/retrieval-eval.md` and rewrite `docs/retrieval.md` and `docs/cli.md`, taking it to 14 files with changed chunk text. The corpus is **not** pinned by filtering those files out — `refreshIndex` calls `corpusFiles` itself (`cli/src/retrieval/refresh.ts`), so a per-file exclusion would mean editing `cli/` code this branch has no reason to touch. Instead the rule, settled here once and carried by Tasks 3, 5, 9 and 10: **every recorded `self-docs` figure is stamped with the corpus file count and chunk count of the run it was taken at, derived from that run's own refresh result and never typed as a literal; and two figures carrying different stamps are never read as a before/after pair.** A comparison that must isolate one variable — the threshold, a code change — takes **both** of its numbers in one task's own pass over one tree, which is why Task 5 re-measures its own *before* figure instead of reading Task 4's, and why Task 9's regenerated provenance states the snapshot it ran at alongside the threshold. The regression gate is untouched by all of this: it runs `fixture-catalog` only, and that corpus changes only when the eval changes.

**The query-set format, settled here once, because three tasks read it.** One JSONL record per query, in `evals/docs-retrieval/queries/<corpus-id>.jsonl`:

```json
{"id":"q-abstain-threshold","query":"when does the docs search abstain","labels":[{"ref":"docs/retrieval.md#abstention","grade":3}]}
{"id":"q-negative-lattice","query":"quantum chromodynamics lattice spacing","labels":[]}
```

`id` is unique and stable. `ref` is `path#anchor` **exactly as `SearchHit.ref` renders it** — repo-relative path, GitHub-style slug, and `path` alone for a preamble chunk. Relevance is **graded, not binary**: `grade` is an integer `1`–`3`, `3` being the section that answers the query and `1` a section that is related and useful; the primary metrics score `grade >= 1` and a strict column scores `grade == 3`, because a threshold calibrated against "any related section" and one calibrated against "the answering section" are different numbers and the results file must show both. A record with an **empty `labels` array is a negative query** — the arm is expected to find nothing — and it is excluded from recall and MRR and is the other half of the abstention calibration. The whole record set is `AUTONOMOUS_SDLC_HARNESS_RETRIEVAL_STUB`-free by construction: the runner refuses to write numbers while that variable is set.

**How anything here is executed.** A bare `node …` from a tool call matches no entry in `.claude/settings.autonomous.json` and **stalls** an unattended run rather than failing it, and no entry is added to that profile on this branch. Two routes exist and the plan uses only them: commands inside `scripts/run-gates.sh` run as a bash subprocess with no per-command check, which is where the regression gate goes; and `bash scripts/scratch-run.sh <file>` runs a **file** under `harness-runs/scratch/`, which is how every one-off measurement pass is driven. Every measurement pass therefore ships as a committed, importable module under `evals/docs-retrieval/` with a three-line scratch launcher, so the pass is reproducible and the scratch file is disposable. Recursive removal and `du` are never shelled out: a `.mjs` scratch file does both in process, which is what `.claude/context/conventions.md` → `## Shell assets` already requires.

**Arm A is built and not run.** Its harness, its fixture, its agent-task text (`evals/docs-retrieval/arm-a/agent-task.md`, named so that it stays off the native eval runner's `evals/**/prompt.md` case-discovery glob) and its written hand-run procedure are in scope; executing it is not, because it needs a `claude -p` subprocess the permission profile does not grant and the `scratch-run.sh` route to it is declined on purpose. No task below invokes `claude`. Arm A's row exists in the results file with empty metric columns and the words *awaiting hand run*.

**Where the numbers are recorded.** `.claude/context/conventions.md` → `### Where a new responsibility goes` puts a measured fact in `docs/`, **and nowhere else**, so the results file of record is `docs/retrieval-eval-results.md` — one file with a generated region between the literal markers `<!-- eval:generated:start -->` and `<!-- eval:generated:end -->` (the runner rewrites only that region: human tables above a trailing fenced `json` block, which is the machine half) and hand-written sections below the end marker for the decisions: the threshold calibration, the cold build, the query-log pass's separate latency, and arm A's awaited hand run.

**Which run the generated region holds when the branch is done, settled here because two tasks write against it.** Task 4 generates the region first, **before** Task 5 moves `ABSTAIN_SCORE_THRESHOLD`, so that first generation records arm E under a threshold the branch then retires. The region is therefore **regenerated after the move**, by **Task 9** (entry 10) — the task that already re-measures post-move for the floor, and the **last** writer of the region on this branch: Tasks 7, 8, 14 and 6 write only hand-written sections, and Tasks 10–13 do not write this file's region at all. What ships is the post-calibration run, and the provenance section says which threshold was in force when it was taken.

That regeneration is lossy in one direction and the plan handles it rather than discovering it: on an abstaining query `searchDocs` returns `{ abstained: true, hits: [] }`, so a post-move generation has no `bestScoreOnPositive` for exactly the queries the new threshold abstains on — and those per-query distributions are the whole evidence the calibration was chosen from. So **the pre-move distributions are quoted into `## Threshold calibration` by Task 14**, which is hand-written territory below the end marker that the runner never rewrites. The evidence survives where regeneration cannot reach it; the generated region carries the shipped behaviour. Neither fact is stored twice: the pre-move numbers live only in that section, the post-move ones only in the region. `docs/retrieval-eval.md` is the operator-facing companion — how to run the eval against any adopter's checkout, what each metric means, the decision rule, the arm A procedure, and how the floor works. `evals/docs-retrieval/floor.json` is a machine artifact the gate reads, not prose, and the statement of what it holds lives in `docs/retrieval-eval.md`.

**Ship order.** The configured layer order is `cli`, `plugin`, `general` with `general` the catch-all, and the plan ships bottom-up inside that where it is free: Task 1 is the `cli` store case and ships first. Task 5, the threshold move in `cli/src/retrieval/search.ts`, is the one deliberate departure — it consumes the reranker score distribution Task 4's runner produces, so it cannot ship before it, and the recorded floor in Task 9 cannot be taken before the threshold moves, because abstention changes arm E's hit set. Task 14 ships immediately after it: the calibration's **record** is a measured fact, which `.claude/context/conventions.md` → `### Where a new responsibility goes` puts in `docs/` and nowhere else, so it is a `general` task while the constant is a `cli` one — one calibration, two layers, two tasks, in that order. Task 9 then closes the loop on the results file: it is the last task that writes the generated region, and it regenerates it post-move so the file of record ships the threshold the branch ships. No task depends on a later one. No task touches `plugin/`.

**Top risks:** the first is a number that looks measured and is not — both committed corpora are small (about 40 and about 166 chunks against roughly 1,500 for a mature catalog), and the lessons ledger's standing rule is that a fixture-sized figure never justifies a design decision unless the branch also ships the step that produces the real-shape figure. Task 14 guards it by recording the corpora the threshold was calibrated on *in the same section as the value*, and Task 9 ships the gate that reproduces it; the real-catalog confirmation stays an out-of-scope hand run and every document says so. The same risk arrives a second way, from the corpus rather than the models — `self-docs` grows as this branch writes into `docs/`, so a pair of figures taken at different points would read as a threshold effect when part of it is a corpus effect. The snapshot rule above guards that: Task 3 emits the stamp, Task 5 takes both halves of its before/after in one pass at one stamp, Task 9's provenance names the snapshot beside the threshold, and Task 10 warns the adopter that a results file written under `docs.root` joins the corpus it measures. The second is an unattended stall rather than a failure: a bare interpreter invocation matches no permission entry and hangs the run, so every task's verification reaches its code through `bash scripts/run-gates.sh` or `bash scripts/scratch-run.sh` and never through `node …` typed into a tool call. The third is the eval gate turning `run-gates.sh` red on every contributor's machine — Task 9 gates it on `modelFilesPresent(retrievalModelCacheDir()).present` (that function returns `{ present, missing }`, not a boolean) and, when the cache is empty, **reports the gate as `BLOCKED` without counting it among the script's failures**, printing it with the `== gates this script cannot run` block instead: anything pushed onto that script's `failed` array makes it exit 1, so counting it would be the failure-on-a-provisioning-gap this risk is about. A shortfall against the floor still fails the script; only the cache-absent exit status is exempt. The fourth is arm A silently vanishing: it has its own task, its own results row and its own procedure section, and acceptance is that the run made no `claude -p` call at all.

**Manual setup required:** none for the tasks below — the retrieval runtime and both model files were installed by hand before this branch was queued, into the machine-shared cache every worktree sees. Each task that loads a model verifies that with `retrievalRuntimeState().installed` and `modelFilesPresent(retrievalModelCacheDir()).present` and **stops and says so** — naming the paths that second call's `.missing` array holds — if either comes back false, rather than improvising an install. Both members matter: `modelFilesPresent` returns `{ present, missing }` rather than a boolean, so a check written against the call itself is always truthy and never fires. Two steps stay human and are documented rather than performed: executing arm A (Task 11's procedure), and running the eval against a private real catalog, which closes the roadmap row after this branch merges.
