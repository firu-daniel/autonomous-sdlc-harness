# Story: A resumed planning run continues the walk it stopped in, and never skips a plan no reviewer passed

## Context

This branch closes a resume hole in autonomous planning. A planning run that pauses or parks part-way through a loop comes back without its place. It can then send a plan no reviewer passed on to implementation, or redo work already done. The walker shipped by `feat_orchestrator_flow_graph_planning_pilot` already keeps that place on disk, in `<state_dir>/.flow_walker_state`. The re-entry rules throw it away. The work is cut into eight single-layer tasks, in bottom-up ship order: `cli`, then `plugin`, then the catch-all `general` last.

**The mechanism, confirmed from the code rather than taken from the prompt.** `plugin/instructions/task_plan_writing_instructions_autonomous.md` → `## Override 2 — resumability` case (b) reads *"Story index exists with a complete Phase 2 Readiness list and no pending clarification"* and skips the task-plan loop. A first draft already has a complete readiness list. `plugin/instructions/task_plan_writing_instructions_core.md` → `## Setup (once per session)` step 7 maps **skip** to `start --entry ui_writer` or `convergence`. In `cli/templates/scripts/flows/task_plan_writing.graph.json`, `ledger: P1` is printed only on the `plan_review` → `PASS` edge. So `P1` stays `[ ]` and nothing notices until the `### 1.8 Completion check` in Phase D. Even when the loop is not skipped, `cli/templates/scripts/flow-walker.sh` → `start` resets every counter and renders its entry with the `initial` prompt (`arrive "$entry" initial`). A resumed UI-test-plan loop therefore rewrites a finished plan and loses pending findings.

**The design chosen.** Three parts, one per owner:

- **The core states continuation, mode-free.** `## The walker — routing is its, judgement is yours` gains a **Continuing a saved walk.** paragraph. A (re-)entry probes the saved walk with `current`, which is read-only. The first lines `current` prints tell the three `awaiting` values apart. The walker code does not change: `awaiting=answer` always prints `binding: <ask>`, and `awaiting=done` always prints `<escalate>` or `<terminal_handoff>` (`flow-walker.sh` → `take_binding`, `render_terminal`).
  - `action: dispatch` — continue by dispatching the printed action.
  - `binding: <ask>` — continue with `next --outcome answered`, and only when the answers are at hand.
  - any other `binding:` — the walk has finished. Do not continue it and do not act on it again.
  - exit 1 — no walk is saved. Fall back.
- **`## Setup` gets two new outcomes, and keeps the three it has.** Step 5 keeps **proceed fresh**, **extend** and **skip**, and adds **review** and **continue**. **review** sends an unreviewed draft back through its loop's first gate. **continue** issues no `start`. The graph adds `business_parity_review` and `ui_review` to `entries` so that **review** can be started.
- **The autonomous fork owns the ledger checks.** The ledger is the only durable record, and it wins. Override 2 takes a saved walk first, unless the ledger contradicts it. Case (b) now skips the task-plan loop only when `P1` is `[x]`. The new case (d) sends a draft whose entry is `[ ]` back through review. Override 5 states that a `ledger:` line printed again is safe to re-apply: the commit wrapper returns exit 3 when nothing changed.

**Decisions this branch establishes, with where each is recorded:**

- **The fork checks whether a saved walk is still usable. The walker does not.** The walker routes only: it reads no plan artifact, and reads nothing from the ledger except its run-mode block. The core checks whether the pending action's artifact is still there. That catches a draft deleted by hand after the walk had moved past `plan_writer`.
- **The ledger decides when it and the saved walk disagree, in both directions.** A walk still inside the task-plan loop while `P1` is `[x]` is not used. A walk already past that loop while `P1` is `[ ]` is not used either, unless its printed action carries `ledger: P1`. That line means the last session died between the walker printing the line and the fork flipping the entry.
- **A saved walk from an earlier walk on the same branch** is not continued once it has finished. If it is still pending, it is checked against the same two tests. `current` already refuses another flow's or another branch's state with exit 1.
- **A finished `<terminal_handoff>` walk with `P3 [ ]` is not continued.** It falls back to the ledger. With `P1` and `P2` resolved, the ledger already maps that case to `--entry convergence`. Override 3 and Override 4 then run again idempotently and `P3` is flipped. The cost is small. A `P2` flip lost in the narrow window between the walker's print and the fork's flip costs one UI-review round. That follows the harness's re-earn-never-trust rule (`plugin/instructions/autonomous_pause_and_ledger.md` → `### 2.5`, *"A lost sub-agent result is re-earned"*).
- **The step 7 mapping from **extend** to `ui_writer` stays, but only as the fallback.** This is the mapping skeptic Finding 2 of the pilot added. With a usable walk parked at `<ask>`, **continue** reaches the writer that parked, through `resume:`. The mapping is still needed for a park at a loop's cap, which is a finished `<escalate>` walk, and for a lost state file.
- **The semi-autonomous fork never picks continue or review.** That mode keeps no flow-progress ledger to check a saved walk against. A machine-local walker state would become the only record of progress, and the pilot's item 3a forbids that. In that mode the user, who is asked `extend / rewrite / stop`, is the check. Only the fork's binding row changes, to say so.
- **Neither the graph format nor `scripts/check-flow-graph.sh` changes.** Both new entries are nodes that `start` already reaches, so `reachable-from-start` and `reaches-terminal` still hold. No check reads `entries`. An entry that is not a node would make the walker fault at `start` with exit 2, and the core routes that to `<escalate>`. `formatVersion` stays `1`, because the set of keys does not change. The schema's `entries` description does change, because a continued walk resumes without naming an entry.

**Out of scope, per the task prompt's `## Out of scope`:** every other flow, the pause protocol (§2.0–§2.5), the watcher and its `pause_resume_clause`, `PAUSE_PROGRESS.md`'s status as a hint, and the loop's routing — gate order, the cap, the skip semantics and the escalation payload.

**Gates that already fail on this branch:** `bash scripts/run-gates.sh` → gate `1a plugin manifest` and gate `6a no machine paths` fail for reasons outside this branch (task prompt → `## Verification`). Each task that runs the gates names them if they still fail, and must add no new failure.

**Top risks:** the likeliest failure is a saved walk continued when it should not be — against a ledger that contradicts it, over a draft someone deleted, or after the walk finished — which would re-create the hole this branch closes from the other side; Task 4 owns the artifact and finished-walk rules and Task 5 owns the ledger-precedence rules, each with a `Verification:` bullet naming the case. The second is drift between the tests and the rules they cite: Tasks 2 and 3 (cli) ship before Tasks 4 and 5 (plugin) and quote exact substrings of the rewritten rules, so both sides of each quoted phrase are fixed in the per-task files and Tasks 4 and 5 verify every one with `grep -F`. The third is a new outcome (**review**, **continue**) that some reader of `## Setup` step 5 does not map — Task 6 closes the semi-autonomous fork's binding row, and the `## Scope register` below enumerates every other reader.
