# Story: Docs retrieval, second backend — the Python service, its parity core, its container and its gates

## Context

This branch builds a **second implementation** of docs retrieval: a Python service that answers the same `search_docs` tool over the same corpus as `cli/src/retrieval/`, with its index on a real Postgres reached by connection string. It is the first of three branches. It makes nothing selectable, changes no adopter-facing file, and runs no real-model comparison. It ends with a backend that is shown to speak the same wire and chunk the same way, ready to be measured.

**Where the work lands.** Everything new sits in one new directory at the repository root, `docs-retrieval-service/`, which is a peer of `cli/`. The distribution is `harness-docs-retrieval`, the import package is `harness_docs_retrieval` in a src layout (`docs-retrieval-service/src/harness_docs_retrieval/`), and there is one console entry point, `harness-docs-retrieval`, with sub-commands `serve-mcp`, `serve-http`, `index`, `self-check` and `fetch-models`. Around that directory the branch edits `scripts/run-gates.sh`, adds one hand-written wrapper `scripts/python-service.sh`, adds backstop entries to the hand-edited top of `.gitignore`, and adds a gate to `docs/development.md` → `## 5. Verifying a change`. No `layers[]` row describes `docs-retrieval-service/`, so it falls to the catch-all `general` layer, and **every task is `general`**. That gap is raised in the return's `## Corpus staleness`, not fixed here. **No file under `plugin/` and no adopter-facing file under `cli/` (`cli/src`, `cli/templates`, `cli/scripts`) is created or edited by any task.** The TypeScript implementation is read: Python tests run it through `cli/dist` and through `cli/test/helpers/fixture.mjs`, the same way `evals/docs-retrieval/` does. It is never changed. `harness.config.json` is not edited. A diff that touches `plugin/agents/` means the port went wrong.

**The architecture constraints every task inherits.**

- **One wire, byte for byte.** The server name `harness-docs`, the tool `search_docs`, its description, its input schema, the `k` clamp, the two-lines-per-hit rendering `n. ref (score s)`, the coverage `note: ` lines and the single-line abstention `no confident match` are all the TypeScript side's (`cli/src/retrieval/server.ts`, `cli/src/retrieval/search.ts`), and they are reproduced exactly. Python's defaults differ from JavaScript's in places, and those differences break bytes without anyone noticing: string length and slicing (UTF-16 code units in JS, code points in Python), sort order (UTF-16 code-unit order), what counts as whitespace (`\s` and `trim()`), `Number.prototype.toFixed` rounding against Python's round-half-even formatting, `JSON.stringify` against `json.dumps`, `split(/\r?\n/)` against `splitlines()`, `readFileSync(…, 'utf8')` against Python's newline translation, and `Object.keys` order. Task 2 owns one module of JS-semantics helpers, and every later task uses it rather than re-deriving a rule.
- **The same SQL.** Statements are taken from `cli/src/retrieval/store.ts` and issued through psycopg 3's `AsyncRawCursor`, which binds PostgreSQL-native `$1` placeholders. That is what lets `ORDER BY text <@> to_bm25query($1, 'chunks_bm25')` and `ORDER BY embedding <=> $1::vector` carry over character for character. Every value reaches SQL as a bound parameter. A statement that cannot carry over is recorded in the package README's `## The seam, as found` (Task 17), never quietly rewritten.
- **Local-only, and no download at run time.** There is no hosted database and no embedding or rerank API. Model weights are downloaded only by the operator-run `fetch-models` sub-command. Every other load is offline (`local_files_only`), and the weight cache is checked for presence even under the stub, the way `cli/src/retrieval/session.ts` checks the TypeScript cache. The Python weights are a separate cache from the Xenova ONNX exports `init` installs, at `${XDG_CACHE_HOME:-$HOME/.cache}/harness-docs-retrieval/models` (overridable by `HARNESS_DOCS_RETRIEVAL_MODEL_CACHE`). That location is deliberately not under the CLI's machine directory, so no literal of `cli/src/retrieval/runtime.ts` gains an undeclared mirror.
- **The service owns its config.** It reads `<repo>/harness.config.json` **read-only**, taking only `docs.root` and `layers[]`, which are the keys `cli/src/retrieval/corpus.ts` reads. It takes a `--docs-root` override and reads its connection string from `HARNESS_DOCS_RETRIEVAL_DATABASE_URL`. It applies no `phases.docs` / `docs.retrieval` gate, because making the backend selectable is the next branch's work. Its own environment variables carry the `HARNESS_DOCS_RETRIEVAL_` prefix. The stub selector reuses `AUTONOMOUS_SDLC_HARNESS_RETRIEVAL_STUB` because its semantics are identical (`hash-v1` / `hash-v2`, any other non-empty value refused).
- **Precision and ids (deliverable 4), decided here.** Both models run **full precision (fp32) on CPU** through `sentence-transformers`. That is the normal Python path, and pinning CPU removes GPU/MPS nondeterminism. The ids are namespaced and encode the precision: `py-st/BAAI/bge-small-en-v1.5:fp32:cls:384:v1` and `py-st/cross-encoder/ms-marco-MiniLM-L-6-v2:fp32:sigmoid:v1`. No figure from this branch justifies the choice, and none may be quoted as if it did (the lessons ledger's stub-figure rule). The README states it as a decision with its reason.
- **Packaging for an offline gate.** `pyproject.toml` declares the base runtime (`fastapi`, `uvicorn`, `mcp`, `psycopg` ≥ 3.2, `huggingface_hub`), a `models` extra (`sentence-transformers`, `torch`) loaded only by a lazy import on the real-model path (the Python twin of the CLI's optional-peer carve-out), and a dev group (`ruff`, `mypy`, `pytest`, `httpx`). `uv.lock` is the pinned lockfile. The gate environment syncs **without** the `models` extra, so no gate installs or imports torch. `scripts/python-service.sh` keeps the virtual environment and every tool cache **outside the checkout**, so gate 6a's `$HOME` grep gains no new hit and needs no new exclusion.
- **Running a unit's own Python test file (the test-run note every task's `Verification:` defers to).** `unit_loop_core.md` → `## The test-run rule` lets a unit run only the test file it created or edited, through a single-file command a conventions document states. No conventions document states one for Python yet, and `scripts/python-service.sh lint|typecheck|test` are gate commands `scripts/run-gates.sh` runs. So a unit **records the skip** for its Python test file and for Python lint and type-check, and Phase G runs them. That gap is raised in `## Corpus staleness`. `bash scripts/python-service.sh lock` and `sync` are provisioning commands, not gates, and Task 1 runs them.
- **Timing is exposed, never recorded.** Tasks 10–12 expose the library-level `search_docs` duration (`search_ms` in the HTTP response, a stderr line for stdio) for the third branch to read. No task records a wall-clock figure, and no `Verification:` bullet grades a duration beyond its presence and type (the lessons ledger's wall-clock rule).
- **Framing.** The task prompt calls this the beachhead for the roadmap item **Second-runtime reference port**. `ROADMAP.md` lists that row as **Withdrawn** (`docs/second-runtime-port-decision.md`). So no file this branch writes describes the package as serving that item or the LangGraph port. The README describes the package by what it is.

**Top risks:** The likeliest failure is a byte difference between the backends that has nothing to do with retrieval: a JS-vs-Python semantics gap in slicing, whitespace, sort order or number formatting. It is guarded by Task 2's helper module and its tests, then by four parity cases that compare against the running TypeScript code rather than a remembered copy of it: chunk keys and hashes (Task 4), stub vectors and scores (Task 6), rendering (Task 8), and tool listing and refusals (Task 11). The second risk is an engine divergence the port did not cause, such as tie order among equal scores or a different planner choice between PGlite and a real Postgres, which would surface in Task 15's end-to-end case. Task 15 reports it as a blocker naming the query and both outputs, never loosens the comparison or changes the query set, and Task 17 records it in `## The seam, as found`. The third risk is that everything Docker-dependent and much of the Python code is first executed after its task lands: this machine has no Docker, and no unit can run Python tests. Tasks 14 and 15 are therefore written to be run by hand, Task 16 makes each unrunnable gate report `BLOCKED` or `SKIPPED` loudly rather than pass silently, and the cross-task interfaces are spelled out on both sides so nothing rests on an implementer's guess.

**Manual setup required:**

- **Before Task 1:** install `uv` on the machine that runs this branch. An agent cannot install a system tool. Task 1's `lock` and `sync` need PyPI to be reachable once, and `uv` fetches a Python ≥ 3.11 interpreter if the machine has none (this one has only `/usr/bin/python3` 3.9).
- **For Acceptance 3 and the container half of Acceptance 2 (Tasks 14 and 15):** on a machine with Docker and network access for the image builds, run `docker compose up` from `docs-retrieval-service/`, and run the opt-in container gate (`HARNESS_GATES_CONTAINERS=1 bash scripts/run-gates.sh`, or `bash scripts/python-service.sh container-test`). This machine has no Docker.
- **Only for real-model use, which no gate and no task needs:** an operator runs `harness-docs-retrieval fetch-models` to provision the PyTorch weight cache (Task 13).
