# Story: Arm A against a real catalog — the decision rule applied, and the abstention threshold re-calibrated on an observed distribution

## Context

This branch runs **arm A** of the docs-retrieval eval — navigation by an agent — against a real documentation catalog, in **two variants** (**A-index**, told to read the catalog's `INDEX.md` first, and **A-search**, told only that the catalog is rooted in its working directory), applies `docs/retrieval-eval.md` → `## The decision rule` to the result bar by bar, records one of that rule's three outcomes, and **re-calibrates `ABSTAIN_SCORE_THRESHOLD` on an observed negative distribution** rather than the censored one `## Threshold calibration` was fixed on. Arms B–E run over the same catalog at the same snapshot as part of the run's own work. Arm A itself is **run by the operator at a terminal**; this run never starts a nested agent session, never routes arm A through `scripts/scratch-run.sh`, never substitutes a `fixture-catalog` run for a real-catalog one, and never publishes an arm A figure the operator's transcripts do not carry.

**The target catalog, and how it is named.** The gate 10 throwaway corpus: two halves under one `docs.root` of `docs` — `docs/expause-web/` (98 files, carrying its own `INDEX.md` at `docs/expause-web/INDEX.md`) and `docs/vite/` (57 files, whose `index.md` files are landing pages, not navigation maps) — with no `docs/INDEX.md` at the root. Gate 10 stamped it at corpus commit `010c50e`, 156 files / 1,960 chunks; the corpus has since moved to `57a6c25`, a `PROVENANCE.md`-only commit, and the operator has verified `docs/` byte-identical between the two (task prompt `## Operator checklist` row 2). **In the committed tree the corpus is identified by its commit and its size, never by a filesystem path.** Its location reaches this run only as the environment variable **`HARNESS_EVAL_CORPUS_ROOT`** (learned with the literal command `printenv HARNESS_EVAL_CORPUS_ROOT`, which the unattended profile allows); every read of the corpus uses the `Read` / `Grep` / `Glob` tools against that value, and **anything that executes against the corpus** — the label pre-flight, arms B–E, a `git` probe of its commit — runs through a launcher under `harness-runs/scratch/` driven by `bash scripts/scratch-run.sh`, which reads `process.env.HARNESS_EVAL_CORPUS_ROOT` itself rather than carrying the literal path. No committed file — plan, clarification answer, scratch file, transcript, results section — carries that path; the variable name is the only thing any of them records. Inside the eval the corpus gets the id **`gate10-catalog`** (Task 7 settles how an id is given to a corpus held outside this tree), and its query set is committed as `evals/docs-retrieval/queries/gate10-catalog.jsonl`.

**The corpus composition every task uses, settled here once.** The eval reads the catalog through the ad-hoc route with `--docs-root docs` plus one `--conventions` per conventions document the **corpus's own** `harness.config.json` `layers[]` names (read with the `Read` tool; the corpus is already initialised with `phases.docs` and `docs.retrieval` on). That composition is expected to reproduce gate 10's stamp, `{ files: 156, chunks: 1960 }`, so the cost bar can cite `### The real-catalog build — 1,960 chunks, 2026-09-22` as the **same** snapshot. A stamp that differs is never silently accepted: the task that sees it establishes which files the composition added or left out against gate 10's, records that beside the figure, and the cost bar then says the snapshot is not the same one. What must hold without exception is that the catalog's commit and its `docs/` are unchanged between the arm A runs and the B–E run (Tasks 16 and 18 check it). **Labels point into `docs/` only**, never at a conventions document. Neither arm A variant is pointed at the conventions documents, though both can reach them with `Read` / `Grep` from the corpus root — that asymmetry, and A-index's index not linking `docs/vite/`, are **disclosed limits reported per half**, never corrected (no root index is written, and the corpus is never edited).

**Hard prohibitions that bind every task.** (1) **No search while the query set is authored or classified**: never run `docs search`, the MCP tool, or any eval arm between the start of Task 12 and the operator's approval in Task 15, never keep, drop or reword a query because of a score, and never read the `bestScore` / `abstained` / `hits` fields of a harvested log while choosing queries; the label pre-flight builds an index and checks chunk keys and runs no arm. (2) **Nothing is typed inside `<!-- eval:generated:start -->` / `<!-- eval:generated:end -->`** in `docs/retrieval-eval-results.md`; that region has one writer, `evals/docs-retrieval/run.mjs` with `--out`. (3) **No machine-local path, credential, token, environment value or account identifier** enters any committed file; the corpus is named by commit and size. (4) **No automated route to arm A** — no permission grant for the agent binary, no `scratch-run.sh` route to a session, no dispatched-subagent route; the one agent-CLI call this run makes is `--help`, which starts no session and bills nothing (Task 16). (5) **The decision rule is applied, never amended**: its two-variant combination and every reading of it are committed by Task 3 **before any figure exists**, and a bar that proves unmeasurable or ambiguous at the values that came back is recorded as a finding about the rule, not fixed by rewriting it. (6) No bare `node …` tool call — every eval module is reached through `bash scripts/scratch-run.sh <file under harness-runs/scratch/>` or through `scripts/run-gates.sh`, because an unmatched tool call stalls an unattended run.

**Who owns which part of `docs/retrieval-eval-results.md`**, so no two tasks write the same bytes. Below the end marker: Task 3 adds `### The re-calibration method, fixed before the real-catalog run` inside `## Threshold calibration`, Task 4 appends to it the record of how the committed sets' negatives were classed, and Task 23 rewrites the rest of that section; Task 14 creates `## The real-catalog query set` (placed after `## The query-log pass`) and Task 15 appends the operator's approval to it; Task 16 renames `## Arm A — awaiting a hand run` to **`## Arm A — the real-catalog hand run`** and writes how the run was taken, Task 17 appends its redaction record, and Task 19 writes its figures; Task 20 creates `## The decision, applied to the real catalog` after it; Task 24 owns `## The shipped default against fusion alone`. Inside the generated region: Task 18 adds the `gate10-catalog` block, Task 21 regenerates the `fixture-catalog` and `self-docs` blocks, and Task 23 regenerates `fixture-catalog` again only if the threshold moved. `docs/retrieval-eval.md` is edited section by section in the same way: Task 3 (`## The decision rule`, the combination), Task 4 (`## The query-set format`), Task 5 (`## What each metric means`), Tasks 7 and 8 (`## How to run it`), Task 10 (`## Running arm A by hand`), Task 16 (the two citations of the renamed heading) and Task 25 (the sentences the run makes false).

**The two mid-run parks, and how each resumes.** Task 15 (operator approval of the query set, checklist row 6) and Task 16 (the arm A runs at a terminal, checklist row 7) each return a plain `blocker:` naming an **operator-only** step the task prompt itself mandates a park for — spend and measurement integrity, never a low-stakes assumption — so the orchestrator's `<escalate>` parks the run and the watcher resumes it on the answer. On resume the answer comes back to the task-plan writer (the planning fork's `## Override 2 — resumability` case (a)), which **records it in that task's own per-task file under `### Operator answer`**, with no machine path, so the re-dispatched implementer finds it in the one file it reads; the top-level `answer_<n>.md` under `harness-runs/clarifications/feat_arm_a_real_catalog_measurement/` (or its `answered/` archive) is the second place the implementer may read it. The arm A transcripts are written by the operator's commands **inside this worktree** at `harness-runs/scratch/arm-a/gate10-catalog/`, which is gitignored by its contents, so neither the hand-off nor the answer has to name a path outside the tree.

**Why a `cli` task sits in the middle of the `general` sequence.** The two `cli` tasks are separate capabilities, not halves of one split: Task 1 adds the uncensored score to the library and ships first, bottom-up; Task 22 moves `ABSTAIN_SCORE_THRESHOLD` and can only follow the measurement it consumes (Tasks 18–21), so it is ordered by that dependency, and the catch-all record of the move (Task 23) follows it. Every other task is `general` — the eval under `evals/`, the documents under `docs/`, and the root prose files. The branch touches nothing under `plugin/`.

**The threshold move and the floor re-record — settled as Route 1.** `docs/retrieval-eval.md` → `## The regression floor` → the same-commit re-record rule requires a floor a change legitimately moves to be re-recorded in the commit that moved it, but the single-layer rule puts `cli/src/retrieval/search.ts` (Task 22, `cli`) and `evals/docs-retrieval/floor.json` (Task 23, `general`) in different commits. One `fixture-catalog` positive is worth about 0.11 of recall@5, more than the floor's 0.05 margin, so a raised threshold that abstains on one more positive turns gate 11 red. The plan resolves it in writing: Task 22, **before editing the constant**, predicts `fixture-catalog`'s arm E recall@5 and MRR at the new value from the regenerated block's per-query `bestRerankScore`, `abstained` and `rank` (a lowered value cannot lower either figure). When no figure is predicted below its floor, Task 22's gates must pass as usual. When one is, the **only** failure Task 22's commit may carry is the named gate 11 `FAIL` line for that metric, at the predicted figure. Task 23 — the immediately following readiness entry — then re-records the arm E floors and turns gate 11 green. `### What the move cost` discloses that the re-record is one commit behind the move, as a **finding about the same-commit rule**, not a quiet workaround. The loop never runs a separate floor-lowering commit. A red gate that differs from the prediction is a `blocker:`, not a commit.

**Settled here, before any figure exists** (and committed to the tree by Task 3 or recorded in the per-task file that owns it): the agent-task change is **a second token plus a second task file** — `agent-task.md` keeps the A-index text and gains an `{{index}}` token for the catalog-specific index path, and A-search gets `agent-task-search.md`, identical but for the navigation paragraph (Task 9 argues it); the generated table **learns a row per arm A variant**, `A-index` and `A-search`, through a repeatable `--transcript` (Task 8); the uncensored score is a new `SearchResult.bestRerankScore` field — the very `best` the threshold is compared against — that neither `renderResults`, the `docs search` output, the MCP answer nor the query log reads (Task 1); and **this branch takes the decision and records it but executes neither a default flip nor a withdrawal** — whichever change the outcome names is opened as roadmap item 18 in `docs/development.md` → `## 6. The roadmap this tree defers to` (Task 20), because a flip is the four-place configuration contract plus every adopter's behaviour and a withdrawal removes a shipped verb, its optional dependencies and the plugin's grants, and neither belongs in the review of a measurement. The operator's optional query-log harvest (checklist row 8) is **used only if that row reads `Done` when Task 12 is dispatched**; it reads `Open` at planning time, so the set is planned as written in full.

> Assumption: the decision rule states no statistic for arm A's "per-query wall time" or "token cost per query", nor what "one positive query's worth" means for a pooled calibration price. Task 3 fixes them before any figure exists — per repetition, the nearest-rank p50 of that repetition's per-query `durationMs` and the per-query mean of its billed tokens, the variant's figure being the median over its repetitions; the calibration price is one positive query, counted over the pooled set — so the reading cannot be chosen after the numbers. A reviewer or the user may correct the choice at review; it is recorded, not hidden.

**Top risks:** the likeliest failure is **a set or a threshold fitted to its own scores** — a query kept or reworded, or a negative marked `near`, after a score was seen. Task 3 commits the combination rule and the calibration method before any figure exists, Task 4 marks the committed sets' negatives `far` / `near` before Task 5 makes their scores observable, and Tasks 12–14 run no search while authoring. The second is **arm A measuring something other than navigation**: the real corpus is harness-initialised, so a session started in it could load its MCP search server or be handed a fenced answer; Task 9 starts every session with no MCP server and records per-query tool-call counts, Task 16 establishes what the corpus root carries before the operator spends, and Task 17 flags any tool outside `Read` / `Grep` / `Glob` in a transcript. The third is **a machine-local path reaching the tree** through a transcript, a provenance line or a park answer; Task 2 adds a standing check over the eval's committed artifacts to the gates, Task 7 stops the provenance from ever rendering a climbing or absolute query-set path, and Task 17 reads every transcript before committing it. The fourth is **two snapshots passing for one**: Task 16 records the corpus commit at hand-off and Task 18 refuses to publish unless that commit and the label pre-flight's snapshot stamp still hold.

**Manual setup required:**

- **Query-set approval** — task prompt `## Operator checklist` row 6, mid-run park raised by **Task 15**: the operator reads `evals/docs-retrieval/queries/gate10-catalog.jsonl`, spot-checks that every grade-3 label answers its query and every negative is uncovered, and approves or returns corrections by query id.
- **Arm A at a terminal, both variants, five repetitions each** — row 7, mid-run park raised by **Task 16**, which hands over the exact commands; repetition 1 of each variant is the cost checkpoint against row 5's pacing rule, and the operator reports the agent CLI version, the model, the 5-hour and 7-day window utilisation before and after each pass, and the operator time spent.
- **Teardown of the machine-local setup, after the branch** — row 9: restore the unattended settings profile and `watcher.env` from their `.bak-2026-09-23` backups in the harness's machine config directory, restart the watcher, and delete both backups. The run does not do this itself; **the closing *branch ready for review* summary must end with this reminder** (task prompt `## Acceptance` 14).
