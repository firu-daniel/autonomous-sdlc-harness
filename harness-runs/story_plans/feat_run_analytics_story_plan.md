# Story: Per-run analytics from the headless event stream

## Context

This branch adds a measurement script, `run-analytics.sh`, that turns each headless session's raw `stream-json` events into a per-run analytics record: where the wall time went (host suspend, idle gaps and their cause, per-request latency, per-tool-call and per-sub-agent time), what the session cost, and how reliable it was. Today that answer takes a forensic pass over a multi-megabyte `<state_dir>/autonomous_logs/<branch>.stream.jsonl`; the motivating three-file branch took 132 min, about half of it host sleep that no artifact recorded. The record is `<state_dir>/run_analytics/<branch>/run-analytics.json` — one record per headless session, the source of truth — with `run-analytics.md` beside it, regenerated from the JSON every time: a whole-run summary first, then one section per session, oldest first. It is measurement only: nothing on this branch kills, retries or delays a request, a tool call or a session on these numbers, and the raw `.stream.jsonl` stays where and as it is.

**The script is three files, so three tasks can each own one.** `cli/templates/scripts/lib/run-analytics.jq` computes per-session records from the stream (Task 1); `cli/templates/scripts/lib/run-analytics-report.jq` computes the run roll-up and renders the Markdown (Task 2); `cli/templates/scripts/run-analytics.sh` is the driver — arguments, paths, host suspend intervals, the idempotent merge by `session_id`, the byte-stable write (Task 3). Bash and `jq` 1.5 only, the floor `cli/templates/scripts/lib/harness-run-lib.sh` already states: no `--rawfile`, no `utf8bytelength`, one `jq` pass over the stream and no per-event shell loop, so a 10 MB stream finishes in seconds. Task 4 ships the three files through `OUTER_LOOP_SCRIPTS` and adds the `run_analytics` row to `STATE_DIR_ENTRIES`; Task 5 wires the watcher; Tasks 6 and 7 are the two test suites; Task 8 is the `/autonomous-sdlc-harness:branch-status` digest and the plugin text naming the new script; Task 9 mirrors the shipped files into this repository's own `scripts/` and `harness-runs/`; Task 10 documents it.

**One call site covers local and remote alike.** `autonomous-watcher.sh` → `spawn_engine`'s detached subshell is the one place a session has just ended, and job mode (`autonomous-watcher.sh job`, which the GitHub Actions `Run the harness` step runs) launches through the same `spawn_engine` — so the call Task 5 adds between `rc=${PIPESTATUS[0]}` and `classify_run_exit` runs after the launch, every park or pause resume, and every job-mode auto-resume, on a laptop and on a runner. No workflow template changes.

**The answer to the prompt's open question — how the file reaches the branch and survives between sessions: the watcher commits it on the run's branch, by plumbing, after each session.** Task 5 calls the watcher's existing `watcher_commit` (`hr_commit_placed` from `RUN_MAIN`) once per file, with the fixed subject `chore: Record run analytics for <branch>`. That is the watcher's established artifact-commit path (`cli/templates/scripts/autonomous-watcher.sh` → the comment above `CREATE_WORKTREE`: *"The artifact commit is not routed through `commit-on-branch.sh`: that wrapper stages its paths into the run's own index and judges the run's working copy"*): it commits exactly that one path, runs no hook, refuses a protected branch, and syncs the copy's index so the copy reads clean afterwards — so the next resume and every reviewer see a clean tree and an ordinary committed run artifact, like the flow-progress ledger. It returns `3` for an identical blob, which is what makes an unchanged re-run commit nothing. On GitHub Actions the commit lands in the job's checkout and the workflow's own `Push the branch` step (under `always()`) pushes it, so the next job — possibly on a fresh runner — checks the file out and appends to it. Locally the watcher does **not** push (the constraint is no network calls); the commit rides the next session's pushes, and the final session's record reaches origin with the branch's next push. Rejected: `commit-on-branch.sh` (stages into the run's own index — the reason above); the remote state bundle (`hr_remote_names_var` — machine-local, gitignored, `run.log`-style files there are never restored, it never reaches the branch, and it expires with the artifact retention, the expiring-store case `<state_dir>/lessons.md` → *Unattended control loops* warns about). The cost taken: two commits per session (one per file), because `hr_commit_placed` commits one path and widening the library's commit primitive is not this branch's change.

**Best-effort, always.** A failure of the script or of either commit is one line in the watcher log (`<state_dir>/autonomous_logs/watcher.log`, through the watcher's `log`), and the script's own output goes to the run's log; it never changes `rc`, the classification, the exit code or any notification. A session whose stream lacks a `result` event (still in flight, or killed by the stall watchdog) is recorded only once a later session follows it in the stream; a recorded session is never rewritten. The JSON and Markdown carry no wall-clock "generated at" stamp and are written with sorted keys, so a re-run over the same stream produces byte-identical files.

**No machine path is ever written (gate 6a).** Every free-text field (a sub-agent's description, a polled command, an error string) passes through one redaction: the run copy's root becomes `<repo_root>`, the main checkout `<main_repo>`, and `$HOME` or any `/Users/<name>` / `/home/<name>` prefix `~`. The watcher hands the script the main checkout's path as an explicit `--main-repo "$MAIN_REPO"` argument (Task 5). Without it, the run library's `hr_main_repo` answers a clone with the clone itself, and every run copy is a clone (Task 3 states the source and its fallback). The session's `cwd` from the `system`/`init` event is never recorded.

**Top risks:** the likeliest failure is the watcher hook changing a run's outcome — a slow or failing analytics step delaying, altering or swallowing the classification — which Task 5 guards by running it in a function that always returns `0` and never touches `rc`, and Task 7 pins by driving a failing analytics script through a real watcher pass and asserting the status and notification are unchanged. The second is a non-idempotent record — a re-run that duplicates or reshapes a recorded session, which would also make every resume commit noise — guarded by Task 3's merge-by-`session_id` with byte-stable output and pinned by Task 6's byte-for-byte re-run case. The third is a machine path leaking into a committed file and turning gate 6a red, guarded by Task 1's redaction and pinned by Task 6's assertion that the fixture repository's own path appears in neither output.

**Manual setup required:**
- Time `run-analytics.sh` once over a real stream of about 10 MB, by hand, outside any headless session, on an otherwise idle machine, to confirm the *"finishes in seconds"* constraint — `<state_dir>/lessons.md` → *Evidence and measurement* bars an in-run timing from being that evidence. Depends on Task 9 (the script is then in this repository's `scripts/`).
