# Story: Gate 11 grades the local build, not the machine-wide retrieval runtime

## Context

`scripts/run-gates.sh` → gate `11 docs-retrieval relevance floor` runs `node evals/docs-retrieval/check-floor.mjs`. On the way to its first index build, `evals/docs-retrieval/index-build.mjs` → `assertRealModelsAreAvailable` refuses unless `retrievalRuntimeState().installed` (`cli/src/retrieval/runtime.ts`). That predicate reads the **machine-wide runtime** under `${XDG_CACHE_HOME:-$HOME/.cache}/autonomous-sdlc-harness/retrieval/runtime`, and it requires that runtime's CLI to be at the local `cli/package.json` version. So every version bump on `dev` turns gate 11 `FAIL` with `missing: autonomous-sdlc-harness` on every machine until the new version is published and reinstalled. Yet the eval never loads that runtime. This branch changes three things. The runtime refusal is replaced by a refusal that tests what the eval really loads: the retrieval peers resolved from this checkout's own `cli/dist`. That new refusal is graded `BLOCKED` by the gate, like the empty model cache, with its own exit status and its own reason line. And the gate's dependencies are restated in `docs/development.md` and `docs/retrieval-eval.md`. The other two refusals stay unchanged: the stub variable must be unset and the model cache complete. Out of scope: publishing, how `init` installs the runtime, the floor values and the floor policy in `docs/retrieval-eval.md` → `## The regression floor`, and every other gate.

**The three "establish, do not assume" questions, answered while planning.**

- **Every caller of `assertRealModelsAreAvailable` loads the local build, and none runs the installed runtime.** There are three callers:
  - `evals/docs-retrieval/index-build.mjs` → `buildIndex` serves gate 11 and every `run.mjs` pass.
  - `evals/docs-retrieval/cold-build.mjs` → `measureColdBuild`.
  - `evals/docs-retrieval/query-log-pass.mjs` → `runQueryLogPass`.

  All three import `../../cli/dist/retrieval/*.js`, and those modules load every peer through `loadRetrievalModule`'s bare `import(specifier)`. That import resolves from `cli/dist/retrieval/` up to the workspace's own `node_modules`. The query-log pass's *"measures the shipped server"* means the shipped **server code**: its `runLeg` spawns `process.execPath` on `join(repoRoot, CLI_ENTRY)` with `CLI_ENTRY = 'cli/dist/cli.js'` → `docs serve`. That is this checkout's build, never `<cache>/retrieval/runtime/…/dist/cli.js`. Its static `@modelcontextprotocol/sdk` import also resolves from the workspace. So the group that "really runs the installed runtime" is empty. The runtime check is dropped from the shared refusal because each caller was shown not to need it, not because one caller does not. It is replaced by the check all three do need.
  - Measured while planning: `retrievalCliEntry()` from the local `cli/dist` answers `source: 'this-installation'`, so every peer resolves by its bare name from the build. On this machine `retrievalRuntimeState()` also answers `installed: true`, version `0.4.0`. That is why the defect is dormant today.
- **Gate 10's hand-run legs do not rely on this refusal.** No leg of `docs/development.md` → `## 5` → **Gate 10** runs a module under `evals/`. Legs (i), (ii) and (vi) run a pinned `npx --yes autonomous-sdlc-harness@<version>`, and legs (iii) and (iv) run the runtime's own entry by path. The guard against measuring a stale runtime there is leg (ii)'s `doctor` → `retrieval-dependencies` (`cli/src/doctor/checks.ts` → `RETRIEVAL_DEPENDENCIES_CHECK`). It answers from `retrievalRuntimeState()` against the pinned CLI's own version, and this branch does not touch it. The one place a gate-10 hand run used an eval module is the cold-build cross-check recorded in `docs/retrieval-eval-results.md` → `## Cold build and index size`. That check drove `measureColdBuild` from a throwaway launcher and is labelled there as the eval route, which always measured the local build. So nothing in gate 10 is weakened.
- **Whether the recorded floors hold on the local build is measured by Task 3, not assumed.** Gate 11 has only ever graded the local build: the runtime check only decided *whether* it ran, never *which code* it ran. So the last green gate 11 on this machine, with the runtime at `0.4.0`, is prior evidence that the floors in `evals/docs-retrieval/floor.json` hold. Task 3's `mismatch` probe takes the figure again with the runtime deliberately out of step. A shortfall is recorded and raised as a finding. `floor.json` is never edited on this branch.

**The `BLOCKED` decision (task prompt, deliverable 2), settled here.** A checkout whose build cannot resolve the retrieval peers is graded `BLOCKED`, like the empty model cache. It gets a **separate** exit status, `LOCAL_PEERS_ABSENT = 4`, so `MODEL_CACHE_ABSENT = 3` stays *"reserved for nothing else"* (`evals/docs-retrieval/check-floor.mjs`), and `scripts/run-gates.sh` prints a reason line that is true for the case it reports. Two reasons:
- Running `npm ci` is provisioning of the checkout, not a property of the retrieval code, which is the line the script already draws for the model cache.
- `BLOCKED` cannot turn an uninstalled checkout green: the gates that depend on the same install go red on their own when `npm ci` has not run (gate `2a build` needs `tsc`, gate `4 npm test` needs the suite).

The accepted cost: an install that resolves every peer the stub-path suites load, but not one only gate 11 loads (`@huggingface/transformers`), reports `BLOCKED` rather than `FAIL`. It is printed with its reason and the command to run, and listed with the gates the script cannot run, never passed over in silence. `docs/development.md` → **Gate 11** records this reason (Task 4).

**The cross-task interface, spelled once here and restated in each task that uses it.**
- `cli/src/retrieval/runtime.ts` → `export function unresolvedRetrievalPeers(): readonly string[]` (Task 1). It returns every `retrievalPeers()` name this installation cannot resolve from its own location, in manifest order. It resolves only, loads nothing, and any throw counts as unresolved.
- `evals/docs-retrieval/index-build.mjs` → `export const LOCAL_INSTALL_COMMAND = 'npm ci'` and the new third refusal of `assertRealModelsAreAvailable()` (Task 2).
- `evals/docs-retrieval/check-floor.mjs` → `export const LOCAL_PEERS_ABSENT = 4` and its stderr line (Task 3).
- `scripts/run-gates.sh`'s status-4 reason line, `  BLOCKED 11 docs-retrieval relevance floor — the workspace's retrieval packages are not installed` (Task 3). Task 4 describes it.

**The acceptance probe — one launcher, specified here so Tasks 2 and 3 build and run the same thing.** The task prompt's Acceptance 1 and 2 name `bash scripts/run-gates.sh` run under an altered cache. `plugin/instructions/unit_loop_core.md` → `## The test-run rule` reserves that script for the Run gates phase, which runs it once, in the unaltered environment (that is Acceptance 3). So the evidence is taken at the gate's own command boundary instead. The probe spawns exactly the command gate 11 runs, `node evals/docs-retrieval/check-floor.mjs`, from the repository root, with the environment altered for that one child. It reports the exit status, and `scripts/run-gates.sh`'s gate-11 block grades by that status alone: `0` → `ok`, `3` and (after Task 3) `4` → `BLOCKED`, anything else → `FAIL`. This probe is an eval run through the eval's documented route (`docs/retrieval-eval.md` → `### The two execution routes, and the one that stalls`). It drives the modules Tasks 2 and 3 edit, and no unit runs the gate script.
- **File:** `harness-runs/scratch/gate11-probe.mjs`. It is gitignored by that directory's rule, so it is never committed. Run it as `bash scripts/scratch-run.sh harness-runs/scratch/gate11-probe.mjs <case>`.
- **What it does, whatever the case:** it resolves the repository root from its own location, two levels up. It reads the local version from `cli/package.json`. It imports `cli/dist/retrieval/runtime.js` for `retrievalModelCacheDir()` (evaluated in the probe's own, unaltered environment, so it is the real model directory) and `retrievalPeers()`. It spawns `process.execPath` with `[<root>/evals/docs-retrieval/check-floor.mjs]`, `cwd` the root, through `spawnSync` with a fixed argument vector. The environment is `{ ...process.env }` plus the case's one change. It prints the case, the local version, the planted runtime version where there is one, `check-floor exit <status>`, and the child's stdout and stderr. Before printing, it replaces every occurrence of the repository root with `<repo>`, of the scratch cache directory with `<scratch cache>`, and of `os.homedir()` with `<home>`. It creates everything under `mkdtemp(join(os.tmpdir(), 'gate11-probe-'))`, never inside this checkout, and removes that directory in process with `rmSync(…, { recursive: true, force: true })` in a `finally`.
- **`mismatch`:** `XDG_CACHE_HOME` is the scratch directory. It holds a **copy** (`cpSync(…, { recursive: true })`) of the real model directory at `<scratch>/autonomous-sdlc-harness/retrieval/models`. It also holds a runtime at `<scratch>/autonomous-sdlc-harness/retrieval/runtime`, planted with an empty `node_modules/autonomous-sdlc-harness/dist/cli.js`, a `node_modules/autonomous-sdlc-harness/package.json` of `{ "name": "autonomous-sdlc-harness", "version": "0.3.0" }`, and a `node_modules/<peer>/package.json` of `{}` for every `retrievalPeers()` name. The runtime's one defect is therefore its version, which is the defect's exact shape. The probe refuses to run if the local version is itself `0.3.0`. The real cache is only read: never moved, renamed, re-pointed or written.
- **`empty`:** `XDG_CACHE_HOME` is the scratch directory, left empty.
- **`peers-absent`:** `XDG_CACHE_HOME` is left alone, so the real model cache is used, read-only. `NODE_OPTIONS` is `--import=<file URL of a register module>`. The probe writes that module, and the resolve hook it registers, into the scratch directory. The hook throws on any specifier that starts with a `retrievalPeers()` name and passes everything else to `nextResolve`. It is the same shape as `cli/test/retrieval-loading.test.mjs` → `writeHook`.

**Left to the maintainer, by hand.** The two whole-script runs the prompt words literally are Acceptance 1 and 2's `bash scripts/run-gates.sh` with `XDG_CACHE_HOME` pointed at a scratch directory for that one invocation. They reproduce what the probe shows through the script's own printing. No unit may run the gate script, and the Run gates phase cannot alter its environment. This is not a precondition of any task.

**Top risks:** The first is replacing the runtime refusal with nothing. A checkout without the peers would then fail inside `loadRetrievalModule`, whose message sends the reader to `init`, and be graded `FAIL`. Tasks 2 and 3 guard it: the local-peers refusal runs before anything loads, status 4 goes to `BLOCKED`, and the `peers-absent` probe proves both. The second is evidence that does not reproduce the mismatch. A scratch cache without the models reports `BLOCKED`, not the defect. Task 2 records the pre-fix `FAIL` with `missing: autonomous-sdlc-harness` from the `mismatch` probe before it edits anything, and Task 3 records the same probe's post-fix result. The third is this branch committing a machine path: the probe's child output carries absolute paths under the checkout, the home directory and the temp directory. The probe redacts them, and Tasks 2 and 3 each grep their own recorded output for `/Users/`, `/home/`, `/private/` and `/var/folders/` before finishing. Gate `6a` reads all of `harness-runs/`.
