# Story: A run copy commits under the main checkout's git identity

## Context

Since `feat_clone_per_run`, every run executes in a clone. `hr_clone_create_var` (`cli/templates/scripts/lib/harness-run-lib.sh`) rewrites the clone's `.git/config` to the allow-list `hr_clone_config_spec` prints, and `hr_clone_config_check_var` refuses any key outside it. The list holds the structural keys, `remote.origin.*`, `core.hooksPath` and the platform booleans, and no `user.*` key. So every git call that uses the clone as its repository takes its commit identity from the user's global `~/.gitconfig`, not from the identity the main checkout sets in its own `.git/config`. That was measured on `fix_run_gates_sandbox_tmpdir` (PR #126): all 23 commits carried the global identity. A legacy worktree run shares the main checkout's `.git/config`, so the defect started with the clone layout. The allow-list exists to keep a program-naming key out of a `.git/config` that the unsandboxed wrappers run git against. Leaving out the identity was never a decision: no plan, task file or review of `feat_clone_per_run` mentions it.

This branch makes the identity travel. `user.name` and `user.email` join the allow-list as **exact copies of the main checkout's values**, listed only when the main checkout's `.git/config` sets them. That is the same conditional form `remote.origin.url` already takes. `hr_clone_create_var` writes them into every new clone. Three properties do not change:
- A clone made before this change carries no `user.*` key and still passes the check, because the new keys are optional, never required.
- A value that differs from the main checkout's is still refused, so a session cannot set its own author identity.
- A main checkout that sets no identity gives a clone with no `user.*` key, which then commits under the global identity. In that case the global identity is the correct one by definition.

**The signing decision (goal 2), made here and recorded by both tasks: the commit-signing keys do not travel.** These are `user.signingkey`, `commit.gpgsign`, `gpg.format` and the program keys `gpg.program`, `gpg.<format>.program` and `gpg.ssh.defaultKeyCommand`. They stay off the allow-list, so the check still refuses them in a clone whatever their value. The reason: the commits that reach the clone's own configuration are the ones written with the clone as git's repository. The measured branch shows such commits are written, because their author came from the clone's configuration. Nothing has measured whether a signing program can run there and reach its key or agent socket. A signature that cannot be made fails the commit, so carrying `commit.gpgsign` could turn every run's unsigned commits into failed ones. Commits the main-checkout wrappers write through `git -C <main> commit-tree` already take the main checkout's identity *and* signing (`docs/cli.md` §6, residual 7), and they are unaffected. The task prompt fixes the terms for revisiting this decision. The program keys would travel only as the main checkout's exact values, with the main checkout's `.git/config` named as the trusted source in a deliberate trust decision, never in a widened rule. The measurement that would reopen it is an owed row Task 2 adds under roadmap item 21 (`docs/development.md` → `## 6. The roadmap this tree defers to`). This is a decision of record, not pending work.

**Goal 3 is checked, not edited.** No code outside the library reads the key list. The only readers of `hr_clone_config_spec` / `hr_clone_config_check_var` are the library itself (`git grep -nE 'hr_clone_config_spec|hr_clone_config_check_var' -- cli/src cli/templates plugin` names only `lib/harness-run-lib.sh`, plus a header comment in `setup-worktree.sh`). The per-run profile write-protects `<clone>/.git/config` as one whole file (`cli/templates/scripts/autonomous-watcher.sh` → `RUN_PROFILE_COPY_GIT_PATHS`), so the new keys are covered with no new entry. `doctor` has no check of a clone's configuration. Task 2 records that consistency statement in the docs.

The work is two single-layer tasks in bottom-up order. Task 1 (`cli`) widens the allow-list, writes the keys at creation, and proves both arms in `cli/test/clone-trust-check.test.mjs`. Task 2 (`general`, the catch-all, last) records the measurement and the decisions in `docs/sandbox-verification.md` and `docs/cli.md`. `phases.parity` is `false`, so no task cites a reference source. **No document of record names an account or an email.** The two identities are always "the main checkout's identity" and "the global one".

**Top risks:** The first is widening a trust surface that exists to keep programs out of an unsandboxed git's configuration. Task 1 guards it: it adds only the two data keys at exact values, and its tests prove that every signing and program key stays refused even at the main checkout's own value. The second is breaking runs already in flight. A clone made before this change, or before the self-adopted scripts are re-rendered, has no `user.*` key. Task 1's compatibility case shows such a clone still passes, and its header records the one new refusal: a main checkout whose identity changes while a clone is live. The third is the signing decision. Carrying `commit.gpgsign` unmeasured could fail every commit a run writes through the clone's configuration. Both tasks state the decision, and Task 2's owed row names the measurement that would reopen it.

**Manual setup required:**
1. After merge, re-render the self-adopted scripts in the main checkout so this repository's own runs pick up the widened library, then restart the watcher. The commands are those `docs/sandbox-verification.md` → `### The clone layout (owed)` → **Setup.** gives: `HARNESS_SELF_ADOPT=1 node cli/dist/cli.js init --force --no-analyze`, then `bash scripts/restart-watcher.sh`, restoring the hand-kept files §0 lists between the two. Earlier re-renders were their own supervised chores (#116, #123), and `scripts/lib/harness-run-lib.sh` is `init`'s output in this checkout. So no task here edits it. Until the re-render, this repository's runs keep committing under the global identity. No task depends on this step.
2. Clones that are live when the re-render lands keep no `user.*` key until they are recreated. Nothing migrates them, by design, the same as for the clone layout itself.
