# Story: Headless sessions wait for their background agents, and `completed` means the ledger finished

## Context

`fix_task_offer_check_script` was marked `completed`, and its "ready for review" notification went out, while every entry of its flow-progress ledger was still `[ ]`. Its resumed session had dispatched the `task-plan-writer` in the background and ended its turn. Headless `claude -p` waits at most 10 minutes for background tasks after the last turn, so the CLI stopped the planner and exited 0. The run log carries the CLI's own line, on Claude Code 2.1.314: `Background tasks still running 10m after the last turn (subagent "Write task plan with answers"); stopping them. Set CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0 to wait indefinitely.` `classify_run_exit` in `cli/templates/scripts/autonomous-watcher.sh` reads nothing but the pause sentinel, the clarification channel and `rc`, so it stamped that exit `completed`. This branch closes both halves. Every engine session waits for its background agents. A zero exit is `completed` only when the run's own ledger says it finished.

**Decisions this plan settles (each task restates the ones it implements):**

1. **The ceiling is set where every session is born, and nobody overrides it.** `spawn_engine`'s launch subshell exports `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` unconditionally, beside the existing `export HARNESS_MAIN_REPO`. It covers the task, user-review and docs engines, fresh launches, every resume pass and job mode. Verified: `run_job` reaches the engine only through `spawn_engine`, and `cli/templates/github/workflows/harness-run.yml` starts no session itself (its run step is `autonomous-watcher.sh job`). Because the export runs after the operator override channel and after any inherited environment, a value in `watcher.env` or in the watcher's environment cannot reach the session. A nonzero value is exactly the failure above. The one other `claude -p` in the shipped scripts, `remote-run.sh` → `control_mention_session`, is not an engine session. It runs with `--tools Read,Grep,Glob` and can start no sub-agent, so it is out of scope.
2. **How the staleness watchdog sees a session that is only waiting on a background agent.** The formatter (`autonomous-format-stream.sh`) keeps every `assistant` event's `tool_use`, whatever agent produced it. The incident's run log shows the background planner's own `→ Read` / `→ Bash` lines arriving after the orchestrator's last turn and before the CLI's stop line. So a working background agent keeps the run log's and the `.stream.jsonl`'s mtime moving. A background agent that hangs produces nothing, so the watchdog warns, kills, resets and resumes from the ledger exactly as before (`STALL_KILL_SECS`, the busy-CPU gate and `STALL_MAX_RESTARTS` unchanged).
3. **The new `pause_reason` is `unfinished`.** On the `rc -eq 0` arm, after the unchanged pause → park order, the watcher reads the run's ledger through a new library reader, `hr_run_ledger_state` (Task 1). `finished` → `completed`, as today. `unfinished` → `status paused` with `pause_reason unfinished`, written in one step, with no `completed` notification. It is the record `/autonomous-sdlc-harness:branch-resume` and `resume_paused_run` already resume from the ledger.
4. **What "finished" means per engine.** Task and user-review engines: the flow-progress ledger at `<state_dir>/flow_progress/<branch>_progress.md` reads all four phases `done` through `hr_ledger_phases`, **and** its header's engine is the run's engine, **and**, for the user-review engine, its round is the active round (the highest `<branch>_review[_<n>].md` under `<state_dir>/user_reviews/`, unsuffixed being round 1). That last pair matters because a user-review round inherits the previous run's all-`[x]` ledger until its Setup re-seeds it (`plugin/instructions/autonomous_pause_and_ledger.md` → `### 1.4 Creation`). Docs engine: it has no flow-progress ledger, and its checklist is the record (`plugin/instructions/docs_orchestration_instructions_autonomous.md` → `## Resume (every re-entry — fresh, or pause-resume)`: *"the committed checkboxes are the ledger"*, and the final entry is always the `INDEX`). It is finished when `<state_dir>/docs_catalog/<branch>_docs.md` has at least one entry and no entry left `[ ]`.
5. **An absent or unreadable ledger keeps today's behaviour, `completed`, plus one `watcher.log` line naming it.** The justification:
   - The task engine's planner fork and the user-review engine's fix-plan fork create their ledger at Setup, before the first dispatch, and the watcher commits a docs run's checklist before launch. So a session that was cut short while sub-agents ran always has one.
   - An absent ledger means the session stopped before Setup (a kill-switch halt, for example), or a flow wrote no ledger at all. A `paused` record there would point `branch-resume` at a ledger that does not exist.
   - Every existing watcher suite's stub exits 0 with no ledger and expects `completed`.
6. **Locally nothing auto-resumes an `unfinished` run.** It carries no `paused_by`, so the usage gate never touches it. The person at hand resumes it with `/autonomous-sdlc-harness:branch-resume`. **A user's pause outranks `unfinished` in job mode.** When `job_control_poll` has already recorded `pause_reason user` and dropped `PAUSE`, and the session exits 0 over an unfinished ledger before honouring it, `classify_run_exit` writes `status paused` and keeps the reason `user`, as the job-mode `PAUSE_ACK` arm does. It still logs the unfinished ledger and sends the same "paused as you asked" notification that arm sends, because `run_job`'s `user)` arm notifies nothing. `run_job`'s `user)` arm then stops the job (`detail="paused by the user"`) with no auto-resume. Only otherwise is the reason written `unfinished`. Writing it unconditionally would hand the record to the auto-resume arm below, and `begin_pause_resume` would delete the user's `PAUSE` (`harness-runs/lessons.md` → *Unattended control loops*, on re-checking an enable another actor can set). **Otherwise, in job mode it gets its own arm.** Today an unknown `pause_reason` falls into `run_job`'s `*)` arm, which treats it as an API-overload self-pause and words its exhaustion notice that way (verified). The new arm takes the same bounded `job_auto_resume` (`REMOTE_AUTO_RESUME_MAX`, `REMOTE_AUTO_RESUME_DELAY_SECS`, the job deadline). On exhaustion it ends `paused` / `stop` with one notification naming what happened and both resume routes. `hr_remote_status_write` gains `unfinished` in the bundle's vocabulary, so `remote-run.sh sync` carries it into the local record. `remote-run.sh` otherwise needs nothing: `sync` copies the reason verbatim, `report paused` words any reason generically, the control `resume` accepts any reason, and `poll` acts on `usage` alone.
7. **The stopped-agents line is logged whatever the classification.** The launch subshell records the run log's byte length before the engine starts. After the engine exits, it scans only what that session appended for a line carrying both `Background tasks still running` and `stopping them`, and writes one `watcher.log` line naming the branch. With decision 1 that line should never appear again. If it does, the setting did not take.
8. **`pause_reason` hygiene now that a local record can carry one.** The local `PAUSE_ACK` arm clears it in the same write that sets `paused`. `launch_run` clears it with the other reused-key fields, and `begin_pause_resume` clears it as the run goes back to `running`. Job mode's later writes (`budget` re-dropped by `job_auto_resume`, `user` by the control poll) all land after that clear. The new `unfinished` write never replaces a job-mode `user` reason (decision 6), so a user's pause survives a zero exit over an unfinished ledger and `job_auto_resume`'s `user` guard still holds.
9. **`scripts/` is re-rendered as a byte copy.** `docs/development.md` → *"Regenerating this repository's adoption after a `cli/templates/` change is one forced self-adopt run"* also rewrites `.claude/CLAUDE.md` and the three `.claude/context/` conventions documents, which this run may not target. For an outer-loop script the route's output is the template's bytes: the scripts are copied verbatim, and that section records every other `scripts/` file coming back byte-identical. So Task 9 copies `scripts/autonomous-watcher.sh`, `scripts/lib/harness-run-lib.sh` and `scripts/autonomous-notify.sh` from their templates and `cmp`s them, as `fix_linux_sandbox_deny_placeholders` Task 5 did. All three are byte-identical to their templates at this branch's base.
10. **The constraint "No orchestration-instruction change" is read as the task prompt explains it: the flows keep dispatching as they do now, and no rule about `run_in_background` is added.** Five orchestration forks and the canonical §2.5 state, as a consequence of their existing don't-end-the-turn rule, that *"the watcher stamps the run **`completed`** and notifies **success**"*. The same consequence is stated in §2.0's ⚠️ paragraph (*"and is stamped `completed`"*) and in the plan core's `### G.1 Run the gates`, clause (c) (*"classified `completed` behind a success notification"*). This branch makes all of them false. Goal 6 asks for every document stating when a run is marked `completed`. So Task 6 replaces only that consequence clause, at the same or a lower word count, and leaves every rule, dispatch and step untouched. No `run_in_background` wording is added anywhere.

**Facts the task prompt marked *verify*, as found:**
- `hr_ledger_phases` has **two** callers, not one: `job_progress_pass` in the watcher, and `remote-run.sh`'s `progress` report (the `forge_progress` path).
- `cli/test/helpers/watcher.mjs` drives local passes with a fake `HARNESS_AGENT_CLI` (`createWatcherFixture` → `tick`, `seedRecord`, `setStub`), and `cli/test/watcher-remote-job.test.mjs` drives job mode the same way.

**Top risks:**
- **A finished run read as `unfinished`**, which would park every good branch behind a `paused` record. A mis-parse of the user-review round or of the docs checklist would do it. Task 1 pins the reader against ledgers in the templates' exact shapes, finished and not, and Task 3 drives each engine's finished case end to end.
- **The setting not reaching the session**, because it was set outside the launch subshell or an operator's value displaced it. Task 2 asserts it from inside the stub, with both an inherited value and a `watcher.env` value set to something else, and the stopped-agents line is the field tripwire.
- **A job-mode regression.** Without Task 4 an `unfinished` job is mis-reported as an overload pause. Task 3's change also turns `watcher-remote-job`'s three `progress:` cases, which end on an unfinished ledger and expect `job: completed stop`, into a 300-second auto-resume wait. Task 4 owns both the arm and those cases.
