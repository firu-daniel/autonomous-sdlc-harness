# Story: Release the hung stall-watchdog stub on a test trigger instead of waiting out `sleep 60`

## Context

This branch stops the stall-watchdog suites from waiting out the hung stub's `sleep 60` when they run inside the sandbox. The task prompt measured the cause. Inside the sandbox `pgrep -P` cannot list processes, so `collect_descendants` in `autonomous-watcher.sh` returns nothing. The watchdog's kill (`stall-watchdog: '$b' is hung … — killing its process tree`, in `check_stalled_runs`) then takes down only the launch subshell `( … ) &` that `spawn_engine` records as the run's `pid`. The stub under it runs `HUNG_BODY` to the end, `sleep 60` included. `tee` and the formatter inherit the subshell's stderr, so they hold the test's `runBash` pipes open until the stub exits. Each case therefore costs about 8.5 s of work plus the whole 60 s sleep. Outside the sandbox the stub is killed and the sleep never matters, and real runs are unaffected because the watcher runs outside the sandbox. No watcher code changes on this branch: every target is a test file under `cli/test/`.

**The mechanism.** A hung stub no longer ends on a timer. After `go` it writes `silent` as today, then waits, writing nothing, until the test creates `<REC>/release`. Its upper bound is `HUNG_RELEASE_BOUND_SECS = scaleBound(90)`. That is a ceiling, so it goes through `scaleBound` (`cli/test/helpers/timing.mjs`, the module rule), and it is never shorter than the old 60 s, which keeps the prompt's *"Do not lower the sleep"* constraint. It stays below each case's own timeout at every scale: the hung wait (`scaleBound(60_000)` ms) plus the bound (`scaleBound(90)` s) is 150 × scale s, against the case timeout of 180 × scale s (`RUN_TIMEOUT_MS` / `STALL_TIMEOUT_MS`). When the bound expires with no release, the stub writes `<REC>/release-missed` and exits. Every case that uses the hung stub asserts that this file is absent, **before** any other assertion on the run, and the message names the missing release. So a missing release fails the case by name rather than passing it silently. Task 1 owns the body, the bound, the trigger predicate and that assertion in the shared driver `cli/test/helpers/watcher.mjs`, so the two suites that today carry identical private copies of `HUNG_BODY` read one definition. The precedent for a stub ended by a control file is `cli/test/watcher-stall-host-sleep.test.mjs`, whose stub waits for `end`.

**The trigger, per case.** The test creates the release once the watchdog has done what the case checks:
- **Local passes** — `watcher-stall-reset-payloads.test.mjs` → `localStall`, and `watcher-placeholder-host.test.mjs` → `stalledPass`. The pass script itself writes `: > "$REC/release"` right after the second `tick` and before `wait`. By then that `tick` has run `check_stalled_runs` to completion: the kill, the sweep, the reset or the give-up, and the relaunch.
  - `watcher-stall-reset-payloads`: the honest case, S1, S2, S3, S4, S4c, S5, S6, S7, S8, S9, S10 and S4 legacy.
  - `watcher-placeholder-host`: `(2)` and `(7)` → `the stall-watchdog resume`.
- **Job passes** — `watcher-stall-reset-payloads.test.mjs` → `jobStall` (J1–J6), and `watcher-placeholder-host.test.mjs` → `jobFixture` → `job` with a `plant` (`job: (1)`, `job: (2)`). `run_job` is one call, so no script line sits between the watchdog and the job's end. Instead the test polls the notification recorder after writing `go`. It releases at the first `failed` or `resumed` notification for the branch whose detail carries `stall-watchdog`. In both arms of `check_stalled_runs` that notification is the watchdog's last act: `notify failed … "(stall-watchdog: $why)"` after the record is set `failed`, or `notify resumed … "(stall-watchdog restart #…)"` after the relaunch. The poll also ends when the run has already settled, and then nothing is left to free.

Outside the sandbox nothing changes. The watchdog has already killed the stub when the release lands, so the release frees nothing. Every case keeps asserting what it asserts today.

**What was found for the two `sleep 30` stubs: neither waits out its sleep, and neither changes.** `watcher-remote-job.test.mjs` → `a job killed mid-run leaves running / continue` (`j.setStub('sleep 30')`) and `watcher-remote-park-sequence.test.mjs` → `jobKilledAfterStart` (used by `stop, then resume: …` with `job2Stub: 'sleep 30'`) work the same way. Each spawns the job `detached: true` with `stdio: 'ignore'` and ends it with `process.kill(-child.pid, 'SIGKILL')`. That is one signal to the job's whole process group: the watcher sets no `setsid` or `set -m`, so its session subshell and the stub stay in that group. The signal is not built on `pgrep`, and because the job's stdio is ignored no test pipe is held. So the stub dies with the group, and the test waits only for `exited` and its fixed `delay(500)` settle window. `cli/test/helpers/timing.mjs` keeps listing `sleep 30` in the killed-job stubs as a fixed stub lifetime.

**Measurement (task-prompt goal 4) is a human step, not acceptance evidence.** The prompt asks for per-case times taken sandboxed, the way its table was taken, and recorded in the PR: a headless session on the watcher's launch line, starting the run through `scratch-run.sh`. The ledger forbids making in-run timing a plan's acceptance evidence (`harness-runs/lessons.md` → *"A plan never makes repeated in-run timing runs its acceptance evidence"*). So each task proves the release mechanism by behaviour: outside the sandbox it is checked with `collect_descendants` overridden to answer nothing, which reproduces the sandbox's empty descendant list. The timing is listed under `Manual setup required:` below.

**Top risks:** The first risk is a release that comes too early. A stub freed before the watchdog's kill exits 0 under a live subshell, which classifies the run `completed`: the exact race the 60 s sleep was raised to avoid. Tasks 2 and 3 guard it by tying each release to an event that is strictly after the kill: the end of the second `tick`, or the watchdog's own verdict notification. Each task also checks this with the sandbox-simulating override. The second risk is a release that never comes and reads as a pass. Task 1's bound arm writes `release-missed`, and every hung-stub case asserts that file is absent before its other assertions. The third risk is a bound that crosses the case timeout under scale, so the runner's kill replaces the named failure. Task 1 fixes the bound at `scaleBound(90)` s and records the arithmetic against both suites' 180 × scale s case timeouts in the constant's doc comment.

**Manual setup required:**
- After Tasks 2 and 3 land, a maintainer takes the sandboxed timings the same way the prompt's table was taken and records the per-case times in the PR. First the three cases `an honest hung run resumes…`, `(S1)…` and `(S2)…`, then `cli/test/watcher-stall-reset-payloads.test.mjs` and `cli/test/watcher-placeholder-host.test.mjs` each as a whole. This depends on Tasks 2 and 3.
