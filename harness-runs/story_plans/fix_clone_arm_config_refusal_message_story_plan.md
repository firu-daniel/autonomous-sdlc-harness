# Story: Name an unresolvable configuration on the clone arm of the git wrappers

## Context

`bash <main>/<scripts_dir>/commit-on-branch.sh --repo <clone> …` refuses correctly when the main checkout's `harness.config.json` is absent or invalid, or when a pre-1.5 `jq` is first on `PATH`. It exits 1 and moves no ref. But it prints the wrong reason. It gives the clone trust check's line, `… its .git is not a regular pointer file, and the run registry records no clone of <main> at that path`, where the main checkout and a linked worktree print `cannot resolve '<main>/harness.config.json' — refusing to commit` followed by its parenthesised causes. The cause is in `cli/templates/scripts/lib/harness-run-lib.sh` → `hr_clone_target_check_var`. It finds the registry through `hr_state_path <main> autonomous_logs/registry.json`, which reads `stateDir` from that same configuration. When the lookup fails, `kind` stays empty and the function falls through to the "records no clone" refusal. Every wrapper loads the configuration only after `hr_wrapper_target_check_var`, so its own `cannot resolve` line never gets a chance to print. `push-branch.sh` and `refresh-branch.sh` have the same ordering. On a main-checkout or worktree target, both now fail at the hooks pin first (`hr_pinned_hooks_path` → `cannot resolve githooksDir from …`). Their configuration line is reached only from a later arm.

The fix has two parts, both in the `cli` layer, and a documentation pass in `general`.

- **Task 1 — the library.** The clone arm tells a failed `hr_state_path` apart from a missing record. It refuses with a sentence that names the configuration, so every caller of the check gets an accurate refusal: the three wrappers, `launch-sandboxed-gates.sh`, `cleanup-merged-worktrees.sh`, `setup-worktree.sh` and `task-offer-check.sh`. The return status stays `1`, because each of those callers treats any non-zero status as a refusal. A registry that is readable but has no matching record keeps today's sentence, and so does a clone `HEAD` that names no branch.
- **Task 2 — the three wrappers.** Each wrapper resolves the main checkout's configuration with `hr_config_load "$main_top"` right after `hr_wrapper_main_of` and before `hr_wrapper_target_check_var`. Each keeps its own existing `cannot resolve` literal and exit code: `commit-on-branch.sh` two stderr lines and exit 1, `push-branch.sh` one stdout line and exit 0, `refresh-branch.sh` two stderr lines and exit 1. So the main checkout, a worktree and a clone all print the same line in both cases. The read is safe to hoist because `<main_top>` comes from the script's own location, never the argument, and the read touches nothing of the target and makes no git call. The warmed per-process cache also means the clone arm's `$(hr_state_path …)` subshell reuses that load instead of running a second `jq`. Task 2 also creates the `cli/test` suite that "Done when" asks for.
- **Task 3 — documentation.** Updates `docs/outer-loop-verification.md` §1.1 and the target-check paragraph of `docs/cli.md` to match.

**Trust is not widened anywhere.** These tasks change which sentence a refusal prints and the order in which two refusals are tried. They never change what is accepted. `.claude/context/conventions.md` → `## The testing bar` and `harness-runs/lessons.md` → `## Trust checks` both apply: every new case asserts the bytes on disk (the branch ref in the main checkout and in the clone, and origin's refs for the push), not only the message.

This repository's own `scripts/` directory is `init`'s output for this checkout (`.claude/context/conventions.md` → `## Documents of record`). No task here edits it. The shipped templates under `cli/templates/scripts/` are the targets. `plugin/hooks/lib/harness-config-lib.sh` has its own clone resolution, which falls back to the default `stateDir`. It is a different design in a different layer and is out of scope.

**Top risks:** The first risk is that moving the configuration read ahead of the target check could look like a way for an untrusted target to steer a decision. Task 2 reads only `<main_top>/harness.config.json`, and its verification asserts that a scratch repository is still refused, and the trust check is otherwise unchanged. The second risk is losing today's registry line in the cases where it is still the true cause. Task 1's library case and Task 2's no-record case each pin it, with a readable configuration and a branch that has no record. The third risk is a documentation edit that rewrites a measured cell as if it had been re-driven. Task 3 keeps the 2026-11-06 reading and cites the new suite as a unit measurement, not a §0 row, the way §1.2's deleted-on-origin row already does.
