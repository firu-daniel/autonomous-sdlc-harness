# Story: Gate 6a passes in a per-branch worktree without losing what it guards

## Context

`scripts/run-gates.sh` → gate `6a no machine paths` runs `grep -rn "$HOME" . --exclude-dir=node_modules --exclude-dir=dist --exclude-dir=.git`. In a linked worktree `.git` is a one-line **file** (`gitdir: <main checkout>/.git/worktrees/<name>`), `--exclude-dir` skips directories only, so the gate prints `./.git:1:gitdir: …` and fails on every unit of every unattended run. This branch makes the gate skip that one line and nothing else, with one command that is the same in a main checkout and in a worktree, quotes the new command where `docs/development.md` quotes the old one, and removes the real machine paths already committed under `harness-runs/` so the gate can actually report `ok` in a worktree. All three tasks sit in the catch-all `general` layer (`scripts/`, `docs/`, `harness-runs/`); no `cli/` or `plugin/` file changes.

**Why an output filter and not a grep flag.** The obvious one-flag fix is `--exclude=.git`, but GNU grep (manual, `--exclude`: *"skip any subfile whose base name matches GLOB"*) and BSD grep both match that flag against a file's **base name**, so it would also skip every nested file called `.git` anywhere in the tree — which the gate prints today, and which the task prompt's first deliverable forbids (*"and nothing else it did not exclude before"*). `--exclude=./.git` is honoured by macOS's BSD grep (measured on this branch: it drops the pointer file) but not by GNU grep, which matches a recursive subfile's base name only, so on Linux it would exclude nothing. The one exclusion that is exact and portable is a second stage that drops output lines beginning `./.git:<line>:` — the path `./.git` exactly, at the search root. In a main checkout `.git` is a directory `--exclude-dir=.git` already skips, so that stage never matches there: the command is identical in both kinds of checkout and needs no branch on which it runs in. The pipe that adds is safe only because `gate_silent` grades **output**, never exit status; Task 1 says so in the script.

**What the tree names today, measured while planning.** With the old command and the system grep, this worktree printed the `./.git` pointer line **plus** home-rooted paths in six committed files under `harness-runs/` — one earlier branch's task prompt, one architecture review and four improvement-observations files, most of them quoting a `gitdir:` line as evidence of this very defect. Those are genuine findings, not false ones, and they are on `dev`, so every worktree cut from it inherits them: fixing the filter alone leaves `commands.test` red in every run, which is the defect this branch exists to remove. Task 3 therefore replaces the home prefix in those six files with a placeholder, following the precedent of commit `281c37f`'s own last step (*"Replace the machine path in the run's improvement observations"*), which wrote `<main checkout>` in place of the same kind of `gitdir:` path. Nothing is excluded for them: the gate still reads all of `harness-runs/`.

**The two "establish, do not assume" questions, answered while planning.**

- **The grep does not honour `.gitignore`.** Run in the main checkout (on `dev`, profile present) with the system grep, gate 6a's command prints `.claude/settings.autonomous.json` — the unattended permission profile `.gitignore` ignores — plus every gitignored log, stream transcript, registry and `.tail_*` command file under `harness-runs/autonomous_logs/`, plus the six committed `harness-runs/` files above. So the profile trips the gate, and so do the logs. That makes `docs/development.md` → the paragraph opening *"The `$HOME` half is a different matter, and self-adoption breaches it."* and the list under it **stale**: the "ignore the profile" way out it describes as open has been taken (the last rule of `.gitignore`, *"Added by hand in this repository, not by init"*), yet its promised result — *"Gate 6a then stays a print-nothing gate and keeps its whole meaning"* — did not follow, because ignoring a file does not hide it from a recursive grep; and *"that one file carries every `$HOME` hit in the tree"* is no longer true. Per the task prompt this branch **reports** that and changes neither the paragraph nor what the gate excludes for the profile — that is a separate decision (a hand edit, per the maintainer's own practice for stale prose).
- **Who quotes the gate's command line.** No test does. `docs/development.md` → `## 5` → **Gate 6 — self-containment.** quotes it in its fenced block, and quotes it already out of date: it lacks the script's `--exclude-dir=.git`, so a contributor running it by hand in a main checkout greps the `.git` directory too. Task 2 replaces that line with the new command. Run artifacts under `harness-runs/` that quote the old command are records of what ran and are left alone (see `## Scope register`).

**Measuring this correctly.** Inside an agent's Bash tool, a bare `grep` is a shell **function** that runs `ugrep --ignore-files` — it honours `.gitignore` and so hides exactly the hits this gate is about. `bash scripts/run-gates.sh` is unaffected (a script does not inherit the function) and is the authoritative measurement; any by-hand probe uses `command grep`, which reaches the system grep. The main checkout is on `dev` and does not carry this branch's script until merge, so acceptance 3 is evidenced before merge by running the old and the new 6a command against it and showing identical output (Task 1).

**Top risks:** the first is an exclusion wider than the pointer file — a `--exclude=.git` or an unanchored filter would silently stop printing a nested `.git` file or a record quoting a `gitdir:` line, which the prompt's first deliverable names; Task 1 guards it with an anchored filter and a planted nested `.git` file and a planted `harness-runs/scratch/` file that must both still be printed. The second is a green result that is not real — measured through the Bash tool's ignore-honouring `grep` function, or in a worktree still carrying the six committed machine paths; Task 3 closes on a full `bash scripts/run-gates.sh` reporting `ok    6a no machine paths` after the redaction, with `git grep -nF "$HOME"` printing nothing. The third is this branch re-committing the breach it fixes: any artifact this run writes — a plan, a return quoted into a record, an improvement observation — that pastes a `gitdir:` line or a probe path with the home prefix intact puts a new hit under `harness-runs/`; every task writes `<main checkout>` or `<home>` instead, and Task 3's closing `git grep` would catch a slip.
