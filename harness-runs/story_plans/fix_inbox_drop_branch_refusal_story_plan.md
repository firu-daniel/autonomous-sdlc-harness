# Story: Refuse an inbox drop for a protected or invalid branch at intake

## Context

The watcher derives a run's branch from the dropped filename alone (`cli/templates/scripts/lib/harness-run-lib.sh` → `hr_inbox_route_var`) and then, in `cli/templates/scripts/autonomous-watcher.sh` → `process_inbox_file`, goes on to create a working copy, place and commit the artifact and launch or dispatch the run. Nothing checks that branch until `hr_clone_create_var` or the commit wrapper refuses it, so a drop named for a protected branch (the configured `defaultBranch`, or anything in `protectedBranches`) or for a name git will not accept as a branch gets as far as `create-worktree.sh`, and a drop whose protected set cannot be resolved gets just as far. The other entry points already refuse such a branch: `hr_branch_taken_judge` for `/autonomous-sdlc-harness:branch-prompt`, the watcher's own `job)` arm, and `remote-run.sh` → `control_check_branch`. Since the unattended sandbox profile grants write access to `<main>/<stateDir>/`, any sandboxed command of any run can now write a drop, so the intake refusal is the only check such a drop meets before the watcher acts on it.

This branch adds that refusal. It lives in one place: a new library function, `hr_inbox_branch_refusal_var <root> <branch>`, next to `hr_inbox_route_var` under the library's `Inbox routing — the one owner of the drop filename patterns.` banner. It refuses (returns 1, with `HR_INBOX_REFUSAL` set to the reason) when the branch is empty, starts with `-`, fails `git check-ref-format --branch`, or is something `--branch` *expands* rather than accepts (the `@{-N}` previous-checkout syntax, which can reach the router because a filename can contain `@{-1}`). It also refuses when `hr_branch_is_protected` answers 0 (protected) or 2 (unresolvable). It reuses `hr_branch_is_protected` and adds no second matcher, as the task prompt requires. `process_inbox_file` calls it immediately after routing and before anything else: before the kill switch, before `execution.target` is read, before the run log is named and before any `remote-run.sh sync`. One call therefore covers all three patterns (`_task_prompt.md`, `_review[_<n>].md`, `_docs.md`) and both targets, and a GitHub-bound drop is refused before `launch_remote_run` is ever reachable. A refused drop is archived as `rejected_<ts>_<name>`, one log line names the reason, and one `failed` notification goes out through the watcher's existing `reject_preserving_status` helper, which never writes the registry. **How the plan reads the prompt's "same … notification as an unroutable filename":** today's unroutable arm archives and logs but sends no notification. The prompt asks for a notification and wants the user to see the reason locally, so the plan uses the existing rejection helper that archives under `rejected_` *and* notifies, and leaves the unroutable arm as it is.

The work is four single-layer tasks in bottom-up order: the library function and its unit case (Task 1, `cli`), the watcher wiring with its header and the adopter-facing inbox README (Task 2, `cli`), the behavioural cases in the watcher's intake suite (Task 3, `cli`), and the watcher's design-of-record document (Task 4, `general`, last). The prompt names "the existing watcher intake suite". The plan reads that as `cli/test/watcher-remote-dispatch.test.mjs`: it holds the one existing intake-routing case (*"with the key absent a drop routes through the library: task engine on its branch, junk rejected"*, which asserts the `rejected_\d+_notes\.md` archive), and its `createDispatchFixture` drives both `execution.target` values.

This repository's self-adopted copies of the changed templates (`scripts/autonomous-watcher.sh`, `scripts/lib/harness-run-lib.sh`, `harness-runs/autonomous_inbox/README.md`) are `init`'s output in this checkout. They catch up at the maintainer's forced self-adopt re-render (`docs/development.md` → *"Regenerating this repository's adoption after a `cli/templates/` change is one forced self-adopt run"*), and no task edits them.

**Top risks:** The first is placement: a refusal placed after anything that writes would still leave something behind — the run log through `remote-run.sh sync`, a working copy, a registry record. Task 2 places the call before every one of those, and Task 3 checks on disk that nothing was created, that a remote refusal makes no `gh` call at all, and that no run log appears. The second is that `git check-ref-format --branch` *expands* `@{-1}` to the previous branch and exits 0, so an exit-status-only check would accept it. Task 1 also requires the printed name to equal the input and covers that case with a fixture that has a previous checkout. The third is the unresolvable answer (status 2) being treated as a permit. Task 1 maps it to a refusal, and Task 3 proves it end to end by making the configuration unresolvable between the watcher's start-up check and the pass.
