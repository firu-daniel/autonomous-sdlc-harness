**The decisions this plan takes**, each one implemented by a task named here and recorded in `docs/github-run-control.md` by Task 16 or Task 17:

- **Item 7.** Classification no longer depends on registry memory that a job boundary loses. Each session records, at launch, every top-level `question_<n>.md` / `answer_<n>.md` pair present on disk (`launch_answered_set`). A non-pause exit archives the union of that set and `resumed_for_index`. The session read those pairs: the canonical consume-then-archive contract says a re-entering engine consumes every top-level answered pair, so this is safe after any sequence of answer, pause (user, budget, usage), stop and resume. Because the set is re-derived from disk at every launch, `status.json` does not need to carry `resumed_for_index`, and its schema stays `1` (Task 1). A `parked` report with no open question now posts nothing and prints an `::error::` line instead (Task 2).
- **Item 5.** `control` handles the `issues: closed`, `pull_request: closed` and `delete` events, and stops the run through the existing `stop` verb (Task 11). `stop` gains `--note`, `--pr` and `--branch-gone` options (Task 9). The poller and the automatic resume skip a branch absent on `origin` (Task 10). `harness-control.yml` listens to the three events (Task 13). A deleted branch's stop marker is dispatched from GitHub's default branch, because that is the only ref still there. `remote_branch_stopped` already finds a marker by its title across every branch.
- **Item 2.** The workflow maps `control`'s exit 2 to step success with `|| [ $? -eq 2 ]` (Task 13). `remote-run.sh` keeps 2 for its script callers.
- **Item 3.** The root cause is in the question file, not in the `report` verb. The canonical clarification format gains a rule: a question file names no answer channel (Task 14). As a backstop, `report` leaves out every line of `question_<n>.md` that names `answer_<n>.md` (Task 2). The file-channel line is not a known line of the canonical format. The writer adds it in its own words, so `report` cannot replace a fixed string.
- **Item 8.** Accepted, and documented. The job token opens the pull request today, and `deliver` already uses `HARNESS_GIT_TOKEN` when it is set. Round 6 measured that the job token puts no cross-reference on the issue. Linking through the issue's Development panel is recorded as a **proposal** for the maintainer, not as owed work: no roadmap row carries it, because no one but this plan decided it (`harness-runs/lessons.md` → `## Evidence and measurement`). Leg (d) and §4 now say that the link is the `completed` comment's URL. §8 records the measured row and an unverified row for `HARNESS_GIT_TOKEN` (Tasks 17 and 19).
- **Item 9.** `harness-run.yml` fails fast in a new job, `wrong-ref`, when `action` is `run` or `pause` and `github.ref_name` is not the `branch` input, naming the ref to use. Item 5's deleted-branch marker must be dispatched from the default branch, and the stop check reads markers by title across all branches.

Every refusal, in-flight reply and `status` reply uses that word (Tasks 7 and 8). The states each verb accepts are unchanged: an answer to a stopped parked run, or a clear of a stopped park-loop run, is its resume. The run list stays the authority, and the bundle vocabulary is unchanged.
- **Item 12.** In job mode, a carried `PAUSE_PROGRESS.md` is kept only when the job's `resume` is `pause`, the restored `remote_status.json` says `status: paused`, and its `engine` equals the job's engine. In every other case — a fresh launch (`resume none`), an answer resume (`resume answer`), a pause resume whose previous job did not pause (a stop or a kill), or a different engine — it is moved aside, never deleted, to `<state_dir>/autonomous_logs/remote_superseded/<epoch>[-<n>]/PAUSE_PROGRESS.md`. ### Item 4 — Open the draft pull request when the run starts; flip it to ready on completion — Medium (design, decided)

- **What:** today `deliver` opens the draft pull request only once the run **completes** (`docs/github-run-control.md` §4–§5). Lifecycle comments use the target rule "PR if one exists, else the issue", so the whole first run is worked on the issue, and the conversation moves to the pull request only after completion.
- **Decision (operator, 2026-10-02):** open the draft pull request when the run starts. A user can already open a pull request from the run's branch by hand, and it is then recognised as the run's (§2 *Which pull requests count*, §4 *A locally executed run gets none*). Opening it at start makes the job do what a user can already do.
- **The fix:**
  - Open the draft pull request (body `Started from #<n>.` plus the commands text) right after the task-prompt commit is pushed: in `start` or the trigger, or at the top of the first `harness run` job. Use the same token rules and the same one ready-PR retry as `deliver`. `deliver` then only reuses the open pull request.
  - **Recognition before the ledger exists.** `forge_recognised` reads the flow-progress ledger at the branch tip, and that ledger is not on `origin` until the flow's first committer push. So a pull request opened at start is not a lifecycle target until then. Decide how a pull request the harness opened is recognised before the ledger lands (for example, the task prompt at the tip, or the `pull-request` marker in its body). Say what that changes for `control_check_branch`.
  - **`completed` goes on the pull request always, and also on the source issue when one exists** (decided). Both get `sdlc-harness: done`. Generalise the target rule: every lifecycle comment goes to the pull request, and the source item (the issue, or a link back to an external ticket) gets `launched` and `completed`. A comment command on the issue keeps working, because it resolves the branch from the `started` comment.
