# Story: Converging plan reviews — every reviewer every round, converging mode from round 3, per-round commits

## Context

This branch changes how the two plan-writing loops review a plan. In the task-plan loop every plan reviewer now runs in every round: a reviewer's `FAIL` no longer sends the plan straight back to the writer, it is recorded and the walk moves on to the next reviewer, and one decision point after the last reviewer closes the round — back to the writer with every findings file of the round when any reviewer failed, on to the UI-test-plan loop when none did. Every reviewer writes one file per round, `PASS` included, named by the round number, so the round's files sit at the same index in every reviewer's folder. From the third round on, reviewers run in **converging** mode: they check their own previous Must Fix items, the changes the writer made and the recorded rejections, and nothing else; anything else they notice goes under `## Incidental findings (not gating)`, which never gates and which the end-of-branch reviewers later read as leads. The writer revises by target file, resolves incompatible findings by precedence, and leaves a revision note per round. In the autonomous fork each round ends with a commit, and a planning pause commits the round so far. The user-review fix-plan loop gets the same treatment in its own prose. The work is cut bottom-up: the `cli` layer (the walker, its gate library, its graph, the bundle's planning paths, the run-artifact tree and their tests), then the `plugin` layer (one new shared instruction module, the two loop cores, the five plan agents, the pause module, the forks, the end-of-branch reviewers, the implementation-flow readers and the flow documents), then the catch-all `general` layer (the schema and its fixtures, the static checker, this checkout's self-adopted copies, and the documents of record).

**The graph format changes, so `formatVersion` becomes 2.** The existing format has no node that routes without an agent's outcome and no walker state that remembers verdicts within a round, so the decision point is a new node kind, `"kind": "round"`. The planning graph's round node is `plan_round`: `gates` lists `business_parity_review`, `architecture_review`, `plan_review` in gate order; `writer` is `plan_writer`; `counter` is `iteration`; `convergingFrom` is `2` (the 0-based counter value from which reviewers run `converging` — the third round of the current walk); `plan` lists the `paths` entries `story_index` and `task_files`; `revisionNote` names the `paths` entry `revision_note`; and its `outcomes` are exactly `PASS` (to `ui_writer`, `reset: iteration`, `ledger: P1`) and `FAIL` (to `plan_writer`, `increment: iteration`, `prompt: revision`, with the one `onCap` escalation whose `summary` carries the token `{open_gates}`). Each gate's `PASS` and `FAIL` both route to the next gate, and `plan_review`'s to `plan_round`; a gate's `PASS` edge still records its `report`. `paths` gains `task_files` (`{state_dir}/task_plans/{branch}/`) and `revision_note` (`{state_dir}/plan_revisions/{branch}/task_plan_revision_{round}.md`, the `{round}` token new). The walker never names a gate in its code: which nodes are gates, and in what order, is read off a round node's `gates`, so turning the sequence into a fan-out later changes edges only (Task 2 owns the graph, Task 3 the walker).

**What the walker prints that it did not print before** (Task 3 produces it; Tasks 4–6, 11, 19 and 28 consume it). The walker keeps **two numbers apart**: the loop **counter** (`iteration`, the heartbeat's `iter`), which alone drives the cap and the review mode, and the **round number**, which names the round files. A dispatch of a round gate prints `arg.iteration: <round number>` — the same in every gate's folder, no longer the next free index — then `arg.review_mode: full` while the counter is below `convergingFrom` and `arg.review_mode: converging` from it on. Every dispatch of a round's `writer` prints `arg.iteration: <round number>` (the round the write feeds), and a revision then prints one `arg.findings_file: <path>` line per findings file the closed round recorded, in `gates` order — the key stays byte-stable and repeats, because a path may contain any character a separator could. `ui_writer`'s revision is unchanged: one `arg.findings_file:` line. `next` requires `--findings` with `PASS` **and** `FAIL` from a round gate, because every gate now writes a file every round. Passing through a round node prints `round: <n> <PASS|FAIL>` among the `skip:` / `ledger:` lines, `<n>` being the round number of the round it closed. A cap escalation reached from a round node prints no `agent:` line, one `findings_file:` line per file of the closing round, `rounds: <gate> <n>` counting that gate's files whose verdict is `FAIL` (a `PASS` file is no longer a failed round), and a `summary:` whose `{open_gates}` is the comma-joined ids of the gates that failed the closing round. **The counter is never derived from round files** (the user's ruling on this run's cap park, restated in the task prompt's Part 4): it carries over only when a saved walk is continued, and every `start` sets it to 0, as today — so a fresh write, an extend and an answered cap park (a finished walk, never continued) each get the full five-round budget and two `full` rounds. The round number carries on across the branch's whole planning history: `start` reads it, and the within-round position, off the round evidence `fw_round_evidence` reports (Task 1), continuing at the next due reviewer when the evidence is complete and consistent and restarting the round at its first gate otherwise — never inferring convergence from files, so a round whose files all read `PASS` is reviewed again. The fix-plan loop keeps the same split in prose: `fix_round` names its files and `fix_round − cap_base` is its counter (Tasks 12 and 20).

**The round file and the reviewer contract are one shared module**, `plugin/instructions/plan_review_rounds.md` (Task 10), cited by both loop cores and all five plan agents rather than copied into each — the ledger's *"state a new behaviour once … and cite it from everywhere else"* rule. A round file is `<findings_folder>/review_<iteration>.md`, opens `# <reviewer title> — round <iteration>`, carries exactly one line `verdict: PASS` or `verdict: FAIL` and one line `review_mode: full` or `review_mode: converging`, and is written on `PASS` too, in which case the reviewer returns `verdict: PASS` then `findings_file: <full_path>` (the verdict-line contract itself is unchanged). A reviewer that finds its own file for the round already on disk replaces it: that file is from an interrupted round. Every Must Fix gains a quoted **`Raised against:`** line (the text the finding was raised against) and a **`Must hold:`** line (the property that must hold), beside its existing target-file naming and `**Fix:**`. The reviewers' dispatch blocks gain two keys, `review_mode:` and `revision_note:`. The writer's revision prompt names every findings file of the round and the revision note it must write: the task-plan writer gets `Revise the task plan per findings at <findings_files>.` followed by `Revision note: <state_dir>/plan_revisions/<branch>/task_plan_revision_<iteration>.md`, where `<findings_files>` is every printed `arg.findings_file:` value joined by `, `.

**Where each new name lives, and why.** Revision notes go under a new run-artifact directory, `<state_dir>/plan_revisions/<branch>/` — one writer-owned folder for both loops, its files numbered by the round they feed so a converging reviewer's lookup is the same index as its own dispatch: `task_plan_revision_<n>.md` for the task plan, `fix_plan_<N>_revision_<k>.md` for the fix plan of user-review round `<N>`. The fix-plan loop's two gate folders become per user-review round, `<state_dir>/business_parity_user_review_reviews/<branch>/user_review_<N>/` and `<state_dir>/architecture_user_review_reviews/<branch>/user_review_<N>/`, because a round-numbered file in today's flat per-branch folder would overwrite an earlier user-review round's files; `<N>` is `1` for the unsuffixed review. The fix-plan loop keeps one counter, `fix_round`, the round index `<k>` in those folders; its cap and its review mode count rounds since `cap_base` — the last writer dispatch that was not a findings revision, or a resumed session's start. The new fixed commit subjects are `chore: Plan round <n> for <branch>`, `chore: Plan round <n> partial for <branch>`, `chore: Fix plan <N> round <k> for <branch>` and `chore: Fix plan <N> round <k> partial for <branch>`; a converging reviewer finds the previous round's commit by its subject, where one exists, and reads the plan's diff since it. The task-plan planning path set — committed at a round's end and on a planning pause — is exactly: the story index, `<state_dir>/task_plans/<branch>/`, `<state_dir>/task_plan_reviews/<branch>/`, `<state_dir>/business_parity_reviews/<branch>/`, `<state_dir>/architecture_reviews/<branch>/` and `<state_dir>/plan_revisions/<branch>/`; the fix-plan set is the active round's fix-plan index and per-finding folder, the two `user_review_<N>/` gate folders and `<state_dir>/plan_revisions/<branch>/`.

**Convergence is the ledger's, never the commit's.** From this branch on an unconverged plan is in branch history by design, so `P1` (and `R1` for the fix plan) is the only signal that a loop converged; every resume reader that inferred convergence from plan files on disk is restated to read the ledger. The supervised and semi-autonomous flows commit nothing during planning; their converging reviewers work from the findings files and the revision note.

**One revision on disk after any interruption.** With task-plan files tracked, a session that ends between a writer's revision and the round's commit could leave the committed round beside newer drafts. A `PAUSE` and an overload self-pause commit the round so far first (Task 18, §2.2 and §2.5; Tasks 19 and 20 in the forks). A remote job killed mid-round takes no commit, so its next job's restore withholds the bundle's task-plan drafts once the checkout tracks the story index, and withholds the saved walk too when a draft differs, so the session resumes from the committed round through the walker's round evidence. The restore logs each withhold on a line of its own, leaving its placed/kept line byte-identical (Task 7; Task 27 copies `remote-run.sh`; Task 29 records it). A withheld restore prints no placed/kept line, so Gate 12's FR6 grader and the FR6 contract are restated to pass a `withheld <n> planning file(s)` line as they pass a placed one (Task 32, ordered after Task 27), and the `cli` suite that grades the grader, `cli/test/gate12-sandbox-round-full-run.test.mjs`, pins that pass in a task of its own layer (Task 33, ordered directly after Task 32).

Reversible: the record is a document, and a reviewer who reads the prompt otherwise can add a results section to it.

**Top risks:** the first is a plan that passes with a real defect because converging rounds look only at changed text — Task 10 makes the incidental-findings heading and its never-gating rule one contract, Task 22 hands those sections to `branch-reviewer` and `skeptic-reviewer` as leads, and Task 30 ships the measurement that tests exactly this. The second is a resume that lands in the wrong place, reviews a mixture of two revisions, or confuses the round number with the cap counter once plan files are tracked — Task 3 keeps the two numbers apart and restarts the round whenever the evidence is incomplete, Tasks 5 and 6 pin both arms and the fresh budget after a cap park, Task 7 keeps a job restore from mixing revisions, and Tasks 18, 19 and 20 make every resume reader read `P1` / `R1`. The third is drift between the walker's new output lines, the core that acts on them and the forks that commit on them — Task 3 defines each line once, Task 11 maps each to a dispatch key, Tasks 19 and 20 commit on the `round:` line and the pause path sets, and Task 9 pins those path sets at the commit wrapper.
