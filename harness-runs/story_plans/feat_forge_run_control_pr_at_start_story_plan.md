# Story: Run control from the pull request — roadmap item 19

## Context

This branch lands the run-control design the operator decided in Gate 12 round 6, roadmap item 19 (`docs/development.md` → `## 6. The roadmap this tree defers to`, row 19). Four behaviours change, all on the GitHub side of a run that executes in GitHub Actions with `forge` `github`. **Item 4:** the draft pull request opens when the run starts. Its draft state follows the run: a draft while the run works, ready on `completed`, back to draft when a user-review round starts. `completed` is posted on the pull request always, and on the source issue too. **Item 8:** the source issue names the pull request as soon as it opens. **Item 13:** at a round's `completed`, the inline review threads the round collected and implemented get a reply naming the fix commit and are resolved. Threads for invalid or out-of-scope findings get the reason and stay open. **Item 6:** one progress comment per run or round on the pull request, ticking over at the four main phases.

The code of record is `cli/templates/scripts/remote-run.sh`, whose header states every verb, its exit map and its `REPRO` block, so each task that changes a verb also changes that verb's header paragraph. Tasks 3, 4, 6, 7, 8 and 9 all edit that one file in sequence, and each depends on the one before it. The other code sites are `cli/templates/scripts/lib/harness-run-lib.sh` (the shared shell library), `cli/templates/scripts/autonomous-watcher.sh` → `run_job` (the job's supervision loop), `cli/templates/github/workflows/harness-run.yml`, and the configuration contract (`schemas/harness.config.schema.json`, `cli/src/config/model.ts`, `cli/src/config/check.ts`, `docs/config.md` §5). Every behaviour is driven by a `gh` stub reached through `HARNESS_GH_CLI` in a throwaway fixture repository, as the existing `cli/test/remote-*.test.mjs` suites do. No case reaches the network.

**Mechanism decisions this plan takes** (the task prompt leaves each one open):

- **Where the pull request opens.** It opens at the top of the run's job, in a new `remote-run.sh open` verb that a new `harness-run.yml` step runs before `Run the harness`. It does not open in `start` or in the trigger: the trigger job reads no repository secret by design (`harness-trigger.yml` → `THE PERMISSIONS`: *"the credential secrets never reach the job that reads untrusted issue text"*), and `HARNESS_GIT_TOKEN` is the token the pull request must be opened with when set. The step runs only on a job whose `chain` input is `0`, meaning a job a person's action started. An automatic continuation never retries the create, so the attempts stay bounded. `deliver` reuses the open pull request. It still opens one, through the same function, only when none is open at completion: the start's attempt failed, or the adopter's pinned `harness-run.yml` predates the step. Its `completed` comment is then the one notification that names the error (lessons ledger, *Unattended control loops*, the bounded-retry rule).
- **Item 8's link.** The trigger's `launched` comment is posted before the run's job exists, so it cannot carry the pull request. When `open` creates the pull request, it posts one short comment on the source issue naming `#<pr>` and its URL, with the hidden marker and `event=opened`. A run with no source issue posts nothing.
- **Recognition before the ledger lands.** `forge_recognised` accepts a branch whose origin tip carries its task prompt (`<state_dir>/task_prompts/<branch>_task_prompt.md`) **or** its flow-progress ledger. The task prompt is committed state that `start` writes as the branch's first commit, so a pull request opened at start is a lifecycle target from its first minute. The pull-request body's `pull-request` marker was rejected as the test: anyone with write access can edit a body, and reading it costs a `gh` call. For `control_check_branch`, a branch is commandable from its first commit. Its refusal text then names neither a task prompt nor a ledger. The `started` clause keeps the deleted-branch refusal, and the in-flight clause keeps covering a run dispatched by hand on a branch with neither file.
- **Item 6's volume, source and opt-out.** The volume is **one progress comment per run or round, edited in place.** It is rendered from the flow-progress ledger in the job's own checkout, which carries every tick as it lands, because the autonomous forks push every commit. One function, `hr_ledger_phases`, maps the ledger's entry ids to the four phases. The watcher calls `remote-run.sh report progress` only when that mapping changes. The render is deterministic, so a chained job that finds the comment already current posts nothing, and no new state is kept. The comment carries the hidden marker with `event=progress` and a `round=<n>` field for a user-review round. The opt-out is the configuration key `execution.progressComments`, boolean, default `true`. `forge` is a string enum, so the task prompt's example `forge.progressComments` cannot exist. A user-review round has no end-of-branch review entries in its ledger (`plugin/instructions/autonomous_pause_and_ledger.md` → `### 1.3 Templates`). Its third line keeps the operator's label, *branch review*, and ticks when the round's closing checks, `R4` and `RG`, are through.
- **Item 13's wire.** The user-review fix plan records the collected inline-comment ids each finding came from, in a `**Review comments:** <id>[, <id>…]` line. That line goes in each per-finding file, and at the end of each `## Out of scope / verified-OK` bullet. Its shape is owned by `remote-run.sh`'s header (`deliver` paragraph), the reader, in the same way the round file's shape already is. The plugin's fix-plan writer conforms to it. A finding is *implemented* when the fix-plan index carries `[x] **Finding K**`. Its commit is the one that introduced that string, because the committer flips the entry in the fix's own commit.
- **The two proposals the prompt leaves to this plan.** The issue's Development panel (`createLinkedBranch`) is **dropped**. It would move `start`'s branch creation into a GraphQL call made from the secret-free trigger job, it rests on GitHub facts an unattended run cannot verify, and item 8's comment already gives the issue its link the moment the pull request opens. Option (c) of item 10, answering a park by a threaded reply, is **not taken** and stays the maintainer's proposal. `§3` is rewritten so that it no longer gives the two reasons the pull request at start removes. `§2`'s reason, that listening to `pull_request_review_comment` starts one job per inline comment, still holds.

**The schema property lands last, by the layer order.** Task 1 adds `execution.progressComments` to the model and the check, and Task 14 adds it to the schema and `docs/config.md` §5. Until Task 14 lands, no configuration carries the key and nothing reads it but the shell reader, which defaults it on. The half-built state is inert. Task 14 closes the four-place contract (`.claude/context/conventions.md` → `### The order files are created, so a half-built feature is still coherent`, shape 1).

Top risks: the widened recognition could send comments or labels to a pull request that is not a run's, so Task 3 bounds it to committed files only `start` and the flows write, and tests a branch carrying neither. The GitHub calls this branch adds for the first time, the draft flips, the thread reply and resolve, and the comment edit, could fail a step or fail silently, so Tasks 6–8 make every refusal one `::warning::` line with exit 0, Task 16 records each unmeasured fact as a `## 8.` row, and Task 19 adds the Gate 12 legs that measure them. The progress comment could duplicate or miss a phase across chained jobs, so Tasks 9 and 10 render from the whole ledger each time and upsert one comment per round, and their suites assert one create, then an edit, and no write when nothing changed.
