# Story: Remove the hand restore a forced self-adopt `init` needs in this repository

## Context

`chore_sandbox_manual_verification` regenerated this repository's own adoption with `HARNESS_SELF_ADOPT=1 node cli/dist/cli.js init --force --no-analyze` and then had to restore several files by hand (`docs/sandbox-verification.md` → the `sandbox1h` follow-up line; the sandbox issues record #5, #6 and #8). This branch takes four of those restores out of the loop and documents the ones that remain. A `--dry-run` of that same forced run, taken while writing this plan against the CLI built in this checkout, showed the current behaviour: `commands.typecheck -> bash scripts/typecheck.sh -> runs no command; the wrapper reports what to fix`, `commands.test -> bash scripts/test.sh -> npm test`, `would replace` on every state-dir README (each `backed up to README.md.bak`) and `~ would merge .gitignore (12 lines added: # The per-machine settings file the agent runner writes., …)`.

**What the branch changes, goal by goal.**

1. **Wrapper bodies (goal 1).** On a self-adopt run, a wrapper whose configured command is its own invocation (`bash scripts/typecheck.sh`, `bash scripts/test.sh` — this repository's `harness.config.json` holds both) keeps the command line the wrapper on disk already runs. The template body is still re-rendered around that line. The line is not replaced by detection (`npm test`) or by the `harness_fail` stub. **This is gated on self-adoption on purpose.** For every adopter, `--force` keeps its documented behaviour (`docs/cli.md` §5 and §2's `--preset` / `--app-dir` note: *"a kept run with `--force` re-renders the wrapper bodies from that detection"*). The task prompt scopes the goal to *"A forced self-adopt run"*, and the adopter-side contract is a different decision that this branch does not make. Task 1 owns the generator rule and Task 3 owns the wiring and the report.
2. **The recipe (goal 2).** `docs/development.md`'s self-adoption paragraphs (§5, Gate 2, after *"That refusal has one way through, and it is not a flag."*) gain the exact regeneration recipe for this repository, plus the list of what it still has to restore: `githooks/pre-push`'s `publish` refusal, `.claude/CLAUDE.md` and the three context documents, and whatever else the dry run reports as replaced outside `scripts/`. Task 7 owns it.
3. **Hidden `.bak` files (goal 3).** The goal is met in both of the ways it allows. A state-dir README whose bytes already match its template is kept even under `--force`, so no `.bak` is taken (Task 2). Four of the five contents-ignored READMEs here (`autonomous_logs`, `clarifications`, `autonomous_inbox`, `scratch`) differ from their templates today. For those, any `.bak` a forced run does take inside a contents-ignored state-dir directory is named in the run's notes, because `git status` never shows it (Task 3). The adopter-facing `.gitignore` template comment that says *"Every other .bak a forced run writes is left visible on purpose."* gains that exception as two appended lines (Task 5), and `docs/cli.md` §3's matching row follows (Task 7).
4. **`restart-watcher.sh` (goal 4).** `HARNESS_CLI` may be a command with arguments (`node <root>/cli/dist/cli.js`). The first word is what is checked on `PATH`, and the rest are leading arguments. Task 4 changes the template and Task 6 re-copies it into this repository's `scripts/`.

Task 6 also aligns this repository's managed `.gitignore` block with the current template (including Task 5's corrected comment), so the forced run's `merge-lines` adds nothing. That removes the duplicated comment line from the list of hand restores.

**Layering.** Tasks 1–5 are `cli`: `cli/src/generators/scripts.ts`, `cli/src/generators/stateDir.ts` with the header of `cli/src/core/writer.ts`, `cli/src/commands/init.ts`, `cli/templates/scripts/restart-watcher.sh`, `cli/templates/repo/gitignore` (one comment, append-only, so an adopter's `merge-lines` re-run adds it without a reworded twin), and one new suite each under `cli/test/` for Tasks 1–4. Tasks 6–7 are the catch-all `general` layer: this repository's own `init` output (`scripts/restart-watcher.sh`, `.gitignore`) and the developer documents under `docs/`. No task touches `plugin/`. Generators plan and never write (`.claude/context/cli.md` → `## How a module in this layer is written`). Reading the wrapper on disk at plan time is permitted, and every byte still goes through the write plan. `SELF_ADOPT_ENV` stays the single owner of the variable name (`.claude/context/conventions.md` → *"An environment-variable name is a constant with an owner too"*). The self-adopt behaviour is documented only in `docs/development.md` and never in `docs/cli.md`'s adopter tables, for the reason the constant's own doc comment gives.

**Top risks:** the likeliest failure is the carry-forward leaking into adopters' `--force` runs, which would silently change a documented re-run contract. Task 3 guards it with a perturbation pair: the same edited wrappers under `--force` in a harness-shaped fixture and in an ordinary fixture, both with `HARNESS_SELF_ADOPT=1`, with opposite outcomes; the option is passed only on a forced self-adopt run, and an unforced self-adopt arm guards that half. The second risk is a carried line that is not a command (an `unresolved` stub, an adopter edit the parser cannot read, a line that runs the wrapper itself) being written back as if it were one. Task 1 limits carrying to the `wrapperCommandLine` → `command` case and keeps the recursion assertion in force. The third is a recipe that describes a run nobody took. Task 7 derives its restore list from the output of a named dry-run command rather than from memory, and puts every command in its own fenced line.
