# Story: Team accounts research

## Context

This branch researches how a **team** uses the harness on GitHub with each member on their own Claude account and usage, and records the answer as one research document, `docs/team-accounts-research.md`, plus the links to it that the task prompt asks for. It changes no code, no workflow, no template and no configuration: every task's targets are prose under `docs/` and the root `README.md`, so every task is in the catch-all `general` layer (`harness.config.json` → `layers[]`, the row whose `path` is `"."`), whose rules are `.claude/context/conventions.md`.

**The web research is already done, and it lives in the per-task files.** An unattended run has no web access, so the planning session fetched every source on **2026-10-02** and carried each finding into the task that writes it up, verbatim, with its URL, page title, section heading and retrieval date, and with every inference and every silent source marked as such. An implementer writes the document from those files and fetches nothing. A claim that a task file does not carry, the document does not make. Where a source was not reachable, the task file says so, and the document says so too.

The document follows the shape of `docs/github-integration-research.md`: a reader statement, how it was researched, a summary, then one numbered section per subject. Each finding is an ID'd entry (`P` for Anthropic plans and terms, `R` for the API, cloud-provider and CI routes, `G` for GitHub, `O` for other agents) carrying a **Status** (`documented`, `partly documented` or `not documented`), an **Answer** stating only what the sources say, a separate **Inference** paragraph where there is one, and its **Evidence** bullets. The options, the recommendation and the open questions come last and cite findings by ID. The cut is five tasks, written in document order: Task 1 creates the file and writes §1 (Anthropic plans, Claude Code sign-in and the terms); Task 2 writes §2 (the API organisation, Bedrock and Vertex, workload identity federation and `anthropics/claude-code-action`); Task 3 writes §3 (GitHub's side) and §4 (what other agents do); Task 4 writes the summary, §5 (the options), §6 (the recommendation) and §7 (the open questions); Task 5 links the finished document from the `README.md` and `llms.txt` documents lists and with one sentence each from `docs/remote-execution.md` and `docs/github-run-control.md`.

The headline answer, which the maintainer asked to see as the document's summary table: a **subscription** credential — Pro, Max, or one Team or Enterprise seat — belongs to one person on every plan and must not be used by teammates' runs; Team gives each member their own seat with per-member limits, but does not make one seat's token shareable. An **API** credential — a Console key, or workload identity federation through a service account — may be used by the organisation's own authorised people, and its usage is billed to the organisation per workspace. The recommendation that follows from the findings, and which the maintainer approved for the plan: a team organisation on the Claude API with workload identity federation (option B) for any repository with more than one writer; the maintainer's own credential with an actor allow-list (option C) for a repository one person drives; per-member credentials selected by the triggering actor (option A) deferred, with what would have to become true for it.

**Top risks:** the first is a claim the evidence does not carry — a terms clause paraphrased beyond its words, an inference written as a documented fact, or a number (a price, a limit) not in the task file — so every task's verification re-reads each claim against its quoted evidence, and the Consumer Terms quotes keep the caveat that only the EEA/Switzerland version was retrievable. The second is the document drifting into a design: §5 describes what would change in `harness-run.yml`, `harness-control.yml`, `harness-trigger.yml`, `harness-resume.yml`, `remote-run.sh`'s `authorise_actor`, `doctor` and the docs, and changes none of them, and the task prompt puts any edit to them out of scope. The third is contradicting a statement already in `docs/remote-execution.md` or `docs/github-run-control.md` without saying so: where a finding bears on an existing statement, the research document names the statement and the finding; the two existing documents get at most one sentence each.
