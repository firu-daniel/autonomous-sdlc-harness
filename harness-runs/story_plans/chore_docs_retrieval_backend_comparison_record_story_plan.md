# Story: Correct the docs-retrieval backend comparison's record to what the BM25 diagnosis measured, with one fresh `fixture-catalog` parity reading

## Context

This branch corrects `docs/retrieval-eval-results.md` → `## The Python backend against the TypeScript one` and the one paragraph of `docs/retrieval-eval.md` that repeats its attribution. They now say what the BM25 diagnosis (`## The BM25 index's state, measured`) measured, and what the two fix branches (`fix_docs_retrieval_bm25_index_state_typescript`, `fix_docs_retrieval_bm25_index_state_python`) shipped. It also takes one fresh, deterministic TypeScript-against-Python reading on `fixture-catalog`, on both backends as they now ship, and tidies the diagnosis section's own prose. It changes no shipped code: `cli/src/`, `docs-retrieval-service/src/`, `evals/` and `evals/docs-retrieval/floor.json` are read and never edited. No abstention threshold, floor, `k` or fusion weight moves.

**What the planner checked before planning.** Neither fix branch corrected any passage this prompt names. The comparison section's **Finding — a defect, recorded and not acted on.** paragraph, `### Which case this is`, and items 3 and 4 of `### Divergence sources, in the order checked` still attribute the arm B divergence to "the Python index's history in its database". `docs/retrieval-eval.md` → step 3's paragraph still says the Python backend's lexical scores "depend on what that database held before". The record does not cite `timescale/pg_textsearch#573` anywhere. The fix branches did correct one passage nearby: `docs/retrieval.md` → **Incremental refresh.** already states the shipped `REINDEX` end state on both backends. This branch leaves it alone (`## Scope register`).

**How the work is cut.** Every task is in the catch-all `general` layer, because `docs/` belongs to it. Four of the five tasks edit `docs/retrieval-eval-results.md`. They run strictly in order, each owns only the passages its file names, and each later one `**Depends on:**` the one before it. Task 4 alone edits `docs/retrieval-eval.md`.

- **Task 1** takes the fresh reading and records it as a new subsection, `### A fresh fixture-catalog reading, both backends as shipped`. It sits after `### Abstention, query by query` and before `### Latency: the library call and the MCP round trip`. Every later task cites it by that exact heading.
- **Task 2** corrects the passages that say *why* the backends differ: `### Which case this is`, item 3, and item 4's **Arms D and E**. It also adds the comparison section's citation of `#573`.
- **Task 3** corrects the comparison section's remaining stale prose. That is the **Finding** paragraph, the section's lead and `### The trade-off, stated`, plus a note beside every wall-clock figure.
- **Task 4** corrects `docs/retrieval-eval.md` → step 3's paragraph.
- **Task 5** tidies the diagnosis section: its lead, the stray-score **The runs.** paragraph, and `#573` where mechanism 2 is named as the cause.

**Decisions this plan makes, stated once for every task:**

- **The 2026-10-08 figures stay exactly as recorded.** These are the four `eval:corpus:*@typescript` / `eval:corpus:*@python` blocks and every figure the comparison section copied from them. A correction changes the attribution and adds citations. It never changes a recorded value. They are the 2026-10-08 reading on `pg_textsearch` 1.3.1. No old → new delta is taken or written, because a re-taken figure would differ through the 1.5.1 upgrade, the fix on both backends, and (on `self-docs`) a corpus stamp that no longer matches, all at once.
- **The generated region is not touched.** No `eval:corpus:*` block is written, moved or regenerated, and `evals/docs-retrieval/floor.json` does not change. The fresh reading's two blocks go into a gitignored scratch file holding only the two generated-region markers. The comparison runs over that file, never over the committed document.
- **Cite, never restate.** Each corrected passage cites the diagnosis subsection that holds the figure. Where a figure is short and load-bearing, it may quote that figure with the subsection named beside it. The diagnosis's tables are not copied.
- **Mechanism vocabulary.** *Mechanism 1* is the dead rows a refresh leaves in the index's `total_docs` / `total_len`. *Mechanism 2* is the index scan scoring memtable rows with their exact length while segments use a quantized length. `### Whether either mechanism moves relevance` defines both in its opening paragraph. The comparison section uses these two names and points there.
- **The `#573` citation.** The form is `timescale/pg_textsearch#573`. Its provenance is stated once per section, in these words or close to them: *reported upstream as `timescale/pg_textsearch#573`, which the maintainer filed after this diagnosis and which is still open on 1.5.1, cited from the task prompt of `chore_docs_retrieval_backend_comparison_record` and not read on that branch*. Every other citation in the same section uses the bare `timescale/pg_textsearch#573`. Task 2 states the provenance in the comparison section, at item 3. Task 5 states it in the diagnosis section, in its lead.
- **No wall-clock figure is taken or recorded** (`harness-runs/lessons.md` → `## Evidence and measurement`, the wall-clock rule). The fresh reading's latency columns are not read and not written. The existing wall-clock figures stay as recorded, each with a note that it was taken on 1.3.1 before the fixes.
- **Captures are evidence for the implementer, never for the record.** Scratch files go under `harness-runs/scratch/backend-parity/`, which is gitignored. The document carries the figures, the commands, the launcher bodies and the setup, and never a pointer to a scratch file as evidence (`harness-runs/scratch/README.md`, last paragraph). Do not write a summary or report file with the Write tool. A measurement summary goes in the implementer's return, because a subagent's report-file write was refused on `fix_docs_retrieval_bm25_index_state_python` Task 5.
- **What is unexplained stays named as unexplained.** No correction claims that only quantization separates the backends unless the fresh reading's arm B agrees on every query.

**Top risks:** The likeliest failure is a fresh reading that leaks into the record the wrong way. Its blocks could land in the committed generated region, its latencies could be written, or its figures could be set value for value against the 2026-10-08 blocks. Task 1 guards this with a markers-only scratch `--out` file, a comparison launcher that reads only that file, latency columns dropped, and a `git diff` check that every hunk sits outside the generated region. The second risk is a correction that overclaims: for example, that the backends now differ only through quantization when arm B still disagrees, or that the 2026-10-08 near-tie swaps were measured on the fresh build. Task 2 makes every claim about the fresh reading conditional on what Task 1's subsection records, and keeps any remaining difference listed as unexplained. The third risk is blurring `#573`'s provenance, which would make false the diagnosis lead's statement that its issue numbers are task-prompt leads not re-read. Task 5 states `#573`'s provenance separately, in the lead and in the recommendation's matching bullet, and Task 2 does the same once in the comparison section.

**Manual setup required** (before `/autonomous-sdlc-harness:branch-implement-plan`). Task 1 needs all three. It checks each and stops with a `blocker:` naming the missing one. It never provisions one, because each reaches the network or the Docker daemon:

- The Python weight cache present under `${XDG_CACHE_HOME:-$HOME/.cache}/harness-docs-retrieval/models`. If it is absent, run `bash scripts/python-service.sh run fetch-models` from the repository root.
- This checkout's Python environment synced with the `models` extra: `bash scripts/python-service.sh sync --with-models`, from the repository root.
