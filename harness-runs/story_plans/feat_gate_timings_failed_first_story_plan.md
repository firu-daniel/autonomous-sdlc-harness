# Story: Gate timings, previously failing first, and no re-run of a finished round

## Context

A Run gates round of this repository takes 30 to 40 minutes inside the sandbox, and most of a run's gate time goes into the full re-runs of its fix rounds. This branch makes three changes. **Every round records how long each gate and each test file took**, beside the round's log, and prints the ten slowest files in the log. **Every round after the first runs first only the gates and test files the previous round saw fail.** If any of them still fails, the round stops there and returns `fail <log>`. If they all pass, the rest of the gates and the whole suite run as they do today. **A resumed session no longer re-runs a round whose gates already finished on the same commit.** It collects that round's verdict instead. The first two changes are this repository's own (`scripts/run-gates.sh`, which `commands.test` names). The third lives in the shipped `run-test-suite.sh`, so every adopter gets it.

**Decisions this plan takes. Every task restates the ones it needs, so no implementer has to re-decide them.**

- **`pass` only ever comes from a round that ran every gate and the whole suite.** A round that stops early can only answer `fail`. A reused verdict is the verdict of a full run on the same commit with nothing changed since, and the run form hands it back unchanged.
- **The seam between the generic wrapper and this repository's gates is two environment variables.** `run-test-suite.sh` (Task 1) exports `RUN_TEST_SUITE_LABEL=<label>` and `RUN_TEST_SUITE_LOG_DIR=<state_dir>/test_run_logs/<sanitized branch>` into both gate commands. The directory is repo-relative, exactly as the wrapper computes its `log_dir`. The wrapper reads nothing a gate writes there. `scripts/run-gates.sh` (Task 9, through the library of Task 8) reads the two values to place its records and to find the previous round. It validates them against the lane constants the run library already owns — `HR_TEST_RUN_LABEL_PATTERN` and `HR_TEST_RUN_LOG_SUBDIR`, in `scripts/lib/harness-run-lib.sh`'s `THE RUN GATES LANE:` block — and retypes neither: `gate-round-lib.sh` defines no label pattern and no lane-directory name, its sourcing script (`run-gates.sh`, and Task 11's driver) sources the run library first, and with either constant unset the round writes no record rather than guess. A gate command run by hand gets neither. It then writes no record, runs no focused phase, and still prints its gate durations and the slowest-files section from a temporary record.
- **The records, all under `<state_dir>/test_run_logs/<sanitized branch>/` and nowhere else.** Every path inside them is relative, never absolute, so gate 6 passes over them. Gate 6a already skips `test_run_logs` by name (`scripts/check-machine-paths.sh` → `THE EXCLUDED DIRECTORIES`).
  - `<label>.commit` is generic and written by `run-test-suite.sh`: one line, the commit id the worker ran against. It is written only under the condition in the reuse bullet below.
  - `<label>.gates.tsv` is written by `run-gates.sh`. Its first line is `phase	gate	status	seconds`. One row follows per gate unit run, where `phase` is `focused` or `full`, `gate` is a unit id, `status` is `ok`, `FAIL`, `BLOCKED` or `SKIPPED`, and `seconds` is a whole number. The last line is `end	complete` or `end	stopped`.
  - `<label>.focused.tests.tsv` and `<label>.full.tests.tsv` are written by the per-file reporter (Task 7) for each gate-4 run of that phase. The first line is `file	status	seconds	tests	failed`. One row follows per test file, sorted by `seconds` descending, where `file` is relative to the runner's working directory (`test/<name>.test.mjs` for this repository's suite), `status` is `pass` or `fail`, `seconds` carries one decimal and is the sum of the file's top-level test durations, `tests` counts those top-level tests, and `failed` counts the failed ones. The last line is `end`. The record keeps every file. Only the log's section is cut to ten (the lessons ledger: *"truncation belongs to a display, never to the record"*).
  - A record with no `end` line, a malformed row, an unknown gate id or an unusable file path is **unreadable**. A round whose previous record is unreadable runs as today.
- **The gate units and the gate line format.** `run-gates.sh` runs its checks as units with these ids, in this order: `1`, `2a`, `2b`, `2c`, `2d`, `2e`, `3a`–`3f`, `4`, `6a`–`6f`, `11`, `13a`–`13d`, `14a`–`14d`, `16`. Unit `1` is gate 1 whole: `1a` and `1b`, or the BLOCKED line when `claude` is absent. Every printed gate line ends with the check's duration:
  - `  ok    <name> (<n> s)`
  - `  FAIL  <name> (<detail>, <n> s)`, where `<detail>` is today's parenthetical, for example `exit 1`
  - `  BLOCKED <name> — <reason> (<n> s)`
  - `  SKIPPED <name> — <reason> (<n> s)`

  The `  FAIL  ` prefix is unchanged, so `scripts/lib/sandbox-probe/legs-local.sh` → `sp__gate_log_failures`, which matches on it, keeps working.
- **Which round is "previous", and what runs first.** The previous round is the newest `*.gates.tsv` in the lane other than this label's own. "Newest" is by modification time, so the latest earlier round of any `<gate_key>` counts. The record's last phase decides what ran: its `full` rows if it has any, else its `focused` rows. Its `FAIL` units run first. Unit `4` runs as `npm run test --workspace cli -- <reporter flags> <files>` over that phase's `fail` files that still exist. A dependant brings its prerequisite with it: any of `2b`–`2e`, `11`, `13c`, `14a`–`14d` brings `2a`. If one of the focused units fails, the round prints the stop line, ends its record `end	stopped` and exits 1. Otherwise the full phase runs every unit whose focused row is not `ok`, plus unit `4` over the whole suite. The plain lines the round prints, byte-exact:
  - `run-gates: running first what failed in <prev label>: gates <ids>; test files <files or none>`
  - `run-gates: stopped early: ran only gates <ids> and test files <files or none>, which failed in <prev label>; every other gate and test file did not run, so this round cannot pass`
  - `run-gates: everything that failed in <prev label> passed; running every other gate and the whole suite`

  Lists are joined with `, `. All three lines sit inside the log's `gate test` section, so the failures stay under the same `run-test-suite.sh` marker lines as today. The marker lines do not change.
- **Gate 4's command pins the stdout reporter.** Gate 4 becomes `npm run test --workspace cli -- --test-reporter=tap --test-reporter-destination=stdout --test-reporter=<repo_root>/scripts/lib/test-timing-reporter.mjs --test-reporter-destination=<record>`. `tap` is pinned because naming any reporter replaces the default one, and `run-gates.sh`'s `not ok` diagnostic printer reads TAP. TAP is also what Node 20 and 22 print by default to a non-terminal, so today's log content is kept.
- **What "nothing the gates read has changed" means.** HEAD is the commit `<label>.commit` names. And `git --no-optional-locks status --porcelain --untracked-files=all -- . ':(exclude)<state_dir>'` printed nothing at three points: when the worker started, when it finished, and at reuse time. Ignored files are never listed, so build outputs and dependency trees do not count. `<state_dir>` is left out because the session writes run artifacts there (the flow-progress ledger, dispatch additions, pause notes, this lane itself) during and between rounds, and the gates do not test them. **One residual, stated generically in the wrapper's header (which names no gate of this repository, since every adopter receives it):** in this self-adopted repository, gate 6a and 6b do scan `<state_dir>`'s committable files, so a state-directory change made after the run is not scanned by a reused verdict. A failing git call, or a `<state_dir>` that resolves to the repository root, means no `.commit` is written and nothing is reused. That way the fault falls on the side of running again. A session can write `<label>.commit` as easily as it can write `<label>.verdict` today, so reuse adds no trust surface. **Reuse covers both execution forms:** the run form, which macOS and remote jobs use, and the `--no-detach` form the Linux launcher runs under `bwrap`. The no-detach form rewrites the verdict in place on reuse, so the launcher's `started()` test (verdict mtime at or after its call) answers `pending`. The lessons ledger requires this: *"A recovery … covers every execution mode the failure reaches."*
- **A generic focused-run mechanism for adopters.** One example is an optional configuration key naming a command that runs a list of test files. The generic `run-test-suite.sh` cannot know an adopter's test files, so this branch does not build one. **Recommendation to the maintainer, not pending work:** it is worth a later branch only once this repository's own per-file records, gathered over a number of real fix rounds, show that failed-first saves enough to justify a new configuration key, its schema, check, documentation and a consumer. The environment seam above already lets an adopter's own `commands.test` script do what `run-gates.sh` does, with no new key.
- **Out of scope.** `cli/test/watcher-stall-reset-payloads.test.mjs`, the file that sets the floor in the task prompt's measurement, is not made faster here. No document of record gains a wall-clock figure from this branch. The task prompt's measurement was taken inside a headless session, which the lessons ledger bars from documents of record.
- **Ship order.** The configured layer order is `cli`, `plugin`, then the catch-all `general` last. The wrapper's change and its tests (cli), the flow text (plugin) and the root copies (general) follow it. The scripts under the root `scripts/` belong to `general`, and their suites live in `cli/test/`. Each suite therefore ships after the script it exercises (Tasks 10 and 11 after Tasks 7–9), on the contract-before-consumer rule. The closing documentation task is last.

**Top risks:** The first is that the restructured `scripts/run-gates.sh` silently drops a gate or changes how one is graded. This branch's own Run gates phase runs the new script, and every later branch depends on it. Task 9 keeps every gate name and grading arm of the old script, checked against the pre-change file. Task 11 pins the round driver that decides what runs. The second is a reused verdict that is wrong because something the gates read did change. Task 1 writes `.commit` only for a clean tree at the worker's start and finish, and Task 2 pins that a moved HEAD, a dirty tree and a dirty finish each force a fresh run. The third is a fix-plan writer that reads a stopped round's short log as "the other failures are fixed". Task 4 tells `test-fix-plan-writer` that a round which says it ran only part of the suite is evidence about that part alone.
