# Story: Start the Run gates worker inside an unattended macOS sandbox again

## Context

Since Claude Code 2.1.323, every local autonomous run on macOS parks at Phase G round 1. `launch-sandboxed-gates.sh` answers `in-session` there, as it should, and the run form `bash scripts/run-test-suite.sh task_round_1` then exits 2 with `run-test-suite.sh: the detached run of task_round_1 did not start`. No `.running`, `.verdict`, `.commit` or log was written. The same run form, issued outside the sandbox in the same run copy, started its worker within a second. This branch does three things. It finds the cause with a probe and records it in `docs/`. It makes the gates run inside the session's sandbox again. And it makes a worker that dies before claiming `.running` leave its reason in the lane directory, because a silent failure is what cost two parks.

**What the code shows, and the leading hypothesis (not yet measured).** The run form and its worker are the same script, `cli/templates/scripts/run-test-suite.sh`. Up to the detach they run the same code: library sourcing, root placement, `stateDir`, branch and lane resolution. The run form got through all of it, because it reached its own start-up refusal. So the worker died between the run form's launch line and its own `printf '%s\n' "$$" > "$running_file"`. That launch line is `RUN_TEST_SUITE_WORKER="$label" nohup bash … </dev/null >/dev/null 2>&1 &`. Its stderr goes to `/dev/null`, so `nohup`'s own message and the worker's own message are both lost. On macOS, `/usr/bin/nohup` detaches from the console through launchd before it execs its command, and fails with `can't detach from console` when that call is refused. That would explain why nothing started, and why the same line worked outside the sandbox and on 2.1.319 (`docs/sandbox-verification.md` → row BG2). **This hypothesis is unverified, and no task may act on it before the probe confirms it.** The task prompt's three changelog candidates are weighed the same way. The probe records the `TMPDIR` path and its canonical form for the symlink candidate. The process-visibility candidate does not reach the start-up path, because the run form signals no process before the worker claims `.running`. The permission-flow candidate cannot refuse a process a permitted command starts, and the run form's own call ran.

**The probe runs in the session, not by hand.** An implementer of this branch's unattended run is itself a session launched with the per-run copy of `.claude/settings.autonomous.json`, on the Claude Code version now in use. A probe issued from that session through the script-allowlist guard is therefore the measurement the prompt asks for, and it needs no launch the session cannot make. Task 1 writes it as a hand-written root script, `scripts/gate-worker-start-probe.sh`. It is not part of `init`'s set, like `scripts/sandbox-probe.sh`. It lays a throwaway fixture under the state directory's `scratch/`, measures seven legs, prints every reading whole, and removes only what it created. A person can re-take it from a terminal, which gives the unsandboxed control. The legs include two controls that remove one candidate at a time, as the lessons ledger requires before an effect is attributed. One is `nohup true` run in the call, not detached, beside `( trap '' HUP; exec true )`. The other is a detached `nohup` arm beside a detached `trap '' HUP` arm. Every write is graded on what reached the disk.

**The fix is gated on the probe.** Task 2 first runs the probe. It replaces the launch line only when the probe shows the sandboxed session's detached `nohup` arm not starting while the `trap '' HUP` arm starts, and the old launch line failing. The replacement is `( trap '' HUP; export RUN_TEST_SUITE_WORKER="$label"; exec bash … ) </dev/null >/dev/null 2>>"$start_file" &`. The worker enters with HUP ignored, which is what `nohup` left it with, so the header's measured `SIGNALS` row for HUP still holds. `$!` stays the worker's own PID, because `exec` keeps the subshell's PID. On any other reading, Task 2 returns a blocker that quotes the probe's summary lines rather than guessing a second cause, and the run parks with that evidence. The worker stays inside the session's sandbox. No profile entry is added, and `sandbox.excludedCommands` is not touched. Every caller-matched wire string stays byte-identical: `pending`, `in-session`, `the detached run of <label> did not start`, and exit codes 0–4.

**The diagnostic file, `<label>.start`, is one contract across four tasks.** Task 2 defines it. Task 3 tests it and documents it in the adopter-facing lane README. Task 5 copies it into this checkout. Task 6 records it. Here is the contract. When it does not reuse a verdict, the run form removes a stale `<label>.start` along with `.verdict` and `.commit`, creates it empty, and launches the worker with its stderr appended there. The worker removes the file as soon as it has written `.running`, then sends its own stderr to `/dev/null`, as today. If the start-up window closes with neither `.running` nor `.verdict`, the run form appends one marker line, `== run-test-suite.sh: worker <pid> of <label> neither claimed .running nor wrote .verdict within <N>s ==`, and then refuses with its unchanged stderr line. A started run therefore leaves no `.start`. A worker that died before claiming leaves its own message, followed by that marker. The `--no-detach` form detaches nothing and also removes a stale `.start`.

**Execution modes.** The change is in the run form itself, so every mode that issues the run form gets it: the local watcher on macOS, and any host where the launcher answers `in-session`. A job on a GitHub-hosted runner is a bubblewrap host. There the launcher answers `pending` and runs `--no-detach` under its own `bwrap`, which detaches nothing, so the failure does not reach it. The launcher's own `nohup` runs unsandboxed and only on Linux, and is left as it is.

**Ship order.** The order follows dependency and does not re-sort by layer. The probe (`general`) comes first, because the fix's gate runs it. The three `cli` tasks follow: the template fix, its suite and lane README, and the probe's own test. The `general` copy into this checkout and the record come last.

**Top risks:** The likeliest failure is a fix built on an unconfirmed cause. Task 2 guards it by running the probe before any edit, applying the replacement only on the reading above, and otherwise returning a blocker that quotes the readings. Second, this branch's own Phase G issues the run copy's `scripts/run-test-suite.sh`, not the template. A copy that is not byte-identical would park this branch exactly as the bug did. Task 5 makes the copy and verifies it with `cmp`. Phase G of this branch is then the real-shape end-to-end check the fixture probe cannot be. Third, a probe that writes outside its own fixture, or leaves one behind, would pollute the run copy or a test host. Task 1 removes only what it created, on every exit path. Task 4 runs it against a temp work base with `HOME` and `TMPDIR` redirected, and checks the work base afterwards.
