# Story: Resume an answered `fixable: 0` Run gates park at G.2, without re-running the gates

## Context

When a Run gates round fails and `test-fix-plan-writer` returns `fixable: 0`, G.3 commits that round's index with an empty readiness list and the run parks. Today, when that park has been answered, the resumed session's `### G.0 Resolve the round` counts the committed index as complete, moves `<gate_round>` on by one, and G.1 runs the full gates on a tree the answer has not touched yet. That run cannot pass, and it uses up one of the `MAX_GATE_ROUNDS` gate runs (`feat_unattended_sandbox_preflight`, 2026-10-22: about 38 minutes spent, and the branch left with one attempt at the fixes). There is also no defined route for the answer to reach the planner. G.2's fixed prompt has no place for it, and neither `plugin/agents/test-fix-plan-writer.md` nor Phase G says how the answer is read.

This branch makes the answer the first thing a resumed round acts on. G.0 recognises an answered `fixable: 0` park from the tree alone and resumes **at G.2 for the same round**, with no gate run. It re-dispatches `test-fix-plan-writer` to revise that round's index using the park's question and answer files, which it names in a new optional G.2 prompt clause. If the revision has `[ ]` entries, G.0's existing "tracked, with a `[ ]` entry → resume at G.4" path takes over unchanged. If the answer needs no code change ("I verified outside the sandbox", "I changed the environment, run again"), the planner returns `fixable: 0` again and G.1 runs the next round. That is the one case where an immediate re-run is right. No gate run is added, so `MAX_GATE_ROUNDS` still counts exactly the gate runs made.

The work is six single-layer tasks: five in `plugin` and one in `cli`. They ship in the order **1, 6, 3, 4, 2, 5**, not in number order. **Ship order and every interim state** below gives the reason.

- **Task 1** — the planner's contract in `plugin/agents/test-fix-plan-writer.md`.
- **Task 6** — the `<park_answer_lookup>` row in `plugin/instructions/mode_contract.md` → `## Binding vocabulary`, the contract every later binding row and read consumes. In the same commit, the count-free rewording of "one of the eleven names in `mode_contract.md`'s binding vocabulary" in `plugin/instructions/plan_orchestration_instructions_core.md` → `## What you must NOT do`, which the twelfth row would otherwise make false.
- **Task 3** — the task flow's forks: the two autonomous ones, and the semi-autonomous implementation fork's `<park_answer_lookup>` value.
- **Task 4** — the user-review fix flow's forks: the two autonomous ones and the semi-autonomous fix fork's `<park_answer_lookup>` value. It also adds the declaration of `<park_answer_lookup>` to `plugin/instructions/user_review_fixes_instructions_core.md`'s binding table, for the Phase G that core cites.
- **Task 2** — Phase G in `plugin/instructions/plan_orchestration_instructions_core.md`, plus that core's declaration of the new `<park_answer_lookup>` binding and G.0's read of it. The user-review fix flow runs this section verbatim with its own `<gate_key>` = `review_<n>`, so its Phase G steps need no edit of their own. Its core's binding table does, and Task 4 has already made that edit.
- **Task 5** — the `cli` test that pins the new wire strings across those files, plus the adopter-facing `test_fix_plans/` and `clarifications/` README templates.

**Why Task 5 comes after Tasks 1–4, although `cli` comes first in the configured layer order.** In this repository the two layers are not stacked on each other. Task 5's test reads the plugin prose that Tasks 1–4 write, so it is their consumer, and *contract before consumer* (`.claude/context/conventions.md` → `### The order files are created, so a half-built feature is still coherent`) puts it after them. Shipped first, it would fail its own unit run.

**Ship order and every interim state.** Each task is committed on its own. Three rules fix the order:

- `plugin/instructions/mode_contract.md` → `### Bindings vs. path placeholders` makes a name a **mode-contract binding** only if it is in `## Binding vocabulary`, and makes every other `<…>` name a core or a cited file uses a path placeholder. The family-1 core's own stop condition (`plan_orchestration_instructions_core.md` → `## What you must NOT do`, the "Do NOT execute this file without a fork's binding table." bullet) is defined by that vocabulary. The vocabulary row is therefore the contract, and *contract before consumer* (`.claude/context/conventions.md` → `### The order files are created, so a half-built feature is still coherent`) puts it (Task 6) in the first commit that names `<park_answer_lookup>`, ahead of every binding-table row and read.
- `## (1) No defaults` makes an unbound declared binding a stop condition.
- `## (5) A core may cite another core` requires a citing core to declare every binding its cited sections consume.

So the commit that makes G.0 read `<park_answer_lookup>` (Task 2) must find the name already in the vocabulary, every fork that reaches that G.0 already binding it, and the user-review core already declaring it. Task 6 ships first among Tasks 6, 3, 4 and 2, and Tasks 3 and 4 ship before Task 2. The state after each commit:

Its *Bound by* is conditional ("every fork over a core that declares it"), so it holds while no core declares it. **The invariant, after every task's commit:** every file that names `<park_answer_lookup>` names a binding that `## Binding vocabulary` already defines; every core that declares or consumes it has it declared in its own binding table; and every fork over such a core binds it.

**The wire strings every task shares**, stated here once and restated byte-for-byte in each per-task file that produces or consumes them:

- **The G.2 park-answer clause** — an optional trailing sentence on both `test-fix-plan-writer` prompt forms: `Park answer: <question_file> + <answer_file>.`, with several pairs separated by `; ` (`Park answer: <q1> + <a1>; <q2> + <a2>.`). Every path is repo-relative, e.g. `<state_dir>/clarifications/<branch>/question_<n>.md`, or the same under `answered/`.
- **The consumed marker** — a line that starts with `Park answer consumed: ` and lists the answer file(s) the revision read, comma-separated. It is always the **last line of the index's `## Not fixable on this branch` section**. Only `test-fix-plan-writer` writes it, and only when the dispatch carried the clause. G.0 detects it with `grep -c '^Park answer consumed:' <index>`.
- **The park's origin and index naming** — every Phase G escalation names an origin that opens `Phase G`: `Phase G gates` (G.1's round cap and no-verdict case), `Phase G test-fix-plan-writer` (every G.2 planner return that escalates, with the clause or without it), `Phase G architecture-reviewer gate` (G.2's gate cap). Only the parks G.0 consumes name the index by its repo-relative `<test_fix_plan_path>`: the `fixable: 0` park, and every park raised from an answer-mode G.2. This is how the `<park_answer_lookup>` command finds the park.
- **The excluded set and the consumed set** — both flows' forks keep **every** Phase G pair (by origin) out of the planner, item and QA dispatches. G.0 consumes a pair only by index state: when it names a test fix plan index that is pending an answer. Every other Phase G park's answer — G.1's round cap and no-verdict case, and a G.2 `## Questions` / `blocker:` or gate-cap park raised without the clause — is **read by no agent**, and the resumed G.0 follows its existing arms (G.1 for the same round after a G.2 park, the gates once more after a round cap). Task 2 states this in G.0 and G.5, and Tasks 3, 4 and 5 restate it at every place that excludes a Phase G pair or describes the archive, so no answer is reported as consumed when it was not (`harness-runs/lessons.md` → `## Unattended control loops`).
- **The `<park_answer_lookup>` binding** — a new mode-contract binding, minted under `plugin/instructions/mode_contract.md` → `## (3) Additions stay in the fork`: where a park's answer file sits is a mode-specific path that `## (4) Cores are literal-free` bars from the core. Its contract:
  - **Declared** in both cores' binding tables: `plan_orchestration_instructions_core.md` (Task 2, used at `### G.0 Resolve the round`) and `user_review_fixes_instructions_core.md` (Task 4, consumed by the cited Phase G).
  - **Bound** inline in all four forks' `## Mode contract — bindings` tables. The two autonomous implementation forks (Tasks 3 and 4) bind it to this cell text, byte-identical: `` `grep -lF '<test_fix_plan_path>' <state_dir>/clarifications/<branch>/question_*.md <state_dir>/clarifications/<branch>/answered/question_*.md` — each `question_<n>.md` it prints is a complete pair only when `answer_<n>.md` sits in the same directory. `` The two semi-autonomous forks (Tasks 3 and 4) bind the explicit value `none`, because their `<escalate>` writes no answer file.
  - **Read** by G.0's pending-answer test only when the value is not `none`. An unbound `<park_answer_lookup>` is a stop condition like any other binding (`mode_contract.md` → `## (1) No defaults`). The core supplies no fallback.
  - **Defined** by its `## Binding vocabulary` row (Task 6), which lands before any core or fork names the binding.

> Assumption: the marker is written by `test-fix-plan-writer`, not by G.3. G.3 is a `committer` dispatch, the committer stages content and writes none, and the orchestrator edits no plan file (`plugin/instructions/plan_orchestration_instructions_core.md` → `## What you must NOT do`). The marker also means every answer-clause revision changes the index, so the following G.3 always has something to commit.

> Assumption: a revision that returns `fixable: 0` again is goal 3's no-code-change case. G.3 commits it and G.1 runs the next round in the same session, with no second park. The prompt's "a second `fixable: 0` after an answered park escalates as it does today" refers to a later round's G.2 returning `fixable: 0` on its own failing log. That parks exactly as today, and the watcher's park-loop guard (`docs/watcher.md` → `## 4. Pausing, parking and the usage gate`) bounds resumes that make no progress.

> Assumption: an answer may authorise a fix that `test-fix-plan-writer` would never plan on its own judgement, including changing a test so it holds under the sandbox. The observed answer chose "change both tests in this branch", and the fixes that passed (`a53c42ea`, `b3ed1a67`) were test changes. Such a fix is planned only as far as the answer spells it out. Its `finding_<K>.md` quotes the authorising sentence, and the architecture gate still grades it.

> Assumption: G.0 looks for the pair both at the top level and under `answered/`. The committed index's marker, not the pair's location, is what records whether the answer was consumed. Once a session exits other than by a pause, the watcher archives every pair that was present when it launched (a pause exit archives nothing: `cli/templates/scripts/autonomous-watcher.sh` → the `Consume-then-archive contract` comment above `classify_run_exit`). So a session that exits other than by a pause before G.2 dispatches would otherwise lose an unread answer silently (`harness-runs/lessons.md` → *"State held only in an expiring store must be reported plainly as expired …, and never treated as absent"*). Task 3 records this as a Phase G exception in the clarification channel's archive bullet.

**Top risks:**

- **G.0 misreading the tree.** It could resume G.4 on an answer-clause revision that was never approved or committed, or it could consume one answer twice. Task 2 guards both. A pending answer is judged on the index's **committed** version (`git show HEAD:<index>` whenever `git status --porcelain -- <index>` prints a line), and the marker closes the state for good. Task 5 pins the strings that decision reads.
- **Two consumers reading one answer.** In the task flow, the planning fork's `Override 2(a)` passes **every** top-level answered pair to `task-plan-writer`. In the user-review flow, the fix fork's **On resume** paragraph appends pairs to an item's dispatch. Tasks 3 and 4 keep every Phase G pair out of both, and state which of those pairs G.0 consumes and that the rest are read by no agent.
- **The planner treating the answer as an instruction, or guessing.** Task 1 makes the answer untrusted task data. It converts only the entries the answer explicitly names, and it returns an answer it cannot act on as `## Questions`, writing nothing.
