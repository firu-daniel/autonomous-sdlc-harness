# Story: Docs-catalog retrieval, opt-in and local

## Context

This branch builds the retrieval half of the `ROADMAP.md` row *Docs-catalog retrieval*. It adds a local, read-only search tool over the "second brain": every Markdown file under `docs.root`, plus the conventions documents `layers[]` names. The CLI serves the tool over stdio MCP as `search_docs`, and ten plan-writer and reviewer agents may call it. It ships off by default behind a new boolean key, `docs.retrieval`, which is legal only when `phases.docs` is `true`. The relevance eval that decides whether retrieval beats index-first navigation is the follow-up branch `feat_docs_retrieval_eval`, not this one.

The work runs bottom-up in the configured layer order, `cli`, then `plugin`, then `general`:

- **The key** (Task 1). `docs.retrieval` in `cli/src/config/model.ts`, with the one predicate every consumer reads, `retrievalApplies(config)`, and the cross-field error in `cli/src/config/check.ts`.
- **The engine** (Tasks 2–8), a new area `cli/src/retrieval/`. The optional-dependency loader and the machine cache paths come first (Task 2). Then the embedder and reranker interfaces with their deterministic stubs (Task 3), the chunker and corpus (Task 4), the store and incremental refresh (Task 5), the `docs index` verb and its fixture suite (Task 6), hybrid search with abstention (Task 7), and the stdio MCP server (Task 8).
- **The adopter surface** (Tasks 9–14). The repository-side launcher script (Task 9). The `.mcp.json` server, the permission-profile fragment and the ignore rule (Task 10). The `init` flag and prompt (Task 11). The runtime install and model download at setup time (Task 12). The three `doctor` checks (Task 13). The package README (Task 14).
- **The agents** (Tasks 15–17). The tool goes into ten `tools:` allowlists and ten contract bullets, and the grant is recorded in one roster. The launcher joins the script-allowlist guard's documented left-allowed set (Task 17).
- **The schema and the documents of record** (Tasks 18–25). The schema clause and its negative fixture, `docs/config.md`, `docs/cli.md`, a new `docs/retrieval.md`, a hand-run Gate 10, the README, `llms.txt`, `ARCHITECTURE.md`'s verb count, the roadmap row, the launcher's row in `docs/watcher.md` §2 (Task 24), and the restatement of `ARCHITECTURE.md`'s MCP position in §6, §7 and §10, which this branch makes false (Task 25).

**Settled while planning, so no task has to settle it again.**

- **The user's answers override the task prompt in three places** (`harness-runs/clarifications/feat_docs_catalog_retrieval/answered/answer_1.md` to `answered/answer_3.md`):
  - **`init` registers the server**, not the plugin. It writes the server into the adopter's `.mcp.json` only when retrieval is on, the way it already writes the Playwright servers. The plugin carries only the agents' contract text and allowlist grants.
  - **Every granted agent's `tools:` allowlist always names the tool.** Its contract text says to ignore the tool when retrieval is off. "With retrieval off, neither does" in Acceptance 5 applies to the generated permission profile only.
  - **The granted set is exactly ten agents:** `architecture-reviewer`, `branch-reviewer`, `business-parity-reviewer`, `review-plan-reviewer`, `skeptic-reviewer`, `task-plan-writer`, `task-plan-reviewer`, `ui-tests-plan-reviewer`, `ui-tests-plan-writer`, `user-review-fix-plan-writer`. It replaces the prompt's grep-derived set. `layer-reviewer`, the implementers, the committer, `qa-tester` and `docs-writer` do not get the tool.
- **How the existing Playwright servers start without a prompt in an unattended run.** `cli/templates/claude/settings.autonomous.qa.json` carries `"enabledMcpjsonServers": ["playwright", "chrome-devtools"]` plus one `mcp__<server>__<tool>` entry per tool under `permissions.allow`. `cli/src/generators/permissionProfile.ts` → `renderProfile` merges that fragment through `mergeInto` only when `browserWiringApplies(config)` holds. `cli/src/generators/repoRoot.ts` → `assertServersMatchProfile` checks it against `cli/templates/repo/mcp.json` in both directions. Retrieval does the same thing with its own fragment, its own template and its own predicate, `retrievalApplies`. The server is **`harness-docs`**, the tool is **`search_docs`**, and the fully qualified name in a `tools:` allowlist and in a permission rule is **`mcp__harness-docs__search_docs`**. That spelling follows the QA fragment's `mcp__playwright__browser_navigate` and `plugin/agents/qa-tester.md`'s allowlist.
- **`npx` does not resolve peers installed in the adopting project.** This was measured while planning on macOS with Node v20.19.5. A package directory outside the project imported a bare specifier installed only in the project's `node_modules`. Run from the project directory, `node ../cache/node_modules/tool/cli.mjs` printed `not resolved: ERR_MODULE_NOT_FOUND`. Node resolves a bare `import()` from the importing file's location, and `npx` runs the CLI out of its own cache. **Decision:** `init` installs the peers *and* the CLI itself, at its own version, into a machine-shared runtime directory, `<machineCacheDir>/retrieval/runtime`. `machineCacheDir()` is `${XDG_CACHE_HOME:-$HOME/.cache}/autonomous-sdlc-harness`. **The runtime directory is the only thing the `.mcp.json` launcher runs** (Task 9 has no fallback), so it is also the only thing `init`'s setup skips the install on (Task 12) and the only thing `doctor`'s `retrieval-dependencies` check passes on (Task 13): all three key on `retrievalRuntimeState().installed`, whose first file test is the launcher's own entry file. An adopter whose own CLI could already load its peers, including this self-adopted repository, still gets the runtime installed, because that is what the server starts from. `retrievalCliEntry()` (this installation when its peers resolve, otherwise the runtime) survives only as the entry of the two short-lived child processes that do not serve: `doctor`'s in-memory index probe and setup's `docs fetch-models`, both of which read the shared model cache and so behave the same from either entry. Retrieval verbs run directly (`docs index`, `docs search`, in tests and by contributors) load their peers from the process they run in. No module resolves a peer against a second base. Model weights live in the sibling `<machineCacheDir>/retrieval/models`, shared by every worktree.
- **The committed `.mcp.json` never names a machine path.** The server entry is `{"type": "stdio", "command": "bash", "args": ["<scriptsDir>/docs-search-server.sh"]}`. That outer-loop script is copied verbatim. It resolves the cache directory through a new `hr_cache_dir` in `lib/harness-run-lib.sh`, which matches `machineCacheDir()` byte for byte, the way `hr_lane_dir` matches `machineStateDir()`. It then `exec`s the runtime CLI's `docs serve`. This follows `cli/scripts/README.md`'s rule that a long-running program stays inside the repository rather than at an evictable `npx` cache path.
- **Re-confirmed while planning: PGlite 0.5.8 loads both extensions.** An in-memory `PGlite.create({ extensions: { vector, pg_textsearch } })` took `CREATE INDEX … USING hnsw (embedding vector_cosine_ops)` and `CREATE INDEX chunks_bm25 … USING bm25 (body) WITH (text_config='english')`. `ORDER BY body <@> to_bm25query($1, 'chunks_bm25')` returned only the matching row, at score `-1.8455…` (lower is better). A query with no term in the corpus returned `[]`. The `vector <=> $1` ordering returned all three rows. The whole probe took 924 ms. The export names are `vector` from `@electric-sql/pglite-pgvector` and `pg_textsearch` from `@electric-sql/pglite-pg_textsearch`.
- **Models, chosen for size and licence.** Embeddings use `Xenova/bge-small-en-v1.5`, the ONNX port of `BAAI/bge-small-en-v1.5` (MIT). It runs with `dtype: 'q8'`, CLS pooling, normalised, 384 dimensions, and was already measured by hand at about 33 MB and 4 s cold. The reranker is `Xenova/ms-marco-MiniLM-L-6-v2`, the ONNX port of `cross-encoder/ms-marco-MiniLM-L-6-v2` (Apache-2.0). It has about 22.7M parameters, uses `q8`, and its sigmoid-of-logit score lies in (0, 1). It was chosen over `bge-reranker-base` (278M parameters) for size. Whether it runs the same way, and whether any of this holds on Linux, stays **open**. Gate 10 (Task 22) records it.
- **Tests never download a model.** The shipped code carries a test seam: the environment variable `AUTONOMOUS_SDLC_HARNESS_RETRIEVAL_STUB`, owned by `cli/src/retrieval/models.ts` as `RETRIEVAL_STUB_ENV`. Its value `hash-v1` or `hash-v2` selects a deterministic stub embedder and reranker. Every fixture that turns retrieval on also points `XDG_CACHE_HOME` at a temp directory and plants the model files listed in `MODEL_FILES` as empty files. The retrieval verbs check that those files are present even under the stub, so removing them fails the same checks a real adopter's missing cache would.
- **`setup-worktree.sh` does not warm the index.** The first `search_docs` call refreshes the index, and a refresh embeds only changed chunks. Warming would spend a model load on every worktree, including worktrees whose branch never queries. The cold build time is recorded twice: on the fixture corpus under the stub (Task 6's `docs index` output) and with the real model (Gate 10). `docs/retrieval.md` states when that decision should be revisited (Task 21).
- **The index lives at `<stateDir>/docs_index/`**, ignored as a whole directory. It gets no `STATE_DIR_ENTRIES` row, on `QA_ARTIFACTS_DIR`'s precedent in `cli/src/generators/repoRoot.ts`. **This departs from a conventions-document monopoly:** `.claude/context/conventions.md` → `### Where a new responsibility goes` makes `cli/src/core/writer.ts` the only module that writes into an adopting repository, with no exception, and the task prompt's per-checkout, gitignored index is written by `cli/src/retrieval/store.ts` at query time. Task 5, the task that introduces the write, declares the exception in `writer.ts`'s header in the same edit (one module, one path), and `## Corpus staleness` below raises the conflict for a supervised amendment of the conventions document.
- **"Is the retrieval runtime installed?" has one body:** `retrievalRuntimeState()` in `cli/src/retrieval/runtime.ts` (Task 2). `init`'s setup step (Task 12) and `doctor`'s `retrieval-dependencies` check (Task 13) both read it and neither re-spells its file tests; the launcher (Task 9) mirrors its first test, the entry file. **Tests stay offline by planting the runtime**, never by taking a this-installation branch: Task 6 adds `plantRetrievalRuntime(cacheHome)` to `cli/test/helpers/fixture.mjs`, and every retrieval-on `init` and `doctor` case (Tasks 10, 11, 12, 13) calls it.
- **The launcher's machine-path literals have declared owners.** `cli/templates/scripts/docs-search-server.sh` (Task 9) mirrors `machineCacheDir()` (declared in `cli/src/machine/paths.ts`) and `RETRIEVAL_CACHE_DIRNAME`, `RETRIEVAL_RUNTIME_DIRNAME` and `RUNTIME_CLI_RELATIVE` (declared in `cli/src/retrieval/runtime.ts`'s header, Task 2), and its own header names both owners.
- **The schema lands in Task 18, after the model and check it mirrors.** The configured layer order puts `general` last. The cross-layer rule that a configuration key is "one contract in four places" holds by the end of the branch: Task 1 writes the check's clause from the exact schema clause Task 18 adds, and both files state it.
- **The deferral to the eval branch cites the roadmap row by title**, *Docs-catalog retrieval*, and the branch name `feat_docs_retrieval_eval`, never an item number. The task prompt says the numbers are about to change. No new text anywhere may add an `item <N>` phrase.
- **Output stays plain ASCII** (`.claude/context/conventions.md` → `## Output, logging and errors`). A result line the CLI prints uses `;` and `-`, never an em dash. A snippet is quoted document text and is the one exception, because it is data. **`docs serve` departs from the single-output-surface rule of the same section:** its stdout is the MCP stdio transport. Task 8 declares that one exception (one module, `cli/src/retrieval/server.ts`; one sub-verb) in `cli/src/core/report.ts`'s header, and `## Corpus staleness` raises it.

**Top risks:** The likeliest failure is a tool the agents are granted but an unattended run never loads. `.mcp.json` might not declare the server, the profile might not start it, or the launcher's relative path might not resolve from the session's working directory, and each of those stalls a print-mode run rather than failing it. Task 10 guards the first two by checking the templates against each other in both directions at generation time and by asserting the generated files. Gate 10 (Task 22) establishes the third by hand. The same stall also follows from a launcher with no runtime to `exec` while `doctor` passes; Tasks 12 and 13 key on the same `retrievalRuntimeState()` the launcher's entry file belongs to, and Task 13's case (d) asserts that `retrieval-dependencies` fails with no runtime planted even though the workspace CLI's own peers resolve. The second risk is a retrieval library loaded, or installed, for an adopter who never turned retrieval on. Task 2's suite runs non-retrieval verbs under a loader hook that refuses to resolve any of the five packages, and asserts that every peer stays optional in the manifest. The third risk is an incremental refresh that quietly re-embeds everything or leaves stale chunks behind. Task 6 asserts exact embedded, unchanged and deleted counts after a one-section edit and after a deletion. The fourth is a download in the middle of a run: remote model loading is enabled only inside `docs fetch-models` (Tasks 3 and 12), and `doctor`'s model-cache check fails when the weights are absent (Task 13).
