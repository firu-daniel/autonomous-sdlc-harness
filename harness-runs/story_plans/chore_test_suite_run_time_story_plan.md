# Story: Make the gate suite cheaper per run — template-copied fixtures, bounded in-file concurrency, and a measured before and after at the runner's core count

## Context

`bash scripts/run-gates.sh` is what every implemented unit runs, and its time is `npm test` (gate 4): the task prompt measured 214 s of a 220 s run on a 10-core machine, with `cli/test/init.test.mjs` (123 s), `cli/test/doctor.test.mjs` (91 s) and `cli/test/stack-presets.test.mjs` (46 s) dominating. This branch makes each run cheaper without removing a test or weakening an assertion, and ships the step that measures it. When and how often the flow runs the suite is the later `feat_run_gates_phase` branch; `plugin/agents/layer-implementer.md` and every instruction document stay unchanged, and gates 1a and 11 are compared, never fixed.

**What the planner measured before choosing (2026-09-25, this worktree, 10 cores, macOS, Node v20.19.5; every figure is re-measured by Task 7 with the shipped script).** The cost is **per-case subprocess work, and it is CPU-bound**. A whole `node --test cli/test/` ran 131 s wall in one run and 168 s in another that recorded 389 s user + 265 s system — about **654 CPU-seconds**, 3.9 cores busy on average. Every slow case is a serial chain of processes: one `createFixture` with its origin ≈ **108 ms and ~14 git processes**; one first `init` ≈ 210 ms (12 git processes, including a commit and the `git maintenance run --auto` it triggers); a re-run `init` ≈ 120 ms (8); one `doctor` ≈ 190 ms (16 git processes plus `jq`); bare CLI start ≈ 40 ms. A chain of 40 fixtures ran at 97% CPU, and so did a chain of 40 `doctor` runs. It is **not** `npm` (every such case uses a stub on `PATH`) and not the network. A `GIT_TRACE` of the whole suite counted **21,604 git processes**, of which the 640 origin-seeded fixtures account for about **9,000 (≈42%)**. `init.test.mjs` alone ran 95 s over 285 tests (111 top-level) with its longest case at 5.2 s; `node --test` ran its cases strictly one after another, which the planner confirmed on this Node: top-level `test()` calls in one file are serial, the children of `describe(name, { concurrency: n }, …)` run `n` at a time. The other 15 files took **152 s** summed when each ran alone (`docs-retrieval.test.mjs` the longest at 26 s).

**What that means at 2–4 cores.** Because the work is CPU-bound, wall time at `n` cores is bounded below by the suite's CPU time over `n`, and `node --test` runs `os.availableParallelism() - 1` files at once — **three files on a 4-core runner, one on a 2-core runner**. GitHub's standard hosted Linux runner has 4 vCPUs for a public repository (this one) and 2 for a private one, so the plan models **4**, with **2** beside it. Neither is measured on this branch: no container runtime exists on the measuring machine, and the user chose (Park 1, `harness-runs/clarifications/chore_test_suite_run_time/answer_1.md`, option (b)) host-only figures now, with the restricted figures recorded as not yet measured and acceptance item 1 left open for the user to close later (Task 7).

**The choices, argued, with the saving each is expected to buy.**

- **Copy fixtures from a template (Task 1) — taken.** Every fixture's seeded state is identical, so each test process seeds one template per variant once and every test gets an in-process copy with the origin's one stored path rewritten. Expected: the ~9,000 fixture git processes (≈42% of the suite's git processes; an estimated 100–125 of the 654 CPU-seconds, 15–19%) disappear, and that saving holds **at every core count** — the only lever here that helps a 2-core runner in full.
- **Bounded concurrency inside the three slow files (hint 2; Tasks 2–4) — taken.** One helper owns the bound (`Math.max(2, os.availableParallelism())`, overridable by `HARNESS_TEST_CONCURRENCY`, whose `1` restores series). It turns a file's serial chain into `n` chains, so one file can use more than one core. Expected, with Task 1: at 10 cores the 95–123 s floor `init.test.mjs` sets goes, and the suite falls toward its CPU share plus the longest remaining serial file — an estimated **60–75 s against 131–214 s**; at 4 cores, from a CPU floor of about 164 s plus `init.test.mjs`'s serial tail, to about 136 s (≈20–35%); at 2 cores, where one file runs at a time and one core idles, from about 410 s (the serial sum) to about 290 s (≈30%). Linux spends less on process creation than macOS did here (265 of the 654 CPU-seconds were system time), so the container figures should come in lower than these.
- **Split the slow files (hint 1) — not taken.** It gains nothing on a 2-core runner (one file at a time) and at most three slots on a 4-core one. It would also move about 13,000 lines between files and duplicate their helpers, where the bounded suite gives the same parallelism with every file, header and history left where it is.
- **Also not taken, each for a stated reason:** caching the CLI's own read-only git probes (the largest remaining CPU after Task 1, but a product change bought with test time, and `init` mutates the repository between probes); a post-`init` template for `doctor`'s wired fixtures (`init` writes the repository's absolute path into what it generates, so a copied wired repository is a different repository); a fixed `--test-concurrency` in `cli/package.json` (a constant would cut a 10-core machine from nine file slots, and once the three heavy files run concurrently the 2-core gain is small); turning off git's auto-maintenance after `init`'s commit (~611 processes, ≈2%, and it changes the environment the CLI under test runs in); and concurrency in the other 15 files (152 s summed, the largest remaining cost **at 2 cores**, but at the modelled 4 cores the runner's three file slots already overlap them). No gate is removed, because every gate other than 4 takes about a second.

**Isolation was audited before any case runs concurrently, not assumed.** In all three files every fixture and every machine-scoped directory (`HOME`, `XDG_*`, `CLAUDE_CONFIG_DIR`, the retrieval cache, the `PATH` stub directories) is a fresh `mkdtemp`, and every environment override reaches the CLI through `runCli`'s per-subprocess `env` rather than `process.env`. A grep for `process.env` assignment prints nothing in any of the three (the two files that do assign it, `push-destination.test.mjs` and `retrieval-loading.test.mjs`, are untouched). `cli/dist/` is only read, and worktrees are keyed on each fixture's unique name. One case asserts wall-clock bounds — `init.test.mjs`'s dev-server wrapper case — and Task 4 runs it after its suite, alone within that file. Each task re-checks the audit for its own file and records it in that file's header, together with the rule a new case must keep to stay concurrent.

**The measurement ships with the decision** (the ledger's `## Evidence and measurement` rule). `scripts/measure-suite.sh` (Tasks 5–6) times `npm test` and `bash scripts/run-gates.sh` at any commit: on the host in a throwaway detached worktree, or with `--cpus <n>` inside a Linux container pinned with `--cpuset-cpus`, where `os.availableParallelism()` answers `n`. macOS cannot confine a process tree to fewer cores, so a container is the only honest way to measure at the runner's count. Task 7 runs it on the host at the pre-branch commit and at `HEAD`, proves the same tests pass with the same assertions, and records the figures in `docs/development.md` gate 4. Per the user's answer to Park 1 (option (b)), it does **not** run `--cpus`: the gate-4 record says plainly that the 2- and 4-core figures are not yet measured and names `bash scripts/measure-suite.sh --cpus 4` as the command that measures them. The shipped `--cpus` mode is the seam that follow-up measurement starts from (the ledger's `## Evidence and measurement` "not yet measured" rule). Acceptance item 1 stays open for the user.

**Top risks:** the likeliest failure is a **concurrency flake**: a case that shared something invisible, or a wall-clock bound that starts measuring machine load. Tasks 2–4 guard it with a per-file isolation audit recorded in each header, the one timing case kept out of the concurrent suite, and the `HARNESS_TEST_CONCURRENCY=1` switch. Task 7 then requires three consecutive green runs on the host. Two full-suite runs during Tasks 1 and 4 had unidentified gate-4 failures (1 of 790, 2 of 791) that passed on re-run, so Task 7 treats any red run as a blocker and must name the failing case rather than re-run until green. The pinned-core half of that check cannot run on this branch (Park 1, option (b)) and stays with acceptance item 1. The second risk is a **copied fixture that is not the fixture it replaces**, for example a git that stores the origin path somewhere new so that two tests share one origin. Task 1 fails loudly unless the path it rewrites occurred exactly once, and its equivalence test compares a copy against a freshly seeded repository query by query. The third is a **restricted-core figure presented as measured when it is not**. Task 6 refuses with its own exit code instead of guessing. Task 7 does not invoke `--cpus`, never writes a host or estimated figure into a restricted-core cell, and labels those cells not yet measured.

**Follow-up for the user, not a task on this branch (closes acceptance item 1):**

- Install and start a container runtime that provides the `docker` CLI (Docker Desktop, colima or OrbStack), with its VM given **at least 4 CPUs** (colima defaults to 2), network access so it can pull `node:20-bookworm` and run `apt-get` and `npm ci`, and the macOS temp directory (`$TMPDIR`, under `/var/folders`) shared with the VM (colima shares only `$HOME` by default). Then run `bash scripts/measure-suite.sh --cpus 4` (and `--cpus 2`) at the before commit and at `HEAD`. No task in this plan depends on it. Without it, `--cpus` exits 3 by design.
