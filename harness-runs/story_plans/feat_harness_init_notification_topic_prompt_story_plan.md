# Story: Make the push-notification setup answerable by a non-technical adopter

## Context

`init`'s push-notification opt-in asks for a destination, and the question reads to a non-technical adopter as *"stand up a server first"*. Where it is asked today there are several wordings, each different. The terminal question (`cli/src/commands/init.ts` → `resolveNotifications`) says *"any endpoint that accepts a POST, e.g. https://ntfy.sh/<your-topic>"*. The blank-answer note (`cli/src/generators/notifications.ts` → `writeNotifications`, the `pushUrl === undefined` arm) says *"Re-run with --push-url <url>, naming any endpoint that accepts a POST"* plus a worked ntfy example. The no-opt-in note says *"--notifications --push-url <url>"*. The flag row (`INIT_OPTIONS` → `pushUrl`) says *"Endpoint unattended-run notifications are posted to"*. And `doctor`'s advice (`cli/src/doctor/checks.ts` → `deliveryOptInAdvice`) says *"`init --notifications --push-url <url>`"*. None of them accepts what the ntfy app actually gives an adopter, which is a topic name.

This branch makes the route that needs no server and no account (install the ntfy app, create a topic, type its name) a **suggestion offered in the same question**. A full URL for any other service stays equally answerable in that same question. It also makes every place that narrates the destination say the same thing.

**The decisions this plan takes, stated once here so every task reads the same ones:**

- **One grammar, one owner.** What may be typed is decided by one pure function, `resolvePushDestination(answer: string): PushDestination` in `cli/src/generators/notifications.ts` (Task 1). It returns one of three results:
  - `{ kind: 'url', url }` for a trimmed answer starting `http://` or `https://` (any letter case) that `new URL()` parses with a non-empty hostname and that contains no whitespace, no control character and no `'`. The value is kept verbatim.
  - `{ kind: 'ntfy-topic', url: 'https://ntfy.sh/<topic>' }` for a bare topic, or for `ntfy.sh/<topic>` with no scheme (host case-insensitive, one optional trailing `/`). The topic must match `^[-_A-Za-z0-9]{1,64}$`, the name rule the ntfy server applies to a topic.
  - `{ kind: 'unrecognised' }` for everything else. That includes a scheme-less `example.com/hook`, which curl would silently have treated as `http://` before.

  Every entry point calls this function: the `--push-url` flag at parse time and the terminal prompt (Task 3), and the generator itself (Task 1). A second copy of the grammar anywhere is a defect. `ROADMAP.md`'s unshipped `notifications set-url` command is the entry point most likely to be added later, and the function's doc comment says it takes its grammar from here.
- **One sentence for "what may I type here".** `PUSH_DESTINATION_FORMS` (Task 1) is the only text that describes the accepted answers. The prompt, the blank-answer note, the no-opt-in note, the unrecognised-answer warning and the parse-time refusal all interpolate it. `PUSH_DESTINATION_PLACEHOLDER = '<url-or-ntfy-topic>'` is the one placeholder the flag row, the notes and `doctor`'s advice print. The flag **name** `--push-url` and the keys `HARNESS_PUSH_URL` / `HARNESS_PUSH_CMD` / `pushEnvPath` are wire identifiers and do not change. The lessons ledger's naming rule changes the prose and the placeholder, never a wire identifier.
- **What is stored is always a full URL.** A topic is written as `HARNESS_PUSH_URL=https://ntfy.sh/<topic>`. So the delivery side (`cli/templates/scripts/autonomous-notify.sh`, which POSTs `"$HARNESS_PUSH_URL"` verbatim after sourcing the file under `set -a`) **needs no change**. This plan states that as a finding (register row 4), not as an omission. A value outside the shell-safe set `[A-Za-z0-9._:/?#@%+=,-]` is written single-quoted. `~` is left out of the set because bash tilde-expands it after a `:` in an assignment. Without the quotes, a URL with a `&` or `;` in its query string would break, or run a command, when the notifier sources the file. `doctor`'s `nonEmptyKeys` already strips one pair of surrounding quotes, so it needs no change.
- **The ntfy topic name is itself a credential.** On the public server anyone who knows a topic can read and publish to it, and the topic is the only secret in its URL. It is therefore handled exactly as the URL already is. It is never printed back by any note, warning, refusal or `--dry-run` preview. The prompt tells the adopter it works like a password and to choose one nobody would guess. The file stays `0600` in a `0700` directory. The terminal echoing the adopter's own typing is the terminal, not the run, and is unchanged (`docs/development.md` §5 already says so).
- **An answer that is neither is refused or re-asked, and nothing is written.** A `--push-url` value is checked in `parseInitFlags`, **whether or not `--notifications` was given**, before the git gate and every other precondition, like `--qa-driver`. An unrecognised value exits 1 with a message that names the accepted forms and does not repeat the value. On a terminal, an unrecognised answer is re-asked up to `REPROMPT_LIMIT` times (the same bound `askYesNo` uses) with a line that does not repeat the value. If the answer is still unrecognised, the generator writes nothing and prints a warning on stderr.
- **An already-configured machine is never re-pointed.** The machine-local file stays `create-if-absent`, a refusal writes nothing, and Task 3 covers the re-run paths with fixture tests.

Cut into four single-layer tasks in bottom-up order:
1. the grammar, the generator's wording and file handling, and the committed example template (Task 1);
2. `doctor`'s advice line (Task 2);
3. `init`'s flag, prompt and re-ask, and its fixture tests (Task 3);
4. the catch-all documentation in `docs/` (Task 4).

The `plugin` layer is untouched: nothing under `plugin/` narrates this destination.

**Top risks:** The likeliest failure is two answers to "what may I type here". A prompt, a note, a flag row or a doc could word the accepted forms differently, or a second copy of the grammar could accept something the other refuses. Task 1 owns the one sentence and the one resolver, and Task 3's tests assert that the same sentence reaches both the question and the blank-answer note. The second risk is leaking the credential: the topic is short and memorable, so a note like "wrote https://ntfy.sh/<topic>" is an easy mistake. Tasks 1 and 3 each assert on a unique value that the topic and the URL appear in neither stdout nor stderr on every path, refusal included. The third risk is a re-run degrading an already-configured machine, which Task 3 covers with fixture cases (a hand-written file kept byte-identical under a topic re-run, a plain re-run and a refused re-run). Parse-time refusal of scheme-less URLs is a deliberate change for a scripted re-run that passed one: it now exits 1 and writes nothing, and the message names the fix.
