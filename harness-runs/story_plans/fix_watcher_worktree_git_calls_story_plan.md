# Story: The watcher family's own git calls in a run's working copy

## Context

This branch closes residual 1 of `docs/cli.md` §6 (`**Residuals, stated rather than hidden:**`, item 1). The run watcher and the scripts it calls run outside the sandbox. Their git calls in a run's working copy, and the scripts they run from one, read whatever a sandboxed session left there. `feat_unattended_bash_sandbox` hardened `push-branch.sh` and `refresh-branch.sh` against exactly that. This branch gives the rest of the family the same discipline, built from the helpers that already ship in `cli/templates/scripts/lib/harness-run-lib.sh`. The design is held to one claim: **a run's commits can carry any content at any path, protected ones included**, because a sandboxed process can write objects, its record's `index` and `refs/heads/<branch>`. Write protection stops a write; it does not stop a commit. The design does not rely on the Linux worktree-glob entries either way. `docs/sandbox-verification.md` (`chore_sandbox_manual_verification`, merged) still records **How the Linux sandbox treats a `denyWrite` entry containing `*`:** as **not run**.

**Probed at plan time** (git 2.50.1, Apple Git-155, a scratch fixture whose main `core.hooksPath` is the repo-relative `githooks` that `init` writes, `cli/src/generators/githooks.ts` → choice 2). `git worktree add <dir> <branch>` and `git -C <copy> reset --hard HEAD` each ran the `githooks/reference-transaction` **committed on the run's branch**: a relative `core.hooksPath` resolves inside the working tree the hook runs in. `git -C <copy> status --short` ran a `core.fsmonitor` from a nested repository's own config, behind a gitlink the run added. Either `--ignore-submodules` or `-c core.fsmonitor=false -c submodule.recurse=false` stopped it.

**The trust classes**, which every task names its sites by:

- **(a) trusted tree**: a fresh copy cut from the default branch's commit **as origin reports it** (not as a local ref states it), or the main checkout's refs only.
- **(b) reads only**: nothing the call reads can run code.
- **(c) exposed**: a planted payload reaches the call.

**Decisions, one per goal**, binding on every task:

- **Every hardened git call runs no hook at all.** `core.hooksPath` is pinned to `/dev/null`, which holds none. `push-branch.sh` keeps its own pin to the main repository's hooks. The pin is not `hr_pinned_hooks_path`, which would newly refuse an adopter whose `core.hooksPath` is foreign on a path, the local review reuse, that never pushes. As a result the watcher's artifact commit runs no commit hook, which is `refresh-branch.sh`'s precedent ("No merge hook runs").
- **Every hardened git call runs as `git -C <main>`, or with `GIT_DIR=<main>/.git`, `GIT_INDEX_FILE=<record>/index` and `GIT_WORK_TREE=<copy>`.** Both forms also carry `-c core.fsmonitor=false -c submodule.recurse=false`, plus `--ignore-submodules` / `--no-recurse-submodules` wherever a call could recurse. They name `refs/heads/<branch>`, never `HEAD`. Git therefore never reads the record's `config.worktree`, `commondir`, `HEAD` or the `.git` pointer, so the per-working-copy config check is **skipped outright** rather than added. The main checkout is placed with `hr_wrapper_main_of`. The target is checked with `hr_wrapper_target_check_var`. The branch is read once with `hr_wrapper_branch_var`.
- **No unsandboxed checkout installs run-authored content at a protected path. The choice is refusal, never restore.** The protected set is the worktree-relative projection of `cli/src/generators/writeProtection.ts` → `protectedPaths`' worktree-glob entries: `<githooksDir>`, `.mcp.json`, `.claude/settings.json`, `.claude/settings.local.json`, and, where docs retrieval applies, `<scriptsDir>/docs-search-server.sh` and `<scriptsDir>/lib`. It is computed from the **main** checkout's `harness.config.json`. Before any fast-forward, reset or `worktree add` writes a tree, that tree must equal the default branch at `merge-base(<tip>, <trusted base>)` on that set. A reused copy's working tree must also match its tip there, with nothing untracked under the set. A copy that fails is refused the way the watcher already fails a pre-launch problem. **Why refusal:** an honest unattended run cannot write any of those paths, because the sandbox and the file-tool deny rules both stop it. Any difference is therefore a commit made through plumbing or a write the Linux glob did not stop. Restoring would leave a dirty tracked tree that wedges the engine's clean-tree precondition.
- **The trusted base is origin's answer, never a local ref.** A sandboxed session can write the common directory's `refs/` and `packed-refs`, so a run that points `refs/remotes/origin/<defaultBranch>` (or `refs/heads/<defaultBranch>`) at its own payload tip makes the merge base that tip and every diff empty. So `hr_run_trusted_base_var` (Task 1) takes the base from `ls-remote origin refs/heads/<defaultBranch>`, held in a shell variable, then fetches that ref with no destination and proves the object arrived with `cat-file -e`; it reads no local ref of the default branch and no `FETCH_HEAD`. When origin cannot be reached the check **refuses**, never falls back: an unattended run needs the network for its model API anyway. `create-worktree.sh`'s default mode cuts from that same commit, and refuses with exit 2 without it (Task 5). In job mode, where the session has had the checkout's `.git` itself, `harness-run.yml` records the default branch's commit id from the fresh checkout before any session (`Record the default branch's commit`, Task 9) into the job's environment, and the watchdog passes it as `doctor --job-surfaces=<branch>@<commit>`, which reads the trusted configuration and the base from that object id (Tasks 4 and 6). The workflow's own refusal step keeps the plain form: it runs on a fresh `actions/checkout`, before any session. **Not closed here, and not probed:** the object store is sandbox-writable as well, and git does not re-hash an object on most reads, so a session that overwrites the bytes of an object the trusted base already names could still substitute them. Task 14 probes it and states it as a residual if it reproduces.
- **`create-worktree.sh --existing` adds the copy with `--no-checkout` under the pins, checks the tip, then populates it with `read-tree` from that same object id.** It bootstraps with the **main** checkout's `setup-worktree.sh --target <copy>` and the main checkout's configuration, never the branch's own script and `commands.*`.
- **The bootstrap's configured commands, `commands.depInstall` and `commands.build`, run against the run's own manifest, are a stated residual, not closed.** `setup-worktree.sh` runs `commands.depInstall` and then `commands.build` (`run_configured depInstall …`, then `run_configured build "build"`), in `create-worktree.sh --existing`'s bootstrap and in the job's `Bootstrap the checkout`. Both run in the run's checkout against that checkout's `package.json`: an install such as `npm ci` runs the manifest's lifecycle scripts, and a build such as `npm run build` runs its `scripts.build` / `prebuild` / `postbuild`. Both start npm inside the checkout, so both still read a run-written project `.npmrc` (`node-options=--require …`) or `node_modules/`. `package.json` is in neither `copySurfacePaths` nor `jobSurfacePaths`, so neither check sees a run that changes those entries. A package manager runs the manifest's lifecycle and script entries by nature, and no out-of-session sandbox runtime ships to run them in.
- **Goal 4 closes the GitHub job's surfaces with a contained change.** A new `harness-run.yml` step, after `Set up Node` (moved up for it) and **before `Read the configuration`**, the only step that sets `SCRIPTS_DIR`, runs the **pinned** CLI as `doctor --job-surfaces=<GitHub default branch>`. That step refuses a branch whose own commits changed any repo-relative path `protectedPaths` names in the main checkout: the outer-loop scripts and `lib/`, `<githooksDir>`, `.mcp.json`, the profile, `.claude/settings*.json` and `harness.config.json`. The trusted configuration is read from the GitHub default branch's tree. A second new step right after it, `Record the default branch's commit`, writes that branch's commit id from the fresh checkout to `$GITHUB_ENV` as `HARNESS_GITHUB_DEFAULT_COMMIT`. Because it precedes the `SCRIPTS_DIR` write, a refusal also stops every `always()`, `!cancelled()` and `cancelled()` step, each gated on `env.SCRIPTS_DIR != ''`, from running a script out of the refused tree, as the run-actor gate's refusal already does. A refused job ends `failure` with an annotation, saves no bundle and sends no notification, and its run is recorded by `remote-run.sh`'s existing no-bundle mapping. In job mode the stall watchdog runs the same check before its reset as `--job-surfaces=<branch>@$HARNESS_GITHUB_DEFAULT_COMMIT`, because by then the session has had the checkout's `.git/refs` and could have moved `refs/remotes/origin/<default>`; that form reads the configuration and the base from the recorded object id. The workflow file itself still runs as the branch carries it. That is `docs/remote-execution.md` §9's existing residual (`**The residual risk, in both set-ups.**`), cited and not reopened.
- **The state directory a dropped file is placed under is the main checkout's.** A copy whose own resolvable `stateDir` differs is the closed "unresolvable" outcome every `run_state_dir` caller already has.

**Constraints every task keeps.**

- The wrappers' shipped behaviour does not change for callers outside the watcher family. `cli/test/wrapper-target-check.test.mjs`, `push-branch-worktree-config.test.mjs` and `refresh-branch-worktree-config.test.mjs` stay green unchanged.
- No existing refusal gets weaker. A new refusal fails as `fail_before_launch`, `reject_preserving_status` or the watchdog's give-up does, and never falls back to the unhardened call.
- An honest copy's outcomes are unchanged: an identical re-drop's skip, a non-blocking local commit or push failure, the remote arm's blocking failures, and the watchdog's resume from the committed ledger. **One deliberate exception:** where origin cannot be reached, a review reuse, a watchdog reset and a `create-worktree.sh` cut (either mode) now refuse instead of proceeding, because no trusted base exists to check against.
- Scripts stay bash 3.2-compatible: no `mapfile`, no `${v,,}`, no associative arrays.
- No git command beyond the shipped floors (2.23 for the wrappers, 2.38 for the refresh). Nothing here needs `merge-tree`.

**Coordination.** `fix_run_job_credential_exposure` also edits `autonomous-watcher.sh` (`spawn_engine`) and `harness-run.yml`, and `feat_unattended_sandbox_preflight` edits `harness-run.yml`. Whichever merges second rebases onto the first; Tasks 6 and 9 stay clear of `spawn_engine` and of steps neither of them adds. **The GitHub half reaches a job only in a release that carries this branch** (`bash scripts/release.sh <version>`, `docs/development.md` → `## 7. Releasing`). Here it is verified by test: Task 9 pins the rendered workflow, and Tasks 11–13 run planted-payload fixtures against the real scripts.

**Top risks:**

1. **A hardened call that changes an honest copy's outcome**: a re-drop no longer skipped, a local failure that now blocks, a watchdog that stops resuming. Task 6 keeps every existing log and notify outcome, and Tasks 11 and 12 each carry an honest-copy case beside every payload case.
2. **The shell copy of the protected set drifting from `writeProtection.ts`.** Task 3 declares the mirror in that module's header, and Task 10's parity case compares the two outputs on an `init`-written fixture.
3. **A base the sandbox can set.** Every surface check is only as good as its base; a local ref of the default branch is sandbox-writable. Task 1's `hr_run_trusted_base_var` is the one source of the base, and Tasks 5, 11, 12 and 13 each carry a forged-base case whose `RED ONCE` mutation is "use the local `refs/remotes/origin/<defaultBranch>`". The cost is stated: an unreachable origin now refuses, where it used to proceed.
4. **The new `harness-run.yml` step landing in the wrong place, or reading a branch value.** The step must run before `Read the configuration`, so a refusal leaves `SCRIPTS_DIR` unset and no post-session step runs a script from the refused tree, and it must take the default branch through `env:`. Task 9's two rendered-template cases pin all of that, and the post-release job below checks it on GitHub.

**Manual setup required:**

- **The post-release GitHub check**, after the release that carries this branch. It depends on Tasks 4, 6, 9 and 15.
  1. Re-render the standing test repository's workflows with `npx autonomous-sdlc-harness@<version> init --upgrade-workflows`.
  2. Commit and push every path the upgrade's `git add` line prints to its default branch.
  3. Run one job on a branch whose earlier job committed a goal-4 payload: a changed `.claude/settings.json` or outer-loop script, committed through plumbing.
  4. Record the outcome in `docs/remote-execution.md` beside goal 4's residual. Until then, Task 15 states the check as not yet run.
