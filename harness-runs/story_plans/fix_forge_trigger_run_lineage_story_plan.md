# Story: Bound a remote run's lookups to its own branch lineage

## Context

Gate 12 round 5 found that a remote run treats an earlier, unrelated run that used the same branch name as its own past. `remote-run.sh restore` picked up a two-day-old state bundle and placed its planning drafts, and the trigger's issue comment linked an older failed run. Both lookups match on the branch name and the `harness run <branch>` title only. This branch adds a lineage bound to both lookups. It also stops the trigger deriving a name that already has run history, and fixes two smaller findings from the same round: `doctor --check-github` drops the trigger confirmation, and the commands' GitHub route uses an out-of-tree `mktemp -d` directory.

**The lineage bound is the run's head commit, not a timestamp.** The task prompt's approach 1 bounds the lookups by `createdAt`. This plan tests the run's `headSha` instead. For `workflow_dispatch`, `gh run list` returns the commit the dispatched ref pointed at when it was dispatched (this repository already reads `headSha` in `docs/development.md` → Gate 12 observation (ii)). A run belongs to the current lineage when its `headSha` is one of the commits `git rev-list refs/remotes/origin/<defaultBranch>..HEAD` lists in the job checkout. `harness-run.yml` checks out with `fetch-depth: 0`, so that list is complete. Commits of a deleted, unmerged branch are not in it. Commits that were merged into the default branch are excluded by the range. Every legitimate own-lineage run is included: a resume after a pause, a user-review round, a chain of jobs, and `--resume answer`. Each is dispatched on a tip that descends from the branch's first own commit. `push-branch.sh` never forces and `refresh-branch.sh` merges rather than rebases, so that ancestry is never rewritten. The prompt's candidates were checked as follows:
- **The fork-point variant of approach 1 is wrong.** On Gate 12's standing repository, the default branch is reset to its seed between rounds. The fork-point commit can therefore be older than the earlier lineage's runs, so the bound would admit them.
- **The task-prompt-commit timestamp variant works, but it depends on clocks.** It compares the clock of the machine that made the commit with GitHub's clock. A machine running fast could drop a run's own bundle.
- **Approach 3 (stamping the bundle) is not taken.** It needs a rule for every bundle that already exists unstamped. `headSha` is a stamp GitHub already records on every run.

When the bound cannot be computed, `restore` behaves as it does today and says so in one line. This happens when `origin/<defaultBranch>` does not resolve, or when `HEAD` has no commit beyond it (for example, a branch already merged). The Gate 12 defect always has the branch's own task-prompt commit, so the bound always applies to it.

**Which routes reach the bound.** The watcher's inbox route reaches the same job-side `restore`, with `resume: none`, when `execution.target` is `github-actions`. So does `/autonomous-sdlc-harness:branch-prompt`, which drops into that inbox, given a name whose branch was deleted. The job runs `create-worktree.sh`, places and commits the prompt, then `remote-run.sh dispatch … --resume none`. Bounding `restore` (Task 1) therefore covers the trigger, `remote-run.sh start` with an explicit reused name, the inbox route and `branch-prompt` alike, with no change to the watcher. The trigger comment uses the same idea (Task 2): it names the run whose `headSha` is the commit `start` pushed, read from `refs/remotes/origin/<branch>`, or else the filtered run list. It never names an older run. The name rule (Tasks 3–4) also counts any run of the run workflow listed under a name as "taken". So `feat: invoices` after an abandoned `feat_invoices` derives `feat_invoices_2`. This complements the bound and does not replace it, because a hand-dropped inbox file or an explicit `start` name never passes through derivation.

**What is deliberately not bounded.** The following all read a branch's *newest* run, which for a recreated branch is its own run once GitHub lists it:
- `sync`, `fetch`, `status`, `list` and `review`;
- `branch-status`'s "earlier runs" table, which the prompt calls harmless.

`restore` and the trigger comment are the only two places that treat an *older* run as authoritative. Bounding `sync` would also need the mirror's local refs to be current, and `sync` does not fetch them.

**The temporary-directory finding.** `branch-pause`, `branch-resume`, `branch-answer` and `branch-user-review` all make an out-of-tree `mktemp -d` directory or `mktemp` file. Each will instead use a fixed, gitignored directory named by the command and a fold of the branch: `<state_dir>/scratch/<command>-<branch_fold>/`. `<branch_fold>` is the branch with every character outside `A-Za-z0-9_-` replaced by `_`. The fold puts the name in one path segment that `hr_scratch_path_var` always accepts, whatever the branch: a `/` would create two directory levels and `discard` would leave the outer one behind, and a character outside the accepted class, or a `..`, would make `discard` refuse the directory the command just created. `.` is folded too, because `..` is refused anywhere in the argument. Two branches that fold to the same name are safe, because the leftover check then stops the second command rather than sharing the directory (Task 7 owns this rule). The directory is created with a literal `mkdir -p`. It is removed through a new `remote-run.sh discard <dir>` verb, which removes only a path that resolves strictly inside `<state_dir>/scratch/`. The agent never runs a recursive `rm` (`.claude/context/conventions.md` → `## Shell assets`), and no command carries a substitution. The judgement "does this path resolve strictly inside `<state_dir>/scratch/`" already exists once, inline in `cli/templates/scripts/scratch-run.sh`. `discard` needs the same judgement, so Task 6 first moves it into the run library as one function, `hr_scratch_path_var`, which `scratch-run.sh` then calls. `discard` (Task 7) calls the same function. There is then one definition of "inside scratch" for both the script that executes a file and the verb that removes a directory (`.claude/context/conventions.md` → `### Where a new responsibility goes`: *"A responsibility that already has a home does not get a second one"*). If such a directory already exists, it is a leftover from an interrupted invocation. The command stops and names the `discard` command rather than removing it, per the lessons ledger rule *"never removes one it did not create"*.

The work is cut into twelve single-layer tasks:
- `cli` tasks 1–7: the scripts, the library (including the shared scratch-path test), `doctor`, the two state-directory README templates, and their suites;
- `plugin` tasks 8–9: the four commands;
- `general` tasks 10–12: the documents of record.

Tasks 1, 2, 4 and 7 each edit a different section of `cli/templates/scripts/remote-run.sh` and are chained by `**Depends on:**` so that only one task has the file at a time. Tasks 3 and 6 each edit a different section of `cli/templates/scripts/lib/harness-run-lib.sh`, and Task 6 `**Depends on:**` Task 3 for the same reason. `scripts/lib/harness-run-lib.sh` and the rest of this repository's own `scripts/` and `harness-runs/` are `init`'s self-adoption output (`.claude/context/conventions.md` → `## Documents of record`), and no task edits them.

**Top risks:**
- **The `headSha` bound excludes a run that is really this branch's own.** That would turn a resume into a first job, or refuse `--resume answer`. Task 1 guards this with a suite case for each legitimate route, an unbounded fallback that says so, and a refusal message that names the lineage. Task 12 adds the Gate 12 leg that records `headSha` on a real repository.
- **The new run-history probe makes every name look taken.** The trigger suite's stub answers every `run list` with a run, so the new probe would make every derived name look taken and break every existing trigger case. Task 4 rewrites that stub to answer the probe from a per-branch table, empty by default, before adding its own case.
- **The scratch move leaks a directory, or removes one it did not create.** Tasks 6–9 guard this: removal is scoped to the scratch directory by the same library function that fences `scratch-run.sh`, every command removes its directory on every path, and a leftover stops the command rather than being removed.
- **Moving `scratch-run.sh`'s path test into the library changes what it refuses.** Task 6 guards this: `scratch-run.sh` keeps its exit codes and its message wording, and its existing refusal suite in `cli/test/outer-loop-scripts.test.mjs` must stay green unchanged except for one added case.
