# Story: Remote execution on GitHub Actions — the execution half of Cloud / CI execution

## Context

This branch lets an unattended run execute in a GitHub Actions job instead of on the local machine. It is the **execution** half of the `ROADMAP.md` row *Cloud / CI execution*; the trigger half (issues, pull requests, comments, Jira) is the separate branch `feat_forge_run_triggers` and nothing here builds it. Local execution is unchanged and stays the default: with the new key absent or `local`, no new file is generated, no watcher path changes and nothing new is asked of an adopter (Acceptance 1).

The work runs bottom-up in the configured layer order, `cli`, then `plugin`, then `general`:

- **The key and its owners** (Tasks 1–4). `execution.target` in the model and the structural check (Task 1). A new area `cli/src/remote/` whose `githubActions.ts` owns every remote-execution name the CLI and the shell share — workflow file names, secret and variable names, the `gh` test seam — and the one bounded `gh` probe (Task 2). The outer-loop library gains the shell reader of the key and the run-registry primitives the watcher and the new script now share (Task 3), and the remote **state bundle** format (Task 4).
- **`remote-run.sh`**, a new outer-loop script (Tasks 5–8): the local verbs `dispatch`, `pause`, `warm`, `stop` (Task 5), `sync` and `status` (Task 6), and the job-side verbs `restore`, `save` (Task 7), `continue` and `poll` (Task 8).
- **The watcher** (Tasks 9–13). A new `job` subcommand runs one run inside the job's own checkout under the watcher's own launch line, exit classification, stall watchdog and usage gate (Task 9), plus the remote-only policies — remote pause, the hosted time budget, in-job waits and bounded auto-resume (Task 10). On the local side the inbox pass dispatches instead of spawning (Task 11), the resume passes relay answers, resumes and pauses (Task 12), and `restart-watcher.sh` stops counting remote records as in flight (Task 13).
- **What an adopter receives** (Tasks 14–20). `init --plugin-root-entries`, which the job uses to generate a profile its own plugin install can run under (Task 14). The two workflow templates, `harness-run.yml` (Task 15) and the self-disabling resume poller `harness-resume.yml` (Task 16), which `init` writes only when remote execution is on (Task 17). `doctor`'s offline `remote-execution` check (Task 18) and its opt-in online `remote-github` check behind `--check-github` (Task 19). The package README (Task 20).
- **The plugin** (Tasks 21–24). `remote-run.sh` joins the script-allowlist guard's deny list (Task 21). The drop and control commands learn to sync a remote record before acting (Tasks 22–23). The pause protocol and the flow document state the job's pause triggers and resumes (Task 24).
- **The schema and the documents of record** (Tasks 25–33). The schema property and a negative fixture (Task 25), `docs/config.md` and `schemas/README.md` (Task 26), `docs/cli.md` (Task 27), a new `docs/remote-execution.md` in two parts (Tasks 28–29), `docs/watcher.md` (Task 30), hand-run Gate 12 (Task 31), the guard and outer-loop verification records (Task 32), and `README.md`, `llms.txt`, `ARCHITECTURE.md` and the roadmap row (Task 33).

**Settled while planning, so no task has to settle it again.** Every decision the task prompt left open is taken here, with its reason, and every task that depends on one restates the part it consumes.

- **The key is `execution.target`, a closed enum `"local"` | `"github-actions"` with schema default `"local"`.** One enum rather than a boolean so a later GitLab CI value is a new member, not a second key. Its readers ship in this branch, which is what `ARCHITECTURE.md` → `## 8. Declaring a seam before building it` requires: `init` writes the workflows from it (Task 17), the watcher dispatches from it (Task 11), and `doctor` reports it — including *on but incomplete* (Tasks 18–19). The predicate every TypeScript reader imports is `remoteExecutionApplies(config)` (Task 1); the shell reader is `hr_execution_target` (Task 3). `buildConfig` does not write the key, so a fresh `init` produces the same file it does today.
- **`forge` gains no reader here.** `execution.target`'s value already names the platform the job runs on; `forge` describes pull-request and remote conventions, and its reader is the draft-PR and trigger coupling `feat_forge_run_triggers` owns. Adding a reader nothing needs is what the prompt forbids. "Done" for a remote run stays a pushed branch; `push-branch.sh` still opens no pull request.
- **The runner is one line, and one workflow serves both kinds.** `runs-on: ${{ vars.HARNESS_RUNNER || 'ubuntu-latest' }}`. The job tells the two kinds apart at run time from `runner.environment` (`github-hosted` | `self-hosted`), because `HARNESS_RUNNER` may also name a hosted label (`ubuntu-24.04`, or a larger-runner label the adopter created). The supported hosted choices are Linux x64 standard runners and Linux larger runners by label; macOS and Windows hosted runners are not supported (the stack scripts and `jq`/`gh` bootstrap are Linux-shaped), and the docs say so.
- **The job runs the watcher, not `anthropics/claude-code-action`.** What the local watcher does for a local run the job must do for itself (the prompt's own rule), and the watcher is already the thing that does it: the launch line flag for flag (`--settings`, `--permission-mode`, conditional `--model` / `--effort`, `--output-format stream-json`, the two `--add-dir`), the stream tee the usage gate parses, `classify_run_exit`, the stall watchdog and the park-loop guard. The action wraps its own launch and permission handling and exposes no teed stream to gate on. So the watcher gains a `job` subcommand (Task 9) that runs exactly one run in the job's checkout, where `MAIN_REPO` and the worktree are the same directory, with the inbox pass, the cleanup sweep, the machine lane and the tail window off. `ARCHITECTURE.md` §5's launch-path sites therefore gain no new site: job mode reaches the engine only through the existing `spawn_engine`.
- **The local watcher is the single dispatcher, and every call from local to remote is a user's action relayed.** With `execution.target` `github-actions`, an inbox drop is prepared exactly as today (working copy, artifact committed and pushed) and then dispatched with `remote-run.sh dispatch` instead of spawned (Task 11). `/autonomous-sdlc-harness:branch-answer`, `branch-resume` and `branch-pause` keep writing the same files into the run's local working copy, which for a remote run is a **mirror**; the watcher's resume and relay passes turn each into a dispatch (Task 12). Nothing local watches, gates, restarts or resumes a remote run on its own: the reconcile pass, the cap, the stall watchdog, the usage gate and the machine lane all skip records whose `execution` field is `github-actions` (Task 12), and `restart-watcher.sh` does not count them as in flight (Task 13). The optional manual route costs nothing extra: `remote-run.sh dispatch` is the same call by hand, and the workflow's `workflow_dispatch` inputs are the seam the trigger branch plugs into.
- **The inbox route could be built for every drop, so no part falls back.** A dropped user review is committed before the dispatch for a remote run — unlike a local one — because a job boundary before the flow's own commit would otherwise lose it; the subject is the new fixed form `chore: add user review for <branch>` (Task 11), which `## Corpus staleness` raises for the conventions document's fixed-subject list. An answer travels as a workflow input, because clarification files are gitignored by design: the watcher reads the mirror's answer files and `remote-run.sh dispatch --resume answer` passes them as one JSON input, refusing, with a message naming the limit, a payload over GitHub's documented `workflow_dispatch` input size.
- **A remote run reports through three channels the user reads on demand, and none the local watcher must receive.** (1) Push notifications from the job itself (`autonomous-notify.sh` unchanged, `HARNESS_PUSH_URL` from a repository secret); (2) GitHub's own run list and job summary; (3) a **state bundle** every job uploads as the Actions artifact `harness-state`: `status.json` (the job's registry record reduced to a fixed schema, plus the job's decision), the branch's clarification directory, `PAUSE_PROGRESS.md`, the walker state and the readable run log (Task 4). `remote-run.sh sync` downloads the latest bundle into the local mirror and updates the local registry record (Task 6); `branch-status`, `branch-answer`, `branch-resume`, `branch-pause` and `branch-user-review` sync a remote record before they read it (Tasks 22–23). Syncing is a read the user asks for, not supervision.
- **The walker state and the park-loop count survive a job boundary in the bundle, never in a commit.** `<state_dir>/.flow_walker_state` stays gitignored and is carried as a bundle file stored without its leading dot, because `actions/upload-artifact` skips hidden files by default (Task 4). The park-loop guard's count, `resume_max_question_index`, the auto-resume count and the stall-restart count ride in `status.json` and are seeded into the next job's registry record (Task 9). A clear taken locally (`PARK_LOOP_CLEAR` in the mirror) is carried to the job as the dispatch input `park_loop_clear` (Task 12). `<state_dir>/.dispatch_counter` needs nothing: every flow resets it on every session entry.
- **How a remote pause reaches a running job.** A running job cannot see a local file, and `GITHUB_TOKEN` can neither read nor write repository variables, so the pause travels as a workflow run: `remote-run.sh pause <branch>` dispatches the same workflow with `action: pause`, whose `run` job is skipped (no runner, no billed minutes) and whose run is named `harness pause <branch>` by the workflow's `run-name`. The running job polls its own workflow's run list for such a run created after a lower bound no later than the dispatch that created it — its own run's `createdAt` for a user's dispatch, the previous job's last poll (`control_polled_at`, carried in the bundle) for an automatic continuation — so a pause sent while the job is queued, or across a chained continuation, is not lost; it then drops `PAUSE` into its checkout (Task 10); the run then yields at its next clean checkpoint exactly as it does locally. **Stopping outright** is `remote-run.sh stop <branch>`. It first always dispatches `action: stop`, a jobless run titled `harness stop <branch>` that acts as a stop marker, then cancels the branch's queued and in-progress runs (Task 5). A cancelled job's chain stops because its re-dispatch step runs only under `!cancelled()`. A usage-paused run waiting for the poller has no job to cancel, and the marker is what reaches it: `continue` and `poll` neither dispatch nor enable the poller for a branch whose newest `harness stop` run is newer than its newest `harness run` run (Task 8). **The remote kill switch** is the repository variable `HARNESS_REMOTE_STOP`: any non-empty value makes every job and every poller tick exit before launching or dispatching anything. The local `AUTONOMOUS_STOP` still stops the local watcher from dispatching.
- **Runs longer than the hosted limit chain through the existing pause/resume, and the self-pause is disabled on self-hosted runners.** On a GitHub-hosted runner the workflow sets `REMOTE_SELF_PAUSE_AFTER_SECS`; job mode drops its own `PAUSE` at that point, the run yields at the next dispatch boundary, the job pushes, uploads the bundle and re-dispatches itself with `resume: pause`, and the next job resumes from the pushed ledger (Tasks 10, 8). The point is sized from a **measurement** Task 15 takes over this repository's real `harness-runs/autonomous_logs/*.stream.jsonl`: the longest single sub-agent dispatch, rounded up, plus a fixed epilogue allowance. Its command, its date and its figures are written into the template's header and restated in `docs/remote-execution.md`; the value is overridable through the repository variable `HARNESS_SELF_PAUSE_AFTER_MINUTES`. On a self-hosted runner the variable is unset, so the self-pause is **disabled rather than merely never reached** — its job cap is five days and a run of this repository has exceeded ten hours — and the step's own `timeout-minutes` is the backstop there as on hosted. A step that times out still lets the later `always()` / `!cancelled()` steps push, upload and re-dispatch, so a dispatch that overruns the margin costs its in-flight unit, never the run. Every automatic re-dispatch increments the input `chain`; at `HARNESS_MAX_CHAIN` (a repository variable with a default) the job stops chaining and notifies `failed`. A user's own dispatch resets `chain` to 0.
- **Resuming a usage pause without the local watcher.** The job's own usage gate (the watcher's, unchanged, with the machine lane off) pauses the run on its own stream. Then: on a **self-hosted** runner the job waits in-job for the reset while the wait fits inside its remaining time; on a **hosted** runner it waits in-job only when the reset is closer than `REMOTE_WAIT_MAX_SECS` (a new job's setup costs minutes and the poller's interval adds latency, so a short wait is cheaper in-job), and otherwise ends — billing stops with the job — after enabling the poller. The poller `harness-resume.yml` is a `schedule` workflow (every 30 minutes by default) that downloads each branch's latest bundle, dispatches `resume: pause` for every usage-paused run whose recorded reset has passed, and **disables itself** once none is left, so ticks are paid only while something is paused (Tasks 8, 16). Whether `GITHUB_TOKEN` with `actions: write` may enable and disable a workflow is **unverified**; if the enable fails the job says so in its `paused` notification — the run then waits for `/autonomous-sdlc-harness:branch-resume` — and Gate 12 records the answer (Task 31). An external scheduler and an environment wait timer are not built: the first adds a dependency outside GitHub, the second is fixed per environment rather than per run.
- **API errors: two failure shapes earn a bounded automatic resume in the job, and local runs gain nothing.** A session that exits non-zero (`failed`) and a session that self-paused on API overload (a `PAUSE_ACK` nobody requested) are resumed from the committed ledger after `REMOTE_AUTO_RESUME_DELAY_SECS`, at most `REMOTE_AUTO_RESUME_MAX` times per run, the count carried in the bundle and reset by any user action. Past the cap the run stays `failed` or `paused` and notifies. The CLI already retries transient API errors, so what reaches the job is either a transient outage (the resume helps) or a persistent fault such as a revoked credential (the cap bounds its cost). Local classification is unchanged.
- **Stalls.** The watcher's own `check_stalled_runs` runs in job mode unchanged (`STALL_WARN_SECS`, `STALL_KILL_SECS`, `STALL_MAX_RESTARTS` read from repository variables through the workflow's `env`), with the step's `timeout-minutes` as the backstop.
- **A killed job is handled generically and best-effort.** The autonomous forks already push after every commit point (`plugin/instructions/plan_orchestration_instructions_autonomous.md` → the **Post-commit push** paragraph), and the job adds one final `push-branch.sh` under `always()`; Task 28 records that finding. Job mode writes `status.json` with decision `continue` the moment it starts and rewrites it at the end, so a job killed mid-run leaves a bundle saying *continue* when the upload step still runs, and the next start — whoever makes it — resumes from the last pushed ledger with no cleanup. A `cancelled()` step sends a best-effort `failed` notification; nothing relies on it. No step checks GitHub account, billing or payment state.
- **The job's permission profile, plugin and credentials.** The job installs the plugin explicitly (`claude plugin marketplace add` from the committed `.claude/settings.json`, then `claude plugin install`), pinned to the version `init` rendered into the template — by a ref if the `claude` CLI's marketplace source accepts one (Task 15 measures its `--help`), otherwise by verifying the installed version and refusing on a mismatch. It then runs `npx autonomous-sdlc-harness@<that version> init --plugin-root-entries`, which generates the gitignored profile for the job's own checkout path **with** the `Read` / `Bash` entries for the plugin roots that install produced (Task 14), and fails loudly if `init` changed any tracked file. `doctor` then runs as a preflight. Adopter-tuned `allow` entries in the machine-local profile do **not** travel; an entry that names no absolute path can be moved into the committed `.claude/settings.json`, which the runtime merges beside `--settings`, and `docs/remote-execution.md` says so (Task 29). Credentials are the repository secrets `CLAUDE_CODE_OAUTH_TOKEN` (subscription) and `ANTHROPIC_API_KEY` (API); the job exports only the non-empty ones, fails before launch when neither is set, and billing follows the API key whenever both are present.
- **Docs retrieval in the job is cache restore.** When `retrievalApplies`, the workflow restores `${XDG_CACHE_HOME:-$HOME/.cache}/autonomous-sdlc-harness/retrieval/` with `actions/cache` keyed on the rendered CLI version, and `init` installs only what is missing. Because a cache saved on a feature branch cannot be read by its siblings, `remote-run.sh warm` dispatches `action: warm` on GitHub's default branch, whose job only provisions and saves the cache (Tasks 5, 15).
- **The task offer's answer 1 still holds, unchanged.** Its option says the request is *"Queued for the harness's run watcher"* and its caveat that *"the watcher does"* launch the run; with remote on, the watcher still consumes the drop and is what dispatches it. The remote job never reads the offer. `cli/templates/claude/harness-task-offer.md` is a `no-change` row in the register below and Task 28 records the check.
- **The leads this planning session could not re-verify.** This session has no web access, so the vendor leads the prompt lists — hosted and self-hosted job limits, runner prices and included minutes, the postponed self-hosted platform fee, the Hetzner price, the subscription-token and billing-precedence rules, the paused Claude billing change, the `GITHUB_TOKEN` event exceptions — are **not** re-verified here. No design decision rests on a price. The decisions that rest on a GitHub behaviour (the dispatch exception for `GITHUB_TOKEN`, the 6-hour hosted cap, `gh workflow enable` under `GITHUB_TOKEN`, a skipped job costing nothing, `timeout-minutes` accepting an expression) are each exposed as a tunable or a degradable path, and Gate 12 (Task 31) is the hand-run that records each against a real repository. Tasks 28–29 carry every figure with its source URL and the prompt's retrieval date, labelled as carried from the prompt's research unless the implementer re-fetched it.
- **This repository's own `scripts/` copies are `init`'s output and are not edited.** Every script change lands in `cli/templates/scripts/`; `scripts/run-gates.sh` is hand-written and Task 31 edits it. `examples/notes-app/` is a frozen capture and nothing here touches it.
- **Output and spelling rules.** CLI output stays plain ASCII. Every slash command written anywhere carries the plugin prefix (gate 6d). Every command an adopter is meant to run sits in a fenced block, one command per line (`harness-runs/lessons.md`). No line number is written into any durable artifact.

**Top risks:** The likeliest failure is a remote run that looks started and never runs, or runs and never reports: a dispatch that `gh` accepted for a workflow GitHub cannot find on its default branch, a job that stalls on a permission prompt because its profile lacks the plugin-root entries, or a bundle nobody can read. Task 19's online check asks GitHub whether it knows the workflow, Task 14 is asserted against a planted plugin install, the workflow's `init` step fails on any tracked-file change, and the job's `doctor` preflight fails the job before launch rather than mid-run. The second risk is a chain that never stops — a re-dispatch after the user cancelled, or an endless resume of a run that keeps failing: re-dispatch runs only under `!cancelled()`, every automatic dispatch counts against `HARNESS_MAX_CHAIN`, auto-resume counts against `REMOTE_AUTO_RESUME_MAX`, and `HARNESS_REMOTE_STOP` stops every start; Task 8's suite drives each stop condition. The third is a local path silently changed for adopters who never opt in: every watcher and `init` change is gated on `execution.target`, and Tasks 11, 12 and 17 each assert the local path byte-for-byte unchanged with the key absent. The fourth is that the design-bearing GitHub behaviours are only as verified as Gate 12's hand-run, which this branch documents but does not execute.
