# Task plan review — iteration 0

## Must Fix

1. **`task_5_plan.md` — the wait-bound case, as specified, never reaches the bound it exists to prove**
   The second Work bullet (*"Job mode, the wait bound."*) gives the case only `Env: REMOTE_WAIT_MAX_SECS: '2'`. `createJobFixture`'s `jobEnv` (`cli/test/watcher-remote-job.test.mjs`) does not pin `USAGE_RESUME_MARGIN_SECS`, so the watcher default applies: `USAGE_RESUME_MARGIN_SECS="${USAGE_RESUME_MARGIN_SECS:-120}"` (`cli/templates/scripts/autonomous-watcher.sh`, usage tunables block). `usage_assess` therefore records `usage_resume_at` = reset + 120, about 121 s ahead. On the first pass through the `usage)` arm, `job_usage_wait_ok` evaluates `[ $((ra - $(date +%s))) -le "$REMOTE_WAIT_MAX_SECS" ]` → `121 <= 2` → false. The job ends `wait-poller` through the **existing** path, with the existing detail (*"usage limit reached — resumes automatically after …"*). It never waits, so the new bound never fires, and the case's assertion (the last `paused` notification names the bound and `/autonomous-sdlc-harness:branch-resume feat_x`) cannot pass. The prompt's criterion *"bound the `usage` arm's in-job wait … whether or not the value was lost"*, and this task's own Goal (*"prove that the in-job wait bound fires even when the value was not lost"*), are then left unproven. The file's other job case and both existing `usage:` cases each pin `USAGE_RESUME_MARGIN_SECS: '0'` explicitly, which shows the omission is not intentional.
   The interval also matters. With `USAGE_CHECK_INTERVAL_SECS` left at its default of 60, the gate does not run again inside the 2 s bound, so `usage_resume_at` is still set when the bound fires. With it at `'1'`, the gate's own resume drops `RESUME` and clears `usage_resume_at` before the bound. The plan has to say which of these two paths the case drives.
   **Fix:** In `task_5_plan.md`'s wait-bound bullet, set the env to `USAGE_RESUME_MARGIN_SECS: '0'` and `REMOTE_WAIT_MAX_SECS: '2'`, and state `USAGE_CHECK_INTERVAL_SECS` deliberately: either leave it at its default so the bound fires before any gate resume, or set it to `'1'` and assert what the bundle then carries. Also add an assertion that the job logged *"waiting in the job"* before the bound fired, so a regression back to the immediate `wait-poller` path fails the case instead of passing it.

## Should Fix

1. **`task_4_plan.md` — the bound path can give the poller a bundle it will never act on.** The bound fires on a record that is still `paused` after `usage_gate` and `resume_paused_runs` have both run. If the gate's own resume has already dropped `RESUME` and cleared `usage_resume_at`, and the relaunch was deferred (for example by the kill switch, which is how Task 5 drives this case), the job ends `wait-poller` with an empty `usage_resume_at`. `remote-run.sh` → `poll` then answers *"is usage-paused with no readable usage_resume_at; skipped"* on every tick. Task 3 calls that arm a corrupt-bundle guard, but this path reaches it by design. The notification does name `/autonomous-sdlc-harness:branch-resume`. A cheap repair is also available: on the bound path, write the captured `ra` back to `usage_resume_at` before `job_write_status`. That value is already in the past, so the poller re-dispatches on its next tick. State the chosen behaviour in the `usage)` bullet and in Task 5's wait-bound assertions.

2. **`task_1_plan.md` — the stale-lock breaker copies a shape whose aside name is `$$`-keyed, and only one breaker is tested.** `hr_lane_acquire` renames the stale lock to `"$lock.stale.$$"`. The plan correctly rules `$$` out for the owner token, because it is the parent's pid inside `spawn_engine`'s subshell. But "the stale-breaking shape `hr_lane_acquire` already uses", copied literally, gives the watcher and its own subshell the same aside name. The story index's `Top risks:` names *"two breakers of one stale lock"* and *"a subshell sharing its parent's `$$`"* as risks Task 1 guards, yet case (c) has one breaker only. Suggested changes:
   - Key the aside name on the per-call token too.
   - After the rename, confirm that the aside's owner is the stale owner that was read. If a fresh owner was moved aside, restore it or give up.
   - Add a case in which two processes break one planted stale lock at once and every write still lands.

   Separately, `hr_lane_mtime`'s comment says it is *"The only `stat` in this file, and it exists for one case"*. Reusing it for the registry lock makes that false, so add that comment to Task 1's `### Targets`.

3. **`task_6_plan.md` — the 300 s sizing argues from the whole-suite figure, but the timeout also applies to parent tests.** `--test-timeout` sets the default timeout that every test inherits, and that includes a top-level `test(…)` whose subtests run in sequence. Several suites group many watcher cases under one parent, for example `watcher-remote-job.test.mjs`'s `usage:` and budget groups. The limit therefore bounds the longest *parent* test on the slowest supported runner, not "a single honest case". The recorded 118 s is concurrent wall time on 10 cores. Serial time on that host is 170 s, and a hosted 2-core runner may be several times slower. Restate the argument in terms of the longest parent test. Say whether the file-level test inherits the limit on the Node versions in use. Choose the value with margin against a slow runner, and carry the same argument into Task 8's Gate 4 paragraph.

4. **`task_6_plan.md` — the hung-watcher child's 3 s timeout also covers building the fixture.** The child's single test builds a watcher fixture (`init` plus git), writes the fixture path, and only then starts `watch`. All of that runs under `--test-timeout=3000`. Under gate-4 load, the fixture can take more than 3 s to build. The child then times out before the path file is written, and `pgrep -f <child fixture path>` becomes vacuous or cannot run. Build the fixture in a `before` hook, or give the child a larger test timeout plus an explicit `timeoutMs` that starts after `watch` is launched. Have the parent assert that the path file exists before it runs `pgrep`.

5. **`task_2_plan.md` — the plan leaves open removing the stub's sleep in `cli/test/helpers/watcher.mjs`, and every watcher suite depends on that sleep.** Choice 1's sleep is shared by every suite that calls `tick`. Under `## The test-run rule`, Task 2 may run none of those suites, so a regression from dropping the sleep would first show up at Phase G. Have Task 2 keep the sleep and only rewrite the reason it states. Leave any change to the sleep's duration to a later task that can observe its effect.
