# Task plan review — iteration 0

## Must Fix

1. **CS6's index check counts the wrapper's own index sync as `git add` getting through** — `task_9_plan.md` (follows into `task_21_plan.md`)
   Task 9 takes the index `shasum` once before the `job-layout` session and once after it. Between those two readings the same session runs `git add sbx_cs6.txt` and then `commit-on-branch.sh --repo <job> sbx_cs6.txt`. On a main-checkout target the wrapper runs outside the sandbox. It writes through `GIT_INDEX_FILE="$wt_gitdir/index"`, which is `<job>/.git/index`, and after the commit it syncs that index (`cli/templates/scripts/commit-on-branch.sh` → `wt_git()` and the *"the index of '$top' could not take the committed paths"* message, plus the header's *"the commit's index sync"*). So when CS6 behaves as expected (the `git add` is refused and the wrapper lands), the index still changes. `<index sum unchanged>` is then `0`, and `sp__cs6_grade`'s second arm prints `fail`, *git add reached the checkout's index*. The grade can never print `pass` for the outcome the row expects. That breaks the ledger rule the plan says it honours (register row 36): *"Grade a write probe on what reached the disk, never on the call's exit status."* The disk reading is taken across a second, legitimate writer.
   **Fix:** In `task_9_plan.md`, measure `git add`'s effect before the wrapper runs. Run `git status`, `git add sbx_cs6.txt` and the `written` control in one session. Take the index `shasum` and `git diff --cached --name-only` from outside. Then run the wrapper call in a second session, each call with its own exact rule, and grade the ref and the `diff-tree` change set after it. Keep `sp__cs6_grade`'s arguments as they are, but state that the index readings bracket the first session only. Update the signature restatement and the `fail` and `pass` fixtures in `task_21_plan.md` to match.

2. **The workflow and the local CS6 recipe check out GitHub's default branch, but job-mode preflight requires the configuration's `defaultBranch`** — `task_14_plan.md`, `task_15_plan.md`
   Job-mode check 3 runs *"as today"* (`task_3_plan.md`). Today's check refuses a checkout that is not on `hr_default_branch`, which is `harness.config.json` → `defaultBranch` (`scripts/lib/sandbox-probe/preflight.sh`, check 3: *"the main checkout … is on '…', not the default branch '…'"*). Task 14 checks the checkout out at `ref: ${{ github.event.repository.default_branch }}`, and Task 15's local recipe is a bare `git clone <origin url> <job>`, which lands on the remote's default branch. The job template itself treats these as two different values: `Record the default branch's commit` reads `HARNESS_GITHUB_DEFAULT_BRANCH` and the configuration's `defaultBranch` separately. They do differ in this repository: `defaultBranch` is `dev` while the GitHub default is `main`, and `main` carries no `scripts/` (`scripts/publish-main.sh`). So Task 15's recipe is refused at preflight, or finds no watcher. The workflow is refused the same way in any Gate 12 repository whose two values differ, and the plan never establishes that Gate 12's are equal.
   **Fix:** In `task_14_plan.md`, after the checkout, switch the working tree to the configuration's `defaultBranch` (read from `harness.config.json` with `jq`, fetched from origin). The step refuses, naming both values, when that branch is missing. Alternatively, keep the checkout and state why Gate 12's two values are equal, with a step that fails when they are not. In `task_15_plan.md`, add `--branch <defaultBranch>` to the clone line, naming `dev` for this repository, and state that the clone must sit on the configured `defaultBranch` for job-mode preflight.

3. **L1's fail arm leaves a `-sbxdash` branch on origin that teardown never removes** — `task_13_plan.md`
   The L1 call is `push-branch.sh`, which `excludedCommands` runs outside the sandbox. If the dash check does not answer, the push lands on origin. That is the `fail` arm *"the remote ref appeared → the push landed"*. `sp__pf_l1_restore` puts `HEAD` back and deletes only the **local** `refs/heads/-sbxdash`. Nothing removes the remote ref, so the Gate 12 origin, or this repository's origin under the local recipe, keeps a branch the probe caused. This repeats the ledger lesson *"A script that creates a temporary working copy or branch removes it on every exit path, success and failure alike, and never removes one it did not create."* (`harness-runs/lessons.md`, Remote and branch-scoped operations). Register row 41 says the lesson is honoured for L1's `-sbxdash` ref, and it is not.
   **Fix:** In `task_13_plan.md`, extend `sp__pf_l1_restore` so it also deletes the remote ref when step 1 found it absent on origin and it is present now. Use the refspec form `git -C "$SP_MAIN" push origin :refs/heads/-sbxdash`, because a dash-leading name cannot go through `--delete`. Do this only when the remote tip equals the commit the probe gave the local ref. On failure, return 1 naming the hand command. Register this through `sp_restore_register` before the session, so an interrupted run removes the ref too. Add the remote-removal case to `task_21_plan.md`'s `sp__pf_l1_restore` subtest.
