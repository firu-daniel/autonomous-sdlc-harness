## Must Fix

1. **The `<main_repo>` redaction never fires on a real run, because every run copy is a clone** — `task_3_plan.md` (the story index's `## Context` makes the promise).
   The Context promises: *"the run copy's root becomes `<repo_root>`, the main checkout `<main_repo>`"*. Task 3 → **Paths through the run library.** gets the main checkout from *"`hr_main_repo`'s answer for the checkout (when it differs)"*. The two do not fit together:
   - `cli/templates/scripts/lib/harness-run-lib.sh` → `hr_main_repo` says in its own header: *"Inside a clone it answers the clone itself."*
   - `cli/templates/scripts/create-worktree.sh`'s header says: *"Every copy it makes is a clone (`hr_clone_create_var`: `git clone --shared` …)"*.
   
   So on every local run, `hr_main_repo` returns the copy's own top. The pair is then skipped as "not different", and the main checkout's path is never mapped to `<main_repo>`. That path does appear in the stream: `spawn_engine` exports `HARNESS_MAIN_REPO="$MAIN_REPO"` and passes `--add-dir "$main_state"`, and every wrapper call an agent makes goes through `<MAIN_REPO>/scripts/…`. With the pair skipped, only the generic `/Users/<segment>` → `~` fallback runs. The committed `.json` and `.md` then hold home-relative machine paths such as `~/Work/<repo>/scripts/commit-on-branch.sh`. That breaks the prompt's constraint: *"record repo-relative or `<state_dir>`-relative paths only, and no usernames or home directories"*. Gate 6a will not catch it, because it greps for the literal `$HOME` only (`scripts/run-gates.sh`, the comment above the 6a scope). Task 6's fixture repository is a plain checkout, so the suite cannot catch it either.
   **Fix:** In `task_3_plan.md` → **Paths through the run library.**, take the main checkout from `HARNESS_MAIN_REPO` when it is set and non-empty, and fall back to `hr_main_repo` only otherwise. `spawn_engine`'s subshell exports `HARNESS_MAIN_REPO` before the call Task 5 adds, so the script inherits it. State this source in the header's tunables paragraph. Add a `**Verification:**` probe that sets `HARNESS_MAIN_REPO` to a directory other than the checkout, puts that path in a command, and shows `<main_repo>` in the output. In `task_6_plan.md` → **Idempotence, refusal and redaction**, add the same case: a second fixture path passed as `HARNESS_MAIN_REPO`, found in neither output and shown as `<main_repo>`.

2. **The watcher suite's commit case cannot produce a commit on `feat_x` with the fixture it names** — `task_7_plan.md`.
   The plan builds the fixture with `createWatcherFixture` and seeds a parked record with `seedRecord` and its defaults. `cli/test/helpers/watcher.mjs` → `seedRecord` defaults `worktree: dir`, which is the fixture's main checkout. Here it returns `1` (*"'<branch>' has no commit yet — refusing to commit"*), or `2` once the branch has a commit (*"branch … is protected"*). So no `chore: Record run analytics for feat_x` commit can exist, and the commit and re-run cases fail as specified. The suites that do assert a watcher commit build a different fixture. `cli/test/watcher-run-profile.test.mjs` → `adoptedFixture` commits the adoption and pushes the default branch, then gives the run a clone copy on the branch (the inbox drop path, `copy_kind: 'clone'`). `cli/test/watcher-review-drop-payloads.test.mjs` uses the same shape.
   **Fix:** In `task_7_plan.md` → the scaffolding bullet and **Commit case**, build the fixture the way `adoptedFixture` does: commit the adoption, push the default branch, and run the session in a copy on `feat_x` that has a commit. Then assert the commits with `git log` on `refs/heads/feat_x` in the copy, and in the main checkout after `classify_run_exit`'s sync. The re-run and failure cases re-seed the same copy.
