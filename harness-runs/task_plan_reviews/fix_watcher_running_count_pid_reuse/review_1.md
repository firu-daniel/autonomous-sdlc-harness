# Task plan review — iteration 1

## Must Fix
1. **`remote-run.sh stop` is excluded from the terminal-write set because it supposedly acts only on remote records, and the tree says it does not** — `task_1_plan.md` (the `### The terminal writes, and what each one does` table and the paragraph below it). The fix also reaches `task_3_plan.md` and the story index (`fix_watcher_running_count_pid_reuse_story_plan.md`) → `## Context`.
   Task prompt → `## The goal` → item 2: *"A run that reaches a terminal status drops its `pid`, wherever a run reaches `completed` or `failed`"*. Task 1 leaves out `scripts/remote-run.sh`'s `status failed` writes with this reason: *"(`stop`, and `sync`'s no-bundle case) act only on remote records, which `hr_remote_record_init` writes with `pid ""`"*. That holds for `sync`: `cli/templates/scripts/remote-run.sh`'s verb gate, `status|sync)`, refuses a record that does not carry `execution: github-actions` (*"refused, nothing written: the local record of '$branch' does not carry execution: github-actions"*). It does not hold for `stop`. `stop` reaches the `*)` arm, which tests only `execution.target`. `verb_stop` then writes `hr_registry_set "$registry" "$branch" remote_stopped_at "$stopped_at" status failed` to any existing record of that branch, whatever its `execution` field. A record keeps the execution it started with (remote-run.sh header: *"A run keeps the execution it started with"*), so a local record holding a `pid` can exist under a repository whose target is now `github-actions`. `cli/test/registry-writer.test.mjs` → *"a remote-run.sh stop racing the watcher's writes loses neither, every round"* runs exactly that case: its record `{ branch: 'feat_x', status: 'running' }` has no `execution` field, and the test asserts `status` becomes `failed`. So this is a reachable `failed` write on a local record that keeps its `pid`, and the plan excludes it on a premise the code contradicts.
   **Fix:** In `task_1_plan.md`, move `verb_stop`'s write out of the "out of this task" paragraph and into the terminal-write table as `hr_registry_set "$registry" "$branch" remote_stopped_at "$stopped_at" status failed pid ""`, with the clear in the same call, per the plan's own ordering rule. Place it in a `cli`-layer task: add `cli/templates/scripts/remote-run.sh` to that task's `### Targets`. Task 2 is the natural home if Task 1's 20 points cannot absorb it. Name the case its suite drives, or the reason it is not driven. In `task_3_plan.md`, add `scripts/remote-run.sh` to `### Targets`, `**Work:**` and the `cmp` verification, so the root copy stays byte-identical to its template (the two are identical today), and keep that file's mode. Keep the `sync` exclusion, restating its real reason: the `status|sync)` gate refuses a non-remote record. Update the story index's `## Context` paragraph on the layers and byte identity so it names the second root copy.
