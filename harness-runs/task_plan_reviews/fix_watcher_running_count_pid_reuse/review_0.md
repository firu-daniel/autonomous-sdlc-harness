# Task plan review — iteration 0

## Must Fix
1. **Refusal 4 is tested on a `completed` record only, but the prompt asks for both `completed` and `failed`** — `task_2_plan.md`.
   Task prompt → `## The goal` → item 5 lists the cases. The first is *"a `completed` and a `failed` record whose `pid` is a live process (the test's own child) are not counted"*. It then requires *"the probe's refusal 4 does not fire on the first case"*. So "the first case" covers both records. Task 2's first new subtest (**4. a finished run whose pid is a live process is not in flight**) seeds *"One record with `status: 'completed'` and the child's pid"*, and no subtest in Task 2 seeds a `failed` record. The `failed` half of the refusal-4 requirement therefore maps to no per-task file. Task 1's `watcher-running-count.test.mjs` covers `failed` only at the `running_count` level, not through the probe's preflight.
   **Fix:** In `task_2_plan.md` → `**Work:**` → the first subtest bullet, seed **two** records: one `status: 'completed'` and one `status: 'failed'`, under two different branch keys, each holding the live child's pid. A single child can serve both, or use one child per record. Keep the assertions as they are: exit `0`, no `sandbox-probe: ` line, and `probeLeftovers(tmp)` is `[]`. Alternatively, add a third `4.` subtest for the `failed` record. Update the subtest title and the `**Verification:**` bullet to match.

## Should Fix
1. **The plan does not say whether a fast-exiting session can leave a terminal record with a stale `pid`** — `task_1_plan.md`.
   `spawn_engine` writes `registry_set "$branch" pid "$!"` in the parent after `) &`. `classify_run_exit` runs inside the backgrounded subshell, and after this task it writes `status completed pid ""` / `status failed pid ""`. If the subshell reached `classify_run_exit` before the parent's `pid "$!"` write, the record would end `completed`/`failed` with the dead subshell's pid. That would break goal 2 (*"A run that reaches a terminal status drops its `pid`"*). In practice the parent's write comes microseconds after the fork, while the subshell must first run the engine pipeline and `record_run_analytics`, so this is very unlikely. Goal 1's filter would also make such a record harmless. The plan's `### Why `running` alone holds a slot` section and the index's `Top risks:` cover only the reverse ordering, a late clear wiping a new pid.
   **Fix:** Add one sentence to `task_1_plan.md` (and to `running_count`'s planned comment, or the `pid` field-list entry) stating this ordering and why it is acceptable: goal 1's status filter covers any terminal record that keeps a pid.

## Nice to Have
1. **`print_status` renders a cleared pid as `pid=`, not `pid=-`** — `task_1_plan.md`.
   `print_status`'s jq uses `pid=\(.value.pid // "-")`. `//` substitutes only for null or false, so a terminal record that now carries `pid: ""` prints `pid=` where an absent pid printed `pid=-`. It is cosmetic. The plan could name it, or decide not to touch it, so the implementer does not have to guess.
2. **"Only `classify_run_exit` moves a record off `running`" reads as unqualified in `task_1_plan.md`.** `reconcile_stale_runs`, the stall watchdog's give-up arms, `fail_before_launch` and `spawn_refused` also write `failed` to a `running` record. The story index qualifies the claim (*"a record whose pid is a live session subshell"*), but the per-task file does not. Copy that qualifier into the per-task file so the comment Task 1 writes does not inherit the unqualified form.
