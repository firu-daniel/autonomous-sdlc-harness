# task_plan_reviews/

One `<branch>/review_<n>.md` per planning **round**, holding the plan-gate review of the task plan. `<n>` is the round number, shared by every plan gate's folder: round `<n>`'s files sit at the same index here, in `architecture_reviews/` and, while the parity phase is on, in `business_parity_reviews/`. Every reviewer runs in every round, so the numbers in one directory are consecutive — a gap is a file that went missing.

A file here is written by the plan reviewer and read by the plan writer on the next round, together with every other gate's file of that round; the writer applies the Must Fix items to the story index or to the named per-task files. The reviewer writes its file on `PASS` as well as on `FAIL`, and each file carries exactly one `verdict:` line — so a file is no longer a failed round, and the number of failed rounds is the number of `verdict: FAIL` lines, not the number of files.

Files stop when the loop ends — at a round every gate passed, or at the iteration cap, where the flow halts and reports the closing round's paths. A file is replaced only by its own reviewer re-running a round that was interrupted; otherwise nothing supersedes an earlier file, the accumulated set is the record of how the plan converged, and the whole directory is committed with the branch, since no ignore rule reaches it.

The mistake worth naming is a second pass over the same branch that inherits the first pass's "start at zero". It writes over `review_0.md` instead of beside it, the earlier round's findings are gone, and the commit records the loss as an ordinary modification to a file that already existed — so nothing flags it, and the convergence history reads as one round shorter than it was. The walker's `start` prevents it by continuing the round numbering from the round files already on disk, even though the loop counter — which drives only the cap and the review mode — starts at `0` on every `start`.
