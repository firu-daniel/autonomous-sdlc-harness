4. **In a clone, the flows' Phase D push-state read always reports "nothing was pushed"** — story index (`feat_clone_per_run_switch_story_plan.md`) and `task_7_plan.md`, Completeness (goal 4, branch visibility).
   Both Phase D cores take the push state from *"the **first line** of one plain, single-statement **bare** `git status -sb`"*, issued in the run copy: *"**no `...<upstream>` at all** means the branch has no upstream and nothing was pushed"*.
   - A clone's `.git/config` holds only the keys in `hr_clone_config_spec` (`cli/templates/scripts/lib/harness-run-lib.sh` → *THE CLONE CONFIGURATION ALLOW-LIST*), and the clone trust check refuses any other key.
   - That allow-list has no `branch.<branch>.remote` or `branch.<branch>.merge`.
   - Task 7 puts the upstream in the main checkout's `.git/config` only (*"so … the upstream lives in the main `.git/config`"*).
   So every clone run's hand-off line would report an unpushed branch. Under the worktree layout, the same command read the shared config and reported correctly. No task covers this regression.
   **Fix:** Settle it in a task. One option is a `cli` change. Admit exactly the run branch's own `branch.<branch>.remote` / `.merge` into the clone allow-list. That is Task 1's file, so the change goes in Task 1 or a split of it. Write the keys at creation (Task 7) and assert them in the trust-check suites. The other option is a `plugin` task (the task from finding 3) that rewrites both **Branch delivery** bullets to a push-state read that holds in a clone, for example a count against the clone's mirrored `origin/<branch>`. In either case, add a case or a verification step that shows the clone answer matches the worktree answer.
