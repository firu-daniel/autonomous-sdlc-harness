# Task plan review — iteration 0

## Must Fix
1. **Task 3 spells `HARNESS_CLI_VERSION` as a literal in a message and never restates `CLI_VERSION_VARIABLE`** — `task_3_plan.md`.
   The first `**Work:**` bullet has doctor push a `notes` entry *"saying which version the workflow was rendered for could not be read, because it carries no `HARNESS_CLI_VERSION` line"*. That is a message naming an environment-variable name to a reader. `.claude/context/conventions.md` → `## Configuration is the source of truth, and it is read at run time` requires such a name to be read through its owning constant, *"never retyped as a literal — including in the message that names it to a reader"*. Task 1 creates that constant, `CLI_VERSION_VARIABLE = 'HARNESS_CLI_VERSION'` in `cli/src/remote/githubActions.ts`. Task 1's first bullet also says *"Nothing else in `cli/src` may spell this variable as a literal after this task"*, and its Verification checks this with `git grep -n "HARNESS_CLI_VERSION" -- cli/src`.
   Task 3's `**Depends on:**` restates only `renderedCliVersions` and `upgradeWorkflowsCommand`. An implementer who reads only this file therefore has no way to know the constant exists. They will type the literal into `cli/src/doctor/checks.ts`, which breaks the convention and Task 1's invariant. This is a cross-task interface Task 3 consumes without restating it, so the file is not self-contained.
   **Fix:** In `task_3_plan.md`, add to `**Depends on:**` the line `From cli/src/remote/githubActions.ts: CLI_VERSION_VARIABLE ('HARNESS_CLI_VERSION')`. Change the notes bullet so the message names the variable through `${CLI_VERSION_VARIABLE}`, never as a literal. Add a `**Verification:**` bullet: `git grep -n "HARNESS_CLI_VERSION" -- cli/src/doctor` returns no hits outside doc comments.
