1. **`task_3_plan.md`, `task_5_plan.md`, `task_9_plan.md`, `task_19_plan.md`: on Linux the `unrecognised` layer turns N3's and N4's grading into `not run`, and the LB grades contradict their own fixtures**
   Task 3 puts the `unrecognised` arm in `sp__judge_matched`, so it applies to **every** `sp_judge_call … network|sandbox` on Linux. Its four conditions are: Linux, expected `sandbox`/`network`, layer `ran`, and `SP__STATUS` `error`. When they hold, it sets `SP_VERDICT="not run"`. Two existing network grades read a plain curl error as their *data*, not as a refusal string:
   - `scripts/lib/sandbox-probe/legs-network.sh` → `sp__net_n3_grade` calls `sp_judge_call "$stream" network "$cmd"`, then `[ "$SP_VERDICT" = "not run" ] && return 0`. Its pass case is `no body came back while the listener answered the probe: <curl line>`. On Linux, a direct `curl: (7) Failed to connect …` to `127.0.0.1` is the outcome the plan itself expects: Task 19's `lb-session` fixture models exactly that line for `--noproxy`. That outcome now becomes `not run`, so N3 is never measured.
   - `sp__net_n4_grade` has the same early return. Its whole design is the comparison of the session's `curl: (<n>)` code with the unsandboxed control (the `*)` arm, `SP__STATUS = error`). That arm becomes unreachable on Linux, because a session curl error with no proxy string is `unrecognised` → `not run` before the comparison runs.

   The task prompt requires both: *"N4 is graded by comparison"* and *"link-local (N4): as on macOS, by comparison with the unsandboxed control"*; and N3 is *"to be measured, not asserted"*. Task 11 repeats both as Gate 15 expectations. Task 5's list of *"the legs that branch on a refusal's layer or text"* names four and omits these two.

   The LB grades have the same gap. `task_9_plan.md` → `sp__lb_grade` never says which layer it judges each curl call at. It is `not run` whenever a call *"got the judge's own `not run`"*. `task_19_plan.md` expects `lb-session`'s `127.0.0.1` pair (`--noproxy` → `Exit code 7\ncurl: (7) …`) to grade `pass` with `--noproxy: no body: curl: (7) …`. That holds only if `sp__lb_grade` judges at `ran`, or handles `unrecognised` itself. Judged at `network`, Task 3 makes it `not run`, and Task 19's own run fails.

   **Fix:**
   - In `task_5_plan.md` (or a new single-layer `general` task before Task 11), give `sp__net_n3_grade` and `sp__net_n4_grade` an `unrecognised` handling that falls through to their existing curl-line logic. N3 then grades on the body and N4 on the comparison with the control, so neither stops at the judge's `not run`. Keep both byte-identical on macOS.
   - In `task_3_plan.md` → `Where this task stops`, name these two grades among the callers a later task adapts.
   - In `task_9_plan.md`, state the layer `sp__lb_grade` and `sp__lb5_grade` judge each curl call at. Use `ran`, reading the outcome from the result text, or else state how `unrecognised` is handled. Restate that layer in `task_19_plan.md` → `**Depends on:**`.

3. **`task_9_plan.md`, `task_19_plan.md`: LB5 can record "unreachable" for a listener that is no longer running**
   `sp__lb5_grade` is `not run` only when the start call was refused or not issued, or printed `sbx_lb5_no_listener`. Every other outcome is `pass`, and an outside `curl: (7)` gives *"unreachable from outside the sandbox"*. The listener is started inside a sandboxed call under `timeout 60`, and the outside requests are made only after session C ends. Two cases therefore read as "unreachable" when the listener is in fact gone:
   - the session outlasts 60 s;
   - the sandbox's process lifetime ends the listener with the call or the session. That is exactly the question BG9 measures, and its answer is unknown on Linux.

   N3 has a rule for this: no body counts only *"while the listener answered the probe's own request"* (`legs-network.sh` header). LB1–LB4 inherit that rule through `<listener answered>`; LB5 has no counterpart. This is the story index's own third Top risk, *"A Linux leg passes on a call that never ran"*. It would also seed a false answer for `docs/cli.md`'s *"`qa` is unmeasured."*, which Task 21 says LB5 measures.
   **Fix:** In `task_9_plan.md`, confirm from outside that the listener is still alive at the time of the outside requests. One way is a bounded `pgrep -f` on its unique `<clone>/sbx_lb5_www` argument, or another check the writer names. Pass that as an argument to `sp__lb5_grade`, which grades `not run` (*"the listener was no longer running when the probe called it"*) when it is gone. Say in the header how the 60 s bound relates to the session's length. In `task_19_plan.md`, restate the new signature and add the dead-listener case.

4. **`task_7_plan.md`: RG3's restore runs on the normal path only, not on every exit path (lessons ledger)**
   `harness-runs/lessons.md` → *Remote and branch-scoped operations*: *"A script that creates a temporary working copy or branch removes it on every exit path, success and failure alike, and never removes one it did not create."* RG3's session may move the **live** `<main>/<stateDir>/autonomous_logs` to `<dir>.aside` and create an empty `<dir>` holding a zero-byte `registry.json`. Task 7 calls `sp__rg_restore` only *"right after the session, before grading"*, and its `### Targets` is the one new file (*"edits nothing else"*). The probe's exit and signal path is `session.sh` → `sp__on_exit` / `sp__on_signal` / `sp_teardown`. It knows nothing of the `.aside`, so an interrupt or a crash during or right after the `registry-rg3` session leaves the main checkout's run registry displaced. The plan claims the opposite: Scope register row 45 says *"honoured … RG3's directory is restored at once (Tasks 6–10)"*. The story index's second Top risk names this exact state change.
   **Fix:** In `task_7_plan.md`, register the pending restore before the `registry-rg3` session launches, so the probe's teardown and signal path runs `sp__rg_restore` too. For example, add a pending-restore variable that `sp_teardown` consults. Add `scripts/lib/sandbox-probe/session.sh` to Task 7's `### Targets` if that is where the hook lands. In `task_18_plan.md`, add a case that drives the teardown path with a pending `.aside`. Then correct Scope register row 45's reason in the story index.

## Should Fix

1. **`task_8_plan.md`: `SP_BG9_SECONDS=20` may be shorter than the `detached` session itself.** The worker starts at the session's first call. A headless session that then issues the control `dd` can run past 20 s. The worker then finishes inside the session, its last beat is at or before the session end, and `sp__bg9_grade` falls into *"anything else → not run"*. BG9 would then never be able to show *"outlives the call and the session"*. Size the bound from the session, for example a worker that runs until a stop file the probe writes after the session ends, bounded by a deadline. Or state why 20 s exceeds the expected session length.
2. **`task_11_plan.md`: the recipe does not say what to do when refusal 6 fires on the AppArmor answer.** `doctor`'s `sandbox-prerequisites` warns *"in both modes"* on an uncertain AppArmor answer (`docs/cli.md`, the `sandbox-prerequisites` bullet). Inside a container, the sysctl `doctor` reads is the colima VM kernel's. If that VM enables `kernel.apparmor_restrict_unprivileged_userns` and the container has no `/etc/apparmor.d/bwrap`, `run`'s refusal 6 refuses and no Linux leg runs. The recipe should name this case and the step that clears it. It should also say that step, and the sysctl's value, go into the §8 stamp.
