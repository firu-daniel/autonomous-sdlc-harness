# Task plan review — iteration 0

## Must Fix

1. **`task_1_plan.md` asks for an unsandboxed measurement the implementing run cannot take**
   The `**Header — SIGNALS.**` Work bullet says: *"Re-measure the shape on the worker, unsandboxed, bash 3.2 if available, exactly as the existing paragraph was measured, and record what you observe."* An unattended implementer cannot do that. Every Bash call it makes runs inside the OS sandbox: `cli/templates/claude/settings.autonomous.json` sets `"allowUnsandboxedCommands": false`, and its `_README` says *"with `allowUnsandboxedCommands` false the `dangerouslyDisableSandbox` parameter is ignored"*. A supervised implementer would hit the same limit wherever the sandbox is on.
   So the bullet leaves the implementer two choices. It can block, which stops the branch at its first task. Or it can write observations into the wrapper's header that it never took the way the header says they were taken, which is the fabricated-evidence failure `.claude/context/conventions.md` → `## Documents of record` (*"A measured fact states what was measured, the command and the exact message"*) exists to prevent.
   The bullet also matters beyond the header. Task 2 asserts *"what Task 1's `SIGNALS` paragraph records"*, and this repository's Phase G runs that suite **sandboxed**. An unsandboxed observation is therefore the wrong baseline for those assertions even if someone could take it.
   **Fix:** In `task_1_plan.md`, have the implementer measure the four cases inside **one** sandboxed Bash call. That is the shape Task 2's suite runs in: the test process signals a worker that its own descendant started, within the same call. The header records what was observed, the date, the bash version, the Claude Code version, and that the measurement was taken sandboxed within one call.
   For any case the sandbox refuses, have the implementer record the refusal message verbatim instead of an outcome. Remove "unsandboxed" and "exactly as the existing paragraph was measured" from the bullet.
   Alternatively, move the unsandboxed re-measurement to the story index's `Manual setup required:` list and scope the header paragraph to what was actually observed. If you take this route, Task 2's signal assertions must name the sandboxed observation they rest on.

2. **`task_8_plan.md`: a Verification bullet fails when the clause is applied correctly**
   Verification bullet 1 says: *"`grep -c 'gate runs not collected' plugin/instructions/user_review_fixes_instructions_core.md` prints `2`: the event form and the `none observed` form, both inside the one clause."* `grep -c` counts matching **lines**, not matches. The D.2 *"Run gates (Phase G): passed on round N"* bullet in that file is a single line (line 226 on the base). Task 8's first Work bullet appends the clause to that line byte-for-byte, so both occurrences end up on one line and `grep -c` prints `1`.
   An implementer who follows the plan therefore fails its own check. The likely response is to break the clause across lines, which would make it differ from the plan core's copy and break the byte-identity Task 8's second Verification bullet requires.
   **Fix:** In `task_8_plan.md`, replace the bullet with a count of occurrences: `grep -o 'gate runs not collected' plugin/instructions/user_review_fixes_instructions_core.md` prints two lines. Alternatively, state that `grep -c` prints `1` and that the line also contains `gate runs not collected: none observed`.
