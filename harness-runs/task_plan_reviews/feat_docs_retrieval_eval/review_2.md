## Must Fix

1. **No task regenerates `docs/retrieval-eval-results.md`'s generated region after Task 5 moves the threshold, so the file of record ships arm E numbers taken under a threshold that no longer ships — and Task 14's own traceability check cannot pass** — the story index (`feat_docs_retrieval_eval_story_plan.md`, `## Context` → the *Where the numbers are recorded* and *Ship order* paragraphs) and `task_14_plan.md` (its `**Depends on:**`, its third `**Work:**` bullet and its first `**Verification:**` bullet).
   Task 4 (entry 4) runs arms B–E and writes the generated region with `--out`. Task 5 (entry 5) then changes `ABSTAIN_SCORE_THRESHOLD`, and the plan already states what that does to arm E: `task_9_plan.md`'s `**Depends on:**` says *"the floor is taken after that move, because abstention changes arm E's hit set and a floor recorded before it would describe a threshold that no longer ships."* The identical reasoning applies to the file of record, and nothing acts on it. Task 5 is a `cli` task and is forbidden from touching `docs/` (*"`git diff --stat` shows one file changed"*); Task 14 states *"It does not touch that file's generated region"* and *"this task runs no arm"*; Task 9 re-runs `fixture-catalog` **with no `--out`**; Tasks 7 and 8 write only their own hand-written sections; Task 12 reads and never writes. So the last writer of the generated region is Task 4, one task before the threshold moved, and `docs/retrieval-eval-results.md` — which the story index names as *the results file of record* — ships arm E's recall, MRR, abstention and per-query hit sets for a threshold of `0.3` while `cli/src/retrieval/search.ts` carries the calibrated one.
   Two concrete consequences, not one stylistic one. (a) `task_14_plan.md`'s third `**Work:**` bullet records *"arm E's recall@5 on both corpora before and after the move"* and tells the implementer to name *"the `json` fence above as where they are re-checkable"*, and its first `**Verification:**` bullet requires every figure to be read from Task 5's commit body **or** that fence and to match *"byte for byte"* — the **after** figures exist in neither, because the fence predates the move. (b) The plan has not settled the tension that makes this non-obvious: regenerating the region is not free either, since on an abstaining query `searchDocs` returns `{ abstained: true, hits: [] }`, so a post-move run erases the `bestScoreOnPositive` values for exactly the queries the new threshold abstains on — and those per-query distributions are, per `task_5_plan.md`, *"the whole evidence"* for the calibration and per `task_14_plan.md` the thing that keeps it re-checkable. Acceptance 1 and 7 are read off this file, so an implementer has no way to tell which run it is meant to hold.
   **Fix:** settle it in the plan, in two places. In the story index's *Where the numbers are recorded* paragraph, state which run the generated region holds after the branch is done and how the calibration evidence survives — either (a) the region is **regenerated after Task 5** by a named `general`-layer task, with the calibration evidence preserved where regeneration cannot erase it (the pre-move per-query distributions quoted into Task 14's `## Threshold calibration`, which is hand-written territory), or (b) the region is **deliberately the pre-calibration run**, in which case the generated region's provenance section must name the threshold in force when it was taken and say that the shipped constant is the calibrated one, with the post-move figures living only in `## Threshold calibration`. Then apply the same choice to `task_14_plan.md`: under (a), name the task that re-runs the eval with `--out` after the move and drop *"the `json` fence above as where they are re-checkable"* for the **after** figures in favour of that run; under (b), correct that clause and the first `**Verification:**` bullet so the after figures are traced to Task 5's commit body alone and the pre-move distributions are quoted into the section rather than cited to a fence a later run may overwrite. Note the constraint on placement: `task_14_plan.md` already carries five `**Work:**` bullets, so a regeneration step added there breaches the 5-bullet ceiling — Task 9 (four bullets, and already the task that re-measures after the move) or a bullet folded into an existing Task 14 bullet are the two ways to land option (a) without a split.
