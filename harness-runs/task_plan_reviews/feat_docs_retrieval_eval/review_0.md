2. **`retrievalModelCacheDir` and `retrievalRuntimeState` are cited as exports of a module that does not export them** — `task_3_plan.md`, the `index-build.mjs` `**Work:**` bullet.
   The bullet reads *"Import `RETRIEVAL_STUB_ENV` from `cli/dist/retrieval/models.js` — the same module this bullet already imports `resolveModels`, `modelFilesPresent` and `retrievalModelCacheDir` from"*. `cli/src/retrieval/models.ts` exports `RETRIEVAL_STUB_ENV` (line 150), `modelFilesPresent` (line 82) and `resolveModels` (line 213), but **not** `retrievalModelCacheDir` or `retrievalRuntimeState` — both are `cli/src/retrieval/runtime.ts`'s (lines 57 and 117), so their compiled home is `cli/dist/retrieval/runtime.js`. An implementer following the bullet as written writes an import that fails at module load. The same conflation appears in `task_3_plan.md`'s verification bullet (*"Verify the model-cache predicate by calling `modelFilesPresent(retrievalModelCacheDir())` and `retrievalRuntimeState()`"* — correct as a call, silent on the module) and in `task_7_plan.md`'s *"the same modules this task already reads the `QueryLogRecord` key list and the model predicates off"*, which is true only because it says *modules*, plural.
   **Fix:** in `task_3_plan.md`, split the claim — `RETRIEVAL_STUB_ENV`, `resolveModels` and `modelFilesPresent` from `cli/dist/retrieval/models.js`; `retrievalModelCacheDir` and `retrievalRuntimeState` from `cli/dist/retrieval/runtime.js` — and keep the single-source point about `RETRIEVAL_STUB_ENV` intact, since that constant really does live in `models.js`.
