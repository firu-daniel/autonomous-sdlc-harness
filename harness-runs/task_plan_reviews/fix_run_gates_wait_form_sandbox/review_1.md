# Task plan review — iteration 1

## Must Fix

1. **Task 1's heartbeat loop depends on a `kill -0` the measurement never covered, and it fails unsafe in the self-detached shape the task prompt requires** — `task_1_plan.md`, the third `**Work:**` bullet (*"The run form heartbeats from its own foreground loop"*). The same claim appears in the story index `## Context` (*"The run form polls only its **own** gate child, which is the one case the measurement found permitted"*).
   The loop is `while kill -0 "$gate_pid" 2>/dev/null; do touch "$running_file"; sleep "$HEARTBEAT_SECONDS"; done`. The bullet justifies it as *"the one case the measurement found permitted (exit 0)"*. But the measurement it quotes (task prompt goal 1; `task_1_plan.md` → *"Why the old check failed"*) took that permitted case only **within one live foreground call, on a child that call had just started**. It took no measurement of a run form that **outlives the call that started it** signalling its own child. That case is the self-detached run form (`nohup … &`, `disown`), which `sandbox2c` may adopt. It is also arguably the tool-backgrounded run form after its call has returned.
   The task prompt's `## Constraints` → *"Scope against `sandbox2c`"* says that the new signal *"must therefore work whichever way the run form is started … It must not depend on the Bash call that started the run still being alive."* Under this design, the run form's own liveness probe is exactly what would depend on it.
   The failure is silent and brings back the original bug. If the sandbox refuses that `kill -0`, the loop exits on its first test without one `touch`. `wait "$gate_pid"` then blocks for the whole gate. The heartbeat goes stale after `STALE_SECONDS`. `--wait` refuses `no run in flight` for a live run, and G.1 escalates. A re-issued run form starts a second run of the same label and truncates the live log.
   The plan's own owed rows do not reliably catch this either. WF2 and WF4 (`task_4_plan.md`) expect *"`pending` while the run is live"*, but neither says the run must be held past `STALE_SECONDS`. A suite that finishes within 30 s passes WF4 even when the loop never heartbeats.
   **Fix:** In `task_1_plan.md`, use a test of gate completion that sends no signal to any process. For example, the gate subshell writes its exit status to a private file beside `.running` when it ends: `( ( set +u +o pipefail; eval "…" ) < /dev/null >> "$log_file" 2>&1; printf '%s\n' "$?" > "<status file>" ) &`. The foreground loop heartbeats until that file exists, then `wait`s and removes it. The file name stays internal, like `$verdict_file.tmp`, and it is removed on every exit path, the trap included. The writer may choose another design, as long as it sends no signal. If the plan keeps `kill -0`, it must instead state the measurement that covers a detached run form signalling its own child. It must not cite the same-call control for that case. Either way, correct the claim in `task_1_plan.md` and in the story index `## Context`. In `task_4_plan.md`, add to WF2's and WF4's **Check** cells that the run is held (by a suite or a stub release) for longer than `STALE_SECONDS`, and that `--wait` is issued after that point. Without that hold, the row cannot tell a heartbeating run from one that never heartbeats.

## Should Fix

1. **`RUN_TEST_SUITE_STALE`'s accepted range contradicts the header Task 1 asks for** (`task_1_plan.md`, carried from iteration 0 and unaddressed). The constants bullet accepts any value `>= 1`. The header bullet says the variable *"must exceed `HEARTBEAT_SECONDS`"* (1). mtimes are whole seconds and the loop period is slightly over 1 s, so a live run's age normally reads up to 2. A value of `1` therefore judges live runs dead. Accept only values `> HEARTBEAT_SECONDS + 1`, i.e. `>= 3`, falling back to the default otherwise. Restate that range in `task_2_plan.md`'s `**Depends on:**` contract.
2. **Task 2's "outlives the window" case is tight enough to be flaky** (`task_2_plan.md`, the fourth `**Work:**` bullet). It runs the wait form with `RUN_TEST_SUITE_STALE: '2'`. A healthy run's age can already read 2 under whole-second mtimes, and one scheduling hiccup under load makes it 3. The case would then fail with `no run in flight` against a correct wrapper. Use a window of at least 3 to 5 s, hold the run for about twice that, and keep the *"Killed"* case's window consistent with the range chosen in Should Fix 1.
3. **`touch` without `-c` can recreate a `.running` that another run removed** (`task_1_plan.md`, third `**Work:**` bullet). This happens in the residual the plan itself names: a run misjudged stale while still alive, followed by a second run that finishes and removes its own `.running`. The first run's next `touch` then creates an empty, fresh `.running` that no run owns. Use `touch -c "$running_file"`, which is POSIX and behaves the same on BSD and GNU, so a heartbeat refreshes and never creates.
4. **The "one `--wait` call" bound is overstated** (story index `## Context`, *"A crashed run is refused within one `--wait` call"*; `task_1_plan.md` header bullet, *"so one `--wait` call ends `pending` for a crashed run"*, which also reads garbled). A crash late in a call's slice can still end that call `pending`. The next call then refuses. The property that holds is that a crashed run is refused no later than about `STALE_SECONDS` after its last heartbeat, so `--wait` never prints `pending` forever. Restate it that way in both places.
5. **Task 4's `WF` grep check cannot pass as written** (`task_4_plan.md`, carried from iteration 0 and unaddressed). The check says `grep -nE 'WF[0-9]'` *"shows no id outside"* the F5 and WF1–WF5 rows. But this same task writes WF ids into the `**Stamp.**` line, the sentence under the table, F5's *"Owed: WF2–WF4. WF5 not run."* and §6's *"and WF5"*. List every place a WF id is allowed.
6. **Task 1's `kill |ps |pgrep` grep check is too loose to grade** (`task_1_plan.md`, carried from iteration 0 and unaddressed). `ps ` matches word endings such as "keeps " and "drops ", and the script has comment lines outside the header (inside `wait_for_verdict`). Anchor the pattern on word boundaries and non-comment lines, or say "comment lines". If Must Fix 1 removes `kill -0` from `run_gate`, update the expected hits to match.
