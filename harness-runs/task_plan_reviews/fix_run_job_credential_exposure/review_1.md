## Must Fix

1. **The launch refusals are placed inside the launch group, where `spawn_refuse` cannot refuse anything** — `task_4_plan.md`.
   Task 4 tells the implementer to apply the strip "Inside the `{ … }` group that `exec`s `"$AGENT_CLI"`". It also says to run the local allow-list "in the same group and before the strip", and that "An exit 2 from `hr_session_pass_env` refuses the launch through `spawn_refuse`". The strip set's read gets the same instruction: "A return of 1 from `hr_profile_env_var_names` refuses the launch through `spawn_refuse`". That group is the head of the `{ … } | tee … | "$formatter"` pipeline, inside the `( … ) &` subshell (`cli/templates/scripts/autonomous-watcher.sh` → `spawn_engine`, the `keep_awake_start "$branch" "$(exec sh -c 'echo "$PPID"')"` block). By the time that group runs, `spawn_engine` has already returned 0 and `registry_set "$branch" pid "$!"` has run. `spawn_refuse`'s own comment says *"SPAWN_REFUSAL holds the reason, which the caller's spawn_refused reads. Both run in the caller's shell, never `$(…)`"*. A `spawn_refuse` call inside the pipeline subshell therefore sets a variable no caller reads, and it never makes `spawn_engine` return 1. A group that then skips `exec` falls through to `classify_run_exit` with a non-zero `rc`, and that stamps a status the refusal did not intend. The fail-closed launch that the story index's third `Top risks:` entry relies on ("refusing the launch rather than launching unscrubbed") would not happen as planned.
   **Fix:** In `task_4_plan.md`, have `spawn_engine` compute both name lists in its own shell, after `run_profile_check "$settings_file" …` and before the `( … ) &` subshell. That means `hr_profile_env_var_names "$settings_file"` in both modes, and `hr_session_pass_env "$MAIN_REPO"` when `JOB_MODE` is not `1`. A failure in either goes through `spawn_refuse` and `return 1`, as the existing pre-launch refusals do. The group itself only `unset`s from those precomputed lists, and runs no reader and no refusal. Add a `watcher-session-env.test.mjs` assertion that a refused launch leaves the registry `failed` with a `not launched:` notification, and that no agent process was started. Assert on the registry and the notifier stub, not on a log line. Make the same change in the Work bullet for each refusal.

2. **The local allow-list does not derive what an HTTPS push needs, and the plan never says what breaks for one** — `task_4_plan.md` (and the mirror sentence in `task_8_plan.md`).
   Goal 5 asks for the allow-list to cover *"what the excluded wrappers' SSH or HTTPS push needs, such as `SSH_AUTH_SOCK` and `GIT_SSH_COMMAND`"*, and to *"State what breaks under each"*. Task 4's `SESSION_ENV_BASE` derives the SSH half (`SSH_AUTH_SOCK GIT_SSH_COMMAND GIT_SSH`) and the harness-owned names, but it derives nothing for an HTTPS push. Its "what breaks" list names gates, Bedrock/Vertex and `watcher.env` only. A local HTTPS push authenticates through whichever credential helper the operator configured, and some of those read the environment. For example, `gh auth git-credential` prefers `GH_TOKEN`/`GITHUB_TOKEN`, and the strip removes those in both modes "whatever `sandbox.passEnv` says". A keyring helper needs its session-bus variable, which the base set does not list. `push-branch.sh` always exits 0. So a local run whose push credential came from the environment would stop putting commits on the remote, with no error beyond a `push failed for` line. That is the goal-2 failure ("Every commit is still pushed as it lands") on a local run.
   **Fix:** In `task_4_plan.md` → **The base set**, add a derivation step for the HTTPS push. Name which environment the credential helpers an operator can configure read when the main checkout's `push-branch.sh` runs as a child of the session, and add the ones the session must keep, or state that each is to be listed in `sandbox.passEnv`. In the **THE SESSION'S ENVIRONMENT** header paragraph, and in `task_8_plan.md` → `### The session's environment` → *what breaks under the allow-list*, state that a local HTTPS push authenticating through `GH_TOKEN`/`GITHUB_TOKEN` stops working, because the strip wins over `sandbox.passEnv`. Give the operator's way on, in fenced commands, one per line (for example a stored `gh auth login` credential, or SSH). Add a `watcher-session-env.test.mjs` case that the base set keeps every name the HTTPS derivation adds.

3. **Round 0's two Should Fixes were neither applied nor recorded under `## Rejected findings`** — `task_4_plan.md` and `task_3_plan.md`.
   Ledger rule (`harness-runs/lessons.md` → *Unattended control loops*): *"In a revision round, a reviewer's Should Fix is applied or recorded under `## Rejected findings` with its reason. It is never held for a go-ahead the loop does not relay."* The index has no such section, and neither file changed on either point.
   - **`task_4_plan.md`.** The `watcher-push-refusal.test.mjs` bullet writes its fixture "through Task 2's `hr_push_refusal_record`", but the **Depends on:** → Task 2 list restates only `hr_session_pass_env`, `hr_profile_env_var_names`, `hr_push_refusals_for_var` and `hr_push_refusal_handled`. This consumer calls a producer function whose signature it does not restate. That also breaks the per-task rule that a cross-task interface is restated on both sides.
   - **`task_3_plan.md`.** After Task 4, an in-session `push-branch.sh` in a job inherits an environment with no `GH_TOKEN`. So the `the job token` source finds nothing there. The scan catches the job token only through the `~/.git-credentials` entry Task 5 writes (`a stored git credential`), and that file is located through `HOME` / `XDG_CONFIG_HOME`. The **Collect the values once** bullet still says the values "come from the environment this excluded command inherited". In a job, the stored entry is now the only route by which the scan knows the job token, so the path to it is a trust input. That runs into `harness-runs/lessons.md` → *Trust checks*: *"An unsandboxed script takes its mode and the path of every trust input from a record the session cannot write, such as the run registry, and never from the argument's shape or an environment variable."* Task 3 records `HOME` only as a residual.
   **Fix:**
   - In `task_4_plan.md` → **Depends on:** → Task 2, add `hr_push_refusal_record <main_top> <branch> <reason>`: it writes `<main_top>/.git/harness-push-refusals/<epoch>-<pid>.refusal` with the two lines `branch=` / `reason=`, and returns 1, writing nothing, on a newline in either argument.
   - In `task_3_plan.md`, say in the **Collect the values once** bullet and in the **NO COMMIT IT SENDS CARRIES A CREDENTIAL.** paragraph that, in a job, the job token reaches the scan only through the stored entry.
   - Locate that stored file from a record the session cannot write rather than from `HOME`. For example, have Task 5's `push-credential store` set the checkout-local helper as `store --file <absolute path>` (the main checkout's `.git/config` is write-protected). Then have Task 3 read that path from the main checkout's config, and keep the `HOME` / `XDG_CONFIG_HOME` files only as extra sources. If you choose this, make the matching edit to `task_5_plan.md`'s verb contract and to the restated contract in `task_6_plan.md`.
   - Add the `task_3_plan.md` test case: no `GH_TOKEN` in the environment, and the token present only in the stored entry and in a commit, is refused.
   - Alternatively, record either point under a new `## Rejected findings` section in the story index, with its reason.
