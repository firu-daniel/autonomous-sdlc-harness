1. **No task updates the setup guidance `init` prints, which still states that `HARNESS_GIT_TOKEN` pushes the run's commits to trigger CI** — the story index (`fix_run_job_credential_exposure_story_plan.md`), and a new or extended `cli`-layer per-task file.
   `cli/src/commands/init.ts`, in the GitHub setup steps it prints (the line starting `` `3. Optionally set ${PUSH_URL_SECRET} to receive push notifications from the job, and ${GIT_TOKEN_SECRET} ``), tells every adopter to set `HARNESS_GIT_TOKEN` *"— a personal or App token — so the job's pushes trigger your own CI, which pushes made with the job's built-in token never do"*. After Task 6 that is false. `HARNESS_GIT_TOKEN` is never referenced in `run`, only `github.token` pushes, and the token's purpose is now opening the draft pull request (`open`) and the `ready_for_review` flip (`deliver`). The task prompt names this exact reason as the one the design replaces (goal 3: *"Today's reason for the token in the `run` job is 'so the job's pushes trigger your own CI' … Find another way"*). Task 6 rewrites the same sentence in `harness-run.yml`'s `# WHAT IT READS.` (the header lines *"a personal or App token, so the job's pushes trigger your own CI"*), and Task 12 rewrites its documentation mirror in `docs/cli.md`. The CLI's own printed copy, the one an adopter actually reads during `init`, is in no task's `### Targets`. The scope register cannot reach it because its entries grep the docs corpus only. That is correct for the register, but it leaves this source-side requirement unplanned.
   **Fix:** Add a `cli`-layer task (or extend Task 1, which has room at 10 points and 3 Work bullets, though its subject differs), ordered after Task 6 and before Task 7. Its `### Targets` names `cli/src/commands/init.ts` → that setup step. Reword the step so `HARNESS_GIT_TOKEN` opens the pull request and flips it ready, so CI runs on `opened` and `ready_for_review`. State that pushes made by the job never trigger CI and that the CI workflow must list `ready_for_review`. Keep the `gh secret set ${GIT_TOKEN_SECRET}` command line as its own `command(...)`. Name `GIT_TOKEN_SECRET` through its constant, as the line does today. Add a case to the init suite that already covers the GitHub setup output, asserting on the new wording and on the absence of *"so the job's pushes trigger your own CI"*. Add the row to the readiness list and update the `## Context` goal-3 bullet to name the task.

2. **The plan cites S1 (runner) and S2 (runner) as measuring the `~/.git-credentials` read-deny, but those rows measure `~/.ssh`** — the story index (`## Context`, goal 3's *"On top of the baseline"* sub-bullet), `task_5_plan.md`, `task_6_plan.md` and `task_11_plan.md`.
   `docs/sandbox-verification.md`'s row S1 is *"A read of `~/.ssh` from a sandboxed command"*, and S2 is *"`Read` tool on `~/.ssh/config`"*. S1 (runner) and S2 (runner) are *"S1 on a GitHub-hosted runner … as its row"*, so they measure `~/.ssh` too. No row in `docs/sandbox-verification.md` or `docs/sandbox-record.md` measures a read of `~/.git-credentials`; its only mention is the probe container's own `credential.helper store` setup. The plan still writes each of the following:
   - Context: *"A sandboxed command is already read-denied `~/.git-credentials` (S1 (runner), **pass**)"*.
   - Task 5: *"The GitHub-hosted runner rows S1 (runner) and S2 (runner) are **pass**"*, as the reason the store entry is safe, carried into `remote-run.sh`'s new header paragraph.
   - Task 6: *"the path-scoped `~/.git-credentials` entry, which the sandbox and the file tools are read-denied (S1 (runner), S2 (runner))"*, carried into `harness-run.yml`'s `# THE CHECKOUT CREDENTIAL.`.
   - Task 11: *"the path-scoped store entry that the sandbox and the file tools are read-denied (S1 (runner), S2 (runner))"*, carried into the document of record.

   This breaks `.claude/context/conventions.md` → `## Documents of record`: *"A measured fact states what was measured"*. It also falls under the ledger rule `harness-runs/lessons.md` → *Trust checks*: *"Never drop a protection because another route 'can already' reach the same target until that route is measured, and close every route the drop opens, file tools included, before relying on downstream checks."* The design moves the push credential out of `.git/config` and relies on the deny of this exact file. Task 10's roadmap row 35 already lists *"`~/.git-credentials` is refused to a sandboxed read"* as owed, which confirms it is not yet measured.
   **Fix:** In the story index and in `task_5_plan.md`, `task_6_plan.md` and `task_11_plan.md`, say that the `~/.git-credentials` deny is *derived from the profile*: its `sandbox.credentials.files` entry and its `Read` deny pair, the same mechanism S1 (runner) and S2 (runner) measured `pass` on `~/.ssh`. Say that the direct measurement is owed to roadmap item 35. Cite S1/S2 (runner) only as measuring the mechanism, never this file. In Task 11, extend the Verification bullet *"nothing is claimed measured that only roadmap item 35 will measure"* to name this deny explicitly. In Task 10, make row 35's `~/.git-credentials` check cover the file tools as well (a `Read` of it), not only a sandboxed read.
