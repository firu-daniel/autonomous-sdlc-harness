# Task plan review — iteration 0

Structure, index-to-file correspondence (33 entries, 33 files), single-layer tags, points (all at most 20), `**Work:**` bullet counts (all at most 5), bottom-up order and the `## Scope register` closure all hold. Derivation entries 2 through 8 were re-run verbatim, and every hit is a row. Entry 9 was walked, and it reaches no rows. No task targets a conventions document, and the three `## Corpus staleness` entries are typed `stale-rule`. The findings below are design defects that would make a remote run lose data or ignore a user action, contrary to the task prompt's requirements and the story index's own settled decisions.

## Must Fix

1. **A failed push of the dropped artifact must block a remote dispatch, not be ignored** — `task_11_plan.md`.
   The contract says the task and docs paths stay "unchanged up to and including the existing commit and push", and that the remote review commit uses "the same non-blocking failure rule as the prompt commit". The existing rule (`cli/templates/scripts/autonomous-watcher.sh` → `WHAT IT COMMITS, AND WHAT IT POINTEDLY DOES NOT`: *"a failed commit or push is one WARNING line in the log and the run launches anyway"*) is only safe locally, because the local run executes in the same working copy that holds the file. A remote job checks out `origin/<branch>` (Task 15: `actions/checkout` at `ref: ${{ inputs.branch }}`), so the push is the only way the prompt, docs checklist or review reaches the run. If the push fails and the dispatch goes ahead, the job starts on a branch without its task prompt, checklist or review. Task 11's own reason for committing the review ("a job boundary … would otherwise lose it") fails in exactly this case.
   **Fix:** In `task_11_plan.md`, state that on the remote arm a failed commit or a failed `push-branch.sh`, for all three artifacts, is `fail_before_launch` naming the step, and that nothing is dispatched. The one exception is the identical re-drop skip, which is still followed by a push, and that push must succeed. Keep the local rule unchanged. Add a `watcher-remote-dispatch.test.mjs` case: a push that fails (for example, a bare `origin` that rejects the push) sends no `workflow run` to the `gh` recorder and leaves the record `failed` with one `failed` notification.

2. **The `chain` count has no single stated source, and Task 9 seeds it from the previous bundle** — `task_9_plan.md` (and `task_8_plan.md`).
   Task 9's `**Depends on:**` says job mode "seeds from" `status.json` keys including `chain`. Task 8's `continue` dispatches `--chain <chain + 1>`, reading `chain` from `status.json` through `hr_remote_status_get`. Task 8 also lists `HARNESS_INPUT_CHAIN` among its environment reads without saying which value wins. If the job's record and its `status.json` carry the previous bundle's `chain`, every continuation sends the same number again, and `HARNESS_MAX_CHAIN` is never reached. It would also carry a stale count across a user's dispatch, which the story index says resets `chain` to 0 (`## Context` → *"A user's own dispatch resets `chain` to 0"*). That is the stop condition named as the second top risk.
   **Fix:** In `task_9_plan.md`, remove `chain` from the seeded keys. Job mode sets the record's `chain` from `HARNESS_INPUT_CHAIN` at start, so `status.json` records this job's own input. Add `HARNESS_INPUT_CHAIN` to the environment Task 9 reads, and Task 15 already provides it. In `task_8_plan.md`, state that `continue` and `poll` take `chain` from `status.json`, now defined as the dispatching job's input, and never from anything else. Add one Task 8 case that chains a bundle whose `chain` is `N` and asserts `--chain N+1`. Add one Task 9 case asserting that `status.json` carries `HARNESS_INPUT_CHAIN`, not the restored value.

3. **`auto_resumes` is never reset by a user action, contrary to the settled decision** — `task_10_plan.md` (and `task_9_plan.md`).
   The story index settles that the auto-resume count is *"carried in the bundle and reset by any user action"* (`## Context` → **API errors**). Task 9 seeds `auto_resumes` from the restored `remote_status.json` on every resume kind. Task 10 loops `while auto_resumes < REMOTE_AUTO_RESUME_MAX`. Neither task resets it. So after `REMOTE_AUTO_RESUME_MAX` automatic resumes in a run's lifetime, a run the user later resumes by hand can never auto-resume again. No task implements this part of the requirement.
   **Fix:** In `task_10_plan.md`, and in the seeding rule in `task_9_plan.md`, state the reset. Any job whose `HARNESS_INPUT_CHAIN` is `0` (a user's dispatch: drop, answer, resume) starts with `auto_resumes` at `0`. Only an automatic continuation carries the count forward. Add a case: a restored `auto_resumes` equal to `REMOTE_AUTO_RESUME_MAX` with `HARNESS_INPUT_CHAIN=0` still gets its automatic resumes.

4. **A remote pause sent while the job is queued, or across a chained continuation, is silently lost** — `task_10_plan.md`.
   The pause poll matches a `harness pause <branch>` run *"created after `HARNESS_JOB_STARTED_EPOCH`"*, which is *"captured in the job's first step"*. Task 12's relay removes the mirror's `PAUSE` as soon as `remote-run.sh pause` exits 0. A pause dispatched while the `run` job is still queued has a `createdAt` earlier than the job's start, so the job never honours it. This is common on a busy self-hosted runner, and whenever a user pauses right after a drop. The same happens to a pause created between job N's last control poll and job N+1's start, for example after a budget self-pause. The local record stays `running` and the mirror no longer holds `PAUSE`, so the user believes the run is paused when it is not. The prompt requires that `/autonomous-sdlc-harness:branch-pause` *"must reach a remote run too"*.
   **Fix:** In `task_10_plan.md`, set the lower bound of `pause-requested` to a time no later than the dispatch that created this run. For example, carry a `control_polled_at` epoch in `status.json`: the time of the last control poll, written with every status write. Job mode passes the restored value, or the job's own run `createdAt` (read with `gh run view "$GITHUB_RUN_ID" --json createdAt`) when there is no bundle. Add `control_polled_at` to Task 4's `status.json` table through this file's `**Depends on:**` restatement, and to Task 9's seeded keys. Add cases for a pause created before the job's start epoch but after the previous job's last poll: `PAUSE` is dropped and the run ends `paused` / `user` / `stop`.

5. **A repeated `sync` re-applies the bundle and moves aside answers the user wrote since the last sync** — `task_6_plan.md`.
   For a finished run, `sync` skips only the **download** when the bundle is already present (*"skipped when that directory already holds it, so a repeated sync is a no-op"*). It then always *"restores it in `mirror` mode into the record's `worktree`"*, and Task 4's restore *"replaces the target clarification directory wholesale"*, moving the existing one to `remote_superseded/`. Consider a run parked on two questions. The user answers `question_1.md` with `/autonomous-sdlc-harness:branch-answer`, and Task 12 relays nothing until every question has its answer. The user then runs `branch-answer` again for `question_2.md`, and Task 22 syncs first. The second sync moves `answer_1.md` out of the mirror, and the relay never fires. Tasks 23 (`branch-resume`, `branch-pause`) sync the same way. The prompt requires that every drop that continues a run *"must still work"*.
   **Fix:** In `task_6_plan.md`, state that when the selected finished run's id equals the record's `remote_run_id`, `sync` restores nothing, rewrites no record field except `remote_synced_at`, and only reports. The mirror is replaced only by a bundle newer than the last one synced. Add a case: sync, write `answer_1.md` into the mirror, sync again with the same canned run, and assert that `answer_1.md` is still in the clarification directory and nothing new is under `remote_superseded/`.

## Should Fix

1. **`task_11_plan.md` — the header-qualification grep cannot hit one of its three sentences.** The Verification grep `defers a fresh inbox drop` looks for text that wraps across a line break in the watcher header (*"which is what defers a"* / *"fresh inbox drop"*), so it can never find the sentence it is meant to confirm. Anchor on `THE HOLD MARKER IS UP` instead.
2. **`task_12_plan.md` / `task_9_plan.md` — the per-record skips depend on the job's own record never carrying `execution`.** Task 12 skips `reconcile_stale_runs`, `check_stalled_runs` and `usage_gate` for any record whose `execution` is `github-actions`. Task 9 does not say its job-mode record never carries that field. If a later change seeds it (for example from a restored registry), the job would switch off its own watchdog and usage gate. State in Task 9 that job mode never writes `execution`. Alternatively, key Task 12's skips on `JOB_MODE` being off as well, and add a Task 9 assertion.
3. **`task_11_plan.md` — an unresolvable `execution.target` is treated as `local`.** `hr_execution_target` exits 2 for an out-of-enum hand-edited value, and the library header's `THE THREE-STATE ANSWER` paragraph (*"A CONSUMER THAT TREATS 2 AS 1 TAKES A MUTATING ACTION ON A CONFIGURATION IT COULD NOT READ"*) argues against guessing. An adopter who typo'd `github-action` would silently get local runs, billed to their local subscription. Prefer rejecting the drop with `fail_before_launch` naming the value.
4. **`task_15_plan.md` — the plugin pin assumes the CLI and plugin versions stay in step.** The job refuses when the installed plugin's version is not `{{cliVersion}}`. Today `cli/package.json` and `plugin/.claude-plugin/plugin.json` are both `0.3.0`, but no document states that they are released in lockstep. Cite a source for that rule, or record it in the header as an assumption the job enforces.
5. **`task_20_plan.md` — link form.** `cli/README.md` writes its document links as absolute GitHub URLs, because the file is published to npm. The new `docs/remote-execution.md` pointer should follow that form.

## Nice to Have

1. **Story index — the register numbering skips row 38.** Renumbering is optional, but a gap invites a reader to look for a missing site.
2. **`task_15_plan.md` — concurrency pending-replacement.** With `cancel-in-progress: false`, GitHub still cancels an already-pending run in the same group when a newer one queues, for example a poller resume and a user resume racing. One header sentence stating that this is harmless would help a later reader. It is harmless because `restore` and `sync` skip runs that have no bundle.
