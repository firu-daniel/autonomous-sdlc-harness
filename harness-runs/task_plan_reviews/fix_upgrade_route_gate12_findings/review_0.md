# Task plan review — iteration 0

## Must Fix

1. **`task_5_plan.md` — the documented route for moving a run in flight fails that run's next job on the first upgrade after this release**
   The route in the `**Moving a run in flight to the new version, on purpose.**` bullet checks out only the two workflow files from `origin/<default branch>` onto the run's branch. But Task 2 adds three ungated lines to the managed `.gitignore` block. Task 3 commits them to the default branch as part of the upgrade: its `git add` names `.gitignore` whenever the run merged into it, and that is the case on the first upgrade after this release (story index, `Top risks:` 1).
   The run's branch was cut before that upgrade, so its `.gitignore` lacks the three lines. Once the branch carries the new workflows, its next job runs the new version's `init`. `cli/templates/github/workflows/harness-run.yml`, step `Generate the job's permission profile`, runs `npx --yes "autonomous-sdlc-harness@$HARNESS_CLI_VERSION" init --plugin-root-entries`. That is a full `init` run: `--plugin-root-entries` is a flag on the ordinary plan (`cli/src/commands/init.ts`, `pluginRootEntries`). So it merges the missing lines into the branch's tracked `.gitignore`. The step's `git status --porcelain --untracked-files=no` test then sees a changed tracked file and exits `1` with `init … changed tracked files`.
   This is the failure the story index's first `Top risks:` entry guards against on the default branch, and here it is not guarded on the run's branch. It is also the one requirement the task prompt's finding 1 makes of this section: give a working deliberate route. The prompt marks its `git checkout … -- harness-run.yml harness-resume.yml` form as a candidate to be verified, not an instruction.
   **Fix:** In `task_5_plan.md`, change the route so the run's branch receives every tracked file the upgrade commit changed, not only the two workflows. One way is to name `.gitignore` (and any other file the upgrade's printed `git add` named) in the `git checkout origin/<default branch> -- …` line, and have the prose say to use the same path set the upgrade committed. Another is to merge `origin/<default branch>` into the run's branch instead of checking files out. Give the reason in the section: the job's own `init` refuses a changed tracked file. Add a `**Verification:**` bullet checking that the route's path set includes `.gitignore`. Also add a sentence to the story index's `Top risks:` 3 entry naming this failure mode.

## Should Fix

1. **`task_1_plan.md` — `doctor`'s version warning still tells the adopter to commit only the two workflows.** The warning's move route reads `run \`…init --upgrade-workflows\`, commit .github/workflows/harness-run.yml and .github/workflows/harness-resume.yml, then …` (`cli/src/doctor/checks.ts` → `REMOTE_EXECUTION_CHECK`). After Task 2, the first upgrade also changes `.gitignore`. An adopter who follows doctor's line rather than the upgrade's printed report leaves it uncommitted, and the next default-branch job fails its setup step, which is the failure `Top risks:` 1 describes. Task 1 already edits this string. Consider replacing "commit X and Y" with "commit the files its report's `git add` names", or naming `.gitignore` there.
2. **`task_5_plan.md` — `git switch <branch>` can land on a stale local branch.** If the adopter already has a local branch of that name, `git switch` checks it out as it is, not as `origin/<branch>` carries it. The later `git push origin <branch>` is then rejected as non-fast-forward, or the commit is built on old history. Consider `git switch -C <branch> origin/<branch>`, or a `git pull --ff-only` step after the switch. Either way, say why.
3. **`task_4_plan.md` — case (d) inherits the developer's own git configuration.** `runStep` in `cli/test/workflow-plugin-pin.test.mjs` passes only `GIT_CONFIG_COUNT`/`KEY_0`/`VALUE_0` on top of the ambient environment. On a machine whose global or system config sets `advice.detachedHead=false`, the fail-before check passes against the unedited template, and the task's own instruction then stops the unit. After the fix, the same config would also hide a regression. Have case (d) isolate git's config, for example with `GIT_CONFIG_GLOBAL=/dev/null` and `GIT_CONFIG_NOSYSTEM=1`, so the before/after result is deterministic.
