## Must Fix
1. **`task_1_plan.md` — the `launch-line` leg reads `fail` everywhere, because its fixture has no lane directory**
   The leg issues the pre-fix launch line directly, with `RUN_TEST_SUITE_WORKER=gwsp_launch`, so the copied script goes straight down its worker path. In `cli/templates/scripts/run-test-suite.sh` the lane directory is created only on the run form's path (`mkdir -p "$log_dir" || refuse "cannot create '$log_dir'"`, inside `if [ "$worker_marker" != "$label" ]`). The worker path starts at `printf '%s\n' "$$" > "$running_file"` and creates no directory. `hr_test_run_lane_dir` only prints `<state_dir>/test_run_logs/<sanitized branch>`, and the fixture as specified (`git init`, a `devscene.config.json` with `stateDir` `devscene`, two script copies) has no `devscene/` directory. The legs run in order, so the `run-form` leg, which would create the lane, runs after `launch-line`. The worker's `.running`, log, `.verdict.tmp` and `.verdict` writes therefore all fail with `No such file or directory` (the script runs `set -uo pipefail` with no `-e`, so it carries on and writes nothing). `gwsp_launch.verdict` never reaches the disk, and the leg grades `fail` sandboxed or not, the unsandboxed terminal control included.
   Task 2's gate needs `launch-line: fail`. Task 6's WS3 and F17 record this leg as the worker's own stderr under the bug, and the task prompt's goal 1 is "Capture the worker's own stderr". As specified, the leg would record a fixture defect as that stderr. Task 1's verification cannot catch it, because "Its verdicts are a measurement, not this task's pass criterion", and Task 4 deliberately asserts no live verdict. This is the lessons-ledger failure *"When a check moves to reading a field one producer writes, the same change makes every path that stands in for that producer (a probe's setup, a fixture helper) write the field too"*: the leg stands in for the run form's launch but leaves out the setup the run form does before it.
   **Raised against:** "issues the run form's **pre-fix** worker launch line verbatim, with stderr redirected to a record instead of `/dev/null` … It waits at most 15 s for the lane's `gwsp_launch.verdict`."
   **Must hold:** Before the `launch-line` leg issues its line, the fixture state it runs against matches what the run form would have prepared: the lane directory `hr_test_run_lane_dir` names for the fixture's branch exists, and no stale `gwsp_launch.*` file is in it. On a host where `nohup` works, the leg can therefore read `pass`. If that setup fails, the leg grades `not run` with the failing command's message, never `fail`.
   **Fix:** In `task_1_plan.md`, extend the fixture bullet or the `launch-line` leg spec: create `<fixture>/devscene/test_run_logs/<sanitized gwsp-probe>` (the path `hr_test_run_lane_dir "devscene" "gwsp-probe"` prints, resolved through the copied library rather than retyped), and remove any `gwsp_launch.verdict` / `.commit` / `.running` before the launch, as the run form does. State that a failed creation is `not run`. Make the leg's evidence quote what reached the lane on disk (the listing, plus `.running` / `.verdict` presence), not only the stderr record, so a `fail` is distinguishable from a setup fault. Add a `REPRO` line, or a Verification bullet, saying that the unsandboxed control (`bash scripts/gate-worker-start-probe.sh` from a terminal) is expected to read `launch-line: pass`. Restate the change wherever Tasks 2, 4 and 6 restate this leg.
