### Task 12 — Make `doctor` in a linked worktree grade the main checkout's profile

**Goal:** Make `doctor`, run inside a linked worktree, read and grade `.claude/settings.autonomous.json` from the **main checkout** — the one profile the watcher loads (`cli/templates/scripts/autonomous-watcher.sh` → `SETTINGS_PROFILE="$MAIN_REPO/.claude/settings.autonomous.json"`) — instead of from the worktree, so that once Task 1 gitignores the profile (and `init`'s first commit, `cli/src/core/git.ts` → `commitAll`'s `git add -A`, therefore stops carrying it), a worktree does not `FAIL permission-profile` with a remedy that sends the operator to run `init` inside the worktree.

**Added in plan revision (review 1, Must Fix 1); ships first, before Task 1.** It is correct on its own before the ignore rule lands — a worktree whose committed copy is identical to the main checkout's grades the same bytes either way — and it has to be in place before Task 1, because Task 1 is what removes the worktree's copy and would otherwise break `cli/test/doctor.test.mjs` → `a sibling worktree is covered by the profile's worktree pattern and does not warn` in its own commit.

**The decision (shape (a) of the review), and why not a worktree-specific disposition.** A per-checkout read in a worktree grades a file no run loads: the watcher never reads a worktree's profile. The file a run *does* load is the main checkout's, and whether it covers *this* worktree's root is exactly `profile-paths`' question — so the context reads the profile from the main checkout and keeps `repoRoot` as the worktree's, and every profile check then grades the right file against the right root. A disposition that only changed the remedy (shape (b)) would leave `plugin-permissions`, `command-permissions` and the deny checks unanswerable in every worktree.

**Behaviour, exactly — the contract Tasks 1, 4, 5 and 9 cite.**

- `buildCheckContext` resolves the profile's checkout as `mainWorktreeRoot(repoRoot) ?? repoRoot`, and reads `join(<that root>, PROFILE_PATH)`. In a main checkout — including a remote job's `actions/checkout` directory, which is never a linked worktree — the answer is `repoRoot` itself and nothing changes. When the probe does not answer, the fallback is `repoRoot`: today's behaviour.
- `ctx.repoRoot` stays the checkout `doctor` runs in; only the profile's location moves. `ctx.profilePath` is the absolute path actually read, so every message that prints it names the main checkout's file.
- `permission-profile`'s absent-profile message, when the profile's checkout differs from `repoRoot`, says that a linked worktree carries no profile of its own, that runs load the main checkout's, names that checkout's path, and tells the operator to run `init` **there** — never in the worktree. The in-main-checkout message is unchanged.
- `profile-paths` is unchanged in code: the main checkout's profile names the main checkout and the sibling-worktree glob, the glob covers the worktree, and the check passes.

**Where this task stops.** It does not add the ignore rule (**Task 1**), the `--remote-job` arms (**Task 4**, which edits `buildCheckContext` after this task — its fourth parameter sits beside the resolution this task adds), or the `profile-tracked` check (**Task 5**, which asks about the tree `HEAD` names in the checkout `doctor` runs in, i.e. `ctx.repoRoot`, not the profile's checkout). In `checks.ts` it edits `CheckContext`'s `profilePath` doc, `buildCheckContext`, `PROFILE_CHECK` and `PROFILE_PATHS_CHECK`'s doc comment only. It edits no document; Task 9 describes this behaviour in `docs/cli.md`.
