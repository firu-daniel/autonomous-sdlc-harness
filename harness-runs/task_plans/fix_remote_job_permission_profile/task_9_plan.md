### Task 9 — Bring `docs/cli.md` and `ARCHITECTURE.md` into line with the new grading and launch

**Goal:** Make the CLI's reference document and the architecture's coupling table describe what `init`, `doctor` and the watcher now do — the ignored profile, `doctor`'s main-checkout read of it in a linked worktree, the `Read` requirement at the runtime root and the correction of the measurement behind the old exemption, `doctor --remote-job`, the `profile-tracked` check, and the job-mode `--add-dir` entries (task prompt → acceptance criterion four, *"`docs/cli.md` … agree with what the code does"*; `## Scope register` rows 2 and 3).

**Depends on:** Tasks 1–7 and 12, which this task describes and does not change. The facts it must state, as those tasks shipped them:

- **Task 12** — in a linked worktree `doctor` reads and grades the **main checkout's** profile (resolved as `git worktree list --porcelain`'s first entry, the same resolution the watcher uses for the profile it loads), against the worktree's own root; a worktree carries no profile of its own. `permission-profile`, when the main checkout has none, names the main checkout as the place to run `init`. `profile-paths` passes in a sibling worktree because the main checkout's profile carries the sibling-worktree glob.
- **Task 1** — the managed `.gitignore` block carries `.claude/settings.autonomous.json` for every adopter.
- **Task 2** — `plugin-permissions` requires `Read(/<root>/**)` at the **runtime root** — the root the runtime substitutes for `${CLAUDE_PLUGIN_ROOT}`, which is the install root itself wherever the marketplace is not `directory`-sourced — whatever `phases.qa` says, and no `Read` at an install root distinct from it. The old *not graded* disposition is gone for any machine where a root resolves. The measurements: 2026-08-26, `directory`-sourced marketplace, reads under the separate install snapshot succeeded ungranted while ten at the runtime root were refused; 2026-09-28, Gate 12 round 1 on a GitHub-hosted runner with a GitHub-sourced marketplace, where the two roots are one directory, every `Read` of an instruction file was refused.
- **Task 3** — `init --plugin-root-entries` also writes every resolved root into `permissions.additionalDirectories`, and writes its `_README` line only when it wrote an entry; `init`'s closing note calls the profile gitignored.
- **Task 4** — `doctor`'s fourth own option `--remote-job`: `profile-paths` fails instead of warning; `plugin-permissions` fails on a missing entry, on a missing root in `permissions.additionalDirectories` (graded only under the option), and when no root resolves. Without it both stay warnings and the exit status is unmoved by them.
- **Task 5** — `profile-tracked`, after `profile-paths`: pass when the profile is not in the tree `HEAD` names, warn when it is, fail when it is under `--remote-job`. Its remedy, and `profile-paths`' remedy under `--remote-job` (Task 4), is the **untrack route** `checks.ts` → `profileUntrackRemedy` prints, in this order and spelling: `git rm --cached .claude/settings.autonomous.json`, `git commit -m "Stop tracking the machine-local permission profile"`, `git push --no-verify origin <defaultBranch>`. It lands on the default branch because every run's branch is cut from `origin/<defaultBranch>`, so an untrack pushed only to a run branch covers one run; it carries `--no-verify` because the `pre-push` hook `init` installed refuses a push to the default branch — the adopter's deliberate push, which the harness never makes.
- **Task 7** — in job mode the launch line carries one more `--add-dir` per `permissions.additionalDirectories` entry of the profile, after the worktree and the state directory; a local launch is byte-identical to before.

**Where this task stops.** `docs/remote-execution.md` is **Task 8's** and `docs/development.md` **Task 10's**; this task edits neither. It adds no roadmap row and no claim that a job now succeeds.
