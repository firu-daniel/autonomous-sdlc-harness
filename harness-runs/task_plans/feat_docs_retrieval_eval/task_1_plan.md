### Task 1 — Store case: the lexical arm's non-matching rows, and the synthetic bisect for the index-scan crossover

**Goal:** Settle `docs/retrieval.md` → `## Still open`'s entry *"Whether the lexical arm filters to matching chunks on every index"* with a store-level case: assert what `DocStore.lexicalSearch` returns at the two committed corpora's sizes, and find — by inserting synthetic rows and bisecting — the row count at which the planner stops choosing a sequential scan and the non-matching rows stop coming back.

**Where this layer stops.** This task produces a **number and an assertion inside `cli/`**, nothing else. It does not edit `docs/retrieval.md`: Task 12 reads the crossover off this suite's own printed line and writes the reworded `## Still open` entry. It does not change `cli/src/retrieval/store.ts` — `lexicalSearch`'s doc comment already records the behaviour honestly and this task is measuring it, not fixing it. If the measurement shows the behaviour is worse than that comment says, that is a finding to raise, not a silent code change.

### Targets

- `cli/test/docs-retrieval-store.test.mjs` (new) — the suite, in its own file rather than appended to `cli/test/docs-retrieval.test.mjs`, because the bisect inserts thousands of rows and gate 4 (`npm test`) runs both; a separate file keeps the existing suite's runtime readable in the gate output. Its header states the rule it exists to enforce, per `.claude/context/conventions.md` → `## The testing bar`.

**Work:**

- [ ] Open the suite with the header the testing bar requires: the rule is *the lexical arm's "matching rows only" property belongs to the BM25 index scan and not to the `<@>` operator, so it holds above a row count and not below it, and that row count is recorded here rather than assumed*. Cite `docs/retrieval.md` → `## Measured, and how`, item (b) as the prior (`Seq Scan` at 3 rows, the index chosen unforced at 2,003) and say that this suite needs **no model**: it opens the store through `openPgliteStore({ dataDir: undefined, dimensions: 384 })` and calls `upsertChunks` with locally generated vectors, so nothing here loads or downloads anything and it is stub-independent.
- [ ] A helper that builds an in-memory store holding `n` synthetic chunks: `n - 1` filler chunks whose `text`/`body` share a fixed vocabulary that does **not** contain the probe term, plus exactly one chunk carrying the probe term `frobnicator`. Each chunk is a real `DocChunk` (`key`, `path`, `anchor`, `heading`, `text`, `body`, `hash` — `cli/dist/retrieval/chunk.js` exports the type's producer; build the records directly rather than chunking Markdown), with a fixed pseudo-random vector per chunk derived from its key so the run is deterministic.
- [ ] Case: **the two committed corpora's sizes**. At `n = 40` (the `fixture-catalog` corpus's order of magnitude) and at `n = 166` (the `self-docs` corpus's measured chunk count), assert what `lexicalSearch('frobnicator', 50)` returns and record it: the passing property is *only the matching chunk comes back*; the expected outcome at these sizes, per item (b)'s prior, is that it does **not** hold and non-matching rows come back after the match. Write the assertion against whichever the measurement shows, with a comment naming the other branch — a case that asserts nothing is not a case, and a case whose expectation was flipped without a comment is worse.
- [ ] Case: **the crossover**. Bisect `n` over the closed range `[166, 4096]` for the smallest `n` at which `lexicalSearch('frobnicator', 50)` returns the matching chunk **and nothing else**, monotonicity assumed across the range and stated as the assumption it is. Reuse one store per probe and insert incrementally rather than rebuilding, and keep the probe count logarithmic. Assert the crossover lies inside the range and — once measured — pin it as an exported-in-file constant with a `±` band the case asserts against, so a PGlite or `pg_textsearch` version bump that moves it fails here rather than silently.
- [ ] Print the result on stdout as one line, in exactly this form and spelling, because Task 12 reads it: `lexical-arm index-scan crossover: <N> rows`. Print it once, from the crossover case, whatever the case's verdict.
