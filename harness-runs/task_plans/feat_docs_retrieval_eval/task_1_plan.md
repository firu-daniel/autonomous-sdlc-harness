### Task 1 — Store case: the lexical arm's non-matching rows, and the synthetic bisect for the index-scan crossover

**Goal:** Settle `docs/retrieval.md` → `## Still open`'s entry *"Whether the lexical arm filters to matching chunks on every index"* with a store-level case: assert what `DocStore.lexicalSearch` returns at the two committed corpora's sizes, and find — by inserting synthetic rows and bisecting — the row count at which the planner stops choosing a sequential scan and the non-matching rows stop coming back.

**Where this layer stops.** This task produces a **number and an assertion inside `cli/`**, nothing else. It does not edit `docs/retrieval.md`: Task 12 reads the crossover off this suite's own printed line and writes the reworded `## Still open` entry. It does not change `cli/src/retrieval/store.ts` — `lexicalSearch`'s doc comment already records the behaviour honestly and this task is measuring it, not fixing it. If the measurement shows the behaviour is worse than that comment says, that is a finding to raise, not a silent code change.

**Work:**

- [x] Open the suite with the header the testing bar requires: the rule is *the lexical arm's "matching rows only" property belongs to the BM25 index scan and not to the `<@>` operator, so it holds above a row count and not below it, and that row count is recorded here rather than assumed*. Cite `docs/retrieval.md` → `## Measured, and how`, item (b) as the prior (`Seq Scan` at 3 rows, the index chosen unforced at 2,003) and say that this suite needs **no model**: it opens the store through `openPgliteStore({ dataDir: undefined, dimensions: 384 })` and calls `upsertChunks` with locally generated vectors, so nothing here loads or downloads anything and it is stub-independent.
- [x] A helper that builds an in-memory store holding `n` synthetic chunks: `n - 1` filler chunks whose `text`/`body` share a fixed vocabulary that does **not** contain the probe term, plus exactly one chunk carrying the probe term `frobnicator`. Each chunk is a real `DocChunk` (`key`, `path`, `anchor`, `heading`, `text`, `body`, `hash` — `cli/dist/retrieval/chunk.js` exports the type's producer; build the records directly rather than chunking Markdown), with a fixed pseudo-random vector per chunk derived from its key so the run is deterministic.
- [x] Case: **the two committed corpora's sizes**. At `n = 40` (the `fixture-catalog` corpus's order of magnitude) and at `n = 166` (the `self-docs` corpus's measured chunk count), assert what `lexicalSearch('frobnicator', 50)` returns and record it: the passing property is *only the matching chunk comes back*; the expected outcome at these sizes, per item (b)'s prior, is that it does **not** hold and non-matching rows come back after the match. Reuse one store per probe and insert incrementally rather than rebuilding, and keep the probe count logarithmic. Assert the crossover lies inside the range and — once measured — pin it as an exported-in-file constant with a `±` band the case asserts against, so a PGlite or `pg_textsearch` version bump that moves it fails here rather than silently.

**Deviations from plan:**

- Plan expected the "matching rows only" property to **fail** at `n = 40` and `n = 166`, per item (b)'s prior. Measured: it **holds**, and holds at `n = 1` upward. The reason is the DDL order, not the row count — `openPgliteStore` creates `chunks_bm25` on an empty table and every row arrives after it, so the planner has no row estimate for `chunks` and takes the index scan at every size. Item (b)'s three-row `Seq Scan` was taken with the index built *after* the rows. Verified by an `EXPLAIN` probe over both orders at 3 / 40 / 166 / 2,003 rows: index-first gave `Index Scan using chunks_bm25` and one row at every size; index-after gave `Seq Scan` and all rows at 3 and 40, and the index scan at 166 and 2,003. The case asserts what was measured and names the other branch in a comment, as the plan's own instruction requires.
- Plan specified the crossover bisect over `lexicalSearch` on the closed range `[166, 4096]`. That crossover is **unreachable through `lexicalSearch`** for the reason above, so the `(b)` case bisects on a table carrying the same BM25 index options and the same `<@>` ordering with the index built after the rows — item (b)'s own conditions — over `[3, 4096]`, whose low end is below the crossover and whose high end is far above it. A range starting at 166 would have returned its own floor and measured nothing.
- Plan asked for the store-side assertion at `n = 40` and `n = 166` only. A third size, `n = 1024`, was added so the `(a)` case shows the property is not a small-corpus artefact; `4096` was not used, at about 17 s of inserts against about 3 s for 1024, and gate 4 runs this file on every invocation.
- The printed line is emitted verbatim but reaches gate 4's output as `# lexical-arm index-scan crossover: 63 rows` — `node --test` prefixes a test's stdout with `# ` in TAP. Task 12 should match the phrase rather than the line start.
