### Task 2 — Add the bounded case-concurrency helper and run `stack-presets.test.mjs`'s cases concurrently

**Goal:** Give the suite one owner for "how many cases of one file run at once", and use it first on `cli/test/stack-presets.test.mjs` (46 s alone, 25 top-level cases, 97 awaited subtests), so that file's cases share the machine's cores instead of running one after another.

**What this task produces for later tasks.** It **creates** `cli/test/helpers/concurrency.mjs`, which Tasks 3 and 4 import by exactly these three exports — `CONCURRENCY_VARIABLE`, `CASE_CONCURRENCY`, `concurrentSuite(name, fn)` — and Task 7 documents. It needs nothing from Task 1: it changes no fixture behaviour and calls `createFixture` exactly as it does today.

**Why concurrency inside the file, not a split (the hint weighed).** `node --test` runs files in parallel and the cases of one file in series; its file-level concurrency defaults to `os.availableParallelism() - 1`. On a **2-core** runner that is **one file at a time**, so splitting a slow file into several gains nothing there, and on a 4-core runner it gains at most three slots. Every case here is a serial chain of subprocesses — the fixture's git calls, then one `init` (~210 ms, 12 git processes) — measured at ~97% CPU, so the only way one file uses more than one core is to have more than one case in flight. A bounded in-file concurrency does that at every core count, moves no test between files, and keeps each file's header, helpers and history in one place. The planner confirmed on Node v20.19.5 that top-level `test()` calls in one file run serially and that the children of a `describe(name, { concurrency: n }, fn)` run `n` at a time.

**Isolation, established rather than assumed (planner's audit of this file, to be re-checked by the implementer).** Every case builds its own fixture through `fixtureFor` → `createFixture` under a fresh `mkdtemp` directory and tears it down with `t.after`; the file sets no `process.env` value (every environment override is passed to one subprocess through `runCli`'s `env` argument); it holds no module-level mutable state — its top-level `await`s import read-only compiled modules; it reads `cli/dist/` and never writes it; and it contains no timing assertion (`sleep`, `Date.now`, `setTimeout`, polling) — `grep -nE "sleep|eventually\(|Date\.now|performance\.now|setTimeout|process\.kill|process\.env\.[A-Z_]+ *=" cli/test/stack-presets.test.mjs` prints nothing.

- `cli/test/stack-presets.test.mjs` — the suite wrapper, the concurrent subtests of its two slowest cases, and its header.
