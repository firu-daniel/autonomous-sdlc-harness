### Task 15 — `docs/github-run-control.md` §4 and §5: the pull request from the start, the target rule and the table

**Goal:** Rewrite the design of record for the draft pull request (§4) and for lifecycle comments and labels (§5), so that they state what Tasks 3–10 ship: the pull request opens when the run starts, its draft state follows the run, the issue names it as it opens, `completed` goes to both items, and a run keeps one progress comment.

**Depends on:** Tasks 3, 4, 6, 7, 9 and 10, whose behaviour this task documents. Restated here so nothing else is needed:

- **Opening (Tasks 4, 5).** `harness-run.yml`'s step `Open the draft pull request` runs `remote-run.sh open <branch>` before `Run the harness`, on every job whose `chain` input is `0`, meaning a job a person's action started. It reuses an open pull request. Otherwise it opens a draft with `HARNESS_GIT_TOKEN` when set, else the job's token. A `PR_CREATE_FORBIDDEN` refusal is not retried, and any other failure is retried once without `--draft`. On success it labels the pull request `sdlc-harness: running` and, when the run has a source issue, posts one comment there naming `#<pr>` and its URL (marker `event=opened`). On failure it posts nothing and logs one `::warning::`. The body: *This pull request carries the harness run on `<branch>`. It stays a draft while the run works, and the harness marks it ready for review when the run completes; the harness never merges it.*, then `Started from #<n>.`, the round sentence, the commands, and the `pull-request` marker.
- **Completion (Task 6).** `deliver` reuses the open pull request, or, when none is open, opens one through the same function as a fallback. It marks a draft ready (`gh pr ready`, the job's token). It leaves a non-draft as it is and says so (*drafts may not be available on this repository's plan, or someone marked it ready*). A refused flip is one warning line. It posts `completed` on the pull request always and on the source issue too (the issue's comment names `#<pr>` and its URL), and sets `sdlc-harness: done` on both.
- **A round (Task 7).** The `round` report turns a ready pull request back to draft (`gh pr ready --undo`). A refusal is one warning line. `failed` on a pull request says the draft stays open, and how to proceed: for a task run, close it to discard the run, or re-apply the trigger label to the issue; for a round, a review requesting changes. `stopped` adds that the draft stays open and that closing it discards the run. Parked, paused and stopped runs change no draft state.
- **Recognition (Task 3).** A pull request from the run's branch is a target when the branch's origin tip carries its task prompt or its flow-progress ledger.
- **Progress (Tasks 9, 10).** One comment per run or round on the pull request only, edited in place, listing *Planning / Implementation / Branch review / Done* for a run and *Fix plan / Fix implementation / Branch review / Done* for a round. For a round, *Branch review* ticks when its QA and run-gates entries (`R4`, `RG`) are through, since a round's ledger carries no review entries. It is rendered from the ledger the job's checkout carries, posted when a phase changes and once at each job's end, never edited when nothing changed, and withheld for a stopped branch. It sets no label. It is off when `execution.progressComments` is `false`, and its marker is `event=progress`, with `round=<n>` for a round.
