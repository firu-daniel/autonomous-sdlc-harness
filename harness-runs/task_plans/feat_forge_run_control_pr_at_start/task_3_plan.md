### Task 3 — Recognise a run's branch by its task prompt or its ledger, and read the pull request's draft state

**Goal:** Make a pull request opened at the run's start a lifecycle target before the flow's first ledger push, and make every caller of the pull-request lookup see whether that pull request is a draft. Today `forge_recognised` accepts only a branch whose origin tip carries `<state_dir>/flow_progress/<branch>_progress.md`. That ledger is not on origin until the flow's first committer push, so a pull request opened at start would be skipped by the target rule for the run's first stretch.

**Where this task stops.** It changes recognition and the lookup only. Opening the pull request is **Task 4's**, flipping its draft state is **Tasks 6 and 7's**, and the documentation of the new recognition is **Task 16's** (`docs/github-run-control.md` §1 and §2). This task is the first of the six that edit `cli/templates/scripts/remote-run.sh`. Each later one (4, 6, 7, 8, 9) depends on the one before it.

**The decision this task carries out, and why.** A branch is recognised when its origin tip carries its task prompt **or** its ledger. The task prompt (`hr_task_prompt_rel "$state_rel" "$branch"`, that is `<state_dir>/task_prompts/<branch>_task_prompt.md`) is committed state, and `start` writes it as the branch's first commit (`verb_start` → `hr_place_artifact` / `hr_commit_placed`). The `pull-request` marker in the pull request's body was rejected as the test, because anyone with write access can edit a body and reading it costs a `gh` call. Committed state is what the function's own comment already promises (*"the harness-branch test, read from committed state"*).

### Targets

- `cli/templates/scripts/remote-run.sh` — `forge_recognised`, `forge_pr_var`, `control_check_branch`'s refusal text, `forge_report`'s not-a-target line, and the header paragraphs that state the rule.
- `cli/test/remote-report.test.mjs` — the `pushBranch` helper and the target-rule cases.
- `cli/test/remote-control.test.mjs` — the `pushBranch` helper and the commandability cases.
- `cli/test/remote-control-review.test.mjs` — the `pushBranch` helper and its not-a-harness-branch case.

**Why three suites, and not only two.** In each of the three suites, the fixture helper `pushBranch(branch, { ledger: false })` still commits the branch's task prompt (`${STATE_DIR}/task_prompts/${branch}_task_prompt.md`) and leaves out only the ledger. Once a task prompt alone is recognised, every existing case that uses `ledger: false` to stand for "not a harness branch" rests on a false premise and fails. No helper can push a branch carrying neither file today, so this task adds that option to each helper.

**The interface later tasks rely on:** after `forge_pr_var <branch>` succeeds, `FORGE_PR` is the open same-repository pull request's number or empty, and the new global **`FORGE_PR_DRAFT`** is `true`, `false`, or empty when `FORGE_PR` is empty. Tasks 6 and 7 branch on `"$FORGE_PR_DRAFT" = true` / `= false` and nothing else.
