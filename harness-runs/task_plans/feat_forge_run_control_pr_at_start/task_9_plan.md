### Task 9 — `report progress`: one phase-progress comment per run or round, edited in place

**Goal:** Item 6's poster. A new `report` event, `progress`, keeps **one** comment per run or per round on the run's pull request. The comment lists the four main phases and whether each is through, rendered from the flow-progress ledger in the job's own checkout. It is created when first rendered and edited in place after that. It is posted on the pull request only, never on the issue. It sets no label. It is withheld for a stopped branch, as every other job event is, and it is off when `execution.progressComments` is `false`.

**Depends on:** Task 8, the previous editor of `cli/templates/scripts/remote-run.sh`. Task 2's library functions, called exactly as that file states: `hr_ledger_phases <ledger_file>` prints `<engine> <round> <phase1> <phase2> <phase3> <phase4>` (engine `task`|`user_review`, round a number or `-`, each phase `done`|`pending`) with status 0, or nothing with status 1. `hr_progress_comments <root>` returns 0 when on (true or absent), 1 when off, and 2 when unreadable. Task 3's `forge_recognised` and `forge_pr_var` decide the target.

**Where this task stops.** This task renders and posts. *When* to call it is **Task 10's**: the job's supervision loop calls `bash "$REMOTE_RUN" report progress <branch> --repo <job checkout>` only when the `hr_ledger_phases` line changes, and once more when the job ends. A `report progress` call itself makes at most one listing and one write, and only when the rendered body differs. The volume decision (one comment edited in place, not one per boundary) and its reason are the story index's, and the documentation is **Task 15's** (§5).
