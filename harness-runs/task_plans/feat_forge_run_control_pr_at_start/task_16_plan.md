**Depends on:** Task 15, which edits §4 and §5 of the same file. This task leaves those two sections alone. The behaviour documented here, restated:

- **Recognition (Task 3).** A branch is a harness branch, and a pull request from it is a lifecycle target, when its origin tip carries its task prompt (`<stateDir>/task_prompts/<branch>_task_prompt.md`) **or** its flow-progress ledger. The refusal now reads `` `<branch>` is not a harness branch: its tip carries neither a task prompt nor a flow-progress ledger, and no `harness run <branch>` run is queued or in progress ``. The `started` clause still refuses a deleted branch, and the in-flight clause still covers a run dispatched by hand on a branch with neither file.
- **Threads (Task 8).** At a round's `completed`, `deliver` handles every inline thread whose comment the round's marker records (`comments=<id,…>`). The verdict comes from the fix plan's `**Review comments:** <id>[, …]` lines (a per-finding file, or the suffix of a `## Out of scope / verified-OK` bullet). For an implemented finding (`[x] **Finding K**`) it posts the reply ``Addressed in `<sha>`.``, `<sha>` being the commit that flipped that entry, then `resolveReviewThread`. For an out-of-scope or invalid observation it posts the reply `Not changed in this round: <reason>` and leaves the thread open. A thread already resolved, one the reviewer replied to after the round was collected, or one already carrying the harness's reply, is left alone. The reply carries the hidden marker (`event=thread`), so the next round never collects it. No review is ever dismissed. Every refusal is one warning line. It uses the job's token, through a paginated GraphQL `pullRequest.reviewThreads` read matched on each comment's `databaseId`.
- **Targets (Task 15's §5).** Every lifecycle comment goes to the recognised pull request, which now exists from the run's start, so a park's questions are posted there. A command on the issue keeps working, because `control` reads the branch from the trigger's `started` comment.
