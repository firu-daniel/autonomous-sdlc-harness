### Task 3 — Make `push-branch.sh` refuse to send commits that carry a credential, or, in a job, change a workflow file

**Goal:** A pushed commit never carries a credential (goal 4). `cli/templates/scripts/push-branch.sh` scans the commits it is about to send for every credential it can find. On a hit it prints a `refusing to push:` line naming what was found and where, but never the value. It pushes nothing, writes a push-refusal record, and still **exits 0**: the wrapper's exit contract and every caller's *never gate on it* stay as they are.

**And, in a GitHub job, it refuses a workflow-file change at the first push** (clarification answer 1, Q2 item 2). After Task 6 a job pushes only with `github.token`, which cannot write `.github/workflows/`. A commit that changes such a file would make that push, and every later push of the run, fail, which breaks goal 2 (every commit pushed as it lands) with nothing but a `push failed for` line. So when the main checkout carries the job push-credential marker, the wrapper checks the commits it would send for a change to a path under `.github/workflows/` and, on one, refuses through **the same refusal record** the credential scan uses. The watcher then fails the run visibly at once with that reason (Task 4), and the wrapper still exits 0. A file under `cli/templates/github/workflows/` is an ordinary file and is not matched.

**Depends on:** Task 2, which adds these to `lib/harness-run-lib.sh` (this script already sources it), the marker's constants and predicate among them:

- `hr_credential_values_var <main_top> [<extra>...]` sets `HR_CREDENTIAL_VALUES` and `HR_CREDENTIAL_LABELS`. Its sources are `GH_TOKEN`/`GITHUB_TOKEN` (`the job token`), `HARNESS_PR_TOKEN`/`HARNESS_GIT_TOKEN` (`HARNESS_GIT_TOKEN`), every `http.*.extraheader` in `<main_top>/.git/config` (`the persisted extraheader`), the passwords in each file that a `credential.*.helper` value of the exact shape `store --file <absolute path>` in `<main_top>/.git/config` names (`a stored git credential`; Task 5's `push-credential store` writes that key), and, as extra sources only, the passwords in `$HOME/.git-credentials` and `${XDG_CONFIG_HOME:-$HOME/.config}/git/credentials` (same label; a password there shorter than `HR_CREDENTIAL_EXTRA_MIN_LENGTH`, 8 characters, is not recorded, so a short local password cannot refuse a clean push). Each value is held raw and as the base64 of `x-access-token:<value>`.
- `hr_stream_has_credential` reads stdin and returns 0 on a hit (setting `HR_CREDENTIAL_HIT_LABEL` and `HR_CREDENTIAL_HIT_FORM`, `raw` or `base64`), 1 on none, 2 when the scan failed. It returns 1 when no value was found.
- `hr_push_refusal_record <main_top> <branch> <reason>` writes `<main_top>/.git/harness-push-refusals/<epoch>-<pid>.refusal`, two lines: `branch=<branch>`, `reason=<reason>`. It returns 1, writing nothing, on a newline in either argument.
- `HR_PUSH_CREDENTIAL_KEY` (`harness.pushCredential`) and `HR_PUSH_CREDENTIAL_JOB_TOKEN` (`job-token`), the job push-credential marker's key and value, owned by the library alone; and `hr_push_credential_is_job_token <main_top>`, read-only, which returns 0 only when `git config --file "<main_top>/.git/config" --get "$HR_PUSH_CREDENTIAL_KEY"` equals `$HR_PUSH_CREDENTIAL_JOB_TOKEN`, else 1, printing nothing.
- `HR_REMOTE_WORKFLOWS_DIR` (`.github/workflows`, no trailing slash), assigned at source time, the library's declared mirror of `cli/src/remote/githubActions.ts` → `WORKFLOWS_DIR`. It is the only code spelling of that path under `cli/templates/scripts`; this script matches against it and never retypes the path (architecture review round 4, Must Fix 1).

**The job push-credential marker, owned by the library.** Task 2 owns the marker's key and value in `lib/harness-run-lib.sh` (`HR_PUSH_CREDENTIAL_KEY`, `HR_PUSH_CREDENTIAL_JOB_TOKEN`) and the predicate that reads it. **Task 5**, which ships after this task, writes it: its `remote-run.sh push-credential store` sets it in the job checkout's local config through those constants, last of its three keys, and its `erase` unsets it. This script only calls `hr_push_credential_is_job_token "$main_top"` and spells neither the key nor the value on a code line (architecture review round 3, Must Fix 1). The marker is present exactly while the job's pushes authenticate through the stored `github.token`. That includes the end-of-job `Push the branch` step, because Task 6 puts `Erase the push credential` after it. A local run never carries it. Until Task 5 lands nothing sets it, so this check is inert in the tree between the two tasks, and this task's tests set the marker themselves.

**Where this layer stops.** This task refuses and records, for both reasons. Acting on the record — stopping the session, marking the run `failed`, notifying, and the job's `::error::` annotation — is **Task 4's** (`autonomous-watcher.sh`). The end-of-job `Push the branch` step of `harness-run.yml` already turns any line containing `refusing to push` into an `::error::` annotation and a job-summary line, and **Task 6** keeps that step. So the refusal line must contain the literal `refusing to push:`, as every other refusal here does.
