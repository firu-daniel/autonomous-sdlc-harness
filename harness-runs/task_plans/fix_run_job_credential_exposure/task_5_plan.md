### Task 5 — Give `remote-run.sh` the shared mention check, the `push-credential` verb and a `HARNESS_GIT_TOKEN` ready flip on every run

**Goal:** Three changes in `cli/templates/scripts/remote-run.sh`, the job-side script no agent may run (it is on the script-allowlist guard's deny list):

- **(a) Goal 4.** The mention reader's credential check becomes a call to the shared library predicate, so one check exists.
- **(b) Goal 3.** A new verb, `push-credential store|erase`, lets the `run` job push with `github.token` while its checkout persists no credential. It writes the token into git's `store` helper file, scoped to this repository, and later erases exactly that entry.
- **(c) Goal 3's CI trigger.** `deliver` makes the draft→ready flip with `HARNESS_GIT_TOKEN` (`HARNESS_PR_TOKEN` in this script's environment) when it is set, so the adopter's CI gets a `pull_request` `ready_for_review` event on the final tip. `github.token` pushes start no workflow. **On every run** (clarification answer 1, Q2 item 1): `ready_for_review` fires only on a draft→ready transition, so when `HARNESS_PR_TOKEN` is set and the pull request is already ready at delivery — a person marked it ready, a round's own `--undo` was refused, a resumed run — `deliver` first converts it back to a draft and then marks it ready again, so the event fires on each run's final tip. The conversion needs no permission `deliver` lacks (below).

**Depends on:** Task 2, which adds these to `lib/harness-run-lib.sh`, which this script sources:

- `hr_credential_values_var <main_top> [<extra value>...]` sets `HR_CREDENTIAL_VALUES` and `HR_CREDENTIAL_LABELS`. Its sources are `GH_TOKEN`/`GITHUB_TOKEN`, `HARNESS_PR_TOKEN`/`HARNESS_GIT_TOKEN`, every `http.*.extraheader` in `<main_top>/.git/config`, the passwords in each file a `credential.*.helper` value of the exact shape `store --file <absolute path>` names in `<main_top>/.git/config` (the file this task's `push-credential store` configures), the passwords in `$HOME/.git-credentials` and `${XDG_CONFIG_HOME:-$HOME/.config}/git/credentials` (those two files' passwords only when at least `HR_CREDENTIAL_EXTRA_MIN_LENGTH`, 8, characters long), and each extra argument (raw only, labelled `a saved credential`). Every non-extra value is held raw and as the base64 of `x-access-token:<value>`.
- `hr_text_has_credential <text>` returns 0 when `<text>` contains one verbatim.
- `HR_PUSH_CREDENTIAL_KEY='harness.pushCredential'` and `HR_PUSH_CREDENTIAL_JOB_TOKEN='job-token'`, the **job push-credential marker**'s key and value, assigned at source time. The library is their only owner; this script spells neither on a code line.

**Depends on:** Task 3, whose `push-branch.sh` reads the marker this task's `push-credential store` writes, through Task 2's `hr_push_credential_is_job_token "$main_top"` on the main checkout's `.git/config`, and only when it is present refuses commits that change a file under `.github/workflows/`, since the job's pushes then authenticate with `github.token`.

**The verb's contract, which Task 6 restates.**

- **`remote-run.sh push-credential store`.** Job-side, in the existing sense the header gives `open` and `deliver`: it runs in the job's checkout root.
  - **What it needs:** a non-empty `GH_TOKEN`. Without one: one line, nothing stored, exit 0.
  - **Where the entry points:**
    - the host is taken from `GITHUB_SERVER_URL` (default `https://github.com`);
    - the path is taken from `git -C <root> remote get-url origin`, which must be `https://<that host>/<path>`. Anything else is one line, nothing stored, exit 0.
  - **The store file:** `<store_file>` is `$HOME/.git-credentials` resolved **now**, to an absolute path. When it is not absolute, or carries a character outside `[A-Za-z0-9_./-]`, the verb prints one line, stores nothing and exits 0, so the helper value below never needs quoting.
  - **Writing the entry:** it writes one entry through `git credential-store --file "<store_file>" store`, fed on **stdin** as `protocol=https`, `host=<host>`, `path=<path>`, `username=x-access-token`, `password=<GH_TOKEN>`, under `umask 077`.
  - **Configuring the checkout:** it then sets three keys in the checkout's local config with `git -C <root> config`: `credential.https://<host>.useHttpPath true`, `credential.https://<host>/<path>.helper "store --file <store_file>"`, and last, once both are set, the **job push-credential marker**, through `git -C <root> config "$HR_PUSH_CREDENTIAL_KEY" "$HR_PUSH_CREDENTIAL_JOB_TOKEN"`. The helper names the file by absolute path, so the file that git pushes from is fixed in the checkout's `.git/config`. In a job that checkout is the watcher's main checkout, whose `.git/` the profile write-protects from the session (`cli/src/generators/writeProtection.ts`'s `.git` rows). `push-branch.sh`'s credential scan (Task 3, through Task 2's `hr_credential_values_var`) reads the same path from there, never from `HOME`.
  - **The marker** is how `push-branch.sh` knows its pushes authenticate with `github.token`, which cannot write `.github/workflows/`, and so refuses a workflow-file change (Task 3). It is a record the session cannot write, so the wrapper takes that mode from it and never from an environment variable such as `GITHUB_ACTIONS` (`harness-runs/lessons.md` → *Trust checks*: *"An unsandboxed script takes its mode and the path of every trust input from a record the session cannot write"*). The key name and its value are owned by `lib/harness-run-lib.sh` (Task 2), which both this script and `push-branch.sh` source, so this script reaches them only through `HR_PUSH_CREDENTIAL_KEY` and `HR_PUSH_CREDENTIAL_JOB_TOKEN` and never retypes them (`.claude/context/conventions.md` → `## Configuration is the source of truth, and it is read at run time`; architecture review round 3, Must Fix 1). The verb's header paragraph names the library as the marker's owner.
  - **Its output:** one line naming the host and path, never the token. Exit 0, and any failure is one `::warning::` line and exit 0.
- **`remote-run.sh push-credential erase`.** The same fields without the password, through `git credential-store --file "<store_file>" erase`, where `<store_file>` is the path the helper key names when it has the `store --file <absolute path>` shape, else `$HOME/.git-credentials`. Then `--unset` of all three keys, the marker first, through `git -C <root> config --unset "$HR_PUSH_CREDENTIAL_KEY"`. One line, exit 0 whatever happened.
- **Its usage and exit.** The verb takes no `--repo`: it runs in the job's checkout root, as `open` and `deliver` do, and the usage line says so. It always exits 0, and 1 only on a usage error (a missing or unknown `store|erase` argument).
  - An entry for the same host with no path, or another path — an operator's own on a self-hosted runner — must survive both `store` and `erase`.
- **Why `~/.git-credentials`.** The deny on this file is **derived from the profile, not measured on it**: the unattended profile names it in `sandbox.credentials.files` (read-denied to a sandboxed command) and so in its `Read` deny pair (the file tools). That is the same mechanism the GitHub-hosted runner rows S1 (runner) and S2 (runner) measured **pass** on `~/.ssh` (`docs/sandbox-verification.md` §9; `docs/sandbox-record.md` → `## 4. The measured results, per leg`, the `credentials` leg). Cite S1/S2 (runner) only as measuring that mechanism, never this file. The direct measurement on `~/.git-credentials` — a sandboxed read and a `Read` of it — is owed to roadmap item 35. Every unsandboxed git still reads it: the excluded wrappers, the end-of-job push, this script. The header says this in a paragraph, **THE PUSH CREDENTIAL STAYS OUT OF THE CHECKOUT.**, together with the derived-not-measured status of this file's deny and the measured-image scope of the mechanism (hosted `ubuntu-26.04` only; unverified elsewhere). The header cites no roadmap number (Task 10 adds the row after this task lands): it says the direct measurement on this file is owed.

**Deviations from plan:**

- *"`git credential fill` … for another path returns the operator's"* cannot hold for an operator entry with **no path**. git's credential store (measured with git 2.50.1, by the probe `harness-runs/scratch/t5_cred_probe.mjs` run through `scripts/scratch-run.sh`) matches a query that carries a path only against an entry carrying that same path. The `credential.https://<host>.useHttpPath` key the contract sets makes every query from the checkout carry its path, so no query from inside the checkout ever matches the operator's host-wide entry. Implemented: the fake `HOME` holds both a host-wide operator entry and one for another path. The other-path `fill` from inside the checkout returns the operator's path entry and never the job token. After `erase`, a host-wide `fill` from outside the checkout returns the operator's host entry. Both entries are byte-identical after `store` and after `erase`.
- The same probe measured a side effect. `git credential-store store` writes the new entry **first** in the file. So while the entry is stored, a host-wide query **outside** the checkout, which has no `useHttpPath`, through a `store` helper reading `~/.git-credentials` — an operator's own git on a self-hosted runner — is answered with the job token. The entry is erased at the job's end (Task 6). Not changed here; flagged.
- The contract says only that origin must be `https://<host>/<path>`. The code adds two narrower checks: the host must be of `[A-Za-z0-9.:-]` and the path of `[A-Za-z0-9_.~/-]`. Each value is written into a credential-protocol line and a config key name. Anything else gets the same one line and writes nothing.
- The three `store` config sets use `git config --replace-all`, so a stale multi-valued key cannot make the set fail. `erase` uses `--unset` as written; an absent key (exit 5) counts as success.
- An `erase` whose host or path cannot be derived writes nothing, the marker included: one line, exit 0. This is the same as `store`.
- `cli/test/remote-control-mention.test.mjs` pins no `MENTION_JOB_TOKEN_B64` internals: its job-token case asserts behaviour only. So it is unedited and was not run by this unit. The Run gates phase's suite run verifies the mention check's unchanged behaviour.
