### Task 12 — Developer docs: the watcher's park protocol, `park_loop` and its knobs

**Goal:** Make the developer documentation of the watcher state what it now does with a park — resume once every open question file is answered, archive exactly the consumed set — and document the park-loop guard: what counts as no progress, the two knobs and why their defaults are what they are, the `park_loop` status and notification, the log evidence, and the operator action that clears it.

**Depends on:** Tasks 1, 2 and 3, restated so this file stands alone:

- **Task 1:** `resume_parked_run` resumes a `parked` record only when every top-level `question_<n>.md` has its `answer_<n>.md`, records every such index as `resumed_for_index` (space-separated), and names every answer file in the resume prompt; `classify_run_exit` archives exactly those pairs on exit and records `parked` when a top-level question is unanswered or a top-level pair remains (one written during the resumed session). One question file is one park (Task 7's channel); a park written under the old layout — several files — follows the same rule.
- **Task 2:** a park-resumed session that parks again counts as a no-progress cycle when it raised no question file above the highest index present at resume time, or when it parked again less than `PARK_LOOP_WINDOW_SECS` (default `300`) after the resume. After `PARK_LOOP_MAX_CYCLES` (default `2`; `0` disables) consecutive cycles the status is `park_loop`, `watcher.log` carries `resume made no progress (cycle <c>/<max>: <reason>)` per cycle and `park loop — <c> consecutive resumes made no progress; not resuming it again`, and one `park_loop` notification is sent. A progress cycle, `completed` or `failed` resets the count; a session launched by the pause-resume pass is never counted. Clearing: create `<state_dir>/clarifications/<branch>/PARK_LOOP_CLEAR` in the run's working copy; the next pass removes it, resets the count and sets `parked`, and the run resumes in that same pass when its park is answered. **Inbox guard:** `process_inbox_file` treats a `park_loop` record like a `parked` or `paused` one that owns the branch's working copy — a dropped task prompt or review file for that branch is archived as `rejected_<ts>_…`, no engine is launched, the record is left byte-identical, `watcher.log` carries a `held by the park-loop guard` line, and the rejection detail names the `PARK_LOOP_CLEAR` action ("create <clar_dir>/PARK_LOOP_CLEAR to clear it, then drop the file again"), never an answer. Measured basis for the defaults (this repository's watcher log, 2026-09-17): real park-resumed sessions of 50m04s, 38m28s and 3h01m56s; spurious ones of 41s and 39s.
- **Task 3:** the notifier's vocabulary is seven words (`park_loop` added, title `Run stuck in a park loop`), and `cleanup-merged-worktrees.sh` and `restart-watcher.sh` treat a `park_loop` record like a `parked` one.

**Where this task stops.** The protocol's canonical definition stays in the plugin (Task 7's channel section and `plugin/instructions/autonomous_pause_and_ledger.md`); this document describes the watcher's side and cites them. `docs/outer-loop-verification.md` is a dated measurement record and is **not** edited.
