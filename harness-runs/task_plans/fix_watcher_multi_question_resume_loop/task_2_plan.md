### Task 2 — Watcher: the park-loop guard, its `park_loop` status and its operator clear

**Goal:** Stop the watcher from re-resuming any run whose park-resumes make no progress, whatever the cause: count consecutive no-progress cycles, and after a bounded number record the distinct status `park_loop`, log the evidence, send one `park_loop` notification and resume the run no further until an operator clears it.

**Depends on:** Task 1, which owns the other half of `cli/templates/scripts/autonomous-watcher.sh`. From it this task relies on: `resume_parked_run` resuming only a fully answered park and computing the consumed set before it calls `spawn_engine`; `classify_run_exit` archiving every index in `resumed_for_index` and then deciding `parked` when a top-level question lacks its answer or a top-level pair remains. This task adds its bookkeeping **inside** those two functions, after Task 1's logic, and changes neither rule.

**Where this task stops.** It emits the notification word `park_loop` through the existing `notify` helper; the notifier's own declaration of that word, and the other scripts that enumerate registry statuses, are **Task 3's** (the notifier delivers an unknown word under a generic title meanwhile, so this task ships on its own). The documentation of the guard is Task 12's and the command that names the clear action is Task 10's. The automated tests are Task 5's.

### Targets

- `cli/templates/scripts/autonomous-watcher.sh` — the tunables block, `print_status`, the header (status vocabulary, subcommand notes, REPRO — the new `a park loop` entry and the existing `a guard` entry), the registry field documentation, `launch_run`, `resume_parked_run`, `resume_paused_run`, `classify_run_exit`, `process_inbox_file` (its record-owns-the-working-copy guards), `tick`, and one new function `clear_park_loops`.

**Work:**

- [ ] Tunables and vocabulary. In the tunables block add `PARK_LOOP_MAX_CYCLES="${PARK_LOOP_MAX_CYCLES:-2}"` (consecutive no-progress cycles before `park_loop`; `0` turns the guard off) and `PARK_LOOP_WINDOW_SECS="${PARK_LOOP_WINDOW_SECS:-300}"`, each with a comment stating what the knob does, what `0` does, and that its default is sized from measured park-resumed sessions — pointing to the harness repository's `docs/watcher.md` §4 (**A resume that makes no progress is bounded.**, Task 12) for the numbers **without repeating them**. This template is copied byte for byte into every adopting repository, so the comment carries no timing, no date and no reference to "this repository's watcher log"; `docs/watcher.md` §4 is the only place the measurements are written (`.claude/context/conventions.md` → `### Where a new responsibility goes`). Append both to `print_status`'s `tunables:` line. Add `park_loop` to the status vocabulary in the header paragraph that fixes it and in the `status` field documentation, and document the new registry fields: `resume_kind` (`answer` | `pause` | empty), `resumed_at_epoch`, `resume_max_question_index`, `park_loop_cycles`.
- [ ] Resume bookkeeping. `resume_parked_run`, on the resume path only (after the deferral checks): `resume_kind` `answer`, `resumed_at_epoch` `$(date +%s)`, and `resume_max_question_index` = the highest numbered `question_<n>.md` index across the top level **and** `answered/`. `resume_paused_run`: `resume_kind` `pause` and `resumed_at_epoch`. `launch_run`, beside its other "never inherit a prior run's state" clears: `resume_kind` empty and `park_loop_cycles` `0`.
- [ ] `classify_run_exit` accounting, after Task 1's archival and parked decision, and never on the pause branch (which returns first). Read `resume_kind`, then clear it. When the run is `parked`, `resume_kind` was `answer` and `PARK_LOOP_MAX_CYCLES` is not `0`: the cycle made **no progress** if no numbered question file (top level or `answered/`) has an index above `resume_max_question_index` — reason `no question above index <m>` — **or** `now - resumed_at_epoch` is below `PARK_LOOP_WINDOW_SECS` — reason `re-parked after <s>s, inside PARK_LOOP_WINDOW_SECS=<w>`. On no progress increment `park_loop_cycles` and log `run '<branch>' resume made no progress (cycle <c>/<max>: <reason>)`; when the count reaches the bound set status `park_loop`, log `run '<branch>' park loop — <c> consecutive resumes made no progress; not resuming it again (clear: <clar_dir>/PARK_LOOP_CLEAR)`, and `notify park_loop "$branch" "$log_path" "<c> no-progress resumes — create <clar_dir>/PARK_LOOP_CLEAR to clear"` **instead of** the `parked` log and notification. Otherwise the ordinary `parked` path runs. A progress cycle, any `completed` and any `failed` exit set `park_loop_cycles` to `0`.
- [ ] Clear pass and inbox guard. New `clear_park_loops`: for each record whose status is `park_loop`, resolve the working copy's state directory as `resume_parked_run` does (a missing copy or an unresolvable directory leaves the record as it is, with the same one-line log shape), and when `<worktree>/<state_rel>/clarifications/<branch>/PARK_LOOP_CLEAR` exists: remove it, set `park_loop_cycles` `0`, set status `parked`, and log `park loop cleared for '<branch>' (PARK_LOOP_CLEAR found) — back to parked`. Call it in `tick` immediately **before** `resume_parked_runs`, so a cleared, fully answered run resumes in the same pass. `resume_parked_runs` still offers only `parked` records, which is what keeps a `park_loop` record from ever resuming. Add a REPRO entry `a park loop` covering the trip, the unchanged record on a following tick with an answer present, and the clear. **Inbox guard:** a `park_loop` record owns its working copy and its outstanding clarification state exactly as a `parked` one does, and a fresh launch would also run `launch_run`'s `park_loop_cycles` `0` reset and silently discard the guard's hold — so in `process_inbox_file` extend the `hint_worktree` / `hint_state` condition (`if [ "$existing_status" = "parked" ] || [ "$existing_status" = "paused" ]`) to `park_loop`, and add a third branch after the `paused` one and before `lane_blocks_start`, with a comment in the style of the two above it: `log "'$branch' has a run held by the park-loop guard — rejecting '$fname' (create $hint_worktree/$hint_state/clarifications/$branch/PARK_LOOP_CLEAR to clear it, then drop the file again)"`, then `reject_preserving_status "$branch" "$file" "$fname" "(the branch has a run held by the park-loop guard — create <clar_dir>/PARK_LOOP_CLEAR to clear it, then drop the file again)"` and `return 0`. The detail names the clear action, never "answer it" — answering does not release a `park_loop` record. Extend the REPRO `a guard` entry's "with a `parked` (or `paused`) record" to "with a `parked`, `paused` or `park_loop` record".
