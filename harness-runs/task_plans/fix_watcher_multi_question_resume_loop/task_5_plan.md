### Task 5 — Tests: the loop guard trips, clears, and never catches a real double park

**Goal:** Prove the park-loop guard against the written watcher: a forced no-progress cycle stops after the documented bound with the `park_loop` status, one notification and a log line naming the loop; the documented clear action restores normal resuming; and neither a run that parks again for real reasons nor a legacy in-flight park nor a pause-resumed session is ever caught.

**Depends on:** Task 2, Task 3 and Task 4.

- From **Task 2**, restated: tunables `PARK_LOOP_MAX_CYCLES` (default `2`, `0` disables) and `PARK_LOOP_WINDOW_SECS` (default `300`). A park-resumed session (`resume_kind` `answer`) that exits `parked` is a no-progress cycle when no question file, top level or `answered/`, has an index above `resume_max_question_index` (the highest index at resume time), or when it parked again less than `PARK_LOOP_WINDOW_SECS` after `resumed_at_epoch`. Each counted cycle logs `run '<branch>' resume made no progress (cycle <c>/<max>: <reason>)`; at the bound the status becomes `park_loop`, the log gets `run '<branch>' park loop — <c> consecutive resumes made no progress; not resuming it again (clear: <clar_dir>/PARK_LOOP_CLEAR)`, and one `park_loop` notification replaces the `parked` one. A progress cycle, `completed` or `failed` resets `park_loop_cycles` to `0`. Each pass runs `clear_park_loops` before the park-resume pass: a `park_loop` record whose working copy has `<state_dir>/clarifications/<branch>/PARK_LOOP_CLEAR` loses that file, gets `park_loop_cycles` `0` and status `parked`, and the log gets `park loop cleared for '<branch>' (PARK_LOOP_CLEAR found) — back to parked`. A session started by the pause-resume pass carries `resume_kind` `pause` and is never counted.
- From **Task 3**: the notifier accepts `park_loop` as a declared event (the suite's recorder replaces it, so this is context, not an assertion here).
- From **Task 4**: `cli/test/helpers/watcher.mjs` → `createWatcherFixture(t, { branch })`, returning `dir`, `branch`, `clarDir`, `writeQuestion(n, body)`, `writeAnswer(n, body)`, `topLevel()`, `archived()`, `setStub(shellBody)` (runs with `CLAR` set, in the run's working copy), `seedRecord(fields)`, `record()`, `tick(env)`, `prompts()`, `notifications()` (`{ event, branch, detail }`), `watcherLog()`. This task imports it and does not edit it; a missing capability is added to this suite as a local helper instead.

**Work:**

- [ ] Header first: the rule (a resume that makes no progress is bounded, the bound is distinct and clearable, and a run that makes progress is never caught), plus a citation of `docs/watcher.md` §4 (**A resume that makes no progress is bounded.**, written by Task 12) as the source of the measured basis for the defaults — cited, not copied: the header repeats no timing, and Task 2's tunables comment is not named as a source, since it carries no numbers.
- [ ] Case **forced no progress, index detector** (`PARK_LOOP_WINDOW_SECS=0`, defaults otherwise): seed a `parked` record with `question_5.md` answered; the stub writes an unanswered `question_<k>.md` for the lowest `k` with no question file in either location (so every new file sits below index 5). Tick, answer the new question, tick again → after the second exit the record is `park_loop` and `park_loop_cycles` is `"2"`, `notifications()` holds exactly one `park_loop` event and no `parked` event for that exit, and `watcherLog()` matches both the `made no progress (cycle 1/2` and `cycle 2/2` lines and the `park loop —` line. Answer the open question and tick once more → no new prompt, record still `park_loop`.
- [ ] Case **the clear action**, continuing that fixture: create `<clarDir>/PARK_LOOP_CLEAR`, switch the stub to one that asks nothing, tick → the sentinel is gone, the cleared line is logged, exactly one new prompt was issued in that same pass, and the record ends `completed` with `park_loop_cycles` `"0"`.
- [ ] Case **window detector**: `PARK_LOOP_WINDOW_SECS=3600`; the stub raises the next index above every existing question each time (real progress by index, but instantly) → caught as `park_loop` after two cycles, with the `inside PARK_LOOP_WINDOW_SECS=3600` reason in the log. Case **a real multi-park is never caught**: `PARK_LOOP_WINDOW_SECS=0`, the same next-index stub, three answer-and-tick rounds → the record is `parked` after every round, no `park_loop` notification, `park_loop_cycles` `"0"`.
- [ ] Case **a legacy in-flight park is not caught, and pause-resume is not counted**: the old-layout fixture from Task 4 (pair 1 archived, pairs 2 and 3 at the top level, `question_4.md` then `answer_4.md`) under the **shipped defaults** (`PARK_LOOP_MAX_CYCLES=2`, `PARK_LOOP_WINDOW_SECS=300`), stub raising `question_5.md` → one resume, record `parked`, **no** `park_loop` notification, and `park_loop_cycles` `"1"` — below `PARK_LOOP_MAX_CYCLES` — with a `made no progress (cycle 1/2: re-parked after` line naming `inside PARK_LOOP_WINDOW_SECS=300` in `watcherLog()`: under Task 2's contract the stub's instant re-park is a window no-progress cycle (the index detector alone would call it progress, since `question_5.md` is above `resume_max_question_index` `4`), so asserting `"0"` here would contradict the watcher. Then answer `question_5.md`, switch the stub to one that asks nothing, and tick → exactly one new prompt, record `completed`, `park_loop_cycles` `"0"`, and still no `park_loop` notification. **Why defaults and not `PARK_LOOP_WINDOW_SECS=0`:** prompt item 5 is about the watcher an adopter actually runs after the upgrade, and zeroing the window would switch off one of the two detectors and prove only the other; with the defaults this case shows that an in-flight run's single post-upgrade resume can spend at most one cycle of the bound, that "not caught" means the guard never trips (no `park_loop` status, no `park_loop` notification) rather than that nothing is counted, and that the run then resumes on through to completion with the count reset. Then a `paused` record with `sdlc-harness/PAUSE_ACK` and `sdlc-harness/RESUME` present, `PARK_LOOP_WINDOW_SECS=3600`, and a stub that exits leaving an unanswered question below the highest index → after the pause-resume tick the record is `parked` and `park_loop_cycles` is unchanged.
