### Task 1 — Replace `run_alive`'s `kill -0` with a `.running` mtime heartbeat in the `run-test-suite.sh` template

**Goal:** Make the template's liveness check one that the unattended sandbox allows. Both `run_alive` callers depend on it: the wait form's `wait_for_verdict` and the run form's one-run-per-label guard. The mtime of `<label>.running` becomes the run's heartbeat. While the run form is alive, a heartbeat process it starts refreshes the mtime every second. A reader treats a heartbeat older than `STALE_SECONDS` as a dead run. The wire stays byte-for-byte as it is, and so does the way each gate runs: in the foreground of the run form, so every signal that stops a gate today still stops it.

**Where this task stops.** It edits the **template** only, which is what a future adopter receives. It does not touch `scripts/run-test-suite.sh`, this repository's byte-identical copy; **Task 3** brings that copy level. It adds no test case and edits no test file. **Task 2** owns `cli/test/run-test-suite.test.mjs` and is the behavioural proof of this task. It names the two environment variables this task defines, drives each of the three run states through them, and drives the signal cases stated under *"Measured signal behaviour"* below. It does not edit `docs/sandbox-verification.md`, which is **Task 4's**.

**Why the old check failed. This is the measurement the header must cite.** It was taken 2026-10-23 on Claude Code 2.1.309, macOS, in a headless sandboxed session on the watcher's launch line, under the live profile.
- `kill -0` from a later sandboxed call on a process another call started: `kill: (68252) - Operation not permitted`, exit 1.
- The same call on a process the wrapper had detached itself (`nohup … &`, `disown`): `kill: (70347) - Operation not permitted`.
- `kill -0` within one call on that call's own child: exit 0.
- `ps -p` was refused even within one call: `/bin/ps: Operation not permitted`, exit 126.
- `pgrep` was refused too: `pgrep: Cannot get process list`, exit 3 (`cli/test/test-timeout.test.mjs`).

So a reader in a later call can neither signal nor list the run.

**Measured signal behaviour of the shape below.** The plan writer measured a prototype of exactly the shape this task prescribes (foreground gate subshell carrying `3>&-`; heartbeat process on `exec 3> >(…)`; the trap below) on 2026-10-23, macOS, GNU bash 3.2.57, **unsandboxed**, with a gate held by `exec sleep 8`. The header states these results as the shape's design properties, not as a sandbox measurement; the sandboxed rows are Task 4's owed WF2–WF4.
- `SIGINT` to the run form's **process group** (a terminal Ctrl-C, or a tool interrupting the group): the gate stopped, the trap ran, `.running` was removed. The gate runs in the foreground with default dispositions, so `SIGINT` / `SIGQUIT` are not ignored in it, exactly as today.
- `SIGKILL` to the run form's **process group**: the gate and the heartbeat both stopped; `.running`'s age grew past the stale bound.
- `SIGTERM` to the run form's **PID alone** while the gate runs: bash defers a trapped signal until its foreground command returns, so the gate kept running, the heartbeat stayed fresh (age 1 three seconds after the signal) and the label stayed live. When the gate ended, the trap ran before the next command: `.running` removed, exit 143, no further marker, no verdict.
- `SIGKILL` to the run form's **PID alone**: the gate survived, orphaned, as it does today under the same signal; the heartbeat **stopped**, because the gate holds no copy of the heartbeat pipe. **Control:** the same prototype without `3>&-` on the gate kept the heartbeat fresh (age 0) after the run form died. That is why `3>&-` is load-bearing.

**Work:**

- [ ] **Constants, the seam, and the mtime read.** Add these beside `WAIT_SLICE_SECONDS`:
  - `HEARTBEAT_SECONDS=1`, a fixed constant with no override.
  - `STALE_SECONDS=30`, overridable through `RUN_TEST_SUITE_STALE` on the same terms as `RUN_TEST_SUITE_WAIT_SLICE`, with a lower bound. The value must match `^[0-9]+$` **and be at least `3`**; any other value, `0`, `1` and `2` included, leaves the default standing. Why `3`: mtimes are whole seconds and the refresh period is slightly over `HEARTBEAT_SECONDS` (1), so a live run's age reads up to `2`; a bound of `1` or `2` would judge a healthy run dead. The variable is a test seam, the lessons ledger's *"behind an environment variable rather than a configuration key"*. It joins no configuration key.
  - `heartbeat_age`, a function that prints the age in whole seconds of `$running_file`'s mtime: `$(date +%s)` minus the mtime. A negative age reads as `0`. It reads the mtime through `hr_lane_mtime "$running_file"`, the portable mtime reader `cli/templates/scripts/lib/harness-run-lib.sh` already owns; the script already sources that library (`hr_lib="$script_dir/lib/harness-run-lib.sh"` / `. "$hr_lib"`). It calls no `stat` itself. `hr_lane_mtime` prints `0` for a missing path or an unreadable mtime, so `heartbeat_age` maps a `0` result to a non-zero return and prints nothing. `run_alive`'s `-f` re-test below then tells "vanished, so finished" from "present but unreadable, so refuse".
  - Do not edit `cli/templates/scripts/lib/harness-run-lib.sh`. Task 3's statement, that only `scripts/run-test-suite.sh` differs from its template, depends on it.
  - Use no external binary beyond `date`, `touch`, `sleep` and `rm`. In particular use no `find -newer*`, whose BSD and GNU flags differ, no `mkfifo`, and no `perl` or `python`.
- [ ] **`run_alive` rewrite, the only liveness decision.**
  - `[ -f "$running_file" ]` fails → return 1.
  - `heartbeat_age` succeeds → return 0 when the age is `<= STALE_SECONDS` and 1 otherwise. The predicate is `<=`: a heartbeat exactly `STALE_SECONDS` old is still live.
  - `heartbeat_age` fails → test `-f` again. A file that vanished meanwhile, because the run finished, returns 1, and the caller's existing verdict re-check then finds the verdict. A file still present but unreadable calls `refuse "cannot read the heartbeat of '$running_file'"`, which exits 2 with one stderr line. It never guesses live or dead.
  - It no longer reads the PID, and it calls no `kill`, `ps` or `pgrep`.
  - Leave `wait_for_verdict` and its two call sites unchanged. A stale heartbeat therefore reaches the existing `refuse "no run in flight for $label"`, byte-for-byte.
- [ ] **The gates stay in the foreground; the heartbeat is a separate process tied to the run form by a pipe, never by a signal.**
  - Add `heartbeat_stop_file="$running_file.stop.$$"` next to the other path assignments. The `$$` suffix makes it per-run, so a finishing run's heartbeat can never stop a later run's. The name stays internal, like `$verdict_file.tmp`: it is not part of the wire and the header does not list it beside `.running` / `.verdict` / `.log`.
  - Define `heartbeat_loop`. It starts a background touch loop, `( while [ ! -e "$heartbeat_stop_file" ]; do touch -c "$running_file"; sleep "$HEARTBEAT_SECONDS"; done ) &`, keeping its PID in a local. It then blocks in `while IFS= read -r _; do :; done` on its standard input, which returns only at end of file, that is, once every writer of the pipe has closed it. It then writes `: > "$heartbeat_stop_file"`, `wait`s for its own touch loop, and runs `rm -f "$heartbeat_stop_file"`. Use `read` **without** `-t`: bash 3.2's `read -t` returns 1 on both timeout and EOF, so it cannot drive the end-of-life test, and that is why the touch loop and the reader are two processes. `touch -c` refreshes and never creates, so a heartbeat that outlives its run by a second cannot recreate a `.running` the run removed.
  - Right after `printf '%s\n' "$$" > "$running_file"` and the trap below, run `rm -f "$heartbeat_stop_file"`, then `exec 3> >(heartbeat_loop > /dev/null 2>&1)`. The run form holds fd 3, the pipe's only write end. The heartbeat's stdout and stderr go to `/dev/null`, so it never writes to the wrapper's streams and never holds the caller's stdout pipe open past the run form's exit. When the run form exits for **any** reason, `SIGKILL` included, the kernel closes fd 3, the reader sees EOF, and the heartbeat stops within `HEARTBEAT_SECONDS`.
  - Define `run_gate <command line>`: the gate's subshell exactly as today, `( set +u +o pipefail; eval "$1" ) 3>&- < /dev/null >> "$log_file" 2>&1`, run in the **foreground**, then `return $?`. `3>&-` closes the gate's inherited copy of the heartbeat pipe, so a gate, or anything it starts, that is orphaned when the run form dies cannot keep the heartbeat fresh. Each gate block calls `run_gate "$typecheck_line"` / `run_gate "$command_line"` and assigns `typecheck_status` / `test_status` from its return exactly as it assigns them from the subshell today, so a failing gate still yields `fail <log>` and exit 1. Keep the marker lines, their order and the typecheck-then-test sequence exactly as they are. `<none>` still runs nothing.
  - **Why the gate is not moved into the background.** A background list in a non-interactive bash starts with `SIGINT` and `SIGQUIT` ignored, the gate inherits that, and `trap - INT` cannot restore it; an interrupt to the group would then stop the run form and leave its gate running while the label reads free. Keeping the gate in the foreground keeps today's signal behaviour.
  - **Why no `kill -0`, even on the run form's own child.** The one permitted `kill -0` the measurement found was within **one live foreground call, on a child that call had just started**. Nothing measured a run form that **outlives the call that started it** signalling its own child, which is the self-detached shape `sandbox2c` may adopt. The task prompt's `## Constraints` → *"Scope against `sandbox2c`"* forbids a signal that depends on the starting call being alive. The heartbeat's end-of-life test is a pipe's EOF and a file, neither of which sends a signal.
  - After the `.running` removal at the end of the run form, run `exec 3>&-`, so the heartbeat stops at once rather than at exit.
- [ ] **A trapped termination drops the heartbeat, and stops no more than the signal did.** After `.running` is written, install `trap … TERM INT HUP` with a handler that removes `.running` only while that file still holds `$$`, the existing ownership rule, then exits `128 + <signal number>`, printing nothing on stdout and writing no verdict. The handler sends **no signal**: the script carries no `kill` at all. Exiting closes fd 3, which stops the heartbeat.
  - State in the header exactly what each signal stops, from *"Measured signal behaviour"* above: a signal to the run form's **group** (`INT` from Ctrl-C, `TERM`, `KILL`) reaches the foreground gate as it does today, then the trap (or the kernel) drops the heartbeat. A trapped signal to the run form's **PID alone** stops nothing at once: bash runs the trap only when the foreground gate returns, so the run stays live and heartbeating until then, and then ends with no verdict. So a run form stopped by a trapped signal never reports its label free while its gate still runs.
  - Once the trap has run, the next `--wait` refuses at once, as `no run in flight for <label>`, rather than after `STALE_SECONDS`.
  - A `SIGKILL` cannot be trapped. That case is the stale-heartbeat path.
  - Clear the trap (`trap - TERM INT HUP`) before the verdict is renamed into place, so a late signal cannot remove `.running` after the verdict decision.
