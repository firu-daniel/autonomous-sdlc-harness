### Task 1 — Compute per-session records from the event stream in `lib/run-analytics.jq`

**Goal:** Ship the `jq` program that reads one stream file's raw `stream-json` events and emits one record per headless session — time, idle gaps, per-request latency, per-tool-call and per-sub-agent time, cost and tokens, reliability — plus the small second mode that re-classifies idle gaps against host suspend intervals.

**Where this file stops.** It reads events and writes session records; it reads no file of its own, resolves no path, consults no host, and merges nothing. The run roll-up and the Markdown are **Task 2's** (`lib/run-analytics-report.jq`); locating the stream and the output, reading host suspend intervals, skipping already-recorded sessions' output, merging and writing are **Task 3's** (`run-analytics.sh`), which is this program's only caller and passes every `--arg` below. Nothing here is shipped by `init` until Task 4 adds its row.

### Targets

- `cli/templates/scripts/lib/run-analytics.jq` (new) — the program. This repository's own `scripts/lib/` copy is Task 9's.

**Work:**

- [ ] **Contract, header and parsing.** Open with a `#` header comment: what the program owns, its two modes, every `--arg`/`--argjson` it takes, its output shape (restate the record below), and the `jq` 1.5 floor (no `utf8bytelength`, no `--rawfile`, no `$ARGS.named`). The header states that **both modes take every variable** — `$mode`, `$idle_threshold_s`, `$known`, `$redact`, `$suspend`, `$suspend_source` — because `jq` resolves every `$name` the program references at compile time, not when the branch holding it runs, so a call omitting one aborts with `$<name> is not defined` whatever its mode; each mode ignores the variables it does not use, and the caller passes them as neutral values. Invocation by Task 3: `jq -n -R -c -S -f run-analytics.jq --arg mode sessions --argjson idle_threshold_s <int> --argjson known '<array of recorded session_id strings>' --argjson redact '<array of [from, to] string pairs>' --argjson suspend '[]' --arg suspend_source none < <stream file>` — one pass, `inputs | fromjson?`, so a non-JSON or truncated line is skipped, never fatal. Output: one compact JSON array of **new** session records, oldest first. Sessions: a session is the run of events from one `system`/`init` event to the next, identified by that init event's `session_id`; events before the first init are dropped; a session whose `session_id` is in `$known`, or was already emitted earlier in the same pass, is emitted nowhere; a session with no `result` event is emitted only when a later session follows it in the stream (it is then `complete: false`) — the stream's last session without a `result` is still in flight or was killed, and is left for a later run. Timestamps: whole seconds from `.timestamp[0:19] + "Z" | fromdateiso8601`, plus the fractional digits after the `.` padded or cut to three, so latency keeps milliseconds; events with no `timestamp` (`tool_progress`, `system`/`task_progress`, `system`/`thinking_tokens`) are ignored for every time computation. Redaction, defined once as a function and applied to every free-text field written: each `$redact` pair replaced literally (Task 3 passes, in order, the run copy's root → `<repo_root>`, the main checkout → `<main_repo>`, `$HOME` → `~`), then any remaining `/Users/<segment>` or `/home/<segment>` prefix → `~`, then cut to 160 characters. The `system`/`init` event's `cwd` is never read into output.
- [ ] **Contexts, requests and retries.** An event's context is `orchestrator` when it has no `parent_tool_use_id`, else the dispatching `Agent`/`Task` `tool_use`'s `input.subagent_type` (or `subagent` when absent). One API request is one `message.id` within a context; its usage is taken from the **last** assistant event carrying that id (output tokens grow across them). `latency_ms` is the task prompt's rule exactly: from the last timestamped event in the same context to the first assistant event carrying a new `message.id` in that context; a sub-agent's first request measures from its dispatching `tool_use`'s timestamp when the context has no earlier event. `after_retry` is `true` when a `system`/`api_retry` event of the same context lies between those two points. Per request emit `{started_at, context, latency_ms, output_tokens, input_tokens, cache_read_tokens, cache_write_tokens, after_retry}` (`cache_write_tokens` = `usage.cache_creation_input_tokens`). Roll up `{count, p50_ms, p90_ms, p99_ms, max_ms, over_threshold}` for the session (`overall`) and per context (`by_context`), percentiles by nearest rank (`sorted[ceil(n*q) - 1]`), `over_threshold` = requests whose latency exceeds `idle_threshold_s`.
- [ ] **Tool calls, polling loops and sub-agent dispatches.** A tool call runs from its `tool_use` event to the `user` event carrying its `tool_result` (matched on `tool_use_id`); per call emit `{tool, context, started_at, duration_ms, result_bytes, is_error, permission_denied}`, where `result_bytes` is the UTF-8 byte length of the result's text (a string, or the sum of an array's `text` parts) computed in `jq` 1.5 by `explode` and code-point ranges (1/2/3/4 bytes below 0x80/0x800/0x10000/above), and `permission_denied` is `true` when the call's `tool_use_id` appears in the `result` event's `permission_denials` or in a `system`/`permission_denied` event. Roll-ups: `by_tool` = `{tool, context, count, total_ms, max_ms}` per tool name per context; `slowest` = the top 10 calls by `duration_ms`; `polling` = `{context, command, count, total_ms}` for every redacted `Bash` `input.command` issued **3 or more** times in one context (the run-gates `--wait` loop is the case it exists for; the `3` is a named constant in the header). A sub-agent dispatch is an `Agent` or `Task` `tool_use`; emit `{type, description, started_at, duration_ms, requests, output_tokens, input_tokens, cache_read_tokens, cache_write_tokens, wall_share}` — `requests` and tokens summed over the requests whose `parent_tool_use_id` is that dispatch's id, `wall_share` = `duration_ms / wall_ms` rounded to 4 decimals. This is the same dispatch rule as `cli/templates/github/workflows/harness-run.yml` → `THE SELF-PAUSE POINT, MEASURED`'s one-off `jq`, so its figure is re-derivable from these records.
- [ ] **Time and idle gaps.** `wall_ms` = last − first timestamp of the session; `duration_ms`, `duration_api_ms` from the `result` event; `host_suspended_ms` = `max(0, wall_ms − duration_ms)` (`duration_ms` is the monotonic clock that excludes suspend — the task prompt's arithmetic); an idle gap is any interval between consecutive timestamped events of the session, any context, longer than `idle_threshold_s`, emitted as `{start_at, length_ms, context, class}`; `idle_ms` = the sum of gap lengths; `active_ms` = `wall_ms − idle_ms`. Class at the gap's start, in this precedence: `in_flight_request` when some context's last timestamped event is a `user` event (or the orchestrator's `system`/`init`) with no assistant event after it — context = the most recently active such context; else `tool_running` when some `tool_use` has no `tool_result` yet — context = the latest-started open call's; else `unknown` — context = the last event's. Record `idle_threshold_s` and `suspend_source: "none"` in `time`. **Mode `overlay`**: `jq -c -S -f run-analytics.jq --arg mode overlay --argjson idle_threshold_s <int> --argjson known '[]' --argjson redact '[]' --argjson suspend '<array of [start_ms, end_ms]>' --arg suspend_source <pmset|journalctl|file|none>` (the full variable set the header requires; `known` and `redact` unused here, `idle_threshold_s` the same value the `sessions` call took) reads Task 3's array of session records on stdin and, per session, sets `time.suspend_source` and re-classes every gap overlapping any interval as `host_asleep` (keeping its context) — host asleep outranks every other class, as the prompt orders.
- [ ] **Cost, tokens and reliability.** From the `result` event (all `null` on a `complete: false` session): `cost` = `{total_cost_usd, by_model: {<model>: costUSD} from modelUsage (else model_usage_since_last_result), input_tokens, output_tokens, thinking_tokens (usage.output_tokens_details.thinking_tokens), cache_read_tokens, cache_write_5m_tokens, cache_write_1h_tokens (the cache_creation ephemeral_5m/ephemeral_1h split), cache_hit_ratio}` with `cache_hit_ratio` = read / (read + write + input), 4 decimals, `null` on a zero denominator; `reliability` = `{api_retries (count of system/api_retry), api_retry_errors: {<error_status>: count}, permission_denials (length), subagents_spawned, subagents_failed, subagents_killed (from subagent_stats), terminal_reason, stop_reason, num_turns, ttft_ms, rate_limit_peak: {<rateLimitType>: max utilization}}`, the last from `rate_limit_event` → `rate_limit_info` with keys `rateLimitType` and `utilization` as `cli/templates/scripts/autonomous-watcher.sh` → the `usage_read_run` comment documents them. Every session record carries exactly the top-level keys `session_id, complete, first_at, last_at, time, requests, tools, subagents, cost, reliability`, where `requests` = `{items, overall, by_context}` and `tools` = `{items, by_tool, slowest, polling}`.

- Re-running the probe with `$known` holding the first session's id emits only the second.
- The same probe runs each mode with exactly the invocation above — `sessions` over the stream, then `overlay` over its output — and shows each exits `0` with no `is not defined` and no `compile error` on stderr; dropping any one of the six variables from either call makes it exit non-zero with `is not defined`, which is the reason the header gives for passing all six.
- `grep -n 'cwd\|utf8bytelength\|rawfile' cli/templates/scripts/lib/run-analytics.jq` finds none outside the header comment's floor statement.

**Deviations from plan:**

- **A resumed session reuses its `session_id`, so the Nth occurrence is recorded as `<session_id>#<N>`.** The plan keys a session on the init event's `session_id` and drops one "already emitted earlier in the same pass". Measured on `feat_unattended_sandbox_preflight.stream.jsonl` in the main checkout's `harness-runs/autonomous_logs/` (`jq -c 'select((.type=="system" and .subtype=="init") or .type=="result") | {type, session_id, uuid, dur: .duration_ms, nt: .num_turns}'`): four inits, four results, and the last three inits share id `2651f418-…`, each followed by its own `result` (`duration_ms` 795138 / 479673 / 210049, `result_index` 0 / 1 / 2). Read literally, the plan would drop two of those three headless sessions. The 1st occurrence keeps the bare id, the 2nd onward gets `#2`, `#3`. The stream is append-only, so the ordinals stay the same on a re-run. `$known` matching and the "already emitted" check use that key, so Task 3's "array of recorded `session_id` strings" contract still holds. Task 2 and Task 3 must treat `session_id` as an opaque key, not a CLI session id. The probe's resumed-id case shows `["sess-b","sess-b#2"]`.
- **`rate_limit_peak` also reads `rate_limit_info.unifiedWindows.<window>.utilization`.** In the measured streams the top-level `utilization` is `null` on every `rate_limit_event` (80 of 80 in `feat_unattended_sandbox_preflight.stream.jsonl`). The per-window values are in `unifiedWindows`. Using only the plan's two keys would always give `{}`. With both read, `fix_swept_run_profile_leak.stream.jsonl` gives `{"five_hour":0.17,"seven_day":0.46}`.
- **A `tool_use` or `tool_result` with no timestamp takes the nearest preceding one.** This is the rule in `harness-run.yml` → `THE SELF-PAUSE POINT, MEASURED`, which the plan says this program must stay re-derivable from. Every other time computation ignores an event with no timestamp, as the plan says. In the measured streams, every `assistant` and `user` event carries a timestamp. No `system` event does, the init included.
- **`complete: false` nulls only the `reliability` values that come from the `result` event.** `api_retries`, `api_retry_errors` and `rate_limit_peak` come from other events and are still counted. `cost` is all `null`, as the plan says.
- **Roll-up `count` is every request. Percentiles and `max_ms` cover only requests that have a latency.** A session's first orchestrator request has no earlier timestamped event in its context, so its `latency_ms` is `null`.
- **Evidence downgrade: the jq 1.5 floor is reasoned, not executed.** The only `jq` on this host is 1.8.2 (`jq --version`). The program avoids every builtin added after 1.5 that I know of: no `utf8bytelength`, no regex, no `$ENV`/`$__loc__`/`halt`/`walk`/`IN`/`isempty`/`abs`/`ceil`/`round`, no unary minus, and `join` only over strings. Nothing has run it under 1.5.
