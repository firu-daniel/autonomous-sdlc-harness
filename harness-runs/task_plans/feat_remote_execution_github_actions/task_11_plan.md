### Task 11 — Dispatch inbox drops to the workflow when `execution.target` is `github-actions`

**Goal:** Keep the inbox the one way a run starts. With `execution.target` `github-actions`, a dropped task prompt, docs checklist or user review is prepared exactly as today — working copy, artifact placed, committed and pushed — and then **dispatched** to the workflow instead of spawned; with the key absent or `local`, the inbox pass is byte-for-byte today's.

**Depends on:** Task 10, which last edited `cli/templates/scripts/autonomous-watcher.sh`, and through it Task 9, whose job-mode qualification of the two anchors passages this task extends. Task 3's `hr_execution_target <repo_root>` (prints `local` | `github-actions`, exit 2 when unresolvable). Task 5's `remote-run.sh dispatch <branch> --engine <kind> [--resume none] [--chain 0]` (exit 0 sent, 1 usage/config, 2 refused, 3 `gh` failed). Task 6's `remote-run.sh sync <branch>`, which refreshes a remote record before the duplicate test reads it.

**The contract, stated once for every consumer** (Task 12 relays for the records this task creates; Tasks 22–23 and 30 describe them):

- **Which drops go remote:** the configuration in effect at the drop, read with `hr_execution_target "$MAIN_REPO"` per inbox file; an unresolvable answer is treated as `local` and logged once. A run keeps the execution it started with for its whole life — the record's `execution` field, not the current key, is what Task 12's relays read.
- **The remote record:** `launch_remote_run <branch> <worktree> <log_path> <engine_kind>` mirrors `launch_run`'s bookkeeping and clears the same inherited fields, and additionally sets `execution: github-actions`, `pid: ""`, `remote_dispatched_at`, and `status: running` **only once the dispatch returned 0**. It notifies `launched` with the detail `dispatched to GitHub Actions`. A non-zero dispatch leaves `status: failed`, logs `remote-run.sh`'s message and notifies `failed` naming it; the artifact is already committed and pushed, so re-dropping the same file re-dispatches (the identical-re-drop commit skip already exists). It opens no live-log window and spawns nothing.
- **Guards for a remote drop, in the existing order:** the kill switch still defers. The usage hold, the concurrency cap and the machine lane are **skipped** — the job gates itself, and no local component gates a remote run. For a branch whose existing record carries `execution: github-actions`, run `remote-run.sh sync <branch>` first (best-effort; a failure is one log line) so the duplicate test reads a current status; a remote record still `running` after the sync is archived as a duplicate (`dup_<ts>_…`) exactly as a live local one is; `parked`, `paused` and `park_loop` are rejected preserving status exactly as today.
- **The task and docs paths** keep today's steps up to and including the existing commit and push; the final `launch_run` becomes `launch_remote_run`, and **the failure rule on the remote arm is blocking** (next bullet).
- **On the remote arm a failed commit or push blocks the dispatch — for all three artifacts.** The local rule (`cli/templates/scripts/autonomous-watcher.sh` → `WHAT IT COMMITS, AND WHAT IT POINTEDLY DOES NOT`: *"a failed commit or push is one WARNING line in the log and the run launches anyway"*) is safe only because a local run executes in the same working copy that holds the file. A remote job checks out `origin/<branch>` (Task 15: `actions/checkout` at `ref: ${{ inputs.branch }}`), so the push is the only way the prompt, the docs checklist or the review reaches the run. So, when the target is `github-actions`: a failed `commit-on-branch.sh` is `fail_before_launch` naming `commit-on-branch.sh` and the artifact; a failed `push-branch.sh` is `fail_before_launch` naming `push-branch.sh`; in both cases `remote-run.sh dispatch` is **never called**. The identical-re-drop skip still skips the commit, but on the remote arm it is **followed by a `push-branch.sh` that must succeed** (the earlier drop's push may be the one that failed), under the same blocking rule. The push stays a separate statement from the commit, as today. **The local arm's non-blocking rule is unchanged**, byte for byte.
- **The review path, remote only:** reuse the existing working copy after the existing sanity check, then bring it level with the remote before touching it — `git -C <worktree> fetch origin <branch>` then `git -C <worktree> merge --ff-only origin/<branch>` — because the remote job, not this copy, is where the branch advanced; a fetch or fast-forward failure is `fail_before_launch` naming it. Place the review file as today, then **commit it** through `commit-on-branch.sh` with the fixed subject `chore: add user review for <branch>` and push through `push-branch.sh`, with the same identical-re-drop skip and the **blocking** remote failure rule above. A review is committed for a remote run because a job boundary before the flow's own commit would otherwise lose it; the local path still never commits it.

**Deviations from plan:**

- "A failed `push-branch.sh`" is detected as `origin/<branch>` (the remote-tracking ref a successful push moves) not equal to HEAD after the wrapper ran. The reason: `push-branch.sh` exits 0 on every path by contract (its header: `EVERY FAILURE PATH IS NON-FATAL (exit 0)`), so its exit status carries no information. A consequence: an identical re-drop whose branch is already level with origin has nothing to push and is dispatched, which is correct because the artifact is already on origin.
- The "identical re-drop, then a failed push" case is tested on the **review** path, not the task path. A task re-drop re-runs `create-worktree.sh`, whose `git worktree add -b <branch>` refuses a branch that already exists. On the task path the skip is only reachable when the base branch already carries the prompt, and then the push has nothing to send. On the review path the same helper (`remote_commit_and_push`) serves all three artifacts. Evidence downgrade: the `create-worktree.sh` refusal rests on reading its body, not on a run.
- On the remote review arm the fetch and fast-forward also run after a `create-worktree.sh --existing` recreation, not only after a reuse. `worktree add <dir> <branch>` checks out the local branch, which can be behind `origin/<branch>` just like a reused copy.
- The fixture replaces `origin`'s seed commit with the adopted tree using a forced `--no-verify` push, because `init` has already made an unrelated first commit and wired the protected-branch pre-push hook.
