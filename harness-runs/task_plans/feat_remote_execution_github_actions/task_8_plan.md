### Task 8 — Add the job-side `continue` and the poller's `poll` to `remote-run.sh`

**Goal:** Close the loop without the local machine: `continue` is the job's last step, which reads the bundle the job just saved and either re-dispatches the run, enables the resume poller, or stops; `poll` is the resume poller's whole body, which resumes every usage-paused run whose recorded reset has passed and disables the poller when none is left.

**Depends on:** Task 7, which last extended `cli/templates/scripts/remote-run.sh` and `cli/test/remote-run.test.mjs`, and whose `save` writes the bundle `continue` reads (a bundle with no `status.json` means the harness step never started). Task 5, whose `dispatch <branch> --engine <kind> --resume pause --chain <n>` both verbs call, and whose input contract (`chain` counts automatic dispatches since the last user action) they honour. Task 5's `stop <branch>` always dispatches `-f action=stop -f branch=<branch>` on the branch, which yields the run titled `harness stop <branch>` that both verbs test for. Task 4, whose `status.json` keys `decision` (`continue` | `wait-poller` | `stop`), `engine`, `chain`, `status`, `pause_reason` and `usage_resume_at` they read through `hr_remote_status_get`. Task 4's format defines `chain` in that file as the writing job's own input `HARNESS_INPUT_CHAIN` (Task 9, which ships later, is the writer that honours it; this task's cases write the bundles themselves, so it ships independently).

**The two verbs, stated once for every consumer** (Task 15's workflow calls `continue` under `!cancelled()`; Task 16's poller workflow calls `poll`):

```
remote-run.sh continue <branch> <bundle_dir>
remote-run.sh poll
```

Environment read by both (set by the workflows from inputs and repository variables — never interpolated into a shell line): `HARNESS_MAX_CHAIN` (default `24` when empty), `HARNESS_REMOTE_STOP`, `HARNESS_REMOTE_SLUG`, `GITHUB_RUN_ID`, `GITHUB_SERVER_URL`, `GITHUB_REPOSITORY`.

**Where `chain` comes from — one source, never another.** Both verbs take `chain` from the bundle's `status.json` through `hr_remote_status_get <status_json> chain`, and from nothing else: not `HARNESS_INPUT_CHAIN`, not the registry, not a run's inputs. Task 4's format defines that key as **the dispatching job's own input** — Task 9's job mode sets the record's `chain` from `HARNESS_INPUT_CHAIN` at start and never seeds it from a restored bundle — so `chain + 1` is always one more than the job that wrote the bundle, and a user's dispatch (input `0`) restarts the count. A `status.json` whose `chain` is absent or not a non-negative integer is treated as `continue`'s chain-limit refusal (one `failed` notification, "chain unreadable"), never as `0`.

**The stop marker — one test, both verbs, ahead of every dispatch and every enable.** Task 5's `remote-run.sh stop <branch>` always dispatches `action: stop` on the branch, a run titled `harness stop <branch>` by the workflow's `run-name` that runs no job. It exists so a user's stop reaches a run no job is executing — the usage-paused run on a hosted runner that ended its job and enabled the poller, which a cancel cannot reach. A branch is **stopped** when its newest run whose `displayTitle` is exactly `harness stop <branch>` has a `createdAt` later than its newest run whose `displayTitle` is exactly `harness run <branch>`. Both come from one bounded, newest-first listing, `gh run list --workflow harness-run.yml --json databaseId,headBranch,displayTitle,status,createdAt`. The bound is safe: a stop marker that falls outside the window is older than any `harness run` inside it, and a branch whose newest `harness run` falls outside the window is not considered by `poll` at all. A user's later dispatch (`harness run <branch>`, from `/autonomous-sdlc-harness:branch-resume` or by hand) is newer than the marker, so the branch stops being stopped with no extra step. The test is one shared function in the script, `remote_branch_stopped <branch>` (0 stopped, 1 not stopped, 2 the listing failed), used by both verbs:

- In `continue`, the test runs in the `decision: continue` arm before the dispatch and in the `decision: wait-poller` arm before the enable. A stopped branch gets neither, one log line and no notification, because the user asked for this. A listing that fails fails **closed**: no dispatch and no enable, and one `paused` notification naming `gh`'s first stderr line and `/autonomous-sdlc-harness:branch-resume <branch>` as the way on. An unconfirmed dispatch could bill a run the user stopped.
- In `poll`, a stopped branch is neither dispatched nor counted as still waiting, so a tick where it was the only waiting branch disables the poller.

- **`continue`**:
  - no `status.json` → the job stopped before the run started: one `failed` notification naming the run URL, no dispatch;
  - `decision: continue` → no dispatch and one `paused` notification when `HARNESS_REMOTE_STOP` is non-empty ("remote stop is set"); no dispatch when the branch is stopped (the stop-marker test above); one `failed` notification when `chain + 1` exceeds `HARNESS_MAX_CHAIN` ("chain limit reached"); otherwise `dispatch <branch> --engine <engine from status.json> --resume pause --chain <chain + 1>`. A job killed by its step timeout reaches this arm, because job mode writes `decision: continue` the moment it starts (Task 9);
  - `decision: wait-poller` → when the branch is stopped, nothing (one log line); otherwise `gh workflow enable harness-resume.yml`; when that fails, one `paused` notification saying auto-resume is unavailable, naming `gh`'s first stderr line and `/autonomous-sdlc-harness:branch-resume <branch>` as the way on — this is the degradable path for the unverified `GITHUB_TOKEN` enable permission;
  - `decision: stop` → nothing (job mode has already notified).
- **`poll`**: exit 0 without dispatching when `HARNESS_REMOTE_STOP` is non-empty. Otherwise list `harness-run.yml`'s runs (`gh run list --workflow harness-run.yml --json databaseId,headBranch,displayTitle,status,createdAt`, bounded), take each branch's newest `harness run <branch>` run, skip a branch the stop-marker test finds stopped (it is not dispatched and does not count as waiting), and for a finished one download its bundle; a bundle saying `status: paused`, `pause_reason: usage` and a `usage_resume_at` that has passed is dispatched `--resume pause --chain <chain + 1>`, subject to the same chain limit; one whose reset is still ahead counts as still waiting. When no branch is still waiting after the tick, `gh workflow disable harness-resume.yml`. Every dispatch and the disable are logged one line each.
- Notifications go through the sibling `autonomous-notify.sh` with the lifecycle words it already knows (`paused`, `failed`). Before notifying, both verbs export `HARNESS_REPO_SLUG` from `HARNESS_REMOTE_SLUG` when that is set (the workflows set it to the repository's `owner/name`, as Task 9's job mode does), so a notification names the repository rather than a runner path.
