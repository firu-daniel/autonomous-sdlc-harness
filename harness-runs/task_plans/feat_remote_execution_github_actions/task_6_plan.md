### Task 6 — Add `sync` and `status` to `remote-run.sh`

**Goal:** Let the user read a remote run's state on demand: `status` reads GitHub's run list without writing anything, and `sync` brings the latest state bundle into the run's local mirror and the local registry record, so the local commands that act on a run (Tasks 22–23) and the watcher's relays (Task 12) read a current record.

**Depends on:** Task 5, which created `cli/templates/scripts/remote-run.sh`, its exit map (0 done, 1 usage/config, 2 refused, 3 `gh` failed) and `cli/test/remote-run.test.mjs`; this task adds two verbs to both. And Task 4, whose `hr_remote_bundle_restore <bundle_dir> <root> <branch> mirror` and `hr_remote_status_get <status_json> <key>` this task calls, and whose `status.json` keys (`status`, `pause_reason`, `usage_resume_at`, `park_loop_cycles`, `decision`, `detail`, `run_url`, `written_at`) it reads.

**The two verbs, stated once for every consumer** (Tasks 11, 12, 22, 23 call them):

```
remote-run.sh status <branch>   read-only: GitHub's recent runs of harness-run.yml for the branch, and the local record's last-synced fields
remote-run.sh sync <branch>     download the newest available bundle into the mirror, and update the local record
```

- Both refuse (exit 2) a branch whose local record does not carry `execution: github-actions` — a local run has nothing remote to read.
- **`status`** writes nothing at all. It prints, from `gh run list --workflow harness-run.yml --branch <branch> --json databaseId,displayTitle,status,conclusion,createdAt,url`, the runs titled `harness run <branch>` or `harness pause <branch>`, newest first and bounded, then the record's `status`, `pause_reason`, `remote_run_url` and `remote_synced_at`, and one line saying whether a run finished after the last sync (so the reader knows `sync` would change something).
- **`sync`** takes the newest `harness run <branch>` run. If it is `queued`, `in_progress` or `waiting`, the record becomes `running` and nothing is downloaded. Otherwise **the newest finished run decides**, in exactly one of four cases, tested in this order:
  1. **Already synced** — its id equals the record's `remote_run_id`. The bundle has already been applied: `sync` downloads nothing, restores nothing, rewrites no record field except `remote_synced_at`, and only reports (one line naming the run and saying the mirror is current). This is what keeps an answer the user wrote into the mirror since the last sync — `/autonomous-sdlc-harness:branch-answer` on the first of two questions, then again on the second, each syncing first (Tasks 22–23) — from being moved aside by a second restore of the same bundle. The short-circuit fires **only** when the newest finished run is itself the synced one; it is never reached by walking past a newer run.
  2. **A newer run with a bundle** — it carries a `harness-state` artifact. Apply it (below).
  3. **A newer run with no bundle, while some bundle exists** — it carries no `harness-state` artifact, and either `remote_run_id` is non-empty or an older finished run in the list carries one. This is a job that died before its `always()` upload ran or never started: a runner failure (the task prompt's `### A remote run supervises itself` → **When the job is killed**), a job cancelled while still queued, or a pending run GitHub replaced in the concurrency group. `sync` records `status: paused`, `pause_reason: killed`, `remote_run_id` / `remote_run_url` set to **that** run, `remote_synced_at`, and a detail naming its URL; it downloads nothing and **restores nothing**, so no mirror file moves and an answer written since the last sync survives. The next `/autonomous-sdlc-harness:branch-resume` then dispatches `resume: pause`, and Task 7's `restore` picks up the newest earlier bundle in the job. Without this case, the walk would pass the dead run, select the already-synced one, short-circuit and leave the record `running` forever — refused by `branch-resume`, reported running by `branch-status`, and a re-drop archived as a duplicate by Task 11 — against Acceptance 9. Because this case re-points `remote_run_id` at the bundle-less run, a later `sync` with no newer run hits case 1 and leaves the `paused` record alone.
  4. **No bundle in any run** — `remote_run_id` is empty and no finished run in the list carries a `harness-state` artifact. `sync` records `failed` with a detail naming the newest run's URL. This stays `failed` rather than `paused` on purpose: no bundle anywhere means no job of this run ever uploaded state, so a `resume: pause` would find nothing for Task 7's `restore` to pick up and would start from the prompt anyway; the recovery is re-dropping the artifact, which re-dispatches a fresh run and which Task 11 does not treat as a duplicate of a `failed` record.

  Applying a bundle (case 2): the mirror is replaced **only** by a bundle from a run other than the last one synced, which, the newest finished run deciding, is a newer one. For such a run it downloads the bundle with `gh run download <id> -n harness-state -D <MAIN_REPO>/<state_dir>/autonomous_logs/remote_download/<branch>/<id>/` (skipped when that directory already holds it; the logs directory is gitignored), restores it in `mirror` mode into the record's `worktree`, copies the bundle's `run.log` to `<MAIN_REPO>/<state_dir>/autonomous_logs/<branch>.remote.log`, and writes the record through `hr_registry_set`: `status` (from `status.json`), `pause_reason`, `usage_resume_at`, `park_loop_cycles`, `remote_run_id`, `remote_run_url`, `remote_synced_at`.
- **A job that ended mid-run** — a finished run whose bundle still says `status: running` (a kill, a timeout with no chain left) — syncs as `status: paused` with `pause_reason: killed`, so `/autonomous-sdlc-harness:branch-resume` resumes it from the pushed ledger with no cleanup (Acceptance 9). A job that ended with no bundle at all is case 3 above (`paused` / `killed`), unless no run has ever produced one (case 4, `failed`).
- A missing mirror working copy is exit 2 naming the path; nothing is written.
