### Task 9 — Add the watcher's `job` subcommand: one run, supervised inside the job's own checkout

**Goal:** Make the watcher able to run exactly one run inside a GitHub Actions job — launched, watched and classified by the same code a local run gets — so that what the local watcher does for a local run, the job does for itself: the launch line flag for flag, the stream tee, `classify_run_exit`, the park-loop guard, the stall watchdog and the usage gate.

**Depends on:** Task 3 (the registry primitives the watcher's `registry_*` wrappers now call) and Task 4, whose `hr_remote_status_write <registry_file> <branch> <out_json> <decision> <detail>` this mode calls at start and at exit, and whose `status.json` keys it seeds from (`park_loop_cycles`, `resume_max_question_index`, `stall_restarts`, `engine`, and — under the conditions stated at **Start** below — `auto_resumes` and `control_polled_at`). **`chain` is never seeded**: it is set from this job's own input `HARNESS_INPUT_CHAIN`, which Task 15's job-level `env:` provides from the `chain` workflow input. Task 7's `restore` has already placed the previous bundle before this runs: the clarification directory, `PAUSE_PROGRESS.md`, `.flow_walker_state`, and `status.json` as `<state_dir>/autonomous_logs/remote_status.json`.

**The interface, stated once for every consumer** (Task 15's workflow invokes it; Task 10 extends it; Task 8's `continue` reads what it writes):

```
HARNESS_JOB_MODE=1 autonomous-watcher.sh job <branch> <engine> <resume>
  <engine>  task | user_review | docs
  <resume>  none | answer | pause
  exit 0    the run reached a state this job stops in; <state_dir>/autonomous_logs/remote_status.json says which, with its decision
  exit 2    usage error, including HARNESS_JOB_MODE not being 1, HARNESS_INPUT_CHAIN not being
            empty or a non-negative integer, or <branch> being protected
            (hr_branch_is_protected answers protected or unresolvable) — nothing is launched
```

- **Refused unless `HARNESS_JOB_MODE=1`.** Job mode resets the checkout it runs in (the stall watchdog's `git reset --hard HEAD`) and treats it as both the main checkout and the working copy; run by accident in a developer's checkout, that would discard work. The workflow sets the variable; nothing else should.
- **In the job's checkout `MAIN_REPO` and the working copy are the same directory**, which the existing anchors already produce there (the first working copy `git worktree list` reports is the checkout). The registry is the checkout's gitignored `<state_dir>/autonomous_logs/registry.json`, ephemeral by construction.
- **Off in job mode:** the inbox pass, the cleanup sweep, the live-log window (`AUTO_TAIL_TERMINAL=0`), and the machine lane (`USAGE_LANE_STATE_ENABLED=0`, `USAGE_LANE_LOCK_ENABLED=0`) — the lane is local-only by the task prompt's rule, and on a hosted runner its directory would not outlive the job. These are assigned **after** the operator-override channel and the tunable defaults, so no environment value can turn them back on.
- **The slug** every notification title carries is `HARNESS_REMOTE_SLUG` when set (the workflow sets it from the repository's owner and name), else the library's derivation, so a phone shows the repository rather than a runner's path.
- **Environment this mode reads**, beyond the watcher's tunables: `HARNESS_JOB_MODE`, `HARNESS_REMOTE_SLUG`, and `HARNESS_INPUT_CHAIN` (a non-negative decimal integer; empty is `0`; anything else is exit 2, nothing launched). Task 10 adds its own reads.
- **Start:** seed the record from `remote_status.json` when present — `park_loop_cycles`, `resume_max_question_index` and `stall_restarts` always; `auto_resumes` **only when `HARNESS_INPUT_CHAIN` is greater than `0`** (an automatic continuation carries the count forward), and `0` otherwise, because a job whose input `chain` is `0` was started by a user's dispatch — a drop, an answer, a resume — and the story index settles that any user action resets the auto-resume count; `control_polled_at` per Task 10's lower-bound rule. **Never seed `chain` from the restored file**: set the record's `chain` to `HARNESS_INPUT_CHAIN`, so every `status.json` this job writes records this job's own input, which is what Task 8's `continue` and `poll` increment. Then set `engine`, `worktree` (the checkout), `log_path`, `status: running`, then write `remote_status.json` with decision `continue` and detail `job started` **before** the spawn — so a job killed at any later point leaves a bundle that tells Task 8 to continue. Then spawn through the existing `spawn_engine`, never a new launch line: `none` → the fresh-launch bookkeeping `launch_run` does, without its `launched` notification (the local watcher sent that at dispatch); `answer` → the answered-set computation, registry fields and `spawn_engine … "<indexes>"` exactly as `resume_parked_run` does them, with a `resumed` notification naming the job; `pause` → `resume_kind: pause` and `spawn_engine … "" 1` as `resume_paused_run` does, with a `resumed` notification.
- **Loop** every `POLL_INTERVAL_SECS` while the record is `running`: `reconcile_stale_runs` (a vanished subshell becomes `failed`), `check_stalled_runs`, `usage_gate`. Task 10 adds its own passes to this loop.
- **Exit:** write `remote_status.json` with decision `stop` for every terminal status (`completed`, `parked`, `park_loop`, `failed`, `paused`) — Task 10 replaces the decision for the `paused` and `failed` cases it continues — print one line `job: <status> <decision>`, and exit 0.
- **Notification details name the user's next action, not a runner path**, whenever job mode is on: a `parked` run says to answer with `/autonomous-sdlc-harness:branch-answer <branch>`; a `park_loop` run says to clear it after `/autonomous-sdlc-harness:branch-status <branch>` shows the question. Implement by consulting a `JOB_MODE` variable where `classify_run_exit` composes those details; the local details are unchanged.
