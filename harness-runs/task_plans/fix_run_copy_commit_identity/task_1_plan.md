### Task 1 — Mirror the main checkout's `user.name` / `user.email` into the clone allow-list, and prove both arms

**Goal:** Make a run clone carry the main checkout's commit identity. `hr_clone_config_spec` lists `user.name` and `user.email` at the exact values the main checkout's `.git/config` holds, and only when it holds them. `hr_clone_create_var` writes them into every new clone. `cli/test/clone-trust-check.test.mjs` proves both arms: a main checkout with a local identity and one without. It also proves three refusals: a different value, an identity key where the main checkout sets none, and any signing key.

**Where this layer stops.** This task changes the shipped library template and its test, and nothing else. The docs record is **Task 2's**: the PR #126 measurement, the owed rows, and the decision text in `docs/cli.md` and `docs/sandbox-verification.md`. Task 2 cites this task's library headers as the code of record, so the headers written here must state each decision in full on their own. Two things are not this task's:
- the self-adopted copy `scripts/lib/harness-run-lib.sh` at the repository root, which is a supervised re-render after merge (the story index's **Manual setup required** 1);
- any edit to `autonomous-watcher.sh` or `cli/src/doctor/`, since neither reads the key list (story index `## Context`, goal 3).

### Targets

**Work:**

- [ ] **One list, one reader of the main checkout.** Add a single owner of the mirrored identity keys in the library, for example a function `hr_clone_identity_keys` that prints `user.name` and `user.email` one per line. Both `hr_clone_config_spec` and `hr_clone_create_var` read the set from it, so it is never typed twice. In `hr_clone_config_spec`, read each key with `git -C / config --file "$main/.git/config" --get <key>`, the same call that already reads `remote.origin.url`. Print `<key><TAB>=<value>` only when the call succeeds with a non-empty value, after the existing `remote.origin.url` line. Add the values to the existing newline test (`case "$top/$rel$url$fmt" in *"$nl"*) return 1`), so a value the line format cannot carry is refused by the one rule already stated. **Do not** add either key to `hr_clone_config_check_var`'s required-key loop (`for req in core.repositoryformatversion extensions.objectformat core.bare remote.origin.fetch remote.origin.url`). That loop stays as it is: the keys are optional, so a clone made before this change still passes.
- [ ] **Write them at creation.** In `hr_clone_create_var`, the loop `for key in core.repositoryformatversion extensions.objectformat core.bare remote.origin.fetch remote.origin.url core.filemode …` writes the clone's `.git/config` from the spec. Extend it with the keys from the single owner above. Its existing `hr_clone_spec_rule_var "$spec" "$key" || continue` already skips a key the spec does not list, and its `=*)` arm writes the exact value. So a main checkout with no identity leaves the clone with no `user.*` key, and the rest of the loop and the rollback stay unchanged.
- [ ] **State the contract and both decisions in the headers.** These are the code of record Task 2 cites.
  - The `THE CLONE CONFIGURATION ALLOW-LIST — one contract.` block and `hr_clone_config_spec`'s description list `user.name` and `user.email` as optional exact-value keys, with the same conditional wording `remote.origin.url` has.
  - Say why they are safe. Git writes them into a commit and never executes them. They are exact copies of the main checkout's values, so a session still cannot set its own author identity. And a session cannot write the clone's `.git/config` at all (`docs/sandbox-verification.md`, row CL5), so the check stays defence in depth.
  - Say what the copy does not cover. The main checkout's `.git/config` is read with `--file`, so an identity it sets only through `include` / `includeIf` is not seen, and the clone falls back to the global one, which is today's behaviour.
  - Name the one new refusal as an accepted cost. A main checkout whose `user.name` or `user.email` changes, or is unset, while a clone is live makes that clone's copy wrong, and the clone is refused until it is recreated.
  - **The signing decision.** `user.signingkey`, `commit.gpgsign`, `gpg.format`, `gpg.program`, `gpg.<format>.program` and `gpg.ssh.defaultKeyCommand` are deliberately **not** listed. A commit written with the clone as git's repository can only be signed by a program that reaches the signing key or agent socket from wherever that commit is written. That is unmeasured, and a failed signature fails the commit. The main-checkout wrappers' `git -C <main> commit-tree` already signs under the main checkout's configuration. If signing is ever carried, the program keys travel only as the main checkout's exact values, as a deliberate trust decision that names the main checkout's `.git/config` as the trusted source, never as a widened rule.
  - Update `hr_clone_create_var`'s header ("rewrite `.git/config` to the allow-list's required keys plus the platform booleans …") to add "plus the main checkout's identity keys it sets".
- [ ] **Test: both arms of the identity.** In `cli/test/clone-trust-check.test.mjs`:
  - Give `fixture` an option, `identity = true`. When it is `false`, the main checkout sets no `user.*` key and makes its seed commit with `-c user.name=… -c user.email=…`, as the `IDENTITY` constant in `cli/test/clone-sync.test.mjs` does.
  - Add a helper that writes a commit in the clone with the clone as git's repository: `git -C <clone> commit-tree <HEAD^{tree}> -p HEAD -m probe`, which moves no ref. Run it through `runBash` with `HOME` set to a temp directory whose `.gitconfig` names a third, *global* identity, and with `GIT_CONFIG_NOSYSTEM=1` and `GIT_CONFIG_GLOBAL` pointing at that file. The bash body unsets `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL` and `EMAIL` first, so the caller's environment cannot mask the configuration. Read the result with `git -C <clone> cat-file -p <oid>`.
  - **With an identity:** the spec lists `user.name` and `user.email` at the main checkout's exact values, the created clone carries both, the check accepts it, and the probe commit's `author` and `committer` lines name the main checkout's identity, not the global one.
  - **Without one:** the spec lists no `user.*` key, the clone carries none, the check accepts it, and the probe commit names the global identity.
- [ ] **Test: what stays refused, and what stays accepted.**
  - Extend case (l)'s map with `user.name` and `user.email` set to a value carrying `MARKER`. Each is refused as "to a value the clone allow-list does not allow", naming the key and never the value.
  - New case: with `identity: false`, a `user.name` written into the clone is refused as "which the clone allow-list does not hold".
  - New case: a clone whose `user.*` keys are `--unset` after creation (the shape of a clone made before this change) is still accepted.
  - New case: changing the main checkout's `user.name` after the clone exists makes the clone refused, naming `user.name`. This is the accepted cost in the header.
  - Extend case (k)'s key list with `commit.gpgsign`, `user.signingkey`, `gpg.format`, `gpg.program` and `gpg.ssh.program`.
  - New case: a main checkout that sets `commit.gpgsign`, `gpg.format` and `user.signingkey` after its seed commit gives a created clone holding none of them, and the spec lists none of them.
  - Case (p) keeps holding the spec and the created clone to one statement. Add `user.name` / `user.email` to its copied-from-main assertion beside the `bool` keys.
  - Restate the file header's rule to include the identity: the clone's `.git/config` may carry the main checkout's identity at its exact value, and nothing else that identifies or signs.
