### Task 2 — Retrieval cache paths and the optional-dependency loader

**Goal:** Build the loader through which every retrieval package reaches the CLI, and the machine cache paths where `init` installs those packages and their model weights. Prove with a test that a verb which does not retrieve loads none of them.

**Why a runtime directory.** This was measured while planning: a CLI run from `npx`'s cache does **not** resolve a package installed in the adopting project. Running `node ../cache/node_modules/tool/cli.mjs` from the project printed `not resolved: ERR_MODULE_NOT_FOUND` on Node v20.19.5. So `init` (Task 12) installs the peers and this CLI, at its own version, into one machine-shared directory. **The runtime is the only installation the `.mcp.json` launcher runs** (Task 9, no fallback), so "is the runtime installed?" (`retrievalRuntimeState`, below) is also the only thing `init`'s setup skips on (Task 12) and `doctor`'s `retrieval-dependencies` passes on (Task 13). `retrievalCliEntry` (this installation when its peers resolve here, otherwise the runtime) is only the entry of two non-serving child processes, `doctor`'s in-memory index probe and setup's `docs fetch-models`, which read the shared model cache and behave the same from either. No code in this package resolves a peer against a second base.

**Where this task stops.** This task installs nothing and downloads nothing; that is Task 12. It uses no retrieval package. The first caller of `loadRetrievalModule` is Task 3.
