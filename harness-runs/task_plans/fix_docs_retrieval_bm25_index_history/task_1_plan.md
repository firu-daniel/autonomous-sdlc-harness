### Task 1 — Score both columns in the committed statement-level probe and record what it measures on PGlite and on the compose Postgres

**Goal:** Meet goal 1 of the task prompt, "the cause is measured, not inferred". The probe `evals/docs-retrieval/bm25-history.mjs` is already committed (commit `78731f0`). It runs one fixed sequence of SQL statements against a `chunks` table carrying the store's own BM25 index, on both engines, and prints the BM25 scores and the index's own corpus statistics after every step. This task makes every score statement read **two** columns, takes the four runs of record, and records the sequence, its setup and its figures in the document of record, so a reader can re-run it. This task changes no shipped behaviour.

**Why two columns.** In `pg_textsearch` 1.3.1 a `SELECT` column whose expression is exactly the `ORDER BY` expression is replaced by the planner with `bm25_get_current_score()`, which returns the score the index scan ranked that row by (`src/planner/hooks.c` → `replace_scores_in_targetlist`; `src/access/scan.c` → `tp_cached_score`). Any other column, the probe's `round((…)::numeric, 6)` included, is computed by the standalone operator function from the row's own text (`src/types/query.c` → `bm25_text_bm25query_score`). The two are different computations, and the store ranks by the first one only (`cli/src/retrieval/store.ts` → the lexical search's `SELECT id … ORDER BY` statement). So every score statement reads:

- `scan`: the bare `BM25_ORDER_CLAUSE` column, the index scan's own score, rounded to six decimals on the client;
- `operator`: `round((BM25_ORDER_CLAUSE)::numeric, 6)`, as the probe reads it today and as item 3's statement read it.

Both are read through the index scan. `enable_indexscan` is never turned off, in this task or anywhere on the branch (task prompt → `## A second defect, found while implementing Task 1` → **What is wanted:**, point 1; `## Constraints`).

**What the probe must settle, each as a measured line rather than an inference, in each column:**

1. **Deleted rows stay counted.** After a `DELETE`, `bm25_summarize_index('chunks_bm25')` still reports the deleted rows in `total_docs` and `total_len`, and the surviving rows' scores differ from a fresh index of the survivors.
2. **Rows from another corpus are the same defect, and their statistics outlive them.** The table holds corpus A ∪ corpus B, and B's rows are then deleted, as a refresh to corpus A deletes them. A `SELECT count(*)` shows that B's rows are gone from the heap. A's scores then still **equal** the A ∪ B ones, not a fresh index of A's: B's statistics remain, B's rows do not. That answers the prompt's "two different defects" lead. (The first attempt measured exactly this, 0 hits differing from `s1` on all four runs, and this point now states it.)
3. **An update is a delete too.** An `INSERT … ON CONFLICT (key) DO UPDATE` of a stored key skews the scores, in the same way.
4. **What `VACUUM` does and does not do.** After `VACUUM chunks`, the summary shows the memtable spilled to a segment, and the scores are still not the fresh ones.
5. **What `REINDEX` does.** After `REINDEX INDEX chunks_bm25`, **every** hit of **every** query scores as in a fresh index of the live rows, to six decimals, at real chunk lengths, **in both columns**. This is the story index's first `Top risks:` entry. The `scan` column matters most here, because a `REINDEX` writes a segment, which stores document lengths approximately above 39 tokens (`src/segment/fieldnorm.h`), while the fresh index of `s0` is a memtable. If any hit differs in either column, other than a value Task 2's stray-score rule names below, stop: report the corpus, query, key, column and both scores to the maintainer, and record nothing as a fix basis.

**The stray score, and how this task treats it.** On the compose Postgres the index-scan statement sometimes returns one (query, key) score that no other run returns (task prompt → `## A second defect, found while implementing Task 1`). This task does not explain it, retry it, re-score it or average it away. A run of record that carries a value no other run of the same pair returns is recorded as it was captured, and that value is named in the record as a stray, with its step, query, key, column and both values, and a pointer to Task 2. A stray is identified only by re-running the same pair; the record lists how many runs were taken.
