### Task 1 — Carry a self-invoking wrapper's on-disk command line forward in `writeWrapperScripts` when asked to

**Goal:** Give the wrapper generator an opt-in rule. When the caller asks for it, and a wrapper's configured value is that wrapper's own invocation, the command line the wrapper **on disk** already runs becomes the body this run renders. A forced run then re-renders the template around the hand-set line instead of replacing it with detection's line or with the `harness_fail` stub.

**Where this layer stops.** This task adds the option, the precedence arm, the on-disk reader and the result field. It does **not** decide when the option is on, print any report row, or touch `cli/src/commands/init.ts`. **Task 3** sets the option to `true` on a self-adopt run only, makes `init.ts`'s `keptWrapperBody` delegate to the reader exported here, and owns the end-to-end test that drives the compiled CLI. With the option absent or `false`, every existing behaviour is byte-identical. That is what keeps `docs/cli.md` §5's adopter-facing precedence true.

**Source:** `cli/src/generators/scripts.ts` → `resolveBody`, `writeWrapperScripts`, `wrapperCommandLine`.

### Targets

- `cli/src/generators/scripts.ts`: the option, the reader, the precedence arm, the result field, and the module and function doc comments that state the precedence.
- `cli/test/wrapper-carry-forward.test.mjs` (new): the generator-level suite for the arm.

**Work:**

- [ ] `WrapperScriptsOptions` gains `readonly carryOnDiskCommandLines?: boolean`, with its doc comment stating that the caller sets it on a self-adopt run only (Task 3) and that it is absent for every adopter. `WrittenWrapper` gains `readonly carried: boolean`. It is true exactly when the body was taken from the file on disk, and it carries the same "what this run resolved" caveat `command` already states.
- [ ] Export `readWrapperBody(path: string): WrapperBody | undefined` from this module, beside `wrapperCommandLine`, which it calls. It returns `undefined` when nothing is at `path` (`existsSync`) and `{ kind: 'unrecognised' }` when the read throws, which is the same contract `init.ts`'s `keptWrapperBody` has today. It reads and never writes: `node:fs` `existsSync` / `readFileSync` only. That keeps the generator a planner (`.claude/context/cli.md` → *"a generator may read the filesystem to decide but may not mutate it"*). Task 3 consumes it under exactly this signature.
- [ ] `resolveBody` gains the new arm **between precedence 1 and precedence 2**. It applies when the option is on, the configured value `=== invocation`, and `readWrapperBody(join(repoRoot, scriptsDir, file))` is `{ kind: 'command', command }` with a non-empty `command`. The body is then that `command`, with `carried: true` and no warning. An `unresolved` or `unrecognised` on-disk body, or an absent file, falls through to precedence 2 and 3 unchanged. A raw configured line (precedence 1) still wins over the file, because it is the adopter's stated intent. Thread `repoRoot` / `scriptsDir` / the option into `resolveBody` as parameters rather than reading module state.
- [ ] Keep the recursion assertion in `writeWrapperScripts` applying to a carried body: a carried line that runs the wrapper itself (`invokesScript`) throws the same `HarnessError` as any other body. Update the `resolveBody` doc comment's numbered precedence and the module header's `## Scope` paragraph, so the header states the arm and that it is opt-in. A reviewer holds the change to the header (`.claude/context/cli.md` → *"A reviewer holds a change to its module's own header"*).
- [ ] `cli/test/wrapper-carry-forward.test.mjs` (new): its header opens with the rule it enforces, in the words *a wrapper whose configured value is its own invocation keeps the command line on disk when the caller opts in, and only then*. It imports `writeWrapperScripts` from `../dist/generators/scripts.js` and `WritePlan` from `../dist/core/writer.js`, on the precedent of the suites that already import from `../dist/` (`cli/test/init.test.mjs`, `cli/test/daemon.test.mjs`). It builds a throwaway directory under `os.tmpdir()`, removed in process, holding `scripts/test.sh` and `scripts/typecheck.sh` whose forwarding lines are `bash scripts/run-gates.sh "$@"` and `npm run build "$@"`, with a config whose `commands.test` / `commands.typecheck` are `bash scripts/test.sh` / `bash scripts/typecheck.sh`. Cases: (a) with the option on, the enqueued requests' `content` forwards `bash scripts/run-gates.sh` and `npm run build`, and `written[].carried` is true for both; (b) with the option absent, `test.sh` renders detection's line passed in `rawCommands` and `typecheck.sh` renders the `harness_fail` stub (`unresolved: true`), which is the perturbation partner of (a); (c) with the option on over an on-disk stub (`harness_fail …`), the stub is not carried; (d) with the option on and a raw configured line, the raw line wins; (e) a carried line that runs the wrapper itself throws. No case writes into this checkout.
