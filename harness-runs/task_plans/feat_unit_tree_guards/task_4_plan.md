### Task 4 — State the tree-guard run in the test-run rule and wire it into the layer implementer

**Goal:** After a unit's own test run, the unit runs every `treeGuards` entry whose `covers` glob matches a path its change touched, through `<test_file_cmd>`, and treats a failing guard as it treats a failing own test — so a unit whose diff adds a `cli/test/*.mjs` file with a bare `process.env` spread fails its own unit run on `main-anchor-isolation.test.mjs`, before Run gates (task prompt, Acceptance 1).

**Depends on:** nothing at run time — the plugin reads `harness.config.json` → `treeGuards`, whose shape Tasks 1 and 6 define as an optional array of `{ test, covers }`, both non-empty strings, absent meaning none. `test` is the argument `<test_file_cmd>` takes, verbatim; `covers` is a repo-relative glob.

**Where this layer stops.** This task states the rule once, in `plugin/instructions/unit_loop_core.md` → `## The test-run rule`, and makes the implementer carry it out and report it. The planners' and reviewers' lines that point at it, and the reword of `plugin/docs/AUTONOMOUS_FLOW.md`'s Phase G sentence that restates the old one-file rule, are **Task 5's**. No other file outside these two changes in this task — every other citer of `## The test-run rule` points and never restates (that section's own *Who may cite this* rule). The roster gains exactly one entry, `docs/config.md`: Task 7's `treeGuards` row in `docs/config.md` → `## 5. Key reference` cites this heading for the run instead of restating it, and a document outside `plugin/` may point at the heading only if it is on the roster.
