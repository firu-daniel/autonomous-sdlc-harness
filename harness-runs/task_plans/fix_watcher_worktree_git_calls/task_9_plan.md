### Task 9 — `harness-run.yml` refuses a branch that changed the job's surfaces before anything runs from it

**Goal:** Settle goal 4 for the `run` job of `cli/templates/github/workflows/harness-run.yml`. Today, `Check out the run's branch` checks out `inputs.branch`. Later steps then run that tree's own `$SCRIPTS_DIR/setup-worktree.sh`, `remote-run.sh`, `autonomous-watcher.sh job` and `push-branch.sh`. They read `scriptsDir` from that tree's `harness.config.json` and generate the profile from it. `Install the pinned plugin` clones the marketplace repository named in that tree's `.claude/settings.json`, and the session loads that tree's `.claude/settings.json` and `.mcp.json`. A previous job's agent can commit any of them. The tree is the main checkout in job mode, so these paths are write-protected in the session, but the protection does not stop a commit.

After this task, a new step runs the **pinned** CLI's `doctor --job-surfaces=<GitHub default branch>` and stops the job when the branch's own commits changed any of those paths. It runs **before `Read the configuration`**, the only `run`-job step that writes `SCRIPTS_DIR` to `$GITHUB_ENV`, and so before the plugin install, the profile and every `$SCRIPTS_DIR` step. It runs, like every other `run`-job step that runs `npm` or `npx`, from `$RUNNER_TEMP` rather than the checkout, so no `.npmrc` or `node_modules/` the branch carries is in npm's reach.

**Why before `Read the configuration`, and not merely before the first `$SCRIPTS_DIR` step.** The post-session steps are gated on `always() && env.SCRIPTS_DIR != ''` (`Push the branch`, `Save the state bundle`, `Upload the state bundle`), `${{ !cancelled() && env.SCRIPTS_DIR != '' }}` (`Open the pull request and report`, `Continue, wait or stop`) and `cancelled() && env.SCRIPTS_DIR != ''` (`Notify a cancelled job`). A failed step skips every later step whose `if:` carries the implicit `success()`, but not those. If the refusal ran after `Read the configuration`, `SCRIPTS_DIR` would already be set, and those steps would run `bash "$SCRIPTS_DIR/push-branch.sh"` and `bash "$SCRIPTS_DIR/remote-run.sh" save|deliver|continue` from the very tree the check refused, unsandboxed, with the push credential. Placed before it, a refusal leaves `SCRIPTS_DIR` unset, and every one of them skips. That is the run-actor gate's existing precedent, which the header states: *"a refused `run` sets no SCRIPTS_DIR, so its `always()` and `!cancelled()` steps skip too."* The placement fails closed. **Any** non-zero exit of the step, including an `npx` that cannot fetch the pinned CLI, leaves `SCRIPTS_DIR` unset. Nothing is lost by skipping: no step that produces state (`Restore the previous job's state`, `Run the harness`) has run yet.

**What a refused job reports**, which the header paragraph and Task 15 state:

- **The job.** It ends `failure`. The step's log carries `doctor`'s report naming each changed path, and the step adds one `::error::` annotation, so the run's summary page shows the refusal.
- **The run's record.** No state bundle is saved or uploaded. The next `remote-run.sh sync` / `status` therefore maps the run by the existing no-bundle rule (`remote-run.sh` header → `THE \`killed\` AND \`expired\` MAPPINGS`): `paused` / `killed` when an older run of the branch carries a bundle, else `failed`. `poll` re-dispatches only a bundle's `pause_reason: usage`, so it never re-dispatches the refused run, and `continue` never runs, so nothing chains.
- **The notification.** The job sends none. Every notify path is a script in the refused tree, so this is the same outcome as the run-actor gate's refusal and `Check for jq and gh`'s.
- **The `collect` job** checks out the default branch and runs that tree's scripts: (a), unchanged.
