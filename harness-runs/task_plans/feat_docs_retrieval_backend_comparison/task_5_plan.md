### Task 5 — Measure the MCP round trip, cold start and resident memory of either backend's stdio server in `mcp-backend-pass.mjs`

**Goal:** One pass that drives **either** backend's shipped stdio MCP server the way an agent session does. It times what an agent actually waits for: the process and model load before the first answer, and each `search_docs` round trip. It also samples each server's resident memory, and the Postgres container's for the Python backend. Both backends are measured by the same code, so the two sets of figures differ only in the server. That covers task prompt item 5: *"Report the MCP round trip and the library-level call separately … Report **cold start** … Report the Python service's resident memory, and the Postgres container's separately."*

**Depends on:** Task 2, for `backends.mjs` → `backendFor(label)`, which returns the label or throws `eval: unknown backend <label>; the backends are typescript, python`. Also Task 1, for `mirror-fixture.mjs` → `buildMirrorFixture(repoRoot, resolved)` → `{ dir, config, files, warnings }` and `removeMirrorFixture(dir)`. Also Task 3, for `python-backend.mjs` → `indexPythonCorpus({ checkout, fixtureDir })` → `Promise<{ files, chunks, embedded, unchanged, deleted, warnings }>`, which warms the Python index before the server is timed. For `evals/docs-retrieval/README.md` only, it also depends on Task 4, the last task to edit that file before this one.

**Where this task stops.** The **library-level** latency is not measured here. It is the runner's per-arm `p50` / `p95` (Task 4: `searchDocs` bracketed in process for TypeScript, `search_ms` for Python). This pass measures the MCP side only, so the write-up can report the two separately. The figures of record are taken by the **operator's hand run** (story index → **Manual setup required**). This task verifies the pass on scratch output only and records nothing.

**The interface this task produces — Tasks 9 and 11 restate it:**

```
runMcpBackendPass({ checkout, corpus, queries, backend })   // the eval's parseArgs surface plus a raw backend label;
                                                            // resolved through backends.mjs → backendFor(backend) first,
                                                            // so an unknown label throws before anything is built or spawned
  -> Promise<{ backend, corpus, snapshot: { files, chunks }, serverId: { name, version },
               coldStart: { connectMs, firstCallMs }, calls: [{ id, roundTripMs, serverMs: number | null }],
               client: { p50, p95 }, server: { p50, p95 } | null,
               residentKb: number, postgresMemory: string | null, host, node, generatedAt }>
renderMcpBackendSection(result) -> string    // plain Markdown, no machine-local path, no connection string
```

**Work:**

- [ ] **Header and fixture.** The header states *"The rule this module exists to enforce"*: both servers are started over the same mirror fixture with a **warm index**, so cold start means process and model load, not an index build. The cold index build is `cold-build.mjs`'s for TypeScript, and the operator's timed `index` run for Python (Task 9's protocol). The header cites `query-log-pass.mjs` as the TypeScript-only precedent and says why this pass does not reuse it: that pass grades the query log, and this one compares two servers. The pass's **first** statement is `const resolvedBackend = backendFor(backend)`, imported from `backends.mjs` (Task 2), the one owner of the backend set. It runs before the corpus is resolved or any fixture is built, so an unknown label, such as an operator's `pyhton`, is refused by name and nothing is spawned or created. Every later branch in this module (the warm-index command, the spawn command, `serverMs`, the Postgres memory, the rendered label) reads `resolvedBackend`, never the raw `backend` argument, and `result.backend` is `resolvedBackend`. Then the pass resolves the corpus through `corpusConfig`, loads the query set through `queries.mjs` → `loadQueries`, and builds the fixture with `buildMirrorFixture(checkout, resolved)`. It warms the index first: for `typescript`, `execFileSync(process.execPath, [<checkout>/cli/dist/cli.js, 'docs', 'index', '--cwd', dir])`; for `python`, `indexPythonCorpus({ checkout, fixtureDir: dir })`. Either one's `files` / `chunks` become `snapshot`. It refuses by name when `RETRIEVAL_STUB_ENV` (`cli/dist/retrieval/models.js`) is set, and removes the fixture in a `finally` on every exit path.
- [ ] **Spawn and cold start.** Branch on `resolvedBackend` only. Use the MCP SDK's `StdioClientTransport` with `stderr: 'pipe'`, as `query-log-pass.mjs` → `runLeg` does. For `typescript` the command is `process.execPath` with args `[<checkout>/cli/dist/cli.js, 'docs', 'serve', '--cwd', dir]`. For `python` it is `bash` with args `[<checkout>/scripts/python-service.sh, 'run', 'serve-mcp', '--repo', dir]`, where `serve-mcp` is `cli/dist/retrieval/pythonBackend.js` → `PYTHON_SERVE_SUB_COMMAND`, imported, not retyped. The database URL is in the child env only: the child env's `PYTHON_DATABASE_URL_VARIABLE` value is `pythonDatabaseUrl(process.env)`, both names imported from `cli/dist/retrieval/pythonBackend.js`. `pythonDatabaseUrl` is the one place the default is decided, so this module neither restates the rule nor imports `PYTHON_DEFAULT_DATABASE_URL`, and it never writes the URL into a message, a return value or the rendered section. `connectMs` runs from just before `client.connect(transport)` to its resolution. `firstCallMs` runs from the same start to the first `search_docs` call's return. `serverId` is `client.getServerVersion()`. Calls use `SEARCH_TOOL_NAME` (`cli/dist/retrieval/server.js`) with `{ query }` only, so `k` is each server's own default, as the query-log pass does.
- [ ] **Round trips and server time.** Call every query once in set order, timing each round trip from the client (`roundTripMs`). A call answered with `isError` refuses with the query id and the text. For `python`, parse each `harness-docs: search_ms=<ms>` stderr line, in call order, into that call's `serverMs`. The prefix is `docs-retrieval-service/src/harness_docs_retrieval/mcp_server.py` → `TIMING_LINE_PREFIX`. Compose it from `DOCS_SERVER_NAME` (`cli/dist/retrieval/server.js`) plus `: search_ms=`, and name the owner in the header. A count of timing lines different from the call count refuses by name. For `typescript`, `serverMs` is `null`: its in-process figure is the runner's arm E. `client` and `server` are `metrics.mjs` → `percentile` at 50 and 95, the eval's one percentile.
- [ ] **Memory, then teardown.** After the last call and before `client.close()`, read `execFileSync('ps', ['-A', '-o', 'pid=,ppid=,rss='])` and sum `rss` over the process subtree rooted at `transport.pid`. For Python that subtree is bash, then `uv`, then the server, and the header says the figure therefore includes the wrapper and `uv`, stating their share when the per-process rows are printed. For `python` only, read the compose `postgres` container's `docker stats --no-stream --format {{.MemUsage}}` for the id `docker compose ps -q postgres` returns, run with `cwd` `docs-retrieval-service/`. Every child process uses a fixed argument vector and no shell. If `docker` is absent or the container is not running, `postgresMemory` is `null` with the reason in the rendered section, and the pass does not refuse. Then `client.close()`, and confirm the server process has exited.
- [ ] **Render, and the README row.** `renderMcpBackendSection(result)` prints one Markdown block: the backend, corpus id and snapshot stamp, server name and version, cold start (both figures), client and server p50 / p95, resident memory, Postgres memory, host, Node and timestamp. Its header line states *"taken through `mcp-backend-pass.mjs`, warm index, model load included in `firstCallMs`"*. Add the README row: *either backend's stdio MCP server over a mirror of the corpus with a warm index — cold start (process and model load), per-call round trip, server-side `search_ms` where the server prints it, and resident memory.* In the same edit, amend the existing `query-log-pass.mjs` row, whose *"the only pass whose latency includes the per-call refresh and the MCP round trip"* this module falsifies: it becomes the shipped `search_docs` query log exercised over the TypeScript server's MCP against the real models, with `mcp-backend-pass.mjs` named as the cross-backend MCP pass. Nothing else in that row changes.
