# business_parity_user_review_reviews/

One `<branch>/user_review_<N>/review_<k>.md` per fix-plan **round**, holding the parity reviewer's review of a hands-on-review fix plan rather than of a task plan. One `<branch>` subdirectory holds one branch's set, and one `user_review_<N>/` subfolder inside it holds one user-review round's: `<N>` is the user-review round, `1` for the unsuffixed review, so a later user-review round's files never land on an earlier one's. `<k>` is the fix-plan round, shared by both fix-plan gates' folders, so round `<k>`'s file here sits at the same index as its file in `architecture_user_review_reviews/`. The fix-plan index plays the role the story index plays at the task-plan gate, and its per-finding folder the role of the per-task files. The round number names the file; the loop's cap counts only the rounds since the last writer dispatch that was not a findings revision or since a resumed session's start, and never names a file — so an index an earlier pass already used is never reused.

The writer is the parity reviewer, the same agent and the same lens that grades a task plan into `<state_dir>/business_parity_reviews/`; it is told which of the two it is holding by the paths it is passed. It asks of each drafted fix what it asks of a planned task: does it cite a real source in the reference implementation for every constant, call name and field, do the described payloads match field by field, do the described predicates match the reference's boundary comparisons. The reader is the fix-plan writer, re-dispatched in revision mode with every file of the round — this gate's and the architecture gate's — and expected to apply their Must Fix items to the fix-plan index or to the per-finding files they name.

The directory exists only while `phases.parity` is `true` in `devscene.config.json`: a project with no reference implementation to compare against will not have it, and turning the phase on and re-running `init` creates it — an absent directory here is a configuration answer, not a missing artifact. While the phase is on, the reviewer writes a file every round, on `PASS` as well as on `FAIL`, each carrying exactly one `verdict:` line — so a file is no longer a failed round, and the rounds this gate failed are its `verdict: FAIL` lines. Every file is written before the fix plan is approved and before any of its fixes is implemented. Files stop at a round every gate passed or at the fifth round, where the flow escalates with the closing round's paths. A file is replaced only by its own reviewer re-running a round that was interrupted; otherwise no file supersedes an earlier one, and the numbered set is the gate's whole history for that user-review round. The whole directory is committed with the branch, since no ignore rule reaches it: the autonomous flow commits at each round's end, and the supervised flow names the files for the human's commit.

The mistake worth naming is reading a later file's silence about a deviation as proof the earlier file was wrong to raise it. The writer revises the plan between rounds, so a deviation an earlier file names and a later one omits was most often fixed, not mistaken; the earlier file is the record of why the plan changed.
