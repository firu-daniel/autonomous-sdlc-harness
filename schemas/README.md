# schemas/

`harness.config.schema.json` is the JSON Schema (draft-07) for `harness.config.json` — the repo-scoped configuration that names the adopting project's layers, verification commands, protected branches, run-artifact directory and optional phases. That file lives at the **root of the adopter's repository and is committed**, so every contributor and every headless run reads the same values, and a change to it is reviewable like any other change. The boundary is deliberate in both directions: machine-local values — filesystem paths outside the repo, background-daemon preferences, a secret's *value* — belong in the plugin's `userConfig`, which stores them per user and can mark a value sensitive, while any **constrained vocabulary** must live here instead, because the `userConfig` option schema has no `enum` and so cannot restrict a value to a fixed set. A third home sits outside both: what a remote run needs beyond `execution.target` — its runner, credentials and tunables — lives in the GitHub repository's own variables and secrets, as `docs/config.md` §2 states. A worked configuration is at `examples/harness.config.json` at the harness root; the sibling `negative/` directory, beside this file, holds the fixtures that must be **rejected**, so a constraint whose whole purpose is to refuse an input has a file proving it does.

`flow-graph.schema.json` is the second schema, and it is not a configuration schema: it describes a **flow graph**, the routing of one harness flow as data — its dispatch and terminal nodes, the edge each outcome takes, its loop counters and caps, and its skip constructs. The graph it validates is `cli/templates/scripts/flows/task_plan_writing.graph.json`, which `init` copies into the adopter's scripts directory. The schema checks shape only; the checks JSON Schema cannot express belong to `scripts/check-flow-graph.sh`, whose schema-valid fixtures live in `flow-graph-check/`, beside this file. `npm run validate:flow-graph` validates the graph and those fixtures.
