# The analyze command

**Who reads this:** someone deciding what `/harness-analyze` may do — an adopter about to run it, or a contributor implementing or reviewing one of the assets that promises it. It answers what the command writes, what it refuses to write, what it does when it cannot tell, and what each of those was chosen over. Every other site in this tree states the rule; the reasoning is here, one section per decision.

`autonomous-sdlc-harness init` is deterministic Node with no model in it: it detects a layout from file existence alone (`docs/cli.md` §4), writes the conventions documents as *skeletons*, and stops. This command is the other half — it reads the adopted repository and turns those skeletons into that project's actual rules. It changes no behaviour on its own; what it produces is what every later run reads as ground truth, which is why the decisions below are mostly about restraint.

---

## 1. The target vocabulary

**Targets are the layer names in `layers[]`, computed at invocation time, plus three reserved names.**

| Target | What it covers |
|---|---|
| `layers` | The layer profile itself — proposed, never written by this command (§3) |
| `project` | The always-loaded `.claude/CLAUDE.md` |
| `conventions` | The shared cross-layer document, which is generated whether or not a layer points at it |
| a `layers[].name` | The document that layer's `layers[].conventions` names |

No argument runs every target, in the order `layers` → `project` → `conventions` → each `layers[]` row in order. The profile goes first because every target after it is one of its rows: a pass that revised the profile last would have written per-layer documents against a layer list it was about to propose changing.

**One document, one write, per run.** Targets are a sequence and documents are a set, and the two do not correspond: every preset this CLI generates ends in a catch-all row whose `conventions` is the shared document, so on a freshly wired repository the `conventions` target and that row name the same file. The run walks the sequence and **skips a row whose document an earlier target already covered**, reporting the pair once. Un-deduplicated, the second visit fails §4's untouched-skeleton test — the first pass removed the marker — and so takes the hand-edited branch: interactively it asks the adopter to merge a document this same run wrote seconds earlier, and under `--yes` it merges the document with itself. The alternative, dropping the `conventions` target where a row names its document, was rejected because the target is the only cover for the configuration where **no** row does, and a target that appears and disappears with the layer list cannot be documented as a target.

**Under dispatch the rule is the same rule; what moved is its enforcement.** The run resolves the target sequence into a **document set** — every `layers[].conventions` value the targets reach, normalized and deduplicated, plus the shared document — and dispatches **per document, not per target** (§11). The pairing a catch-all row creates therefore collapses before anything is written rather than being walked past mid-pass: two targets naming one file produce one dispatch, and two writers can never be aimed at one file. What was a property of the order one session happened to walk in is now a property of a set the session computes before it sends anything, which is what makes the rule hold under concurrent writers rather than in spite of them.

**The command body enumerates no list.** It carries the rule — read `harness.config.json`, take the names from `layers[]` — and nothing else. That is the only way a static plugin command and a per-adopter layer list cannot drift: a command file naming targets is written once at publication and is wrong for the first adopter whose layer list is not a preset's, and wrong silently, because a target nobody can spell reads as a target that does not exist.

**One spelling ships, and it is the layer name.** `autonomous-sdlc-harness init`'s closing next step names layer targets, and so does every conventions stub footer (`cli/src/generators/claudeContext.ts`, the `target` value). A path vocabulary was rejected because it cannot express two of the four rows above — no file path names `project` or `layers` — so it would need a second vocabulary beside itself.

**The collision rule.** The schema's `name` pattern permits `project`, `conventions` and `layers`, so a layer may legitimately carry one of them. A layer so named **loses the bare word to the reserved meaning**, the run says so rather than resolving it silently, and that layer's document is still covered by the no-argument pass — the only thing lost is the one-word invocation, and losing it visibly costs less than a run that wrote the profile when it was asked for a layer.

## 2. Mode: greenfield or existing

**A flag answers it, detection is the default, and provenance makes a wrong answer visible.** `--existing` and `--greenfield` each answer outright. With neither, the mode is detected: a repository carrying source outside the harness's own generated paths is `existing`. The resolved mode is **printed before any write**.

Detection alone is not enough because it is file existence, the same class of signal as stack detection, and a repository that is genuinely being started fresh inside an existing tree looks exactly like one that is not. A flag alone is not enough either: the adopter most likely to run this is the one who just finished setup and has not been asked anything yet.

What makes the wrong answer cheap is not the flag, it is that **every rule the command writes carries provenance** — the files it was derived from in `existing`, `proposed from the skeleton` in `greenfield`. A greenfield pass over a real codebase then produces a document whose every line says it was proposed from a skeleton, which is readable as wrong at a glance, and re-running with the explicit flag corrects it. The cost is a per-rule tax on the prose; it is paid twice over, because the same provenance is what §5's reconciliation and §6's gap report are argued from.

## 3. What it may write

**The conventions documents and `.claude/CLAUDE.md` are the command's to write. `harness.config.json` is not.**

A layer-profile revision is **proposed**: shown as a diff of the `layers` array, and applied only through `autonomous-sdlc-harness config set layers '<json>'` after an explicit yes. That verb validates the result, keeps the schema's catch-all `contains` clause — at least one row with `path: "."` — enforced, and writes the `.bak` on every set (`docs/cli.md` §8). A second writer of that file would be a fourth view of a value `autonomous-sdlc-harness init`, `autonomous-sdlc-harness config set` and the schema already share, and the first three agree only because none of them is a model.

**The verdict record is the second key, and the last one.** After the `layers` diff decision — applied, or declined — the `layers` target records what it concluded with `autonomous-sdlc-harness config set detection.review '<json>'`: one of `applied` / `considered-no-change` / `proposed-and-refused`, with a one-line rationale and a date. It reaches `harness.config.json` through the same validating writer, which takes the `.bak` on this key as on `layers`. Two clauses bound it, and both belong in the section a reader consults about what this command may write. **Recording a refusal is not applying it** — the record says the profile was examined and the answer was no, `layers[]` is untouched on that arm and the run says so, so the record may never read as the change having landed. And the record is what `doctor`'s `layer-profile` warning clears on (§7), which is what closes the loop the propose-never-write rule opens: the profile leaves this command as a proposal, and what became of it comes back as a graded fact instead of as nothing at all.

**An accepted proposal makes the command write less, not more.** In a no-argument run whose `layers` proposal was applied, every document that proposal did not newly name is still asked, with **`skip`** its default answer rather than §4's `merge`, and `--yes` takes that default with the rest — so registering one layer costs one write and no merges. Nothing else moves: an untouched skeleton is still written without asking, a `conventions` path the accepted proposal newly named is written because no file is behind it, and outside an accepted proposal the ask keeps `merge` as its default.

**Under dispatch the prohibition binds a party this section never had.** What may be written is unchanged; who holds the authority is not — every conventions document is now written by a dispatched `conventions-writer` carrying `Write` and `Edit` (§11), so the rule is enforced **in each writer's own fence**: it writes the one `document_path` it was given and nothing else, and never `harness.config.json`. That is the same decision rather than a weakening, because the reason for it is unchanged — a second writer of that file would still be a fourth view of a value `autonomous-sdlc-harness init`, `autonomous-sdlc-harness config set` and the schema already share — and what a fence buys over a convention is that a writer with no reason to open that file also has no instruction that would let it. Chosen over handing the writers a read-only view of the configuration and letting them propose changes back — rejected because the `layers` proposal is one decision about the whole repository and no single-document writer sees enough of it to make it, so it stays the session's — and over leaving the prohibition stated in this file alone, rejected because a rule that binds an agent has to stand in that agent's own definition, the only text it reads.

**What that hand-off costs at run time, plainly.** `/harness-analyze` is a **supervised, first-session command**. It is not part of any unattended flow, and shelling the harness CLI out of a session is a tool call the generated permission profile does not allow-list — so on the apply path the session is **expected to ask**, and a person is expected to be there to approve it. That is consistent rather than accidental: applying a layer-profile revision already needs an explicit yes or `--apply-layers`, so the permission prompt lands on a decision that was never going to be automatic.

**Any write under a repository's own `.claude/` tree is a supervised action, and no permission entry moves that wall.** That is a second reason the command is supervised, beside the one above. The tool layer treats `.claude/**` as a sensitive path and evaluates that **ahead of** the permission profile's allow entries. An unattended run's `--permission-mode acceptEdits` does not cover it, and **no `permissions.allow` entry can grant it**, so any fix premised on generating or hand-adding one is wrong before it starts. A first run of this command needs that write access, because the conventions documents it fills live there; the command is bounded by the wall rather than owning it. Measured on Claude Code **2.1.237**: an unattended run completed with **exit 0 having written nothing**, reporting its own targets as blocked, while the identical invocation under a permissions bypass wrote all five documents. Silent success is the shape to expect, so run the command interactively and check that the conventions documents actually changed. One consequence of the wall is closed. An unattended run's planner could once schedule a task whose targets are conventions documents, and such a task parks the run rather than failing it. Both ends are now shut: the corpus is rules-only, so growing the code does not falsify a conventions document (`plugin/agents/conventions-writer.md`), and the planner raises an invalidated rule in its `## Corpus staleness` return section — written to the branch's improvement-observations intake and the run's closing Done summary — instead of scheduling it (`plugin/agents/task-plan-writer.md`). What that removed is an unattended run's exposure to the wall, not the wall: this command still fails silently when it is not run supervised.

**The alternative not taken** is an allow-list entry for the CLI binary in the generated profile. It is out of scope here: a profile entry that lets a session rewrite the repository's own configuration unattended is a bigger decision than this command, and it would be taken to save one approval on a path that already requires one.

## 4. Re-run, and what an interrupted run leaves behind

**One whole-document write per target.** A pass is a sequence of complete documents, not a document assembled in place, so an interrupted run always lands on a document boundary: the targets it reached are finished, the ones it did not are untouched, and the half-written file that later reads as authoritative cannot occur. What an interruption costs is time, which is the cost the adopter already accepted by saying yes.

**Under dispatch the guarantee is re-derived, not inherited — and it costs one thing it did not.** Each document is still written whole by one writer, on one dispatch, so every document is either untouched or complete and the half-written file that later reads as authoritative still cannot occur. Two properties of the sequential pass do not survive with it. The finished set is **no longer a prefix** of the announced order, so *which targets were reached* is answered by re-running and letting the table below classify each document, never by reading the report's order down to the point of interruption. And a document written but not yet reviewed is indistinguishable from a reviewed one, so a re-run classifies it as filled and asks, with **merge** the default: a review pass a re-run cannot see is a review pass it will not redo. That is accepted rather than solved. The alternative is a marker recording review state inside the adopter's document — a fourth signal on a file that already carries three, the unfilled marker, the `**What belongs here**` block and the provenance line — read by every later run and by `doctor` for the benefit of the interrupted one.

| State of the target | How it is recognised | What the command does |
|---|---|---|
| Untouched skeleton | its `<!-- harness:unfilled -->` marker is present **and** its `**What belongs here**` block is still there | written without asking |
| Filled by an earlier pass | either half of that test fails | asked, with **merge** the default |
| Hand-edited | either half of that test fails | asked, with **merge** the default |

**Skip is always available** on both asked states, and the two are deliberately not distinguished: the command cannot tell an adopter's edit of a filled document from a document written by hand, and a rule that guessed would guess against the more careful adopter. `--yes` takes those defaults without asking — and after an accepted `layers` proposal the default on every document that proposal did not newly name is `skip` rather than `merge` (§3). Applying a `layers` proposal needs `--apply-layers` and **never `--yes` alone** — a blanket yes is consent to write documents, not to rewrite the configuration everything else is generated from.

The recognition test is two-part rather than one because the skeletons tell a hand-writer to replace everything above the footer; a leftover marker in an otherwise hand-written document would make the marker alone report a finished document as untouched, and overwrite it. §7 grades on the same test for the same reason.

**What a forced setup re-run costs the analysis.** `autonomous-sdlc-harness init --force` regenerates every `create-if-absent` artifact after one `.bak` each (`docs/cli.md` §3), so a filled conventions document goes back to its skeleton and `.claude/CLAUDE.md` is re-rendered from the template with the setup-pending banner back in it — which re-opens `doctor`'s `setup-analysis` warning until the command is run again or the banner block is deleted by hand. **Two artifacts are kept instead, on what the run measures rather than by name** (`docs/cli.md` §3): a conventions document **already** a skeleton whose `.bak` holds the filled one, which the run keeps and names that `.bak` as the reason for; and `.claude/CLAUDE.md` when regenerating it would write the bytes already there, which the run keeps and leaves its `.bak` alone. So a second forced pass no longer costs the analysis the first one rescued. That is still stated as the cost of a forced run, not as a defence against one: a forced pass over a filled corpus skeletonises it exactly as before, and the one thing changed is that the single-generation `.bak` is no longer overwritten with content carrying less than it already holds.

## 5. The adopter's existing material

**Harvest-and-reconcile, in `existing` mode.** An adopter's own always-loaded file, their per-area convention documents and their contributor guides are inputs alongside the code. The case that decides it is a repository that already carries a mature, hand-grown convention set: everything a good conventions document needs is already written there, and derive-from-code-only would read past it and re-derive a weaker version of what it just ignored.

Reconciling costs what ignoring does not: prose goes stale in ways code cannot, so a harvested rule may describe a repository that no longer exists. The tiebreaker is therefore split by what each source can testify to.

- **Code wins for what *is*.** A prose rule the code contradicts is **not written as a rule**. It goes into `## Not determined` with both sides — what the document says, what the code does — because the disagreement is information the adopter has and the command does not.
- **Prose wins for intent** the code can neither corroborate nor contradict: a prohibition, a security rule, a policy. Those are carried over **attributed to their source**, because there is nothing in the tree that could have produced them and dropping them discards the better source.

**Harvesting and reconciling are two jobs, and two actors hold them.** The **repo-level harvest** — finding the adopter's always-loaded file, their per-area convention documents and their contributor guides — is done once by the session and reaches every writer as an inventory of source paths. The **reconciliation** of a harvested source against the code is per document and belongs to whoever writes that document: the dispatched writer for every conventions document (§11), because the tiebreaker above cannot be applied without the code side, and the code side is gathered per `scope` by that writer alone. The one exception is the `project` target, which is why this is not stated as "the writer's" wholesale — `.claude/CLAUDE.md` is written by the session itself (the command's step 4b), so there the session holds both sides, its harvest inventory and its own repo-wide file-name and layout survey, applies this tiebreaker itself, and reports a contradiction it finds in the run's closing report, that file carrying no `## Not determined` section to hold one.

**What the split costs, plainly.** Reconciliation is now performed several times over one corpus by writers that do not see each other, so the same harvested rule may be resolved differently in two documents. The corpus pass (§12) is what **detects** that — C1 and C3 are the checks that reach this shape, and for C3 it is one of two, a rule carried in two members being its subject whether the two statements agree or have drifted apart — but it detects rather than prevents: the divergence is written before it is found, and a corpus of one has nothing to compare. The shared cross-layer document, written first and passed down as a read-only anchor, narrows it for the vocabulary but not for the verdict. Chosen over the session reconciling centrally and handing each writer settled rules — rejected because that re-imports the whole-repository read the delegation exists to avoid, and because a rule reconciled without that document's code in view is the weaker version of the derivation this section already refuses.

## 6. What it could not determine

**Every filled document ends with a `## Not determined` section**, carrying two classes of line: one per thing the pass looked for and did not settle, plus what would settle it — **several outstanding items sharing one reason and one thing that would settle them being one entry naming that reason once, never one entry each repeating it** — the section's primary meaning — and one per **reviewer finding the writer decided not to apply**, each beginning with the exact literal `Reviewer finding not applied — ` and carrying the finding, the writer's reason and what would settle it. That literal is a **wire string**: the command's closing report, both halves of the agent pair — `conventions-writer` owes the line, `conventions-reviewer` grades it — and Gate 8's roll-up (`docs/development.md` §5) all grep for it, so a paraphrase at any one of those four sites breaks the count silently and none of them may be reworded alone. `grep -rln "Reviewer finding not applied" plugin/ docs/development.md` is the set, and is the check that it has not moved.

**One section rather than two.** Both classes make the same claim — this pass did not settle it, and here is what would — and a reader of the finished document needs the disagreement in the place they already read for gaps, not in a second section they may not know exists. It is durable rather than run-time only because the report is read by the person running the command, once, while the document is read by everyone afterwards, and the one reader who can judge a writer/reviewer disagreement is the adopter. Chosen over a separate `## Declined findings` section — rejected as a fifth signal on a document that already carries several, and invisible to every reader who scans for gaps — and over recording a declined finding in the report alone, rejected because it evaporates with the session that printed it.

The section is **present and says "nothing outstanding" when there are no gaps.** An absent section is ambiguous between a document with no gaps and a document written before the rule existed, and the adopter reading it is the one person who cannot tell which. A confident wrong convention is worse than an admitted gap by a wide margin: an admitted gap costs one reader one lookup, while a wrong rule is read as ground truth by every implementer, every reviewer and every plan from then on, and it is read most confidently by the runs least able to check it. The second class stands on the same footing: recording a finding the writer declined is **mandatory** — a duty, not a permission — while whether to apply it stays the writer's judgement.

## 7. `doctor`'s share

**`doctor` grades deterministic facts only, and never the quality of prose:**

- a configured conventions document that is still an **untouched skeleton** by §4's two-part test — the `<!-- harness:unfilled -->` marker **and** the `**What belongs here**` block both still present;
- the setup-pending banner still present in `.claude/CLAUDE.md`;
- a configured `layers[].conventions` path with no document behind it;
- a configured `layers[].path` with no directory behind it — that value is the scope every dispatched agent is handed, so a path resolving to nothing returns no files and each agent scoped to it reports having found nothing wrong; its remedy is the one its `conventions` sibling has, a corrected value through `autonomous-sdlc-harness config set layers`.

It stays a `warn`, so it never moves the exit status on its own: a repository that has been correctly set up and not yet analyzed is not broken, and the exit contract in `docs/cli.md` §7 — a warning never turns a build red — is what makes that safe in CI. What a freshly wired repository exits is a different question and not this check's to answer: `remote` fails an adoption with nowhere to create a run's working copy from, so a repository carrying only this warning and no remote still exits 1.

**The unfilled fact uses the command's own two-part test rather than the marker alone.** The footer tells a hand-writer to replace everything above it, so a document somebody wrote by hand plausibly still carries the HTML comment; grading on that alone would report a finished document as unfilled forever, and the only remedy on offer would be the command that adopter declined.

**Two further checks are this command's share without being `setup-analysis`, and neither grades prose either.** `layer-profile` warns while the profile carries no row scoped below the repository root **and** its provenance does not account for that — the unrecognised-layout fallback, unrecorded, or a detected preset whose source root did not resolve — and it clears on the verdict §3 describes — any of the three, since what it grades is whether the profile was considered, not what was concluded. `layer-drift` names the source directories no layer covers, looking under the application directory and under the parents of the configured layer paths, and it is **not graded** while the profile carries no such row: there every directory would qualify, and that state is `layer-profile`'s to report once, as itself. The boundary is stated because a reader of §3 will otherwise take the verdict to silence both: a recorded verdict clears `layer-profile` and leaves `layer-drift` grading, since a layer hand-added after the review is precisely what that check reports. `layer-drift` does **name** the record where there is one — the verdict and, where it was recorded, its date — so a reader can tell a directory an earlier review already declined from drift that appeared after that date. It reads the record to report with, never as a gate: the grade is the coverage derivation's alone, and that derivation reads no `detection` field.

**Every state `doctor` reports has a remedy that does not require running the command.** An unfilled document can be written by hand; the setup-pending block can be deleted by hand; the verdict `layer-profile` waits for is a hand `autonomous-sdlc-harness config set detection.review`, and the layer `layer-drift` names is added with `config set layers`. Where a verdict is already recorded, that `config set layers` is the *whole* remedy the check gives and re-running this command is worth something only where the tree has moved since the recorded date — over the tree the review already read it re-derives the decision the record holds. That is the coupling worth having — `doctor` predicts what a run of this command will find — without the one that is not, which is `doctor` grading judgement and turning a repository red over prose one person wrote and another would have written differently.

## 8. How this is verified

The command is judgement, so the deterministic gates that cover the CLI do not reach it. The acceptance evidence is three legs, and only the first is mechanical.

1. **The deterministic half is genuinely testable, and is tested.** The marker, the banner, the templates, the generator's output and the `doctor` check are ordinary CLI surface: `cli/test/**`, the plugin validator and the leak scan cover them exactly as they cover everything else (`docs/development.md` §5).
2. **The command body is reviewed by reading, and so are the two agent definitions.** The reviewed-by-reading surface is three files rather than one: the command dispatches a writer and a reviewer (§11), so the definitions those dispatches arrive in are read beside it. The reading also has to check a **wire**, not only prose — every field a dispatch sends is a field the receiving definition declares, under the name it declares, and every value a return carries is one the report or the next dispatch consumes. A renamed or dropped field fails silently: the receiving agent reads it as prose. **Three field sets are what that reading now covers beyond the single-document wire**, named so the check is a list rather than a habit: `pass` on both definitions and on all five dispatch shapes the command sends — write, document review, document fix, corpus review, corpus fix — required on each and never defaulted, since a defaulted axis lets a caller bug read as a document pass; the corpus review dispatch's own values, `corpus_documents` with its per-member `document_path`, `target`, `scope` and `role` plus `iteration`, read against the reviewer's corpus table **including the fields that axis deliberately does not send**; and `shared_document_divergences:`, produced by every **document-axis** writer return — `none` on the corpus axis, whose fix returns reach no collector — and consumed by the shared document's reconciliation dispatch, the one field whose producer and consumer sit in different files and whose omission the caller's stop condition is what catches. That reading is acceptable *because* leg 3 exists — reading alone would be an assertion that the instructions are good, which nobody can make about a document nobody has run.
3. **A supervised run against a throwaway fixture repository outside this checkout**, whose pass criteria are **invariants of the output** rather than judgements of it — with the one exception Gate 8 states, its corpus criterion (v), a citation-support check whose disposition is invariant but whose residual is the hand-runner's reading: every configured document exists and no longer carries the marker; every one carries provenance and a `## Not determined` section; every one still carries the stack-independent rule block its skeleton stated between `**What belongs here**` and the example, restated in the project's own vocabulary or verbatim but not absent, and the surfaces layer's document states the test-attribute convention an interactive test locates elements by; the setup-pending banner is gone; the `layers` array is untouched unless a proposal was explicitly applied to it, **and** a `detection.review` record is present whichever way that target went — its `verdict` matching the outcome the run reported in step 6, and on the refused arm its `rationale` naming the proposal that was refused; after an accepted proposal, every already-filled document that proposal did not newly name is **byte-identical** and only the newly named one is written; and each `<convention_symbols>` / `<impl_stack>` / `<commit_conventions>` question the shipped agent definitions ask of a conventions document has an answer somewhere in the documents `layers[]` points at — the agent set derived by grep rather than listed (`grep -rln "convention_symbols\|impl_stack" plugin/agents/`, plus `plugin/agents/committer.md` for the commit policy). **What a run now shows that no reading can** is that the pair is **dispatched** rather than merely defined — a definition says nothing about whether anything called it, and a writer no dispatch reaches produces an empty document set — and that a finding the writer declined is visible in **both** places it is owed, the document's `## Not determined` and the run's closing report (§11). The corpus axis is inside that same leg for the same reason and adds two facts to it: that the pass is **dispatched at all** rather than only specified, and that its findings **reach a fixer** — the fan-out to each named document, and the session's own application of a finding against `.claude/CLAUDE.md`, which no definition attests because no definition performs it. What that run is graded on is unchanged: the criteria are Gate 8's own (`docs/development.md` §5).

**What this does not prove is that the rules are right.** No gate here can reach the last of it: a rule whose citation **supports** it — the construct the rule asserts present in the file it names — and which is complete and answers every question the agents ask passes all three legs while still being wrong about what this project intends. What the review does now reach is narrower and real, and stating it keeps this sentence from conceding ground the command has since taken: a rule whose cited file does not show the construct it asserts, or shows a competing one instead, is a finding before the adopter ever meets it. What the legs establish is that the output is *shaped* like a document the harness can use and *says where it came from*, which is what makes a wrong rule findable by the one reader who can judge it.

**The review moves the line, and not to there.** A shallow, unattributable or code-contradicted document now has a second reader before the adopter meets it, which is more than the sequential pass could claim. Three things stay unverifiable by any gate here, each of them a judgement and each of them the adopter's: whether a review improved a document, whether a finding the writer declined was rightly declined, and whether concurrent writers converged on one vocabulary beyond what the shared document forces. The declined findings are recorded in the document itself for exactly that reason. The criteria leg 3 is graded on are Gate 8's own (`docs/development.md` §5) and are not restated here.

## 9. How the offer reaches the command, and the naming hazard

**The offer is a flag on `autonomous-sdlc-harness init` defaulting to yes, and that command does not run the analysis.** It records the intent in the `.claude/CLAUDE.md` it generates — the one file every session in that repository loads without being asked — and this command removes that banner as its last act. The hand-off is a written intent, and the thing that acts on it is the first session the adopter opens.

Two mechanisms were weighed and not taken:

- **Shelling setup back into the host tool.** It makes a deterministic Node program's output depend on a model session — the exact property that lets a second `init` over the same repository produce the same result and an adopter re-derive the recorded preset by hand (`docs/cli.md` §2), and the reason there is no model call anywhere in that command. Immediacy is not worth it.
- **A `SessionStart` hook, for v1.** This is the one question here that cannot be settled by argument: whether such a hook fires as expected under a plugin install is **unmeasured**, and a hand-off that silently never fires is worse than one that waits for a person to read a banner. The probe that would settle it is small and named rather than assumed — ship a no-op `SessionStart` entry in `plugin/hooks/hooks.json`, open a session in a wired repository, observe whether it fired — and it is not this branch's.

**The hand-off has two halves, and the closing report states them in order.** The written intent reaches the first session through the banner; the command that acts on it ships in this package's plugin, so it exists only in a session that resolves that plugin. `autonomous-sdlc-harness init`'s closing report therefore opens on the plugin-wiring state this same run left behind — the `enabledPlugins` key it merged into `.claude/settings.json`, and whether an `extraKnownMarketplaces` entry went with it — and names the analysis in the step after it. A numbered list is acted on in its order, so the step that makes the command exist cannot come after the step that runs it. Chosen over a precondition sentence appended to the run step, which annotates the ordering rather than fixing it, and over a banner-only clause, which reaches the first session but not the terminal the adopter is standing at while the two halves are still un-sequenced — the banner carries a clause too (§10), for the reader who never sees the report. The failure closed is roadmap item 15's own acceptance criterion 5 — no site left describing a command that behaves differently — read against the ordering of the CLI half and the plugin half rather than against the command's own promises.

**The run step prints a pasteable invocation, and printing is the whole of it.** `autonomous-sdlc-harness init` starts no process, opens no window and waits for nothing: it prints a string a person may copy. Chosen over naming the command for the adopter to open a session and then type it — two actions for one intent. It reopens nothing: spawning a session or a terminal stays rejected on its own four counts — a permanent cross-platform surface, a spawned process inheriting an environment the CLI cannot predict, failure that is invisible because `autonomous-sdlc-harness init` has already exited 0, and dead code on every non-interactive run — and a printed line has none of those properties. **What is measured, and what is not:** the headless `-p` form of an agent-CLI invocation carrying a prompt is attested in this tree (`cli/templates/scripts/autonomous-watcher.sh`); the interactive initial-prompt form this line prints is not, and the hand-run leg of §8 measures it (`docs/development.md` §5, Gate 8). If that measurement comes back negative the line is dropped and the step goes back to naming the command to type — there is no third wording.

**The precondition is stated at two sites, and deliberately not everywhere the command is named.** It belongs where a site tells the adopter to run the command **as their next action**: the closing report, and the setup-pending banner. It is left out where a site names the command as one route among two, or as the owner of a judgement — `doctor`'s `setup-analysis` warnings, whose standing rule is that every state it reports has a remedy not requiring the command (§7); the conventions stub footers, which keep the hand-fill verb §10 protects; and the layer-detection warnings `autonomous-sdlc-harness init` prints in its own output (`cli/src/detect/signals.ts`'s unrecognised-layout fallback, `cli/src/detect/presets.ts`'s `flat` exclusion and `general`-layer note). The last is the case that looks like a counter-example and is not: it names the command as the owner of a judgement the detection table refuses to make, and it prints **above** the ordered report that states the precondition for the whole run — so repeating it there would put the install fact in front of a reader who has not yet been told there is anything to run. The rule is therefore: the precondition goes where a site directs the adopter's next action, once, and nowhere a site merely names the command as the owner of a decision.

**The naming hazard.** An adopter about to be offered this meets two initializers: this package's setup verb, and the host tool's own built-in initializer, which also writes an always-loaded project file from the codebase. So **every adopter-facing line writes the verb in full — `autonomous-sdlc-harness init` — never a bare `init`**, and the command body states in one sentence how it differs from the host tool's writer: this one fills the per-layer conventions documents the configured `layers[]` points at, and refuses to guess what it could not determine.

## 10. What the skeletons say now the offer exists

**Each conventions stub's closing line leads with the analyze route and keeps the "replace everything above" verb.** Leading with the route matches what most adopters will actually do, and keeping the verb keeps the hand-fill path visible — it is also the thing §4's two-part test measures, so removing it would remove half the recognition test.

**The generated `.claude/CLAUDE.md` carries the setup-pending banner under its heading**, plus its two reworded fill prompts — the opening paragraph and the file-naming table.

**Both banner wordings state where the command comes from**, each naming it as a command of the harness plugin that `autonomous-sdlc-harness init` enabled for this repository in `.claude/settings.json`, and each placing that clause **before** its own disposal sentence so neither ends on anything else. It is a fact about this repository's state rather than an instruction — it names no marketplace and no install step — so it neither implies the command is the only route nor becomes a standing order, and the two rules below survive it. It is in **both** wordings rather than the accepted one alone because the decliner who changes their mind reaches for the same command as the accepter: on one arm only, the other reader meets a banner naming a command that a session which does not resolve the plugin will not have, with nothing in the block saying what would have to be true for it to exist.

One rule makes all of that true for the adopter who **declined** the offer as well as the one who accepted: **no wording may imply the command is the only route**, and **every block the setup writes into a file that is loaded on every turn states its own disposal** — the command removes it, or the adopter deletes it once those sections are written. Without that rule, declining leaves a permanent "setup is not finished" block in the one file every session reads, and a standing `doctor` warning behind it, with no way out but the command that was declined. That is the failure this section exists to prevent.

## 11. Per-document dispatch, the single review pass, and the corpus pass beside it

**The command keeps the decisions and delegates the documents.** Every conventions document is written by a dispatched `conventions-writer`; on the **document** axis each written one gets exactly one `conventions-reviewer` pass and the writer is re-dispatched once with those findings. Each is also one **member of a set** the same reviewer reads on the **corpus** axis, at most twice per run, where a finding against it costs at most one further writer dispatch per iteration — plus, for the shared cross-layer document alone, the fix-only reconciliation sent before iteration 1. The cap is stated on both sides rather than only here: `conventions-writer.md` → `## Invocation contract` admits that third dispatch explicitly, so a caller that exceeds it is refused by the receiving contract. This section records that split and what each half of it was chosen over; §12 records the corpus axis's own decisions.

**A dedicated pair, not an extension of the documentation pair.** Reusing `docs-writer` and `docs-reviewer` was the cheap shape and does not fit, on four counts that are properties of those definitions rather than preferences: `docs-writer` is gated on `phases.docs` and returns a clean no-op when it is off, while a conventions document exists for every adopter regardless of that phase; every path it writes is contracted to sit under `docs.root`, and no conventions document sits there; its templates are `feature` and `concept`, neither of which is the skeleton contract a conventions document is graded against; and `docs-reviewer` grades backend payloads, stored shapes and reachability, which is not the question a conventions document is graded on. Widening either to carry a second contract would put a phase gate that has nothing to do with conventions in front of the document every agent reads its rules off.

**What each agent is given, and what it is not.** The writer receives the values its own dispatch tables name — `conventions-writer.md` → `## Invocation contract`, whose write, document-fix and corpus-fix tables are the one list, `pass` among them and required on every dispatch of either axis. The set is **cited here and enumerated there**: a second copy in this file is a second thing to keep in step, and the copy that goes stale is the one a reader reaches first. It is given **no** authority over `harness.config.json`, no setup-pending banner and no layer proposal — those stay with the session (§3), and a writer able to reach the configuration would be the second writer of it that §3 exists to prevent — and it **writes** exactly one file, its own `document_path`, on either axis. What the corpus axis relaxes is a **read** and nothing else, granted in one place and cited here — `conventions-writer.md` → `## Resolved values`: on a `pass: corpus` fix the writer may read any sibling a finding names, `.claude/CLAUDE.md` included, because that sibling *is* the finding's evidence; it still resolves no value of its own from it, and reading a sibling is no licence to write it.

The reviewer's two dispatches are disjoint sets rather than one and its superset. On `pass: document` it receives that document, the same scope, mode, exclusions, harvest inventory, demand set and anchor the writer worked from, plus the pre-write state nobody else can re-read. On `pass: corpus` it receives `corpus_documents` instead — one entry per member carrying that member's `document_path`, `target`, `scope` and `role` — plus `mode`, `excluded_paths`, `harvested_sources`, `demand_set` and `iteration`, and **neither** `shared_document` **nor** the three `prior_*` fields: the pre-write comparisons are document-pass checks that do not run on this axis, and the set itself is the anchor. On both it holds **no write tool at all**: the read-only guarantee is its `tools:` allowlist rather than a sentence in its prompt, which is the same closure every agent in this package is held to.

**Both agents ship static, generated for no adopter.** They are ordinary plugin files: the per-adopter values reach them from `harness.config.json` and from the dispatch, never by templating the definition at setup time. A generated agent is a file that differs on every adopter's disk from the one this repository reviews, and nothing downstream reads it again.

**An adopter may keep a pair of their own outside the plugin, and the two are not kept in step.** A repository that maintains conventions documents of its own may carry independent definitions of such a pair under its own `.claude/agents/`, dispatched by hand to amend those documents when a branch changes a convention one of them states, and may later migrate onto the packaged pair. Neither copy references the other and nothing keeps them in step: each is written against a different vocabulary — one against an adopter's configured layers and dispatch arguments, the other against one repository's actual documents and directories — so they may diverge in wording, and that is not a defect to be reconciled.

**What the session keeps: everything decided once for the whole run.** The target and document sets and their announcement, the mode decision, the repo-level harvest of the adopter's own prose, the derivation of what the shipped agent definitions ask a conventions document for, the classification of every document and every `project` section, the `layers` proposal, the `project` target itself and the closing report. What it delegates is **every conventions document, the shared cross-layer one included.** Keeping that one in the session was the obvious alternative — it is written first, everything else anchors on it, and the session holds the widest view of the repository. It was rejected on three grounds: the wide view that document needs reaches a writer as dispatch arguments anyway, so keeping it buys nothing it does not already have; keeping it re-imports the context saturation the delegation exists to avoid, for the largest document of the run; and it would leave exactly one document with no dispatch to hang a **document-axis** review on, for the document every other one is written against — leaving it exactly what the `project` target has: the corpus axis's read of it as one member of a set, which §12(g) calls the review-time half rather than the whole.

**Review coverage, read per axis: every delegated document exactly once on the document axis, plus membership in at most two corpus reads.** The two targets the session writes itself **split rather than lump**. The `project` target is unreviewed on the **document** axis — there is no dispatch to attach a review to, and a session reviewing its own work in its own context is not an independent read — but it **is** read on the **corpus** axis as an ordinary member of the set, which is what gives the most widely loaded file in the repository a rule-holder at review time (§12(g)). That does not offend the second ground: the corpus read is dispatched to the same independent, write-less reviewer every other document gets, and the session applies its findings on that target rather than grading itself. The `layers` proposal is unreviewed on **both** axes — it is a proposal rather than a document, and its reviewer is the person who says yes to it (§3).

**The writer applies the fixes, re-dispatched with its own document and the findings.** That is the closest available thing to "the same writer": a returned sub-agent's context is gone and nothing resumes one, so the fix dispatch carries back what the write returned, including the pre-write state that is no longer on disk. A fresh reviewer-independent fixer was rejected — it would re-derive from scratch what the writer already knew, for one pass over a handful of findings — and the reviewer fixing its own findings was never available: it holds no write tool, and its independence is what its findings are worth.

**Vocabulary coherence is bought with one serialization.** In a run that **writes** the shared cross-layer document — every no-argument run in which classification did not skip it, a `conventions` run, and a single-target run naming the layer whose `conventions` is that document — it is written, reviewed and fixed first, and its finished text is then handed to every later writer as a read-only anchor. A run that does **not** write it — a single-target run naming another layer, or any run in which it was skipped — anchors on whatever already stands on disk, and on nothing where that file is missing or still a skeleton. The discriminator is whether the run writes it, never whether its document set contains it: a run may hold the document in its set and still not write it. Chosen over a glossary artifact the adopter never asked for and nothing later reads, and over nothing at all — which is five writers naming one concept five ways across documents the same agents read as one vocabulary. The cost is one document serialized ahead of the batch, paid once per run.

**Concurrency changes nothing a reader sees.** The remaining documents go out in waves — all writes, then all reviews, then all fixes, one message per wave — and the report is printed in the announced target order regardless of completion order. A run that serialized the waves produces the same documents and the same report; concurrency is an efficiency choice and nothing depends on it.

**A declined finding surfaces in both places, not one.** It stands in that document's own `## Not determined`, on a line beginning with the literal `Reviewer finding not applied — ` and carrying the finding, the writer's reason and what would settle it; and it stands in the closing report, once per document, with the same finding and the same reason. Both, because the two have different readers: the report is read once, by the person running the command, and the document is read by everyone afterwards — and the one reader who can judge the disagreement is the adopter, who may meet it months later with no report to hand.

**Dispatch discipline: the policy this command does not activate, and what it does instead.** `/harness-analyze` is this tree's first **command** that composes sub-agent prompts with no instruction core behind it, so the question of what an orchestrator may add to a prompt arrives here without the usual answer. It **declines** to activate `plugin/instructions/dispatch_discipline_instructions.md`, and both alternatives were weighed. **Activating it whole** was rejected on two independent grounds, either sufficient: that file's `## Activation` list is closed — *"no document beyond the six named above may activate it"* — so a seventh activator means editing a shared policy every dispatching instruction core obeys, a change to the fleet's contract carried on one command's branch; and its obligations have no write point in an adopter's repository, where a setup run has no branch, no committer and no run-control tree to hold the record or the disclosure that reports it, and where this command's write authority is fixed at the conventions documents plus `.claude/CLAUDE.md` (§3). **Splitting it** — activating the knowledge-not-conclusions boundary while declaring the record and the disclosure inapplicable — was rejected because a partial activation is a restatement by another name: it re-weights a policy this document does not own, and leaves two readings of one contract in the tree. What ships instead is the **closed dispatch block**: every write, review and fix prompt this command sends carries exactly the fields the command declares and no added prose — no `context_notes:` line, no "where to be suspicious", no severity or verdict calibration, no scope narrowing — which holds the same boundary in a shape a reader can check against the command file itself. The cost, plainly: nothing records an addition made anyway, because there is no run-control tree to record it in, so what this buys is a legible contract rather than an audit trail. It matters most on the review dispatch, whose independence is the only check the one-pass design has, and a caller that aims a reviewer gets confirmation back rather than evidence.

**What this deliberately is not, on either axis, is a convergence engine.** The **document** axis has no cap, no verdict and no re-review, because there is no loop: one review, one fix dispatch, and the run moves on. An iteration cap there would imply a loop worth capping. The **corpus** axis adds a **fixed** two iterations, and that is a count rather than a cap for the same reason the document axis has neither: the reviewer emits no verdict by design, so there is nothing to converge against, and an unbounded loop against a verdict-less reviewer terminates on exhaustion rather than on agreement — the ping-pong a review loop with no convergence signal produces. Two rather than one because the corpus fixes go out concurrently and iteration 1's writers cannot see each other's corrections, so iteration 2 is the safety net for a fix that introduced a new problem; it is narrowed to what iteration 1 changed plus the members those findings' evidence cited, and does not run where nothing changed. The rule that a receiving party's obligation must be a duty with a test applies on **both** axes to the **recording** — the writer must record every finding it declines, and both sites are checkable — not to the applying, which the writer decides on the merits. A verdict would still imply a gate that does not exist.

## 12. The corpus pass's own decisions

§11 states the shape of the second axis. Recorded here is what each decision inside it was chosen over — one lead per decision, in the order a reader meets them.

**(a) A mode on the existing pair, not a new agent pair.** A dedicated corpus reviewer was the obvious shape and was rejected: it would be a second holder of the same rules, which is the duplication the single-writer design exists to avoid, and the same argument that makes the `project` target's missing rule-holder a defect at all — (g) below. One contract governs both axes instead — the dispatch's `pass` value selects the value set, the check list and the return shape, and the strings a document is graded against are quoted from one place, so writer and reviewer cannot disagree about a contract that exists twice. The cost is admitted rather than hidden: each definition now carries two dispatch tables that are **disjoint sets rather than one and its superset**, and a reader of either has to resolve which axis they are on before reading a table. That is the price of one rule-holder, and it is paid in two files rather than in every adopter's corpus.

**(b) Two fixed iterations.** Chosen over loop-until-PASS and over one iteration. Loop-until-PASS has nothing to loop on: the reviewer emits no verdict by design (§11), and an unbounded loop against a verdict-less reviewer terminates on exhaustion rather than agreement. One iteration was rejected because the corpus fixes go out concurrently — iteration 1's writers cannot see each other's corrections, so a fix that introduces a new incoherence would ship unread. Iteration 2 is that safety net and nothing more, which is why it is **narrowed** to the members iteration 1's fixes changed plus the members those findings' evidence cited, and why it does not run at all where iteration 1 raised nothing or every finding was declined. The count is the terminator, and that is the design position rather than a compromise: fixed-two is the shape a verdict-less reviewer admits.

**(c) A `skip`ped document is context, never a fix target.** Chosen over grading and fixing it anyway. A `skip` is the adopter's own answer to a question this run asked, and a pass running after it that overrode it would make `skip` mean *"not yet"* rather than *"no"*. It is chosen equally over dropping such a document from the set, which would leave the corpus grading only the run's own output: a contradiction is measurable only against what the sibling documents actually say, and the documents the adopter kept are exactly where a partial re-run's contradictions land. So a skipped member is sent as evidence with `role: context`, and a finding whose correction lands in one is reported as an outstanding result of the run rather than dispatched to anybody. **One exclusion, and it is the document axis's own** — the third case in which `shared_document` is `none`: a skipped document still carrying `<!-- harness:unfilled -->` is left out of the set entirely, because an unfilled skeleton is template prose and measuring the adopter's documents against it produces findings against the template, which a writer then applies. It is reachable — §4's untouched-skeleton test is two-part, so a half-edited file is asked and can be answered `skip`. That is not the drop this decision refuses: the closing report names the excluded document and the marker, and the reviewer refuses such a member as evidence if one reaches it anyway.

**(d) The corpus axis grades only what a single-document pass cannot.** Its checks sit in an id space disjoint from the document pass's and cover contradiction, role vocabulary, duplication — of which divergence is one shape and not the trigger — cross-layer claims, coverage, and the document pass's voice test judged once over the set, of which census-vs-rule is one shape — every one of them a defect visible only **between** members. Chosen over re-running the document checks over the corpus, which is the *"the second pass just repeats the first"* failure: a finding whose evidence sits inside one member alone belongs to that member's own pass, and raising it here spends a dispatch to say what has already been said. The one exception is `.claude/CLAUDE.md`, which has no document pass at all, so a subset of the document checks applies over that member only — the subset, and the reason each excluded check is excluded, are named in `conventions-reviewer.md` → `## The corpus pass — what to verify` and are **not** restated here, one rule-holder being the whole of (a).

**(d2) The corpus reviewer returns its findings and writes no review file — a stated departure from the fix direction this pass was designed from, which had it write one.** Recorded as a departure so it does not read as an oversight. The reviewer's `tools:` allowlist carries no `Write`, and that omission *is* the read-only guarantee (§11); restoring `Write` for one artifact spends the guarantee on the artifact. The artifact is also unwanted at its destination: there is no committer behind a `/harness-analyze` run, so a findings file lands untracked in the adopter's repository for the adopter to clean up, and nothing downstream reads it — while the return is consumed in-session by the fan-out that applies it, and the durable record of anything the writer declines is already that document's own `## Not determined` line (§6). Chosen over adding a write tool to a deliberately read-only agent for a file with no reader.

**(e) The `demand_set` absence answer is never a finding.** The writer is *required* to answer every `demand_set` question falling in its scope, and for many projects the true answer is an absence — there is no logger, no localization accessor, no theming accessor. Two false positives follow directly from that requirement, and both are **rules of the pass** rather than advice to the reviewer's judgement: the same question answered in several members is required behaviour, so a duplication finding never fires on it — that check's subject is one **rule** carried in two members, and a question answered twice, each answer binding its own member's files, is the contract instead; and an answer shaped *"there is no `Y` and adding one is a decision to state"* is the document pass's own rule carve-out and is never a voice finding. A pass that flags a correctly framed absence answer is a defect in the pass, not in the document. That matters more here than in a hand-run gate, and the difference is who acts on the output: a gate's false positive is read by a person who can dismiss it, while these findings are **applied by a writer**, which edits correct prose out of the corpus.

**(f) `action: merge` adopter prose is graded like any other line, with a bounded correction.** Chosen over a provenance-based shape exemption, which was the alternative on offer and would make the corpus's enforceability depend on its authorship: a rule an implementer reads binds regardless of who wrote it, and the merged document is what an adopter with mature conventions actually ends up with — the corpus most worth grading, not least. What bounds it is the **correction** rather than the check: where restating a carried-over line as the rule it stood in for would decide something only the adopter can, the correction is to move it to `## Not determined` carrying both sides — what the prose says, what the code does — never to delete it. That is §5's own tiebreaker reused rather than a second rule invented for this axis, so the merge path and the write path resolve a contradiction the same way.

**(g) The `project` target's rule-holder is closed by reference — not by a second dispatch, and not by an inline copy.** Two candidates were weighed and both cost more than the third. **Dispatching `conventions-writer` for that target too** removes the exemption outright, but costs a dispatch and requires the writer contract to grow a mode that writes two named sections rather than a whole document — a second document contract inside the one agent whose contract is *one whole document*. **Restating the writer's content rules inside the command's `project` step** costs no dispatch and re-creates exactly the duplication the single-writer design exists to avoid; the two copies then drift, and the drifting one is the copy the session reads. What ships is a third shape: the step **names** `conventions-writer.md` → `## The document` and `## House rules` and applies them to the sections it composes, on `write` and on `merge` alike, with the single adaptation that obligations presupposing a document contract have no subject in two sections. That leaves exactly one rule-holder at write time and costs nothing. Corpus membership adds the other half at review time — the most widely loaded file in the repository is now read by the same independent reviewer every other document gets, which is what *checked by nothing at all* meant.

**The shared cross-layer document's reconciliation: what it buys.** The document keeps its first-and-complete write→review→fix chain. Making the ordering two-phase instead — write it, run the layer wave, then review it last against the finished corpus — was rejected because the layer writers' read-only anchor is load-bearing (§11), and a two-phase ordering spends precisely that. What is added is a **fix-only** dispatch, sent before the corpus review, spending divergences the run already holds: each layer writer returns them as a **typed field** on its own return, the session collects that field across the layer wave, and the lines go back to that document's writer as ordinary findings. Typed rather than harvested from incidental report prose, because a divergence the run states and cannot act on is the failure this closes; it runs first so the corpus review reads an already-reconciled anchor and its findings are net-new.

**And the honest residual.** The one-pass rule for *review* is intact, so a divergence **no layer writer reported and the corpus pass did not raise** still survives the run: the reconciliation converges what the run knows, not what it might have known. That is the price of keeping the anchor, and it is stated rather than argued away — the shared document still gets no second independent read of its own, and the corpus pass is the only thing standing where one would have been.

**Why a forwarded divergence is recorded under the existing literal.** §6 makes `Reviewer finding not applied — ` a wire string with four sites that none may reword alone, so a second literal for a second origin would mean a second grep and a second count, and every consumer would have to learn which one it was reading. One literal, one grep, one count: a forwarded divergence lands on that line like any declined finding, and the **origin travels inside the line** under the `Layer-writer divergence — ` prefix — the same prefix the writer's own contract uses to tell a forwarded divergence from a reviewer finding, and the one the closing report prints intact.
