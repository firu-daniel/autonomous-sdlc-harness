## Should Fix

1. **Open question 2 can be closed now, from source.** The "same tokeniser and k1/b" inference is labelled Inference (§3) and is technically sound. `pg_textsearch` parses with the index's `text_config` and extracts terms and frequencies from a `TSVector` (`src/access/build.c` → `tp_extract_terms_from_tsvector`, lines 1102–1158). Document length is the sum of per-lexeme position counts (lines 1146–1152). IDF is `log(1 + (N − df + 0.5) / (df + 0.5))` (`src/scoring/bm25.c:27-38`), with `avg_doc_len` kept by the index (line 164). Change: cite these lines in §3 and in recommendation 3. State that `tsvector-bm25` must use that IDF variant and `length = Σ positions`, which `to_tsvector` caps the same way on both paths. Note that `pg_textsearch` statistics are per partition (README → `### Partitioned Tables`). Reduce OQ2 to "confirm by test".

2. **The exit criteria test rank overlap only, but under R2.3 scores matter too.** Lexical becomes the default, and the round 1 synthesis leaves lexical abstention open (`README.md` → `### 5.2`: "whether lexical abstention can be calibrated is **Unconfirmed**"). Any abstention or floor on BM25 scores is one threshold across hosts. So the fast path and the portable path must agree on **scores**, not only on top-10 overlap. Otherwise "switching to it should change speed, not answers" fails at the abstention edge. Change: add a per-query score check to step 1, for example max absolute score difference ≤ 1e-3 on the shared top-10, and name abstention as the reason. The candidate bound (§3, step 3) changes answers on the portable path only, so state that it breaks cross-host parity unless the fast path is bounded the same way, or the bound is off by default.

3. **Option (b) is compared against a strawman.** The table gives (b) a "`ts_rank` everywhere popular" fallback. ### Still open

**Should Fix**
1. **Score parity holds only on a freshly built index.** `pg_textsearch` uses "physical index statistics, not MVCC-filtered corpus statistics" (`timescale/pg_textsearch` → `ARCHITECTURE.md`, the paragraph ending at line 67). Dead tuples count in `N`, `df` and `avg_doc_len` until `REINDEX` or compaction. A `tsvector-bm25` that reads live rows will drift from it between rebuilds. Change: in step 1, compare scores right after `REINDEX`, which today's store issues after every refresh that wrote. Name this drift in recommendation 2 and in the verdict's "score parity is likely", because it bears on a shared abstention threshold. Alternatively, have `tsvector-bm25`'s write-time statistics adopt the same "as of last rebuild" rule.
2. **"Identical order" conflicts with the 1e-3 tolerance.** Two `float4` scores within the tolerance can swap order without either engine being wrong. Change step 1 to "identical order except between rows whose scores differ by ≤ 1e-3". Also state that `<@>` scores are negated (lower is better, `cli/src/retrieval/store.ts:276`) before they are compared.
