# Configuration

**Who reads this:** anyone adopting the harness into a repository, and anyone adding a parameterized asset to it. It answers one question per value — *resolve it at runtime, read it from `harness.config.json`, or let `init` write it* — and then, one row per parameterization token, says where that token's value comes from.

---

## 1. The three resolution classes

Anything that varies between one adopting repository and the next falls into exactly one of three classes. The class decides how a parameterized file is written, so it is worth settling before the asset is authored.

**Derived at runtime.** Paths and identities the harness computes on each run: the account home directory, the repository root, the directory above it, the sibling-worktree glob, the remote slug. These are *resolved*, never templated — a file that hardcodes them is wrong even when the hardcoded value happens to be right, because it stops being right the moment the checkout moves or a second worktree appears. The repository root comes from a **bare** `git rev-parse --show-toplevel`, the home directory from `os.homedir()`; everything else in this class derives from that root, that home, or the git remote. A bare invocation matters: an unattended run's permission profile can allow-list a literal read-only git command, while the same command wrapped in a shell substitution or embedded in a compound statement is a different string and stalls on a prompt.

**Config value.** Anything a team has to agree on and then commit: the verification commands, the default and protected branches, the architectural layers and their directories, the artifact and script directories, the optional phase toggles. These live in `harness.config.json` at the adopter's repository root. They are stable between runs, they are reviewable as a diff, and two people working in the same repository must not disagree about them.

**Generated at `init`.** Files the CLI writes into the adopter's repository once, which the adopter then owns and edits like any other checked-in file: the settings and permission profile the unattended modes run under, the run-artifact state tree, the git hooks, the wrapper scripts, and the conventions stubs the analyze command later refines against the real code. The harness does not keep reading a private copy of these — after `init`, the adopter's copy is the only copy.

---

## 2. Where configuration lives

`harness.config.json` sits at the root of the adopter's repository and is **committed**. A teammate who clones the repository is configured by that clone: no re-run, no per-machine setup step, and no drift between what a human sees locally and what an unattended run sees. Because it is a tracked file, a change to a layer list or a verification command arrives as a reviewable diff rather than as a silent difference between two developers' machines.

Machine-local values do not belong there. What varies per machine rather than per repository — filesystem paths that point outside the checkout, background-daemon preferences, and any secret's *value* — goes into the plugin's `userConfig` instead, which stores values per user in the user-level settings rather than in the repository, preserves native JSON types, and can mark a value `sensitive` so it is routed to OS secure storage instead of being written into a settings file in the clear.

What decides the side is variance, not secrecy. A repo-relative *path* to a gitignored credentials file is not machine-local: the path is the same for everyone who clones, and only the file's contents differ. So the path stays a config value while the file itself is never committed — which is why `qa.credentialsPath` and `pushEnvPath` are both declared here, and why neither of the files they point at is.

The split is not arbitrary — three properties of `userConfig` make it the wrong home for repo-scoped configuration:

- **It is per *user*.** Two developers on one repository could hold different layer lists or different test commands, and nothing would reconcile them. Values the team must agree on cannot live in a store whose whole design is per-person.
- **It is prompted at enable time.** That is reasonable ergonomics for two or three machine-local paths, and unreasonable for a layer table with a name, a directory and a conventions document per entry.
- **Its option schema is `.strict()` and has no `enum`.** An option declares `type` (`string` | `number` | `boolean` | `directory` | `file`), `title`, `description`, `required`, `default`, `multiple`, `sensitive`, `min` and `max` — and nothing else. A constrained vocabulary therefore cannot be expressed there at all, whereas a JSON Schema can restrict a value to a fixed set and reject anything outside it.

This release declares **no** `userConfig` keys. Declaring a key whose reader does not exist yet would prompt an adopter for a value nothing consumes; the one key §4 reserves — `reference_toolchain_path`, an absolute path to a toolchain directory outside the checkout — **stays reserved**, because that reader still does not exist. The CLI cannot read plugin `userConfig` at all, and the only consumer this release has for the path is the generated permission profile's allow-list for a toolchain outside the checkout, which takes it from `init --reference-toolchain-path` instead (read only when `phases.parity` is true). The key is declared when the parity module ships the agent-side reader that consumes it. That deferral is specific to `userConfig`, which prompts: a config key costs an adopter nothing until something reads it, so the schema declares its keys as soon as they are decided.

## 3. `stateDir`

`stateDir` is the repo-relative directory the harness writes run artifacts into — task prompts, plans, review findings, flow-progress records, statistics, ledgers. Its default is `sdlc-harness/`.

**It must not be a dot-directory.** The run-artifact tree has to be writable by an unattended run, and a dot-path is where a host reserves directories an unattended run may not write to. The measured case is narrower than the rule: `.claude/**` is treated as a sensitive path that `--permission-mode acceptEdits` does not cover, and an unattended run there completes with exit 0 having written nothing, reporting its own targets as blocked (`docs/analyze.md` → `## 3. What it may write`). Which dot-paths a host reserves is the host's decision rather than this tree's, so the rule refuses every dot segment instead of enumerating them, and the failure it prevents is a silent one — a run reporting success with nothing on disk to show for it. **Do not "fix" this to a dot-name in a later tidy-up.** The leading dot looks like the tidier choice and is the one that risks unattended operation.

The rule is enforced in three places:

- The schema constrains `stateDir` with a character-class `pattern` that permits only a letter, a digit or an underscore as the first character, **and** with a separate `not` clause on `(^|/)\.`. The `not` clause is what carries the rule for every *later* segment as well — the character class admits `.` and `/` after position 0, so `pattern` alone would accept `sdlc/../.claude` and resolve to a dot-directory at runtime; `(^|/)\.` refuses a dot at the start of any segment, which covers `../`, `/./` and `/.hidden/`. For the leading dot the two clauses are deliberately redundant, so that a later edit to the pattern cannot quietly drop the prohibition.
- `schemas/negative/` holds fixtures that must each be **rejected**, `state-dir-leading-dot.json` among them; the `validate:config:negative` script fails if the schema ever starts accepting one of them.
- `doctor`'s `state-dir` check re-checks the configured directory at runtime — that it is not dot-named and that it is writable — because a config can be edited by hand after validation, and it is the only one of the three that runs against the value the repository *currently* holds. Both of the schema's clauses are applied separately, as the schema states them, and the dot clause is applied to the **raw** configured value, since normalising one would strip a leading `./` that is itself a dot segment. Writability is answered by trying, because a permission bit, a read-only mount and a full filesystem are indistinguishable from a `stat`.

Both commands that can set the value refuse a dot-named one at the input as well — `init --state-dir` before it assembles anything, and `config set stateDir` before it writes — so the enforcement above is what catches a file edited by hand rather than the only thing standing in the way.

Two rows carry a class that is not one of the three, each for its own reason.

`<example_feature_slug>` names the illustrative feature the shipped sample fixtures are written around — the plans, prompts and review artifacts that demonstrate the flow have to be *about* something. It is neutralized once, when those assets ship, and is never resolved again in an adopter's repository; recording it as a config key would invent a key nobody sets. The three classes classify adopter-side parameterization, and this token has none.

`<reference_toolchain_path>` is an absolute path to an SDK directory that sits outside the checkout, so it varies per machine rather than per repository — the case §2 routes to `userConfig`. Its key is reserved rather than declared, because a `userConfig` option is prompted at enable time and nothing reads this one yet: the one consumer this release has is the generated permission profile, and `init` takes the path from a flag for exactly that reason. Its neighbour `<push_env_path>` looks similar and is not: that one is a repo-relative path to a gitignored file, which §2 keeps as a config value, so it resolves from `pushEnvPath` exactly as `<qa_creds_path>` resolves from `qa.credentialsPath`.

## 5. Key reference

One row per key; each row stands on its own. The five required top-level keys are `version`, `defaultBranch`, `stateDir`, `layers` and `commands`; unknown keys are rejected at any level, so a typo is a validation error rather than a setting that is silently ignored.

| Key | Type | Default | Meaning |
|---|---|---|---|
| `$schema` | string | — | Optional pointer to this schema, so an editor can offer completion and inline validation. Declared explicitly because unknown top-level keys are rejected. Editor metadata, not a setting: its value is a URI or a path resolved relative to this file's own location, not a repo-relative path. |
| `version` | `1` (const) | — (required) | Format version of this file. A release that changes the key set raises it and ships a migration, so an older config is recognized rather than misread. An **added optional key with no default** does not raise it: nothing in an older file is then misread, while raising the number would make every file already written against the current one fail validation outright, since the only version this release accepts is the one it declares. |
| `projectName` | string | — | Short identifier for the adopting project; the stem of generated daemon labels and worktree directory names. When omitted, `init` uses the repository directory name. |
| `defaultBranch` | string | `main` (required) | The branch work starts from and merges back into; also the diff base for a branch review. `init` **detects** this rather than assuming it — `origin/HEAD`, else the checked-out branch, else git's `init.defaultBranch`, else the default in this column — and `--default-branch` overrides the detection, so a repository whose integration line is `master` or `develop` is wired to that name. The second rung has **three** answers rather than two: the branch `HEAD` names, a **detached** `HEAD`, and a repository with no branch to name; the last two fall through to the rung below, and the rung that answers says which of them it met. A detached `HEAD` is the ordinary working state of a colocated `jj` repository — after every `jj new` — so there it is the rung that is normally lost rather than an anomaly. A value a **guessing** rung produced (the checked-out branch, `init.defaultBranch`, the schema default) that names neither a local branch nor an `origin/` remote-tracking ref here **draws a warning on the run that writes it**, and `doctor`'s `default-branch` check re-reads the configured value and reports whether the repository still resolves it. Both name the same two remedies: `config set defaultBranch <branch>`, which changes this key alone, or `init --reset-config --default-branch <branch>`, which rebuilds this file from detection and the flags after a `.bak`. A bare `--default-branch` is **not** one of them — a run that reads an existing `harness.config.json` rather than rebuilding it resolves that flag and drops it (`cli.md` §2). |
| `protectedBranches` | string[] | `["main"]` | Branches an automated run may never commit or push to directly. Entries may be globs, so a release namespace is one entry. **Not the whole protected set**: the effective set is this list unioned with `defaultBranch`, so the branch work merges back into is protected whatever the list says, and an empty list means exactly that one branch. An entry naming a branch this repository does not have is **reported and never removed** — by `doctor`'s `protected-set` check, and at the point of edit by `config set defaultBranch`, which names what this key still lists — because narrowing a protected set automatically is the one direction that fails unsafely. A **glob** entry is not graded at all: a namespace written ahead of use is what a glob is for. Setting either key leaves the guard behind it: the committed `<githooksDir>/pre-push` carries the set substituted into its `case` label when it was rendered, and git runs that file, so a push is judged by the rendered label until the hook is re-rendered — `init --force`, or deleting the hook and re-running `init`; an `init --reset-config` re-renders it as a consequence of the rebuild that stranded it (`cli.md` §2), never as a way to change the set. |
| `forge` | `"github"` \| `"gitlab"` \| `"none"` | — | Which code-hosting platform's pull-request and remote conventions the flow uses; `"none"` means no forge integration at all — work stays on branches and no pull request is opened. **Nothing reads this key in this release**: it is declared ahead of its reader, on the §2 principle that a config key costs an adopter nothing until something reads it. That reader is the **forge coupling** — an issue-label trigger, draft-pull-request output and comment-based park-and-ask — and not any numbered roadmap item in `development.md` §6: the outer-loop item that once carried this reference has shipped, and its `push-branch.sh` opens no pull request and consults no platform. It therefore has no default, so an absent value reads as *not yet decided* rather than as a silently assumed platform. |
| `stateDir` | string | `sdlc-harness/` (required) | Repo-relative run-artifact directory. Must not be dot-named — see §3. |
| `appDir` | string | `.` | Repo-relative directory of the project the harness operates on, for a repository that nests its application in a larger tree. Anchors where the application lives; it is not a working directory — commands run from the repository root and paths in this file are relative to it, except where a key's own row says otherwise. **Stack detection reads this key**: `init` resolves the directory it probes as `--app-dir`, then this value, then `.`, so a re-run and an `init --reset-config` both derive their layer scopes under the application directory the repository already declared. |
| `scriptsDir` | string | `scripts` | Repo-relative directory the generated wrapper scripts are written to. An unattended run's permission profile allow-lists literal paths under it, so it has to be stable and committed. |
| `githooksDir` | string | `githooks` | Repo-relative directory holding the committed git hooks; adoption points the repository's hooks path here so hooks travel with the checkout. |
| `agentModel` | string | `opus` | Model identifier the outer loop passes to a headless run — one place to trade run cost against capability. The default is a **family alias**, which the runtime resolves to the latest model of that family rather than to a pinned version, so it does not go stale when one release supersedes another; give a full model name instead when a pin is what you want. |
| `agentEffort` | `"low"` \| `"medium"` \| `"high"` \| `"xhigh"` \| `"max"` | — | Reasoning-effort level an unattended run is launched at, passed on the same launch line as `agentModel`. **Having no default is the setting**: with the key absent no effort flag goes on that line at all and the runtime applies its own per-model default, so a value here is a deliberate pin rather than a level this file chose for every adopter. Set it with `config set agentEffort <level>`. There is no `config unset`: to go back to the runtime's own default, delete the line from `harness.config.json` — an empty string and `null` are both refused by the enum, as they should be. One limit: the value set mirrors the levels the launch flag accepts, so a runtime that gains a level needs this enum widened before it can be configured, and a runtime that does not accept the flag at all fails the launch — which is why the key is opt-in. |
| `pushEnvPath` | string | — | Repo-relative path to the file holding the unattended runner's push-notification settings, sourced before a run starts. Keep that file out of version control; only its location is configured. |
| `clientEnvPrefix` | string \| null | `null` | Prefix a build tool requires before it exposes an environment variable to a client bundle. Lets a reviewer tell an intentionally public value from a leaked secret. `null` when the stack has no such rule. |
| `detection.preset` | `"monorepo"` \| `"layered-clean-arch"` \| `"python-package"` \| `"api-service"` \| `"flutter"` \| `"android-gradle"` \| `"jvm"` \| `"dotnet"` \| `"apple-native"` \| `"rust-cargo"` \| `"ruby-bundler"` \| `"php-composer"` \| `"cmake-cpp"` \| `"flat"` | — | The layer preset stack detection selected. A preset is a layer profile rather than a build tool, which is why `"jvm"` is one name for both Maven and Gradle JVM projects: they share the `src/main/<java\|kotlin>` source root and differ only in the runner, so a second preset would buy a second name and the same profile. `"dotnet"` is one name for a .NET backend and a .NET frontend on the same argument: they share the build tool, the `*.sln`/`*.csproj` manifests and the `src/` source root, and what would tell them apart is the optional-phase set, which `init`'s own flags decide rather than the preset. `"apple-native"` is one name for iOS and macOS, and for a SwiftPM package and an Xcode project alike, on that same argument: nothing a file-existence test can ask separates the platforms — the manifests, the `Sources/` root and the toolchain are the same — and which of `swift` and `xcodebuild` answers is the command family's question. `"rust-cargo"` names its build tool instead, because in Rust the manifest, the toolchain and the source root are one set — `Cargo.toml`, `cargo` and `src/` — with no second runner for the name to stay neutral about. `"ruby-bundler"` names its dependency tool on that same argument — `Gemfile` is the only manifest and `bundle` the only resolver — and its profile is a source root (`app/` or `lib/`, whichever exists) beside the `tests` row every preset takes where its toolchain's conventional test root exists — RSpec's `spec/`, else `test/` — rather than a Rails layer list, since naming a Rails application's `app/` sub-directories as layers would decide its architecture. A Rails-shaped repository never reaches it: it matches `api-service:route-directory` on its `app/controllers` and gains the Bundler commands through the command family, which is selected independently of the preset. A repository whose root `package.json` declares a script the npm commands are derived from does not reach it either: a React Native tree's root `Gemfile` pins CocoaPods and fastlane rather than declaring a Ruby stack, so the row declines it and it keeps its npm lines. `"php-composer"` names its dependency tool for that same reason — `composer.json` is the only manifest and `composer` the only resolver — and its profile is a source root (Laravel's `app/` or PSR-4's `src/`, whichever exists) beside a `tests` row on PHPUnit's `tests/`; a Laravel-shaped repository matches `api-service:route-directory` on its `routes/` and gains the Composer commands through the family. `"cmake-cpp"` names the build system for `"rust-cargo"`'s reason inverted — C++ has no single toolchain to name, since compiler, test runner and dependency source all vary, while `CMakeLists.txt` is the one file the ecosystem agrees on — and its profile is the `src/` source root where one exists, `include/` as a **second source row** on the same single-module document where that directory exists — a target's public headers are the API half of that same module, so they are source rather than tests — and a `tests` row on `tests/` or `test/`. Every row of every preset's profile is dropped where its directory is absent, and `cli.md` §4 states the rule once for all of them. It is the **last** detection row before the fallback, because a `CMakeLists.txt` is the manifest most likely to describe a sub-component of a repository whose own stack is something else — and row order settles only the cases whose stack has a row of its own. Node has none, so the row also **declines** a repository whose root `package.json` declares a script the npm commands are derived from: a `node-gyp`/`cmake-js` addon keeps its npm lines instead of being handed a `cmake` build and a `ctest` run with no tests in it. `init` writes it on the run that generates this file, so an adoption commit says which layout was detected instead of leaving a `flat` fallback indistinguishable from a deliberately chosen profile. `harness.config.json` is exempt from `--force`, so a plain `init` re-run keeps the record already in the file; `init --reset-config` is what rebuilds it. `doctor`'s `layer-profile` check reads it. |
| `detection.signal` | string | — | Identifier of the detection-table row that matched — the rows are `cli.md` §4's — or `forced` when `--preset` bypassed the table, since no row was evaluated then. Written and left standing on `detection.preset`'s terms. |
| `detection.evidence` | string | — | The repo-relative path or manifest key that row matched on, so the recorded preset can be checked against the tree. **Absent under `--preset`**: nothing was evaluated, so there is nothing to record. Written on `detection.preset`'s terms. |
| `detection.commandFamily` | string | — | Which command family derived `commands.*` on the run that wrote this file, by the ids `cli.md` §4 lists. It is recorded because the family is selected independently of the preset and cannot be read back off it, so a `flat` preset beside an `npm` family is a description of the repository rather than an inconsistency. Recorded **only where that family derived at least one of `commands.typecheck` / `commands.test`**, so it is **absent exactly where the two required commands hold placeholders** — whether no family answered, or the one that answered derived neither key (a family answers off any command set, so `composer` can supply a `depInstall` alone) — absent rather than null, on `detection.evidence`'s discipline. | `detection.review` | object: `verdict`, `rationale`, `at` | — | The verdict a layer-profile review reached, written by `/harness-analyze`'s `layers` target through `config set detection.review` and never by `init`. `verdict` is `"applied"` (a revised profile was written), `"considered-no-change"` (the target examined the profile and declined to propose one) or `"proposed-and-refused"` (a revision was proposed and the operator refused it); `rationale` is the one-line reason; `at` is the ISO `YYYY-MM-DD` date, a plain string nothing parses. Recording any of the three verdicts is what clears `doctor`'s `layer-profile` warning, so a decline leaves a trace instead of nothing. No key inside `detection` is required, so that `config set` is legal on a config written before this key existed. |
| `layers[].name` | string | — (required) | Layer identifier used in task assignment and as the routing tag a task is matched to; it is also how the layer appears in a run's dispatch labels. Lower-case letters, digits and hyphens, starting with a letter. |
| `layers[].path` | string | — (required) | Repo-relative directory the layer's source lives in. Compared against a change's repo-relative file paths to check it landed in the layer it was assigned to. At least one row must set this to `.` — see the catch-all note below the table. |
| `layers[].conventions` | string | — (required) | Repo-relative path to that layer's rules document, loaded before its implementer or reviewer starts work. |
| `commands.typecheck` | string | — (required) | Static-analysis command that must exit zero before a change counts as done. Holds the wrapper invocation `bash <scriptsDir>/typecheck.sh`, the form the permission profile allow-lists; a raw command line here is stored exactly as typed and reported by `init`, by `config set` and by `doctor`'s `command-wrappers` check. **Or exactly `<none>`** — the sentinel that answers the key with *this repository has no type check*, spelled that way and no other: unquoted, lower-case, nothing around it. It is an answer rather than an unfilled key, so the structural check grades it as answered instead of warning, no `typecheck.sh` is written for it and no permission entry is implied. It is recognised on this key only — written into any other `commands.*` key it is stored as a literal command line and run, and the check says so — and a near miss (`none`, `<None>`, `"<none>"`) is a command line too, warned about by name. `init` never writes it: it is the adopter's own answer, given after `init` with `config set commands.typecheck "<none>"` or by hand. |

A Default cell showing a value on a required key is the value `init` seeds; the key still has to be present in the finished file.

**Every path in this file is repo-relative**, including `layers[].path` and every path appearing inside a `commands.*` or `deploy.command` string; commands are executed from the repository root. Two values sit outside that rule and state their own frame in their own rows: `$schema` and `parity.referenceImplPath`.

**Why only two commands are required.** `commands.typecheck` and `commands.test` are the two the flow cannot proceed without: they are what "this change is done" means. `build`, `devServer` and `depInstall` are optional because a library package with no separate build step and nothing to serve is a legitimate adopter, and a config that could not describe it would push that adopter into inventing a no-op command. Whether the requirement on `commands.typecheck` should stand is settled in `typecheck-key-decision.md`, which ratifies option (b): the key stays required, and an explicit `none` sentinel becomes a valid answer to it. That sentinel is `<none>`, and the `commands.typecheck` row above states it — so a repository with no type check answers the required key rather than being asked to name a command it does not have.

**Phase toggles default to off.** An adopter opts into a phase deliberately rather than discovering it mid-run. In particular, **`phases.parity` is the parity module's only toggle and defaults to `false`** — the `parity` section is read only while it is true, so a project with no second implementation configures nothing and the phase never runs.

**`layers` must carry a catch-all row.** At least one `layers[]` row must have `path` set to `.` — **at least one**, never exactly one: the schema states the requirement with `contains`, which asserts one or more, and this is a `draft-07` schema, which has no `maxContains`, so an upper bound is neither expressible nor claimed; a second such row is degenerate — two candidates for the same work — rather than dangerous, and is deliberately not rejected. That row is where work matching no other layer's `path` is assigned, and such work exists on every run: the flow's own artifacts under `stateDir`, `harness.config.json`, the scripts and githooks directories, CI files. The row is therefore a requirement of the flow rather than a claim about the adopter's tree — a repository whose layers genuinely tile its source tree still needs it. Without it the orchestrator escalates a configuration gap mid-run, which is the most expensive moment to discover a one-line config mistake, and no validator can tell "the layers genuinely tile the tree" from "the row was forgotten". The cost is the single row every `init` preset already emits, and the constraint is on `path`, not on the name `general` — any layer may carry it. The schema, `config set`, `init` and `doctor` all refuse a configuration without it.

A worked configuration is at `examples/harness.config.json`; the schema itself is `schemas/harness.config.schema.json`. The commands that write and update this file — what `init` generates from it, what `doctor` re-checks in it, and what `config` will and will not let you set — are in `cli.md`.
