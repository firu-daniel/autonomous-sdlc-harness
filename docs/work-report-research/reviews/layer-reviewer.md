## Bug claims

- **Per-layer `review_<i>.md` collision in a shared `findings_folder`: CONFIRMED, with narrower scope and a different consequence than stated.**
  - **Mechanism.** `findings_folder` is the row's `Per-item findings folder`, which is per unit with no layer component (`unit_loop_core.md` → `## Substitution table`: `task_<K>/`, `item_<N>/`, `item_<K>/`). `iteration` resets to 0 on entering each layer (`unit_loop_core.md:71`, `:86`). The reviewer writes `<findings_folder>/review_{iteration}.md` (`layer-reviewer.md:55`, `:169`, `:179`). A unit with a comma-joined tag (`:57`) therefore has every layer write to `review_0.md`, `review_1.md` … in one folder. The first layer's file at each shared index is overwritten.
  - **Scope.** Only fix rows (`A1.5.3`, `A2.3`, `C`, `C2.4`, `E.3`, `UR-A`, `G.4`), only while `<per_unit_review>` is `on` (semi-autonomous plan/fix flows and the user-review flows), and never row `A` (`:55`).
  - **Consequence.** Layer 1's Should-Fix/Nice-to-Have record in `item_<N>/` is lost. That record is not part of `branch-reviewer`'s Pass 2 safety net (`branch-reviewer.md:128` reads `task_<N>/` only), so the report's safety-net framing is wrong. The more serious effect is that "the most recent `review_*.md`" (`unit_loop_core.md:73`) can hand layer 2's implementer layer 1's findings when layer 1 reached a higher index. The `iteration >= 5` escalation's "latest findings file" (`:108`) has the same ambiguity.
