# The CLI

**Who reads this:** someone about to run `init` against a repository, or debugging a repository it already wired. It answers what each command does, what it writes, what it refuses, and what its exit status means — so the decision "is this repository correctly adopted, and if not what do I change" can be made from the CLI's own output rather than from its source.

The commands are `init`, `doctor`, `config`, `daemon` and `docs`. The process assets a wired repository then runs — agents, slash commands, hooks, instructions and samples — are not in this package; they ship as the sibling plugin.

---

## 1. Global flags and exit codes

Every command takes the same seven global flags.

| Flag | Effect |
|---|---|
| `-h`, `--help` | Print usage — for the harness, or for `<command>` — and exit 0 |
| `-v`, `--version` | Print the version and exit 0 |
| `--dry-run` | Print what would be written and write nothing |
| `--force` | Overwrite an existing generated file, after a `.bak`; never `harness.config.json`, which `init` reads (`--reset-config` rebuilds it — §2), and never the two ledgers, which nothing rebuilds (§3). Three more things are kept by what the run measures rather than by name (§3 for all three): a conventions document already a skeleton whose `.bak` holds the filled one, `.claude/CLAUDE.md` when regenerating it would write the same bytes, and — inside a profile that is still replaced — every `allow` entry naming a plugin root this machine resolves |
| `--quiet` | Suppress progress narration; a command's results, warnings and failures still print |
| `--non-interactive` | Never prompt: take each prompt's documented default (§2) |
| `--cwd <path>` | Act on this directory instead of the current one |

Three exit codes, and callers branch on these rather than on the report text:

| Code | Meaning |
|---|---|
| `0` | The command did what it was asked to do — including `--help` and `--version`, and including a `doctor` run whose only findings were warnings. |
| `1` | A refusal or a failed check: an unknown command, bad usage, a `doctor` FAIL, a write the re-run contract refused. Always accompanied by a message naming the cause. |
| `2` | An unexpected internal fault — a condition the CLI did not model. Reaching it means the CLI has a bug, not that the adopting repository is misconfigured. |

Nothing in the package calls `process.exit()`: a command signals failure by throwing, and one place turns that into an exit code. Exiting outright can truncate stdout mid-write when it is piped, which is also why the acceptance gates are run without a pipe.

`--dry-run` is a faithful preview rather than a separate code path. Every outcome is computed against the real filesystem — including which keys a merge would add and which refusals would fire — and only the acts that change something are skipped, so a dry run cannot report a success a real run would not have. Those acts are the write plan's one commit boundary and, where a command has one, each mutation that sits outside a plan: `init`'s repository creation and first commit (§2), `daemon install`'s entry in the machine registry (§9), and the message `doctor --test-notification` delivers (§7).

---

## 2. `init`

Wires a repository in one deterministic pass: stack detection, then one write plan built by every generator and applied once at the end. There is no model call anywhere in it, which is what lets a second `init` over the same repository produce the same result and an adopter re-derive the recorded preset from the detection table by hand.

Every flag is optional; the two generator-flag groups are listed as `init --help` prints them.

| Flag | Effect |
|---|---|
| `--git-init` | Create a git repository when the target directory is not in one. Without it, a run outside a repository is refused — see the first bullet below. |
| `--reset-config` | Rebuild `harness.config.json` from detection and the flags, after a `.bak` (`init` otherwise reads it). The rebuild re-reads `appDir` from the file it is replacing **when that file can be read**, so the layer scopes are re-derived under the same application directory; when it cannot, the run says so and names the directory they were derived under instead — see "`--reset-config` is the start-over path" below. The rebuild also re-renders `<githooksDir>/pre-push`, after a `.bak`, where the label it carries no longer matches the set the rebuilt configuration resolves — the one kept `create-if-absent` artifact (§3) this flag replaces. |
| `--preset <name>` | Force a layer preset instead of detecting one. Validated at parse time against the five names in §4. |
| `--app-dir <dir>` | Repo-relative directory of the application, for a repository that nests it. Detection probes that tree, resolving the directory in one order: this flag, then `harness.config.json`'s `appDir`, then `.`. The bad-value arms differ by **source**, and deliberately: a value given here that resolves outside the repository is refused, while a configured one that resolves outside the repository or names no directory that is there falls back to `.` with a warning naming this flag — refusing out of the file `--reset-config` exists to rebuild would leave a repository with a bad `appDir` unrepairable by the one command documented to repair it. A config file that is **present but unreadable** takes that same fallback-and-warn arm, since it supplies no configured value either. |
| `--project-name <name>` | Short project identifier. Defaults to the repository directory name. |
| `--default-branch <branch>` | The branch work merges back into, and the one a run may never push to. Detected when absent — see "The default branch is detected" below. Like every flag in this table whose value is **written to a `harness.config.json` key**, it writes that value nowhere on a run that reads that file rather than rebuilding it, and such a run now warns **naming each dropped flag** with the two ways to apply it: `config set <key> <value>` for the one key, or this command line again with `--reset-config`, the only route that also re-derives what a value implies. The class is about where the value is written, not about everything the flag reaches: `--preset` and `--app-dir` are in it and also steer stack detection, so the warning that names either of them says so — a kept run with `--force` re-renders the wrapper bodies from that detection (§5), while this file stays the one that was read. |
| `--state-dir <dir>` | Repo-relative run-artifact directory. A dot-named value is refused — see §3. |
| `--qa` | Turn the interactive test phase on. |
| `--qa-driver <driver>` | Which interactive-test driver the QA phase runs (with `--qa`): `web-playwright`, `mobile-maestro` or `mobile-mcp`. Validated at parse time; asked for on a terminal when absent — see "The interactive-test driver is asked for" below. |
| `--docs` | Turn the documentation phase on. |
| `--docs-root <dir>` | Documentation root the docs phase keeps current (with `--docs`). |
| `--docs-retrieval` | Turn docs retrieval on: a local search tool over the docs and conventions (with `--docs`), written as `docs.retrieval: true`. Without `--docs` it is refused while the flags are parsed, rather than warned about as `--qa-driver` is: `init: --docs-retrieval needs --docs: …`. Asked for on a terminal when absent — see "The interaction rule" below. |
| `--parity` | Turn the reference-parity phase on. |
| `--reference-impl <path>` | Checkout of the reference implementation to compare against (with `--parity`). |
| `--reference-toolchain-path <abs>` | Absolute directory of the reference implementation's own toolchain (with `--parity`). See §7. |
| `--marketplace <owner>/<repo>` | Marketplace repository written into the committed project settings. |
| `--analyze` | Accept the offer to run `/harness-analyze` in this repository's first session. The documented default; asked for on a terminal — see "The analysis is offered, and the offer defaults to yes" below. |
| `--no-analyze` | Decline that offer. Given together with `--analyze` it is refused while the flags are parsed, rather than one silently winning. |
| `--notifications` | Set up push notifications for unattended runs. Off by default; asked for on a terminal — see "Notifications are opt-in" below. |
| `--push-url <url>` | Endpoint those notifications are posted to (with `--notifications`). Any endpoint that accepts a POST. Without it nothing is written — see below for why that is deliberate. |

**Three preconditions, all settled before a single generator runs**, so a plan that is never built cannot be half-applied. Two are checks the flags alone answer; the third is settled by an answer — a flag, a prompt, or the non-interactive default. They are taken in that order, and the order is load-bearing: the git gate's accept path *creates a repository*, so every refusal that needs nothing but the parsed flags is raised ahead of it and a refused run leaves the directory as it found it (`--qa-driver`'s check sits one step earlier still, in the flag parser, for the same reason):

- **`--state-dir` names, or reaches through, a dot-directory.** §3. Answerable from the flag, so it is raised before the git gate — as is `--preset`'s check against the closed set of preset names (§4).
- **Not inside a git repository, and the run was not told to create one.** The root every write is confined to cannot be resolved, and the worktree-based flow `init` wires cannot prepare a checkout without one, so git is a hard gate rather than something the command works around. git is the only version-control system supported — no SVN, no Mercurial — and a `jj` repository adopts either way, colocated or not (§7's `jj-repository` bullet). `--git-init` creates the repository and the run continues against it. On a terminal without the flag, `init` asks first — nothing is ever created silently. A run that cannot be asked refuses, which is the unchanged default (see "The interaction rule" below). Two edges: under `--dry-run` no repository is created — the run says it would create one and previews the rest of the plan against the directory — and a `git` that is not on `PATH` is reported rather than offered, because the accept path would fail for the same reason.
- **The resolved root is the harness's own repository.** Recognised by a marketplace manifest at the root *and* a `cli/package.json` naming this package — either signal alone is ordinary. Wiring the harness itself would generate a configuration, a run-artifact tree and a permission profile into the tree that ships them. Last of the three because it is the one check that needs the root the gate above resolved.

Those three are the preconditions, not the whole of what `init` can refuse: a `harness.config.json` that is present but unusable, a wrapper whose configured command line would run the wrapper itself, and every safety rail the write engine applies to the assembled plan (§3) each refuse with exit 1 and write nothing. What is *not* a refusal is anything the adopter merely ought to know — an unresolved command line, a conventions stub two layers share, an omitted marketplace entry. Those are warnings, collected and printed after the action log rather than as they arise, because a warning scrolled off by a hundred action lines is a warning nobody read.

**When the repository being wired has no commit yet, `init` makes the first one.** A repository with an unborn `HEAD` — one `git init` has just made, and equally one that was already there and has never been committed into — fails `git worktree add`, so without this the adoption would be correctly wired and still one non-obvious step short of a flow that can prepare a checkout, with only `doctor` to say so and no guarantee `doctor` was run. What decides it is the repository's **state**, not who created it: a repository that **has** commits is never committed into, whatever made it and whatever this run did. The commit is made **after** the write plan has been applied, so the managed `.gitignore` block is already on disk and its `git add -A` stages this directory's **whole working tree** — the generated wiring and whatever was already here — and none of the machine-local run-control artifacts or `*.env` files that block excludes. It is skipped under `--dry-run`, along with the repository creation itself. If git declines, the run keeps everything it wired, warns, and still exits 0: the usual cause is a machine with no commit identity, which `init` deliberately does not set for you, so the warning names `git config user.email`, `git config user.name` and then `git add -A && git commit` as the steps that finish the adoption.

Two consequences of that follow, and the run states both rather than leaving them to be inferred. The commit's `git add -A` stages the **whole working tree** — what `init` generated and whatever was already in the directory, in a repository `init` created as much as in one it adopted — one commit, one message, with the managed `.gitignore` block deciding what is left out; a repository `--git-init` created is not an exception, since detection read that directory's manifests before the plan was built. The action log names which of the two the run was in, because *who* left the repository without a commit is what differs between them, not what got staged. And `--git-init` against a directory that is **already** inside a repository creates nothing and says which of the two states it found: a repository with history, so nothing is committed into it and this run only wires it; or a repository with no commit, so this run makes the first one here from what is in the working tree. Under `--dry-run` **both** states are phrased in the conditional — a run that writes and commits nothing says what a real run *would* wire and *would* commit, never what this one did. The "nothing was created" half is printed only when the flag was actually given: a run that never asked for a repository has nothing to report about it. The first-commit half is not gated that way — a `--dry-run` in a repository with no commit previews that commit whether or not `--git-init` was passed, for the same reason the commit itself no longer consults the flag: what decides it is the repository's state, and a preview that left it out would be silent about the one mutation outside the plan a real run makes there.

**`--reset-config` is the start-over path**, and the only thing that rebuilds `harness.config.json`. It re-derives the file from stack detection plus this command line, after the write engine has copied the one that is there to a `.bak` sibling. It **re-derives rather than restores**, deliberately: detection is deterministic and the command line is the other input, so nothing new has to be persisted for the rebuild to be exact — while a `.bak` is not a promise anyone can keep, since there is none at all on a first `init` and `config set` writes one on every `set`, so the newest `.bak` may be a single key old rather than the file as it stood before `init` ran. One value is not re-derived from the flags alone, and the run says which rung supplied it: **`appDir` is re-read from the file being rebuilt** before detection runs, so every layer scope is re-derived under the same application directory rather than under the root, and `--app-dir` overrides it (the flag row above states the whole order). That re-read is what the note claims only when it happened. A file that is present but **cannot be parsed** — the file `--reset-config` is most often reached for — supplies no `appDir` at all: detection then probes the repository root, the run **warns** naming the parse problem and `--app-dir`, and the rebuild note names the directory the layer scopes were actually derived under rather than asserting an application directory survived. The cost is stated plainly for everything else: a value that lived only in the edited file — a phase toggle turned on by hand, an added `protectedBranches` entry, a corrected command line — is now whatever detection and the flags say, so anything you meant to keep has to be given as a flag on this run or set again afterwards with `config set`. It composes with `--force` rather than implying it: `--reset-config` alone rebuilds the configuration and leaves every kept `create-if-absent` artifact (§3) exactly as it stands, so `init --reset-config --force` is the full start-over and a bare `--reset-config` deliberately is not.

**One artifact is the exception to that last sentence, and only where this rebuild is what made it wrong.** `<githooksDir>/pre-push` carries the protected set substituted into its `case` label at write time, so a rebuild that moves `defaultBranch` or `protectedBranches` leaves a guard enforcing the branch set it was written with — and the guard is the file git runs, so the state is not cosmetic: a branch in one set and not the other is either pushed to unguarded or refused for no configured reason, and the two can be inverted entirely. It is an exception because the remedy this document publishes was producing it: `init --reset-config --default-branch <branch>` is what corrects a wrong integration line, and it stranded the guard on the old one. So a `--reset-config` run re-renders that hook, after a `.bak`, when — and only when — the label on disk no longer matches the set the rebuilt configuration resolves; a label that matches and a hook whose label this CLI cannot read are both left byte-identical, the second with a warning naming `doctor`'s `pre-push-guard` check (§7). The asymmetry with `--force` is deliberate: `--force` re-renders the hook unconditionally, this run re-renders only a hook its own rebuild falsified. A hand edit in a replaced hook is then in the `.bak` rather than in the guard git runs, and the run says so.

**The default branch is detected, never assumed.** Without `--default-branch`, `init` takes `defaultBranch` — and with it `protectedBranches` — from the first of these that answers: `origin/HEAD`, the checked-out branch, git's configured `init.defaultBranch`, and finally the schema default. `--default-branch` overrides the lot. The second rung answers for a repository that has **no commit yet** as well — `HEAD` names a branch from the moment `git init` runs, only the commit is missing — so such a repository, whether `--git-init` created it or it was already there, is wired to the branch its own first commit lands on rather than to a name guessed further down the ladder. A repository whose integration line is `master`, `develop` or `trunk` is therefore wired to that name rather than to a conventional one, because an assumed `main` is silent in every direction it is wrong — it is a valid config, so nothing refuses it, while every branch diff, every review's diff base and the pre-push guard are all taken from it. Each run says in its notes which rung answered — the flag included, which reports itself as the source it is. Every rung that is a **guess** rather than a statement by the repository also warns about the name it produced, and that is **three** of them: the checked-out branch, `init.defaultBranch` and the schema default, which used to say nothing at all and is the guess that is wrong most often. What the warning tests is **resolution first**: a name that names neither a local branch nor an `origin/` remote-tracking ref here is wrong whatever it is called, because a review's diff base and the protected-branch guards then both read a ref that is not there — the diff is against a ref git cannot find, and the guard matches no branch and so stops nothing. Where that arm does not fire, what is left is the weaker signal, reported only where it is present: the name is neither `main` nor `master`, which is what `init` run from a feature branch looks like. The resolution arm is gated on the repository having a commit, since in one that has none nothing resolves at all and every `--git-init` adoption would draw it.

The second rung has **three** answers rather than two, and the rungs below it name which of them they met: a `HEAD` that names a branch, a **detached** `HEAD`, and a repository with no branch to name. The distinction is not cosmetic — on a colocated `jj` repository a detached `HEAD` is the ordinary state after every `jj new`, so it is the wording every such adoption run lands on, and reporting it as *no checked-out branch answered* describes a repository with nothing to offer instead. Every one of those warnings closes the same way, and the remedy it names is `config set defaultBranch <branch>` or `init --reset-config --default-branch <branch>`, and deliberately **never a bare `--default-branch`**: the warnings are published on the runs where this configuration landed, so by the time one is read the repository has a `harness.config.json` and the next `init` reads that file and drops the flag (the flag row above). `doctor`'s `default-branch` check (§7) is the standing half: it re-reads the configured name and reports whether the repository still resolves it, with `jj-repository` beside it for the rung a colocated repository loses.

**The interactive-test driver is asked for, not assumed.** With `--qa`, `init` puts one question — which driver the phase should run — and **back-references** the detection line printed above it rather than naming that preset a second time, because detection is file existence and manifest keys only (§4), has no mobile signal, and so says nothing about how an application is actually reached. `--qa-driver` answers it without being asked and is validated while the flags are parsed, so an unknown value is refused before a repository is created or a generator runs. A run that cannot be asked writes the documented default `web-playwright` and says in its notes that it defaulted, which is exactly what earlier releases wrote — the interaction rule below, applied to this decision. The key it sets is `qa.driver` (`docs/config.md` §4's `<qa_driver>` token, §5 for what the key means), and `--qa-driver` **without** `--qa` writes nothing and warns: no `qa` section exists while the phase is off, so the value would have nowhere to go. The two mobile values are **declared but not implemented in this release** — their `qa-tester` variants ship with built-ins-only tool allowlists — so choosing one configures the project correctly and makes the phase report a blocker, instead of driving a browser at an application that is not there. That is now said where a value is offered or rejected rather than only here: both mobile values reach the question — and the `--qa-driver` refusal's list of the legal ones — marked `[not implemented]`, and a run that **writes** one warns on whichever rung answered, the flag or the answer — a re-run that keeps the config already on disk discards the value it resolved, and warns about neither, since the sentence is a claim about the repository's driver rather than about a value nothing kept. There is no third rung to warn on: only the generation path resolves the key, so a mobile driver an existing `harness.config.json` already carries is never warned about by `init`, which reads that file and never rewrites it (§3). Its standing reporter is `doctor`'s `browser-wiring` check (§7), which **passes** such a repository on every run, naming the driver and its declared-not-implemented status.

**The analysis is offered, and the offer defaults to yes.** The fourth of the five questions `init` puts — after the repository, the interactive-test driver and docs retrieval, before notifications — is whether the next session in this repository is told to run `/harness-analyze`, and what the answer changes is a **wording, not an action**: `init` runs nothing, gains no model call and starts no session. Accepted, the setup-pending banner in the generated `.claude/CLAUDE.md` says running the command is that session's first action; declined, the same banner says the conventions documents are yours to write by hand and the command is still there if you change your mind. Both wordings end by stating how the block is disposed of — the command removes it, or it is deleted by hand once those sections are written — so declining does not leave a permanent "setup is not finished" block in the one file every session loads. The closing report keys on **what the write engine actually did** to that file rather than on the answer alone, so it claims a record only where one was made: on an unforced re-run over a file that is already there nothing is written into it, and the report says so and names `doctor` (§7) as the standing reader of what is still unfilled. The documented default is **yes**, and that is the interaction rule's continuity clause rather than an exception to it — every earlier release ended by telling every adopter to run this command, so a run that answers nothing says what it has always said and *declining* is what is new. The question is **not put at all when nothing is left to fill**: an unforced run whose conventions documents are all written and whose `.claude/CLAUDE.md` is there with no open banner says so in its notes and moves on, while `--force` regenerates both from the template and so asks again. No repository size, no duration estimate and no other condition ever declines on the adopter's behalf. What the command itself writes, refuses to write and does when it cannot tell is `docs/analyze.md`.

**Notifications are opt-in, and default to nothing pushed.** An unattended run is a background process nobody is watching, so its completed, parked and failed events reach an operator only through the notifier — which until now nobody was ever *asked* about, leaving a correctly wired repository delivering a desktop banner where one is available and nothing else. `init` asks on a terminal; `--notifications` answers without being asked; a run that cannot be asked takes the default and stays exactly as every earlier release behaved. Saying yes writes the machine-local settings file **only when an endpoint was also given** (`--push-url`, or the terminal's answer to the same question). With the opt-in and no endpoint, nothing is written and the run prints the guided setup instead — the file's path, the two key names and a worked example. That is not a shortcut: `docs/watcher.md` §6's precedence is that the machine-local file is read *first* and the repository's configured `pushEnvPath` is then not read at all, so an empty machine-local file would shadow a repository-side file that already has values and turn the opt-in into a silent opt-out. The endpoint itself is never printed back — the action log names the path, the note names the keys. The file is machine-local rather than committed, which is why it is one of the few paths this CLI writes outside the repository (§3), it is created `0600` inside a `0700` directory, and it is create-if-absent like everything else `init` writes: a later run leaves an edited one alone.

**Every command key in effect is named, with the line behind it, before the file log.** The `commands` step walks a fixed order — `typecheck`, `test`, `devServer`, `build`, `depInstall`, then `deploy` — which is wider than the wrapper set on purpose, since `build` and `depInstall` are deliberately never wrapped (§5) and are still command lines this run put into effect. A **wrapped** key prints the invocation *and* the raw line inside the wrapper, because the value `harness.config.json` holds is the wrapper and the line that actually runs is inside it, so reading the configuration alone answers half the question; a key still holding the **placeholder** prints as such — no wrapper was written for it and nothing runs until it is set — rather than being omitted, since an omitted key is indistinguishable from a key nobody looked at; a key answered with the `<none>` sentinel prints that **this repository states it has no such command**, that no wrapper was written for it and that **this run** allow-listed none — said of the run and not of the repository's state, because a wrapper an earlier run wrote is still on disk (§5), and where it is the row names that file and says what clears the permission entries naming it — three things the wrapped and raw rows would each say wrongly of it, and a row reachable only on a re-run over a config an adopter has already answered, since `init` never writes the sentinel (§4); and a key set to a **raw line** says where that line stands against the wrapper, on §3's `create-if-absent` condition: it reaches the wrapper only where that file was not already on disk, and there the row names the wrapper as the form the permission profile allow-lists, while over a wrapper already there the row leads with the line that file already carries and names `--force` as what replaces it — the same rule this paragraph states for wrapped keys. The block prints **identically under `--dry-run`**, which is the whole point of it: a preview is where a wrong command line is cheapest to see, and the only thing a dry run phrases differently is the write provenance, in the conditional like everything else it says. What a row reports is **the line that will run, which is not always the line this run resolved**: wrappers are `create-if-absent` (§3), so over a wrapper already on disk the body resolved here is discarded and the kept file keeps running its own line — the row therefore leads with the line that file **already carries**, names the line this run resolved beside it where the two differ, and says that `--force` is what replaces the file with it. That is the whole of a row's provenance vocabulary, one per row and never mixed: the line the file already carries, the line **this run writes**, and the line **a real run would write** under `--dry-run`. A wrapper on disk whose body this command cannot read is reported as exactly that, because *what that file runs cannot be said here* is not a licence to guess.

**The source directories the profile in effect does not cover are named by this run, not only by `doctor`.** A gap in a *detected* profile used to appear in `doctor` alone, so an adopter who read `init` and never ran `doctor` learned nothing about it. The set is the one `doctor`'s `layer-drift` check reports (§7) and the remedies are word for word the same, because both surfaces render them from one composer (`cli/src/core/layerGapRemedy.ts`) rather than each spelling its own — so the gap is not learned only by running the second command, and the two commands cannot word one repository's next step two ways. It is a **note**, not a warning: a freshly detected repository routing a directory to the catch-all is an ordinary adoption outcome, and this command's warnings are reserved for what needs fixing. It is derived from the configuration **in effect**, so a re-run that kept the adopter's own file reports it too — and that is the population which can carry a recorded layer-profile review, so where the config holds a verdict the note names it and its date and takes the same `config set layers`-first remedy §7's `layer-drift` bullet describes. Nothing is said where the profile carries no row scoped below the repository root: every directory would qualify there, and that state is `layer-profile`'s to report once, as itself (§7).

**The run ends with four numbered steps, in the order they are performed.** The first is the plugin wiring this run left, and it is first because `/harness-analyze` is a command of this package's plugin and exists only in a session that resolves it: `init` merges the enablement key into `.claude/settings.json` on every run, while the `extraKnownMarketplaces` entry beside it — the half that tells a clone where the plugin comes from — is written only when the owner slug resolves, so where it was not the step says so and names both routes out of it, `claude plugin marketplace add <owner>/<repo>` for this machine and `--marketplace <owner>/<repo>` for the committed file. The step states what **this run wrote** rather than probing the machine for what is installed on it, which is the determinism the interaction rule below closes on; under `--dry-run` it is in the conditional, like everything else the run says.

The second step is the analyze command, in the vocabulary that command settles: `/harness-analyze` with no argument runs every target, and `/harness-analyze <target>` takes **this repository's configured layer names** plus the three reserved targets `project`, `conventions` and `layers` — computed from `layers[]` at invocation time, so a static command file and a per-adopter layer list cannot drift. It fills the conventions documents from the repository's real code, and it **proposes** a layer-profile revision rather than writing one: the revision reaches `harness.config.json` only through `autonomous-sdlc-harness config set layers` (§8), which validates the result and takes the `.bak` — and that target then records what it concluded through `config set detection.review`, the second and last key it reaches the file through, whichever way the proposal went. `init` detects a layout from file existence alone and writes conventions *skeletons*; turning those into a project's actual rules is deliberately not its job, and a freshly wired repository is not a finished one. On the accepted arm a **pasteable** invocation is printed on its own line under that step — `claude "/autonomous-sdlc-harness:harness-analyze"`, run from the repository root — rather than a command to be typed in a session opened first; `init` still starts nothing, and it is a string a person pastes. It is spelled with the plugin prefix where the step above it is not, and the introducing sentence gives the reason: **the bare name is what a session's picker takes**, while a first message meets no picker and is matched exactly, so the bare form fails there with `Unknown command`. That the prefixed form *succeeds* as a first message is the part not established: the only measurement in this tree is headless and negative on both spellings (`docs/development.md` §6), and the interactive form this line prints waits on the hand-run gate — if that comes back negative the line is dropped rather than respelled (`docs/analyze.md` §9). The printed sentence says so on **both** arms rather than only in these documents: it names the outcome as intended, not as fact, and points at the typed route above it as the measured one. It is withheld wherever it would contradict the report around it: on the declined arm, on a re-run with nothing left to fill, and under `--dry-run`. Where the marketplace slug did not resolve it is printed but **qualified** rather than withheld — the sentence introducing it opens "Once the plugin resolves — step 1 names both routes —" — because withholding it would make it dead on any run whose manifest names no resolvable owner, while handing the line over without that precondition would contradict the first step's own statement that the session resolves the plugin only once one of its two routes is taken. The third step is reading `harness.config.json` and correcting anything the run got wrong, and the fourth is `doctor` (§7) — which, **while `phases.qa` is on**, also names the two steps `doctor` reports that no run can perform for the adopter, each with what a missing one costs: `daemon install`, without which nothing polls the inbox, and the hand-added `permissions.allow` entries the plugin's install root needs, without which an unattended run parks at the first helper script with no error (`docs/watcher.md` §6). That step carries a **second clause on a different gate**, printed where this run wrote the browser wiring rather than wherever the phase is on: the two MCP servers `.mcp.json` declares are launched with `npx -y`, so each pinned package is fetched from the registry on first use rather than installed now, and `doctor --check-registry` (§7) is what answers before the first interactive-test dispatch whether it can be. Both are clauses on the fourth step rather than a fifth step, and each carries its own gate because what it names belongs to that gate alone: the `permissions.allow` entries to the phase's helpers, the pins to a repository that has an `.mcp.json` at all — a mobile-driver run has the phase on and declares no browser server.

### The interaction rule

Where `init` puts a question to whoever is running it, the question obeys the same three-part contract — and no decision anywhere in the CLI may be askable without all three:

- **A flag supplies the answer.** The flag is the interface; the prompt is a convenience on top of it, and every such flag appears in the table above.
- **A documented default answers when the flag is absent.** That default is always *exactly the behaviour this release already had* before the decision became askable, so a run that never answers is the run an earlier release would have made.
- **The prompt appears only on a terminal** — both stdin and stdout — and only when the flag was not given.

The questions this contract governs, in the order `init` puts them, each with its flag and its default:

1. **Create a git repository** — `--git-init`; default: refuse (§2's second precondition).
2. **The interactive-test driver** — `--qa-driver`; default `web-playwright`. Asked only with the QA phase on.
3. **Docs retrieval** — `--docs-retrieval`; default **off**. Asked only while the docs phase is on in a configuration this run **generates** — never on a run that reads an existing `harness.config.json` — and a run that could not ask notes `docs retrieval stays off: this run could not ask`. The question states the cost: setup installs a local runtime and downloads two small models into a cache every checkout on the machine shares (see "Generator order" below).
4. **Run `/harness-analyze` in the first session** — `--analyze` / `--no-analyze`; default yes.
5. **Push notifications** — `--notifications`, with `--push-url` for the endpoint; default off.

To turn retrieval on after adoption, set the key and then re-run with `--force`, because the permission profile is `create-if-absent` and a plain re-run keeps the one that lacks the retrieval entries (§6):

```bash
npx autonomous-sdlc-harness config set docs.retrieval true
npx autonomous-sdlc-harness init --force
```

**A run that cannot be prompted never blocks.** With no terminal it takes the default and prints one line naming the flag that chooses otherwise, so the choice is discoverable from the run that skipped it. `--non-interactive` forces that same default-taking path on a terminal, for a CI runner that allocates one; `--quiet` takes it too, since a prompt under `--quiet` would block on a question that was never printed.

This is what keeps **`init` deterministic**. With no terminal, its output is a function of its flags and the state of the repository alone — no model call, no hidden input — so a second `init` over the same repository produces the same result, and the recorded preset can be re-derived from the detection table by hand.

### Generator order, and why it is load-bearing

The configuration is written first, and every later generator reads **the configuration in effect** — freshly built on a first run and under `--reset-config`, and the file the adopter already has on every other run, `--force` included. That is the only way a second `init` writes the state tree, the profile and the hook against the values the adopter edited rather than the ones detection would have chosen again.

The wrapper scripts come next, before the permission profile, because the profile allow-lists their literal paths: a profile written without them would allow-list files that do not exist, leaving the configured verification commands matching neither `allow` nor `deny` — a stall, not a refusal (§6). The state tree, the conventions stubs, the profile, the project settings and the repository-root files follow, and the git hook is last, with the repository's hooks path pointed at it only **after** the plan has been applied and the hook it enables therefore exists.

**Docs retrieval setup is a post-plan step**, run only where the configuration in effect has `phases.docs` and `docs.retrieval` both true. It installs this package at `init`'s own version, with the optional retrieval peers, into a machine-wide runtime with `npm install --prefix`, then downloads the two models with the package's `docs fetch-models` verb. Both land under `${XDG_CACHE_HOME:-$HOME/.cache}/autonomous-sdlc-harness/retrieval/` — `runtime/` and `models/` — shared by every checkout on the machine. Each step is skipped where it is already satisfied, and under `--dry-run` each is a note rather than an action. It follows the plan because it writes nothing into the repository and a cold install takes minutes, which must not hold back the plan's own report; it precedes the adoption commit because a failure is a **warning** and must not stop that commit — the wiring the plan wrote stays valid, and `doctor` (§7) reports what is missing until a re-run completes it. To complete a failed setup, re-run `init`:

```bash
npx autonomous-sdlc-harness init
```

## 3. The re-run contract

A second `init` on a wired repository must not clobber an adopter's edited files. That is a property of the write engine rather than of each generator's discipline: every write is enqueued as a request carrying one of four policies, and the whole plan is checked before any of it is committed.

| Artifact | Policy | Why |
|---|---|---|
| `harness.config.json` | create-if-absent | The adopter edits it, and everything else is generated from it — so `init` reads it whenever it is there, and `--force` does not apply to it. `--reset-config` (§2) is the one thing that rebuilds it, after a `.bak` — and the rebuild reads the outgoing file's own `appDir` first, so the tree detection probes is the one this repository already declared. |
| `<scriptsDir>/` | ensure-dir | The directory the wrappers and the profile both name. |
| `<scriptsDir>/typecheck.sh`, `test.sh`, `start-dev-server.sh`, `deploy.sh` | create-if-absent | The raw command line in each is the adopter's to correct, and a re-run keeps the corrected copy. |
| `<scriptsDir>/lib/` | ensure-dir | The subdirectory the outer-loop set's shared run-time library sits in. |
| The outer-loop scripts and `<scriptsDir>/lib/harness-run-lib.sh` | create-if-absent | Copied verbatim rather than rendered, so a re-run on an untouched repository is a no-op and an adopter who patched one keeps the patch. The corollary is deliberate: a fix shipped in the package reaches an already-wired repository only through `--force`, and the `.bak` is what makes that safe. |
| `<stateDir>/` and every artifact directory the configured phases call for | ensure-dir | Creating what is missing is the whole operation; nothing is emptied. |
| `<stateDir>/README.md` and the per-directory READMEs | create-if-absent | An adopter may have rewritten a contract sentence to match how their flow actually uses the directory; a re-run does not revert it. |
| The lessons and improvement-suggestions ledgers | create-if-absent, **not upgraded by `--force`** | Ledgers accumulate and nothing can re-derive one; the engine's `.bak` is single-generation, so `--force` may not touch them. |
| `.claude/CLAUDE.md` | create-if-absent | The analyze command fills it; a re-run must not undo that. It carries neither marker below, so its setup state is the `<!-- harness:setup-pending -->` banner the generated file carries, read by `doctor`'s `setup-analysis` check (§7) and deleted by the command as its last act. `--force` regenerates it, **except when its bytes already are the text that run renders**: that write would put nothing in the `.bak` and would destroy what an earlier forced pass left in the single one already there, so the run keeps the file and its closing sentence says which of the two happened. |
| `.claude/harness-task-offer.md` | create-if-absent | The change-request dialogue the always-loaded file's `## Where a change request runs` fence points at by name. It is planned on **every** run, gated on no phase, so a repository the fence reaches never lacks it; where it is already there the run keeps it. Nothing fills it, so after the first run the adopter's copy is the only one; `--force` re-renders it after a `.bak`. |
| The conventions stubs | create-if-absent | The analyze command fills them; a re-run must not undo that. Whether one has been filled is **checkable rather than merely intended**: a stub still carrying its `<!-- harness:unfilled -->` marker **and** its `**What belongs here**` guidance block is one nobody has filled — by the command or by hand — and `init`, `doctor` (§7) and the command all apply that one two-part test, so a stub written by hand is never treated as an untouched skeleton. `--force` regenerates one, **except where that test says the document on disk is already a skeleton and its `.bak` is not** — the second forced run over an already-skeletonised corpus, where the write would spend the single `.bak` generation on the only surviving copy of the analysis; the run keeps the document and names that `.bak` as the reason. |
| The push-notification and test-account `*.env.example` files | create-if-absent | Copied and completed by the adopter. |
| `.claude/qa_test_scenarios.md` (written only when the QA phase is on) | create-if-absent | A skeleton the adopter fills with the project's own test-scenario rules; after the first run that copy is the only one. |
| The permission profile `.claude/settings.autonomous.json` | create-if-absent | Hand-tuned after generation; an overwrite silently drops the entries added to close a stall. So the one run that does replace it re-reads it first and **carries forward every `allow` entry naming a plugin root this machine resolves** — the lines `doctor`'s `plugin-permissions` check (§7) dictates and no generator can produce, a root being machine-local — reporting what it carried and warning about what it left behind: an entry naming an absolute directory no resolved root answers for, and one carrying a character the permission guard would never match. Where **no** plugin root resolves at all — `init` run before the plugin is enabled, a shell resolving another config directory — it carries every absolute entry outside the checkout forward **unverified** and says so, rather than dropping them: a run that graded nothing revokes nothing, and both left-behind warnings name a cause that run did not observe. |
| `.claude/settings.json` | merge-json (missing keys only) | Shared with the adopter's own project settings. |
| `.mcp.json` (written when either half applies, each adding its own entries: the browser servers when the QA phase is on **and** its `qa.driver` is `web-playwright`, and `harness-docs` when `phases.docs` **and** `docs.retrieval` are both true — so a mobile-driver repository with retrieval on gets a file holding `harness-docs` alone, and one with neither gets no file — §6) | merge-json (missing keys only) | Shared with whatever other servers the repository declares. |
| The permission profile's retrieval half (`settings.autonomous.retrieval.json`, merged into `.claude/settings.autonomous.json` when `phases.docs` and `docs.retrieval` are both true — §6) | create-if-absent, as the profile it is part of; `--force` regenerates it after a `.bak` | Retrieval turned on after adoption reaches a profile already on disk only through `--force` — the fenced block under "The interaction rule" (§2). |
| `.gitattributes` | create-if-absent | Adopter-owned once written. |
| `.gitignore` | merge-lines (a managed block, lines not already present) | Every repository already has one. |
| `.gitignore`'s `<stateDir>/docs_index/` line (written when `phases.docs` and `docs.retrieval` are both true) | merge-lines, in the same managed block | The per-checkout search index is a derived cache and is never committed. |
| `<githooksDir>/` | ensure-dir | — |
| `<githooksDir>/pre-push` | create-if-absent | The adopter may have edited the guard. The hook alone is also replaced, after a `.bak`, by the one run that rebuilt the config it is rendered from (`init --reset-config`, §2) — and only where its rendered `case` label no longer matches the set that config resolves, never where the label cannot be read. |

Four things follow from that table and are worth stating on their own:

- **`--force` upgrades `create-if-absent` only**, to overwrite-after-backup — with three files excepted by name. `harness.config.json` is one: `init` reads it whenever it is there and only `--reset-config` (§2) rebuilds it, so `--force` leaves the adopter's edited values in effect for every artifact it does regenerate. The **two ledgers** are the other two, and for a related reason — no command rebuilds a ledger, because an accumulating record has no derivable content to rebuild it from, so a forced overwrite would be pure loss. It never applies to a merge policy — those are already non-destructive — and it never deletes a directory. The `.bak` sibling is overwritten rather than chained, so a second `--force` leaves the same two files as the first; that single generation is the reason the exception has to be the policy for a ledger rather than a backup being enough. The same property reaches three further artifacts, and there it makes them **kept conditionally rather than exempted by name**: the run measures the tree and decides per file, because regenerating a skeleton is a legitimate thing to want and a blanket exemption would forbid it. A **conventions document** is kept when the two-part filled test says the document on disk is already a skeleton *and* its `.bak` is not — the second forced run, where the write would spend that one generation on the copy holding the analysis. **`.claude/CLAUDE.md`** carries neither marker, so byte-identity with the text the run renders is the exact statement of the same loss for it: the `.bak` that write would produce receives nothing the template does not already carry, and the one there is destroyed to make room. A **profile entry** is kept when it names a plugin root this machine resolves — the file itself is still replaced, and the discriminator is entry-level, because that class is the one the generator knowingly cannot produce and the one a second forced run would leave no copy of anywhere. On the other side of each test the forced behaviour is what it always was — a filled document is still put back to a skeleton after a `.bak`, and everything the generator does produce is still regenerated. One route replaces an artifact with **no `--force` at all**, through that same per-request mechanism read the other way: a `--reset-config` run answers the overwrite question for `<githooksDir>/pre-push` itself and replaces it after a `.bak`, where and only where the label on disk no longer matches the set the rebuilt configuration resolves (§2). So the whole of what the table permits is: `--force` upgrades every `create-if-absent` row but the three excepted by name; three artifacts are kept against it by what the run measures; and one is replaced without it, by the run that made it wrong.
- **A merge adds only what is absent, and adds it back where it belongs.** An existing key or an ignore line already present is left exactly as it is, and the action log names what was added. A line that is *not* present is spliced into the managed block **at its position in the generated payload** — after the nearest line of that payload still there — rather than at the end of the block, because position is content in an ignore file: git resolves a path by the last pattern that matches it, so a rule deleted by hand and restored below its own `!` negation would re-hide the file that negation exists for, silently, in a run reporting one added line. A rule the adopter wrote beneath the block stays where they put it, blank separator or none. A merge also **removes nothing**, so an ignore rule an earlier release wrote and this one replaced survives every re-run and can only be deleted by hand — `doctor`'s `ignore-rules` check (§7) is what reports the one case where that silently keeps a committed file untracked.
- **Nothing is written outside the repository** except the machine-local artifacts named individually below, each of which lives outside it by that artifact's own definition rather than by this CLI's choice, and each of which is written by a request that says so explicitly. They are: the **daemon unit file**, because a user service manager reads its units from the account's home directory (§9); the **push-notification settings file** `init --notifications` writes, because a push credential belongs to a person and a machine rather than to a checkout (§2, `docs/watcher.md` §6); and the **repository registry** `repos.json` that `daemon install` records the repository in, because an index of which checkouts on this machine have a daemon installed is by definition not any one of their property (§9, `docs/watcher.md` §7). The registry is the one of the three that is not written through the engine this section describes — it is a machine-scoped index the CLI owns end to end and rewrites in place, with none of the create-if-absent, merge or backup behaviour an adopter's own file needs; `cli/src/machine/registry.ts`'s header states why. The docs-retrieval **runtime directory and model cache** are machine state outside the write engine altogether: `npm` and the model library write them during the setup step (§2, "Generator order"), which skips each where it is already satisfied, so no policy in the table applies to them. The per-checkout search index under `<stateDir>/docs_index/` is a derived, uncommitted cache that no `init` run writes — only its ignore line is `init`'s.
- **Nothing is written through a symlink**, and no two requests may aim at one path — both are refused against the whole plan before anything lands.

## 4. Stack detection

Detection is pure file-existence and top-level manifest-key inspection, evaluated as an **ordered, first-match-wins table**. No content heuristics, no scoring, no model call: `init` has to be reproducible, and a judgement call cannot offer that. The table is exported as data so this section and the code cannot describe different rows. That rule is about **the table**, and it is stated that way because one probe below is not on it: the dart family reads its `pubspec.yaml` for an `sdk: flutter` line to decide **which tool an already-selected preset's lines name**, never which row matches or which preset is selected — a read inside a family, argued at that family's paragraph.

Order is the decision — a workspace repository is a monorepo even when one of its packages is layered, and a layered tree is layered even when it also has a routes directory.

| # | Signal id | Preset | Matches when |
|---|---|---|---|
| 1 | `monorepo:workspaces-key` | `monorepo` | The repository root `package.json` declares a top-level `workspaces` key |
| 2 | `monorepo:workspace-manifest` | `monorepo` | A workspace-tool manifest sits at the repository root: `pnpm-workspace.yaml`, `lerna.json`, `turbo.json`, `nx.json` |
| 3 | `layered-clean-arch:layer-directories` | `layered-clean-arch` | At least **two** of `data/`, `domain/`, `presentation/` exist under the application directory or its `src/`, `app/`, `lib/`, `internal/` or `pkg/` |
| 4 | `python-package:packaging-manifest` | `python-package` | A Python packaging manifest: `pyproject.toml`, `setup.py`, `setup.cfg` |
| 5 | `api-service:route-directory` | `api-service` | A `routes/`, `controllers/`, `handlers/` or `api/` directory under the application directory or its `src/`, `app/`, `lib/`, `internal/` or `pkg/` |
| 6 | `api-service:go-module` | `api-service` | A `go.mod` file |
| 7 | `flutter:pubspec-manifest` | `flutter` | A `pubspec.yaml` file |
| 8 | `android-gradle:android-manifest` | `android-gradle` | An `app/src/main/AndroidManifest.xml` or `src/main/AndroidManifest.xml` file |
| 9 | `jvm:maven-manifest` | `jvm` | A `pom.xml` file |
| 10 | `jvm:gradle-manifest` | `jvm` | A Gradle project manifest: `settings.gradle.kts`, `settings.gradle`, `build.gradle.kts`, `build.gradle` |
| 11 | `dotnet:solution-or-project` | `dotnet` | A `.sln`/`.slnx` solution, or a `.csproj`/`.fsproj`/`.vbproj` project at the application directory or the repository root, or one level under its `src/` |
| 12 | `apple-native:swift-package-or-xcode-project` | `apple-native` | A `Package.swift` file, or a `*.xcworkspace`/`*.xcodeproj` container, at the application directory or the repository root |
| 13 | `rust-cargo:cargo-manifest` | `rust-cargo` | A `Cargo.toml` file |
| 14 | `ruby-bundler:gemfile` | `ruby-bundler` | A `Gemfile` file, in a repository whose root `package.json` declares no script the npm commands are derived from |
| 15 | `php-composer:composer-manifest` | `php-composer` | A `composer.json` file |
| 16 | `cmake-cpp:cmake-lists` | `cmake-cpp` | A `CMakeLists.txt` file, in a repository whose root `package.json` declares no script the npm commands are derived from |
| 17 | `flat:fallback` | `flat` | Nothing above matched — the unconditional fallback |

**Every row added after `flat:fallback` first existed was inserted immediately above it**, and that placement is the whole of the compatibility argument: first-match-wins means a repository that matched row *n* still matches row *n*, so an added row cannot change the preset of a tree that already had one — only a tree that reached the fallback moves, and it moves onto a row naming its own manifest. The collisions among those rows are settled by **order plus one file-existence test each**, never by reading a manifest's contents: Flutter above Android and Apple, because a `pubspec.yaml` repository carries `android/` and `ios/` trees either would otherwise claim; Android above the two JVM rows and separated from them by `AndroidManifest.xml`, because both stacks carry the same Gradle manifests and only that file tells them apart; CMake last of the manifest rows, because a `CMakeLists.txt` is the one manifest that routinely describes a sub-component of a repository whose own stack is something else — and, for the one such stack that has no row of its own to be caught by, one file-existence-plus-key test on the row itself. Each settlement is argued at its own row below.

**`findLayeredRoot` was deliberately not widened to reach those stacks.** It still tests exactly `<root>/<name>` against three fixed lowercase names over the candidate roots. Added depth, case-insensitive matching or a suffix rule would widen the **two** rows that resolve over that same list — rows 3 and 5 — together, and widening them moves trees *between* presets rather than answering where nothing answered before: `Finding 47`'s cost, paid a second time and over a larger table. So each recognised stack gets its own row and its own layer locator instead, and what such a row yields is deliberately a **single source root** — `lib`, `app`, `main` or `src`, whichever the stack fixes — rather than a guessed decomposition. That is strictly better than `flat`, since it names a directory that exists and records a preset somebody's tree actually matched, and the per-module split stays where `monorepo` and `flat` already leave it: with `/harness-analyze`, which proposes a revision applied only through `config set layers`.

Two of the thresholds are deliberate and both cut the same way. **Two** layer directories rather than three: a repository that grew `data/` and `domain/` but keeps its interface elsewhere is still a layered tree, and demanding all three would push it to `flat`, the one outcome that costs the adopter a hand-written layer list. And **one** would be too few, because a lone `data/` directory is common in trees that are not layered at all.

**The last two candidate roots are conventions rather than guesses.** `internal/` is Go's compiler-enforced privacy boundary and the most conventional place a Go repository puts its packages, `pkg/` is its long-standing companion, and both are widely borrowed into Node and Python trees that never touched Go — without them a textbook `internal/{data,domain,presentation}` tree got the same catch-all profile an empty repository does. Those roots are consulted by exactly **two** rows, 3 and 5, so a tree whose only match is `internal/api/` now answers `api-service` where it answered `flat`, while first-match-wins order leaves every tree that already matched matching the same row. Rows 4 and 6 resolve over a different list — the application directory and the repository root — so the five names above reach neither `api-service:go-module` nor `python-package:packaging-manifest`, and rows 7 through 16 resolve over that same manifest list. **Row 8 is what tells an Android project from a plain JVM one**, and the file it matches on is chosen for that: both carry `build.gradle` and `settings.gradle`, so neither name can decide it, while an `AndroidManifest.xml` is present in every Android module and in no plain JVM one — and reading a Gradle script for its plugin line would be the content heuristic this section refuses. It looks for that file under `app/` and under the manifest root itself, and under nothing else, so a Flutter repository — whose Android manifest sits at `android/app/src/main/` — is never reached by it, quite apart from row 7 claiming it first. **Rows 9 and 10 are that separation's other half**, and their position below row 8 is the whole of it: they match on the Gradle manifests an Android project also carries, so evaluating either above row 8 would claim every Android repository. They are **two rows on one preset**, the shape rows 5 and 6 already have: a preset is a layer profile, and Maven and Gradle JVM projects share the `src/main/<java|kotlin>` source root and differ only in the runner — so a second preset name would buy the same profile twice. Which build tool answers is decided by the command family the matched row hoists, not by the preset. Maven is ordered first because a repository carrying both manifests is a Maven build with a Gradle script beside it more often than the reverse, and first-match-wins has to answer one of them. **Row 11 is the first of the table's two suffix matches**, because a .NET solution and project are named after the product and there is no fixed file name to test for: it takes the sorted-first `*.sln` in a manifest root — or, where the repository has migrated, the sorted-first `*.slnx`, the XML solution format the .NET 9 SDK ships and `dotnet sln migrate` converts to, which every `dotnet` verb accepts in the same position — so a repository holding two solutions answers the same one on every run, and falls back to a project file at that root and then to **exactly one** level under its `src/` — one level and no further, since a project may legitimately sit anywhere in a solution and following it would be a recursive scan rather than the existence test this section is defined as. It is **one preset for a .NET backend and a .NET frontend**, which is rows 9 and 10's argument taken one step further: the two share the build tool, these manifests and the `src/` source root, so the layer profile is identical, and what would tell them apart is the optional-phase set — which comes from `init`'s own `--qa` / `--docs` / `--parity` flags rather than from the preset, so a second name would carry no behaviour. **Row 12 is the other suffix match**, for row 11's reason — an Xcode container is named after the product — and its `.xcworkspace` and `.xcodeproj` halves are **directories** rather than files, which is why the suffix locator searches sub-directories as well. A workspace anywhere the search reaches beats a project anywhere it reaches, since `xcodebuild` prefers one and a project built on its own misses the schemes and package dependencies its workspace declares; the row also matches a `Package.swift` by name, so one row covers both ways an Apple repository declares itself. It is **one preset for iOS and macOS**, on rows 9 and 10's argument again: nothing a file-existence test can ask separates the platforms — the manifests, the `Sources/` root and the toolchain are identical, and the platform appears only inside a scheme or a target setting this section may not read — so the name says `apple-native` rather than implying an iOS-only scope. A `Podfile` is not matched on: CocoaPods sits beside either container rather than instead of one, and the `.xcworkspace` it generates has already answered the question. A Flutter repository's `ios/` tree is out of reach here for row 7's reason and for this row's own: both locators probe the application directory and the repository root, and neither descends into `ios/`. **Row 13 is matched by name and asks nothing further**: `Cargo.toml` is Rust's only manifest, so its presence is the whole test. A Cargo **workspace** root carries that same file and is deliberately not told from a plain crate — separating them would mean reading the file for a `[workspace]` table, and what it would buy is a per-member layer list, which is a judgement call and therefore `/harness-analyze`'s. Its position above the fallback costs nothing, since no earlier row matches on a Rust name. **Row 14 is matched by name for row 13's reason** — `Gemfile` is Ruby's only dependency manifest — and it is the one row that **deliberately loses a collision**: a Rails application matches row 5 on its `app/controllers` and never reaches here, which is the better of the two answers, since `api=app/controllers` names a real request-handling layer where this row would name only the `app/` source root above it. It loses nothing by losing, because the Bundler command family is selected independently of the preset, so a Rails repository keeps the `api-service` profile **and** gets the `bundle exec` lines. It also **declines** a collision it must not lose: a repository that is not Ruby at all. The converse of row 13's reason is false — a repository with a `Gemfile` is not thereby a Ruby one — because Ruby's packaging is the standard way to pin mobile and static-site tooling, so the React Native project template ships one at the root for CocoaPods and fastlane, a native iOS repository ships one for fastlane, and a Jekyll site ships one beside an npm build. Unguarded, a React Native repository was detected `ruby-bundler`, took the `general` layer only and had both required keys written as placeholders while the npm scripts in its root manifest went unread. So row 14 carries row 16's guard, for row 16's reason and on the same top-level `scripts` key inspection: it declines a repository whose root `package.json` declares a script the npm family would answer with. The row guard is the smaller half — the Bundler **command family** is selected independently of the preset and is tried above npm whether or not this row matched — so the family carries the same guard on its own gate, and where it does not apply is argued with the family order below. What reaches row 14 is therefore every other Ruby repository — a gem, a script collection, a Sinatra service with no route directory. **Row 15 is row 14 repeated on PHP**, collision included: `composer.json` is PHP's only dependency manifest, and a Laravel application matches row 5 on its root `routes/` and never reaches here — keeping `api=routes`, and getting the Composer lines anyway from the family below. Its manifest is the one on this table that is **JSON**, so a top-level key test would be available to it within this section's rule; no row asks one, because the file's presence is already the whole answer. What reaches row 15 is every other PHP repository — a PSR-4 library, a Symfony service with no route directory. **Row 16 is matched by name for row 13's reason** — `cmake` and `ctest` take the same arguments whatever a `CMakeLists.txt` declares, so its presence is the whole test and reading it for targets would be the content heuristic this section refuses — and **its position last among the manifest rows is the whole of its design**. Every row above matches on a file that names the repository's own stack; a `CMakeLists.txt` is the one manifest here that routinely describes a **sub-component** of a repository whose stack is something else — a native extension in a Python distribution, a `node-gyp` addon, a Rust FFI shim. Evaluated any higher it would claim all three; evaluated here, a Python distribution keeps `python-package` and its `mypy`/`pytest` lines and a Cargo crate keeps `rust-cargo`. **Order settles two of those three populations and cannot settle the third**, because Node has no row on this table: an npm repository reaches `flat` or a directory-shaped row by fallback rather than by a positive match, so there is nothing above row 16 for a `node-gyp`/`cmake-js` addon to be caught by — and claiming it was silent, since both required keys resolved to a `cmake` build that never type-checks the published TypeScript and a `ctest` run against a build tree registering no tests. So row 16 **declines** a repository whose root `package.json` declares a script the npm command family would answer with (`typecheck`/`check-types`/`tsc`/`lint`, `test`, `build`, `dev`/`start`/`serve`) — a top-level `scripts` key inspection, which is inside this section's rule, and the same question the npm family's own gate asks. What reaches row 16 is therefore the repository whose only manifest is CMake's, or whose root `package.json` declares none of those scripts.

**The last row is a fallback, never a refusal.** An unrecognised layout gets the `flat` preset plus a warning naming `/harness-analyze` — an unrecognised repository is precisely the one that command exists for, and refusing there would block adoption on it. What that command then does to the layer profile is **propose** a revision, applied only through `autonomous-sdlc-harness config set layers` (§2's closing pointer, §8): the warning hands off a judgement call, not a second writer of the file `init` reads on every run. **That verdict is about the layer half alone**, and the run says so where the other half answered: the command families are selected independently of this table, so a repository that reached the fallback may still have had `commands.typecheck` and `commands.test` derived from its own manifest — and where a family did, a note names it, the manifest it read and **which of the two keys it actually supplied**, so an adopter is not told the repository was unrecognised when half of it was recognised. The note's subject is that the command half resolved, so it is withheld wherever neither required key did — no family answered, or the family that answered derived neither (a `package.json` declaring only a `build` script is answered by the npm family and supplies neither verifier). Both keys then already carry the undetected-command warning, and a second line saying the same thing is duplication. **The fallback also carries a note where the repository looks like it nests its application and nobody said so.** Where the application directory was named neither on the command line nor in the configuration, `init` probes the **direct subdirectories** of the repository root with this same manifest table, and where exactly one of them holds a manifest `init` reads, the note names that directory, the manifest found in it, and `--app-dir <dir>` as the re-run that would point detection at that tree. What it does **not** do is the point of it: it adopts nothing, because which directory is the application is the adopter's statement rather than a detection result; and it says nothing at all on **two or more** hits, because a repository holding several applications is undefined here and naming one of them would be a recommendation nothing here has a basis for making. It is withheld on a third condition too — a run started in that directory or anywhere below it already says so on its own line, and two lines saying one thing is how a notes block stops being read — and it is a **note** rather than a warning, since a repository is not at fault for nesting its application. The probe is also silent where the root itself holds a manifest `init` reads: it could then not tell that manifest from a child's, and printing nothing is the conservative failure. `--preset <name>` bypasses the table entirely; the run then reports that no signal was evaluated, rather than naming one that was never tested.

**The outcome is recorded, so the hand-off leaves a trace.** `init` writes what detection concluded — the preset, the signal row that matched and the evidence it matched on — into `harness.config.json`'s `detection` object, so the adoption commit states which layout was detected and on what, and a `flat` fallback is no longer indistinguishable from a profile somebody chose. Under `--preset` the signal is `forced` and **no** `evidence` key is written at all, because no row was evaluated — which is what a reader tells a forced preset from a detected one by. **`detection.commandFamily` is the one key in that object that is not about the layer table**: it records which command family derived `commands.*`, on the same present-or-absent discipline `evidence` follows — absent, rather than null, wherever there is no such family: a family answers off any command set it can build, so the key is written only where that family derived at least one of `commands.typecheck` / `commands.test`, and it is absent exactly where the two required commands hold placeholders. It is not a cross-check on the preset, and a reader acts on it that way: the layer preset and the command family are two independent answers to two different questions, so a `flat` preset beside an `npm` command family is a description of the repository, not an inconsistency. `doctor`'s `layer-profile` check (§7) is the standing half: it warns while `layers[]` carries no row scoped below the repository root and that record does not account for it — it names the `flat` fallback, names nothing, or names a preset whose source root did not resolve. The record is written on the run that generates the file and no plain re-run refreshes it: `harness.config.json` is one of the three artifacts `--force` does not upgrade (§3), so a re-run keeps the record already there and `--reset-config` is what rebuilds it.

**What a preset's layer profile carries.** Each preset writes the source rows its own paragraph above resolves, then a `tests` row, then the catch-all `general` row. The `tests` row points at `.claude/context/tests.md` — one document and one layer name across every stack, so an instruction can say "the `tests` layer" once — and the directory it names is that toolchain's convention rather than a guess: Maven's and Gradle's `src/test`, an Android module's `app/src/test` ahead of a single-module `src/test`, Dart's `test/`, SwiftPM's `Tests/`, RSpec's `spec/` ahead of a leftover `test/`, pytest's and CMake's `tests/` ahead of a `test/`, the `tests/` .NET, Cargo and PHPUnit projects use, and — for the two directory-shaped presets, `layered-clean-arch` and `api-service`, whose stacks fix no convention — `test/` ahead of `tests/`, each also spelled under `src/` because those two presets' source rows search a wider set of roots than the test row does. It follows the rule every source row follows — **a row whose directory does not exist is dropped rather than written**, so a generated configuration never points an implementer at a path that is not there — and `monorepo` and `flat` have none at all, their layer-less profile being a stated decision rather than an unresolved source root. `cmake-cpp` is the one preset with **two source rows**: `include/` is declared beside `src/`, pointed at the same single-module document, because a CMake target's public headers are the API half of that same module — implementation work rather than a test tree, and a sibling no single path covers. The consequence an adopter sees is in `doctor`'s `layer-drift` check (§7), which warns about a source directory under the application directory that no layer covers: a conventional test root and a C++ `include/` are now covered by rows rather than reported as drift.

Detection yields a preset name and **raw** command lines. It never formats a wrapper invocation and never reads `scriptsDir` — that belongs to §5.

**Which command family answers, and in what order.** The first family whose derivation returns a command set supplies everything it can and the search stops there — falling through to a second family for a key the first could not resolve would pair, say, an npm type-check with a `pytest` run in a repository that asked for neither combination. **Where more than one manifest `init` reads is present, the run says so**, in a note naming the family that answered, the manifest **that family itself read**, **which of `commands.typecheck` and `commands.test` that family supplied** — a family that answered is not both required keys resolved, so a key it did not derive is reported as carrying a placeholder rather than as having come from it — the manifests present that did not supply these lines, and the families that were tried, read their own manifest and **declined** where the run recorded any — declined is the accurate verb, because a family reached above the winner did read and did run: `bundler` reads a root `Gemfile`, builds what it can and yields where that root's `package.json` declares an npm script. The note closes on a configuration edit rather than a fix, because taking a different lane is not a fault: setting `commands.typecheck` or `commands.test` by hand is how a repository takes one. That note is that run's; `detection.commandFamily` in `harness.config.json` is the durable record of the same fact. The standing order puts **npm second to last**, for a property of the manifest rather than a preference between stacks: `package.json` routinely appears in a repository of some other stack — a documentation site, a lint-only tooling manifest, a bundled front end — while `go.mod`, `pyproject.toml`, `pubspec.yaml`, `AndroidManifest.xml`, `pom.xml`, the Gradle manifests, a `*.sln`/`*.slnx`/`*.csproj`, a `Package.swift`/`*.xcodeproj` and a `Cargo.toml` name the repository's own stack. Two manifests share `package.json`'s property and are handled by a **gate on the family** rather than by the order: a `CMakeLists.txt`, whose family is the one placed below npm, and a `Gemfile`, whose family stays above npm and declines instead — each is argued in its own paragraph above. **`cmake` is the family below npm**, and it is the first of those two: a `CMakeLists.txt` routinely describes a sub-component of a Node repository — a `node-gyp`/`cmake-js` addon — so between the two the npm claim is the more specific one, and the npm family's own gate is what separates them, since it answers only where the root manifest declares a script and a C++ tree's `package.json`, where it has one at all, does not. A genuine C++ repository is unmoved: row 16 decides its preset and hoists `cmake` to the front, ahead of the standing order. Ahead of the standing order, the family named by the **signal row that matched** is hoisted to the front, so a repository whose preset was decided by its own manifest gets that manifest's commands: rows 1 and 2 hoist npm, row 4 python, row 6 go, row 7 dart, row 8 android-gradle, row 9 maven, row 10 gradle-jvm, row 11 dotnet, row 12 apple-native, row 13 cargo, row 14 bundler, row 15 composer, row 16 cmake. A directory-shaped row hoists nothing, and `--preset` hoists nothing either — it evaluates no row at all. **Among the non-npm families the order is manifest specificity**, which is what keeps a family from answering for a stack whose manifest it merely shares: `android-gradle` sits above both JVM families because an Android module carries the Gradle manifests they gate on while `classes` is not the task that compiles it, and the Gradle JVM family sits below the Maven one because a repository carrying both manifests is more often a Maven build with a Gradle script beside it than the reverse. Every other family gates on a manifest no other family reads, so its position among them is free and only its position above npm — and, for `cmake`, below it — is load-bearing. A family only stops the search when it resolves something: a root `package.json` declaring none of the scripts the four npm keys accept (`typecheck`/`check-types`/`tsc`/`lint`, `test`, `build`, `dev`/`start`/`serve`) hands the search on rather than answering with nothing. **The dart family chooses its tool on two positives**: a package carrying `lib/main.dart`, `android/` or `ios/`, **or** whose `pubspec.yaml` declares a dependency on the Flutter SDK (an `sdk: flutter` line, matched without parsing the YAML), is an application and gets `flutter analyze` / `flutter test` / `flutter pub get`; anything else is a plain package and gets the `dart` spellings — the two are not interchangeable, since `dart analyze` reports every `package:flutter` import as unresolved and `flutter test` needs the Flutter SDK on `PATH`. The manifest read is the one place in this section that reads a file's content, and it is deliberately outside the table above: file existence alone cannot tell an application whose entry point moved out of `lib/main.dart` and which checks in no platform trees, and the probe decides only **which tool an already-selected preset gets**, never which row matches or which preset is selected — so the table's no-content-heuristics rule is untouched. The marker test is evaluated first, and the disjunction is additive: every tree that resolved `flutter` before still does. It resolves no `build` and no `devServer`: `commands.build`'s only consumer is `setup-worktree.sh`, so a `flutter build apk` would cost minutes in every worktree the flow cuts and prove nothing `analyze` and `test` have not, and a dev server needs a device selection, which is a judgement call rather than something file existence answers. A `build.yaml` beside the manifest is reported as a **note**: generated sources are a precondition of the analyzer, so the generator belongs on the line above the analyze line inside the wrapper `commands.typecheck` names, not in a command key of its own. **The android-gradle family runs the project's own Gradle wrapper where it ships one** — `./gradlew` pins the Gradle version the project builds with, and `gradle` from `PATH` is the fallback for a project without it, preferred from the same directory `-p` names and falling back to a root `gradlew` before a `PATH` lookup, on the two-candidate rule the JVM-families paragraph below states — and names the two per-variant tasks the Android Gradle plugin registers for every module on AGP 7 and 8: `compileDebugSources` for `typecheck` and `testDebugUnitTest` for `test`, both with `--console=plain --quiet`, since these lines run unattended inside a wrapper and a progress bar rendered into a captured log helps nobody. It resolves **none** of the other three keys, each for its own reason: `commands.build`'s only consumer is `setup-worktree.sh`, so an `assembleDebug` would spend a multi-minute native build in every worktree the flow cuts and buy no verification an agent runs; an Android application has no dev server; and Gradle resolves dependencies as part of the task being run, so a separate install would pay the same download twice per worktree and verify nothing.

**The two JVM families sit below the android-gradle one**, and both are gated on their own manifest. **Both run the project's own wrapper where it ships one** — `./mvnw` for Maven, `./gradlew` for Gradle — with `mvn` and `gradle` from `PATH` the fallback for a project that ships none, for the reason the android-gradle paragraph above states. **Maven** runs `compile` for `typecheck` and `test` for `test` — lifecycle phases every POM has, so neither is an invented line — with `-B` dropping the progress rendering a captured log turns into noise and `-q` leaving the failure output. It is the one JVM family that resolves `depInstall`: `dependency:go-offline` warms the local repository once per worktree, which is what that key is for. **Gradle JVM** runs the Java plugin's own `classes` and `test` tasks, with the same `--console=plain --quiet` pair, and resolves no `depInstall` for the reason above. Below the repository root each anchors itself — `-f <dir>/pom.xml` for Maven, `-p <dir>` for Gradle — since every command line runs from the root. **The wrapper is preferred from the same directory the anchor names**, so a nested project runs its own `./<dir>/mvnw` or `./<dir>/gradlew` where it ships one; a repository that keeps only a root wrapper with its manifest below it falls back to that root wrapper rather than to `mvn`/`gradle` from `PATH`, since the anchor names the tree either way and a `PATH` lookup exits 127 on a machine with no system build tool installed. Neither emits `build` or `devServer`: `commands.build`'s only consumer is `setup-worktree.sh`, so a `package` or an `assemble` per worktree would prove nothing `compile` and `test` have not, and a JVM service has no dev server file existence can start. The `typecheck`/`test` pair **overlaps by construction** on a compiled stack — the test task recompiles what the compile task compiled — and is kept anyway, because `typecheck` is the cheaper of the two, runs first on every task and fails faster: collapsing them would make every task pay the test run to learn that the code does not compile.

**The .NET family sits below both JVM families and above npm**, gated on the solution or project row 11 found. It runs `dotnet build --nologo` for `typecheck` and `dotnet test --nologo` for `test`, with `--nologo` dropping the banner for the reason `-B` drops Maven's, and resolves `depInstall` as `dotnet restore` — the whole dependency graph, warmed once per worktree, which is what that key is for. Below the repository root all three name the found solution or project, since every line runs from the root and a bare `dotnet build` there would find no project; at the root the argument is omitted, because `dotnet` resolves the single solution or project itself. It emits **neither** `build` nor `devServer`: `commands.build`'s only consumer is `setup-worktree.sh` and an MSBuild line there would repeat the compile `typecheck` already runs, and `dotnet run` needs a project chosen from among the solution's, which is a judgement rather than something file existence answers. Its `typecheck`/`test` pair overlaps by construction like the JVM families' and is kept for their reason.

**The Apple-native family sits below the .NET one and above npm**, and it is the one family on this matrix that cannot serve both required keys. Its **SwiftPM arm** — a `Package.swift` exists — runs `swift build` for `typecheck` and `swift test` for `test`, with `--package-path <dir>` below the repository root; `depInstall` is `swift package resolve` carrying that same anchor, for the Cargo family's `cargo fetch` reason — `depInstall`'s only consumer is `setup-worktree.sh`, so the resolve is paid once per worktree rather than inside that worktree's first build, and it is not paid twice, since a later `swift build` reads the `Package.resolved` and `.build/checkouts` the resolve wrote. No `build` and no `devServer`, for the reasons the JVM families give. Its **Xcode arm** — no `Package.swift`, but a project or workspace — derives `typecheck` as `xcodebuild -project|-workspace <container> -scheme <name> build` **only where the container shares exactly one scheme** under `xcshareddata/xcschemes`: `-scheme` takes one name, a user-local scheme under `xcuserdata/` exists on one machine and no CI runner, and picking among several shared ones is a judgement rather than something file existence answers — so zero or two shared schemes leave `typecheck` a placeholder too.

**`commands.test` in the Xcode arm is the one entry on this matrix that stays hand-written, and it is argued rather than left silent.** `xcodebuild test` requires a `-destination`, which names a simulator or device on the machine that runs it; no file in the repository states which one, so deriving it would be the invention this section forbids everywhere else. The run leaves the placeholder, raises the standing undetected-command warning for it — so no `test.sh` is written and none is allow-listed — and adds a **note** naming the container, the scheme if exactly one was shared, the `-destination` reason, and the line to set by hand. One further departure belongs to this arm alone: it **stops the family search even where it resolved nothing**, unlike a scripts-less root `package.json`, because an `.xcodeproj` names the repository's own stack — handing on would pair an npm line with an Xcode repository and leave that note attached to a key some other family had filled.

**The Cargo family sits below the Apple-native one**, gated on the `Cargo.toml` row 13 found. It runs `cargo fmt --check && cargo clippy --all-targets -- -D warnings` for `typecheck`, `cargo test` for `test` and `cargo fetch` for `depInstall`, with `--manifest-path <dir>/Cargo.toml` below the repository root on every one of them — both halves of the compound included, since an anchor on one half leaves the other reading the root manifest — because every line runs from the root. **The linter is the static-analysis key here**, as `bundle exec rubocop` is for the Bundler family below; the difference is the gate — RuboCop is a gem the repository has to declare, while clippy and rustfmt are components of the toolchain a `Cargo.toml` already commits the adopter to, so there is no configuration file to condition the line on. `-D warnings` is what makes clippy's lints fail the key rather than print it, and `--all-targets` is on it for the reason it was on the `cargo check --all-targets` this key used to run: without it tests and benches go unchecked, so the cheap key passes on code the expensive one then fails to compile. Nothing goes uncompiled by the change either, since `cargo clippy --all-targets` compiles exactly what that line compiled. `init` says both of those things in a **note**, which also names the older line as the softer one a crate carrying existing lint or format debt can set the key back to. One consequence reaches §5: the line is a compound ending in `--`, so an argument the wrapper forwards lands among rustc's flags rather than reaching a filter. It emits **neither** `build` nor `devServer` — `commands.build`'s only consumer is `setup-worktree.sh`, so a `cargo build` there would recompile what the type-check line already compiled in a key no agent runs, and a crate has no dev server file existence can start.

**The Bundler family sits below the Cargo one**, gated on the `Gemfile` row 14 found, and it is the family that answers a Rails repository whose preset came from row 5. `depInstall` is `bundle install`. It **hands the search on** where that install is all it would emit and the repository's root `package.json` declares an npm script — row 14's guard on the family, needed because the family is tried above npm whether or not the row matched, and this is the React Native repository whose root `Gemfile` pins CocoaPods and fastlane rather than declaring a Ruby stack. The family stays **above** npm rather than moving below it as `cmake` does, and that is the reason the condition is drawn this narrowly: a Rails application's preset comes from directory-shaped row 5, which hoists nothing, and Rails routinely carries an asset-pipeline `package.json`, so moving the family would answer `npm run build` where `bundle exec rspec` is the right line. A `Gemfile` repository that resolved either verifier keeps every line it resolved, npm scripts beside it or not, and a Ruby repository that configures neither still gets `bundle install`, since nothing else is waiting to answer there. The other two keys are emitted **only** on the repository's own evidence and left unresolved otherwise, because Ruby offers nothing that could stand in for them: `typecheck` is `bundle exec rubocop` where a `.rubocop.yml` or `.rubocop.yaml` sits beside the manifest, and nothing at all where neither does — Ruby has no type checker in the general case, Sorbet and Steep are opt-in and separately configured, and a placeholder plus its warning tells an adopter what to fill in where an invented line would hand them a step that verifies nothing. `test` is `bundle exec rspec` where a `spec/` directory exists, `bundle exec rake test` where a `test/` one does **and a `Rakefile` sits beside the manifest**, and unresolved otherwise — RSpec's and Minitest's locations are fixed, so the choice is existence rather than judgement, and `rake` reads its tasks from a `Rakefile`, so the line aborts without one. That precondition is also what makes `test/` count as Ruby evidence for the guard above: `test/` alone is `node:test`'s, Mocha's and Ava's directory too, so a Node repository with a root `Gemfile` and a `test/` directory resolves nothing here and is handed on to npm. It emits **neither** `build` nor `devServer`: Ruby is interpreted, so there is nothing for `setup-worktree.sh` to build, and a Rails server needs a port and a binding chosen, which is a judgement call. Below the repository root each line is prefixed with `BUNDLE_GEMFILE=<dir>/Gemfile ` — `bundle` has no directory flag, so the environment variable is the only spelling that points it at a nested manifest, and it is an ordinary command line rather than a change to anybody's environment because it lands inside the wrapper script `commands.*` names — with the directory passed to the runner as well: a path for `rubocop` and `rspec`, `rake -C <dir>` for the Minitest line, since a `Rakefile` is found relative to the working directory.

**The Composer family sits below the Bundler one**, gated on the `composer.json` row 15 found, and it answers a Laravel repository whose preset came from row 5. `depInstall` is `composer install --no-interaction`, and it is **load-bearing rather than a convenience**: both other lines run out of `vendor/bin`, which does not exist until that install has run, so a fresh worktree without it fails every command this family emits. The two verifiers are emitted **only** on the repository's own configuration file, for the Bundler family's reason in a sharper form — PHP has no analyser every project has, and PHPStan, Psalm and PHPUnit are each opt-in, separately installed and separately configured, so a line naming a tool the repository does not configure would fail on a missing binary rather than check anything. `typecheck` is `vendor/bin/phpstan analyse --no-progress` where a `phpstan.neon` or `phpstan.neon.dist` sits beside the manifest, `vendor/bin/psalm --no-progress` where a `psalm.xml` or `psalm.xml.dist` does and PHPStan configured none, and unresolved otherwise; PHPStan is tried first because a repository configuring both is a PHPStan project with a Psalm baseline more often than the reverse. `test` is `vendor/bin/phpunit` where a `phpunit.xml` or `phpunit.xml.dist` exists, and unresolved where neither does. It emits **neither** `build` nor `devServer`: PHP is interpreted, so there is nothing for `setup-worktree.sh` to build, and `php artisan serve` needs a port and a host chosen, which is a judgement call. Below the repository root the install takes `--working-dir <dir>` and each verifier `-c <dir>/<config file>`, since every line runs from the root.

**The CMake family is the one family below npm**, gated on the `CMakeLists.txt` row 16 found, and it is the one family whose two keys share a prefix rather than standing on separate tools. `typecheck` is a compound line — `cmake -S . -B build && cmake --build build` — because the configure step and the compile are one act on this stack, and the compile is the only static check a C++ project has; the whole line lands inside `typecheck.sh`, where a compound is an ordinary command line rather than two command keys, the same shape a code-generation precondition takes above an analyzer. `test` **carries that same compound as a prefix** — `cmake -S . -B build && cmake --build build && ctest --test-dir build --output-on-failure` — because `ctest` reads a build tree and nothing establishes an order between the two keys: no instruction in the plugin states one, and a worktree `setup-worktree.sh` provisioned holds no build tree either, since this family emits no `build` key. A bare `ctest` run first would fail on a missing directory before a test executes, which reads as a broken checkout rather than as a step taken out of order; configure and build are both incremental, so repeating them where `typecheck` already ran costs near-nothing. **`build/` is the family's own choice rather than something the repository declares** — no CMake project states where its build tree goes, so a name had to be picked, and both keys are composed from the same string, so neither can come to name a different tree than the other. It emits **none** of the other three keys: `build` would repeat the compile already inside `typecheck` in the one key no agent runs, a C++ project has no dev server file existence could start, and dependency acquisition here is project-specific — `FetchContent`, a submodule, a system package, Conan, vcpkg — so any `depInstall` would be invented rather than derived. Below the repository root every path carries the manifest's directory, since each line runs from the root.

**What each family emits, and what it leaves unset on purpose.** The five keys are not equally expensive to get wrong, because they do not run equally often: `typecheck` and `test` run on **every task for every agent**, `devServer` **once per QA phase**, and `depInstall` and `build` **once per worktree**, in `setup-worktree.sh` — and `build` is never wrapped, so it is never allow-listed to an agent and no line an agent runs reaches it. The rule that follows, and that no family below breaks: **a compiled stack does not get a `build` key just for being compiled** — a build that repeats the compile `typecheck` already ran spends minutes in every worktree the flow cuts to prove what the cheaper key proved on every task — and a **code-generation** step belongs on the line above the analyzer inside the wrapper `commands.typecheck` names, not in a key nothing an agent runs would reach. The rows are in the standing family order of the paragraphs above: npm second to last, and `cmake` below it for the reason §4 gives.

`npm` is the one family that emits `build` at all, and it emits it only because a repository **declared** the script — which is the rule above stated from the other side: a `build` key exists where the repository asked for one, not where a toolchain could produce one.

**A `typecheck` resolved from the `lint` fallback is reported, and the severity is decided by evidence.** `lint` is the last of the four candidates for that key because it is the one that may not type-check at all: an ESLint run without type-aware rules exits zero on a type error, which is the same outcome as a detected command that never checked anything — reached by a different route. The candidate is nonetheless **kept**, unchanged in membership and order, and the selection is **said out loud** instead: a **warning** where a `tsconfig.json` sits at the repository root, since that is file-existence evidence the repository is typed and a `lint` line is very unlikely to be its type check; a **note** where none does, since `lint` is plausibly exactly what a plain-JS adopter meant and a warning on every correct adoption is how a warning list stops being read. Only the root `tsconfig.json` counts, because the four script-derived keys are read from the root `package.json` only — a nested one is not evidence about a root-derived line. The message names the script, the line that was set, what it may not do, and the same second step every wrapped key's remedy carries (§5). Two alternatives were considered and rejected: **dropping `lint`** from the candidate list replaces a weak check with a placeholder for every plain-JS adopter, which is worse for the adopters who meant it; and **deriving `npx tsc --noEmit`** from a `tsconfig.json` would invent a command the manifest does not declare, against this section's own rule that nothing here is guessed. **The population this reaches is the npm family's alone**, and npm-last is what bounds it: every stack with a manifest of its own is answered by its own family above, and each of those families either derives a real type check or leaves `typecheck` unresolved with the undetected-command warning — none of them has a `lint`-shaped fallback to report on. So this selection, and this warning, are reached only by a repository whose commands came from a root `package.json` whose sole recognised script for that key is `lint`.

**Where a family resolves no `typecheck` at all, the adopter has an answer as well as a placeholder.** Four arms on this matrix can leave that key unresolved; they are enumerated in `docs/typecheck-key-decision.md` → `## 3. Can another family reach this state?`, which is where that list is maintained rather than re-derived here. A repository that genuinely has no type check answers the required key with the sentinel `<none>` — exactly that, unquoted and lower-case (`docs/config.md` §5's `commands.typecheck` row): the configuration check grades it as **answered** instead of warning, no `typecheck.sh` is written for it and no permission entry is implied (§5), so the key is closed rather than carrying a placeholder nothing will ever fill. What the sentinel is **not** is a detection outcome. `init` never writes it, because reaching an unresolved arm establishes that **detection failed**, not that the repository has no type check — a Ruby repository with no RuboCop config and one with Sorbet configured some other way are the same state to this table, and only the adopter can tell them apart. A generated configuration therefore still carries the placeholder and its undetected-command warning on every one of those arms, and the sentinel arrives afterwards, through `config set commands.typecheck "<none>"` or by hand.

**Two residuals, both stated because neither is free.** *Family order:* a repository carrying a root `package.json` **with** a recognised script alongside a root non-npm manifest now gets the non-npm family's lines where it got the npm ones — the accepted price of npm-last, and it reaches two populations rather than one. Where the preset came from a directory-shaped row (3 or 5, which hoist nothing) only the commands move. Where the non-npm manifest is itself a **row** — a `Cargo.toml` in a napi-rs or neon addon is the routine case — the preset moves too, from `flat` to that stack's name, and the hoist makes the family unavoidable. On that second population `depInstall` moves as well: a family that resolves it (`cargo fetch`) suppresses the root npm fallback below, so `setup-worktree.sh` installs no `node_modules` in any worktree the flow cuts. That population is **accepted rather than guarded**, and row 13's comment records why: rows 14 and 16 decline because the family they would hoist verifies nothing (`bundle install` alone) or verifies a tree that is not there (`ctest` against a build registering no tests), while the cargo family's type-check line and `cargo test` check the crate the repository really carries. *Dependency install:* the `depInstall` fallback below is no longer bounded to an install site below the root, so **any** repository whose `typecheck` and `test` come from a non-npm family while a root `package.json` sits beside them now gains a root `npm ci`/`npm install` where it previously got no `commands.depInstall` at all — and `setup-worktree.sh` runs that install in every worktree the flow cuts.

**A raw line derived from a manifest under `appDir` carries that directory**, because commands are executed from the repository root and a line derived at one root and run at another either fails or, worse, reads none of the configuration the manifest holds and reports success. Each family that can be anchored carries it in the spelling its own tool accepts: a Python manifest below the root yields `mypy <dir>` and `pytest <dir>`, a `go.mod` below the root yields `go -C <dir> vet ./...` and `go -C <dir> test ./...`, a `pubspec.yaml` below the root yields `<tool> analyze <dir>`, `<tool> test <dir>/test` and `<tool> pub get --directory <dir>`, an Android module below the root yields `<runner> -p <dir> …` naming the Gradle project directory rather than the module — a subproject named on its own is a project without the settings file that declares it — a .NET solution or project below the root is named as the trailing argument of `dotnet build`, `dotnet test` and `dotnet restore`, a `Package.swift` below the root yields `swift build --package-path <dir>`, `swift test --package-path <dir>` and `swift package resolve --package-path <dir>`, a `Cargo.toml` below the root is named by `--manifest-path <dir>/Cargo.toml` on both halves of the type-check compound, on `cargo test` and on `cargo fetch`, a `Gemfile` below the root is named by a `BUNDLE_GEMFILE=<dir>/Gemfile` prefix on every Bundler line plus a directory for the runner, a `composer.json` below the root is named by `--working-dir <dir>` on the install and `-c <dir>/<config file>` on each verifier, a `CMakeLists.txt` below the root puts its directory into every path on both of its lines — `cmake -S <dir> -B <dir>/build` on the type-check line and that same pair ahead of `ctest --test-dir <dir>/build` on the test line, both composed from one string, which is what keeps the two naming the same build tree — and a Node **dependency install** is `--prefix`-anchored to the manifest it was derived from — the first `package.json` under the application directory or the repository root — as `npm --prefix <dir> ci`, or `install` where no lockfile sits beside that manifest. **A root `package.json` is not a precondition for that anchored install.** The four script-derived npm keys are read from the root manifest only, so a repository whose sole manifest is `<appDir>/package.json` gets a placeholder and a warning for `typecheck` and `test` — and the anchored install all the same, because the alternative is no `commands.depInstall` at all: `setup-worktree.sh` then installs nothing into every worktree the flow cuts, and no line of output says so. That fallback reaches the **root** install site too, so a repository whose verification keys came from a non-npm family gets its root install alongside them: `depInstall` is a whole command line rather than a verification key, it is derived independently of whichever family won, and it is never wrapped or allow-listed, so deriving it beside another family's lines is not the family-mixing the order above forbids. The anchoring has one carve-out: on a **workspace root** — an npm `workspaces` key, or a `pnpm-workspace.yaml` / `lerna.json` / `turbo.json` / `nx.json` at the root, which is the union of the two `monorepo` rows above — the root install covers every member and the anchored form would fail for want of a member lockfile, so the root line stands. That carve-out applies to the fallback as well, and has to: the fallback is now reached with a root manifest present whenever that manifest declares no recognised script, so a workspaces root under `--app-dir <member>` would otherwise be anchored at a member that keeps no lockfile of its own. Where no manifest sits at the root at all, there is no root line to keep and the anchored form stands. **The other two script-derived keys are answered too, and differently, because they get no placeholder.** An unresolved `build` or `devServer` is simply absent from the generated config, so where `<appDir>/package.json` declares the script it would have come from, the run says so in a **note**: the manifest, the script it declares, the root-anchored line to set, and what the absence costs — `setup-worktree.sh` skips the build in every worktree the flow cuts (`docs/watcher.md` §2), and the interactive test phase has nothing to start the application with. A note rather than a warning, since a repository with no build step is ordinary and an optional key nothing declares is not a fault; the note names a value to set by hand and derives nothing, so the root-manifest rule above is unchanged for all four keys. A repository whose application *is* the repository generates exactly what it generated before, in every one of those shapes. A run that anchors a command says so in its notes, naming the manifest the line was derived from and the directory it is executed in, which is the repository root.

**A third residual, and it is the asymmetry the paragraph above leaves standing.** With an application directory named, `depInstall` **is** derived from the manifest under it and anchored — `npm --prefix <dir> ci` — while `typecheck` and `test` stay placeholders beside a warning that names the exact anchored line to set. That is this module's standing rule rather than an oversight: `depInstall` is a whole command line, so it can follow the manifest that was actually found, while the four script-derived keys are **script names resolved against the manifest the runner reads**, and the runner reads the root's. The warning is what keeps the gap repairable without guessing — it names the manifest, the script it declares and the line to paste, composed from the same candidate table detection itself selects from, so the offered line is the one that would have been derived had that manifest been the root's, and the second step every wrapped key carries (§5) is the rest of the remedy. **Why the two are not derived too, in the terms a change would have to answer.** The historical reason — a nested script produces a line that does not run — no longer covers the anchored `npm --prefix <dir> …` form, which runs from the repository root like every other line here. What is unsettled is the **family** question: deriving those keys from `<appDir>/package.json` would let the npm family answer for a repository whose root manifest belongs to another stack, which is exactly the pairing the first-family rule above exists to prevent, and it would move what is derived for **every** nested adoption rather than only the npm ones. That is a change to the command-family surface with a blast radius across all of them, and it is not a change a report may take on its own. What changed instead is that the state is now **said out loud at adoption time**: the commands step (§2) prints the placeholders and the derived install together, in one block, and where the application looks nested and nobody said so the `flat` fallback's note names the directory and `--app-dir`. The asymmetry is where an adopter can see it, rather than silent.

**The adoption matrix, and the one key on it that stays hand-written.** Every stack the harness is installed against is served by `init` with no hand-written configuration: a Flutter application in either layout, a native Android application, a native iOS project through either toolchain, a Node backend, a .NET backend or frontend, a Java backend through Maven or Gradle, and a C++ tree built by CMake — plus the Python, Go, Rust, Ruby and PHP adoptions above. **The layer half is served for all of them**: none answers `flat:fallback`, and each names a source root below the repository root, which is what `doctor`'s `layer-profile` check grades. The command half has exactly **one** required key on the whole matrix that stays hand-written — `commands.test` on the Xcode arm, because `xcodebuild test` needs a `-destination` no file in the repository states — and it stays a placeholder, with the undetected-command warning and a note naming the line to set, rather than an invented line. That is a test result, not a claim: `cli/test/stack-presets.test.mjs` → `every stack on the adoption matrix is served end to end` runs the real `init` against one repository per entry and asserts the preset, the layers, the derived lines, the wrappers on disk and the Xcode exception, and asserts on every entry that no `commands.build` was emitted.

## 5. The wrapper-script contract

Three files hold three views of one string: `harness.config.json`, the wrapper scripts, and the generated permission profile. Drift between them is invisible until an unattended run stalls, so one table declares the wrapper set and one function formats the invocation, and the config and profile generators import both rather than spelling out `bash …/….sh` themselves.

- **`commands.typecheck`, `commands.test` and `commands.devServer` hold the wrapper *invocation*** — `bash <scriptsDir>/<name>.sh`, repo-relative and unquoted, because commands are executed from the repository root and every path in the configuration file is repo-relative. `deploy.command` takes the same form on its own object.
- **The wrapper file holds the raw command line** and **prints its own verdict** — `PASS: <name>` or `FAIL: <name> (exit n)` — so a caller never appends an exit-code probe to it. That compound form is exactly what stalls an unattended run on a permission prompt, and a wrapper that reports its own result removes the reason to write one.
- **`build` and `depInstall` stay raw, unwrapped and deliberately not allow-listed.** They are human- or orchestrator-run rather than agent-run; wrapping them would hand an agent a script path it is permitted to execute, which is what those two must not have. The generated profile's rationale block states this rather than leaving it to be inferred from an absence. `depInstall`'s raw line is nonetheless **anchored** at the manifest detection found it in (§4), because it is executed from the repository root like every other configured command.
- **Every wrapper anchors itself, then forwards its arguments.** It resolves its own directory from `${BASH_SOURCE[0]}`, asks git which checkout that directory belongs to and runs there — so the repo-relative form, its absolute twin and a sibling worktree's own copy all run at the root of *their* checkout, which is what makes "commands are executed from the repository root" true for a wrapper an agent invoked from a subdirectory. Whatever arguments it was given go to the **last** command of its raw line — and what that command makes of them is the command's own property rather than the wrapper's: a test runner usually takes a bare path or name filter, so `bash <scriptsDir>/test.sh <path>` filters that run, while a line ending in a sub-command's own flags takes none (`ctest` needs `-R <regex>`, and a `cargo clippy … -- -D warnings` line forwards into the compiler's arguments). Each wrapper says so at the line, so the shape is read where the raw line is. A directory that resolves to no checkout gets one message and a non-zero exit and **no** verdict line: nothing ran, so there is no result to report.
- **`start-dev-server.sh` is the wrapper with no verdict**, because a long-running process has none to give. Its first argument is an optional port, numeric or a usage error, which reaches the command on one channel: exported as `HARNESS_DEV_SERVER_PORT`. The wrapper shifts it off before forwarding the rest, so the raw command line is never handed the port positionally — a server that takes its port only as an argument has to name that variable on its raw line. **One step runs to completion before the launch**: a pre-start line, rendered from `commands.build`'s raw line where the dev-server body is a detected line that serves pre-compiled output (`npm run start`, `npm run serve` — never `npm run dev`, which rebuilds itself), and the shell no-op `:` everywhere else, which is every other wrapper, an adopter's own raw `commands.devServer`, and a pre-compiled line whose manifest declares no `build` script — that last case being the one `init` reports as a note, naming the two ways out of it, declaring a `build` script or pointing the key at a watch-mode line. It is synchronous and above the launch rather than chained into it, because a `build && serve` backgrounded as a list makes the printed pid a subshell a caller's `kill` does not reach past. Its output goes to the caller's stdout rather than to the log file below, ahead of the pid and log lines, and the wrapper does not return until it finishes. A pre-start step that fails is reported by the wrapper's own `harness_fail` — one message, a non-zero exit and **no** pid line, since the server was not launched. Everything below it is unchanged: it starts the command in the background with both streams to `${TMPDIR:-/tmp}/harness-dev-server-<port>.log` and prints the pid and that path, which is what a caller checks liveness against and reads a failed start out of. It exits non-zero **only** if the launch itself failed: a server that has started but is not answering yet is success, and probing until it answers is the plugin's own `scripts/poll-dev-server.sh` rather than a second poll living in a file the adopter edits.

**Which wrappers are written.** `typecheck.sh` and `test.sh` for every one of those two keys that holds a command line, because those two are what "this change is done" means — the selection is what the value decides, not whether the key matters. `start-dev-server.sh` only when a dev-server command resolved, and `deploy.sh` only when the configuration carries `deploy.command`, which `init` does not generate this release — writing either one anyway would put a path in the profile that nothing runs. **Two values are not command lines, and each gets no wrapper and therefore no allow entry, by a different route and with a message of its own.** A key still holding the placeholder `init` writes for a command it could not detect: the placeholder stays visible where the configuration check and `doctor` both report it, and the warning says to set the key. And `commands.typecheck` answered `<none>` (§4, `docs/config.md` §5): the configuration check passes it as answered, so its warning states what the repository decided and what **this run** did about it — *this run wrote no `typecheck.sh` and allow-listed none* — with the residue named rather than denied: a `typecheck.sh` an earlier run wrote is left where it is, since wrappers are `create-if-absent` and nothing deletes, and the permission entries naming it are removed only by `init --force`, which regenerates the profile. It deliberately does not tell the adopter to fill the key in, which would be an instruction to undo the answer. The sentinel is recognised on that one key: written into any other `commands.*` key it is a literal command line, wrapped and allow-listed like any other, and the configuration check warns that it will be run.

**Where a wrapper's body comes from**, in the one precedence that cannot produce a circular pair: a **raw** line already in `commands.<key>` wins, because an adopter who edited it to a real command line meant it; otherwise, when the configured value *is* this wrapper's own invocation — the normal state after a first `init` — the body is stack detection's raw line; and when neither resolves, the body says which key to set and exits non-zero rather than appearing to have run a check it never ran. A body that would run the wrapper itself is refused outright, because the failure mode of missing it is a run that hangs rather than one that reports anything.

That first arm is now **reported rather than silently blessed**, at all three sites that can see it: `init` warns as it inlines the raw line into the wrapper, `config set` warns as the value is stored — and names the **write that has to precede** the corrective `set`, because at that boundary the key was the placeholder and no wrapper was written for it yet — and `doctor`'s `command-wrappers` check (§7) grades it on every later run. The value is stored verbatim and the wrapper runs it once `init` has inlined it — what the report names is that the permission profile allow-lists `bash <scriptsDir>/<name>.sh` and not the raw line, so an agent told to run the configured string as written is refused on it. **That inlining has a condition, and the message carries it:** wrappers are `create-if-absent` (§3), so a plain re-run writes one from this line **only while the file is absent** — the hand-fill boundary's own state, where the key held the placeholder and no wrapper was written for it. Over a wrapper already on disk a re-run keeps the file and discards the body it just computed, so that arm is `init --force`, which copies the file to a `.bak` before replacing it, or the file deleted and `init` re-run. Then, and only then, set the key to the invocation. Setting it first leaves the precedence above nothing to inline — the raw line is gone from the key and detection only ever produced the placeholder — so the wrapper is written to fail and the adopter's command line is lost. One condition and one sentence serve all three, so the three cannot come to describe one defect differently.

**Two families land in `scriptsDir`, and only one of them is generated.** A **wrapper** is generated: its body is a command line detected for or configured by this repository, so `init` renders it and the configuration holds its invocation. An **outer-loop script** — the run watcher, the git wrappers, the worktree tooling, the docs-retrieval server launcher, the scratch runner and the shared library they all source — ships fixed and is copied byte for byte, because it reads `harness.config.json` *at run time* instead of carrying values frozen in when `init` ran; a guard whose protected-branch set was baked into a file at generation time enforces the wrong set the moment that list changes, and does it silently. The permission profile treats the two differently as well. Every wrapper that is written is allow-listed (§6), because the whole reason it exists is that an agent runs it. An outer-loop script is allow-listed **only** when its row in the shipped table marks it agent-invocable — true of the git wrappers a dispatched agent commits, pushes and refreshes its branch through, and of `scratch-run.sh`, which runs a dispatched agent's language probe or mutation check in the interpreter that file's extension names and refuses any argument that does not resolve inside `<state_dir>/scratch/`; false of everything the watcher process, the agent runner or a person starts — the agent runner starts `docs-search-server.sh` from `.mcp.json` when `docs.retrieval` is on, and its one tool is granted by the retrieval half of the profile (§6) rather than by a script entry. That flag records what a script is **meant** to be run by and decides the profile; it is not what puts the rest out of reach. The plugin's script-allowlist guard grants independently of the profile — it auto-allows a `.sh` under `scriptsDir` whose basename it does not deny, so absence from the profile withholds nothing on its own. That allow is bounded, and by the command rather than by the file: the guard scans the whole command string and withholds it when anything — a commit subject included — carries `$(…)`, a backtick, `|` (hence `||`), `<`, a braced expansion other than a bare `${IDENT}`, or a `>` that is neither a descriptor duplication (`2>&1`, `>&2`, `2>&-`) nor a redirection to the literal `/dev/null`, and refuses outright any `.sh` token carrying a `$` in any spelling. What makes a destructive script unreachable is that guard's `DENY_SCRIPT_BASENAMES`, which carries the watcher, its restart wrapper and the worktree sweep; a row that must not be agent-runnable needs an entry there **as well as** `agentInvocable: false` here. The flag sits in the same table that writes the files, so a profile cannot name a script `init` did not write, nor one it wrote for something other than an agent to run.

## 6. The failure modes the permission profile encodes

In print mode a tool call that matches neither `allow` nor `deny` does not prompt and does not fail — it hangs, and the run parks with no diagnostic. Every shape in the generated profile is the way it is because some run already paid for the alternative, and the generator is built so it cannot emit an entry that stalls: an entry carrying a quote or a shell operator is refused before the profile can be written. Which side the value came from decides how the refusal reads. A repository-side value every entry is built from — the checkout path, `projectName`, `scriptsDir`, `stateDir` — is screened first and exits `1`, naming the value and the remedy that fits it: rename or move the checkout, or set the key in `harness.config.json` and run `init` again. Only what survives that screen — an entry this CLI or its shipped template produced — is an internal fault (`2`).

- **Wrapper paths are unquoted literals.** The allow-list guard matches the raw command string, so a *quoted* path fails a `*.sh` match, falls through to a prompt, and stalls.
- **One command per entry, never a compound.** A joined block matches no entry and is refused where each of its commands would have succeeded on its own.
- **The checkout *and* its sibling worktrees.** A glob that misses the worktree a run is executing in does not fail loudly; it silently skips whatever phase needed the path. The worktree entries are therefore unconditional — a single-checkout adopter simply has no sibling for them to match — rather than a second template.
- **Every wrapper is allow-listed in three forms, not one:** the repo-relative invocation an agent runs verbatim from the repository root, its repo-root-absolute twin for a caller that resolves the path first, and its sibling-worktree twin. A profile carrying only the absolute form would leave the configured verification command matching nothing at all. The forms are derived from the wrapper table, never by parsing a `commands.*` value back into a path — that value may legitimately be a raw command line, and parsing it is how the three views drift apart. The agent-invocable outer-loop scripts (§5) are emitted through the same builder and take the same three forms, and they land in `allow` rather than `ask`: they sit on the unattended commit path, and because `ask` is evaluated first, an `ask` there *is* the stall.
- **No browser-namespace `deny`.** A deny is evaluated before any allow and cannot be overridden, so a namespace-wide deny would revoke the interactive-test agent's own grant along with everyone else's. The browser closure is made per agent, by each agent definition's `tools:` allowlist — which is also why an agent added without a `tools:` field silently re-opens browser access.
- **No `hooks` key.** The plugin ships its own guard hooks; they fire from the plugin, resolve their own root and append to the adopter's hooks rather than replacing them, so writing them into settings as well would run each guard twice. The template says so in a comment field, so the omission reads as a decision rather than as something to fix.

The interactive-test wiring is a **fragment merged into the base** when the QA phase is on **and** `qa.driver` is `web-playwright`, not a second full profile — two full files would drift the first time an entry was added to one of them. Its two keys do different jobs and both are needed: one starts the servers the repository's MCP wiring declares, the other gates which of their tools may run. An un-loaded tool stalls a print-mode run rather than failing it, so the two are checked against each other in both directions.

Both conditions are the gate, and the browser block of the repository's `.mcp.json` (§3) is gated on the same one, in the same run: with a **mobile** driver neither the fragment nor any browser block is written, and `init` says so in its notes. The two mobile variants of the interactive test agent ship declared-not-implemented with built-ins-only tool allowlists, so a fragment would start servers no agent can call and a `.mcp.json` browser block would be wiring nothing enables. The docs-retrieval half is gated the same way on its own condition, `retrievalApplies` — `phases.docs` and `docs.retrieval` both true — which gates both the `harness-docs` entry in `.mcp.json` and the retrieval profile fragment `settings.autonomous.retrieval.json`, whose `enabledMcpjsonServers` names `harness-docs` and whose allow entry is `mcp__harness-docs__search_docs`, in the same run; the two halves are independent, so a mobile-driver repository with retrieval on gets a `.mcp.json` holding `harness-docs` alone. Gating one side of either half alone is the un-loaded-tool stall above, so each half's two sides move together, and turning retrieval on later is the configuration change and forced re-run in §2's fenced block under "The interaction rule". For the browser half, gating one side alone is worse than gating neither — it leaves the profile starting a server the repository never declares, which is the un-loaded-tool stall above rather than a failure — so the two move together. Turning the driver (or the phase) on later is a change to `harness.config.json` followed by `init --force`, and `init`'s own note says so where an adopter meets the omission: set the value in the file — by hand, or with `config set qa.driver web-playwright` / `config set phases.qa true`, each of which copies the file to a `.bak` sibling before replacing it — then re-run with `--force`. The two halves are not symmetrical, and the phase one leaves a value behind: `config set phases.qa true` arms the phase and writes **no `qa` section at all**, so the driver is left unchosen. The command says so in the same breath as it arms it — the structural check runs over the result of the edit and names `config set qa.driver <value>` — and `doctor`'s `config` check repeats it on every later run, because nothing else will: `--force` cannot supply the value, `init` reading `harness.config.json` and never rewriting it (§3). The `--force` is what moves the half a plain re-run cannot: `.mcp.json` is `merge-json` and would be merged in, while the permission profile is `create-if-absent` and would be kept, leaving the profile starting none of the servers `.mcp.json` declares — the one-sided state above, and so a stall rather than a failure. No flag is part of that remedy, and none needs to be: `--force` regenerates the profile from the configuration **in effect**, which is the file `init` reads on every run and never overwrites (§3), so the value just set is the one both halves are wired from. Everything `--force` regenerates gets a `.bak` sibling first.

The deploy entries live in `ask` rather than `allow`, so a deploy stays a decision a person makes. Because `ask` is evaluated before `allow`, **all three** forms are asked about: asking about one spelling would leave the other two running unattended.

## 7. `doctor`

Checks a wired repository and reports everything wrong with it, rather than only the first thing — every check is evaluated whatever the earlier ones answered. It takes two options of its own, both described at the end of this section and both off by default, and neither moves the exit status: `--test-notification` delivers a message, `--check-registry` reads package metadata from the registry. With neither given, nothing it does reaches outside the repository it was aimed at at all.

**The exit status is the contract:** `0` when no check failed, which includes a report whose only findings were warnings, and `1` when at least one check failed. A warning names something worth fixing that does not stop a run; a failure names something that does. An adoption an operator considers finished can still exit `1`, and one check is written to: `remote` fails a repository the flow has nowhere to create a working copy from (below). The contract is about whether a run can happen here, not about whether the wiring was done. `--quiet` drops the PASS lines; the WARN and FAIL lines still print on stderr and the counts summary on stdout, whatever the flags are — as does the `--test-notification` `would run:` preview under `--dry-run`.

Nothing is repaired and nothing is written, beyond a temp file the writability probe creates and removes inside the configured state directory. No MCP server is started and no browser is launched: reachability is command resolution on `PATH`, plus — under `--check-registry` — one read-only registry metadata query per pinned MCP package, which fetches and installs nothing.

| `repo-registry` | this repository is recorded in the machine-local registry of installed daemons |

The list is also the order of evaluation and of the report, and a fix works down it the same way: a failed `git` check makes every question below it unanswerable, and an unreadable profile makes the three profile checks unanswerable, so the first failure is almost always the one to act on. A check whose preconditions did not hold says so rather than guessing. Two placements in that order carry a reason worth stating. `jj-repository` sits immediately under `git` because it is that check's own question one step on — `git` establishes that there **is** a work tree, this says what shape of work tree it is — and every branch line below it is qualified by that answer, the detection rung a detached `HEAD` costs and the caller set the committed hook actually reaches. And `pre-push-guard` and `protected-set` close the branch block under `base-freshness`, because they ask the two remaining questions about the same value from opposite sides: whether the guard on disk is the one the configured name describes, and whether the configuration still names branches this repository has. They come after the trio rather than before it so that a reader who has just read three lines about one name reads next what enforces it.

Which severity a check carries is a decision, not a default:

- **The run watcher's absence is a warning**, because `init` writes it and one `init` writes it back: an absence means the file was deleted or `scriptsDir` moved, and grading that a failure would make an opt-in daemon's asset decide the exit status of a repository that runs fine in the foreground. A **missing artifact directory** is a warning for the same shape of reason: `init` creates what is missing and rewrites nothing, so it is the state a repository is in between turning a phase on and the next `init`.
- **`setup-analysis` is a warning in every state it can report**, so it never moves an exit status by itself while it still says what a run there will find — whether a freshly wired repository exits 0 is `remote`'s to decide, below. It sits beside `artifact-tree` because the two answer the neighbouring halves of what `init` wrote: the directories a run puts artifacts in, and the documents the agents it dispatches read their rules from. It reports four facts and grades no prose — a configured `layers[].conventions` path with no document behind it; a configured `layers[].path` naming no directory, which is the scope every dispatched agent is handed, so an agent scoped to it is returned no files and reports having found nothing wrong; a document that is still an untouched skeleton by §3's two-part test; and the setup-pending banner still present in `.claude/CLAUDE.md`, which is every session in that repository being told on every turn that setup is unfinished. Whether a rule somebody wrote is a *good* rule is not a question this command can answer, and a check that tried would turn a repository red over a document one person wrote and another would have written differently. Every one of the four names a remedy that **does not require the analyze command**: replace the guidance block by hand, delete the banner block by hand, or correct the `layers[].conventions` or `layers[].path` value with `config set layers` — a warning whose only route out is a command the adopter declined is a warning they can never clear. The document set is the one `init` derives — every `layers[].conventions` value, deduplicated, plus the shared cross-layer document whether or not a layer names it — so the two cannot disagree about which documents should exist.
- **`task-offer-rules` is a warning in every state it can report**, and the state it exists to make visible is a silent one: the change-request fence in `.claude/CLAUDE.md` fails closed, so a rules file that is not there turns the offer off with no error, no artifact and no line anywhere. What is lost is the offer and never the work — every request is still carried out, in the session that receives it — so grading it a failure would turn a repository red over a feature it can run entirely without. It warns in both directions. A fence pointing at nothing is one; so is the reverse — the rules file on disk with no fence naming it, which is what an already-wired repository comes out of an upgrade `init` holding, because the rules file is planned on every run and an existing `.claude/CLAUDE.md` is kept as it stands by every unforced one. Only a repository carrying neither half passes. The remedy for a missing rules file is one `init`, which re-creates it under create-if-absent and touches nothing else; for a missing fence it is the `## Where a change request runs` section added by hand, or `init --force`, which re-renders the whole project file after a `.bak` and costs every section `/harness-analyze` filled — a choice, which is why the warning names both.
- **`layer-profile` is a warning in every state it can report**, for `setup-analysis`'s reason: an unreviewed profile is a repository whose flow runs, with worse routing. What it grades is a **conjunction**, and that is the point — `layers[]` carrying no row scoped below the repository root is not a finding on its own, since `monorepo` writes such a profile deliberately and so does an adopter who decided this repository has one scope. What tells that profile from a placeholder is the `detection` record beside it (§4), so it warns on the four shapes of one state: a record naming the `flat` unrecognised-layout fallback, a record whose signal is `forced` — `--preset` decided it and no row was evaluated — no recorded preset — no `detection` record at all, or one that holds only a review — which is a repository wired by an earlier release or a hand-edited file, and a record naming a preset whose **source root did not resolve**. That last shape is why the clearing arm reads `LAYERLESS_BY_DESIGN_PRESETS` (`cli/src/detect/presets.ts`) rather than "any preset but the fallback": `monorepo` writes one catch-all row as a decision, while every other preset resolves a source root and writes that row alone only when the directory was absent — a `pubspec.yaml` with no `lib/`, a Gradle project with no `src/main` — which `init` warns about once and nothing else repeats. **The by-design arm says what `init` said**, in the same terms: every dispatch in this repository is routed to that one layer, and per-package or per-module layers are `/harness-analyze`'s to propose — so an adopter who ran only one of the two commands has the whole state. It stays a **pass**, because it names what would propose a profile rather than a remedy to run, which is what separates it from the warn arms; no grade moves. The **`tests` row does not count as scoped here**, and `init` gates that one-time warning on the source rows alone for the same reason: every preset splices a test row in wherever its toolchain's conventional test root exists (§4), independently of whether a source root resolved, so a repository whose only row below the catch-all is `tests` has the unresolved implementation profile both channels report. It is deliberately **blind to the conventions documents**: `setup-analysis`'s skeleton warning above was the last indirect trace that a fallback profile had never been examined, and `/harness-analyze conventions` clears that by filling the documents, leaving `doctor` green about a profile nobody looked at — so this check reads no document and that command does not move it. Whether the profile is a *good* one is not asked, for the prose reason `setup-analysis` carries. Two things clear it: the `layers` target of `/harness-analyze` recording its verdict — all three verdicts, the two declines included, because what is graded is whether the profile was considered rather than what was concluded — or that same record written by hand with `config set detection.review`. Not `init --reset-config`: it rebuilds the whole configuration from detection and the flags, keeping only `appDir` (§2), so clearing a cosmetic warning that way costs every hand-set value.
- **`layer-drift` is a warning in every state it can report** too, and on the same grounds — a directory routed to the catch-all is worse routing, not a stopped run. It is **gated**, and the gate is the check's own subject: where `layers[]` carries no row but the catch-all every directory would qualify and the report would be the whole tree, so it reports **not graded** there and leaves that state to `layer-profile` above, to be reported once, as itself. Where it does grade, it looks in **two** levels of the configuration rather than one — the application directory, and every proper ancestor of a configured layer path at or below it — which is what reaches a drifted sibling *inside* `src/`: the ordinary shape `init` writes is `appDir` at the repository root with layer paths under `src/`, so `appDir`'s only child is `src` and nothing beneath it would otherwise be a candidate. The exclusions are deliberately short — dot-directories, `node_modules`, the configured `stateDir`, `scriptsDir`, `githooksDir` and documentation root, and any directory the repository's own ignore rules already exclude — because every one of those is either a directory the harness itself configures or a declaration the repository has already made, where a longer built-in list would be this command inventing an opinion about the adopter's tree, and the gate is what removes the noise. It reads `detection.review` **for reporting, never as a gate**: a recorded verdict does not silence it, for the reason it always had — a verdict describes the profile at the moment it was reviewed, a layer hand-added afterwards is exactly the drift this check exists to name, and the record is `layer-profile`'s to clear on and nothing else's — while where one exists the warning names that verdict and its date, so an adopter can tell an already-declined directory from drift that appeared since. **The remedy splits on the same record**, and both arms are `cli/src/core/layerGapRemedy.ts`'s single spelling, the sentences `init`'s gap note prints (§2), which is why that note and this bullet are one statement rather than two. With **no** record: `/harness-analyze` answered `skip` for every already-filled document, never the `--yes` spelling, which takes `merge` on all of them and rewrites documents nobody asked to touch. With a record: `config set layers` leads, since it is the whole of the change for a directory that is a real layer, and re-running the analyze command is named only for the case it is worth anything in — the tree has moved since that review — because over the tree it already read it re-derives the decision the file holds. The profile itself is applied through `config set layers` either way.
- **`notifications` never fails**, whatever it finds. Delivery is opt-in by design (`watcher.md` §6) and a repository with none configured runs everything, so the worst grade is a warning — one for a settings file that exists with both arms empty, one for neither file existing. Both say what an unconfigured run actually gets: a macOS desktop banner where one is available, and nothing at all on a Linux host. The check reports **which candidate file is in effect** — machine-local first, the repository's configured `pushEnvPath` second, the first that exists winning and the other then not read — by walking the CLI's one definition of that order rather than a second copy of it, and it names the other candidate and why it lost: below the winner it is shadowed however complete it is, above the winner it lost only by not being there. A config carrying **no `pushEnvPath`** has only the machine-local candidate, matching what the notifier itself reads there, so the report names no repository-side file and points the remedy at setting the key first. It **never prints a value**, from either file: the report names paths and the key names it found set, because a push URL is a bearer credential and a terminal scrollback is not private. It reads at most one file and creates nothing, the machine-local directory included.
- **`repo-registry` never fails either**, and one sentence settles that: the registry **is not consulted before starting a run** (`watcher.md` §5), so it is enumeration rather than a precondition and nothing it can report stops anything. A repository with **no entry** warns — no daemon has been installed from this checkout, so nothing polls its inbox and a file dropped there sits until something starts a run by hand (`watcher.md` §6 step 1) — naming `daemon install`; it is the ordinary state of a repository that runs in the foreground, which is why it is a warning and not a fault. An entry graded **stale** — the recorded checkout gone, no longer a repository root, or its unit file deleted — warns with the state named and both remedies: re-install from this checkout, or `daemon list --prune` to drop the row. The **count of other stale entries** on the machine rides along on every grade, so one run surfaces a machine that has drifted without making another checkout's move this repository's finding. The path, the parse and the staleness grading are the ones `daemon list` uses (§9), asked here rather than re-derived, so the two consumers cannot report one machine differently — and the read **writes nothing**, the machine-local directory included: pruning is the explicit verb's, never a read's.
- **`machine-footprint` never fails either, and it answers for the machine rather than for this checkout.** It names every repository in the machine-local registry — per entry the slug, `projectName`, `root` and state, and for an `ok` entry its model, effort, live-run count and the **per-repository** cap; a stale entry carries the state and the cap only — then how many are armed, stale and live. `repo-registry` directly above answers whether *this* checkout has a daemon installed from it; this one answers what else the machine around it is armed to run, and the two are meant to be read together: a repository correctly armed on a machine already running several others at high effort is a different situation from the same repository alone, and neither line says that on its own. An entry whose state is not `ok` is reported **stale** rather than counted as armed, graded by the four-state table `watcher.md` §7 holds and `daemon list` grades by (§9), so the two consumers cannot report one machine differently. The cap cell is the machine-local `watcher.env` value a daemon **inherits** unless its own environment overrides it — an override nothing readable from here reveals, which the cell states rather than papering over — and `MAX_PARALLEL_RUNS` is per repository either way. A registry that is empty, unreadable or hand-edited into something this release does not parse warns once naming both readings, because failing open cannot tell them apart; a registry whose every entry is stale warns naming `daemon install` and `daemon list --prune`. **It never fails**, for `repo-registry`'s reason — nothing in the registry is a precondition for a run (`watcher.md` §7 `### What it is not`), so a file that cannot be read degrades to a warning and never to a fault — and it **writes nothing**, the machine-local directory included: pruning is `daemon list --prune`'s alone. What it does not bound is burn rate — the per-repository cap × model × effort is the adopter's call, and several concurrent high-effort runs will exhaust a rate-limit window that one would not (`watcher.md` §4).
- **`daemon-path` never fails either, and what it grades is a *file* rather than this machine.** `doctor` runs in a login shell, where the adopter's package manager and agent CLI resolve by construction, so it can say nothing about the environment a service manager hands the daemon — except by reading the unit that environment comes from. It re-renders the unit through the same call `daemon install` makes (§9), so the label and the install path are that command's rather than a second composition of them, reads the installed file, and compares the `PATH` it carries against the binaries an unattended run invokes **by name**: `git`, `jq`, the watcher's `${HARNESS_AGENT_CLI:-claude}` — taken from the **unit's own** environment stanza and never from the shell `doctor` runs in, whose value the daemon never sees — and the **head of every command line a run executes**, which lives in one of two places. A `commands.*` key holding a raw line contributes that line's own head — the leading word `setup-worktree.sh` has to resolve, the rest being arguments — and so do the unwrapped `build` and `depInstall` (§5). A key holding the **wrapper invocation** contributes `bash` read that way, the executable line sitting inside the wrapper — so a **second** head is taken, from the **raw command line inside that wrapper file**: that is the binary the daemon actually needs, and grading the value alone left every adoption whose wrapped keys are all in that form with its whole toolchain ungraded. Both are reported, `bash` against the key and the toolchain binary against the key **and** the wrapper file it was read from, because both are things the daemon resolves. The set is still derived from the configuration rather than listed, because a hardcoded `npm` would be wrong for every adopter whose package manager is not npm. Only the wrapper's **contents** are read: its path is composed from the wrapper table and never parsed back out of a `commands.*` value, which is §6's rule and the reason the three views do not drift. `deploy.command` is graded by neither route — no daemon-launched run deploys. **Every binary is reported with the source it was derived from** — `npm (commands.test → scripts/test.sh)` — which is what distinguishes a working unit from a broken one on the page rather than in a run that has already failed; on the report Finding 66 measured, the line came back byte-identical across both. **A command line no binary name can be derived from is named as ungraded** rather than silently dropped — an unrecognised wrapper body, a file that will not read, and a line whose head is not a binary: a leading `VAR=value` assignment is stripped the way a shell strips it and the command behind it graded, but a head that is a shell builtin, which is what a compound line (`cd app && npm test`) presents, resolves through no `PATH` at all and is reported rather than warned about — and the naming rides on the pass as well as the warning, the pass qualifying its own universal claim in the same breath, because a check that could not see a file it grades has not reached every binary a run invokes. **A wrapper the config invokes and no file backs is named in a clause of its own**, apart from those three: their one remedy is to reduce the line in the file, and a file that is not there has no line to reduce and nothing to read, so folding the two together printed an instruction that cannot be followed. That clause names `init`, which writes wrappers create-if-absent, and says what else the absence costs — every dispatch of that command fails, and the permission profile allow-lists a path with no file at it — which nothing else in the report says, `command-wrappers` grading the configured value rather than the file. A unit carrying **no `PATH` key** warns: it is the state every unit installed before that key shipped is in, and the four directories launchd then supplies reach neither a Homebrew toolchain nor `~/.local/bin`. A unit whose `PATH` **misses** a required binary warns naming each one *and the directory it actually lives in on this machine*, which is what shows an operator that their shell and their daemon disagree. Both remedies are the same and both are operator steps — `daemon stop`, then `daemon install --force`, which re-renders from the shell it is typed at, plus the `systemctl --user daemon-reload` line that prints on systemd — which with an unaffected foreground run is why it never rises above a warning. Two states are **not findings and pass silently**: a host with no service manager, and a checkout no daemon has been installed from. The second is `repo-registry`'s line, directly above it, and reporting it twice would double the report of every repository that runs in the foreground.
- **`command-wrappers` is a warning in every state it can report.** It grades the four wrapped keys — `commands.typecheck`, `commands.test`, `commands.devServer` and `deploy.command` — and warns for each one whose value is not that key's wrapper invocation, which is the state the hand-fill path leaves behind: the raw line is what the adopter typed, the wrapper is what it was inlined into, and `bash <scriptsDir>/<name>.sh` is what the permission profile allow-lists, so an agent told to run the configured string as written is refused on it. It never fails, for `profile-paths`' reason: the repository still runs in the foreground and the remedy is one `config set <key> "bash <scriptsDir>/<name>.sh"` — but only once the wrapper already carries the configured line, since that `set` is what removes the line from the key. Where it does not, the write that puts it there comes first, on §5's condition: a plain `init` where the wrapper file is absent, `init --force` or deleting the file where it is not. Three neighbouring questions are **not** its: a key still holding the placeholder `init` wrote is `config`'s line directly above, reported there once; `commands.typecheck` answered `<none>` holds no command line at all, so there is no invocation to grade against a wrapper nobody wrote — `config` passes it as answered, and this check names it in its own pass text as *an answer rather than an unfilled key, so no check reports it as one*, which is what keeps an answered key from reading as an unfilled one; and whether the wrapper exists under `scriptsDir` with its three allow entries is a separate question this check does not put — it is `command-permissions`' line directly below — since a repository can answer all of those clean and still have the configured string refused. With no wrapped key holding a command line it reports **not graded**, saying of each remaining key that it *is unset or still holds the placeholder init wrote* and naming any answered key beside them, rather than a pass that would read as coverage.
- **`command-permissions` is a warning in every state it can report**, for `profile-paths`' reason: the repository still runs in the foreground, and the profile is a file the adopter owns. It puts the question the two lines above it leave open, the three narrowing on one key in reading order — `config` grades the **slot** (is it still the placeholder `init` wrote), `command-wrappers` the **value** (is it the wrapper invocation), and this one the **entries** that value implies: does the profile carry the wrapper's own permission entries, and is the wrapper file readable under `scriptsDir`. The state it exists for is invisible to both of them, because `init` writes those entries from the commands it **detected** — a key filled in afterwards adds none, and no ordinary re-run regenerates the profile (§3), so a repository can hold a valid config whose configured string is allow-listed nowhere. What that costs is §6's stall rather than a failure. It grades only a key that is **set, not a placeholder and not answered `<none>`** — an answered key implies no wrapper, and so no entry for this check to look for, and it is named as answered in whichever of this check's pass sentences the repository reaches; with none it reports **not graded**, saying of each remaining key that it *is unset or still holds the placeholder init wrote* and naming `config` as the line that covers the placeholder, with any answered key named beside them in the words the line above uses, rather than a pass that would read as coverage. The expectation is **re-derived** — the profile generator `init` itself uses is called and the wrapper entries read back out of what it produced — so this check cannot come to disagree with the generator and keeps no second copy of the three forms (§6); each rendered entry is looked for in **its own** list, an `ask` entry in `ask` and an `allow` entry in `allow`, because a wrapper entry that moved into `ask` is the stall rather than the grant. **A missing wrapper file and missing entries are two sentences, because they are two repairs**: a wrapper that is not there is written by a plain `init`, create-if-absent from the line its key holds, while the entries need `init --force`, which regenerates the profile from the configuration as it now stands after copying the current one to a `.bak` sibling and carrying the plugin-root entries forward. The missing entries are also printed one per line, grouped by the list each belongs in, so an adopter who would rather not re-run can paste them. Nothing underivable is guessed at: no root, no config, no readable profile, and a generator that could not render are each reported **not evaluated** naming the check that owns that input, because a check that cannot derive the expectation may not report the profile as wrong.
- **`command-resolves` is a warning in every state it can report**, for `command-wrappers`' reason: the repository still runs in the foreground, and installing a tool is an operator step. It puts the one question the three lines above it leave open. They grade the slot, the value and the entries; this grades **what the value runs** — a repository can answer all three clean while every one of its wrappers exits 127 on every invocation, because nothing has yet asked whether the command *inside* the wrapper is installed. So it takes the **head of every configured command line**, with `command -v` semantics, from the two places such a line lives: a `commands.*` value that is itself a raw line contributes its own first token, and a key holding the wrapper invocation contributes the first token of the raw line **inside that wrapper file**, read off the file — a leading run of `VAR=value` assignments stripped the way a shell strips it. It grades **all four wrapped keys, `deploy.command` included**: the reason `daemon-path` leaves `deploy` out — no daemon-launched run deploys — is that check's own and does not hold here, the shell a deploy is dispatched from being the shell this grades. Every head is reported with the source it came from, a bare key for a raw line and `<key> → <path>` for a wrapper's, and a head that does not resolve names both remedies — install the tool, or correct the raw line that source names. **Four classes are reported *not graded* rather than warned about**, each with why: a head carrying a `/`, which a shell resolves against the filesystem and the directory the command runs in rather than through any `PATH`; a line that reduced to no binary name at all, which is what a shell builtin and a compound line (`cd app && npm test`) present; a wrapper body that would not read or that this release does not recognise; and a wrapper the config invokes and **no file backs**, which is a clause of its own because the other three are repaired by correcting a line and a file that is not there has none to correct. Three further states contribute nothing and are said so rather than left silent, since a universal claim is worth what its scope says: a wrapper whose body runs **no command at all** yields no head to grade and is `config`'s and `command-wrappers`' line between them; a key still holding the placeholder `init` wrote is not a command line and is `config`'s line, reported there once; and `commands.typecheck` answered `<none>` is not a command line either — it names no tool to install, so **no head is derived for it and this check demands no binary for it**, `config` passing it as answered and `command-wrappers` naming it in its own pass text. That last skip is taken on the key rather than on the value: the same string in `commands.test` is a command line, its head is graded here, and the config check warns that it will be run. With no graded head at all it reports **not graded** and names why, rather than a pass that would read as coverage; and no root, no readable config is reported **not evaluated** naming the check that owns that input. **The environment it grades is not `daemon-path`'s**, and neither finding subsumes the other: this asks the `PATH` of the shell `doctor` was typed at, while that one reads the `PATH` carried by the installed **unit file**. A binary that resolves here and not there is a daemon that dies on a command the operator can run by hand, and the reverse is a shell short of a tool the daemon has — two findings, each reported once, on its own line.
- **`profile-paths` is a warning**, and it asks "does any rule cover this repository root", not "is every path in the profile correct" — the profile is hand-tuned, and an adopter may deliberately have pointed a rule elsewhere. Complete absence is the signal, and it is what a moved or copied checkout looks like: the absolute entries are materialized at `init` time, so a relocated repository carries a profile whose edit, write, read and script rules match nothing here. A rule **covers** this root when it names it literally *or* when it is a pattern matching it — the sibling-worktree glob every generated profile carries names no worktree as a substring, so a run in one is covered by that pattern and does not warn. Which is the whole reason the distinction is drawn: the remediation this check prints is `init --force`, and running that inside a worktree would regenerate the committed profile against the worktree's own path and leave the main checkout named by nothing.
- **`plugin-permissions` is a warning, and it is the check that prints its own remedy.** A plugin root is machine-local and the install root carries the plugin version in its path, so no document can hold an entry naming it and one generated once would go silently stale on an upgrade (`plugin/scripts/README.md` states what does and does not block generating them) — the `permissions.allow` entries are an operator's to add, and until this check existed the requirement lived only in prose reached by already knowing to look. What a missing entry costs is a **silent stall**: a run that reaches a plugin helper with nothing matching parks with no error, and an agent whose read of a plugin file is refused improvises in place of the contract it was told to follow. So the check resolves **both** of the plugin's roots from the agent runner's own records — the install root from `installed_plugins.json`, and the root the runtime substitutes for `${CLAUDE_PLUGIN_ROOT}` from `known_marketplaces.json` plus the marketplace manifest that entry locates — **on every run**, which is what catches a version bump that has quietly invalidated entries added against the previous root — and, for each requirement the profile is missing, prints **the exact line to paste**, one per line and unquoted in the same form the profile's wrapper entries use, grouped by root with each group naming the record its root came from. What it requires: one `Bash(bash <root>/scripts/<name>.sh:*)` per helper script **at every graded root**, **only while `phases.qa` is on** — those scripts are that phase's alone, and with it off the check says nothing whatever about them — plus a `Read` grant at a runtime root that resolves to a directory the install root does not, which is **not** phase-gated, because instruction files and samples are read by every unattended run. Both roots are graded because the two call-site classes reach a helper by different routes — the agent resolves the root itself for one named in an instruction file, the runtime substitutes it for one named in an agent definition body — and on a `directory`-sourced marketplace those were measured 2026-08-26 to land on different directories, so an entry is needed at each; where they coincide, which is every git-sourced adoption, the two sets dedup to one. No `Read` grant over the **install** root is ever among them: measured the same day under a generated profile naming no rule over either root, sixteen reads from the install root succeeded while ten at the runtime root were refused, so requiring one at the install root would warn at every correct adoption forever. With nothing left to grade it reports **not graded** and names why, rather than a pass an adopter would read as coverage. The helper names come from **reading** each graded root's `scripts/` directory and taking the union, so they are declared once — in the plugin's own `scripts/README.md` — rather than copied into this CLI, and nothing here classifies a helper by its call site. A machine where the plugin is not enabled warns differently: it names the step (enable the plugin, then re-run `doctor`) and **prints no entry at all**, because every entry it could print would carry a path it made up — but it does say **how many** absolute-directory `permissions.allow` entries outside the checkout the profile is carrying that nothing there can grade, which is the same set `init --force` carries forward unverified on that arm (§3), so the disposition that grades nothing is not silent about the file it just read. It names the gap in the other direction too: an entry in the **helper form whose directory no plugin root on this machine resolves**, which is what an upgrade leaves behind, the install root carrying the plugin version in its path. Nothing else grades those, and no command removed one until a forced `init` began carrying forward only the entries at a root that still resolves (§3) — so they are named in every disposition that **grades** them, a pass included, and counted rather than named where no plugin root resolves at all, a check that resolved nothing having no basis to call an entry stale — and in neither case do they move a grade: the remedy is a deletion the adopter owns, and a check that failed over an entry costing nothing at run time is one adopters learn to ignore. Only the helper form is tested, because a `Read` granted over a reference implementation outside the checkout is correct configuration and naming it would be a false positive. It never fails, for `repo-registry`'s reason — a machine-local gap with an operator remedy — and it writes nothing, the runner's directory included.
- **`profile-deny-floor` is a warning** — a profile an earlier release generated is legitimately missing an entry, and a run short of one is worse-defended rather than unable to proceed. It compares against the **shipped template's own deny list** rather than a second copy of those entries kept in the check, so the floor has one declaration.
- **`jq` is a failure in both of its bad states**, and the second is the reason the check exists. Two shipped subsystems reach their configuration only through `jq` — the plugin's guards, and the outer-loop scripts `init` writes into `scriptsDir` — so an **absent** `jq` stops both, and the fix is a one-line install. A `jq` **older than 1.5** is worse to diagnose: both loaders use jq 1.5 constructs, so an old `jq` makes the load program a *compile* error rather than a missing binary, every configuration read fails, and both subsystems take their unresolvable-configuration path — a push to a non-protected branch refused, the commit guard asking, the remaining guards silent — while `command -v jq` succeeds throughout. `jq` present but not answering, or answering with a version string the check cannot parse, is a **warning**: it is installed, the harness may well work, and a repository should not go red over a string. The check reads no configuration and touches no repository, so it answers the same in a repository whose config is broken.
- **`ignore-rules` is a failure when the repository is hiding a file it commits**, and it is the only check whose remediation is a hand edit rather than a re-run. **What it grades is git's answer, not the block's layout.** Each run-artifact directory with a committed contract file is ignored by its contents with that README excepted, and for **every README the tree generator commits into such a directory** — the set it declares, not the negations the audited file still carries — the check asks git whether the path is excluded here; each one that is makes it fail, named. Deriving the subjects from the file under audit was itself a hole: a negation deleted by hand takes the path out of the file, and would take the question with it while the contents rule beside it goes on hiding the README. Direction is not read: a rule above the negation and a rule below it hide the file identically, and git resolves a path by the **last** pattern matching it — so a contents rule an adopter deleted and an older release's re-run put back at end of file breaks the pair exactly as a superseded directory rule above it does. The remedy the message names follows which of the two states the path is in: with its negation still in the block, the one line to move back above it or the superseded rule to delete, because no re-run removes a line (§3); with no negation left, a re-run of `init`, which merges that line back in at its position (§3). A probe git **could not answer** is a **warning** saying the property was not measured, never a pass — a check asserting a property it did not test is the fault this one was rewritten to stop. It keeps the diagnosis it already carried, which no property test reaches: a repository wired before the contents-plus-exception pair existed still carries the whole-directory rule it replaced, and the failure names that exact line together with the superseded comment lines above it, so one edit closes the whole thing. Two lesser states **warn**: that old rule with no pair beneath it yet — nothing is hidden until the next `init` writes the README — and the comment lines left behind on their own, which is what sends the next reader to re-add the rule.
- **`profile-browser-deny` is a failure**, and it is the only profile check that is. It is the one profile edit that silently disables a whole phase: a deny is evaluated before any allow and cannot be overridden, so a browser-namespace deny revokes the interactive-test agent's own grant along with everyone else's.
- **`jj-repository` is a warning in every state it can report**, and on a plain git repository it reports **not graded** in one line: there is no `.jj/` beside `.git`, so no `jj` manages this working copy and neither the hook gap nor the detection rung a colocated repository loses can arise in one. **That directory establishes that `jj` manages the working copy, not that the repository is colocated**: measured on **jj 0.44.0**, a non-colocated repository's `.jj/repo/store/git_target` holds `../../../.git` and `.jj/repo/store/git` does not exist, so that shape too keeps a real non-bare `.git` at the working-copy root with a `.jj/` beside it, and `probeRepoRoot()` grades it `repository` exactly as it grades a colocated one. The probe therefore separates the two shapes nowhere, the report calls no repository colocated, and the one clause that holds only of a colocated repository carries that qualifier itself. Older jj kept the store at `.jj/repo/store/git`, where a git repository underneath would have separated the two shapes; on 0.44 it separates nothing, which is why the version is part of the claim. Both shapes adopt: `init` on the non-colocated fixture exited 0 (`48 created, 28 ensured`), took the ordinary unborn-`HEAD` first-commit path (§2) with no refusal and no warning, and `doctor` afterwards graded `18 pass, 4 warn, 0 fail` — byte-identical to the grade both colocated fixtures received. No `jj` binary is looked for and none is run. What it says of a `jj`-managed repository is a coverage **split**, and both halves are stated as plainly as each other because reading one without the other sends an adopter to the wrong place. The committed `<githooksDir>/pre-push` is a *git* hook: git runs it on every push git performs, and a tool that implements push against the git backend itself, as `jj git push` does, performs no git push and runs no git hook — measured on one repository and one instrumented hook seconds apart, where `git push` fired it, `jj git push` did not, and the ref landed. The release that added this check bounded the hook's caller-agnostic claim at where git ends, in `cli/src/generators/githooks.ts`'s header. **The session-level protected-branch guard the plugin installs covers a `jj git push` that names a protected target**, refusing it with the identical decision `git push origin <protected>` draws — measured the same way, on `jj git push -b <protected>` — so that form is **not exposed**, and the caller the committed hook does not reach is a person at a terminal. The bound is carried with the claim: `jj git push` with no bookmark argument gives that guard no target token to judge, and its other arm — a push while `HEAD` is on a protected branch — cannot fire on a shape where jj leaves `HEAD` detached, so there **the argument-less push is refused by neither layer** and the forge-side branch ruleset named below is the only thing that covers it. The third thing it says is the detection rung, and it is the clause **bounded to a colocated repository**: there `jj` exports its refs and `HEAD` to git on every command and points `HEAD` at a raw commit id after every `jj new`, so the rung that reads the branch `HEAD` names cannot answer and the configured value came from a rung below it (§2), while a non-colocated repository exports nothing and keeps git's own `HEAD`, which costs that rung nothing — git there sees an unborn `HEAD` and an untracked working copy until something writes to it — reported as the state of *this* checkout right now rather than asserted of `jj` in general, since the answer flips at the next `jj new`. It repairs nothing and invents no jj-side hook, because there is none to name: it names the session guard, a branch ruleset on the forge as the only floor a person at a terminal cannot get around, and the two incantations that settle `defaultBranch` by hand. Every figure in this bullet was taken on one pair of fixtures on one jj version, which a later jj can move. It reads no configuration, so it answers the same in a repository whose `harness.config.json` is broken — which is exactly the repository an adopter is especially likely to be running `doctor` against.
- **`default-branch` splits**, because the two states it distinguishes are knowable to different degrees. A repository with **no commit at all** is a **warning**: `HEAD` names a branch that does not exist until something is committed to it, so nothing resolves and the configured value is unverifiable rather than wrong, and grading that a failure would turn a fixable state red. That state is narrower than it sounds: `init` makes the first commit in any repository it wires that had none — the one it created and the empty one it adopted alike (§2) — so a freshly wired repository normally arrives here already answerable, and what still reaches the warning is a run whose commit git **declined**, most often on a machine with no commit identity, or a repository wired by an earlier release. So the warning names that cause rather than only the commit — which, by the time it is read, is the act that has already been refused — and it names both ways to close it: set a commit identity with `git config user.email` and `git config user.name`, in the same words `init` uses when its own commit is declined (§2), and then either re-run `init`, which commits on the next ordinary run because the repository still has none, or commit by hand. A configured branch that, in a repository that **does** have commits, names neither a local branch nor an `origin/` remote-tracking ref is a **failure**: a branch review's diff base and the protected-branch guards are both taken from that value, and a name resolving nowhere makes the first a diff against a ref git cannot find and the second a gate that matches no branch and so stops nothing — it fails by *skipping*, not by erroring, which is why it is asked about here. Both resolutions pass, remote-tracking included: that is the ordinary shape of a clone that has never checked the branch out. The remedy the failure names is `config set defaultBranch <branch>`, with `git branch -a` to see what the repository has. **The question is not finished at the config value**, and the two lines below close it: `pre-push-guard` asks whether the guard on disk enforces the set this value resolves to, since a `config set` moves the key and not the rendered hook; and `protected-set` asks whether the other half of that pair still names branches this repository has, since the set the guards read is the union of the two and this check grades only one member of it.
- **`remote` is a failure, and it is the check that can make a freshly wired repository exit non-zero.** `create-worktree.sh` fetches `origin/<defaultBranch>` and creates every run's working copy **from that ref**, then pushes the new branch back to `origin`; that script refuses both of the states below in its own voice before it creates anything (`exit 2`, naming the remedy and this check), so a repository missing one still gets no worktree and nothing downstream — no phase, no agent, no commit — runs. For a drop into the inbox, the watcher then archives it as `failed_<timestamp>_<name>` and sends the `failed` notification (`docs/watcher.md` §1 step 8; the leg is driven in `docs/outer-loop-verification.md` → `## 1. The refusal matrix`), and no session runs. A run started **in place** — in the adopted repository itself — calls no worktree script, so it meets no refusal and reaches the end instead: `push-branch.sh` is non-fatal by contract (`docs/watcher.md` §2), so every push fails, every committer returns `pushed: failed`, and the flow still reports the branch done with every commit sitting locally. The same non-fatality covers a remote that exists and is unreachable or refuses, in either shape of run. The run captured in `examples/notes-app/` was started that way, in a scratch repository with no remote, and its own intake says so (`examples/notes-app/sdlc-harness/improvement_observations/feat_note_updated_at.md` → *"Every push in the run failed"*). The run's closing Done summary states the branch's push state — a branch-delivery line reporting the commit count and whether those commits reached the remote, re-derived from the tree at Phase D (`plugin/instructions/plan_orchestration_instructions_core.md` → `### D.2 Done summary`) — so a run that pushed nothing says so, while the wrapper's non-fatal exit, the committers' returns and the flow's completion are unchanged. A run ends at a pushed branch only when there is somewhere to push it. What this check adds is **when** that is said: before a prompt is dropped, rather than in the run log of the drop that failed. Two states fail. **No remote at all** is the first. **A remote with no `origin/<defaultBranch>` remote-tracking ref** is the second, and it is the one worth having a check for: `git remote -v` reassures while the ref the script actually names is absent, and a *local* branch of that name does not satisfy it — which is why this question is asked separately from `default-branch`, whose pass a local branch is enough for. Why it fails where `notifications` and `repo-registry` — whose remedies are hand steps too — only warn: neither of those is a precondition for a run to *begin*, and this one is. A repository adopted with `init --git-init` has no remote by construction — the default state of such a first adoption, not an edge case — so it is freshly wired and still exits `1`; the remedy is the adopter's, `git remote add origin <url>` and `git push -u origin <defaultBranch>`, or running the flow in a checkout that already has one. The check reads refs only — no fetch, no network call — so it answers the same offline.
- **`base-freshness` is a warning, and promoting it to a failure would be wrong.** It asks the one further question `remote` leaves open: not whether `origin/<defaultBranch>` exists, but whether it is **current**. A ref that exists and is behind the local branch satisfies `remote` completely, so the repository this reports on is one every other line is green about — and `create-worktree.sh` branches every run's working copy from that ref, so a run started there gets a base missing whatever was never pushed — the harness's own wiring, in the adoption this check was written from — discovered only after a planning phase has been paid for and the run has parked. It stays a warning because the run does *start* and parks cleanly, and because a check that failed a repository whose remote is a few commits behind is a check nobody keeps green. It names **both** remedies, because there are two states to be in when it is read: `git push origin <defaultBranch>` in the checkout holding the commits, which is the fix at the source; and, for a working copy that already exists and is already stale, `bash <scriptsDir>/refresh-branch.sh --local` — the one refresh route the protected-branch guard permits, for the reason that script's own header states. Two states are **not findings and report "not graded"**, each because another line owns it: no `origin/<defaultBranch>` at all is `remote`'s, directly above; and no local `<defaultBranch>` — the repository between `git init` and its first commit, and the clone that has the branch only as a remote-tracking ref — is `default-branch`'s, since neither holds anything the remote ref is missing. Like `remote`, it reads refs only and issues no fetch, so it answers the same offline — which means it compares against the remote as this checkout last saw it rather than making it current.
- **`pre-push-guard` is a warning in every state it can report**, and it is the only check that grades the file rather than the value. The three lines above it ask what the configured name is and what a run's working copy can be cut from; this compares the guard **on disk** with the set that configuration resolves — `protectedBranches` unioned with `defaultBranch` — by reading the `case` label the hook was rendered with. The hook is `create-if-absent` (§3), so it carries the set substituted into it when it was written, while `config set defaultBranch <name>` and a hand edit to `harness.config.json` both change only the config; the state it was written from is a measured adoption whose report was all passes and warnings while its hook **allowed** a push to the integration line and **refused** one to an ordinary feature branch, because nothing anywhere compared the rendered list to the value it was rendered from. Four graded states: the label matching the resolved set **passes**; a label naming a different set **warns**, saying that git runs the file and a push is therefore judged by the hook's set rather than the config's; **no readable hook** warns that nothing in this checkout judges a push at all, naming a plain `init`, which writes it because it is create-if-absent; and a hook carrying no label in the generated shape warns that it was edited or not written by this CLI, so what it protects cannot be read out of it. It never fails because the flow runs — what is wrong is which branch is guarded — and the true floor is a rule enforced by the host the repository is pushed to. Its remedy is `init --force`, which `.bak`s the hook and re-renders it from the config in effect, or deleting the hook and re-running `init`; **never `--reset-config`**, which would rebuild the whole configuration and cost every hand-set value. One thing it deliberately does not grade is whether `core.hooksPath` points at the directory the hook is in — that is `init`'s own warning, and saying it again here would report one fault twice.
- **`protected-set` is a warning in every state it can report** too, and it closes the branch block from the opposite side: it asks whether every branch `protectedBranches` **lists** still exists here, as a local branch or an `origin/` remote-tracking ref. The key is optional, and an **absent** one is graded all the same — the guards are rendered from the same schema default (`docs/config.md` §5) — but every line says which of the two it read, because a report telling an adopter the file "lists" an entry sends them looking for a line that is not there. The state it exists for is a guard permanently protecting a branch nobody will ever push to again — `config set defaultBranch <new>` moves one key of a pair the guards read together, so the abandoned name stays in the list, gets rendered into the next hook's `case` label and is resolved by the git wrappers on every call, with nothing ageing it out and nothing saying it is there. Three things are deliberately **not graded**, each because grading it would make one finding two or nag about a supported use: a **glob** entry, which names a namespace rather than one branch and is the documented way to protect a whole family with one entry; an entry equal to **`defaultBranch`**, whose resolution is that check's line above; and a **repository with no commit**, where nothing resolves at all and which state that is, is again `default-branch`'s to say. The first two are named wherever the grade lands, so an entry a reader can see in the file is never silently absent from the line. **A stale entry is reported and never removed**, and that decision is settled rather than pending: narrowing a protected set automatically is the one direction that fails unsafely — a tool that dropped an entry it could not resolve would unprotect a branch on the strength of a ref lookup — so the check names what it found and names the edit, `config set protectedBranches '<json>'` followed by `init --force` to re-render the guard from it, and the adopter makes it. It never fails because an over-wide set stops nothing, and a branch that does not exist *yet* is a legitimate thing to have listed.
- **`browser-wiring` asks about whichever driver is configured**, which is why the row above says *the application* rather than *a browser*. It reads the same condition the generators write on (§6), so a repository whose `qa.driver` is one of the mobile values **passes**, naming that driver: `.mcp.json` and the profile's interactive-test fragment are deliberately absent there, and warning about wiring `init` withheld would be a finding no adopter could clear. The four warnings above — an undeclared server, an absent `enabledMcpjsonServers`, a launch command that does not resolve, and, under `--check-registry` alone, a pinned MCP package the registry did not answer for — are asked only of the browser driver. A resolved launch command answers none of the fourth, so a default run says so where it passes: the declared servers are launched with `npx -y`, each pinned package is fetched from the registry on first use rather than installed by `init`, and this run did not check that it can be.
- **The three `retrieval-*` checks come last, under `browser-wiring`**, in the order each needs the one above it: the runtime, the models, then whether an index builds from both. Each **passes** with the same sentence where retrieval is off — `phases.docs` and `docs.retrieval` not both true — because no library, model or index is expected there; each is **not evaluated** where the repository root or `harness.config.json` did not resolve, naming the `git` or `config` check; and where retrieval is on, each **fails** when unsatisfied and names the same remedy, which is the command that installs the runtime and downloads the models:

  ```bash
  npx autonomous-sdlc-harness init
  ```

- **`retrieval-dependencies` grades the runtime the launcher runs**, `<machineCacheDir>/retrieval/runtime` — `${XDG_CACHE_HOME:-$HOME/.cache}/autonomous-sdlc-harness/retrieval/runtime` — installed at this CLI's version with every optional peer. It fails where that installation is absent, at another version or short of a peer, naming what is missing: `docs-search-server.sh` `exec`s that installation's `docs serve`, so without it the search server never starts. Whether the CLI running `doctor` can load its own peers is **not** consulted — the launcher never runs that installation, so a pass on it would be a pass on a server that never starts.
- **`retrieval-model-cache` fails when any model file is missing** from `<machineCacheDir>/retrieval/models`, naming the first five and counting the rest. A session loads the models with remote loading off, and an unattended run has no web access, so a file missing now is never fetched later.
- **`retrieval-index` builds the index in memory in a child process** — this CLI's `docs index --in-memory` (§11), bounded by a 600-second timeout because a real corpus embeds every chunk on this probe. It starts no server and writes nothing, so it keeps this section's promise that nothing is written. It passes with the child's one output line and fails with the last line the child wrote to stderr; where neither this installation nor the runtime can load the retrieval libraries it fails without spawning, pointing at `retrieval-dependencies`.

**`--test-notification`** sends one message, after the report and the counts summary, so a repository whose wiring is broken still gets its findings first. It goes out through **this repository's own `autonomous-notify.sh`**, resolved under the configured `scriptsDir` exactly as the daemon resolves the watcher beside it — so there is one place a message is built, with one credential precedence, one pair of delivery arms and one title format, and what you are testing is the thing an unattended run will actually use. The event word is `doctor-test`, which is deliberately none of the watcher's six lifecycle words (`watcher.md` §1 lists them; the script's own header is where that vocabulary is normative): the script delivers an unrecognized word under a generic title, so the message cannot be read as a real run's outcome. The script's exit status and its stderr lines are reported as it wrote them — it prints one line per arm that did not deliver and never prints a value — and an absent notifier is reported as a warning naming the path and `init`, with nothing sent. Under `--dry-run` it reports the invocation it would make and sends nothing; every refusal above still applies, so a dry run cannot report a send a real run would not have made.

**A default `doctor` run sends nothing**, which is why this is a flag: the command is safe in CI, in an `&&` chain and in the run daemon's own preflight, and a POST fired by every invocation would cost it all three. The flag **does not move the exit status** either — that stays `0` when no check failed — because a best-effort notifier that could not reach an endpoint is not a failed check, and a caller's condition has to mean the same thing whether or not the flag was passed.

**`--check-registry`** widens the `browser-wiring` check by one question and changes nothing else. For every server `.mcp.json` declares with `npx` as its launch command it looks the pinned spec up with `npm view <spec> version`, taking that spec from the declaration's own `args` rather than from a list kept here, and warns for each one the registry did not answer for, naming what `npm` printed. It starts no server, launches no browser, and fetches and installs nothing; where `npm` itself does not resolve on `PATH` the report says the question was not put, which is neither a reachable package nor an unreachable registry. It **does not move the exit status**, for the reason above. It is off by default for the same reason the send is — with it off nothing here touches a network at all and the answer is the same offline, which is what keeps the command safe in the three callers above — and it is the one of the two `--dry-run` does **not** suppress: a metadata read changes nothing, so there is nothing for a preview to withhold, and §1 lists only acts that do.

## 8. `config`

Reads and updates `harness.config.json`. The verb is required.

| Verb | Effect |
|---|---|
| `list` | Print the file as it stands, formatted |
| `get <key>` | Print one value, addressed by a dotted key path |
| `set <key> <value>` | Replace one value and write the file back |

`<key>` is a dotted path — `defaultBranch`, `commands.test`, `phases.qa`, `qa.portSeed`, `layers`. A list is addressed **as a whole**: `get layers` prints it and `set layers <json>` replaces it, never element by element.

`<value>` is read as JSON when it parses as JSON and as a plain string when it does not, so `set phases.qa true` stores the boolean and `set projectName '"3"'` stores the string. A value that would otherwise be read as a global flag is separated with `--`, which stops flag parsing.

`get` prints a string raw and anything else as JSON, so a shell can consume it directly, and it **exits non-zero when the key is not set**. An optional key with no value is absent from the file rather than written as `null`, and no declared default is filled in for it.

`set` refuses and writes nothing when the key is not one the file may carry — a typo is an error, not a new setting — when the value contradicts that key's type, or when the result would fail the structural check; every problem found is reported, not only the first. A dot-named state directory is refused there too, for the reason in §3 of `config.md`. It writes a `harness.config.json.bak` sibling before replacing the file **every time** — a path the managed `.gitignore` block ignores, so on a repository wired by this release the write leaves nothing untracked behind. A repository wired *before* the rule existed carries no line for it: the block is append-only and merged, so one `init` adds it in place without touching anything else in the file (§3), and until then the sibling shows in `git status` as an untracked file. `set` preserves key order and formatting, so the diff is the changed value and nothing else.

**A `set` of `defaultBranch` or `protectedBranches` also reports what the edit leaves behind**, because the branch guards read the two keys together: the protected set every guard resolves is `protectedBranches` unioned with `defaultBranch`, so setting one of them alone leaves the other in the set. Setting `defaultBranch` names what the sibling key holds while it is being set — unset and standing at its schema default, listing nothing, or listing the names it lists — and names it as a **report rather than an offer**: nothing removes an entry automatically and nothing will, because narrowing a protected set is the one direction that fails unsafely, so that edit is the adopter's. Both keys also get a hook half, which no `set` can act on and which is **read rather than assumed**: the committed `<githooksDir>/pre-push` is opened and the branch set in its `case` label is compared with the set this configuration resolves, so the report says one of four things about it. Where the label is **behind** the configuration — the state that decides pushes, because a push is judged by that file — it names the two routes that re-render it on demand: `init --force`, which copies the hook to a `.bak` and re-renders it from the config in effect, or deleting the hook and re-running `init`, which re-renders it because it is create-if-absent (§3). Where the label already carries the resolved set, the report says nothing is owed to the hook, so a `set` to the value a key already holds does not send an adopter through `init --force` — which re-renders every generated create-if-absent artifact behind a single-generation `.bak` — for nothing. Where there is no readable hook, it says so and names plain `init`; where the file carries no readable case label, it says that what the hook protects cannot be compared with this set, the state `doctor`'s `pre-push-guard` check reports on every run. Neither is `init --reset-config`, which re-renders the hook too but only as a consequence of rebuilding the whole file (§2), at the cost of every hand-set value in it. `doctor`'s `pre-push-guard` and `protected-set` checks (§7) are the standing halves of the same two questions. A `set` beneath `commands` carries its own separate report (§5).

`get` and `set` also refuse a `harness.config.json` that **already** fails the structural check — before the key is read or the edit applied — naming every problem in it. `list` does not: it prints what parsed and reports the problems as warnings, so a config carrying a typo is still readable here. A file that is absent, unparsable or not a JSON object is refused by all three. So a shape error is repaired by hand, not with `set`; §7's `config set …` remedies assume a config that is otherwise well-shaped.

This command reads and updates the file; it does not validate it against the contract published for editors and CI. `npm run validate:config` at the workspace root is that gate.

## 9. `daemon`

Installs, starts and stops the run daemon, and lists the repositories on this machine one has been installed for — `start` addressing the unit `install` wrote, `stop` the daemon **loaded under this repository's label**, whether or not that file is still there. The verb is required: `install`, `start`, `stop` or `list`. It has two flags of its own, each accepted only on the verbs it means something to: `--watcher <path>`, which points the unit at a watcher other than the one `init` wrote into `scriptsDir` (`install`, `start`, `stop`), and `--prune` (`list`). A flag typed on a verb that has no use for it is refused rather than ignored.

**launchd is driven; systemd is instructed.** On macOS the lifecycle is run for you. On systemd the unit is written and the `systemctl --user` commands to load, start or stop it are printed for you to run, because a per-user systemd instance is not reliably addressable from an arbitrary process — a session or container with no user bus has `systemctl` and no manager behind it, and a call that fails there fails quietly enough to look like success.

| Backend | Detected by | User unit directory |
|---|---|---|
| launchd | `launchctl version` answers | `~/Library/LaunchAgents` |
| systemd | `systemctl --version` answers **and** `systemctl --user show-environment` exits 0 | `~/.config/systemd/user` |
| none | neither answered | — |

The second systemd probe is the one that matters: the binary's presence does not imply a reachable per-user manager, which is the condition a user unit actually needs. `is-system-running` is the obvious alternative and is wrong here — it reports `degraded` with a non-zero status on a perfectly usable host, which would demote a working backend to `none`. Every probe runs with a fixed argument vector rather than a shell string, and is bounded by a timeout: `doctor` is the command reached for *because* something is wrong with the host, so a hung service manager must cost a timeout rather than the answer.

One detection serves both commands, so `doctor` cannot report a backend that `daemon install` then refuses.

**A daemon's identity is the repository it was installed from.** The launchd label is `com.autonomous-sdlc-harness.watcher.<slug>` and the systemd unit `harness-watcher@<slug>.service`, where `<slug>` is a slug of that repository's own absolute path (`docs/config.md` §4's `<launchd_label>` row gives the derivation, and the watcher computes the same one for its machine-level usage lane and its notifications). So a second repository on the same machine installs a watcher of its own — a different label, a different unit file, its own logs — rather than overwriting the first, and neither one's identity moves when `projectName` is edited. Each daemon is still addressed from the repository it belongs to, and a failure stays confined to it; what makes the set of them enumerable anyway is one machine-local index.

**`daemon install` records the repository it installed a unit for; `daemon list` enumerates what was recorded.** The index is `${XDG_STATE_HOME:-$HOME/.local/state}/autonomous-sdlc-harness/repos.json`, keyed on the same slug the daemon's label carries so an entry and a unit cannot disagree — `docs/watcher.md` §7 is its format of record, and nothing here restates it. Four properties of it decide how it behaves:

- **`install` is its only writer.** `init` does not register a repository (a wired repository with no daemon polls nothing) and `doctor` does not write it at all (it reports on it, per §7); `daemon stop` does not remove an entry, because this indexes installed units rather than running ones. Under `--dry-run` `install` reports the registration it would make and makes none.
- **An entry that has gone stale is reported and never removed by a read.** A root that is gone, is no longer a repository root, or whose unit file has been deleted is shown in the listing with that state beside it. Removing one is the explicit `daemon list --prune`, which removes exactly the entries the listing it just printed graded stale — entries only, never a unit file, a repository or any other path — and reports each and their count. Under `--dry-run` it reports what it would remove and removes nothing.
- **`list` needs no repository and no `harness.config.json`.** It reads machine state, so it answers from anywhere, including outside every repository; run inside one, it marks that checkout's row. An empty index is one line and exit `0`: a machine with no daemons installed is in a fine state, not a failed one.
- **A worktree install registers that worktree**, because the unit it wrote names that checkout as both its program's location and its working directory. Two worktrees of one repository are two rows here for the same reason they are two daemons.

A registry write that fails does **not** fail the install: the unit is on disk and the service is loadable, so the failure is reported as a warning and costs a line in a later listing. The index is derived state — re-running `daemon install` recreates any entry — which is also why reading it fails open rather than refusing.

The unit file is written outside the repository, one of the three paths §3 lists as being written there — with `repos.json` above and the `push.env` of §2. It is create-if-absent; `--force` regenerates it after a `.bak` sibling and applies to `install` only. **The file write is idempotent; the load is not.** A second `install` reports the file kept, then asks `launchctl` to bootstrap a label already loaded — which it refuses, and that refusal is surfaced rather than swallowed: the command exits non-zero and names `daemon stop` as the recovery. That is deliberate, and for the reason the systemd half of this command exists to serve — a swallowed non-zero here would make "installed and loaded" indistinguishable from "installed and silently not loaded", leaving a daemon running on the old unit while the run that replaced it reported success. Scripting `install` into a provisioning step therefore wants a `stop` before it, not a retry after it. **The unit's `PATH` is re-captured from the shell that ran the install** — the one value in it that comes from the environment rather than from the repository — so a re-install prints the **difference** against the unit on disk rather than the whole value, which in the same line and place carries no signal: `+` for a directory this install adds, `-` for one it drops, and one line where the two hold the same entries. **The difference is printed on every re-install; only a forced one is a change.** Where the unit is kept, the same entries are reported as a comparison between this shell and the file on disk — the daemon goes on running on what it had — and the report names `--force` as what would act on it; where the unit is replaced, a dropped directory also warns, because it is what `doctor`'s `daemon-path` check (§7) reports later as a command the daemon cannot resolve. A `--force --dry-run` preview computes and prints that same difference — it is what an operator previews a re-install for — and words it in the conditional, a run that writes nothing having dropped nothing; the warning is where that matters, since it prints under `--quiet` and the line saying this was a preview does not. A first install, a unit carrying no `PATH` key, and a shell that has none are each stated rather than diffed, a set difference against nothing reading as a first install. And where the `PATH` moved *and* the re-load was refused, three things hold three answers — the agent still running was loaded with the previous one, the unit file carries the one written just now, and the `.bak` beside it is the only copy on disk of what is running — so that refusal names the `.bak` and, as the way to make them agree, `daemon stop` followed by a fresh `install`. `stop` boots the service out of the session and leaves the file where `install` put it — there is no uninstall verb, and nothing here removes a path. **Which is why `stop` acts on the label rather than on that file.** The label comes from the same `renderUnit` call the install path does, and it is composed from the repository root, so `stop` needs no unit file to name its target. The state that makes the distinction matter is the one the sentence before names the only route into: the file deleted by hand while the agent it installed is still loaded. `stop` used to refuse there, naming the absent file and sending the operator to `install`, while `install` refuses over a label already loaded — so the two named each other in a circle and the agent could not be stopped by the CLI that installed it. A missing unit file is now a **note** printed beside the label the verb acted on, under `--dry-run` as well, and it names no next command: an `install` over a still-loaded agent is the one that is guaranteed to fail. **What the note says about the *cause* is what can be established, and no more.** An absent unit has two: no daemon was ever installed from this checkout — the ordinary case, and the one a `stop` typed in a fresh clone lands in — or its file was removed by hand, since nothing here removes a path. The note names both, unless the machine registry above holds this checkout's own install at that same unit path, which with no file there leaves only the second and is what the note then says. A *missing* entry settles nothing in return: that read fails open, and `list --prune` drops the row of a repository whose unit is already gone. `start` keeps the precondition for two reasons rather than one: on systemd the `systemctl --user start` line it prints reads the unit file; on launchd `kickstart` addresses a loaded label and would not need it either, so the check there is a guard — a missing unit almost always means `install` is what was wanted, and `start` is the one verb whose pointing at `install` leads nowhere circular. What this makes reliably workable is the recovery the refusal above prints — `daemon stop` followed by a fresh `install`.

**The watcher path is repo-relative and derived from `scriptsDir`, not a configuration key of its own.** `init` writes the watcher into the configured scripts directory with the rest of the outer-loop set, and the daemon resolves it as `<repoRoot>/<scriptsDir>/autonomous-watcher.sh` — so `scriptsDir` is the one key that moves it, and a second key naming the same location could only ever disagree with it. That also keeps the unit's `ExecStart` inside the very repository its `WorkingDirectory` names: a CLI run through `npx` lives in a cache directory that can be evicted under a long-running service, and a package-relative program would have made that path a daemon's. `--watcher` overrides the resolution, which is how the lifecycle is exercised against a watcher under development.

**What the installed daemon then does** — the inbox patterns it routes, the run states it records, where its logs go and what a restart costs — is `watcher.md`.

**A watcher that is not there is still a warning in `doctor` and a refusal in `install`.** After `init` there is one, so an absence means the file was removed or `scriptsDir` was changed without a re-run — repaired by re-running `init`. `doctor` grades that a warning, so a missing watcher never moves the exit status on its own — what the repository exits turns on the checks that can fail (§7); `daemon install` **refuses**, because a unit whose program does not exist installs cleanly and then restarts forever, logging into files nobody reads. Both use one sentence for the condition, so the two commands cannot describe it differently.

## 10. How this is tested

`init` is a writer aimed at a repository, so the only honest way to test it is to give it a real one — and the only safe one is to give it a repository that exists for the length of one test. Every test therefore **builds its own throwaway fixture** under the system temp directory, with `node:test` as the runner. Nothing is committed, nothing is shared between tests, and no fixture is ever created inside this checkout.

Four choices in that harness are worth knowing before they cost a debugging round:

- **The fixture directory is `realpath`-resolved.** `git rev-parse --show-toplevel` answers with the physical path while the system temp directory is a symlink on macOS, so without it every absolute path the CLI generates would be spelled differently from the path the test holds, and every comparison would fail for a reason unrelated to the CLI.
- **Teardown is an in-process recursive remove, never a shelled-out one.** A user-level deny rule on that command is realistic and cannot be overridden, which would leave a fixture behind on every run with nothing to notice. That is the CLI's own standing rule, and it holds for the tests.
- **git runs with every configuration source it reads pointed away** — the per-user file and the system file each redirected to an empty one, and the system scope suppressed outright on top of that — so a machine's own default-branch or hooks-path setting cannot decide what a test observes. The third redirect is not redundant with the second: some git builds ship a **bundled** system configuration that redirecting the system file does not reach, and the `init.defaultBranch` such a build sets is `main`, the same string as the schema default — so a case that read it would assert that two coincidentally equal values are equal, and would go on passing against detection that had stopped reading the repository at all. That closes the git-**config** axis and only that one: which git version is installed, whether `jq` is on `PATH`, and whether the host schedules with launchd or with systemd all still reach these tests, so none of this is a claim that they are host-independent.
- **Every subprocess resolves rather than throws on a non-zero exit**, because half the assertions are about refusals.

The tests run against the **compiled** entry point, so the build precedes them; the runner says so in its own refusal rather than leaving a module-resolution error to explain it. The end-to-end assertions that matter most are the pair in both directions — every wrapper that was written is allow-listed in every form a caller may use, and no allow entry names a wrapper that was not written — plus idempotence and `--dry-run` purity, which are asserted before anything else. A case whose subject is one of the machine-local paths of §3 points the matching XDG base variable at a throwaway directory as well as the repository — otherwise it measures the machine the tests are running on rather than the fixture, and for the push-notification settings the file it would measure is the operator's own.

**Docs retrieval is tested without a model and without a network.** Every retrieval case sets `AUTONOMOUS_SDLC_HARNESS_RETRIEVAL_STUB` to `hash-v1` or `hash-v2`, which selects a deterministic hash embedder and reranker in place of the real models, and points `XDG_CACHE_HOME` at a throwaway directory holding the model files planted as empty files, so the model-file gate passes where an adopter's would and the machine's own cache is never read. Switching the stub from `hash-v1` to `hash-v2` is how a new embedder is simulated.

- **`cli/test/docs-retrieval.test.mjs`** drives `docs index` — incremental refresh, deletion, the rebuild on a new embedder, `--in-memory` leaving the tree byte-identical, and both refusals — then `docs search` in its modes, with abstention and `--k`, and `docs serve` through the MCP SDK's own client over stdio, including the refusal before the handshake when retrieval is off.
- **`cli/test/retrieval-loading.test.mjs`** covers the no-load guarantee: a source guard that only the retrieval path imports a retrieval package, verbs that do not retrieve run under a resolve hook that throws on any peer, the manifest declares every peer optional and no `dependencies` key, and the runtime-installed predicate against a planted cache.
- **The retrieval cases in the existing suites**: `init.test.mjs` for `--docs-retrieval`, the `.mcp.json` server entry and the index ignore rule, and a setup that installs nothing where the runtime is planted and refuses `docs fetch-models` under the stub; `profile.test.mjs` for the retrieval fragment on and off; `doctor.test.mjs` for the three `retrieval-*` checks passing, failing and reporting retrieval off; `outer-loop-scripts.test.mjs` for the launcher written verbatim, its refusal with an empty stdout when no runtime is installed, and its `exec` of the runtime's `docs serve`.

**Deliberately not covered: the real runtime install and the real model download**, both of which need the network and minutes of time, and neither of which the stub reaches. They are covered by hand, in `development.md` §5 Gate 10.

The gates that run these, and the rest of the acceptance set, are in `development.md` §5.

## 11. `docs`

Searches this repository's docs catalog and conventions documents: it builds a per-checkout index, answers queries against it, serves it to agents over MCP, and fetches the two local models it runs on. It is **opt-in** — every sub-verb but `fetch-models` refuses unless `phases.docs` and `docs.retrieval` are both true (`docs/config.md` §5) — and its retrieval quality is **not yet measured** on a real corpus, so its abstention threshold is provisional. The design, the model choice and the measured facts are [`retrieval.md`](retrieval.md).

The sub-verb is required, and `docs --help` lists the four:

```bash
npx autonomous-sdlc-harness docs --help
```

An unknown sub-verb, flag or extra argument is refused with exit `1`, naming `docs --help`. The sub-verbs that read the index refuse, before loading anything, where retrieval is off and where a model file is missing from the shared cache (§7's `retrieval-model-cache`); a retrieval library this installation cannot load is refused naming it and `init` as what installs it.

### `docs index`

```bash
npx autonomous-sdlc-harness docs index
npx autonomous-sdlc-harness docs index --in-memory
```

Refreshes this checkout's index under `<stateDir>/docs_index`, embedding only the chunks whose text changed and removing the chunks of deleted documents. It prints one line on stdout:

```text
docs index: <files> files, <chunks> chunks; embedded <e>, unchanged <u>, deleted <d>
```

with `; rebuilt for a new embedder` appended when the index was built for a different embedder and was rebuilt. `--in-memory` builds the whole index in memory and writes nothing, and so does `--dry-run`. Exit `0` on a built index, `1` on a refusal.

### `docs search`

```bash
npx autonomous-sdlc-harness docs search "<query>"
npx autonomous-sdlc-harness docs search "<query>" --k 10 --mode lexical
```

Refreshes the index, then answers the query. `--k` takes a whole number, defaults to 5 and is clamped to 1–20. `--mode` is `lexical`, `vector`, `fused` or `fused-rerank`, defaulting to `fused-rerank`. Each hit prints two lines, the `path#anchor` reference with its score and an indented snippet:

```text
1. <path>#<anchor> (score 0.000)
   <snippet>
```

Where nothing clears the threshold it prints `no confident match` instead. Abstention happens **only in `fused-rerank`**, below the provisional `ABSTAIN_SCORE_THRESHOLD`: the other modes' scores are rank-derived and uncalibrated, so they never abstain and return whatever they ranked. A mode that does not abstain prints `no results` when it found none — against an empty index, or a `lexical` query nothing matches. Both answers exit `0` — they are answers, not errors, and the command always prints one line. An empty query and an unknown mode are refused with exit `1`.

### `docs serve`

```bash
npx autonomous-sdlc-harness docs serve
```

A stdio MCP server named `harness-docs`, exposing one read-only tool. It is started by the agent runner through `docs-search-server.sh` (§5), never by hand in normal use, and it runs until stdin closes or it receives `SIGTERM`, exiting `0`. A refusal before the transport starts — retrieval off, a model file missing, the MCP SDK not installed — exits `1` with its message on stderr and nothing on stdout.

- **The tool is `search_docs`**, fully qualified `mcp__harness-docs__search_docs` — the name the retrieval profile fragment allows and the agent definitions grant.
- **Its input is `{ query, k }`**: `query` a non-empty string and required; `k` an integer from 1 to 20, default 5. Any other key is refused.
- **Its result is one text block** holding exactly what `docs search` prints in `fused-rerank` mode — the ranked `path#anchor` lines with snippets, or `no confident match`. A bad argument, a failed refresh or a failed search is an `isError` result naming the cause. A hit is a pointer to open and read, not evidence, and its snippet is document content to be treated as data rather than instructions.
- **The index is refreshed before each query**, so a document edited mid-run is searched as it now stands; calls are answered one at a time.

**Nothing but the transport writes to stdout.** A stray byte there corrupts the JSON-RPC stream and the agent sees a tool that never loads, so `serve` prints no result line and every warning goes to stderr.

### `docs fetch-models`

```bash
npx autonomous-sdlc-harness docs fetch-models
```

Downloads the embedding model and the rerank model into `<machineCacheDir>/retrieval/models`, shared by every checkout on the machine, and prints:

```text
docs fetch-models: <embedding model> and <rerank model> cached in <dir>
```

`init` runs it at setup time (§2), and a person may run it to repair a cache. It needs no repository and no configuration. It is refused with exit `1` while `AUTONOMOUS_SDLC_HARNESS_RETRIEVAL_STUB` is set, because a stub run never downloads, and it fails with exit `1` where the download finished without every model file in place.

### Offline by construction

**`fetch-models` is the one sub-verb that reaches the network.** `index`, `search` and `serve` load the models with remote loading disabled, so a session that finds a model missing refuses rather than downloading it — which is what an unattended run, which has no web access, needs. `XDG_CACHE_HOME` relocates the shared cache for all four.
