## 1. Anthropic's plans, Claude Code sign-in and the terms

### P1. What do Pro, Max, Team and Enterprise give for Claude Code: seats, per-member usage, admin controls, price?

**Status:** `partly documented`

**Answer:** Claude Code is included on all four plans.

- **Pro** is an individual plan at "$20 per month (US)", or "$17 Per month with annual subscription discount ($200 billed up front)". Its usage has a session limit that resets every five hours and a weekly limit. Usage credits let a subscriber continue past the included limits at standard API rates, under a monthly spending cap the subscriber sets.
- **Max** is an individual plan in two tiers: "Max 5x: $100 per month" and "Max 20x: $200 per month", monthly only. Max 5x gives five times and Max 20x twenty times "the Pro plan's per-session usage allowance", with the same five-hour session reset and a weekly limit. Anthropic "may limit your usage in other ways, such as weekly and monthly caps or model and feature usage, at our discretion." Usage credits work as on Pro.
- **Team** takes "a minimum of two members" and "up to 150 seats". A Standard seat costs "$25 per member per month, billed monthly" or "$20 per member per month, billed annually"; a Premium seat "$125 per member per month, billed monthly" or "$100 per member per month, billed annually". Claude Code "is included with every Team plan seat", Standard included; a Premium seat only adds usage (1.25x against 6.25x "the Pro plan's per-session usage allowance"). Limits are per member and are not pooled: "If one team member reaches their seat's included usage limit, it does not affect the limits of other team members." Seats are assigned to members, and admins can reassign seat types.
- **Team admin controls.** Owners can turn on usage credits, billed "at standard API pricing rates", set a monthly spend limit for the whole organisation and a monthly spend limit for each member, or disable usage credits entirely. Server-managed settings are available on Team and Enterprise and need the Owner or Primary Owner role; through them an admin can set `forceLoginMethod` / `forceLoginOrgUUID` to require that members' logins belong to the organisation. Org analytics show estimated spend per user and per model, and adoption metrics.
- **Enterprise** costs "US$20/seat/month, billed annually", needs "a minimum of 20 seats", and bills usage on top at API rates. Its single Enterprise seat includes Claude Code. Admins set organisation-level and individual-level spend limits, which work hierarchically. Enterprise adds SCIM, audit logs, role-based permissions and the Compliance API, and the Enterprise Analytics API "returns per-user usage and cost reports".

**Two Anthropic pages conflict on Enterprise.** The Enterprise billing support article says "Enterprise seats don't come with an individual token allowance. All usage across your organization is billed together at API rates, regardless of who consumed it", and that on self-serve Enterprise "Everyone's usage draws from the same credit balance." The Claude Code costs page says "On Claude for Teams and Enterprise plans, each member's Claude Code usage draws from a per-seat allowance that resets on a rolling five-hour window and a weekly window." Both are Anthropic's own pages, both were retrieved the same day, and this entry prefers neither.

**Inference:** the costs page's per-seat-allowance paragraph fits Team and legacy seat-based Enterprise (the Team-and-Enterprise support article still names older Enterprise plans with seat-based billing); for current, usage-based Enterprise the support article is the more specific source. That reading resolves the conflict but is not stated by either page, so which page describes current Enterprise is left for §7. Separately, the seat-management article speaks of seats assigned to named members ("assign and reassign users") but does not use the words "one person per seat".

### P2. Can a Team or Enterprise seat sign Claude Code in non-interactively, with `claude setup-token` and `CLAUDE_CODE_OAUTH_TOKEN`?

**Status:** `partly documented`

**Answer:** Yes. `claude setup-token` runs the same browser authorisation as `/login` once, then prints "a one-year OAuth token" without saving it; setting it as `CLAUDE_CODE_OAUTH_TOKEN` signs Claude Code in without a browser. The token "requires a Pro, Max, Team, or Enterprise plan" (Free is not listed) and is inference-only: "It can only make model requests, so it can't establish Remote Control sessions or fetch claude.ai connectors." Bare mode (`--bare`) does not read it. The token belongs to one person: on GitHub Actions, "an OAuth token is tied to the subscription of the person who ran `claude setup-token`", and for a secret shared across repositories Anthropic's GitHub Actions page points to a Console API key instead. Deleting the repository secret does not end the token: "If you delete a secret, the credential it held stays valid." An organisation's `forceLoginOrgUUID` does not bind `setup-token`, which enforces only `forceLoginMethod`, "so they can mint a token in a different organization". Server-managed settings are still delivered to a session running on a `CLAUDE_CODE_OAUTH_TOKEN` token. For contrast, the scope that controls cloud sessions is capped server-side at 30 days, which the one-year token does not cover.

**Not documented:** how to revoke a `setup-token` token, and whether a Team or Enterprise admin can see or revoke a member's tokens. Pages checked: authentication, cli-reference, env-vars, github-actions, server-managed-settings, costs, and a full-text search of `https://code.claude.com/docs/llms-full.txt` for "revoke". No page checked says either that a Team seat holder's token must not be given to another person; that rule comes from the terms and the legal-and-compliance page (P4).

### P4. What do the terms say about sharing one account's credentials, or one subscription's OAuth token, with other people or with automation?

**Status:** `partly documented`

**Answer:**

- **Consumer Terms (Free, Pro, Max; EEA/Switzerland version).** § 2 "Account creation and access": "You may not share your Account login information, Anthropic API key, or Account credentials with anyone else or make your Account available to anyone else." § 3 "Use of our Services" bars, "Except when you are accessing our Services via an Anthropic API Key or where we otherwise explicitly permit it", access "through automated or non-human means, whether through a bot, script, or otherwise."
- **Claude Code legal-and-compliance page (all plans).** "**OAuth authentication** is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications." Developers building products, including on the Agent SDK, "should use API key authentication", and may not "route requests through Free, Pro, or Max plan credentials on behalf of their users" or "collect, store, or intermediate Claude.ai credentials or session tokens". The page carves out API keys and third-party inference credentials provisioned "for use by the customer's own authorized users — provided the resulting usage is billed to the key owner". For subscriptions, the matching carve-out names only "an end user from signing in to the unmodified Claude Code binary with their own Claude subscription": it does not extend to a subscription OAuth token used by others.
- **Support articles.** "Subscription plans can only be used by subscribers", in an article that names all five plans, Team and Enterprise included. The Cowork article says "Shared logins aren't supported."
- **Commercial Terms (Team, Enterprise, API).** § D.4 "Use Restrictions" restricts building a competing product, reselling, reverse engineering and duplicating, and supporting a third party in doing so. § D.5 "Service Account": "Customer is responsible for all activity under its account."

**Not documented:** the Commercial Terms contain no clause on sharing credentials or logins between individuals and no automated-access ban; for Team and Enterprise the operative restrictions on OAuth tokens come from the legal-and-compliance page and from the per-member seat model (P1). The Usage Policy has no general clause on account sharing, usage-limit circumvention or ordinary automation: its account clauses target bans, multi-account abuse and unsupported regions. No support article titled "Can I share my account" was found. Pages checked: the Commercial Terms, the Usage Policy, a search of support.claude.com for "share my Claude account" and "Shared logins are not supported", https://support.claude.com/en/articles/13133750-manage-members-on-team-and-enterprise-plans (no statement on shared logins) and https://support.claude.com/en/articles/9267247-get-started-with-the-team-plan (only "Data isn't shared between separate accounts").

**Inference:** the Claude Code docs, which document `claude setup-token` "for CI pipelines and scripts" on Pro and Max, read as the explicit permission Consumer Terms § 3 allows for, for that one tool. That permission is still bounded by § 2 (no sharing) and by the "ordinary, individual usage" language on the legal-and-compliance page. § 2's "make your Account available to anyone else" reaches a teammate whose runs use your token, not only one who is given your password.

### P5. What happens to one person's subscription limits when teammates use it?

**Status:** `partly documented`

**Answer:** A subscription's usage is metered per account, or per seat on Team, and every surface draws on the same limit: claude.ai, Claude Code and Claude Desktop "counts towards the same usage limit". ### R4. How is Console usage attributed: to a key, a workspace, or a person?

**Status:** `partly documented`

**Answer:**

- **Usage and Cost API.** Usage can be filtered and grouped "by API key, workspace, model, service tier, context window, data residency, or speed (beta)". Cost can be grouped "by workspace or description" only. Neither list has a user dimension. Playground usage has a `null` `api_key_id`, and the Default Workspace's usage a `null` `workspace_id`. The endpoints are Admin API endpoints: "workspace API keys don't work". For per-user Claude Code cost the FAQ points to the Claude Code Analytics API, and for general API usage with many keys to the Usage API "to track token consumption as a cost proxy".
- **Claude Code Analytics API.** "Each record represents one user's activity for the specified day". The `actor` is "either `user_actor` with `email_address` or `api_actor` with `api_key_name`", and each record carries `estimated_cost.amount` in cents USD. It "only tracks Claude Code usage on the Claude API": Amazon Bedrock, Microsoft Foundry, Google Cloud and Claude Platform on AWS usage "is not included".
- **The Console's Claude Code dashboard** (platform.claude.com/claude-code) shows "Usage metrics, spend tracking, team insights" to Developer, Billing, Admin, Owner and Primary Owner roles. Its **Members** list shows "API key users ... by key identifier, OAuth users ... by email address". "Contribution metrics with GitHub integration are not currently available for API customers."
- **Responses** carry an `anthropic-workspace-id` header naming the workspace "that the request's API key or access token resolved to".
- **OpenTelemetry.** Claude Code's OpenTelemetry export "works on every setup and is the only option that streams per-user token and cost metrics into your own observability stack in near real time." Its user attributes are `user.account_uuid` and `user.account_id`, each "(when authenticated)", and `user.email`, "Always included when available"; `user.id` is a random anonymous identifier, "not derived from your Claude account". Teams can add `OTEL_RESOURCE_ATTRIBUTES` to "Filter metrics by team or department". Its cost metrics "are approximations", and Claude Code ignores the exporter variables in a repository's `.claude/settings.json` and `.claude/settings.local.json`.

**Inference:** for API traffic other than Claude Code, per-user attribution is reachable only indirectly: give each user a personal key, group usage by `api_key_id`, and map each key to its `principal.user_id` (R2). ### R5. How does a team run Claude Code through Amazon Bedrock or Google Vertex AI: credentials, per-user attribution, and GitHub Actions?

**Status:** `partly documented`

**Answer — what Anthropic's Claude Code pages say.**

- **Billing.** On Bedrock, Google Cloud's Agent Platform and Microsoft Foundry, "Claude Code is billed per token to your cloud account, and spend controls live in your cloud provider's billing console." Claude Code sends no metrics back to Anthropic, so the analytics dashboards and the Claude Code Analytics API do not cover this usage (R4).
- **Bedrock credentials.** "Claude Code uses the default AWS SDK credential chain", with five options listed: AWS CLI configuration, access-key environment variables, SSO-profile environment variables, AWS Management Console credentials and Amazon Bedrock API keys. `awsAuthRefresh` "runs only when Claude Code detects that your AWS credentials are expired", and `awsCredentialExport` "runs at session start and on each credential reload". The page advises "Create a dedicated AWS account for Claude Code to simplify cost tracking and access control", and `modelOverrides` can route each model version to "its own application inference profile ARN".
- **Vertex credentials.** "Claude Code uses standard Google Cloud authentication", including "X.509 certificate-based Workload Identity Federation" through Application Default Credentials, addresses the project in `ANTHROPIC_VERTEX_PROJECT_ID`, and needs `roles/aiplatform.user`. The page advises "Create a dedicated GCP project for Claude Code to simplify cost tracking and access control."
- **GitHub Actions.** The Claude Code GitHub Action can route inference through the team's cloud account: "configure your cloud to trust the workflow's OpenID Connect (OIDC) token ... so you store no long-lived cloud credential in your repository." On AWS that is a GitHub OIDC identity provider with audience `sts.amazonaws.com` and an IAM role whose trust policy is limited "with a subject condition such as `repo:your-org/your-repo:*`"; on Google Cloud, a Workload Identity Pool limited to the repository, impersonating "a dedicated service account with only the `Vertex AI User` role". The action's own document says "Bedrock, Vertex, and Microsoft Foundry use OIDC authentication exclusively". With a cloud provider the team chooses the GitHub identity: the official Claude GitHub App, a custom GitHub App, or `GITHUB_TOKEN`, with which "GitHub doesn't trigger your CI workflows on commits made with it". The credential steps "run before the Claude Code GitHub Action checks the commenter's write access", so an unauthorised commenter is rejected only after the workflow has signed in to the cloud provider.

**Answer — what AWS and Google say.**

- **Bedrock, per caller.** With IAM principal data enabled in CUR 2.0 ("Include caller identity (IAM principal) allocation data"), AWS "automatically records the caller identity (IAM principal ARN) for each Bedrock API call in the line_item_iam_principal column", in forms that include `user/...`, `role/...` and `assumed-role/<role>/<session-name>`; tags on the principal are captured with the costs. AWS's cost-attribution guide gives IAM principal attribution for "Per-user or per-team dollars on your bill" and application inference profiles (or, on bedrock-mantle, Projects and Workspaces) for "Per-application or per-workload dollars"; application inference profiles take tags "to track costs". Per-request metadata tags are recorded in model invocation logs on bedrock-runtime and are not supported on bedrock-mantle. For a role assumed through `AssumeRoleWithWebIdentity`, the `RoleSessionName` "is included as part of the ARN", and AWS says it is typically "the name or identifier that is associated with the user". To attribute by user, AWS advises "a stable internal identifier (for example, a hashed user ID) rather than an email address."
- **Vertex, per call.** Labels on a call are "forwarded to the billing system", Anthropic is a partner model that supports them on `rawPredict` and `streamRawPredict` (up to 32 labels per call, passed in an `X-Vertex-AI-Labels` header, base64-encoded), but only on pay-as-you-go: "Requests using the Provisioned Throughput consumption option will silently ignore labels sent in the request."

**Not documented:** per-user cost attribution, IAM-principal cost allocation or cost-allocation tags on Claude Code's Bedrock page, beyond the dedicated-account note (pages checked: `amazon-bedrock`, `costs`, `iam`, `monitoring-usage`); labels or per-user billing on Claude Code's Vertex page (pages checked: `google-vertex-ai`, `costs`, `env-vars`, `monitoring-usage`). ### R6. How does workload identity federation take a GitHub Actions job to the Claude API, and does the stock `claude` CLI support it?

**Status:** `partly documented`

**Answer — the exchange.**

- **What it is.** "With Workload Identity Federation, your workflow exchanges that token for a short-lived Anthropic access token, so your CI jobs can call the Claude API without an `ANTHROPIC_API_KEY` secret stored in your repository." The token acts as a Claude Console service account: Anthropic's GitHub Actions page describes the exchange as "through a Claude Console service account", and the action's setup guide's first step is "**Create a service account** (Settings → Service accounts) and add it to the workspace it should act in." Anthropic's key guidance prefers federation, or identity-backed keys, to workspace keys (R2).
- **What the job needs.** "GitHub only issues an identity token to jobs that explicitly request it. Add the `id-token: write` permission at the workflow or job level".
- **Lifetimes.** "Each GitHub-issued identity token expires roughly five minutes after issuance", but the token-request endpoint "stays valid for the entire job". "For jobs that run longer than the Anthropic token's lifetime, the SDK re-reads `ANTHROPIC_IDENTITY_TOKEN_FILE` on each refresh, so re-run the fetch step periodically (or wrap it in a background loop) to keep the file current." The Anthropic token's lifetime is the rule's `token_lifetime_seconds`: "Integer between `60` and `86400` (1 minute to 24 hours). Default `3600`."
- **What a rule matches.** The `sub` claim takes the forms `repo:<owner>/<repo>:ref:refs/heads/<branch>` for a push to a branch, `repo:<owner>/<repo>:pull_request` for pull-request runs, and `repo:<owner>/<repo>:environment:<name>` for environment-gated deployments; a rule "matches against this claim (and others, such as `repository_owner` and `ref`)". The page's sample decoded token carries `iss`, `sub`, `aud`, `repository`, `repository_owner`, `ref`, `sha`, `workflow`, `actor` and `event_name`. A rule's matchers are a `subject_prefix`; `claims`, where "Each key is a top-level claim name and each value is the required exact string value"; and a `condition`, "A CEL expression that must evaluate to `true`" over "The full decoded JWT claim set". "All populated fields are evaluated with AND semantics: the JWT must satisfy every populated matcher."
- **The fork warning.** "A `subject_prefix` of `repo:your-org/*` alone matches every repository in your organization, and without a `ref` constraint it also matches `pull_request` runs triggered from forks. Anyone who can open a pull request against a matching repository could obtain a federated Anthropic token." The page advises pinning `"ref": "refs/heads/main"` under `claims`, or, for deploy jobs, a `subject_prefix` on a deployment environment gated by required reviewers.
- **Billing.** A rule's `workspace_id` is "The workspace (`wrkspc_...`) whose quota, billing, and rate limits apply to tokens minted under this rule."
- **Failures.** "Every assertion denial returns the same opaque `401` `authentication_error` with the fixed message `Authentication failed`, regardless of which check failed"; the reason is recorded in the authentication history.
- **In `anthropics/claude-code-action`.** The inputs are `anthropic_federation_rule_id` (`fdrl_...`) with `anthropic_organization_id`, and optionally `anthropic_service_account_id` (`svac_...`). "Do not set `anthropic_api_key` or `claude_code_oauth_token` alongside the federation inputs — a static credential takes precedence and federation will not be used." Inline comment classification "currently requires `anthropic_api_key`; with federation it is skipped".

**Answer — the `claude` CLI.** Claude Code lists "Anthropic profile and Workload Identity Federation credentials" among its supported authentication types. It takes the federation route when `ANTHROPIC_FEDERATION_RULE_ID` and `ANTHROPIC_ORGANIZATION_ID` are both set, and "also reads the other variables in the WIF reference, such as `ANTHROPIC_IDENTITY_TOKEN_FILE`". The WIF reference's own direct environment-variable path activates only when four are set: those two, `ANTHROPIC_SERVICE_ACCOUNT_ID`, and one of `ANTHROPIC_IDENTITY_TOKEN_FILE` or `ANTHROPIC_IDENTITY_TOKEN`. Federation ranks below both static credentials, in the precedence list's own words:

> "3. `ANTHROPIC_API_KEY` environment variable. … In non-interactive mode (`-p`), the key is always used when present."
> "5. `CLAUDE_CODE_OAUTH_TOKEN` environment variable. A long-lived OAuth token generated by `claude setup-token`. Use this for CI pipelines and scripts where browser login isn't available."
> "6. Anthropic profile and federation credentials, the credentials that the `ant` CLI and Workload Identity Federation use."

So a job that authenticates through federation leaves both `ANTHROPIC_API_KEY` and `CLAUDE_CODE_OAUTH_TOKEN` unset, and blanking one is not enough: "A variable that is set to an empty string still occupies its slot in the credential precedence chain. If `ANTHROPIC_API_KEY=""` is exported, the SDK selects the API-key path with an empty key rather than falling through to federation. Unset unused credential variables rather than blanking them." Claude Code "doesn't read profiles or federation variables in bare mode, in Claude Desktop, or in cloud sessions", and "Cloud sessions always use your subscription credentials."

**Inference:** `actor` is a top-level claim of GitHub's token and `claims` takes any top-level claim name, so a rule can be bound to one GitHub login with `"claims": {"actor": "<login>"}`, a value GitHub signs and a writer to the repository cannot forge. Not tested in this research.

### R7. What does Anthropic document for running Claude Code in CI: `anthropics/claude-code-action` and the Claude GitHub App?

**Status:** `partly documented`

**Answer:**

- **Credentials the action accepts.** `anthropic_api_key` ("required for direct API, not needed for Bedrock/Vertex"), `claude_code_oauth_token` ("alternative to anthropic_api_key"), the federation inputs (R6), and `use_bedrock` / `use_vertex`, each "with OIDC authentication" (R5). The README lists "Anthropic direct API (API key or workload identity federation), Amazon Bedrock, Google Vertex AI, and Microsoft Foundry". For a secret shared across repositories Anthropic's GitHub Actions page points to a Console API key "since an OAuth token is tied to the subscription of the person who ran `claude setup-token`" (P2), and "If you authenticate with an OAuth token, runs use your Claude subscription instead of API billing." It advises storing the secret "as an organization-level Actions secret so each repository doesn't need its own copy".
- **Who may trigger a run.** "The action can only be triggered by users with write access to the repository", checked on issue, pull request, comment, review and `workflow_run` events; `workflow_dispatch`, `repository_dispatch` and `schedule` "are not checked separately". "By default, GitHub Apps and bots cannot trigger this action", except those listed in `allowed_bots`. `allowed_non_write_users` bypasses the write check, and "Only works when `github_token` is provided as input (not with GitHub App authentication)". **Read from source, not documented:** `src/github/validation/permissions.ts` calls `octokit.repos.getCollaboratorPermissionLevel` for the actor and accepts `"admin"` or `"write"`. The check gates who may trigger a run and plays no part in billing. [`github-integration-research.md`](github-integration-research.md) → T4 records both checks against the action's code. `cli/templates/scripts/remote-run.sh`'s `authorise_actor` makes the same two: `admin` or `write` from the collaborator-permission API, and a non-`User` account refused unless listed.
- **The Claude GitHub App.** It "is shared by every Claude feature that integrates with GitHub, including the Claude Code GitHub Action, Code Review, and auto-fix for pull requests in cloud sessions." Its permissions are read and write on Actions, Checks, Contents, Discussions, Issues, Pull requests, Repository hooks and Workflows, and read on Members, Metadata and Statuses; "GitHub doesn't let you accept a subset", and a custom app covers only the action. The action's own `docs/security.md` is older and narrower than the code.claude.com table: it lists Contents, Pull Requests and Issues as read and write, plus "Permissions for Future Features". The App "receives only a short-lived token scoped specifically to the repository it's operating in". **Read from source, not documented:** `src/github/token.ts` fetches the workflow's OIDC token with `core.getIDToken("claude-code-github-action")` and exchanges it at `https://api.anthropic.com/api/github/github-app-token-exchange`, which is why the default path needs `id-token: write` even with an API key.
- **Authorship.** Comments appear as `claude[bot]` "when the action uses its built-in authentication"; a `github_token` input makes them appear "under a different username". `bot_name` and `bot_id` default to `claude[bot]` and `41898282` for git operations. **Read from source, not documented:** `src/create-prompt/index.ts` instructs Claude to add a `Co-authored-by:` trailer naming the triggering user "When committing and the trigger user is not "Unknown"". That trailer lives in git history, not in billing. With `ssh_signing_key`, "Commits will show as verified and attributed to the GitHub account that owns the signing key."
- **Who opens the pull request.** "In its default configuration, **Claude does not create pull requests automatically** when responding to `@claude` mentions": Claude commits to a new branch, links the PR creation page, and "**The user must click the link and create the PR themselves**".
- **`/install-github-app`.** It installs the Claude GitHub App and sets up the workflows' secret: it reuses Claude Code's existing API key if there is one, and otherwise offers a long-lived subscription token or a pasted API key. "Claude Code saves the credential as a repository secret, named `ANTHROPIC_API_KEY` for an API key or `CLAUDE_CODE_OAUTH_TOKEN` for a subscription token." It needs "admin access to the repository" and works only with the Claude API and Claude subscriptions. Like `claude setup-token`, it enforces only `forceLoginMethod`, "so they can mint a token in a different organization" (P2).

**Not documented:** any per-user credential model, in which the person who triggered `@claude` has the run billed to their own subscription or key. Pages checked: code.claude.com `github-actions`, `github-actions-cloud-providers`, `iam`, `costs`; and in `anthropics/claude-code-action`, `README.md`, `docs/setup.md`, `docs/usage.md`, `docs/security.md`, `docs/faq.md`, `docs/cloud-providers.md`, `docs/configuration.md`. Every documented credential is a single workflow-level value: one API key, one OAuth token, one federation rule acting as one service account, or one cloud OIDC role or service account. The `Co-authored-by:` trailer above is also undocumented; it was found only in source.

**Inference:**

- All of a workflow's model usage bills to the one credential configured in it: on the Claude API the Usage API sees one `api_key_id` or one service account per workflow, and with an OAuth token every run consumes the one subscriber's allowance.
- A workflow author could in principle choose a credential by `github.actor`, for example a per-user secret. No source documents this pattern.
- In the default `@claude` flow, the pull request's author is the human who clicks the link, and the branch's commits are by `claude[bot]`.
- `/install-github-app` stores the running user's own credential as a repository secret — their reused API key, which may be a personal key, or their subscription token — so from then on every collaborator's `@claude` run bills to that one person or key.
