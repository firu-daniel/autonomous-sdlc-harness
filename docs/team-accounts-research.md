## Summary

**The question:** may a run that a teammate starts on GitHub use another person's Claude credential, and whose usage does that run consume?

| Credential | May teammates' runs use it? | Whose usage it consumes | Findings |
|---|---|---|---|
| Pro or Max subscription token | No | The one subscriber's 5-hour and weekly limits | P2, P4, P5 |
| One Team seat's token | No: a seat is one member's | That member's own limits; Team limits are per member and not pooled | P1, P2, P4, P5 |
| One Enterprise seat's token | No: a seat is one member's | The organisation's pooled balance at API rates, with optional per-user caps — Anthropic's two pages disagree (P1) | P1, P2, P4 |
| Console API key, or workload identity federation through a service account | Yes, by the organisation's own authorised people | The organisation's, per workspace; per person only through personal keys or the Claude Code Analytics API | P4, R2, R4, R6 |

The table does not settle how each member's runs could use that member's own credential on GitHub: Actions has no per-user secret scope (G1), any writer can read every repository secret by running an edited workflow (G7), and every harness run the trigger, the commands, a continuation or the poller starts is dispatched by a token that is not the person who asked for it, while a writer who starts one from the **Run workflow** form, the GitHub CLI or a re-run passes no actor check at all ([§5](#5-options-for-the-harness) → *The repository facts the options rest on*).

## 1. Anthropic's plans, Claude Code sign-in and the terms

### P1. What do Pro, Max, Team and Enterprise give for Claude Code: seats, per-member usage, admin controls, price?

**Status:** `partly documented`

**Answer:** Claude Code is included on all four plans.

- **Pro** is an individual plan at "$20 per month (US)", or "$17 Per month with annual subscription discount ($200 billed up front)". Its usage has a session limit that resets every five hours and a weekly limit. Usage credits let a subscriber continue past the included limits at standard API rates, under a monthly spending cap the subscriber sets.
- **Max** is an individual plan in two tiers: "Max 5x: $100 per month" and "Max 20x: $200 per month", monthly only. Max 5x gives five times and Max 20x twenty times "the Pro plan's per-session usage allowance", with the same five-hour session reset and a weekly limit. Anthropic "may limit your usage in other ways, such as weekly and monthly caps or model and feature usage, at our discretion." Usage credits work as on Pro.
- **Team** takes "a minimum of two members" and "up to 150 seats". A Standard seat costs "$25 per member per month, billed monthly" or "$20 per member per month, billed annually"; a Premium seat "$125 per member per month, billed monthly" or "$100 per member per month, billed annually". Claude Code "is included with every Team plan seat", Standard included; a Premium seat only adds usage (1.25x against 6.25x "the Pro plan's per-session usage allowance"). Limits are per member and are not pooled: "If one team member reaches their seat's included usage limit, it does not affect the limits of other team members." Seats are assigned to members, and admins can reassign seat types.
- **Team admin controls.** Owners can turn on usage credits, billed "at standard API pricing rates", set a monthly spend limit for the whole organisation and a monthly spend limit for each member, or disable usage credits entirely. Server-managed settings are available on Team and Enterprise and need the Owner or Primary Owner role; through them an admin can set `forceLoginMethod` / `forceLoginOrgUUID` to require that members' logins belong to the organisation. Org analytics show estimated spend per user and per model, and adoption metrics.
- **Enterprise** costs "US$20/seat/month, billed annually", needs "a minimum of 20 seats", and bills usage on top at API rates. Its single Enterprise seat includes Claude Code. Admins set organisation-level and individual-level spend limits, which work hierarchically. Enterprise adds SCIM, audit logs, role-based permissions and the Compliance API, and the Enterprise Analytics API "returns per-user usage and cost reports".

**Two Anthropic pages conflict on Enterprise.** The Enterprise billing support article says "Enterprise seats don't come with an individual token allowance. All usage across your organization is billed together at API rates, regardless of who consumed it", and that on self-serve Enterprise "Everyone's usage draws from the same credit balance." The Claude Code costs page says "On Claude for Teams and Enterprise plans, each member's Claude Code usage draws from a per-seat allowance that resets on a rolling five-hour window and a weekly window." Both are Anthropic's own pages, both were retrieved the same day, and this entry prefers neither.

**Inference:** the costs page's per-seat-allowance paragraph fits Team and legacy seat-based Enterprise (the Team-and-Enterprise support article still names older Enterprise plans with seat-based billing); for current, usage-based Enterprise the support article is the more specific source. That reading resolves the conflict but is not stated by either page, so which page describes current Enterprise is left for §7. Separately, the seat-management article speaks of seats assigned to named members ("assign and reassign users") but does not use the words "one person per seat".

### P2. Can a Team or Enterprise seat sign Claude Code in non-interactively, with `claude setup-token` and `CLAUDE_CODE_OAUTH_TOKEN`?

**Status:** `partly documented`

**Answer:** Yes. `claude setup-token` runs the same browser authorisation as `/login` once, then prints "a one-year OAuth token" without saving it; setting it as `CLAUDE_CODE_OAUTH_TOKEN` signs Claude Code in without a browser. The token "requires a Pro, Max, Team, or Enterprise plan" (Free is not listed) and is inference-only: "It can only make model requests, so it can't establish Remote Control sessions or fetch claude.ai connectors." Bare mode (`--bare`) does not read it. The token belongs to one person: on GitHub Actions, "an OAuth token is tied to the subscription of the person who ran `claude setup-token`", and for a secret shared across repositories Anthropic's GitHub Actions page points to a Console API key instead. Deleting the repository secret does not end the token: "If you delete a secret, the credential it held stays valid." An organisation's `forceLoginOrgUUID` does not bind `setup-token`, which enforces only `forceLoginMethod`, "so they can mint a token in a different organization". Server-managed settings are still delivered to a session running on a `CLAUDE_CODE_OAUTH_TOKEN` token. For contrast, the scope that controls cloud sessions is capped server-side at 30 days, which the one-year token does not cover.

**Not documented:** how to revoke a `setup-token` token, and whether a Team or Enterprise admin can see or revoke a member's tokens. Pages checked: authentication, cli-reference, env-vars, github-actions, server-managed-settings, costs, and a full-text search of `https://code.claude.com/docs/llms-full.txt` for "revoke". No page checked says either that a Team seat holder's token must not be given to another person; that rule comes from the terms and the legal-and-compliance page (P4).

### P5. What happens to one person's subscription limits when teammates use it?

**Status:** `partly documented`

**Answer:** A subscription's usage is metered per account, or per seat on Team, and every surface draws on the same limit: claude.ai, Claude Code and Claude Desktop "counts towards the same usage limit". The limit has a five-hour session window and a weekly window, and on Pro and Max Anthropic may add other caps at its discretion. "Advertised usage limits for Pro and Max plans assume ordinary, individual usage of Claude Code and the Agent SDK." On Team, limits are per member and not pooled. For contrast, Claude Console (API) rate limits "apply at the organization level, not per individual user". `claude -p`, the Agent SDK and third-party app usage currently draw from the subscription's own limits: the support article announcing a separate Agent SDK credit says the change is paused and "For now, nothing has changed". The same article's preserved text, which the page marks as not in effect, says the credits were to be per user and not poolable, and that "Teams running shared production automation should use Claude Platform with an API key for predictable pay-as-you-go billing."

**Not documented:** whether usage through a `setup-token` token counts differently from interactive usage. The planning session's evidence records this as silent across the Claude Code pages it fetched for P2, and names no page checked for this point specifically.

**Inference:** a `setup-token` token draws on the same per-seat or per-account limits as the minting user's interactive use, since it "authenticates with your Claude subscription" and all surfaces share one limit. So if teammates run Claude Code on one person's subscription token (Pro, Max or a Team seat), every request draws down that one account's five-hour and weekly windows, and the teammates and the owner exhaust a single allowance together. On Team, the other seats' allowances are untouched and cannot be borrowed: no pooling exists except usage credits, which are billed at API rates and charged to the token owner's member limits. Separately, the terms forbid it on consumer plans (§ 2, "make your Account available to anyone else"), and for all plans the docs and support pages say subscription OAuth is "intended exclusively for purchasers", that "Subscription plans can only be used by subscribers", and that an OAuth token "is tied to the subscription of the person who ran `claude setup-token`" (P2, P4).

### R2. Who owns a Console API key, and who may use it?

**Status:** `documented`

**Answer:** There are three key types, each with a different owner and a different event that retires it.

| Key type | Owner | Retired when |
|---|---|---|
| **Personal key** | "You, the user, with your roles and permissions" | "You lose access to the organization or, for a single-workspace key, to that workspace. Personal keys are archived when you are removed from the organization." |
| **Service account key** | "A service account" | "The service account is archived or, for a single-workspace key, is removed from that workspace" |
| **Workspace key** (legacy) | "No one: it belongs to the workspace it was created in" | "It expires, is disabled or deleted, or its workspace is archived, regardless of whether its creator leaves the organization" |

- **Anthropic's guidance.** "Use a personal key for your own development and scripts. A shared personal key acts as one person and breaks when they leave. For shared or automated workloads (CI, production services), have an organization admin create a service account so the workload has its own identity." Workspace keys "should be considered legacy; identity-backed keys or Workload Identity Federation are preferred" (federation is R6).
- **How a key is bound.** A key's **Linked account** is set "to yourself for a personal key, or to a service account for a key shared across multiple users". "A **personal key** or **service account key** acts as its user or service account", and "Every request runs in exactly one workspace": a single-workspace key's own, or for a multi-workspace key the one its `anthropic-workspace-id` header names.
- **The owner is machine-readable.** The Admin API reports each key's `principal`: `{"type": "user_actor", "user_id": "user_..."}` for a personal key, `{"type": "service_account_actor", "service_account_id": "svac_..."}` for a service account key, and `null` for a workspace key.
- **Who may use it under the terms.** The legal-and-compliance page does not restrict API keys provisioned "for use by the customer's own authorized users", provided the usage is billed to the key owner (P4).
- **The Claude Code workspace's keys** are per member and stop working when that member is removed (R1).

### R3. What limits a Console organisation's spend and request rate, and at what level?

**Status:** `documented`

### R5. How does a team run Claude Code through Amazon Bedrock or Google Vertex AI: credentials, per-user attribution, and GitHub Actions?

**Status:** `partly documented`

**Answer — what Anthropic's Claude Code pages say.**

- **Billing.** On Bedrock, Google Cloud's Agent Platform and Microsoft Foundry, "Claude Code is billed per token to your cloud account, and spend controls live in your cloud provider's billing console." - **Bedrock, per caller.** With IAM principal data enabled in CUR 2.0 ("Include caller identity (IAM principal) allocation data"), AWS "automatically records the caller identity (IAM principal ARN) for each Bedrock API call in the line_item_iam_principal column", in forms that include `user/...`, `role/...` and `assumed-role/<role>/<session-name>`; tags on the principal are captured with the costs. ### R6. How does workload identity federation take a GitHub Actions job to the Claude API, and does the stock `claude` CLI support it?

**Status:** `partly documented`

**Answer — the exchange.**

- **What it is.** "With Workload Identity Federation, your workflow exchanges that token for a short-lived Anthropic access token, so your CI jobs can call the Claude API without an `ANTHROPIC_API_KEY` secret stored in your repository." The token acts as a Claude Console service account: Anthropic's GitHub Actions page describes the exchange as "through a Claude Console service account", and the action's setup guide's first step is "**Create a service account** (Settings → Service accounts) and add it to the workspace it should act in." Anthropic's key guidance prefers federation, or identity-backed keys, to workspace keys (R2).
- **What the job needs.** "GitHub only issues an identity token to jobs that explicitly request it. Add the `id-token: write` permission at the workflow or job level".
- **Lifetimes.** "Each GitHub-issued identity token expires roughly five minutes after issuance", but the token-request endpoint "stays valid for the entire job". "For jobs that run longer than the Anthropic token's lifetime, the SDK re-reads `ANTHROPIC_IDENTITY_TOKEN_FILE` on each refresh, so re-run the fetch step periodically (or wrap it in a background loop) to keep the file current." The Anthropic token's lifetime is the rule's `token_lifetime_seconds`: "Integer between `60` and `86400` (1 minute to 24 hours). Default `3600`."
- **What a rule matches.** The `sub` claim takes the forms `repo:<owner>/<repo>:ref:refs/heads/<branch>` for a push to a branch, `repo:<owner>/<repo>:pull_request` for pull-request runs, and `repo:<owner>/<repo>:environment:<name>` for environment-gated deployments; a rule "matches against this claim (and others, such as `repository_owner` and `ref`)". The page's sample decoded token carries `iss`, `sub`, `aud`, `repository`, `repository_owner`, `ref`, `sha`, `workflow`, `actor` and `event_name`. A rule's matchers are a `subject_prefix`; `claims`, where "Each key is a top-level claim name and each value is the required exact string value"; and a `condition`, "A CEL expression that must evaluate to `true`" over "The full decoded JWT claim set". "All populated fields are evaluated with AND semantics: the JWT must satisfy every populated matcher."
- **The fork warning.** "A `subject_prefix` of `repo:your-org/*` alone matches every repository in your organization, and without a `ref` constraint it also matches `pull_request` runs triggered from forks. Anyone who can open a pull request against a matching repository could obtain a federated Anthropic token." The page advises pinning `"ref": "refs/heads/main"` under `claims`, or, for deploy jobs, a `subject_prefix` on a deployment environment gated by required reviewers.
- **Billing.** A rule's `workspace_id` is "The workspace (`wrkspc_...`) whose quota, billing, and rate limits apply to tokens minted under this rule."
- **Failures.** "Every assertion denial returns the same opaque `401` `authentication_error` with the fixed message `Authentication failed`, regardless of which check failed"; the reason is recorded in the authentication history.
- **In `anthropics/claude-code-action`.** The inputs are `anthropic_federation_rule_id` (`fdrl_...`) with `anthropic_organization_id`, and optionally `anthropic_service_account_id` (`svac_...`). "Do not set `anthropic_api_key` or `claude_code_oauth_token` alongside the federation inputs — a static credential takes precedence and federation will not be used." Inline comment classification "currently requires `anthropic_api_key`; with federation it is skipped".

**Answer — the `claude` CLI.** Claude Code lists "Anthropic profile and Workload Identity Federation credentials" among its supported authentication types. It takes the federation route when `ANTHROPIC_FEDERATION_RULE_ID` and `ANTHROPIC_ORGANIZATION_ID` are both set, and "also reads the other variables in the WIF reference, such as `ANTHROPIC_IDENTITY_TOKEN_FILE`". The WIF reference's own direct environment-variable path activates only when four are set: those two, `ANTHROPIC_SERVICE_ACCOUNT_ID`, and one of `ANTHROPIC_IDENTITY_TOKEN_FILE` or `ANTHROPIC_IDENTITY_TOKEN`. Federation ranks below both static credentials, in the precedence list's own words:

> "3. `ANTHROPIC_API_KEY` environment variable. … In non-interactive mode (`-p`), the key is always used when present."
> "5. `CLAUDE_CODE_OAUTH_TOKEN` environment variable. A long-lived OAuth token generated by `claude setup-token`. Use this for CI pipelines and scripts where browser login isn't available."
> "6. Anthropic profile and federation credentials, the credentials that the `ant` CLI and Workload Identity Federation use."

So a job that authenticates through federation leaves both `ANTHROPIC_API_KEY` and `CLAUDE_CODE_OAUTH_TOKEN` unset, and blanking one is not enough: "A variable that is set to an empty string still occupies its slot in the credential precedence chain. If `ANTHROPIC_API_KEY=""` is exported, the SDK selects the API-key path with an empty key rather than falling through to federation. Unset unused credential variables rather than blanking them." Claude Code "doesn't read profiles or federation variables in bare mode, in Claude Desktop, or in cloud sessions", and "Cloud sessions always use your subscription credentials."

**Inference:** `actor` is a top-level claim of GitHub's token and `claims` takes any top-level claim name, so a rule can be bound to one GitHub login with `"claims": {"actor": "<login>"}`, a value GitHub signs and a writer to the repository cannot forge. Not tested in this research.

## 3. GitHub's side

### G1. Which Actions secret scopes exist, what may a secret be named, and is any scope per user?

**Status:** `partly documented`

**Answer:**

- **Three scopes.** "Secrets allow you to store sensitive information in your organization, repository, or repository environments." Where one name exists at several levels, "the secret at the lowest level takes precedence": an environment secret wins over a repository secret, and a repository secret over an organisation secret. "GitHub Actions can only read a secret if you explicitly include the secret in a workflow."
- **Who creates them.** A secret for an organisation repository needs `write` access; an environment secret in an organisation repository needs `admin` access. "Organization-level secrets and variables are not accessible by private repositories for GitHub Free."
- **Two stores that are not Actions secrets.** Codespaces keeps secrets on a personal account: "You can add development environment secrets to your personal account that you want to use in your codespaces", and each "is exported as an environment variable into the user's terminal session." Dependabot keeps its own: "When a Dependabot event triggers a workflow, the only secrets available to the workflow are Dependabot secrets." Dependabot secrets are not per user.
- **Names.** A name "Can only contain alphanumeric characters (`[a-z]`, `[A-Z]`, `[0-9]`) or underscores (`_`)", "Must not start with the `GITHUB_` prefix", "Must not start with a number", and is case-insensitive: "GitHub stores secret names as uppercase regardless of how they are entered." A GitHub login "can only contain alphanumeric characters and dashes (`-`)."
- **Counts and size.** "You can store up to 1,000 organization secrets, 100 repository secrets, and 100 environment secrets." A workflow can use all 100 repository secrets, all 100 environment secrets and, when more are assigned, "the first 100 organization secrets (sorted alphabetically by secret name)". "Secrets are limited to 48 KB in size." "Organization and repository secrets are read when a workflow run is queued, and environment secrets are read when a job referencing the environment starts."

**Not documented:** a per-user Actions secret. No page checked describes one; the only scopes listed are organisation, repository and environment. Pages checked: concepts/security/secrets, reference/security/secrets, how-tos/.../use-secrets, reference/workflows-and-actions/contexts (the `secrets` context), reference/workflows-and-actions/deployments-and-environments. Whether Codespaces user secrets reach Actions: the Codespaces page does not say, and a docs.github.com search for that statement found nothing. A limit on the number of environments: none was found on the pages checked, apart from the 255-character name limit (G3).

**Inference:**

- GitHub has no per-user Actions secret store, and Codespaces user secrets are not available to Actions: the `secrets` context holds the secrets "that are available to a workflow run", and the Actions scopes include no user scope.
- A login containing `-` cannot be a secret-name component as is. Mapping `-` to `_` is not guaranteed injective, because Enterprise Managed User logins carry an `_SHORTCODE` suffix, so `_` occurs in some logins. Keying on `github.actor_id`, which is numeric (G2), avoids this; because a name must not start with a digit, it still needs a prefix, as in `CLAUDE_TOKEN_1234567`.
- One repository secret per login caps a team at about 100 members per repository, minus the repository's other secrets. Environment secrets are limited per environment, so one environment per member (G3) scales with the number of environments.

### G2. How is the person who started a run named, and what happens on a re-run?

**Status:** `documented`

**Answer:** `github.actor` is "The username of the user that triggered the initial workflow run", and `github.actor_id` is "The account ID of the person or app that triggered the initial workflow run", which "is different from the actor username". `github.triggering_actor`, also exposed as `GITHUB_TRIGGERING_ACTOR`, is "The username of the user that initiated the workflow run." On a re-run the two can differ, and the run keeps the first one's privileges: "Any workflow re-runs will use the privileges of `github.actor`, even if the actor initiating the re-run (`github.triggering_actor`) has different privileges." A re-run also keeps "the same `GITHUB_SHA` (commit SHA) and `GITHUB_REF` (git ref) of the original event", and "A workflow run can be re-run a maximum of 50 times."

**Inference:** a credential chosen by `github.actor` lets member B's re-run of member A's run spend A's credential, because `actor` stays A. The evidence names two ways to close that: select on `github.triggering_actor`, which follows whoever started the re-run, or refuse to run when `triggering_actor` differs from `actor`, for example in a job-level `if:`, which can read the `github` context (G4).

### G3. Can each member have an environment holding that member's secret, and what protects it?

**Status:** `partly documented`

**Answer:**

- **A computed environment name.** For `jobs.<job_id>.environment`, "The value of `name` can be an expression. Allowed expression contexts: `github`, `inputs`, `vars`, `needs`, `strategy`, and `matrix`." "Environment names are not case sensitive. An environment name may not exceed 255 characters and must be unique within the repository."
- **A missing environment is created empty.** "Running a workflow that references an environment that does not exist will create an environment with the referenced name. ... Otherwise, the newly created environment will not have any protection rules or secrets configured. Anyone that can edit workflows in the repository can create environments via a workflow file, but only repository admins can configure the environment." A secret that is not set reads as an empty string: "If a secret has not been set, the return value of an expression referencing the secret ... will be an empty string."
- **The secrets wait for the rules.** "Secrets stored in an environment are only available to workflow jobs that reference the environment. If the environment requires approval, a job cannot access environment secrets until one of the required reviewers approves it." "All deployment protection rules must pass before a job referencing the environment is sent to a runner." `deployment: false` uses an environment's secrets without creating a deployment object, and "is not compatible with custom deployment protection rules."
- **Required reviewers.** "You can list up to six users or teams as reviewers." "Only one of the required reviewers needs to approve the job for it to proceed." With self-review prevented, "users who initiate a deployment cannot approve the deployment job, even if they are a required reviewer." "By default, administrators can bypass the protection rules and force deployments to specific environments", unless the environment is configured "to prevent admins from bypassing configured protection rules."
- **Deployment branches and tags.** "The deployment branch or tag rule is matched against the `GITHUB_REF` of the workflow run." Under **Protected branches only**, "If no branch protection rules are defined for any branch in the repository, then all branches can deploy."
- **Custom deployment protection rules** "are currently in public preview and subject to change", gate deployments "with third-party services", and "a maximum of 6 deployment protection rules can be enabled on any environment at the same time."
- **Plans, for a private repository.** "If you are on a GitHub Free, GitHub Pro, or GitHub Team plan, required reviewers are only available for public repositories." Deployment branches and tags are available for private repositories on GitHub Pro or GitHub Team. "Custom deployment protection rules are only available for public repositories for users on GitHub Free, GitHub Pro, and GitHub Team plans." "If you are using GitHub Free, environment secrets are only available in public repositories."
- **Self-hosted runners.** "Workflows that run on self-hosted runners are not run in an isolated container, even if they use environments." (G6)

**Not documented:** a custom protection rule that approves a job only when the run's actor matches the environment's owner. The pages checked describe custom rules in general, not this check.

**Inference:**

- An environment named after the actor, such as `name: ${{ github.triggering_actor }}` or `name: ${{ format('claude-{0}', github.actor) }}`, is legal as documented, and login casing does not matter.
- It does not fail closed. A login with no configured environment silently gets a new, empty one, and the job runs with an empty secret; nothing fails unless the workflow itself checks that the secret is non-empty.
- With "required reviewer = that member" and self-review allowed, every run waits for that member's manual approval, which defeats unattended runs. With self-review prevented, the member cannot approve their own run.
- A custom protection-rule GitHub App could approve only when the run's actor matches the environment's owner, which would enforce the per-member binding on GitHub's side without a manual approval.
- **Security cost.** Without a protection rule, any writer can set `environment: <other-member>` in a modified workflow and read that member's secret. Only required reviewers or a deployment branch rule close that (G7), and required reviewers on a private repository need GitHub Enterprise.

### G4. Can a workflow pick one secret per login with an expression?

**Status:** `partly documented`

**Answer:** Contexts take two syntaxes, "Index syntax: `github['sha']`" and "Property dereference syntax: `github.sha`", and "If you attempt to dereference a nonexistent property, it will evaluate to an empty string." The expressions page lists `[ ]` as "Index" and documents `format( string, replaceValue0, replaceValue1, ..., replaceValueN)`. The `secrets` context itself is documented only as `secrets.<secret_name>`. `secrets` may be used in `env`, `jobs.<job_id>.env`, `jobs.<job_id>.steps.env`, `.steps.with`, `.steps.run` and `jobs.<job_id>.secrets.<secrets_id>`, and not in `jobs.<job_id>.if`, `jobs.<job_id>.steps.if`, `jobs.<job_id>.environment` or `runs-on`: "Secrets cannot be directly referenced in `if:` conditionals." A secret that is not set reads as an empty string (G3). Redaction is best-effort: "Because there are multiple ways a secret value can be transformed, this redaction is not guaranteed. Additionally, the runner can only redact secrets used within the current job."

**Not documented:** computed indexing of `secrets`, as in `secrets[format('CLAUDE_TOKEN_{0}', github.actor)]`. No page checked shows it or forbids it, and a full-text search of every fetched page for the literal `secrets[` found no hits. Pages checked: contexts, expressions, workflow-syntax, use-secrets, reference/security/secrets, concepts/security/secrets, secure-use. It needs a live test.

**Inference:**

- The general index operator on contexts suggests a computed key evaluates, but that is not a documented guarantee. Either way, every repository and organisation secret is already loaded when the run is queued (G1), and an unknown key returns an empty string, so the lookup does not fail closed.
- **Security cost.** This is the weakest of the four patterns. Every member's token sits in one repository-scoped pool, and any writer who edits the workflow, on any branch reachable by `workflow_dispatch` or `pull_request_review` (G7), can reference `secrets.CLAUDE_TOKEN_OTHERMEMBER` directly. Redaction only hides printed values; sending a value to a remote host, or transforming it, defeats it.

### G5. Can an external secret store release a member's credential through GitHub's OIDC token?

**Status:** `partly documented`

**Answer:**

- **The permission.** "The job or workflow must grant the `id-token: write` permission to allow GitHub's OIDC provider to create a JSON Web Token (JWT)". "This setting only enables fetching and setting the OIDC token; it does not grant write access to other resources."
- **The claims.** `actor`: "The personal account that initiated the workflow run." `actor_id`: "The ID of personal account that initiated the workflow run." `environment`: "The name of the environment used by the job." `event_name`: "The name of the event that triggered the workflow run." `job_workflow_ref`: "For jobs using a reusable workflow, the ref path to the reusable workflow." `workflow_ref`: "The ref path to the workflow." `ref`: "The git ref that triggered the workflow run." The live discovery document's `claims_supported` lists `actor`, `actor_id`, `environment`, `job_workflow_ref`, `event_name`, `ref_protected`, `run_attempt` and others. There is **no `triggering_actor` claim** (G2).
- **Trust conditions.** "To control how your cloud provider issues access tokens, you **must** define at least one condition, so that untrusted repositories can't request access tokens for your cloud resources." Admins can choose, through the REST API, the claims the `sub` claim carries; for `include_claim_keys`, "Each claim key can only contain alphanumeric characters and underscores." When a job references an environment, "The subject claim includes the environment name", as `repo:ORG-NAME/REPO-NAME:environment:ENVIRONMENT-NAME`.
- **HashiCorp Vault** binds on any claim: GitHub's example role sets `"user_claim": "actor"`, and "To check arbitrary claims in the received JWT payload, the `bound_claims` parameter contains a set of claims and their required values."
- **AWS**: "Support for custom claims for OIDC is unavailable in AWS." The trust policy conditions on `sub`.
- **Google Cloud and Azure.** GitHub's Google Cloud page says "Configure the mapping and add conditions"; its Azure page defers to the OIDC reference.
- **The Anthropic-side analogue** is a workload identity federation rule's `claims` matcher, which R6 records.

**Not documented:** whether `actor` is accepted in `include_claim_keys`: the page's examples name other claims only. Actor-specific conditions on Google Cloud and Azure: GitHub's pages do not cover them, and the detail lives in each provider's own documentation, which this research did not take as a GitHub primary source. Which person is the `actor` for each trigger event.

**Inference:**

- `actor` and `actor_id` are listed custom claims, so `include_claim_keys` plausibly accepts them.
- A Vault role per member with `bound_claims` on `repository` and `actor_id`, or a templated policy keyed on `user_claim`, can release only that member's secret. This is the documented route to a condition directly on the actor.
- On AWS the actor is reachable only by customising `sub` to include it, which is undocumented for `actor`, or by a `sub` carrying `environment:<member>`, which combines this pattern with G3.
- **Security cost.** GitHub sets `actor` from the event and workflow YAML cannot forge it, so a writer who edits the workflow can obtain only a token bound to their own actor. This is the strongest of the four patterns, with these caveats: a re-run keeps the original `actor` (G2), so member B re-running A's run gets a token as A; any step in the job can read the fetched credential, so a modified workflow can still exfiltrate the actor's own credential; a store that does not also bind `repository`, and `workflow_ref`, `job_workflow_ref` or `ref`, lets the same member use it from an arbitrary repository or branch; and for some events the actor is not the member: `issue_comment` and `issues` come from whoever commented or labelled, and `repository_dispatch` from the owner of the token that called the API.

### G6. Can each member's runs go to a self-hosted runner holding that member's login?

**Status:** `partly documented`

**Answer:**

- **Routing.** "You can target runners based on the labels assigned to them, or their group membership, or a combination of these." `runs-on` accepts the `github`, `needs`, `strategy`, `matrix`, `vars` and `inputs` contexts. With no matching runner online, "the job will remain queued until a runner comes online", and "until the 24 hour timeout period expires."
- **Persistence.** "**Self-hosted** runners for GitHub do not have guarantees around running in ephemeral clean virtual machines, and can be persistently compromised by untrusted code in a workflow." Anyone who can fork a private repository and open a pull request can compromise the runner's environment, "including gaining access to secrets and the `GITHUB_TOKEN`", and environments with required reviews give no isolation there. "there is no way to guarantee that a self-hosted runner only runs one job." "When a self-hosted runner is defined at the organization or enterprise level, GitHub can schedule workflows from multiple repositories onto the same runner."
- **Runner groups.** A group can be "accessible to a specific list of repositories, or to all repositories in the organization." "To control access to runners at the organization level, organizations using the GitHub Team plan can use runner groups." Restricting a group to selected workflows, pinned to a branch, is documented only on the GitHub Enterprise Cloud version of the page: "Only jobs directly defined within the selected workflows will have access to the runner group."
- **The harness's existing warning.** [`remote-execution.md`](remote-execution.md) → `## 11. Security` already warns that a persistent self-hosted runner on a public repository can be targeted by a workflow a fork's pull request adds or rewrites.

**Not documented:** gating a runner by actor. No page checked restricts which person's runs may reach a runner.

**Inference:**

- `runs-on: [self-hosted, ${{ github.actor }}]` is legal as documented, from the context-availability table.
- **Security cost.** Labels are not access control. Any workflow in a repository that can reach the runner or its group can target a member's label, including one a writer modified (G7), and that job then runs on the member's machine with the member's login on disk; a job reaching member A's runner can be triggered by member B. A runner group restricted to selected workflows pinned to a branch (Enterprise Cloud) narrows this to a named workflow file at a named ref.

### G7. Who can read a secret by changing a workflow?

**Status:** `partly documented`

**Answer:**

- **GitHub's statement.** "Any user with write access to your repository has read access to all secrets configured in your repository."
- **Which file runs.** "Each workflow run will use the version of the workflow that is present in the associated commit SHA or Git ref of the event." For the events a per-member design would listen to:

  | Event | `GITHUB_SHA` | `GITHUB_REF` | Note on the page |
  |---|---|---|---|
  | `workflow_dispatch` | "Last commit on the `GITHUB_REF` branch or tag" | "Branch or tag that received dispatch" | "This event will only trigger a workflow run if the workflow file exists on the default branch." |
  | `pull_request_review` | "Last merge commit on the `GITHUB_REF` branch" | "PR merge branch `refs/pull/PULL_REQUEST_NUMBER/merge`" | no default-branch note |
  | `issues` | "Last commit on default branch" | "Default branch" | the same default-branch note |
  | `issue_comment` | "Last commit on default branch" | "Default branch" | the same default-branch note |
  | `repository_dispatch` | "Last commit on default branch" | "Default branch" | the same default-branch note |

  "Once a workflow has run at least once, you can dispatch it against any branch or tag via the GitHub API or GitHub CLI." Dispatching needs write access, and "To run a workflow on a branch other than the repository's default branch, use the `--ref` flag."
- **Environments.** "The deployment branch or tag rule is matched against the `GITHUB_REF` of the workflow run", and environment secrets are reached only "after any configured rules (for example, required reviewers) pass." Repository and organisation secrets are "read when a workflow run is queued" (G1).
- **`permissions:`** modifies "the default permissions granted to the `GITHUB_TOKEN`", and "Owners of an organization can restrict write access for the `GITHUB_TOKEN` at the repository level." `id-token: write` "only enables fetching and setting the OIDC token" (G5).
- **Fork pull requests** get no secret: "With the exception of `GITHUB_TOKEN`, secrets are not passed to the runner when a workflow is triggered from a forked repository. The `GITHUB_TOKEN` has read-only permissions in pull requests from forked repositories." [`github-integration-research.md`](github-integration-research.md) → C2 records what a fork's `pull_request_review` and `issue_comment` events get.
- **CODEOWNERS** on `.github/workflows` means "any proposed changes to these files will first require approval from a designated reviewer."
- **A compromised third-party action** "would have access to all secrets configured on your repository, and may be able to use the `GITHUB_TOKEN` to write to the repository."

**Not documented:** that `permissions:` restricts access to `secrets.*`. No page checked says it does. That a deployment branch rule keeps environment secrets from an unmerged workflow edit: no page states it as one sentence.

**Inference:**

- `issues`, `issue_comment` and `repository_dispatch` run the default branch's workflow file, so a modified workflow must be merged before these triggers run it, and the default branch's protection, rulesets and CODEOWNERS are the gate.
- A writer can push a branch carrying a modified copy and run it with `workflow_dispatch --ref <branch>`, so the modified YAML runs with the repository's and the organisation's secrets. A writer who opens a same-repository pull request that edits the workflow has the edited version run when any review is submitted, since `pull_request_review` runs the pull request's merge commit.
- A deployment branch rule naming only the default branch keeps environment secrets from both routes: a dispatch on a feature branch has `GITHUB_REF = refs/heads/<branch>` and a review has `refs/pull/N/merge`, and neither matches. The default-branch triggers match, but they run the default branch's file. Required reviewers stop it too, and with self-review prevented the writer cannot approve their own run. Repository and organisation secrets have no equivalent gate. Two caveats: **Protected branches only** lets every branch deploy when no branch protection exists, and administrator bypass is on by default (G3); and on a self-hosted runner environments give no isolation (G6).
- `permissions:` scopes only the `GITHUB_TOKEN`, and gates the OIDC token through `id-token`; it has no effect on whether a job can read a repository, organisation or environment secret. A writer modifying the workflow can raise it, within the maximum the organisation or repository owners set.
- CODEOWNERS gates **merging** into a protected branch. It does not stop a push to an unprotected branch, nor a `workflow_dispatch --ref` or `pull_request_review` run of the unmerged edit.

### G8. What can an organisation control?

**Status:** `partly documented`

**Answer:**

- **Secret visibility by repository.** "When creating a secret or variable in an organization, you can use a policy to limit access by repository. For example, you can grant access to all repositories, or limit access to only private repositories or a specified list of repositories." "By default, the secret is only available to private repositories."
- **Push rulesets.** "With push rulesets, you can block pushes to a private or internal repository and that repository's entire fork network based on file extensions, file path lengths, file and folder paths, and file sizes." "Push rules do not require any branch targeting because they apply to every push to the repository." The **Restrict file paths** rule prevents "commits that include changes in specified file paths from being pushed to the repository", up to 200 entries. A ruleset can name users who bypass it. Rulesets are for "customers on GitHub Team and GitHub Enterprise plans", and organisation-level rulesets for "organizations on the GitHub Enterprise plan".
- **Path-based required reviewers.** A branch ruleset can "require review or approval from specific teams when a pull request changes certain files or directories", up to 15 teams; "This rule is not available on user-owned repositories as they do not contain teams."
- **CODEOWNERS.** "The people you choose as code owners must have write permissions for the repository." Enforcement is a branch protection option: "Require review from Code Owners".
- **Required workflows** (GitHub Enterprise Cloud): "Ruleset workflows can be configured at the organization or enterprise level to require workflows to pass before merging pull requests."
- **Runners and `GITHUB_TOKEN`.** "Organization owners can choose which repositories are allowed to create repository-level self-hosted runners." "Owners of an organization can restrict write access for the `GITHUB_TOKEN` at the repository level." Runner groups restricted to selected workflows are in G6.

**Not documented:** whether a composite action or script the workflow calls, living outside `.github/workflows`, also needs restricting by a push ruleset.

**Inference:**

- Secret visibility is per repository only; there is no per-user or per-actor visibility.
- A push ruleset restricting `.github/workflows/**`, with a bypass list of trusted maintainers, stops ordinary writers from pushing **any** branch carrying a modified workflow, which closes the `workflow_dispatch --ref` and `pull_request_review` routes of G7. It applies only to private and internal repositories. Files the workflow calls from outside that path would need restricting too, because they run with the job's secrets.
- CODEOWNERS and path-based required reviewers gate merges only (G7).
- A required workflow enforces that a centrally owned workflow runs as a merge gate; it does not restrict who can edit workflows in the target repository.

### G9. `HARNESS_GIT_TOKEN`: per-member fine-grained tokens, or a GitHub App installation token?

**Status:** `partly documented`

**Answer:** [`github-run-control.md`](github-run-control.md) → `## 4. The draft pull request` opens the draft pull request with the `HARNESS_GIT_TOKEN` secret when it is set, and [`remote-execution.md`](remote-execution.md) → `## 11. Security` says a run cannot push a workflow-file edit without a workflow-capable `HARNESS_GIT_TOKEN`. What GitHub documents about the two kinds of token that secret could hold:

- **Authorship.** "An installation token identifies the app as a GitHub App bot account, such as @jenkins\[bot]", and "API requests made by an app installation are attributed to the app." A personal access token acts as its owner: "Personal access tokens are intended to access GitHub resources on behalf of yourself. To access resources on behalf of an organization, or for long-lived integrations, you should use a GitHub App." Both kinds of personal access token "are tied to the user who generated them and will become inactive if the user loses access to the resource." A commit's author is set by its email, not by the token that pushes it: "GitHub links a commit to a user by matching the email address in the commit header to an email address on a GitHub account." A bot signature is verified only for a request authenticated as the App that "contains no custom author information, custom committer information, and no custom signature information, such as Commits API."
- **Approvals.** "Pull request authors cannot approve their own pull requests." **Request changes** "is purely informational and will not prevent merging unless a ruleset or classic branch protection rule is configured with the "require a pull request" option"; under such a rule, "the pull request cannot be merged until the same collaborator submits another review approving the changes". A ruleset can "require an approval from someone other than the last person to push to a branch before a pull request can be merged."
- **Which pushes start workflows.** Events raised with `GITHUB_TOKEN` "will not create a new workflow run", except `workflow_dispatch` and `repository_dispatch`, and `pull_request` runs a `GITHUB_TOKEN` creates wait in an **approval-required** state; "a GitHub App installation access token or a personal access token" triggers them normally. [`github-integration-research.md`](github-integration-research.md) → S3 records the measured side of this.
- **Rate limits.** A personal access token: "your personal rate limit of 5,000 requests per hour". An App installation: "the installation's minimum rate limit of 5,000 requests per hour", scaling with users and repositories, and "The rate limit cannot increase beyond 12,500 requests per hour", or 15,000 on a GitHub Enterprise Cloud organisation. `GITHUB_TOKEN`: "1,000 requests per hour per repository". Content creation: "no more than 80 content-generating requests per minute and no more than 500 content-generating requests per hour".
- **Organisation and enterprise policies on personal access tokens.** An organisation can restrict access by personal access tokens, for fine-grained and classic tokens separately; "By default, both Personal access tokens (classic) and fine-grained personal access tokens are enabled." For fine-grained tokens, "the default the maximum lifetime policy for organizations is set to expire within 366 days", and "Require administrator approval" "is the default value"; "Only fine-grained personal access tokens, not personal access tokens (classic), are subject to approval." An enterprise's restriction binds its organisations: "Organizations cannot override this setting." A user can create at most 50 fine-grained tokens.
- **Minting an App token in a workflow.** GitHub documents `actions/create-github-app-token@v3`, with the App's client ID as a configuration variable and its private key as a secret. "The installation access token will expire after 1 hour." The App needs the **Contents** permission for Git access and **Workflows** to edit `.github/workflows`, and opening a pull request needs **Pull requests** write. GitHub recommends an App for organisation automation: "A GitHub App installed on an organization is not dependent on a user. Additionally, unlike a user, a GitHub App does not consume a GitHub seat."
- **Machine accounts, in GitHub's Terms.** "You must be a human to create an Account. Accounts registered by "bots" or other automated methods are not permitted. We do permit machine accounts:" "A machine account is an Account set up by an individual human who accepts the Terms on behalf of the Account, provides a valid email address, and is responsible for its actions. A machine account is used exclusively for performing automated tasks. Multiple users may direct the actions of a machine account, but the owner of the Account is ultimately responsible for the machine's actions. You may maintain no more than one free machine account in addition to your free Personal Account." "Your login may only be used by one person — i.e., a single login may not be shared by multiple people." "A machine user account consumes a GitHub Enterprise seat"; "GitHub App bots do not consume a GitHub Enterprise seat."

**Not documented:** that a pull request's author cannot **request changes** on their own pull request. [`github-run-control.md`](github-run-control.md) → `## 4. The draft pull request` states that rule ("GitHub does not let a pull request's author request changes on their own pull request"), and its `## 8. What is not verified here` lists it as "GitHub's documented rule, not retrieved here". This research found no GitHub page stating it: the four pull-request review pages and the REST pull-request reviews page, which lists only `APPROVE`, `REQUEST_CHANGES` and `COMMENT`, say nothing either way. It stays a live-test question. Also not documented on the pages checked: the email address format that makes a commit show as an App's bot.

**Inference:**

- With per-member fine-grained tokens, each member's token needs one owner approval by default. A pull request opened with member X's token is authored by X, so X cannot approve it, and X counts as "the last person to push" for fix-round pushes made with that token. The evidence's own reading, not from a source and needing a live check, is that GitHub's interface hides both **Approve** and **Request changes** on one's own pull request and the API answers `422` for either.
- With an App installation token, the pull request's author and the last pusher are the App's bot. To make commits show as the bot, the git author has to be set to the bot's identity; that address format is unverified here. A session longer than an hour has to re-mint the token, or keep the private key available to do so.
- A shared machine account's token makes the machine account the pull request's author, so every member can review it; it costs a seat in a paid organisation and makes one human responsible under the Terms, which allow that "Multiple users may direct the actions of a machine account".

### O1. GitHub Copilot cloud agent: who pays for, and who is credited with, a session a team member starts?

**Status:** `partly documented`

**Answer:**

- **AI credits are current; premium requests are legacy.** "As of June 1, 2026, GitHub replaced request-based billing with usage-based billing, where the cost of an interaction depends on two things: the **model** and the **number of tokens consumed**." "As of June 1, all Copilot plans bill based on GitHub AI Credits consumed." The premium-request pages are marked legacy and say "This article only applies to Copilot Pro and Copilot Pro+ subscribers on an existing annual plan who remained on legacy premium request-based billing after June 1, 2026." Under that legacy billing, "Each cloud agent **session** consumes one premium request", and "**Premium requests** come from the monthly allowance associated with your Copilot license."
- **What a session costs.** "Copilot cloud agent uses GitHub Actions minutes and AI credits. The AI credits consumed depend on the model used and the number of tokens processed during the session." "1 AI credit = $0.01 USD".
- **Business and Enterprise.** Each user includes "Copilot Business | 1,900" or "Copilot Enterprise | 3,900" AI credits a month, and "A user's included AI credits are pooled at the billing entity level." Additional usage "is charged to your organization or enterprise", and is "**enabled by default**". A per-user budget caps one person: "If you have set a user-level budget and a user exhausts it, that user's access to Copilot is halted, regardless of whether the organization's pool still has capacity." "Copilot licenses are required for each user who uses Copilot", at "$19 USD per user per month" for Copilot Business.
- **Actions minutes.** GitHub's Actions billing page says "Minutes usage is charged to the repository owner, not the person who triggered the workflow runs." The cloud-agent pages do not name the owner.
- **Automations** are billed to their creator: each run "uses GitHub Actions minutes and GitHub AI Credits. This usage is billed to the user who created the automation."
- **Attribution.** "Copilot cloud agent's commits are authored by Copilot, with the developer who assigned the issue or requested the change to the pull request marked as the co-author." The requester cannot approve: "**Prevents the user who asked Copilot cloud agent to create a pull request from approving it.**" and "your approval of a Copilot pull request won't count toward the required number." A pull request "under its own app identity", not attributed to a person, needs "one more approval", a ruleset setting "enabled by default, for both new and existing rulesets". An automation's pull requests and pushes "are attributed to the user who created the automation."
- **Who can use it.** "Copilot cloud agent is available for all paid Copilot plans." On Copilot Business and Copilot Enterprise it "is disabled by default and must be enabled by an administrator"; on Pro, Pro+ and Max it "is enabled by default". "Only users with write access to the repository can trigger Copilot cloud agent to work."

**Inference:** a cloud-agent session's AI usage is charged against the license of the user who starts it, which on Business and Enterprise draws on the organisation's or enterprise's pool. Its Actions minutes are charged to the repository owner, and are free on a public repository with standard runners; the cloud-agent pages say "your account's" and do not name the owner. GitHub treats "Copilot opened it for person X" as X's pull request for approval purposes.

It is not available for organizations with Zero Data Retention enabled." › Set up Code Review: "You need the Owner or Primary Owner role in your Claude organization and permission to install GitHub Apps in your GitHub organization." / "To review a pull request, Claude reads your repository contents through the app's read access, and posts comments and the check run through its write access to pull requests and checks." › Manually trigger reviews: "`@claude review` | Starts a single review without subscribing the PR to future pushes" / "You must have write, maintain, or admin permission on the repository" › Pricing: "Code Review is billed based on token usage. Each review averages $15-25 in cost, scaling with PR size, codebase complexity, and how many issues require verification. Code Review usage is billed separately through usage credits and does not count against your plan's included usage." / "Costs appear on your Anthropic bill regardless of whether your organization uses Amazon Bedrock or Google Cloud's Agent Platform for other Claude Code features. To set a monthly spend cap for Code Review, go to claude.ai/admin-settings/usage and configure the limit for the Claude Code Review service." › View usage: "Go to claude.ai/analytics/code-review to see Code Review activity across your organization." The dashboard rows include "Cost weekly | Weekly spend on Code Review" and "Repository breakdown | Per-repo counts of PRs reviewed and comments resolved".

**Inference — the contrast across this section.** Copilot can charge the person who started a session because GitHub is both where the session is started and the AI provider, so it knows who assigned the task (O1). A GitHub Actions job running `claude` reaches Anthropic with whatever credential the workflow holds, and Anthropic sees that credential, not the GitHub user: R7 found no documented per-user credential model, and GitHub has no per-user Actions secret (G1). The Anthropic surface that is per person is Claude Code on the web (O3), and it runs on Anthropic's machines rather than in the adopter's workflows.

## 5. Options for the harness

Each option says what *would* change; this document changes nothing. The workflow files named below are the shipped templates under `cli/templates/github/workflows/`. An adopter's copy is written create-if-absent and is theirs to tune (`harness-run.yml`'s header, `WHO WRITES IT`), so a template change reaches an existing adopter only through `init --upgrade-workflows`.

### The repository facts the options rest on

Read from the tree, not from an external source.

- **Only the run job holds a Claude credential.** `harness-run.yml` → the steps `Check the credentials` and `Run the harness` read `secrets.CLAUDE_CODE_OAUTH_TOKEN` and `secrets.ANTHROPIC_API_KEY` into `IN_OAUTH` / `IN_API`; the first fails before launch when both are empty, and the second exports each only when non-empty. `harness-trigger.yml` and `harness-control.yml` each say *"The job reads no repository secret"*, and `harness-control.yml` references no `secrets.` at all. The secret names are `OAUTH_TOKEN_SECRET` and `API_KEY_SECRET` in `cli/src/remote/githubActions.ts`, mirrored by `harness-run.yml`'s `DECLARED MIRRORS` header.
- **The run job's permissions carry no `id-token`.** `harness-run.yml`'s workflow-level `permissions:` block grants `contents`, `actions`, `issues` and `pull-requests` write; its header's `THE PERMISSIONS` paragraph says every permission it does not list is `none`.
- **Every automated dispatch is made by a token that is not the person who asked for it.** `harness-trigger.yml` and `harness-control.yml` run with `GH_TOKEN: ${{ github.token }}`; `remote-run.sh` is, by its header comment, *"the one place a `gh workflow run` of the run workflow is composed"*; a chained continuation is dispatched from the run job itself (`harness-run.yml`'s header: *"`remote-run.sh continue` chains a new job"*); and `harness-resume.yml`'s scheduled poller dispatches `resume: pause` with `GH_TOKEN: ${{ github.token }}`. A run the local watcher dispatches uses the `gh` login of the machine it runs on ([`remote-execution.md`](remote-execution.md) → `## 7. Turning it on`, opening paragraph). A writer can also start a run directly, and the run job then checks nobody: [`remote-execution.md`](remote-execution.md) → `## 1. The lifecycle of a remote run` documents the **Run workflow** form of `harness-run.yml` as the fallback route, `gh workflow run` reaches the same `workflow_dispatch` (G7), and a re-run reuses the original run's privileges (G2). `harness-run.yml`'s `run` job is gated only by `if: inputs.action == 'run'` and reads neither `github.actor` nor `github.triggering_actor`, so none of these routes reaches `authorise_actor`.
- **The run's inputs name no person.** `harness-run.yml` → `THE INPUT CONTRACT` lists `action`, `branch`, `engine`, `resume`, `answers`, `park_loop_clear` and `chain`; none records who started the run, and any writer can dispatch the workflow with any inputs (G7).
- **The run job runs on the run's own branch**, not the default branch: `remote-run.sh`'s worked examples dispatch `workflow run harness-run.yml --ref feat_x`. An environment rule that admits only the default branch would refuse the run job itself (G3, G7).
- **One actor check gates the trigger, the commands and a review round's authors.** `remote-run.sh` → `authorise_actor` is called by the trigger, by the comment-command path and by `round_collect` (`remote-run.sh collect`, which `harness-run.yml`'s `collect` job runs). A person passes with `admin` or `write` from `repos/<repo>/collaborators/<login>/permission`. A bot passes only when listed in `HARNESS_TRIGGER_ALLOWED_BOTS`, and `ghost` or a non-login never passes ([`github-run-control.md`](github-run-control.md) → `## 6. Who can act, and pull requests from forks`). The repository variable that check reads reaches it only through an explicit `env:` line in each of those three jobs: `harness-trigger.yml`'s, `harness-control.yml`'s and `harness-run.yml`'s `collect` job. `harness-trigger.yml` and `harness-control.yml` also list it under `DECLARED MIRRORS`; `harness-run.yml` does not.
- **`doctor` reads secret names, never values.** `cli/src/doctor/checks.ts` → the remote check's header: *"Secret **values** are never read: `gh secret list` returns names only"*. It fails when neither credential secret is set, and notes when both are that *"billing follows `ANTHROPIC_API_KEY`"*.
- **The job limits.** `harness-run.yml` sets `HARNESS_HOSTED_JOB_LIMIT_MINUTES: '360'` and `HARNESS_SELF_HOSTED_JOB_LIMIT_MINUTES: '7200'`. A run job outlasts a federated token's default lifetime of 3,600 seconds on either runner, and its maximum of 86,400 seconds only on a self-hosted one (R6).

### Option A — each member's own credential, selected by who triggered the work

**What it is.** Each member's own subscription token or own personal API key, held in a per-member environment (G3), a per-login secret (G4), an external store (G5) or a per-member runner (G6), or reached through a federation rule bound to that member's `actor` (R6, **Inference**). The run job uses the credential of the member who started the run.

**Compliance with the terms.** A member's own subscription used only for their own runs is the use the legal-and-compliance page permits, *"an end user … with their own Claude subscription"* (P4); a personal API key falls under the same page's carve-out for keys used by the customer's own authorised users (P4). Each holds only while no other member's run can reach it.

**Setup per member.** A credential of their own, registered under the name the chosen pattern needs: an environment, a secret, a store entry, a runner or a federation rule.

**Security exposure.**

- Every writer can read every repository and environment secret by running an edited workflow (G7), unless a protection rule seals it. A deployment branch rule naming the default branch would also refuse the run job, which runs on its own branch (repository facts); required reviewers turn every run into a manual approval, and need GitHub Enterprise on a private repository (G3).
- A missing environment or secret reads as empty and does not fail closed (G3, G4).
- A re-run spends the original actor's credential (G2).
- The harness has no trustworthy record of who started a run: every dispatch is made by `GITHUB_TOKEN`, by the run itself or by the watcher's `gh` login, and an input naming the starter is forgeable by any writer (repository facts).

**What would change.**

- `harness-trigger.yml` and `harness-control.yml`: pass the authorised actor's login into the dispatch, through `remote-run.sh`, the input contract's one composer.
- The run's state bundle: persist the starter, so chained continuations and `harness-resume.yml`'s `resume: pause` dispatches inherit it.
- `harness-resume.yml`: dispatch with the inherited starter.
- `harness-run.yml`: select the credential from the starter (an expression `environment:` name, G3), refuse an empty credential rather than run (G3), and refuse a re-run whose `github.triggering_actor` differs from `github.actor` (G2).
- `authorise_actor`: also refuse an actor with no registered credential.
- `doctor`: check that each member allowed to start runs has a credential registered, by name.
- `cli/src/remote/githubActions.ts`: carry the per-member naming scheme beside `OAUTH_TOKEN_SECRET` and `API_KEY_SECRET`.
- Docs: [`remote-execution.md`](remote-execution.md) → `## 7. Turning it on` step 4, `### Every secret and variable` and `## 9. Credentials and billing`; [`github-run-control.md`](github-run-control.md) → `## 6. Who can act, and pull requests from forks`; [`github-issue-trigger.md`](github-issue-trigger.md) → `## 3. Who can start a run`.
- A policy for a review round or an answer from someone other than the starter ([§7](#7-open-questions)).

It rests on an open measurement: who `github.actor` is on a `workflow_dispatch` made with `GITHUB_TOKEN` ([§7](#7-open-questions)).

### Option B — a team organisation on the Claude API

**What it is.** One Console organisation with a workspace for the harness, its spend and rate limits set (R1, R3), and a service account the run job authenticates as: through workload identity federation, with no stored secret (R6), or through that service account's API key in `ANTHROPIC_API_KEY`, which the template already reads.

**Compliance with the terms.** The legal-and-compliance page's carve-out for API keys used by the customer's own authorised users (P4), and Anthropic's guidance for CI, *"have an organization admin create a service account"* (R2). Billing is the organisation's, under the Commercial Terms (P3).

**Setup per member.** None for runs on GitHub. A member who also works locally signs in with their own account.

**Security exposure.**

- Any writer can run an edited `harness-run.yml` on a branch and spend up to the workspace's limit (G7). **Inference:** a dispatched run's `sub` names its own branch (G7's `GITHUB_REF` for `workflow_dispatch`, R6's `sub` forms), and the run job runs on the run's branch, so the rule cannot pin one `ref` the way R6's fork warning advises.
- With federation there is no long-lived secret to copy, and each token is short-lived (R6). With a stored service-account key, the key itself can be read and kept (G7).
- Attribution is one service account in one workspace, not per member (R4).

**What would change.**

- `harness-run.yml`: grant `id-token: write` to the run job only (R6); fetch GitHub's identity token into the file `ANTHROPIC_IDENTITY_TOKEN_FILE` names and refresh it for the life of the job (R6's refresh, and the job limits above); export `ANTHROPIC_FEDERATION_RULE_ID`, `ANTHROPIC_ORGANIZATION_ID`, `ANTHROPIC_SERVICE_ACCOUNT_ID` from **repository variables**, since none is a secret, each only when set (R6); the workspace is the rule's own `workspace_id` (R6). Its credential check would accept federation as a third credential and refuse a job where `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY` would shadow it (R6's precedence). The `Run the harness` step already exports each static credential only when non-empty, which is the unset-not-blank rule R6 states.
- The federation rule, in the Console: pin the repository, the owner and `event_name` `workflow_dispatch` through `claims` or a CEL `condition` (R6).
- `harness-trigger.yml`, `harness-control.yml`, `harness-resume.yml` and `authorise_actor`: no change, since none holds a credential.
- `doctor`: report which credential kind is configured, reading the variable names; warn when a subscription token is set in a repository with more than one writer, read from the collaborators list with the `gh` it already runs.
- `cli/src/remote/githubActions.ts`: carry the variable names as constants beside `OAUTH_TOKEN_SECRET` and `API_KEY_SECRET`.
- Docs: [`remote-execution.md`](remote-execution.md) → `## 7. Turning it on` step 4, `### Every secret and variable` and `## 9. Credentials and billing`; [`github-run-control.md`](github-run-control.md) → `## The GitHub entry point`, setup step 8.

### Option C — members run locally; only the maintainer's account runs unattended work on GitHub

**What it is.** The repository's credential stays the maintainer's own. Every other member uses their own login on their own machine (`README.md` → *"A teammate clones"*), and only the maintainer may start or steer a run on GitHub.

**Compliance with the terms.** The maintainer's subscription used for the maintainer's own runs (P4). It holds only while no one else can start or steer a run on it.

**Setup per member.** Their own Claude account and a local `init`, as today.

**Security exposure.** An allow-list in `authorise_actor` alone does not stop another writer from starting a run on the maintainer's credential through the **Run workflow** form, `gh workflow run` or a re-run, none of which calls it (repository facts; G2, G7); only a gate in the run job itself closes those routes. Other writers can still read the maintainer's token through an edited workflow (G7); the maintainer accepts that or closes it with a protected environment, at G3's cost. Whether that exposure alone is "make your Account available" under Consumer Terms § 2 is an **Inference** (P4), and a question for Anthropic ([§7](#7-open-questions)).

**What would change.**

- `authorise_actor`: accept a person only when their login is on an allow-list in a repository variable, as well as holding `write`. What an unset list means — today's behaviour, or the repository owner only — is the maintainer's decision ([§7](#7-open-questions)). Because the check also screens a review round's authors, writers not on the list can no longer steer a run through a review either.
- `harness-trigger.yml`, `harness-control.yml` and `harness-run.yml`'s `collect` job: pass the new variable into the job's `env:` beside `HARNESS_TRIGGER_ALLOWED_BOTS`, and add a `DECLARED MIRRORS` entry for the new variable in each of the three files — in `harness-run.yml` as a new entry, since its header does not list `HARNESS_TRIGGER_ALLOWED_BOTS` today.
- `harness-run.yml`'s run job: refuse to launch when `github.triggering_actor` is a person not on the allow-list, so a direct dispatch or a re-run by another writer spends nothing (G2). Dispatches made with `GITHUB_TOKEN` — the trigger, the commands, a chained continuation and the poller — must still pass; which identity they carry is the open measurement [§7](#7-open-questions) lists, so this gate rests on it as option A does.
- `harness-resume.yml`: no change.
- `doctor`: warn when a subscription token is set, the allow-list is unset and the repository has more than one writer.
- `cli/src/remote/githubActions.ts`: carry the allow-list variable's name, as it carries `TRIGGER_ALLOWED_BOTS_VARIABLE`.
- Docs: [`github-run-control.md`](github-run-control.md) → `## 6. Who can act, and pull requests from forks` and [`github-issue-trigger.md`](github-issue-trigger.md) → `## 3. Who can start a run` describe the list.

## 6. Recommendation

This is a recommendation from documented sources and inference. Nothing in it was measured, and the change it implies is a later branch's to make.

- **Option B with workload identity federation, for any repository more than one person can trigger or steer.** It is the route the terms permit for shared use (P4), the one Anthropic recommends for CI (R2, and R7's organisation setup), and it leaves no long-lived secret for a writer to copy (R6, G7). Where federation cannot be set up, option B with a service-account key, accepting that any writer can read and keep that key (G7).
- **Option C, for a repository one person drives.** It is what the shipped templates already assume.
- **Option A, deferred.** It is the only option that bills each member's own subscription. It needs a trustworthy record of the starter that survives every dispatch — for example a dispatch made with an identity GitHub signs for that member, as GitHub marks the developer who assigned a Copilot cloud agent's work as its commits' co-author and treats its pull request as theirs for approval (O1) — and the measurements [§7](#7-open-questions) lists for it.
