# Development

**Who reads this:** anyone changing a file in this repository. It answers how to run the plugin from your working copy instead of from an installed copy, what that choice forces on the way references between plugin assets are written, which commands decide whether a change is good, and what the roadmap item numbers cited throughout the tree mean.

Everything below was measured against the shipped `claude` CLI at version 2.1.226, except where a fact names its own version. Where a fact is a measurement, the command and the exact message are given, so a later version that behaves differently is detectable rather than merely surprising.

---

## 1. Source types and the plugin root

**The committed marketplace entry sources the plugin as the relative path `./plugin`, and that one entry serves both consumers.** There is no separate development entry and no second manifest. What differs between a contributor and an adopter is not the entry — it is how the *marketplace* was added, and that is what decides where `${CLAUDE_PLUGIN_ROOT}` points.

**An adopter** adds the marketplace from its repository:

```
claude plugin marketplace add firu-daniel/autonomous-sdlc-harness
```

That is a **git-sourced** marketplace. The plugin installs as a `git-subdir`, and `${CLAUDE_PLUGIN_ROOT}` resolves to a **version-pinned cache directory** — a copy checked out at the installed version, keyed by marketplace, plugin and version. Nothing an adopter edits in a clone affects it; a new version arrives only through the plugin's own update path.

**A contributor** adds the marketplace from the repository root of their working copy:

```
claude plugin marketplace add ./
```

That is a **`directory`** source, and what it does *not* do is run your working copy. Two of the runtime's own records say so, both readable without `claude`, both read on **2.1.246** on 2026-08-27: `<claude home>/plugins/known_marketplaces.json` gives this marketplace an `installLocation` **equal to the source tree** — the marketplace manifest is read in place, never copied — while `<claude home>/plugins/installed_plugins.json` gives the **plugin** an `installPath` of `<claude home>/plugins/cache/<marketplace>/<plugin>/<version>`, carrying a `gitCommitSha`. The install is a **snapshot copy pinned to a commit**, exactly as for a git source. The source type decides where the snapshot is taken from, not whether one is taken.

Write that command with a **relative** path. An absolute one would encode where this tree happens to sit on the machine that wrote it, and this tree is designed to be relocatable by plain copy. The registry entry the command creates is stored in the contributor's own user-level settings; it is **machine-local and is never committed**, so nothing in the repository depends on any particular checkout location.

**Treat that snapshot as what executes, and refresh after every edit you want a run to see.** What the adoption rehearsal's unattended run measured is one-sided, and it is one-sided in the direction that costs a debugging round: the only plugin **code** that run executed — `find-free-port.sh`, `poll-dev-server.sh` and `kill-dev-server.sh`, three invocations — ran out of the cache directory, under the permission entries an adopter hand-adds against the resolved install root (§3's closing bullet), and no plugin script ran out of the source tree (its own stream's `init` record, `claude_code_version` `2.1.246`, 2026-08-26). What the same stream **does** settle, and it settles pessimistically, is what `${CLAUDE_PLUGIN_ROOT}` expands to in an **agent definition body**. A sub-agent dispatched with a four-line prompt carrying no path read `<installLocation>/plugin/samples/sample_story_plan.md`: nothing it had read could have supplied that path, and the cache copy carries that file too, so its own system prompt with the token substituted is the only channel. Under a directory source the token therefore resolves to the **live source tree** — the same directory that record names as the plugin's `path`, mirroring the marketplace `installLocation` above — while the plugin's `installPath` names the cache. A contributor's machine has **two** plugin roots at once, which is why `doctor`'s `plugin-permissions` check grades both and why an entry is owed at each (`docs/cli.md` §7). Refresh regardless: the cache copy goes stale the moment the working copy moves, and `diff -rq <claude home>/plugins/cache/<marketplace>/<plugin>/<version>/ plugin/` reports a differing file for every asset edited since the last install.

**Refreshing it takes two commands, and the two that look like they should are no-ops that report success.** Measured on `claude` **2.1.246** on 2026-08-26, with a marker file planted in the live `plugin/` tree:

| command | effect on the installed copy |
|---|---|
| `claude plugin marketplace update <marketplace>` | **none** — prints `✔ Successfully updated` and changes nothing |
| `claude plugin install <plugin>@<marketplace>` again | **none** — reports "already installed" |
| `claude plugin uninstall <plugin>@<marketplace>`, then `install` again | **refreshes it** |

The first two rows are the trap: a contributor who runs `marketplace update`, reads `✔ Successfully updated` and goes back to editing has changed nothing at all.

**`uninstall` edits committed files in this repository, so check `git status` after every refresh.** It rewrites the `enabledPlugins` block of **every project-scope `.claude/settings.json` on the machine**, and one of those is `examples/notes-app/.claude/settings.json`, a committed fixture here: the probe above **emptied it**, and it was restored by hand. Nothing warns you, and refreshing from inside this repository is the ordinary case rather than the careless one.

**What is left of the reason to prefer a directory source.** Not "no reinstall": a refresh is `uninstall` + `install` + a `git status` check, per edit. What survives is that the snapshot is taken from **your working copy** — the marketplace entry, the plugin manifest and the whole component set are the ones you are editing, with no version bump, no tag and no push — and that the refresh is two commands against your own tree rather than a release. That is a smaller advantage than the sentence this paragraph replaced claimed, and the smaller one is the measured one.

One more consequence is worth knowing before it costs a debugging round:

- **`file://` URLs are rejected outright.** The accepted forms are `<owner>/<repo>`, an `https://…` URL and a `./path`. What that costs is the *published* form of the command — `marketplace add <owner>/<repo>` needs the repository to exist — and nothing more. It does **not** put the install story out of offline reach: a `./` add is one of the accepted forms, it writes an entry of the same shape into the same settings file, and it installs the same pinned snapshot (above), so every question about what `marketplace add` writes is answerable from a clone. Assuming otherwise is what let a malformed `extraKnownMarketplaces` entry ship (`cli/src/generators/projectSettings.ts`, `## The entry's shape, and how it was measured`).

## 2. The one authoring rule that follows

Because the runtime root differs between the two source types, **every reference from one plugin asset to another is written `${CLAUDE_PLUGIN_ROOT}/<path>`.** Never a relative path, never a path assembled from a version, never a path into a sibling plugin. It is the only form that is correct under both roots.

The rule holds from **every** asset type, not just slash commands: `${CLAUDE_PLUGIN_ROOT}` interpolates inside **agent definition bodies** as well, and inside a hook's `command` string. This is what the sample fixtures depend on — an instruction or agent body that points a writer at a worked example dereferences it as `${CLAUDE_PLUGIN_ROOT}/samples/<file>`, and that reference resolves for a contributor running from the source tree and for an adopter running from the pinned cache without either one being special-cased.

**What the runtime does not substitute, and it is measured rather than assumed: a file an agent opens with `Read`.** An instruction or sample file arrives as the bytes on disk, token and all, and the agent resolves the root itself. Measured 2026-08-26 against the adoption rehearsal's own unattended run, from the stream it left at `<state_dir>/autonomous_logs/<branch>.stream.jsonl`: that session's own plugin record named the **source tree** as the plugin path — the marketplace was directory-sourced — while every helper-script command the run issued named the **cache** root instead. Those three commands were the **top-level orchestrator's** (`parent_tool_use_id` `null` on each), typed from a root it had located by hand with `find` after its own `${CLAUDE_PLUGIN_ROOT}` citations were refused: they are evidence that a hand-resolved entry at the cache root matches, and evidence about the substitution in neither direction — §1 records the sub-agent read that does measure it, and that one yields the source tree. Scanning every `"command"` field in that stream, and every `"file_path"`, emits no unresolved token in either.

Two things follow, and neither weakens the rule above. The token stays the only form correct under both roots — an agent resolving it is not a reason to write a path. And a `permissions.allow` entry meets the **command string an agent issues**, which carries a resolved path whichever route produced it, so a call site being an instruction file rather than an agent definition body does not decide whether an entry naming a resolved root **matches**. What it does decide, on a directory source, is **which** root that resolved path names — the agent resolves one for itself, the runtime substitutes the other (§1) — so an entry is owed at each (`plugin/scripts/README.md`).

The negative case is worth stating because it works mechanically and is still wrong: a **cross-plugin sibling read** — reaching from this plugin's root into another installed plugin's directory — is unauthorable in production. The pinned cache path contains a version segment belonging to the *other* plugin, and that segment cannot be known at the time the reference is written. It appears to work exactly once, on the machine where it was authored, and then breaks on the other plugin's next update.

## 3. Manifest facts a contributor must not rediscover

Five measured behaviours and one shipped contract, each of which costs a round if it is met by surprise:

- **`hooks/hooks.json` needs the `{"hooks": { … }}` wrapper.** A bare event map — `{"PreToolUse": [ … ]}` — fails validation with `hooks: Invalid input: expected record, received undefined`. The event names go one level down, inside `hooks`.
- **Plugin hooks append to an adopter's own hooks; they do not override them.** A hook declared by this plugin composes with whatever the adopter has in their own settings, so the CLI never needs to write guard hooks into user settings to make them take effect. Related and easy to get backwards: `${CLAUDE_PLUGIN_ROOT}` **expands** inside a hook `command` string declared here, and **does not** expand in a settings-file-defined hook — which is the reason the guards live in `hooks.json` rather than in generated settings.
- **A `permissions.allow` entry was not able to pre-approve a command whose script path is written `${CLAUDE_PLUGIN_ROOT}/scripts/<name>.sh`.** Measured against `claude` **2.1.227**, on a session that could **not** be isolated from the measuring machine's own hooks — read the hook caveat that follows the runs below before treating this as a property of `claude` itself. The runs used a throwaway fixture outside this tree — `<scratch>/plugin-root/scripts/probe.sh`, two lines, printing `PROBE OK` — and settings files differing only in their `permissions.allow` list. Each run was `env CLAUDE_PLUGIN_ROOT=<scratch>/plugin-root claude -p --permission-mode default --settings <scratch>/<name>.json '<prompt>'`, the prompt instructing one verbatim Bash command and nothing else:
  - `allow: ["Bash(bash ${CLAUDE_PLUGIN_ROOT}/scripts/:*)"]`, command `bash ${CLAUDE_PLUGIN_ROOT}/scripts/probe.sh` — **blocked; the script never ran.** On its own this attributes nothing: the entry is a directory prefix, and the by-product below records that form missing even as a literal path, so this run and the next are consistent with the entry form alone. The attribution is the fourth run's.
  - `allow: []`, same command — **blocked.** The entry bought nothing.
  - `allow: ["Bash(bash <scratch>/plugin-root/scripts/probe.sh:*)"]`, command written as that same literal absolute path — **`PROBE OK`.** Same session shape, same script, same settings mechanism, so the blocks above are about how the path is spelled and not about the fixture.
  - `allow: []`, command `echo ${CLAUDE_PLUGIN_ROOT}/scripts/probe.sh`, under a `Bash(echo:*)` allow already in force — **blocked.** This puts the cause on the **command** side rather than the entry side: a `${…}` in the raw command defeats matching, so no wording of an entry rescues it — provided the refusal came from the permission guard at all, which is what the caveat below is about.

  In the probe's own vocabulary the outcome is **DOES NOT MATCH**. Read as permission outcomes — the reading the next paragraph qualifies — the result rests on the fourth run and the third: the third shows a file-form literal entry does match, so the mechanism and the fixture are sound, and the fourth shows a `${…}` in the raw command blocked a call an allow already in force would otherwise have permitted. Re-measuring this on a later `claude` means re-running those two — repeating the first two alone would only re-confirm the directory-prefix by-product. One by-product is worth keeping: a **directory-prefix** entry — `Bash(bash <scratch>/plugin-root/scripts/:*)`, trailing slash, literal path, against the literal command — did not match either, so an entry has to name the script file the way the generated profile already does rather than the directory holding it.

  And the refusal surfaced as a `PreToolUse` hook's **`ask`** reason rather than as a permission message. That is a caveat, not a curiosity: a `PreToolUse` `ask` pre-empts the permission decision, so it is an independent sufficient cause for every block above, and the nested session ran with the measuring machine's own user-level hooks in force — isolating it, by pointing `CLAUDE_CONFIG_DIR` at a scratch home, is not available, because that invocation exits 1 with `Not logged in`. Nothing here separates "the guard did not match" from "a machine-local hook asked". Re-measuring therefore takes more than re-running those two runs: this section's opening asks a measurement for its exact message and this bullet carries none, so a re-measurement records the refusal's message verbatim together with which `PreToolUse` Bash hooks were active. And the run that would settle it directly has not been made: a **file-form entry carrying the token** — `Bash(bash ${CLAUDE_PLUGIN_ROOT}/scripts/probe.sh:*)` against `bash ${CLAUDE_PLUGIN_ROOT}/scripts/probe.sh` — is the shape this fact is about, and the first run and the fourth approach it from either side without meeting it. What none of this changes is what the generator does: it emits no entry for these scripts either way. The **reason** recorded here for that was wrong, and is corrected rather than re-measured — the agent runner's own `<claude home>/plugins/installed_plugins.json` records an `installPath` per plugin and per scope, so the root is knowable, and `doctor`'s `plugin-permissions` check reads it on every run (`docs/cli.md` §7). What stands between `init` and a generated entry is two other things: `init` may run **before** the plugin is enabled, leaving no row to read; and the path carries the plugin **version**, so an entry written once goes silently stale on an upgrade. Neither is touched by this bullet's measurement, and the second is why the shipped remedy re-derives the root every run instead of writing it once.

  The probe stands an ordinary environment variable of that name in for the plugin runtime's own, which is faithful exactly insofar as the guard matches the raw command string — the same claim the result rests on, and one the literal-path run tests without any variable at all. The fourth run's finding — a `${…}` in a raw command defeats matching — **stands, and the one run measured against it never reached it**: §2 records the scan of every command the rehearsal's unattended run issued, with no unresolved token among them. Keep it anyway; it is what makes a resolved-root entry the only form worth adding.

  And the leg this bullet once called unmeasured — whether a helper invoked from an **instruction file** rather than an agent definition body reaches the guard with a resolved path — **is now measured, and it resolved in the hand-added entry's favour — at the cache root.** The same run invoked `find-free-port.sh`, `poll-dev-server.sh` and `kill-dev-server.sh`, all three from the instruction-file side, with the resolved **install** path, which its top-level orchestrator had located by hand, and under hand-added entries of that form; none stalled. §2 states why the call site is not the discriminator for **matching**: what the guard meets is the command an agent issues, not the text it read. Which root that resolved command names is a different question, and on a directory source it does differ by call site — the agent-body class resolves the source tree (§1) — so an entry is owed at each root. `doctor`'s `plugin-permissions` grades both, and `plugin/scripts/README.md` carries the corrected remedy.
- **The marketplace entry carries no `version`.** `plugin.json` is the sole version of record and wins at install time. An entry that declares a version which drifts from `plugin.json` is a `--strict` failure, so the field is deliberately absent rather than duplicated and kept in sync by hand.
- **`agents/` and `commands/` carry `README.txt`, not `README.md`.** Component discovery loads every `.md` file in those two directories as an agent or a command, so a `README.md` there is parsed as a component and fails `--strict` with `frontmatter: No frontmatter block found`. Every other directory that carries a README carries an ordinary `README.md`; only these two use `.txt`.
- **A guard resolves the repository it judges from the command it was handed, and reads `harness.config.json` at that root and nowhere else.** In order: the first `git -C <dir>` in the command string, else a leading `cd <dir>`, else the hook payload's own `.cwd`, else the process `$PWD` — then `git -C <that anchor> rev-parse --show-toplevel`. Never a hardcoded path and never an assumed session root, because a plugin hook fires in every session the plugin is enabled for and the command it is handed may name a sibling worktree. Two outcomes are closed rather than left to the author: a resolved root with **no `harness.config.json`** — or one the guard's own process cannot read, which the `[ -f ] && [ -r ]` jurisdiction test puts *outside* jurisdiction rather than inside it — means that repository has not adopted the harness, so every guard stays silent in it; and **within** jurisdiction a configuration that will not resolve — invalid JSON, more than one JSON document, or a `jq` too old to run the load — must never produce an `allow`. Two near neighbours are not that invariant: an absent `jq` is a payload the guards cannot parse at all rather than a configuration they cannot resolve, and an absent `defaultBranch` closes only the three guards that consult the protected set — the other three go on permitting, correctly, because nothing they decide depends on it. Which non-permit each guard emits instead of that `allow` differs per guard and is tabulated in `plugin/hooks/README.md`; read it there rather than inferring it from one guard's behaviour.

More generally, `--strict` promotes unknown fields and missing metadata from warnings to errors. Adding a field to a manifest because it seems like it should exist is the fastest way to fail gate 1; add only fields the validator recognizes, and confirm by running it.

## 4. `userConfig`, reserved

`userConfig` is the plugin-level place for values that belong to a *person and a machine* rather than to a repository. The option shape below was recovered from the shipped schema and confirmed by a live install:

- Per key, **required**: `type` — one of `string`, `number`, `boolean`, `directory`, `file` — plus `title` and `description`.
- **Optional**: `required`, `default`, `multiple` (string only), `sensitive` (routes the value to OS secure storage instead of the settings file), and `min` / `max` (number only).
- The object is **strict**, and there is **no `enum`** — a constrained vocabulary cannot be expressed here at all.

Values are stored per user in the user-level settings file — except a key marked `sensitive`, which is routed to OS secure storage and is never written to settings — are readable from agent and command bodies as `${user_config.KEY}` (non-sensitive keys only), and are exposed to hooks as the environment variable `CLAUDE_PLUGIN_OPTION_<KEY>`.

**This release declares no `userConfig` key.** Options are prompted at enable time, so declaring a key before the asset that reads it exists would ask every adopter for a value nothing consumes — a cost paid by everyone for a feature that does not yet run. One key is **reserved** for the machine-local home the configuration map points at, `reference_toolchain_path` — an SDK directory outside the checkout, which is machine-local because it varies per machine. It stays reserved after the CLI shipped, and the reason is worth recording because it looks at first like an omission: **the CLI cannot read plugin `userConfig`**, so declaring the key would not have given the CLI the value anyway. The only consumer this release has for that path is the generated permission profile's allow-list for a toolchain outside the checkout, and `init` takes it from `--reference-toolchain-path` instead, reading it only when the parity phase is on. The key is declared when the parity module ships the agent-side reader that consumes it — an agent body *can* read `${user_config.KEY}`, which is what makes the declaration worth its prompt at that point and not before. The counterpart path `push_env_path` is *not* reserved here: it is repo-relative, so `config.md` routes it to the committed config key `pushEnvPath` instead.

The repo-scoped side of the same boundary — what belongs in the committed `harness.config.json` instead, and why — is in `config.md`.

## 5. Verifying a change

Eleven gates. Run each **without a pipe** and read the exit status: piping into a pager or into `head` returns the *pager's* status, not the tool's, so a failing gate reads as a passing one.

**Six of the eleven run unattended, and `scripts/run-gates.sh` is how.** It runs gates 1, 2, 3, 4, 6 and 11 — every gate below that a process can run without a terminal, a browser, a model session or a network — grades each one the way this section says to grade it, and prints the remaining five, gates 5, 7, 8, 9 and 10, rather than passing over them. **Gate 11 is the one conditional member of that six:** it runs unattended **where the retrieval model cache is provisioned**, and where the cache is empty it is printed with the gates the script cannot run and counted among neither the passes nor the failures — so the script's exit status never depends on a several-hundred-megabyte download. `commands.test` in `harness.config.json` points at it, so a branch review's verification is the automatable half of this section rather than gate 4 alone. It is hand-written and is not in the set `init --force` regenerates; the `scripts/test.sh` that wraps it is generated and is not this file. Running the gates by hand, as written below, stays correct and is what the script's own text is checked against.

**One standing exemption, stated here so no gate has to restate it.** `examples/notes-app/` is two
things with different obligations, and its own README draws the line (*"The capture is frozen; the
fixture is live"*). Its **capture** — the run artifacts under `sdlc-harness/` and the prose of the
five documents under `.claude/context/` and `.claude/CLAUDE.md` — records what the harness produced
on 2026-09-07, and **no criterion added after that date grades it**. Every criterion standing at
that date does, and gate 8 below records the result rather than assuming it: that corpus was written
by today's CLI and today's analyze command, so it predates none of gate 8's corpus-content rules and
was held to the ones this fixture's shape can exercise. Its **fixture** — that project's own source
and toolchain, and the presence of what `init` generated — is live, and gate 9 is what holds it
there. A criterion added below inherits this and needs no exemption of its own; a failure measured
against the capture is a fact about what the harness used to do, never a reason to weaken the rule
that found it.

**Gate 1 — manifests.** From the repository root:

```
claude plugin validate --strict plugin
claude plugin validate --strict .
```

Both must report `Validation passed` with zero warnings. The first checks the plugin manifest, its hooks file and its components; the second checks the marketplace manifest and the entry it declares.

**Gate 2 — CLI build and run.** From the repository root:

```
npm install && npm run build
```

Then four invocations, in this order and with these expectations: `node cli/dist/cli.js --version`, `node cli/dist/cli.js --help` and a real subcommand's own usage — `node cli/dist/cli.js init --help` — all **exit 0**; an unknown command — `node cli/dist/cli.js not-a-command` — **exits non-zero**. The point of the gate is that the CLI answers for itself: it describes each command it lists, and refuses one it does not have. `cli/dist/` is a build output and is not committed, so this gate's build is the precondition for every `node cli/dist/cli.js …` line below.

**Do not use a bare `node cli/dist/cli.js init` as the refusal probe.** It was one for as long as `init` refused everything; now it would wire the harness's own repository — a configuration, a run-artifact tree and a permission profile generated into the tree that ships them. `init` refuses that by name, recognising this root by its marketplace manifest together with a `cli/package.json` naming this package, but that refusal is the safety net rather than the gate: it is a check on the trap, not a demonstration that the CLI works, and it would still exit non-zero if every command in the package were broken.

**That refusal has one way through, and it is not a flag.** Self-adoption — wiring this repository so the harness's own flows plan, implement and review changes to the harness — is a contributor workflow, so the escape is the environment variable `HARNESS_SELF_ADOPT=1` rather than a command-line option. An option would appear in `--help` and owe a row in `docs/cli.md`'s flag table, whose only reader is an adopter, for whom it can never mean anything but a mistake; the variable is invisible there and documented here, beside the gates that are the rest of a contributor's contract. Three properties are the whole of it, and `cli/test/init.test.mjs` asserts each:

- **It is checked after both identity tests**, so it is inert in every repository but this one. A value left in a shell's environment changes no adopter's run, because that run returned from the check before the variable was read.
- **Only the exact value `1` opens it.** A variable that is merely *set* — `yes`, `true`, the empty string — is too easily inherited from a parent process to be allowed to wire a repository.
- **The refusal names it**, so a contributor who meets the refusal learns the way through from the message rather than from the source. Every reader of that message is standing in a harness clone, which is what makes naming it safe.

A one-off source edit is the other way to get a single run through, and it was rejected for a reason worth recording: `init` is not one-shot. `--force` regenerates a generated file when `cli/templates/` changes, and `--reset-config` rebuilds the configuration, so the run this exists for recurs every time a template moves. An edit-build-revert-build cycle per template change is a standing invitation to ship the CLI with its guard removed — and while the refusal *is* covered (`cli/test/init.test.mjs`, the harness's-own-repository subtest), a test only catches a forgotten revert if it is run before the commit.

**A fifth invocation, optional per run where the four above are mandatory: the linked binary.** `cli/package.json` declares `"bin": {"autonomous-sdlc-harness": "./dist/cli.js"}`, and every gate below runs `node cli/dist/cli.js …` instead, so nothing in this repository exercises that declaration — the form an adopter installs is otherwise first executed on publication day. Run it when the `bin` declaration, `cli/dist/cli.js`'s shebang or the package layout changed, and skip it otherwise:

```
npm link                      # from cli/
autonomous-sdlc-harness --version
npm unlink                    # from cli/, removes the global link again
```

The middle line must print the version and exit 0. Measured on 2026-08-26 against `0.1.0`: it printed `0.1.0`. `npm link` writes outside this checkout — a global link and a `node_modules` symlink — so the third line is part of the leg rather than cleanup a reader may skip.

**Gate 3 — configuration schema.** From the repository root:

```
npm run validate:config
npm run validate:config:negative
```

The first validates the worked example against the schema. The second asserts the inverse case once per fixture, one chained assertion for each document `schemas/negative/` wires into it: `ajv test … --invalid` passes only when a fixture is read *and* rejected, so a green run means **every** wired fixture was still refused — not merely that something exited non-zero — and each assertion prints the keyword path that rejected its own fixture, naming the constraint that fixture proves. A red one means either the schema started accepting a fixture or a fixture could not be loaded, and the message says which: `<file> failed test` and exit 1 for the first, `Cannot find data file …` and exit 2 for the second. Neither red case prints a keyword path — do not go looking for one.

**Gate 4 — `init` against a throwaway fixture.** From the repository root:

```
npm test
```

This gate needs `jq` 1.5 or newer on `PATH`: the outer-loop library reaches a configuration only through `jq`, and the library reader this suite exercises reports its absence as exit `2` with no message of its own. It does not need gate 2's build — `cli/package.json` runs `pretest`, so `npm test` compiles `cli/src/` before it runs and always grades the source in the tree.

Every test builds its **own** fixture repository under the system temp directory and removes it in process; nothing is written inside this checkout and no fixture is committed. The gate is red if a first `init` produces a configuration the schema rejects, if a second `init` on the same tree changes anything the first one wrote, or if a `--dry-run` writes at all — idempotence and dry-run purity are asserted before any other behaviour, because a writer aimed at a repository that fails either is destructive rather than merely wrong.

Rehearsing it by hand means running `node cli/dist/cli.js init --cwd <scratch>` twice against a scratch git repository **outside** this checkout; the second run reports every artifact as kept. Do not aim it at this repository — gate 2 says why.

**Gate 5 — `doctor`'s exit contract.** Covered by the same suite, and worth exercising by hand against the scratch repository from gate 4:

```
git init --bare <scratch>-origin.git
git -C <scratch> remote add origin <scratch>-origin.git
git -C <scratch> push --no-verify -u origin HEAD
node cli/dist/cli.js doctor --cwd <scratch>
```

It **exits 0** against a freshly wired repository **that has a remote**, warnings and all: a fresh adoption always carries at least the missing-watcher warning, and a warning that moved the exit status would make every correct adoption read as broken. **Gate 6 — self-containment.** Nothing in this tree may name a location on the machine that wrote it, and no generator template may have been committed into the adopter's own dot-namespace. Run this **before committing, on the machine you are committing from**. From the tree root:

**(iv) An edited configuration survives a forced re-run.** The configuration is the one generated file `init` reads back rather than rebuilds, so the thing to demonstrate is that a hand-edited value is still in effect after a re-run that regenerates everything derived from it. From a scratch git repository outside this checkout:

```
node cli/dist/cli.js init --cwd <scratch-edited> --non-interactive
```

Then edit `<scratch-edited>/harness.config.json` by hand and add a second entry to `protectedBranches` — say `release`, so a repository whose integration line is `main` now reads `["main","release"]` — and re-run:

```
node cli/dist/cli.js init --cwd <scratch-edited> --force --non-interactive
```

Read three things, in the files rather than in the run's report. `protectedBranches` still carries the added entry. There is **no** `harness.config.json.bak` beside it — `--force` did not rewrite the file, so it had nothing to back up, and the absence of that sibling is the cleanest evidence the file was read rather than regenerated. Read that absence with `ls` on the directory and never out of `git status`: the managed block ignores that path, so `git status` says nothing whether the file is there or not, and a git-status reading passes this leg unconditionally. And in the regenerated `<githooksDir>/pre-push`, read the **`case` label** — the one line whose glob pattern a push target is matched against, which must read `main|release)`.

Read that label specifically, and not the file as a whole: the whole-file check is the trap this leg exists to catch. The hook's own header names `release/*` as an example of a namespace-protecting entry, so a `grep` for the added branch across the file answers yes on a hook whose guard would never match it — a passing gate on a broken guard.

One contrast, because this is also the leg that shows the two flags are not the same thing. It opens with a **negative**, because everything below it would pass on an implementation that re-rendered the hook on every run:

```
rm -f <scratch-edited>/githooks/pre-push.bak
cksum <scratch-edited>/githooks/pre-push
node cli/dist/cli.js init --cwd <scratch-edited> --non-interactive
cksum <scratch-edited>/githooks/pre-push
```

The two checksums are **equal** and no `githooks/pre-push.bak` came back: a plain re-run rebuilds nothing, so it re-renders nothing, and `create-if-absent` leaves the hook byte-identical whatever the configuration says. The `rm` is part of the leg rather than tidying — the `--force` run above left a `.bak` of its own, and an absence is only evidence once nothing else could have written it. Then:

```
node cli/dist/cli.js init --cwd <scratch-edited> --reset-config --non-interactive
```

That **does** rebuild the configuration, after copying it to `harness.config.json.bak`, and the added entry is then gone **from the file**. That the copy was taken is read with `ls` on the directory and never out of `git status`: the managed block ignores that path, so `git status` says nothing whether the file is there or not, and a git-status reading fails this leg unconditionally. It also **re-renders the guard its own rebuild stranded**, copying the hook to `githooks/pre-push.bak` first. So this run is read as **three** things rather than two: the rebuilt `harness.config.json`, whose `protectedBranches` is back to `["main"]`; the re-rendered `case` label, which now reads `main)`; and `githooks/pre-push.bak`, which holds the old label `main|release)`. Read both of those labels the way this leg's own discipline prescribes — the `case` label line, never the file as a whole, for the reason the paragraph above gives: a `grep` across either file answers yes on a guard that would match neither branch.

The second negative closes that assertion from the other side, since a re-render that fired on every rebuild would satisfy all three readings:

```
rm <scratch-edited>/githooks/pre-push.bak
node cli/dist/cli.js init --cwd <scratch-edited> --reset-config --non-interactive
```

The configuration is rebuilt again, and this time the set it resolves is the label already on disk: **no** `githooks/pre-push.bak` comes back and the hook is byte-identical. That is the whole of the asymmetry between the two flags — `--force` re-renders unconditionally, `--reset-config` re-renders only a hook its own rebuild made wrong, and it leaves both a matching label and one this CLI cannot read at all exactly as they are, the second with a warning naming `doctor`'s `pre-push-guard` check.

The staleness the run's own note states is what makes the hook worth reading at all, and it is unchanged: the hook is committed and travels with the checkout, while the git wrappers re-read `harness.config.json` on every call, so until the hook is re-rendered the two can enforce different sets and a push is judged by the hook. **Three** runs re-render it — `init --force`, which copies the hook to `githooks/pre-push.bak` and re-renders it from the configuration in effect; deleting the hook and re-running `init`, which re-creates it because it is create-if-absent; and the `--reset-config` run above, as a **consequence** of the rebuild rather than as a route to change the set, since that rebuild takes the whole configuration from detection and the flags. Rebuilding the configuration is still `--reset-config`'s own job, and a bare `--reset-config` is that job plus the guard it would otherwise strand (`docs/cli.md` §2).

**(v) A repository that exists but has no commit.** A repository with no commit is the state `git worktree add` cannot prepare a checkout from, so a run that wires such a repository and leaves it commitless leaves an adoption that reads as complete and cannot start a run. git -C <scratch-unborn> worktree add ../<scratch-unborn-wt> -b <new-branch>
```
git -C <scratch-unborn-wt> rev-parse HEAD
```

The `init` **exits 0** and notes both facts about the flag it was given: nothing was created, *and* this run makes the first commit anyway. Then `rev-list --count` answers `1` rather than `fatal: ambiguous argument 'HEAD'`, and `worktree add` prepares a checkout **from that commit** rather than printing `No possible source branch, inferring '--orphan'` — the final `rev-parse` in the new worktree resolves to the same commit the main checkout is on. An orphan worktree is the failure this leg names, and it is quiet: the command still exits 0.

One property of that commit is worth reading rather than assuming. The staging is `git add -A`, so the commit carries the directory's whole working tree — what `init` generated and whatever else was already there — minus what the managed `.gitignore` block excludes. That is the same property leg (i) reads off `adopter_notes.txt` in a repository the run *created*: the two legs are one behaviour, and what differs between them is who left the repository without a commit. The run says so in its own notes instead of leaving it to be discovered.

**One convention is part of this project's published design and survives packaging.** Every agent definition declares a `tools:` allowlist; the browser-automation MCP tools are granted to the single QA agent and to no other agent.
