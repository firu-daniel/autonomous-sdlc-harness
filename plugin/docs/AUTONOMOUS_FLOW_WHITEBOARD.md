# Autonomous flow — whiteboard explainer

**Who reads this:** someone who has to explain this system to a person who will **operate or extend it** — a new contributor being handed the run loop, or an adopter deciding how much of it to keep. It answers *how the pieces fit together* and *in what order to say them*, and it is allowed to be discursive about both.

**Its companion is the specification; this file is the narrative.** `${CLAUDE_PLUGIN_ROOT}/docs/AUTONOMOUS_FLOW.md` is the canonical statement of the inner loop — the phases a run walks, the artifacts it writes, what it promises when it stops, and which file owns each piece. This document explains how those pieces fit, and is **not a second owner of any contract**: where the two disagree the flow document is right and a paragraph here has drifted. A sentence that *states* a contract rather than explaining one belongs there, and this file cites it instead. Configuration tokens — `<state_dir>`, `<default_branch>`, `<protected_branches>`, `<MAIN_REPO>`, `<scripts_dir>`, `<githooks_dir>` — are declared once in that document's `## Resolved values` table and are used here exactly as it declares them.

**The outer loop is neither file's.** What turns a dropped file into a running session — the inbox, the filename routing, the working-copy strategy, the headless launch, the registry, the exit classification, the usage gate and the stall watchdog — belongs to the harness repository's `docs/watcher.md`, cited here by section and never restated. This document describes what that layer is *for*; that one is how it behaves.

# Part 1 — How it works

## The one-sentence version

A daemon watches an inbox directory; a dropped file like `<branch>_task_prompt.md` gets its own working copy, a headless session running a fixed orchestration engine, and a generated permission profile — and the run drives a fleet of single-purpose sub-agents through plan → implement → review gates → interactive tests → statistics, committing and pushing after every unit, ending at "branch ready for review" and never touching a protected branch.

## The five layers

| Layer | What it owns | Where it lives |
|---|---|---|
| **1. Trigger / control plane** | Turning a file drop into a running session and a finished session into a recorded outcome: inbox polling, working-copy lifecycle, the run registry and its concurrency cap, log capture, exit classification, notifications, park and pause re-launches, the account's usage gate, the stall watchdog | the outer-loop scripts written into `<scripts_dir>` — chiefly `autonomous-watcher.sh` — plus the daemon unit the harness CLI installs. The harness repository's `docs/watcher.md` is the format of record for all of it |
| **2. Entry-point commands** | One thin entry point per work type, each naming the instruction file it runs and resolving nothing else | `${CLAUDE_PLUGIN_ROOT}/commands/` — nineteen `branch-*` commands across supervised, semi-autonomous and unattended operation, of which three are the unattended entry points a drop can be routed to, beside `/autonomous-sdlc-harness:harness-analyze`, the supervised setup command that fills the conventions documents `init` writes as skeletons |
| **3. Instruction cores and their forks** | The phase loops themselves. Across the **four instruction families** — orchestration, planning, hands-on-review fixing and fix-plan writing — a mode-free **core** owns every phase body and each mode file is a **thin fork** carrying binding values plus what its mode purely adds. The documentation engine sits outside the shape as a standalone flow with no core | `${CLAUDE_PLUGIN_ROOT}/instructions/` — twenty-seven instruction files, including the shared unit loop the per-unit phases cite and the mode contract the pairs compose through. `${CLAUDE_PLUGIN_ROOT}/docs/AUTONOMOUS_FLOW.md` → `## Instruction-file shape` states the rule |
| **4. The agent fleet** | Single-purpose sub-agents, each with its own `tools:` allowlist: the layer implementer and its per-unit reviewer, the plan writers and plan reviewers, the branch gates and their meta-reviewer, the skeptic, the interactive-test agents, the docs pair, the conventions writer and the conventions reviewer the setup command dispatches, the statistics writer, and the one agent that commits | `${CLAUDE_PLUGIN_ROOT}/agents/` — twenty-one agent definitions |
| **5. The sandbox** | What the run may and may not reach: an allow/ask/deny permission profile selected per run, the tool guards that judge a command before it executes, and the protected-branch backstop git itself runs | the generated permission profile in the adopting repository, the six `PreToolUse` guards in `${CLAUDE_PLUGIN_ROOT}/hooks/`, and `pre-push` in `<githooks_dir>` |

Those three counts are of `.md` files in the named directories, and `ls <dir>/*.md | wc -l` prints the number as stated only for `agents/`, where it returns twenty-one. It returns twenty in `commands/`, because the row above counts `branch-*` commands and `/autonomous-sdlc-harness:harness-analyze` is not one; twenty-eight in `instructions/`, because that directory **does** hold a `README.md` — a README rather than an instruction file, and not one of the twenty-seven. `agents/` and `commands/` hold a **`README.txt`** instead, deliberately not `.md`, because component discovery parses every `.md` file in those directories as a component and would load a `README.md` there as a twenty-second agent or twenty-first command; renaming either is the trap.

## The structural decision the rest of it rests on

**The control plane contains no orchestration logic, and the engine contains no infrastructure logic.** Layer 1 knows about files, working copies, process ids and a JSON registry, and never inspects what it launched. Layers 2–4 know about phases, agents and artifacts, and resolve every path from a bare `git rev-parse --show-toplevel`, so a run does not know whether it is executing in a sibling working copy or in the checkout the daemon was installed from.

That separation is why the second and third work types cost no new orchestration: a hands-on-review fix cycle and a documentation run are new bindings of the same registry record and the same launch path, and the exit classifier, the resume paths, the concurrency cap, the kill switch and the notifications were all shared unchanged. It is also the answer to "could it be triggered by something other than a file?" — a different trigger is a new adapter over the same entry-point commands, not a rewrite of anything below them.

## What one run does, end to end

**The trigger, and everything up to the first token.** A file lands in the inbox; the next poll pass routes it by filename to an entry-point command and a working-copy strategy, prepares that copy, places and commits the dropped artifact, and launches one headless session in it under the generated permission profile, teeing the session's raw event stream to one file and a formatted, tailable log to another. All of that is the harness repository's `docs/watcher.md` §1, and the reason it is worth naming here at all is what it hands the run: a **clean working copy of the run's own branch, with the prompt already committed in it**, so the engine's clean-tree precondition is honest from its first step rather than something it has to establish.

**The prompt is data, not instruction.** The launch names the prompt's **path**; the body is never inlined into the trusted instruction layer, and the planner reads it as untrusted task data. What the run does with it comes from the plugin. The containment underneath — the deny floor, the protected-branch backstop, the script allowlist, no deploy and no bare push — is what makes a prompt that tries to be an instruction harmless even if the delimiting failed rather than merely unlikely to be read.

**Planning.** One writer/reviewer loop with two plan gates nested ahead of the structural one:

```
task-plan-writer → business-parity gate → architecture gate → task-plan-reviewer
       ↑_____________ FAIL: revise, then re-run every gate ______________|
```

The order is cheapest-to-fix-if-wrong first: a plan that targets the wrong behaviour is worth catching before a reviewer spends effort on where its code should live, and both are worth catching before anyone grades the plan's structure. The output is deliberately **split**: a thin story index carrying the ordered readiness list, plus one self-contained detail file per task. A separate loop produces the interactive-test plan where that phase is configured on. At convergence the plan is **committed** — it is an artifact of the branch, which is what makes the run resumable and the plan reviewable afterwards.

**Implementation.** Phase **A** walks the story index's readiness list one unit at a time: route by the `_(layer: …)_` tag on the index line, dispatch the implementer, optionally review, then dispatch the committer once — which flips that entry to `[x]` and stages it *with* the code, so the checkbox and the commit land together. Then the branch gates in a fixed order — **A1.5** parity (where configured), **A2** architecture, **B** the end-of-branch review and its meta-review, **C** the fixes for it, **C2** the adversarial skeptic, which re-runs the earlier gates' reachability, citation and divergence checks from the opposite posture and files only what their trusting pass missed. **E** exercises the running application where that phase is on, and **D** closes: documentation where configured, then the statistics file, then the phase's own dispatch-additions record, then the improvement-observations intake, then the clarification digest, then the Done summary. The ordered walk, and what each phase is gated on, are `${CLAUDE_PLUGIN_ROOT}/docs/AUTONOMOUS_FLOW.md` → `## The inner loop of a task-prompt run`.

The thing worth pointing at on a whiteboard is that **every review phase has the same shape**: generate the findings → commit the index → walk the index's checkboxes → fix each → commit each. Same unit loop, same committer, same readiness heading, and the loop does not care which index it was handed. Adding a gate is adding an index; it is not adding a mechanism.

**Isolating the interactive-test phase is the hard part of running several at once.** Two runs sharing a git working copy is prevented by construction, but a dev server, a browser and a set of test accounts are all outside git. So the phase binds its **own** port — probing for the first free one at or above the configured seed, failing loudly on a collision instead of sliding quietly to the next port, and naming that same port again at teardown so a finishing run never kills a sibling's server. Each per-test dispatch is a fresh **agent** session but not a fresh browser — the browser servers are session-level and shared across dispatches — so the tester clears the application's client storage itself before its first step, which is what buys clean per-test attribution *within* a run; the port and the account locks, not that step, are what keep two runs apart. Test accounts are reserved through a **machine-global** lock set rather than a per-working-copy one — deliberately, because two working copies of the same repository are exactly the pair that would otherwise park the same account.

**The exit.** A session's outcome is classified from the engine's real exit code **plus the sentinels it left behind**, into one of the five terminal states in the harness repository's `docs/watcher.md` §1. That the classification lives out there rather than in a session-end hook is a design decision, not an accident: the plugin declares only `PreToolUse` guards and no session-end hook, because a hook inside the session can only report that the session ended — it cannot tell a run that parked with a question from one that finished from one that died.

## The ways a run stops, and which of them come back

| | Who initiates | Comes back? | Mechanism |
|---|---|---|---|
| **Park** | the run, because it has a question | yes, when the park's question file is answered | writes a question file under `<state_dir>/clarifications/<branch>/` and **ends the session** |
| **Operator pause** | a person | on a `RESUME` sentinel | `PAUSE` request → the run yields at a clean boundary → `PAUSE_ACK` |
| **Usage pause** | the usage gate, on the account's own rate-limit signal | yes, when the window resets | the same protocol, plus a recorded resume time the gate acts on |
| **Self-pause** | the run, after repeated infrastructure failures on one dispatch | no — an outage has no predictable reset | writes the ack directly, with no request from anyone |
| **Per-run brake** | a person | no | `<state_dir>/STOP` in one working copy, checked by the run before every dispatch |
| **Global kill switch** | a person | no | `<MAIN_REPO>/<state_dir>/AUTONOMOUS_STOP`, which also blocks new launches and resumes |
| **Stall watchdog** | nobody — the control plane, on a run that is alive but hung | yes, up to its restart cap | kills the process tree and brings the run back through the ordinary resume path |
| **Park-loop guard** | nobody — the control plane, on a run whose resumes make no progress | once an operator clears it | stops resuming the run and records `park_loop` |

The protocol behind the first four is `${CLAUDE_PLUGIN_ROOT}/instructions/autonomous_pause_and_ledger.md`, the two brakes are `${CLAUDE_PLUGIN_ROOT}/docs/AUTONOMOUS_FLOW.md` → `## Safety / reversibility`, and the daemon's half of all of it is the harness repository's `docs/watcher.md` §4.

**The shape to notice is that every voluntary stop ends the session.** That is what makes waiting free: a run that polled for its answer would burn dispatches against its own ceiling to learn nothing. It also means every one of these is the *same* mechanism seen from different sides — which is only possible because of what holds the state.

**Durable state is the branch, not the model's memory.** Every unattended run keeps a committed, phase-level **flow-progress ledger**, and it is deliberately two levels that are never conflated: the **ledger** says which *phase*, and the **detail indices** — story index, each review's findings index, the interactive-test index — say which *item*. A phase entry flips `[x]` only *after* that phase reached a recorded outcome — its artifact committed where the phase produces one, or the clean pass where it correctly produces none — and a review phase's generate and fix halves are separate entries. So a crash during generation re-generates, a crash mid-fix-loop skips regeneration and resumes from the findings index, and "where do I resume" is **computed** — jump to the first `[ ]` — rather than inferred from a transcript that may have been compacted away. The ledger's schema, its flip contract and its resume algorithm are the pause-and-ledger instruction's; that it exists is why pause, park, usage pause and watchdog restart are one mechanism rather than four.

**The usage gate acts on the one signal a run cannot see about itself.** Rate limits are account-global and arrive as events on a run's own output stream — which that run cannot read, because it is producing it. The control plane tees every stream, so it is the only component positioned to see the account's state; it pauses through the ordinary protocol and nothing else, and never kills anything. The stall watchdog is its neighbour and handles the opposite case: a run that is alive but has stopped making progress, which needs corroboration beyond a stale timestamp because a long silent reasoning turn looks identical from outside. Both are the harness repository's `docs/watcher.md` §4 and §5.

## Why the safety model is shaped the way it is

- **Working-copy isolation is the primary boundary**, not a convenience. Two runs share no index, no working tree and no branch, and nothing a run does reaches the checkout a person is working in.
- **The deny floor beats every allow**, which is exactly why the browser-tool closure is *not* made there: a namespace-wide deny would revoke the interactive-test agent's own grant along with everybody else's. That closure is made per agent, by each definition's `tools:` allowlist, and an agent added without one silently re-opens the namespace.
- **Allow-list completeness is load-bearing in a way it is not interactively.** In a headless session an un-allowed, un-denied tool call **stalls** rather than prompting, so a permission gap is an outage rather than a question. The profile is generated from the repository's own configuration for that reason, and the one entry generation cannot write — a helper reached through a runtime-resolved plugin root — is called out for the adopter to hand-add.
- **Capability is withheld by basename, not by hope.** The script-allowlist guard auto-allows the wrappers a run legitimately needs and stays **silent** on the rest — it has no deny arm, so a withheld allow is a fall-through to the permission profile, which carries the project's deploy command in `ask` — evaluated before any `allow`, and unanswerable in an unattended run. The allow is bounded twice: by the deny list, which carries that deploy command and the outer loop explicitly, and by a whole-string construct scan that withholds it from any command carrying `$(…)`, a backtick, `|`, `<`, a braced form other than a bare `${IDENT}`, or a `>` that is neither a descriptor duplication (`2>&1`, `>&2`, `2>&-`) nor a redirection to the literal `/dev/null` — subject included. So no deployment is reachable **from a command string**; what a subprocess reaches instead is the next bullet's subject, and it is ranked there rather than claimed away here.
- **The protected-branch guarantee is ranked honestly**: the `pre-push` git hook is the layer the model depends on for a push **git performs**, because git runs it however git was invoked, including from an allow-listed interpreter subprocess; the string-matching guard above it is fast, legible refusal that a subprocess trivially bypasses. The ranking moves on one shape, measured: a tool that pushes against the git backend itself, as `jj git push` does, runs no git hook, and there the string-matching guard is the only layer that fires — while the push **names** a protected target. Name no bookmark and that guard does not fire either, since jj leaves `HEAD` detached and it has neither a target token nor a branch to judge: that form is refused by neither layer, and only a forge-side ruleset covers it. Both resolve the protected set from configuration — `<protected_branches>` together with `<default_branch>` — and neither carries a branch name of its own. `${CLAUDE_PLUGIN_ROOT}/docs/AUTONOMOUS_FLOW.md` → `## Output guarantee` states the model; the point here is that it is written down in that order rather than presented as a floor it is not.

# Part 2 — How to explain it

## The short version

> A headless multi-agent development system built on an agent runtime's plugin surface. You drop a task prompt into a directory; a daemon gives it an isolated working copy and launches a sandboxed headless session that plans the work, implements it unit by unit, puts the result through independent review gates including an adversarial one, exercises the running application, and ends at "branch ready for review" — never merging, never pushing to a protected branch, never opening a pull request. Several run at once, they survive crashes and rate limits by resuming from a committed phase ledger, and one asks a question by writing a file and ending its session rather than by blocking.

## The structure to draw

Three boxes and one arrow each way — **inbox → control plane → engine → agents** — with the **working copy** as the substrate underneath and **git commits** as the state store. Then four points, in this order.

**1. The control plane is a thin adapter, and that is the whole architecture.** It handles files, working copies, processes and a registry; the engine handles phases. Neither imports the other's concepts. That is why the second and third work types needed no new orchestration, and why a different trigger would be an adapter rather than a rewrite.

**2. Durable state is git, not memory.** A long agentic run gets its context compacted, crashes, and hits account limits. So nothing that matters lives in the model's head: progress is checkboxes in committed markdown at two levels, and a phase flips only after its recorded outcome — its artifact committed and pushed where it produces one, or the clean pass where it correctly produces none. That single decision is what makes pause, park, usage auto-pause and the hang watchdog the same mechanism.

**3. Context discipline is the performance constraint, not a style preference.** The orchestrator is forbidden from reading anything substantive. Reviewers return a verdict line, not a report. The orchestrator passes the *path* to the next implementer and never opens it — even dispatch routing is index-only, because the layer to route to is a tag on the index line rather than something inside the detail file. Plans are split into a thin index plus self-contained per-item files precisely so no agent ever loads more than the one item it is working on. This is the difference between a run that completes hundreds of dispatches and one that collapses early.

**4. Trust is layered, and the layers are ranked honestly.** Several review gates with different failure models — parity against a reference implementation, architecture, a general end-of-branch review, an adversarial skeptic that re-runs the end-of-branch reachability, citation and divergence checks while distrusting the spec they were graded against, and exercising the running application. The skeptic files *only* what the earlier gates did not — de-duplication against their filed findings, not a narrower scope. The two riskiest of those are **meta-reviewed by a different agent** before their fixes are applied, because an adversarial reviewer is the most false-positive-prone participant in the system and its output goes straight to code.

## The tradeoffs worth volunteering before being asked

- **Per-unit review is off in the unattended task flow and on in the fix flow.** It is one binding value in two forks over the same core, and the reason is an audit of real runs: the per-unit reviewers' findings were being re-derived downstream by the branch gates, while the extra dispatches dominated the implementation phase's wall-clock. The unattended flow leans on the branch gates; the **semi-autonomous** fork over the same core keeps the per-unit pass — a person is watching there and latency is cheap. (The third, fully supervised mode is not a fork over this core at all: it is a human-gated item loop that dispatches no reviewer agent and reviews in-session.) Same cores, different risk profile, different binding.
- **Regression coverage on re-test is intentionally incomplete.** A re-test round re-runs only the tests that were still failing. A fix that breaks an already-passing test is not caught until a full sweep, and forcing one is a documented, reversible action: un-check the boxes. That is a stated trade, not an oversight.
- **The protected-branch guarantee is a backstop, not a floor.** The string-matching guard sees only the literal command submitted, so any allow-listed interpreter defeats it; what actually holds is the git hook, which is itself bypassable on the box that runs it. A forge-side branch ruleset would be a true un-bypassable floor, and this release applies none — the configuration key for forge coupling is declared and has no reader yet. All of it is written down as a decision with an upgrade path rather than presented as a guarantee.

## Failure stories that make it concrete

- **The silently-wrong test target.** A dev server's default behaviour on a busy port is to take the next one instead. Two runs testing at once therefore produced a phase that passed while driving *another run's* build — every result confidently reported and none of them about the branch under test. The fix is three parts that only work together: probe for a free port per run, start the server with the flag that makes a collision an error, and tear down by naming the port that was bound. **Fail loudly beats fall back gracefully whenever the graceful path can produce confidently wrong results.**
- **The stranded run.** A usage pause is *requested* at one moment and *honored* minutes later, when the run reaches a clean boundary — and the tag that says "this pause was automatic, resume it when the window resets" is written at the request. A cleanup pass that removed stale tags, run naively inside that window, left a run that then paused with no tag at all: still paused, and skipped forever by a resume path that keys on the tag alone. The lesson is not about pausing. It is that a two-file protocol has an **intermediate state**, and the component that garbage-collects it has to be able to tell that state from a finished one.
- **A `completed` that was not.** A session interrupted part-way through a review still exits cleanly, so a zero exit code read as success and the branch was reported ready. Classification now takes the exit code **together with** the sentinels and artifacts the run left behind. **An exit code is a hint about a long-running agent, not a verdict.**

## The questions that get asked, and short answers

**"How do you stop it going off the rails?"** Independent limits, each on a different axis: a convergence cap per writer/reviewer loop (five iterations, then it halts and surfaces the findings), a hard dispatch ceiling per session, a re-test round cap, a per-run brake, a global kill switch and a park-loop guard that stops resuming a run whose resumes make no progress — plus a deny floor that beats every allow. The values live in the instruction cores that enforce them. Nothing retries forever, and anything that hits a cap stops and says so.

**"How does it ask a question without blocking?"** By an explicit ask-vs-assume policy: a low-stakes, reversible decision is assumed, documented in the plan, and the run continues; a high-stakes or irreversible one that cannot be resolved from the sources becomes a self-contained question file and the run **ends its session**. Parking costs nothing while it waits. The control plane notices the answer, re-launches the same entry point in the same working copy, and archives the pair only *after* that resumed session exits — consume-then-archive, so the answer is neither missed on re-entry nor processed twice.

**"How do you know it is any good?"** Every branch writes its own statistics file: a story-point-weighted success rate whose denominator is the scope that plan committed to and whose subtraction is the severity-weighted cost of what a human's hands-on review found afterwards. It is written once at branch-ready and recomputed after a fix cycle. The escapes are the other half — each becomes a one-line rule in the lessons ledger at `<state_dir>/lessons.md`, which an agent that plans work or grades it reads before it starts, so a defect that got past every gate once is a rule the next run is planned against.

**"What would you do differently, or what is next?"** The honest scope of this release is stated rather than defended in `${CLAUDE_PLUGIN_ROOT}/docs/AUTONOMOUS_FLOW.md` → `## Out of scope in this release`: no forge coupling — an opted-in run executes in a GitHub Actions job, but file drops still start and steer it — the flow ends at "branch pushed", and one machine by default, or a GitHub Actions job when opted in, with git only. Two more are known and deliberate — there is no cross-branch statistics roll-up, because aggregating across parallel working copies needs a writer that can see every branch at once and a home for the result that is not any one run's branch; and the protected-branch floor is still a backstop. On the other side of the ledger, the instruction corpus's own restructure has already landed: what were single large files with an override-over-canon indirection are now mode-free cores with thin forks over them, which is why a mode difference in this system is visible as a binding value rather than as a second copy of a phase that drifts.
