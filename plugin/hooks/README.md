# hooks/

**Who reads this:** an adopter deciding whether to enable this plugin in a repository, and a contributor changing a guard or adding one. It answers what each guard decides, *which* repository it decides about, what it does when it cannot read the answer, and how to reproduce any one decision by hand. The per-guard detail — every case, every refusal, the defects a shape already fixed — lives in each script's own header comment; this file is the contract they share.

Six guards ship here, declared in `hooks.json`. All six register on the `PreToolUse` event under the `Bash` matcher, take **no arguments** and carry **no `if:` condition**: each reads the command out of the hook payload and verifies for itself whether it has anything to say. That is deliberate — a `${…}` substitution in a command defeats static command matching, so a condition fires on commands that are not the guarded shape at all, which is how a plain `echo ${SOME_VAR}/scripts/probe.sh` once drew a commit refusal. A spurious fire is harmless; a wrong condition is not.

| Guard | May emit | What it decides |
|---|---|---|
| `autonomous-protected-branch-guard.sh` | `deny` or silence | Refuses a `git push` / `git merge` / `git rebase` it can **prove** targets a branch the resolved repository's own config protects (including as a `+<branch>` force refspec), or that is issued while HEAD is on one, or whose target names a *set* of refs it cannot clear against the protected set — a glob refspec, `--all`, `--mirror`. **Every** push/merge/rebase in a compound is judged, not just one of them, and git's global options do not hide the subcommand from it, in either spelling git takes (`--git-dir=<dir>` and `--git-dir <dir>` alike) — for the word-taking options `hc_git_piece_parts` enumerates, which is its stated bound and is derived from git's `handle_options` rather than from its usage block. The only guard in the plugin that denies. |
| `git-commit-branch-guard.sh` | `allow`, `ask` or silence | Allows a `git commit` when the repository it names is on an ordinary branch; asks when that branch is protected, when HEAD is detached, or when the protected set will not resolve. |
| `git-rewrite-branch-guard.sh` | `allow` or silence | Allows `git mv`, `git rm` and tracked-file `rm` on an ordinary branch — only when every piece of the compound is a known-safe prefix, a `git mv`/`git rm` whose own `-C` (if it has one) resolves to the repository the guard judged, or an `rm` whose every path is non-glob, in-workspace and git-tracked. |
| `autonomous-script-allowlist-guard.sh` | `allow` or silence | Allows a script invocation only when **every** script the command runs resolves under the configured `scriptsDir` of the resolved repository or one of its sibling worktrees, and none of them is on the deny list (§The deny list). The allow covers the **whole command**, so it is all-or-nothing over every piece: a piece that runs no script must match the same safe-prefix set `allow-safe-compounds.sh` judges it against, and a piece that names a script must *run* it — `rm -rf <scriptsDir>/<wrapper>.sh` names an impeccable path and is silent. **"Every piece" is every piece of the separators the shared splitter reads — `&&`, `\|\|`, `;` and a bare `&`.** A pipe and a balanced `$(…)` are none of those and would ride along inside a piece, so they are withheld by a second mechanism instead: a whole-string scan for the shell's composition grammar — `$(`, a backtick, `\|`, `<`, every superstring of those such as `<<`, `<<<` and `<(`, any `${…}` that is not a bare `${IDENT}`, and any `>` that is neither a **descriptor duplication** (`2>&1`, `>&2`, `2>&-`) nor a redirection to the literal **`/dev/null`** — silences the command before any piece is judged (`docs/guard-verification.md` §2.4, residual `j` — disclosed against the separator bound, then closed by this scan). That is a scan for **constructs, not for binaries**: unlike its `allow-qa-credentials-read.sh` twin this guard refuses no token by name, deliberately, because it judges commands carrying prose and paths where a false positive is a stall. **The cost is two classes, both one prompt and never a permit**, since this scan grants nothing: (i) `\|\|` is a superstring of the scanned `\|`, so it no longer reaches the splitter either; and (ii) the `<`, `>`, backtick and `\|` arms fire on **prose in a wrapper's own arguments** — a commit subject naming a placeholder in angle brackets or quoting an identifier in backticks is silenced. Class (ii) is the larger one and it is accepted, because the alternative is parsing quoting. Two parts of it are **not** accepted, and each is why its arm is scanned by shape rather than as a byte: the `${…}` part, so that arm admits `${IDENT}` — the shipped instruction corpus's own commit invocation carries `${branch}`, so **that invocation is auto-allowed by this guard**, not left to the profile's literal forms — and the redirection part, so the `>` arm admits the two destinations above, which is what makes `bash <scriptsDir>/<wrapper>.sh 2>&1`, the flow's own route around a missing permission entry, reach the decision at all. `${x@P}` and every other braced spelling, and every `>` naming a **file** — the spelling that overwrites a wrapper — stay silenced (`docs/guard-verification.md` §3.3, W19–W21 and W23–W24). **Neither narrowing moves what this guard emits when it withholds**: silence, and never a deny — the §Fail closed row below is unchanged. Without that, one allowable wrapper at the front would carry the rest of the compound with it, and a permission `deny` cannot catch the remainder because a profile deny is anchored at the start of the command string. **A `.sh` token carrying a `$` in any component is never granted**, in any spelling and whether the `$` is in the basename or in a directory: the deny list and the `..` test both compare literals, so `<scriptsDir>/$NAME.sh` and `<scriptsDir>/$D/x.sh` would otherwise be granted while the shell decides afterwards which file runs (§3.1's N84–N86). This is the capability containment for an unattended run. |
| `allow-safe-compounds.sh` | `allow` or silence | **What it is handed is a compound, or a single statement naming a workspace directory with `git -C`** — nothing else reaches it, and a single statement carrying no `-C` is left to the permission profile. That one exception is the spelling the profile cannot express: its `git <verb>` entries are prefix matches anchored at the start of the command string, so none of them fires on `git -C <dir> <verb>` (`docs/guard-verification.md` §3.3, W25–W26). It allows when every piece begins with a known-safe prefix, so a block of individually-allowed statements does not stall on one prompt. Every piece is judged against the same prefix set a single statement would be — a piece naming a workspace directory with `git -C` or `<runner> --prefix` is judged on its subcommand; it never splits on a pipe, and it does split on a bare `&`, so the statement after one is judged rather than carried by the prefix in front of it (the redirection spellings `&>` / `>&` / `<&` are not separators). One class of piece is refused whatever prefix it matches: a `git branch` that deletes, renames or overwrites a ref, in any abbreviation git accepts for the option — behind a `-C` as plainly as without one, which is what a broad `Bash(git -C:*)` profile entry would have undone. **Admitting that statement moves what reaches the judgement, not what is emitted when it withholds**: silence, and never a deny — the §Fail closed row below is unchanged. |
| `allow-qa-credentials-read.sh` | `allow` or silence | Allows a read-only inspection of the file named by `qa.credentialsPath`, and only while `phases.qa` is `true`. **What "that file" means is a word of the command whose BASENAME equals the configured path's** — equality, so a path merely *carrying* that basename (`<creds>.bak`, `/tmp/notes-<creds base>-draft`) gets nothing, and a same-named file in another directory is the one thing equality cannot tell apart (`docs/guard-verification.md` §2.4, residual `l`, and §3.1's N108–N113). Keying on the basename rather than on a resolved path is what makes a relative and an absolute spelling of the configured file one pattern. Silent on any mutation, exfiltration or interpreter token — the shells, `env`, `xargs`, `awk`, `sed`, `sort` and `uniq` among them, because it never splits on a pipe — and on **any** redirection, wherever it points. The allow covers the **whole command**, so it is all-or-nothing over every piece: a piece that names the credentials file must *read* it (`find <creds> -delete` names an impeccable path and is silent), and a piece that names it nowhere must match the same safe-prefix set `allow-safe-compounds.sh` judges it against, so no **piece** rides along on the read. **"Every piece" is every piece of the same four separators — `&&`, `\|\|`, `;` and a bare `&`.** A pipe and a balanced `$(…)` are none of those, and here it is the refused-token scan above, not a piece test, that reaches those tails: a tail naming no refused token still rides along (`docs/guard-verification.md` §2.4, residual `k`). That is why `sort` and `uniq` are refused tokens rather than merely absent from the read set — off the read set they are refused in command position only, and `cat <creds> \| sort -o <out>` writes the second cleartext copy from the tail (§2.4, residual `i`, and §3.1's N87–N92). |

## Registration, and why it lives here rather than in generated settings

Three facts about this manifest were measured rather than assumed, and are recorded alongside the rest of the packaging contract in `docs/development.md` §3:

- **`hooks.json` needs the `{"hooks": { … }}` wrapper.** A bare event map — `{"PreToolUse": [ … ]}` — fails validation with `hooks: Invalid input: expected record, received undefined`. The event names go one level down.
- **`${CLAUDE_PLUGIN_ROOT}` expands inside a hook's `command` string declared here, and does *not* expand in a settings-file hook.** That asymmetry is the whole reason the guards are declared in this file: it is the only place a plugin-relative path resolves under both a git-sourced install and a directory-sourced one. The generated permission profile therefore writes no `hooks` key at all, deliberately — plugin hooks **append** to whatever the adopter already has rather than overriding it, so nothing needs to be written into settings to make these fire.
- **Every occurrence of the token in a `command` string here sits inside double quotes together with the path it prefixes** — `bash "${CLAUDE_PLUGIN_ROOT}/hooks/<guard>.sh"` — because `claude plugin validate --strict` warns on an unquoted token, which fails gate `1a`, and because a plugin root containing a space otherwise splits the command, so the guard errors instead of judging. Shell form was kept over exec form: quoting changes only word boundaries, is correct whether the runtime substitutes the token or the shell expands it, and needs no field beyond `matcher` / `type` / `command`. The exec-form findings and the measured validator message are in `docs/development.md` → `## 3. Manifest facts a contributor must not rediscover`.

Keep the JSON strictly valid — no comments, no trailing commas — and add no field beyond `matcher`, `type` and `command`: `claude plugin validate --strict` promotes an unrecognized field to an error, and rejects a bare `${CLAUDE_PLUGIN_ROOT}`, so a new entry double-quotes the token together with its path.

The entries are ordered by the severity of what they can emit — the single `deny`-capable guard first, then the one that can `ask`, then the four allow-only ones. **That order is documentation, not precedence.** A `deny` from any hook beats every `allow` from every other, whatever sequence they appear in, so reordering the file changes no outcome; the sequence exists so a reader can see at a glance which entry is the one that can refuse.

## Which repository a guard judges

A guard resolves the repository it is judging **from the command it was handed** — never from a hardcoded path, and never from an assumed session root. In order:

1. the first `git -C <dir>` in the command string (for the commit guard, the *commit piece's own* `-C`, not any earlier piece's);
2. else the first leading `cd <dir>`;
3. else the hook payload's own `.cwd`;
4. else the process `$PWD`.

That anchor then goes through `git -C <anchor> rev-parse --show-toplevel`, and `harness.config.json` is read **at that resolved root and nowhere else**.

This is what makes one registration serve every checkout. The alternative — a registration carrying a fixed repository path — judged the *primary* checkout, permanently on the default branch, every time a commit was made in a sibling worktree on a feature branch. Interactively that is a stray prompt; in an unattended run an `ask` cannot be answered, so it is a silent stall.

## Jurisdiction: no config, no opinion

**A repository with no `harness.config.json` at its resolved root has not adopted the harness, and every guard here stays silent in it** — no `allow`, no `ask`, no `deny`. The same silence covers a path that is not inside a git repository at all.

This is the one deliberate permit-by-default in the set, and the reason is the delivery mechanism: a plugin hook fires in **every** session the plugin is enabled for, including repositories that never ran `init`. A guard that answered those would either nag in a repository that never asked for it or, worse, grant in one. The caller-agnostic backstop for a repository that *has* adopted is the adopter's own committed pre-push hook at `<githooks_dir>/pre-push`, wired through `core.hooksPath`: git runs it on every push **git** performs, whoever invoked git, so it catches the subprocess pushes a Bash-string matcher structurally cannot see. Caller-agnostic *within git* is the whole of that, and the split runs the other way at the edge: a tool that implements push against the git backend itself, as `jj git push` does, performs no git push and runs no git hook, while these guards read the submitted command and **do** see it, drawing the same decision `git push origin <protected>` draws **when a protected target is named in it** (`jj git push -b <protected>`) — both measured, one repository, seconds apart. So the case the hook does not cover is a person at a terminal rather than an unattended run — as far as the target is named. An argument-less `jj git push` runs no git hook, carries no target token for the explicit-target test, and cannot trip the HEAD-on-a-protected-branch test either, because jj leaves `HEAD` detached and a detached `HEAD` is a silent row in the table below: that form is refused by neither layer, and the forge-side ruleset named at the end of this paragraph is its only cover. These guards are the fast on-box feedback layer; that hook is the caller-agnostic one within git, and a forge-side branch ruleset is the only real floor. Nothing here provisions one, and nothing here assumes one exists.

## Fail closed — and what that means for an allow-only guard

Within jurisdiction, a configuration document that cannot be resolved — invalid JSON, more than one JSON document in the file, or a `jq` too old to run the load — must **never** produce a permit. Which is not the same as producing a refusal:

| Guard | Configuration unresolvable, within jurisdiction | No `harness.config.json`, or one that cannot be read | Payload will not parse |
|---|---|---|---|
| `git-commit-branch-guard.sh` | **`ask`**, with a reason naming the unresolvable configuration | silent | silent |
| `autonomous-protected-branch-guard.sh` | **`deny`** | silent | silent |
| `git-rewrite-branch-guard.sh` | silent | silent | silent |
| `autonomous-script-allowlist-guard.sh` | silent | silent | silent |
| `allow-safe-compounds.sh` | silent | silent | silent |
| `allow-qa-credentials-read.sh` | silent | silent | silent |

**Three conditions look like that first column and are not it.** An **absent** `jq` is not an unresolvable configuration — with no `jq` no guard can parse its payload, so all six are silent, the deny guard included; a `jq` *older than 1.5* is the first column, and §Prerequisites below separates the two. An absent **`defaultBranch`** resolves the document but not the protected set: the three guards that consult it answer as the first column says, and the three that never read it — `autonomous-script-allowlist-guard.sh`, `allow-safe-compounds.sh`, `allow-qa-credentials-read.sh` — go on permitting, correctly, because nothing they decide depends on it. And a configuration file that is present but **unreadable** — root-owned, or `0600` to another user, which is a shape a CI checkout produces — is *outside* jurisdiction rather than unresolvable inside it: the jurisdiction test is `[ -f ] && [ -r ]`, so all six guards are silent exactly as they are with no file at all, the deny guard included. If you want a push to `main` refused, the configuration has to be readable by the process the guard runs in; an unreadable one buys the second column, not the first. Every cell of that column, of the two beside it and of the conditions this paragraph separates out is measured, with a live positive control per guard and with fault injection identifying which leg produces each silence, in `docs/guard-verification.md` §2.3.

For the four allow-only guards, **failing closed means never emitting `allow` — not emitting something else.** Silence defers to the adopter's permission profile, which still prompts for whatever it would have prompted for, so a closed outcome costs a prompt and never a false permit. Those four are structurally incapable of overriding a deny, because they never emit one.

The protected-branch guard is the inverse, and that is why its unresolvable-configuration row reads `deny`: refusal is its whole job, so *inside jurisdiction* silence would be exactly the permit it exists to withhold. A guard that cannot parse its payload at all has no command to judge and exits 0 silently in every case.

No branch name is baked into any of these files, and no command name from the stack this was extracted from. The protected set is *(`protectedBranches` if present, else the schema default)* ∪ *{`defaultBranch`}*, matched as globs so one `<ns>/*` entry covers a namespace; the scripts directory and the credentials path come from the adopter's own configuration, and the safe prefixes are the adopter's configured commands on top of a stack-neutral base set the library carries in `hc_safe_prefixes`. The literal file names that do appear are the four deny-list basenames, in §The deny list below. A guard that failed to recognise an adopter's protected branch would not stall — it would **permit**, which is why none of them carries a literal branch list.

## The deny list

`autonomous-script-allowlist-guard.sh` auto-allows scripts under the configured `scriptsDir`, and this list is the *second* of two subtractions from that allow. The first is the construct scan in the table above, which withholds it — silently, whatever the basename — from any command carrying `$(…)`, a backtick, `|`, `<`, a braced form other than a bare `${IDENT}`, or a `>` whose destination is neither a descriptor nor `/dev/null`, and from any `.sh` token carrying a `$` in any component. The deny list subtracts by basename instead, because `scriptsDir` is where `init` writes the outer-loop scripts too and a small set of them must not be reachable however plainly it is spelled. Four entries, and they are all of it:

| Basename | Capability withheld |
|---|---|
| `deploy.sh` | A deployment reachable from an unattended run. |
| `autonomous-watcher.sh` | Starting or ticking the daemon that supervises the run — an agent that could start runs could start runs about itself. |
| `restart-watcher.sh` | Bouncing that daemon: it kills whatever run is in flight, and since the watcher's sweep force-deletes merged branches it reaches a branch deletion at one remove, through a service manager. |
| `cleanup-merged-worktrees.sh` | Removing sibling working copies and force-deleting local branches (`git branch -D`). |

**Being on this list is not a refusal by this guard.** It is the withdrawal of a permit: the guard grants nothing and the invocation falls through to the adopter's permission profile, which asks or refuses on its own terms — exactly as it would for any other command. For the three outer-loop entries the generated profile emits no rule at all (`agentInvocable` is `false` for each of them in `cli/src/generators/outerLoopScripts.ts`), and the deploy wrapper's own rows are written into `ask` deliberately — so the practical outcome for a dispatched agent is a prompt it cannot answer, never a silent permit. The other outer-loop scripts written into the same directory — `create-worktree.sh`, `setup-worktree.sh`, `autonomous-notify.sh`, `autonomous-format-stream.sh`, `docs-search-server.sh`, `scratch-run.sh` — stay allowed: none is destructive, and narrowing past a measured need is a change nothing has justified. The last of them executes an *argument*, and is allowed on a narrower ground: it runs only a file under the run-artifact tree's `scratch/` directory, which the script itself enforces rather than this list.

Matching is on **basename**, **lower-cased on both sides**, so one entry covers a relative spelling, an absolute one, a quoted one, any capitalisation and the same script inside any sibling worktree. **It covers those spellings and no others, because it compares a literal:** a path whose basename is a shell variable is not any of the four names, and the four capabilities above are withheld from it by a different rule — the guard grants nothing for a `.sh` token carrying a `$` in any component, so it never reaches this table. Read the two together; neither withholds these capabilities on its own. Case is ignored because a case-insensitive filesystem — the macOS default — runs `deploy.sh` under the spelling `DEPLOY.sh` too; where the filesystem is case-sensitive that spelling is a different file, and ignoring case there costs at most one permission prompt for a script whose basename differs from an entry only in case. A compound naming one allowed and one denied script gets nothing, because the guard requires *every* script a command runs to be allowable — and, more generally, every piece of the command to be judged safe, so appending a denied wrapper to an allowed one buys nothing and neither does appending anything else.

**Why this list was extended by a later item.** Roadmap item 5 shipped this guard when the only script generated under `scriptsDir` was the deploy wrapper; the watcher, its restart wrapper and the cleanup sweep are roadmap item 6's, and item 6 is also where the destination decision was settled — that those scripts are written into the adopter's `scriptsDir` rather than run from the installed CLI package. Until that landed there was no basename to deny and no directory to deny it in, so the two halves could not be settled in one place: item 6 owns both the scripts and the entries that withhold them, and extended an item-5 asset to add them.

## The shared library

Configuration is reached only through `hooks/lib/harness-config-lib.sh`, which owns the resolution order above, the compound splitter every guard shares, and an explicit three-state answer (`protected` / `not protected` / `unresolvable`) so a caller can never mistake "could not read" for "not protected". It also owns the *path-anchored* prefixes — the arms that name a per-checkout directory (`cd <dir>`, and the exact, tail-free `<pkg-manager> --prefix <dir>`), derived from the resolved root, the configured `projectName` / `appDir` / `stateDir` and the leading word of each configured command — and, alongside them, the two rewrite helpers that handle the shapes carrying a **subcommand** after the directory (`git -C <dir> …`, `<pkg-manager> --prefix <dir> …`): an arm matches on the directory alone, so a subcommand would ride along on it, and instead the piece is rewritten to its directory-free form and judged against the same prefix set the bare spelling is judged against. That rewrite is also the whole of what `allow-safe-compounds.sh` does with the one **single** statement it is handed: the `git -C` form takes the same helper and the same prefix set, so only the route in is new. All four allow-only guards — `git-rewrite-branch-guard.sh`, `autonomous-script-allowlist-guard.sh`, `allow-safe-compounds.sh` and `allow-qa-credentials-read.sh` — build all of it from these same functions, so no two of them can end up applying a different definition of the workspace.

It owns one **refusal** on the same terms, for the same reason. Prefix matching is on leading words, so the base set's `git branch` — the listing form the flow needs — also covers `git branch -D <x>`, which is one of the forms the generated permission profile denies outright; a permission `deny` is a prefix match anchored at the start of the whole command string, so it cannot reach that piece inside a compound — nor a `git -C <dir> branch -D <x>` standing on its own, where the directory defeats the anchor and which `allow-safe-compounds.sh` is now handed (`docs/guard-verification.md` §3.3, WK30). `hc_piece_is_never_safe` refuses both instead, and all four of those guards call it before every other test, so the plugin does not hand out with one file what it refuses with another. Its header lists which `git branch` operations are refused and which spellings stay granted; a long option is matched as a **prefix** of one of those operations, because git accepts any unambiguous abbreviation and `--dele` deletes; an entry added to the profile's `deny` floor that names a base-set prefix belongs there too.

Each guard sources it by a path computed from `${BASH_SOURCE[0]}`:

```sh
. "$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)/lib/harness-config-lib.sh"
```

**Never `${CLAUDE_PLUGIN_ROOT}` inside a script body.** That token is substituted by the runtime into a hook's `command` string — it is not an environment variable the resulting `bash` process can rely on, so a script that dereferenced it would work when launched through the manifest and break the moment anyone ran it by hand, which is precisely what the reproduction recipe below asks them to do.

## Prerequisites

`git` and `jq` **1.5 or newer**, both on `PATH`. Nothing else — the guards are plain `bash` with `set -u` (never `set -e`), and `bash` 3.2 is the floor so that macOS's `/bin/bash` qualifies. Five of the six run a cheap top-level string filter before any `git` or `jq` work, because they fire on *every* Bash call and an unconditional subprocess per hook is a per-tool-call tax. `allow-qa-credentials-read.sh` is the exception and cannot be otherwise: the string it keys on is the adopter's configured credentials file name, unknown until the configuration has been read, so it decodes the payload first and then runs its (configuration-independent) refused-token scan before resolving the repository. Enabling this plugin therefore costs two `jq`, one `grep` and one `git rev-parse --show-toplevel` on every Bash call in every session, including in repositories that never adopted the harness — all four from that one guard, and the `git rev-parse` is the largest of them. That guard's own header carries the numbers under **WHAT THAT COSTS, AND WHY THE COST IS ACCEPTED RATHER THAN UNNOTICED**, and the paragraph after it, **THE `git rev-parse` STAYS, DELIBERATELY**, is where the further narrowing that would remove the `git rev-parse` is measured and rejected.

**A missing `jq` and a too-old `jq` fail differently, and the second is the one that will confuse you.** If `jq` is missing, **every guard exits 0 silently**: no permit is granted, no refusal is issued, and no guard errors. The behaviour is safe but it is also invisible, so a repository whose guards have all gone quiet is worth checking with `command -v jq` before anything else. If `jq` is present but older than 1.5, `command -v jq` **succeeds** and the guards are not quiet — the configuration load is a compile error, so every **adopted** repository reads as one whose configuration cannot be resolved: within jurisdiction, ordinary pushes to non-protected branches are denied by `autonomous-protected-branch-guard.sh`, `git-commit-branch-guard.sh` asks on every commit, and the four allow-only guards stop permitting anything. (A repository with no `harness.config.json` is outside every guard's jurisdiction and stays silent, as always.) Check `jq --version`, not just `command -v jq`. The constructs that set the floor are listed in `lib/harness-config-lib.sh`'s header under **JQ 1.5 IS THE FLOOR**.

## Reproducing a decision by hand

Every guard takes its payload on stdin and prints at most one JSON object. To reproduce any decision:

```sh
printf '{"tool_input":{"command":"<the command>"},"cwd":"<the directory>"}' \
  | bash plugin/hooks/<guard>.sh
```

Read the emitted object's `hookSpecificOutput.permissionDecision` (`allow`, `ask` or `deny`) and its `permissionDecisionReason`. **No output and exit 0 is a decision too** — it is the deliberate silent outcome from the tables above, not a failure and not a crash; check it against the guard's own fail-closed table before treating it as one.

Each guard's header carries its own worked REPRO block: the exact command strings that produce each decision, and the ones that produce silence, including the standing regression cases (a quoted script path, an incidental protected-branch name in a non-argument position, a worktree commit with no `-C` in the command). Point `<the directory>` at a throwaway `git init` fixture carrying a `harness.config.json` and two branches to exercise the jurisdiction and protected-set legs without touching a real checkout.

What reproducing a single decision cannot show — what the set costs per Bash call, and the matrices that only make sense across guards rather than within one — is measured and kept in `docs/guard-verification.md`, which is also where a change to any guard or to the shared library records its own re-measurement.
