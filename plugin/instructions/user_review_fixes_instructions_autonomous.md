# Autonomous user-review fix loop

Autonomous variant. Run `${CLAUDE_PLUGIN_ROOT}/instructions/user_review_fixes_instructions_core.md` Phases **A → QA → D** verbatim by reference, with the bindings below and the overrides that follow them. Do not restate the phase bodies — the Setup, the Safety contract, the Phase A fix-item loop, the Phase QA augment + E.0–E.4 loop, Phase D's statistics + Done summary, the stop-condition list and the "What you must NOT do" list are canonical there; the unit loop with its substitution row `UR-A`, its named exceptions and its gated per-unit review step is canonical in `${CLAUDE_PLUGIN_ROOT}/instructions/unit_loop_core.md`, and the QA loop itself in `${CLAUDE_PLUGIN_ROOT}/instructions/plan_orchestration_instructions_core.md` → `## Phase E — QA testing` — both cited by the core, not by this fork.

**This fork differs from the core only in the binding values below and the overrides after them.** Three former overrides are now binding *values*: path resolution (`<repo_root>` / `<app_root>`, with the residue those two values do **not** carry kept as **Override A**), the clarification reroute (`<escalate>` / `<ask>`), and the committer half of Override E (`<committer_push>`). What stays an override is what this mode purely **adds** and the core has no surface for: the worktree-relative reads the two path bindings leave uncovered (A), the global kill switch (B), the post-user-review statistics commit (D) and its direct-`git` push (E), the pause/resume + flow-progress ledger (G), the docs phase (H), the improvement-observations intake (I), and the hard boundary. **This fork has no Override F** — this flow never dropped the per-unit layer reviewers, so `<per_unit_review>` is bound **`on`** explicitly in the table below; do not infer a value from the absence of that override. Everything else — the per-item implement→review→commit loop, the per-run `<state_dir>/STOP` check, `<state_dir>/.dispatch_counter`, `MAX_TOTAL_DISPATCHES`, the heartbeat formats, the per-test QA fan-out, Phase D — is identical and is NOT duplicated here. (The per-run safety scaffolding is kept as-is: it is already per-worktree.)

### `<escalate>` / `<ask>` — the park-and-yield clarification reroute

Both bindings resolve to the **same** file-based channel and differ only in what triggers them. Together they cover a **closed list** of the core's — and its cited sections' — "a supervised flow would stop and surface here" paths, and nothing else: an implementer reporting `blocker:` or `error:`, a review loop hitting `iteration >= 5` without PASS, a `committer` returning `error:`, a file path you expected to exist being missing, the `ui-tests-plan-writer` surfacing `## Questions` in QA.0 (that one is `<ask>`; the rest are `<escalate>`), the QA dev server failing to start (E.0), a `qa-tester` returning `error:`, the `MAX_QA_ROUNDS = 3` re-test cap, a `MAX_TOTAL_DISPATCHES` hit, and — reachable only in this fork, which is the one that keeps a flow-progress ledger — the Phase-D completion check failing, on a round entry still `[ ]` or on a recorded-vs-live `phases:` disagreement (`## Override G` below; the core's `## Stop conditions` entry for it) — **the one path in this list that does not first apply the ask-vs-assume policy: it is unconditional, and has no assume-and-proceed arm.**

Every one of those paths — **except** that completion check — **first applies the ask-vs-assume policy** owned by `${CLAUDE_PLUGIN_ROOT}/instructions/task_plan_writing_instructions_autonomous.md` → `## Ask-vs-assume policy` (referenced, not restated). When that policy says *ask*, behavior splits by the **entry point** (see the calling command for the two entry points):

- **Headless / watcher entry point:** write the blocker as one or more self-contained `<state_dir>/clarifications/<branch>/question_<n>.md` files (inside this worktree's own `<state_dir>/`; the `clarifications/` directory **is** part of the run-artifact tree `init` materializes and carries its own committed `README.md`; the question and answer files inside it are machine-local and created on first write), each naming the phase (`A` / `QA` / `D`), the item or finding it arose on, the latest findings-file path where applicable, and the concrete decision needed. Emit a one-line `PARKED: <branch> — N question(s) at <state_dir>/clarifications/<branch>/` to the run log, **tear down the Phase QA dev server if it is running**, then **truly stop and yield — end the session.** Do NOT spin, poll, sleep-loop, or re-dispatch waiting for an answer — ending the session is what makes the park dispatch-free. For the question/answer file format and the archive-on-resume mechanism, see the canonical **`${CLAUDE_PLUGIN_ROOT}/instructions/task_plan_writing_instructions_autonomous.md` → `## Clarification channel — file format`** — it is not restated here.
- **Manual / interactive entry point:** surface the blocker — or the questions — live and stop, exactly as a supervised flow does (unchanged). No files are written.

**On resume**, the engine re-enters via the fused command (`<reentry_command>`); Phase A and Phase QA resume naturally from their readiness checkboxes (the fix-plan index's `[ ]` entries and the UI-test index's `[ ]` entries). If a top-level `answer_<n>.md` exists whose paired `question_<n>.md` **this fork raised** (it names a Phase `A`/`QA`/`D` origin — the fix-plan fork's Override 2(a) leaves such answers unconsumed), read the question + answer pair and **append both to the next dispatch prompt for the blocked item/phase** (the implementer fix-iteration prompt, or the QA re-dispatch) before continuing from the readiness checkboxes. The pair stays at the top level for the watcher to archive after exit, per the consume-then-archive contract (canonical in the clarification-channel section above; referenced, not restated). Wherever a halt message names a command to re-run, it is `<reentry_command>` above — the fused command — never a supervised one.

**Neither binding reaches a STOP-file halt.** The core's `<state_dir>/STOP` sites — `## Setup (once per session)` step 4, `## Safety contract — applies before EVERY Agent dispatch` step 1 and `## Stop conditions (halt and do NOT continue)` entry 1 — and the global `<MAIN_REPO>/<state_dir>/AUTONOMOUS_STOP` check in `## Override B` below are plain reports naming `<reentry_command>`, and they stay that way: routing an operator's brake through the park would turn it into a spurious park the watcher would then try to resume (see Override B's closing sentence). The `MAX_TOTAL_DISPATCHES` hit in the list above, by contrast, **is** in scope — this family's cap halt is an escalation and the core routes it through `<escalate>`.

### `<committer_push>` — `push: true` on every committer dispatch

**Every** `committer` dispatch this fork makes by reference into the core's phases — and into the unit loop's commit step — carries the **additional arg line `push: true`**, so the committer pushes the branch after its commit lands (per the committer's `push:` contract, `committer.md`). This applies to **every** committer dispatch class this fork drives, with no exception: the Phase A `mode: review_item` per-finding fix commits, and Phase QA's `mode: ui_test_pass` per-test mark-pass commits and `mode: review_item` QA-fix commits.

The push is best-effort by the committer's own contract: it runs only after a commit has actually landed, and a push failure is reported (`pushed: failed`) without undoing the commit. The committer's no-commit paths (`error: nothing to commit`, the `ui_test_pass` already-`[x]` `noop:`) make no commit and therefore no push regardless of the arg — so passing `push: true` unconditionally on every dispatch is safe.

## Override A — worktree-relative reads

`<repo_root>` and `<app_root>` above rebase every `<app_dir>`-rooted and credentials path the core names — and, when `phases.parity` is `true`, every `<reference_impl>`-rooted one — including the QA.1+ `test_credentials` source, which resolves to this worktree's own `$REPO_ROOT/<qa_creds_path>` with no restatement here. Four facts those two bindings do **not** carry:

- **Never start the Phase QA dev server with a raw package-manager or dev-server-binary command.** The **Phase QA dev server** is started via the configured `commands.devServer` string with `<qa_port>` appended (the pinned start script under `<scripts_dir>` that string names encapsulates the raw dev-server command line, with the fail-loudly-on-a-taken-port behaviour enforced inside it), with `<qa_port>` assigned by E.0's `find-free-port.sh` probe and the readiness poll run via `poll-dev-server.sh` — both invoked through the **resolved** plugin-root path E.0's **Resolve the plugin root before you issue any command in this phase.** paragraph prescribes, never through the literal `${CLAUDE_PLUGIN_ROOT}` token, which matches no allow entry however that entry is worded. Do NOT start it with a raw package-manager invocation into `<app_root>` (nor with an absolute path to the dev server's own binary inside the installed dependencies) — those are permission-gated in worktree headless runs and silently skip the start; always go through the configured `commands.devServer` string.
- **Reference-implementation source reads are this worktree's own.** *Applies only when `phases.parity` is `true` in `harness.config.json`.* The `<parity_vocabulary>` source reads that the per-unit `layer-implementer` and `layer-reviewer` perform — dispatched by the unit loop inside Phase A (row `UR-A`) and inside Phase QA's E.3 fix loop (row `E.3`) — must read **this worktree's own** copy of `<reference_impl>` — resolved under `$REPO_ROOT` whenever that path is repo-relative — not the main repo's. Each worktree is a full checkout of the branch under review. (This is the case `## Resolved values` flags: `<reference_impl>` commonly resolves to `<repo_root>` itself, which is exactly what makes "this worktree's own source" the right reading.)
- **The QA credentials file is the qa-tester's to read.** The qa-tester reads that file itself — the orchestrator never reads or passes credentials. How it resolves the path and its absent/empty behaviour are the qa-tester's own contract (`qa-tester.md`), not an orchestrator override. (The path itself is `<repo_root>`-anchored and carried by that binding, above.)
- **`<state_dir>/` is already per-worktree.** All `<state_dir>/…` paths already live **inside** the worktree — the fix-plan index, the per-finding files, `<state_dir>/STOP`, `<state_dir>/.dispatch_counter`, the point-review roots, the QA reviews, and the branch statistics are already per-worktree with **no path change** — leave every `<state_dir>/…` reference exactly as the core writes it. `<fix_plan_path>` and `<fix_finding_dir>` arrive from the calling command already resolved under `$REPO_ROOT` — use them verbatim, exactly as the core's Setup says.

## Override B — global kill switch

In addition to the per-run `<state_dir>/STOP` check (which is per-worktree and stays unchanged), honor a **global** kill switch that stops every run and prevents new launches:

- **Path:** `<MAIN_REPO>/<state_dir>/AUTONOMOUS_STOP` — a single file in the **main** repo, distinct from each worktree's per-run `<state_dir>/STOP`. `<MAIN_REPO>` is the main worktree's root; resolve it from the watcher-supplied environment, or as the first entry of `git worktree list` (since `$REPO_ROOT` inside a run points at the run's own worktree, not the main repo).
- **Check it at session start** (alongside the per-run STOP soft-fail): if `<MAIN_REPO>/<state_dir>/AUTONOMOUS_STOP` exists, halt before dispatching anything and report it. Do NOT delete it — the user controls it.
- **The watcher honors it before every launch and during resume** — that watcher-side enforcement belongs to `<scripts_dir>/autonomous-watcher.sh`, not to this file. This file only states the engine's session-start check and that the file is the global switch.

The per-run `<state_dir>/STOP`, `.dispatch_counter`, `MAX_TOTAL_DISPATCHES`, and heartbeat from the core's safety contract are unchanged — they are per-worktree and already correct. A STOP-file halt (per-run or global) is a user-initiated stop, not a blocker — it halts as written and is **never** routed through `<escalate>`.

## Hard boundary — no auto-merge / push / PR (load-bearing, restated intentionally)

The autonomous flow ends at **Phase D "branch ready for review"** and must **never**:

- merge to a branch in `<protected_branches>`,
- push to a branch in `<protected_branches>`, or
- open or push a pull request.

Two layers enforce it at the harness level — the `pre-push` git hook, and above it the plugin's `PreToolUse` protected-branch guard together with the generated permission profile's `Bash(git push:*)` **`ask`** entry, which is evaluated before any `allow` and which an unattended run cannot answer — and this instruction restates the intent so the orchestrator never *attempts* it. Phase D stops after the Done summary exactly as the core's Phase D does ("Do not push, do not open a PR") — there is no autonomous extension past that point.

## Per-run statistics / Done summary

Phase D's `statistics-plan-writer` dispatch and the Done summary remain **purely per-worktree**, unchanged from the core's Phase D — each run writes (here: **updates**) `<state_dir>/branch_statistics/<branch>/statistics.md` inside its own worktree. ### Override D — commit the post-user-review statistics file in Phase D (autonomous fork only)

**Autonomous fork only.** The core's Phase D leaves `statistics.md` uncommitted between D.1 and D.2, and the semi-autonomous fork over it deliberately keeps it that way for the human review/merge step — it does **not** commit it (the supervised `user_review_fixes_instructions.md` delegates its orchestration to the supervised item loop `plan_orchestration_instructions.md`, not to this core, and has no Phase D). Only the autonomous flow self-commits it, so a watcher-driven run ends with a clean `git status`. Do **not** propagate this step into the core; its Phase D (D.1 / D.2) is untouched. This is the user-review-fix analogue of the task flow's `Override D` (`${CLAUDE_PLUGIN_ROOT}/instructions/plan_orchestration_instructions_autonomous.md`).

**Why a commit is needed here.** Phase D's D.1 dispatches `statistics-plan-writer` to **update** `<state_dir>/branch_statistics/<branch>/statistics.md`, but neither Phase D nor any other step commits it, so at "branch ready for review" the updated file dangles in the worktree and is lost at PR time. This override commits that file once, after the writer returns and before the Done summary.

**Trigger / ordering.** Fires **after** the D.1 `statistics-plan-writer` dispatch returns its contract (`statistics_file:` / `success_rate:` / `status:` …) and **before** the D.2 Done summary. Run it once, at that single point.

**`error:` gate (skip on failed write).** If D.1 returned `error:` (e.g. the story index is missing — the path the existing Phase D already handles by skipping the statistics summary bullet and not inventing numbers), **skip this commit entirely**: do not commit a missing/partial file, do not create an empty commit, do not error.

**Commit mechanism (direct `git` in the fork, not a committer dispatch).** Commit directly here, exactly as the task flow's Override D does — not via a `committer` agent dispatch. The existing `committer` modes do not fit a single-file report with no `## Phase 2 Readiness` checkbox to flip, and adding a new mode would collide with other `committer.md` edits. Committing the as-written statistics file is a workflow-document operation, so the fork performs it directly.

**Exact staging + commit.** Stage and commit through the `<scripts_dir>/commit-on-branch.sh` wrapper — never a direct `git add` / `git commit` here, because a `git commit` carrying a `${branch}` expansion is what stalls a headless run on the `Bash(git commit:*)` branch-guard; the `bash <scripts_dir>/commit-on-branch.sh …` invocation is auto-allowed and never matches that guard even with the expansion in its args. That allow is withheld, though, when **anything in the command** — subject included — carries `$(…)`, a backtick, `|` (hence `||`), `>`, `<` (hence a subject naming a `<placeholder>`) or a braced expansion other than a bare `${IDENT}`; the guard scans the whole string. Pass **only** the statistics file as the single explicit path the wrapper stages (the `statistics_file:` the writer reports, canonically `<state_dir>/branch_statistics/<branch>/statistics.md`) — the wrapper stages only that path with `git add -- <path>` and never `git add -A` / `git add .`. Keep the fixed subject `chore: Update branch statistics for <branch>` verbatim:

```zsh
bash <scripts_dir>/commit-on-branch.sh --repo "$REPO_ROOT" \
  "<state_dir>/branch_statistics/${branch}/statistics.md" \
  -- "chore: Update branch statistics for ${branch}"
```

using the `$REPO_ROOT` resolved once at session start from `<repo_root>` — the wrapper path is repo-relative and takes no app-root prefix. No `Co-Authored-By:` / trailer and no `--no-verify` / hook-skip flag — the wrapper enforces both: it builds the message from the positional args after `--` only (subject only here) and never passes `--no-verify`. (The task flow's Override D uses `chore: Add branch statistics for <branch>` for the **first** write; this Phase D **updates** an existing file, so the fixed subject `chore: Update branch statistics for <branch>` reads more truthfully.) Do not bypass a hook with a hook-skip flag and do not create a partial commit.

**Wrapper exit status (surface the error).** The wrapper returns a loud non-zero on any non-commit outcome — surface it rather than retrying or bypassing. The codes are: **exit 0** (committed), **exit 1** (non-git dir / detached HEAD / hook failure — surface the error), **exit 2** (protected-branch refusal — surface the error), **exit 3** (nothing to commit). Exit 3 is normally unreachable here because Phase D's writer freshly **updates** `statistics.md`, but it is now reachable on a resumed run that re-writes the file identically while it is already tracked — when it fires, the file is already committed, so there is nothing to commit. The Override E push that follows is **not** gated on these codes (see Override E) — an unconditional push is a harmless no-op whenever no commit landed.

**Interaction with the hard boundary.** This commit is local to the worktree and changes nothing about Phase D's terminal state: the flow still ends at "branch ready for review," never merges, never pushes to a branch in `<protected_branches>`, and never opens a PR (see the **Hard boundary** section above). It lands **before** the Done summary and does not extend the flow past Phase D. The Override E push that follows this commit (below) reaches **only** the non-protected worktree branch and likewise does not change Phase D's terminal state or the protected-branch hard boundary — it is a local→remote sync of an already-landed commit, not an extension past Phase D.

**Shared rationale.** This commit is one of the autonomous-fork commit points that collectively keep the clean-tree precondition honest — see **Autonomous-fork commit points — the clean-tree invariant** in `${CLAUDE_PLUGIN_ROOT}/instructions/plan_orchestration_instructions_autonomous.md`.

### Override E — push after the Override D direct-`git` commit (autonomous user-review-fix fork only)

**Autonomous user-review-fix fork only.** This fork's push delta is: **every commit it lands is followed by a push of the worktree branch to its upstream.** For every commit that goes through a `committer` dispatch, `<committer_push>` = `push: true` above already discharges that. Override D commits the post-user-review statistics file with direct `git` (not via a committer dispatch), so its push cannot ride on a `push:` arg. It is the user-review-fix analogue of the task flow's Override E (`${CLAUDE_PLUGIN_ROOT}/instructions/plan_orchestration_instructions_autonomous.md`).

```zsh
bash <scripts_dir>/push-branch.sh "$REPO_ROOT"
```

> ⚠️ **No exit-code gate — deliberate and load-bearing.** Do **not** wrap the push in `if [ "$?" -eq 0 ]; then … fi` (or any `if …; then … fi` / `for …; do … done` block). Per `${CLAUDE_PLUGIN_ROOT}/instructions/autonomous_pause_and_ledger.md` §1.6 that control-flow block is a headless trap: `allow-safe-compounds.sh` splits on `;` and the ` then bash …` piece begins with a non-allow-listed prefix, so the command falls through the safe-compound allow, nothing else matches it, and the run **stalls on a permission prompt it cannot answer headlessly** — **the commit silently does not land.** `$?` is unreliable across Bash calls anyway: each runs in a fresh shell, so a gate issued as a separate call inspects the new shell's status, not the wrapper's. No gate is needed — `push-branch.sh` is non-fatal and only fast-forwards already-committed work, so an unconditional push is a harmless no-op ("Everything up-to-date") whenever the wrapper made no new commit.

using the `$REPO_ROOT` resolved once at session start from `<repo_root>`. The unconditional push is a harmless no-op in every non-commit case: when Override D **skipped** its commit (the `error:` write path — D.1 returned `error:`, nothing was committed), when the wrapper **refused** (exit 2, protected branch) or **failed** (exit 1, hook failure), and when the wrapper returned its **nothing-to-commit status** (exit 3 — `statistics.md` already tracked and re-written identically on a resumed run). The helper is best-effort (it exits 0 and logs on any failure — non-git dir, detached HEAD, protected branch, transient push failure), so a push problem is visible but never blocks the D.2 Done summary and never extends the flow past Phase D.

**Shared rationale.** This push is the post-commit half of the autonomous-fork commit points that collectively keep the clean-tree precondition honest, and reaches only the run's own non-protected worktree branch (the protected-branch hard boundary above is unchanged) — see **Autonomous-fork commit points — the clean-tree invariant** in `${CLAUDE_PLUGIN_ROOT}/instructions/plan_orchestration_instructions_autonomous.md`.
