# Autonomous orchestrator loop

Autonomous variant. Run `${CLAUDE_PLUGIN_ROOT}/instructions/plan_orchestration_instructions_core.md` Phases **A → A1.5 → A2 → B → C → C2 → E → D** verbatim by reference, with the bindings below and the overrides that follow them. Do not restate the phase bodies — Setup, the Safety contract, every phase, the stop conditions and the "What you must NOT do" list are canonical there, and the unit loop with its substitution table, named exceptions and gated per-unit review step is canonical in `${CLAUDE_PLUGIN_ROOT}/instructions/unit_loop_core.md`, which the core cites.

**This fork differs from the core only in the binding values below and the overrides after them.** Four former overrides are now binding *values* — path resolution (`<repo_root>` / `<app_root>`, with the residue those two values do **not** carry kept as **Override A**), the clarification reroute (`<escalate>`), the per-unit layer reviewers (`<per_unit_review>` = `off`) and the committer push (`<committer_push>`); the approval gate it once removed is already gone. What stays an override is what this mode purely **adds** and the core has no surface for: the worktree-relative reads the two path bindings leave uncovered (A), the global kill switch (B), the branch-statistics commit (D) and its direct-`git` push (E), the pause/resume + flow-progress ledger (G), the docs phase (H), the improvement-observations intake (I), the hard boundary and the clean-tree invariant. Everything else — the per-task implement → commit loop, the per-run `<state_dir>/STOP` check, `.dispatch_counter`, `MAX_TOTAL_DISPATCHES`, the heartbeat formats, the QA fan-out, Phase D's statistics + Done summary — is identical and is NOT duplicated here.

## Resolved values

**Three vocabularies of `<…>` name appear in this file, and they resolve from three different places.** Mode-contract **bindings** (`## Mode contract — bindings`, immediately below) are the values *this fork supplies* to the core. Ordinary **path placeholders** (`<branch>`, `<code_review_path>`, `<parity_review_path>`, …) resolve from the core's `## Setup`, which this fork does not restate. The tokens in the table below are neither: they resolve from the runtime or from the adopting repository's `harness.config.json`, are declared here once, and after this table the body uses each one as an ordinary placeholder. (The counters and ids `<n>` / `<i>` / `<N>` / `<phase>`, and the `<path>` inside a quoted wrapper behaviour, are none of the three: each is bound where it is written.)

| Token | Class | How to resolve it |
|---|---|---|
| `<repo_root>` | derived at runtime | The absolute root of the checkout this run is executing in. Obtain it with a **bare** `git rev-parse --show-toplevel` and build every literal path from the result. Never embed the `$(…)` substitution inside another shell command, and never stash it in a shell variable across separate Bash calls — separate calls do not share shell state. |
| `<state_dir>` | config value | `stateDir` — the run-artifact tree every artifact path in this file is relative to. Default `sdlc-harness/`. It is never dot-named: no path segment of it may begin with a dot. |
| `<app_dir>` | config value | `appDir` — the app's directory inside the checkout, repo-relative. The **binding** `<app_root>` below is built from it (`<repo_root>/<app_dir>`) and is deliberately a different name: this row is the configured directory, that one is the resolved root. |
| `<scripts_dir>` | config value | `scriptsDir` — the directory the wrapper scripts this file invokes by path live in. The commit / push / watcher scripts named by path here are outer-loop scripts rather than generated wrappers — they are named by their destination path, and the item that delivers them settles it. The two guard hooks this file names (`allow-safe-compounds.sh`, `git-commit-branch-guard.sh`) ship as plugin hooks and are **not** under it: they are named bare and take no prefix. |
| `<test_cmd>` / `<typecheck_cmd>` | config value | `commands.test` / `commands.typecheck`. Each **normally** holds the repo-relative wrapper invocation — `bash` followed by that wrapper's path under `<scripts_dir>`. **Run the configured string as-is**: never rebuild it from its parts, and never write an absolute path in its place. If that call is **refused**, the key holds a raw command line rather than the wrapper invocation — run `bash <scripts_dir>/<name>.sh`, whose body is the line `init` inlined into it — not necessarily the configured string, if the key was edited after that wrapper was written — and report in your return which string you ran. | `<worktree_glob>` | derived at runtime | The **parent directory of `<repo_root>`** joined to `<project_name>` and a `-*` suffix — the sibling-worktree pattern this fork's per-branch worktrees match, and the pattern the generated permission profile is materialized with. |

| `<protected_branches>` | config value | `protectedBranches` — the branches the commit wrapper and the `git-commit-branch-guard.sh` hook refuse to commit or push to, and the branches the hard boundary below forbids merging into. The effective set is these together with `<default_branch>`. |

### `<escalate>` — the clarification reroute

When an agent is genuinely blocked (a supervised flow would surface the blocker and stop), first apply the **ask-vs-assume policy** owned by the planning fork (`${CLAUDE_PLUGIN_ROOT}/instructions/task_plan_writing_instructions_autonomous.md` → `## Ask-vs-assume policy`) — the criteria for assume-and-proceed vs park-and-ask, and the requirement to record every assumption in the plan and Done summary, live there and are **not** restated here — with one exception, the Phase-D completion check of canonical-doc `### 1.8` (`## Override G` below), which is unconditional and escalates without consulting the policy. When that policy says *ask*, the behavior depends on the **entry point** (see the command for the two entry points):

- **Headless / watcher entry point:** write **every** blocker of this park into **one** self-contained `<state_dir>/clarifications/<branch>/question_<n>.md` in the canonical format (inside this worktree's own `<state_dir>/`; the `clarifications/` directory **is** part of the run-artifact tree `init` materializes and carries its own committed `README.md`; the question and answer files inside it are machine-local and created on first write), emit a one-line `PARKED: <branch> — N question(s) at <state_dir>/clarifications/<branch>/` to the run log, then **truly stop and yield — end the session.** Do NOT spin, poll, sleep-loop, or re-dispatch. **Ending the session is what makes the park free of dispatch cost** — a polling run would burn dispatches against `MAX_TOTAL_DISPATCHES` while idle. The watcher detects this exit + the unanswered `question_<n>.md`, marks the run `parked`, and resumes it (re-launching this same engine command in the same worktree) once the park's question file is answered; the answer is fed back via the planner's resumability branch (`task_plan_writing_instructions_autonomous.md` → Override 2(a)). For the question/answer file format and the archive-on-resume mechanism, see the **clarification channel — single source of truth in `task_plan_writing_instructions_autonomous.md` → `## Clarification channel — file format`** — it is not restated here.
- **Manual / interactive entry point:** questions surface **live** to the user for inline answering, exactly as a supervised flow does (unchanged). No files are written.

The entry point determines which behavior applies; both are valid for this one engine.

### `<committer_push>` — `push: true` on every committer dispatch

**Every** `committer` dispatch this orchestrator makes by reference into the core's phases — and into the unit loop's step-5 commit — carries the **additional arg line `push: true`**, so the committer pushes the branch after its commit lands (per the committer's `push:` contract, `committer.md`). This applies to **every** committer dispatch class the autonomous task fork drives, with no exception:

- the **`mode: task`** Phase-A per-task commit dispatch;
- **every** `mode: review_plan_file` dispatch (the parity-review index in Phase A1.5, the architecture-review index in Phase A2, the code-review index in Phase B, the skeptic-review index in Phase C2, and the merged QA-review index in Phase E);
- **every** `mode: review_item` dispatch (each per-finding fix commit in Phases A1.5 / A2 / C / C2 and each QA-fix commit in Phase E);
- **every** `mode: ui_test_pass` dispatch (each per-test mark-pass commit in Phase E).

The push is best-effort by the committer's own contract: it runs only after a commit has actually landed, and a push failure is reported (`pushed: failed`) without undoing the commit. The committer's no-commit paths (`error: nothing to commit`, the `ui_test_pass` already-`[x]` `noop:`) make no commit and therefore no push regardless of the arg — so passing `push: true` unconditionally on every dispatch is safe.

## Override A — worktree-relative reads

`<repo_root>` and `<app_root>` above rebase every `<app_dir>`-rooted path the core names — and, when `phases.parity` is `true`, every `<reference_impl>`-rooted one. Three facts those two bindings do **not** carry:

- **The QA-user reservation is the qa-tester's, and its locks are machine-global.** The reserve/release scripts (`${CLAUDE_PLUGIN_ROOT}/scripts/reserve-qa-user.sh` / `${CLAUDE_PLUGIN_ROOT}/scripts/release-qa-user.sh`, Phase E.1) are invoked **by the qa-tester itself**, not by the orchestrator — the orchestrator neither reserves a user nor reads creds (`qa-tester.md`, "Which user"). The reserve script reads this worktree's own `$REPO_ROOT/<qa_creds_path>` (the worktree's link to the main checkout's copy) to enumerate user slots, but the **locks it writes live in a fixed machine-global `/tmp` dir** — NOT under the worktree — precisely so parallel autonomous runs in **different** worktrees share one lock set and never park the same QA account.
- **Reference-implementation source reads are this worktree's own.** *Applies only when `phases.parity` is `true` in `harness.config.json`.* The `<parity_vocabulary>` source reads that the parity reviewer (Phase A1.5) and the architecture reviewer (Phase A2) perform must read **this worktree's own** copy of `<reference_impl>` — resolved under `$REPO_ROOT` whenever that path is repo-relative — not the main repo's. Each worktree is a full checkout of the branch under review. (This is the case `## Resolved values` flags: `<reference_impl>` commonly resolves to `<repo_root>` itself, which is exactly what makes "this worktree's own source" the right reading.)
- **`<state_dir>/` is already per-worktree.** The per-run `<state_dir>/STOP`, `<state_dir>/.dispatch_counter`, the story index, the per-task files, all the review indices/findings, the QA reviews, and the branch statistics already live **inside** each worktree with **no path change** — leave every `<state_dir>/…` reference exactly as the core writes it. Only the `<app_dir>`-rooted and `<reference_impl>`-rooted reads are rebased onto `$REPO_ROOT` / `$APP_ROOT`.

## Override B — global kill switch

In addition to the per-run `<state_dir>/STOP` check (which is per-worktree and stays unchanged), honor a **global** kill switch that stops every run and prevents new launches:

- **Path:** `<MAIN_REPO>/<state_dir>/AUTONOMOUS_STOP` — a single file in the **main** repo (the checkout the watcher launches from), distinct from each worktree's per-run `<state_dir>/STOP`. `<MAIN_REPO>` is the main worktree's root; the engine resolves it from the watcher-supplied environment (or `git worktree list` — the main worktree is the first entry) since `$REPO_ROOT` inside a run points at the run's own worktree, not the main repo.
- **Engine command checks it at session start** (alongside the per-run STOP soft-fail): if `<MAIN_REPO>/<state_dir>/AUTONOMOUS_STOP` exists, halt before dispatching anything and report it. Do NOT delete it — the user controls it.
- **The watcher honors it before every launch and during resume** — that watcher-side enforcement belongs to `<scripts_dir>/autonomous-watcher.sh`, not to this file. This file only states the engine's session-start check and that the file is the global switch.

The per-run `<state_dir>/STOP`, `.dispatch_counter`, `MAX_TOTAL_DISPATCHES`, and heartbeat from the core's safety contract are unchanged — they are per-worktree and already correct.

## Hard boundary — no auto-merge / push / PR (load-bearing, restated intentionally)

The autonomous flow ends at **Phase D "branch ready for review"** and must **never**:

- merge to a branch in `<protected_branches>`,
- push to a branch in `<protected_branches>`, or
- open or push a pull request.

This is the binding architectural constraint of the whole flow. Two layers enforce it at the harness level — the `pre-push` git hook, and above it the plugin's `PreToolUse` protected-branch guard together with the generated permission profile's `Bash(git push:*)` **`ask`** entry, which is evaluated before any `allow` and which an unattended run cannot answer — and this instruction restates the intent so the orchestrator never *attempts* it. Phase D stops after the Done summary exactly as the core's Phase D does ("Do not push, do not open a PR") — there is no autonomous extension past that point.

## Per-run statistics / Done summary across parallel runs

Phase D's `statistics-plan-writer` dispatch and the Done summary remain **purely per-worktree**. Each run writes `<state_dir>/branch_statistics/<branch>/statistics.md` **inside its own worktree** — exactly as the core's Phase D does, with no change. There is **no** cross-run roll-up across parallel worktrees: that is a deliberate choice, not an omission — a roll-up is new machinery this flow does not add.

### Override D — commit the branch-statistics file after the writer returns (autonomous fork only)

**Autonomous fork only.** The core's Phase D leaves `statistics.md` uncommitted between D.1 and D.2, and the semi-autonomous fork over it deliberately keeps it that way for the human review/merge step (the supervised `plan_orchestration_instructions.md` is a standalone item loop with no Phase D, not a fork over this core). Only the autonomous flow self-commits it, so a watcher-driven run ends with a clean `git status` in the worktree. Do **not** propagate this step into the core; its Phase D (D.1 / D.2) is untouched.

**Why a commit is needed here.** D.1 dispatches `statistics-plan-writer` to write `<state_dir>/branch_statistics/<branch>/statistics.md` (the **first**, pre-user-review statistics file, per D.1's own wording), but Phase D never commits it. So at "branch ready for review" the file dangles untracked in the worktree and is lost at PR time. This override commits that first file once, after the writer returns and before the Done summary.

**Trigger / ordering.** The commit fires **after** the D.1 `statistics-plan-writer` dispatch returns its contract (`statistics_file:` / `success_rate:` / `status:` …) and **before** the D.2 Done summary. Run it once, at that single point.

**`error:` gate (skip on failed write).** If D.1 returned `error:` (e.g., the story index is missing) — the path the existing Phase D already handles by skipping the statistics summary bullet and not inventing numbers — **skip this commit entirely**: do not commit a missing/partial file, do not create an empty commit, do not error. The skip is consistent with the existing "omit the statistics summary bullet" behavior.

**Commit mechanism (direct `git` in the fork, not a committer dispatch).** Commit directly here, exactly as the planning fork's UI-test-plan commit and the watcher's prompt commit do — not via a `committer` agent dispatch. The existing `committer` modes do not fit: `review_plan_file` is locked to a different fixed subject (`chore: add code review for <branch>`); `task` / `review_item` / `ui_test_pass` each flip a `## Phase 2 Readiness` checkbox, but `statistics.md` is a single-file report with **no** `## Phase 2 Readiness` section (nothing to flip). Adding a new `committer` mode here would change the committer's contract, which this fork does not own. Committing the as-written statistics file is a workflow-document operation, so the fork performs it directly.

**Exact staging + commit.** Stage and commit through the `<scripts_dir>/commit-on-branch.sh` wrapper — never a direct `git add` / `git commit` here, because a `git commit` carrying a `${branch}` expansion is what stalls a headless run on the `Bash(git commit:*)` branch-guard; the `bash <scripts_dir>/commit-on-branch.sh …` invocation is auto-allowed and never matches that guard even with the expansion in its args. That allow is withheld, though, when **anything in the command** — subject included — carries `$(…)`, a backtick, `|` (hence `||`), `>`, `<` (hence a subject naming a `<placeholder>`) or a braced expansion other than a bare `${IDENT}`; the guard scans the whole string. Pass **only** the statistics file as the single explicit path the wrapper stages (the writer's reported `statistics_file:`, canonically `<state_dir>/branch_statistics/<branch>/statistics.md`) — the wrapper stages only that path with `git add -- <path>` and never `git add -A` / `git add .` (matches the committer's no-blanket-add rule). Keep the fixed subject `chore: Add branch statistics for <branch>` verbatim:

```zsh
bash <scripts_dir>/commit-on-branch.sh --repo "$REPO_ROOT" \
  "<state_dir>/branch_statistics/${branch}/statistics.md" \
  -- "chore: Add branch statistics for ${branch}"
```

using the `$REPO_ROOT` resolved once at session start from `<repo_root>`. No `Co-Authored-By:` / trailer and no `--no-verify` / hook-skip flag — the wrapper enforces both: it builds the message from the positional args after `--` only (subject only here) and never passes `--no-verify`. Do not bypass a hook with a hook-skip flag and do not create a partial commit.

**Wrapper exit status (surface the error).** The wrapper returns a loud non-zero on any non-commit outcome — surface it rather than retrying or bypassing. The codes are: **exit 0** (committed), **exit 1** (non-git dir / detached HEAD / hook failure — surface the error), **exit 2** (protected-branch refusal — surface the error), **exit 3** (nothing to commit). Exit 3 is normally unreachable here because `statistics.md` is a fresh write, but it is now reachable on a resumed run that re-writes the file identically while it is already tracked — when it fires, the file is already committed, so there is nothing to commit. The Override E push that follows is **not** gated on these codes (see Override E) — an unconditional push is a harmless no-op whenever no commit landed.

**Interaction with the hard boundary.** This commit is local to the worktree and changes nothing about Phase D's terminal state: the flow still ends at "branch ready for review," still never merges, never pushes to a protected branch, and never opens a PR (see the **Hard boundary** section above). The new commit lands **before** the Done summary and does not extend the flow past Phase D. It is **not** the last commit of Phase D — Override I's improvement-observations commit and Override G's terminal `D` flip both follow it, still inside Phase D; the run order for all of them is in **Autonomous-fork commit points — the clean-tree invariant** below. The Override E push that follows this commit (below) reaches **only** the non-protected worktree branch and likewise does not change Phase D's terminal state or the protected-branch hard boundary — it is a local→remote sync of an already-landed commit, not an extension past Phase D.

This override is one of the autonomous-fork commit points that collectively keep the clean-tree precondition honest — see **Autonomous-fork commit points — the clean-tree invariant** below.

### Override E — push after the Override D direct-`git` commit (autonomous task fork only)

**Autonomous task fork only.** This fork's push delta is: **every commit it lands is followed by a push of the worktree branch to its upstream.** For every commit that goes through a `committer` dispatch, `<committer_push>` = `push: true` above already discharges that. Override D commits the first branch-statistics file with direct `git` (not via a committer dispatch), so its push cannot ride on a `push:` arg. Issue the push as a **plain, single-statement Bash command immediately after** the Override D commit command, using the `$REPO_ROOT` resolved once at session start:

```zsh
bash <scripts_dir>/push-branch.sh "$REPO_ROOT"
```

> ⚠️ **No exit-code gate — this is deliberate and load-bearing.** Do **not** wrap the push in `if [ "$?" -eq 0 ]; then … fi` (or any `if …; then … fi` / `for …; do … done` block). Per the canonical rule in `${CLAUDE_PLUGIN_ROOT}/instructions/autonomous_pause_and_ledger.md` §1.6, such a control-flow block is a **headless trap**: `allow-safe-compounds.sh` splits on `;` and the ` then bash …` piece begins with a non-allow-listed prefix, so the command falls through the safe-compound allow, nothing else matches it, and the run **stalls on a permission prompt it cannot answer headlessly** — the commit is silently **NOT** made. A `$?` test is also unreliable here for a second, independent reason: each Bash tool call runs in a **fresh shell**, so a gate issued as a separate call from the command it gates inspects the new shell's status, not the wrapper's. **No gate is needed anyway** — `push-branch.sh` is non-fatal and only fast-forwards already-committed work, so an unconditional push is a harmless no-op ("Everything up-to-date") in every non-commit case: when Override D **skipped** its commit (the `error:` write path), when the wrapper **refused** (exit 2, protected branch) or **failed** (exit 1, hook failure), and when it returned its **nothing-to-commit status** (exit 3 — `statistics.md` already tracked and re-written identically on a resumed run). The helper is best-effort (it exits 0 and logs on any failure — non-git dir, detached HEAD, protected branch, transient push failure), so a push problem is visible but never blocks the D.2 Done summary.

This override is one of the autonomous-fork commit points that collectively keep the clean-tree precondition honest — see **Autonomous-fork commit points — the clean-tree invariant** below.

## Override F — per-unit review off

`<per_unit_review>` is bound **`off`** above. That switches off `${CLAUDE_PLUGIN_ROOT}/instructions/unit_loop_core.md` → `### Per-unit review step`, the gated section the unit loop's step 4 enters only on `on`. That file is the step's only owner: nothing of the dispatch block, the verdict parse or the `iteration >= 5` convergence cap is restated — or re-deleted — here.

**Scope (cross-check).** Every per-unit *implement → review → commit* loop this fork drives by reference, i.e. all six unit-loop substitution rows: **`A`** (per task), **`C`** (per code-review item), **`A1.5.3`** (per parity item), **`A2.3`** (per arch item), **`C2.4`** (per skeptic item), and **`E.3`** (per QA-fix item).

**Why.** The per-unit `layer-reviewer` step is structurally redundant here. Every file it reads is read again at end of branch: the `branch-reviewer` reviews the same diff whole, and the finding classes a layer reviewer owns are the ones `business-parity-reviewer` and `architecture-reviewer` are dispatched to find. What it adds that they do not is a second opinion *before* the commit — which in a supervised flow shortens the human's feedback loop, and in an unattended one is spent against the same reviewers that will run anyway. Its cost is not redundant: a per-unit reviewer fires once **per layer per unit per iteration** — roughly doubling Phase-A dispatch count and adding the dominant share of wall-clock latency (each dispatch re-reads every changed file and, when `phases.parity` is `true`, re-cross-checks it against `<parity_vocabulary>`). The autonomous fork therefore drops them and relies on the end-of-branch reviewers (now including the **Phase C2 adversarial skeptic**) plus the browser-QA pass as the safety net. The supervised flow, where a human is watching and the latency is acceptable, keeps them.

**What is NOT changed:**

- **Every end-of-branch reviewer still runs in full** — A1.5 (`business-parity-reviewer`), A2 (`architecture-reviewer`), B (`branch-reviewer` + the B.2 `review-plan-reviewer` meta-review), C2 (`skeptic-reviewer` + the C2.2 meta-review), and the Phase E QA pass, each subject to the phase gate the core already carries for it. Only the *per-unit* layer reviewer **between an implementer and its committer** is dropped; the generate→fix structure of A1.5 / A2 / B+C / C2 / E is otherwise intact (their fix loops just commit the implementer's output directly, without an interposed re-review).
- The implementer self-verifies per its existing contract (it builds / runs tests where it can and reports a blocker otherwise). The per-unit reviewers were **read-only static reviewers, not a build gate**, so dropping them removes static re-review redundancy, not a verification gate.

**Deliberate tradeoffs (stated plainly):**

- A per-unit *fix* is no longer re-checked by a layer reviewer before it is committed. A bad fix is caught downstream by the next end-of-branch pass (B / C2), by the **E.4 QA re-test** (for E.3 QA fixes, which are re-verified by re-running the test), or by human review — the same backstops that already catch everything per-unit review missed.
- The `per_task_findings_root` the orchestrator passes to the `branch-reviewer` in Phase B is now **empty** (Phase A wrote no per-task review files), so the branch-reviewer's Pass-2 reconciliation degrades to a **no-op**. That is correct and expected — not an error.

**Interaction with the clean-tree invariant:** unchanged. Fewer dispatches, identical commit points — the implementer→committer commit per unit still lands (and pushes via `<committer_push>`), so the working tree is still clean at every engine checkpoint.

## Autonomous-fork commit points — the clean-tree invariant (single source of truth)

The autonomous fork adds commit points that exist **nowhere** in the core or in the semi-autonomous fork over it (the supervised `plan_orchestration_instructions.md` is a standalone item loop, not a fork over this core). They are a **set**, and they collectively preserve **one invariant**:

> **The worktree's working tree is clean at every engine checkpoint** — launch, planning convergence, and "branch ready for review." Each autonomous-fork commit point exists to keep that precondition honest. (The engine asserts/relies on a clean tree at session-start launch and tolerates only untracked `<state_dir>/…` artifacts; these commits ensure the durable artifacts each phase produces are tracked rather than left dangling-uncommitted and lost at PR time.)

The points, in run order. The first group is the **task flow**; the last group is the **user-review-fix flow** (the fused `/autonomous-sdlc-harness:branch-start-user-review-fix-autonomous` engine), which has the same invariant and its own analogue commit points — grouping that the trailing points no longer follow strictly, since the two marked **(both flows)** belong to neither group and the two after them alternate between the flows one entry at a time:

1. **Watcher commits the copied prompt before launch** — `<scripts_dir>/autonomous-watcher.sh` (the prompt-commit block in the task path), so the engine starts from a clean tree on its very first step.
2. **Planning fork commits the UI-test plan at convergence** — Override 3 in `${CLAUDE_PLUGIN_ROOT}/instructions/task_plan_writing_instructions_autonomous.md`.
3. **Planning fork commits the task plan at convergence** — Override 4 in `${CLAUDE_PLUGIN_ROOT}/instructions/task_plan_writing_instructions_autonomous.md`.
4. **Phase D commits the branch statistics before the Done summary** — Override D above.
5. **Phase D commits the run's improvement observations after the statistics commit** — Override I above. It fires between the Override D/E statistics commit+push and the D.2 Done summary, is **skipped entirely when the run logged no observations and no intake file is tracked for the branch yet** (no file, no empty commit, no error — the analogue of Override D's `error:` gate), and is safe to re-enter on a resumed run, which appends only its own observations and commonly yields wrapper exit 3 (nothing to commit). Before the wrapper runs, the file is checked for machine paths and any hit is rewritten; a hit that cannot be cleared means no commit, handled like a wrapper refusal (module `## Commit mechanics` → **Machine-path check — before every wrapper call.**). Like entry 1's watcher prompt commit — and with its fix-flow twin, entry 8 — it is **best-effort and never a gate**: a wrapper refusal or failure (exit 2 / exit 1) is logged, never escalated. But on a **later** write its intake file is by then **already tracked**, so leaving such a failure alone would dirty a tracked file rather than leave an untracked one; it therefore reverts its own edit rather than leaving the tree dirty, and reports the outcome in the Done summary — see the module's `## Commit mechanics`.
6. **User-review-fix-plan fork commits the fix plan + source review at convergence** — Override 3 in `${CLAUDE_PLUGIN_ROOT}/instructions/user_review_fix_plan_writing_instructions_autonomous.md` (commits the fix-plan index, the per-finding folder when non-empty, and the watcher-copied source review for the active round; critical on a zero-finding round, where Phase A commits nothing).
7. **User-review-fix fork commits the post-user-review statistics in Phase D** — Override D in `${CLAUDE_PLUGIN_ROOT}/instructions/user_review_fixes_instructions_autonomous.md`.
8. **User-review-fix fork commits the round's improvement observations in Phase D** — Override I in `${CLAUDE_PLUGIN_ROOT}/instructions/user_review_fixes_instructions_autonomous.md`. Same position and semantics as the task flow's improvement-observations point above, in its own flow: after that fork's Override D/E statistics commit+push and before its D.2 Done summary, **skipped entirely when the round logged no observations and no intake file is tracked for the branch yet**, and safe to re-enter on a resumed run, which appends only its own observations and commonly yields wrapper exit 3 (nothing to commit). It runs the same machine-path check as entry 5 before its wrapper call. It carries the same **best-effort, never-a-gate** property as entry 5 — and hits its tracked-file case more often, since the task run will usually have committed the intake file already: **on a later, already-tracked write**, a wrapper refusal or failure means it reverts its own edit rather than leaving the tree dirty (module `## Commit mechanics`).
9. **Flow-progress ledger — creation + every phase-flip commit (both flows)** — Override G above (task flow) and the planner / user-review ledger overrides. The driving fork creates the ledger at Setup and commits each `[ ]`→`[x]` phase-flip, all via direct `<scripts_dir>/commit-on-branch.sh` (never a committer), canonical in `autonomous_pause_and_ledger.md` §1.6. These land the durable phase pointer that keeps resume deterministic; each is idempotent (re-flip → wrapper exit 3 → skip), so they are safe to re-run on a resumed run.
10. **Every phase boundary commits the run's dispatch-additions record (both flows)** — the record step of `${CLAUDE_PLUGIN_ROOT}/instructions/dispatch_discipline_instructions.md`, run at the end of each phase in which an addition was made and **before** that phase's flow-progress flip (entry 9), via direct `commit-on-branch.sh` (never a committer, canonical in `${CLAUDE_PLUGIN_ROOT}/instructions/autonomous_pause_and_ledger.md` §1.6) and followed immediately by that module's own `push-branch.sh` call. The two planning loops have no phases and write theirs once at their `## Convergence`, alongside entries 2/3 and 6 in either order — the record carries its own push, so it never depends on theirs. It is **skipped entirely** when the phase added nothing — no file, no empty commit, no error — and is **best-effort and never a gate**, exactly like entries 1, 5 and 8: a wrapper refusal or failure (exit 2 / exit 1) is logged, never escalated, and on an already-tracked record it reverts its own block rather than leaving the tree dirty (module `## Commit mechanics`). A re-entered phase commonly yields wrapper exit 3.
11. **Phase D commits the run's clarification digest after the observations commit** — Override J above. It fires between the Override I observations commit+push and the D.2 Done summary, is **skipped entirely when the branch parked on nothing** (no file, no empty commit, no error), and is safe to re-enter on a resumed run, which re-derives the same blocks from disk, appends none of them again and commonly yields wrapper exit 3 (nothing to commit). Like the improvement-observations points above it is **best-effort and never a gate**: a wrapper refusal or failure (exit 2 / exit 1) is logged, never escalated, and on an already-tracked digest it reverts its own edit rather than leaving the tree dirty (module `## Commit mechanics`).
12. **User-review-fix fork commits the round's clarification digest in Phase D** — `Override J` in `${CLAUDE_PLUGIN_ROOT}/instructions/user_review_fixes_instructions_autonomous.md`. Same position and semantics as the task flow's digest point above, in its own flow: after that fork's Override I observations commit+push and before its D.2 Done summary, **skipped entirely when the branch parked on nothing**, and safe to re-enter on a resumed round, which re-derives the same blocks from disk and commonly yields wrapper exit 3. It carries the same **best-effort, never-a-gate** property and the same revert duty: an untracked first write is left alone on a refusal or failure, an already-tracked digest has its own edit reverted rather than leaving the tree dirty (module `## Commit mechanics`).

Editing any one of these in isolation risks regressing the shared invariant — treat them as a group. Each block back-references this section as the single rationale source rather than restating it.

**Post-commit push.** In the autonomous fork **each** of these commit points is now followed by a push of the worktree branch to its upstream, so that wherever the run stops the remote branch tracks the local commit chain **as far as each of those pushes succeeded**: the committer-funneled points push via the committer's `push: true` arg (`committer.md`), bound here as `<committer_push>`, and the direct-`git` points push via `<scripts_dir>/push-branch.sh` — for the task flow, Override E's follow-on push after Override D, Override I's own follow-on push after its improvement-observations commit and Override J's after its clarification-digest commit; for the user-review-fix flow, that fork's Override E push after its Override D statistics commit, its Override I push after its own observations commit and its Override J push after its own digest commit (all in `user_review_fixes_instructions_autonomous.md`); and, in both flows and in both planning loops, the dispatch-additions record's own follow-on push (entry 10, `${CLAUDE_PLUGIN_ROOT}/instructions/dispatch_discipline_instructions.md` → `## Push`). Each of those is a plain, single-statement `push-branch.sh` call issued immediately after the commit it follows. The push is best-effort (the helper and the committer's push step are both non-blocking) — a refused or failed push is never escalated, and what the remote actually carries is then whatever the D.2 **Branch delivery** bullet reads off the branch, not an assumption made here — and is scoped to the run's **own non-protected** worktree branch — the protected-branch hard boundary (see **Hard boundary** above) is unchanged: the helper and the harness guard both refuse protected branches, and the flow still ends at "branch ready for review."
