# Context: instructions for Claude on how to run a supervised UI/browser QA session on the current branch.

## Resolved values

The tokens below are neither Mode-contract **bindings** (this file declares none) nor ordinary **path placeholders** (`<branch>`, `<N>`, `<qa_port>`, `<round>`, `<qa_review_findings_dir>`, which this file's own text resolves): they are derived at runtime or resolve from the adopting repository's `harness.config.json`. They are declared here once, and after this table the body uses each one as an ordinary placeholder.

| Token | Class | How to resolve it |
|---|---|---|
| `<repo_root>` | derived at runtime | The absolute root of the checkout this session runs in. Obtain it with a **bare** `git rev-parse --show-toplevel` and build every literal path from the result. Never embed the `$(…)` substitution inside another shell command, and never stash it in a shell variable across separate Bash calls — separate calls do not share shell state. |
| `<worktree_glob>` | derived at runtime | The **parent directory of `<repo_root>`** (the work root) joined to the configured `projectName` stem and a `-*` suffix — the sibling-worktree pattern an autonomous run's per-branch worktrees match, and the pattern the generated permission profile is materialized with. |
| `<state_dir>` | config value | `stateDir` — the run-artifact tree every artifact path in this file is relative to. Default `sdlc-harness/`. It is never dot-named: no path segment of it may begin with a dot. |
| `<app_dir>` | config value | `appDir` — the app's directory inside the checkout, repo-relative. The app root the dev server serves is `<repo_root>/<app_dir>`. |
| `<scripts_dir>` | config value | `scriptsDir` — the directory the generated wrapper scripts live in: the one the configured `commands.devServer` string in the next row normally points into. The QA helper scripts this file names by path (`find-free-port.sh`, `poll-dev-server.sh`, `kill-dev-server.sh`, and the `reserve-qa-user.sh` / `release-qa-user.sh` pair it names only to disclaim) are **not** under it — they are plugin assets, addressed as `${CLAUDE_PLUGIN_ROOT}/scripts/<name>.sh`. |
| `<dev_server_cmd>` | config value | `commands.devServer`. It **normally** holds the repo-relative wrapper invocation — `bash` followed by that wrapper's path under `<scripts_dir>` (i.e. `bash <scriptsDir>/start-dev-server.sh`). **Run the configured string as-is**, appending only the port: never rebuild it from its parts, and never write an absolute path in its place. If that call is **refused**, the key holds a raw command line rather than the wrapper invocation — run `bash <scripts_dir>/start-dev-server.sh`, whose body is the line `init` inlined into it — not necessarily the configured string, if the key was edited after that wrapper was written — and report in your return which string you ran. |
| `<qa_port_seed>` | config value | `qa.portSeed` — the base the QA port probe counts up from. Default `3001`. |
| `<qa_creds_path>` | config value | `qa.credentialsPath` — the repo-relative path of the gitignored test-account file. Read only when `phases.qa` is `true`, and read by the qa-tester, never by this flow. |

---

This is the **supervised** QA flow, triggered by `/branch-qa-test`. It is the opt-in, hands-on counterpart to **Phase E** of `${CLAUDE_PLUGIN_ROOT}/instructions/plan_orchestration_instructions_core.md` (the automatic QA phase the semi-autonomous task-plan orchestrator runs, entering the core through its `…_semi_autonomous.md` fork). The difference is the same as `/branch-review` vs the semi-autonomous review phase: **this flow presents findings to the user and stops. It never auto-fixes and never commits.** The user drives next steps (fix manually, run `/branch-implement-review`-style follow-up, or run the semi-autonomous QA loop if they want the fixes applied and committed automatically).

You drive the agents; you do **not** edit app code, you do **not** edit the UI-test plan, and you do **not** commit. Reuse the existing conventions — do not invent parallel ones:

- Dev-server lifecycle: the **Phase E convention** in `${CLAUDE_PLUGIN_ROOT}/instructions/plan_orchestration_instructions_core.md` (`### E.0 Start the dev server`). You own the server lifecycle; the qa-tester only consumes an already-running one.
- The `qa-tester` invocation contract: the **Phase E.1** block — **one qa-tester dispatch per UI-test case** (`test_ids` of one), not one dispatch for the whole plan. **Do NOT inherit Phase E.1's per-test mark-pass step.** The semi-autonomous Phase E flips the UI-test index `**Test N**` checkbox to `[x]` (via a `committer` `mode: ui_test_pass` dispatch) after each per-test PASS; this supervised flow is contractually **non-committing / read-only** on the UI-test index, so it does **not** flip those checkboxes and does **not** dispatch the committer. It only **reports** PASS to the user. Do not "keep it in lockstep" with the auto flow's marking step — the marking step belongs to the committing flow only.
- Per-test return aggregation: the **Phase E.2** convention — the orchestrator assembles the per-dispatch returns into a single round-level QA-review index.
- The `qa_reviews` family paths: Phase E's shape, **round suffix included** — `<qa_review_findings_dir>` = `<state_dir>/qa_reviews/<branch>_qa_review[_<round>]/`. Phase E re-binds it per re-test round from a `<round>` counter it carries in-session; a supervised session carries no counter across invocations, so **step 3 resolves it from disk** to the next free slot. Inside that folder the qa-tester writes namespaced per-dispatch artefacts (`qa_review_<iteration>_t<T>.md` index + `finding_t<T>_<N>.md` findings) and you assemble the merged round index `qa_review_<iteration>.md`. Resolve the folder through the placeholder every time; never write it as a literal.

## Flow

### 1. Ensure a UI-test plan exists

**Skip this flow unless `phases.qa` is `true` in `harness.config.json`.**

1. Determine the current git branch with `git branch --show-current`.
2. Confirm the story index exists at `<state_dir>/story_plans/<branch>_story_plan.md` (the writer and qa-tester need it). If missing, stop and ask the user.
3. Check whether the UI-test plan **index** exists at `<state_dir>/ui_test_plans/<branch>_ui_test_plan.md`.
   - **If it is missing**, dispatch `ui-tests-plan-writer` in initial-write mode:

     ```
     Write the UI-test plan.
     Branch: <branch>
     Inputs: task prompt <state_dir>/task_prompts/<branch>_task_prompt.md, story index <state_dir>/story_plans/<branch>_story_plan.md, per-task files <state_dir>/task_plans/<branch>/
     Outputs: index <state_dir>/ui_test_plans/<branch>_ui_test_plan.md and per-test files <state_dir>/ui_test_plans/<branch>/ui_test_<N>.md
     ```

   - **If it already exists**, do NOT re-write it by default. Only if the user explicitly asks to refresh it (e.g., because behaviour changed since it was written), dispatch `ui-tests-plan-writer` in augment mode:

     ```
     Augment the UI-test plan.
     Branch: <branch>
     Additional input: user-review fix plan <state_dir>/user_reviews/<branch>_fix_plan*.md (+ its finding_<K>.md files)
     ```

     (Augment mode reads the existing plan and only adds/revises cases for behaviour the fixes changed — see `ui-tests-plan-writer.md`. Pass the augment input only if such a fix plan exists; otherwise just tell the user the plan is current and skip the refresh.)
4. **Present the UI-test plan summary to the user and pause for approval before testing.** Report the writer's `ui_test_index`, `ui_test_files_dir`, and `tests_count` (do not paste the plan body — the user can open the index). **If the writer returned `no_ui: true`** (it wrote no plan because the branch renders no interactively-testable UI), tell the user there is nothing to QA on this branch (give the writer's `reason`), then **stop** — do **not** start the dev server (step 2) or dispatch the qa-tester; there is no plan to run. If the writer returns a `## Questions` section, surface the questions verbatim and stop; do not proceed to testing until the user answers and you re-dispatch the writer with the answers. Once the user approves the plan, continue.

### 2. Start the dev server (background)

The helper invocations in this step and in step 5 name a script under the **plugin root** and never spell that root themselves: resolve it and issue an absolute path — the rule, what a refused *resolved* invocation means, and why the root is not to be discovered by globbing are all in `${CLAUDE_PLUGIN_ROOT}/instructions/plan_orchestration_instructions_core.md` → `### E.0 Start the dev server`, its **Resolve the plugin root before you issue any command in this phase.** paragraph.

Follow the **Phase E.0 convention** verbatim — do not invent a different mechanism:

1. **Assign the port.** Run the resolved path to `find-free-port.sh` (the rule cited above), passing `<qa_port_seed>` as its one argument, and capture its stdout as **`<qa_port>`** — the first free port ≥ `<qa_port_seed>` (the argument is the probe's base/seed, not a hardcoded server port). The seed is deliberately **one above the port a dev server takes by default**, so that default port is left free for a human developer's own run and an automated session cannot disturb one already in progress; a lone QA run gets the seed itself. A non-zero exit means "QA dev server failed to start" — stop and surface to the user.
2. **Start the dev server.** Run the command configured at `commands.devServer` — `<dev_server_cmd>`, with `<qa_port>` appended — one allow-listed pinned-script command that encapsulates the raw dev-server command line for the app at `<repo_root>/<app_dir>` (the script does not inspect the port — the strict-port flag that makes a taken port fail loudly instead of silently falling through to port+1 is the adopter's to put on that command line), the same way `find-free-port.sh` / `poll-dev-server.sh` / `kill-dev-server.sh` encapsulate their commands. (Same rationale: a pinned script-path allow matches in worktree headless runs where a raw package-manager invocation into a nested app directory is permission-gated — see the script's header.) It launches the server detached and prints its **PID + log path** to stdout — capture both. Where the wrapper carries a pre-start line, that step runs to completion first and its output — a project build's, most often — precedes those two lines; capture the last occurrence of each. A pre-start failure prints one `…: the pre-start step failed, so the server was not launched` line and no PID line at all: that is a build failure, not a taken port, so report it rather than retrying the probe. The **PID** is what step 3 checks "is my own background process still alive" against, and the **log path** is where you inspect a startup failure. **Read that log through Bash, never with the file-reading tool:** it is written under the system temp directory, outside every `Read` rule the profile grants, and a `Read` of it is refused with *"Path is outside allowed working directories"*. `cat` and `tail` are allow-listed with no path restriction, so `tail -n 50 <the log path just captured>` (or `cat`) is the route — here, and wherever step 3 sends you back to it. If the start fails because the port was taken between probe and bind, re-run step 1 (fresh probe) and retry — at most 3 total attempts; after that, stop and surface "QA dev server failed to start" to the user.

   **Do NOT** start the server with a raw package-manager invocation into `<worktree_glob>/<app_dir>`, nor with an absolute path to the dev server's own binary inside the installed dependencies — both are known to be permission-gated in worktree headless runs (the mid-path `<worktree_glob>` glob does not match the worktree path), so they silently skip the dev-server start and the browser QA pass never runs. **Always go through the configured `commands.devServer` string.**
3. Poll until it answers by running the resolved path to `poll-dev-server.sh` (the rule cited above) with `<qa_port>` as its one argument — one allow-listed command that loops `curl -sf -o /dev/null http://localhost:<qa_port>` internally with a short sleep and a bounded wait (~60s default), never a fixed sleep as the readiness signal. (An open `curl … http://localhost:*` prefix allow would permit arbitrary trailing args headlessly; the pinned script closes that — see the script's header, same rationale as `find-free-port.sh` / `kill-dev-server.sh`.) It exits `0` on the first answer and non-zero on timeout — treat non-zero as "QA dev server failed to start": stop and surface to the user. **A poll answer only counts if your own background dev-server process is still running.** Before trusting the script's `0` exit, run `ps -p <pid>` against the **PID the `commands.devServer` script printed** — **bare**, with no `-o` format string — and grade its **exit status**: `0` means the process is alive, non-zero means it is gone. Both halves of that spelling are load-bearing, for different reasons: the **bare** form is the one measured to run where an `-o`-formatted form was refused (`ps -p <pid> -o pid=,command=` → *"This command requires approval"*, on a profile carrying no `ps` entry of any form, where the bare `ps -p <pid>` was allowed and sufficed), so it is the spelling that survives a profile narrower than this one; and grading the **exit status** rather than parsing the output keeps a platform-dependent output shape out of the contract. The `Bash(ps -p:*)` entry itself is a command prefix and would admit either form — the bare spelling is prescribed for the profiles that do not carry the entry, not because the entry excludes the other. If that PID is gone, that is the port-taken failure (step 2's retry path; the URL that answered belongs to a *different* run's server, and step 2's log path will show the bind error), so re-probe and restart instead of recording `base_url`.

   **If the probe itself is refused** — a narrower profile, a machine-local hook, or an interactive-test permission fragment generated before its `Bash(ps -p:*)` entry existed (that fragment is written create-if-absent, so a plain re-run does not add it); the bare form has been measured to run even without that entry, so a refusal here is not diagnosed from the fragment alone — do **not** proceed on the poll alone: a poll answering on a port says nothing about *whose* server answered, which is the whole failure mode this step exists to catch. Take the substitute that discriminates the same two cases: `tail` the step-2 log (step 2's Bash-reader rule) and look for the server's own bind or exit error. If the log shows the process exited, treat it as the port-taken failure and take step 2's retry path. If **neither** route is available, the disclosure is inline and immediate — this flow has a person in the loop and no Done summary to carry it: report that the liveness check could not run and which route was refused, then **stop and surface to the user**, who decides whether to test against an unverified server. What is never allowed here is the third option: proceeding on the poll alone without saying the guard did not run.
4. Record `base_url = http://localhost:<qa_port>`.

You own this server. **You tear it down in step 5** — when QA finishes (PASS or FAIL) and on any halt (server-start failure, qa-tester `error:`, user abort). You do **not** own the QA user: the qa-tester reserves and releases the account each test needs itself (its "Which user" contract) — you never read creds, pass a user, or call `${CLAUDE_PLUGIN_ROOT}/scripts/reserve-qa-user.sh` / `${CLAUDE_PLUGIN_ROOT}/scripts/release-qa-user.sh`.

### 3. Bind this round's findings folder, then dispatch `qa-tester` once per UI-test case

**Resolve `<round>` to the next free slot, and bind `<qa_review_findings_dir>` to it.** Each `/branch-qa-test` invocation is one QA round, and this branch may already carry earlier rounds — written by a previous supervised run or by the semi-autonomous Phase E. Run `ls -d <state_dir>/qa_reviews/<branch>_qa_review <state_dir>/qa_reviews/<branch>_qa_review_* 2>/dev/null` (name the unsuffixed folder separately: a lone `_*` glob that matches nothing aborts the command in zsh) and pick the **next free** suffix: if no folder exists, `<round> = 1` and `<qa_review_findings_dir> = <state_dir>/qa_reviews/<branch>_qa_review/` (unsuffixed); otherwise `<round>` = one past the highest existing suffix and `<qa_review_findings_dir> = <state_dir>/qa_reviews/<branch>_qa_review_<round>/`. Same next-free rule as `${CLAUDE_PLUGIN_ROOT}/instructions/user_review_fixes_instructions_core.md` → `### QA.0 Resolve the round suffix, then augment the UI-test plan`. Reusing an occupied folder overwrites that round's merged index and its per-test finding files in place — a silent loss.

`iteration = 0` — and it stays `0` in **every** round: the round number lives in the folder segment, never in a file name (Phase E, `#### Notes on the QA-review paths`).

Read the UI-test plan **index** at `<state_dir>/ui_test_plans/<branch>_ui_test_plan.md` to get the ordered test-case list. **Loop over those test cases, in order**, dispatching `qa-tester` **once per case** with the **same per-single-test invocation contract as Phase E.1** (`test_ids` of one — a fresh agent session per test, each establishing its own starting state per `qa-tester.md` → `## Preconditions`):

```
ui_test_index: <state_dir>/ui_test_plans/<branch>_ui_test_plan.md
ui_test_files_dir: <state_dir>/ui_test_plans/<branch>/
test_ids: <N>
base_url: http://localhost:<qa_port>
findings_folder: <qa_review_findings_dir>
iteration: 0
# test_credentials — optional; omit it (the qa-tester self-reads the creds file). See below.
```

Collect each dispatch's short return keyed by test number; do not branch to step 4 until you have looped every test in the index (except on a per-test `error:`, which you surface immediately per step 4). You do not read or pass credentials — the qa-tester self-reads them (below).

**No auto-skip on `[x]` here.** The semi-autonomous Phase E skips readiness entries already marked `[x]` so QA resumes across rounds (it marks on pass). This supervised flow is non-committing and **never marks**, so any `[x]` in the index reflects prior automatic-flow history, not this session. It therefore does **not** auto-skip `[x]` entries: it runs the test cases the **operator selects** — by default the full index loop above, or a focused `test_ids` subset the operator asks for (e.g. re-run only the cases that failed). The skip-`[x]` resume behaviour is specific to the automatic semi-autonomous flow.

(The qa-tester creates `<qa_review_findings_dir>` itself only when it has findings to write — do NOT `mkdir -p` here. It namespaces its per-dispatch artefacts by test id — `qa_review_0_t<N>.md` index + `finding_t<N>_<M>.md` findings — so dispatches do not collide.)

**Where `test_credentials` come from.** The qa-tester self-reads the gitignored test-account file at `<repo_root>/<qa_creds_path>`; how it locates and parses that file is the qa-tester's own contract (`qa-tester.md`) — this flow does **not** parse the keys or pass them in. `test_credentials` is an optional override you normally **omit**. If the file is absent or empty, the qa-tester reports auth-gated tests as `blocked` (not failed) — relay that to the user rather than treating a blocked run as a pass.

**Test scenarios** (the project's own test-scenario rules, including any cross-account visibility rules it has) are documented in `.claude/qa_test_scenarios.md` — the adopter-side file `init` writes when `phases.qa` is `true`, and the single shared source the qa-tester and ui-tests-plan-writer also read. **That file holds the rules; `<qa_creds_path>` holds the account-specific values.** Do not re-derive gating semantics here.

### 4. Aggregate the per-test returns, present findings to the user, and STOP

Fold the per-test returns from step 3 into a single round outcome, mirroring **Phase E.2**:

- **Round PASS** — *only* if **every** per-test dispatch returned `verdict: PASS`. Report to the user that QA passed for every test case. Tear down the dev server (step 5) and stop. (No index is assembled when the whole round passes, and — unlike the semi-autonomous Phase E — the UI-test index `**Test N**` checkboxes are **not** flipped to `[x]`: this flow never commits, so it reports PASS without marking the index.)
- **A per-test `error:`** (dev server unreachable, an auth-gated test blocked with no credentials, etc.) → surface the error to the user verbatim the moment any dispatch returns it — do not let later per-test dispatches mask an earlier blocked one, and do not roll a blocked test into a pass. Tear down the dev server (step 5) and stop. Do not continue.
- **Round FAIL** — if no dispatch errored but **at least one** returned `verdict: FAIL`. The qa-tester wrote each failing test's namespaced per-dispatch artefacts to disk (`qa_review_0_t<N>.md` index + `finding_t<N>_<M>.md` findings in `<qa_review_findings_dir>`). **Assemble the merged round index** at `<qa_review_findings_dir>qa_review_<iteration>.md` (iteration `0`) exactly as Phase E.2 describes — a `## Context` paragraph plus a single `## Phase 2 Readiness — Ordered Fix List` enumerating every failing test's findings once, each pointing at its `finding_t<N>_<M>.md` — so the user (or a follow-up flow) reads one readiness list, not N fragmented ones. (Assembling the index is a workflow-document edit, the supervised counterpart to Phase E.2; you do **not** edit app code or the per-finding files.) Then **present the findings to the user** — point them at the merged index path and summarise the headline counts (total `must_fix` across tests, total findings). Do NOT paste the full review. **Do NOT auto-fix and do NOT commit** — this supervised flow stops here, exactly like `${CLAUDE_PLUGIN_ROOT}/instructions/code_review_instructions.md` ends with "the review is on disk, stop here, fixes happen in a separate session." Tell the user their options for applying the fixes:
  - Fix manually, then re-run `/branch-qa-test` to re-verify; or
  - Run a `/branch-implement-review`-style follow-up against the QA-review index (it carries the byte-identical `## Phase 2 Readiness — Ordered Fix List`, so it loops through the normal implementer / reviewer / committer agents); or
  - Run the **semi-autonomous QA loop** (Phase E of `${CLAUDE_PLUGIN_ROOT}/instructions/plan_orchestration_instructions_core.md`, reached through its `…_semi_autonomous.md` fork) if they want the fixes applied and committed automatically.

If anything in the findings is unclear or seems off, do not patch over it — ask the user clarification questions, or re-dispatch the qa-tester with a focused `test_ids` subset (e.g., re-run only the cases that failed). Re-running QA after a fix is a fresh round the **user** initiates, not something you loop automatically — that re-run resolves its own next-free round folder in step 3, so it never overwrites this round's artefacts.

### 5. Tear down the dev server

Kill the background dev-server process started in step 2 before exiting — on PASS, on FAIL, and on any halt — by running the resolved path to `kill-dev-server.sh` (the rule cited in step 2) with `<qa_port>` as its one argument — **always pass the assigned port** (one allow-listed command encapsulating `lsof -ti tcp:<qa_port> -sTCP:LISTEN | xargs kill` — it kills only the pid(s) *listening* on the port, never your own browser's client connections; a bare pipe would otherwise prompt, since `allow-safe-compounds.sh` covers `&&`/`||`/`;`/a newline but not pipes). It is a no-op if nothing is listening, so it is safe on any halt. (No QA-user teardown here — the qa-tester releases its own reserved user per dispatch.) The supervised flow then ends: the review (if any) is on disk; fixes happen in a separate session the user chooses.
