# Autonomous task-plan writing loop

Autonomous variant. Run `${CLAUDE_PLUGIN_ROOT}/instructions/task_plan_writing_instructions_core.md` verbatim by reference, with the bindings below and the overrides that follow them. Do not restate the flow body — the Setup, the Safety contract, the `## Loop` writer/reviewer steps, the `## UI-test-plan write loop`, the `## Convergence` fact list, the stop conditions and the "What you must NOT do" list are canonical there.

**This fork differs from the core only in the binding values below and the overrides after them.** Three former overrides are now binding *values*: the removed approval gate is `<terminal_handoff>` (emit the convergence summary and fall straight through), the headless clarification reroute is the `<escalate>` / `<ask>` pair, and the non-interactive existing-plan decision is `<existing_artifact_decision>`, whose three cases stay stated in **`## Override 2 — resumability`** below rather than in the table — the watcher and sibling instruction files resolve `Override 2(a)` **by name**. What stays an override is what this mode purely **adds** and the core has no surface for: the resumability half of Override 2, the UI-test-plan commit at convergence (3), the task-plan commit at convergence (4), and the pause/resume + flow-progress ledger (5) — plus the two sections this fork owns on behalf of **every** autonomous flow, `## Clarification channel — file format` and `## Ask-vs-assume policy`. Everything else — the writer/reviewer dispatch blocks, the iteration caps (`>= 5` per loop), the `<state_dir>/STOP` / `<state_dir>/.dispatch_counter` / `MAX_TOTAL_DISPATCHES` safety contract (**except** Override 5 folds a `<state_dir>/PAUSE` check in immediately after the STOP check), and the heartbeat formats — is identical and is NOT duplicated here.

### `<escalate>` / `<ask>` — the headless clarification reroute

Both bindings resolve to the **same** file-based channel and differ only in what triggers them. `<ask>` fires when the `task-plan-writer` (or `ui-tests-plan-writer`) returns a `## Questions` section. `<escalate>` fires when the flow is genuinely blocked — a missing task prompt, a review loop that did not converge, an agent returning `error:` / `blocker:` — and for a blocker you first apply the **`## Ask-vs-assume policy`** below, which this file owns: a question file is written only when that policy says *ask*. Either way the behavior depends on the **entry point** the planner was invoked from (see `/autonomous-sdlc-harness:branch-start-plan-autonomous` for the two entry points):

- **Headless / watcher entry point:** write **every** blocking question or blocker of this park into **one** self-contained `<state_dir>/clarifications/<branch>/question_<n>.md` in the format defined in `## Clarification channel — file format` below — naming the raising agent/phase, the latest findings path wherever the core's site names one, and one section per concrete decision needed — emit a one-line `PARKED: <branch> — N question(s) at <state_dir>/clarifications/<branch>/` to the run log, then **truly stop and yield — end the session.** Do NOT spin, poll, sleep-loop, or re-dispatch waiting for an answer. **Ending the session is what makes the park free of dispatch cost** — a polling/sleeping run would keep burning dispatches against `MAX_TOTAL_DISPATCHES` for nothing. The watcher detects this exit plus the unanswered `question_<n>.md`, marks the run `parked`, and resumes it once every top-level question file has its `answer_<n>.md` (Override 2(a) consumes the answers on re-entry).
- **Manual / interactive entry point:** surface the `## Questions` — or the blocker — **live** for inline answering, exactly as a supervised flow does (unchanged): stop, surface them to the user verbatim, and dispatch the writer again with the answers appended once they reply. **No files are written** — the file-based channel is the headless behavior only.

The entry point determines which behavior applies; both are valid for this one engine.

**Neither binding reaches a `<state_dir>/STOP` halt or the cap halt.** The core states all of those sites — `## Setup` step 3, `## Safety contract` steps 1 and 2, `## Stop conditions` entries 1 and 2 — as a plain report followed by stopping: `<reentry_command>` is named at the three STOP sites, and the cap figure plus the inspect paths at the two cap sites. It names no escalation binding on any of them and this fork adds none. A STOP file is a user-initiated stop rather than a blocker, and the orchestration family's `MAX_TOTAL_DISPATCHES` halt stops plainly. Routing either through the park would turn the operator's brake into a spurious park the watcher would then try to resume.

### `<terminal_handoff>` — no approval gate

The supervised value of this binding ends the flow at a **"Present to user"** step and then **stops** ("Then stop. Do not auto-proceed to implementation — the user must approve the plan first."). This flow **removes that gate**:

- When the core's `## Convergence` condition is met — **both** loops complete: the task-plan loop returns `verdict: PASS`, and the UI-test-plan loop either returns `verdict: PASS`, **or** short-circuits because the `ui-tests-plan-writer` returned `no_ui: true` (a no-UI branch — no plan written, no reviewer dispatched), **or** never ran because `phases.qa` is `false`, **or** never ran, because `qa` is among the recorded skipped ids (an authored exclusion rather than a writer's finding — equally not an error) — the planning phase is **done** and the caller proceeds **directly to implementation**. There is **no** "present to user / wait for approval" step in this variant — do not pause, do not ask the user to invoke the next command. (The engine command chains planning → implementation in one uninterrupted session.)
- Still **emit the same short convergence summary** to the run log so the manual/interactive watcher and the central log capture it: `tasks_count`, the story-index path (`<state_dir>/story_plans/<branch>_story_plan.md`), the per-task directory (`<state_dir>/task_plans/<branch>/`), **when `phases.parity` is `true`, any excluded or deferred `<parity_vocabulary>` behaviours the writer reported (each with its authorising task-prompt line or `TODO: @claude` marker, per the core's `## Convergence` fact list; `none` if it reported none — when `phases.parity` is `false` the summary carries nothing on this line)**, the UI-test index path (`<state_dir>/ui_test_plans/<branch>_ui_test_plan.md`), and `tests_count` — **or, when the UI-test writer returned `no_ui: true`, emit `ui_test: no-UI (QA skipped)` in place of the index path + count** (no UI-test plan file was written), **and when `phases.qa` is `false`, emit `ui_test: QA phase not enabled`** in their place (the loop never ran), **or, fourth, when that loop never ran because `qa` is among the recorded skipped ids, emit `ui_test: skipped by run mode` in place of the index path + count** (no writer ran, so this variant never borrows the `no_ui` wording and never carries a writer's `reason`), and the mandatory `📌 Dispatch additions: …` disclosure line in the exact form `${CLAUDE_PLUGIN_ROOT}/instructions/dispatch_discipline_instructions.md` → `## The disclosure line` gives it (including its `none` form, which is a normal outcome; `<N>` is your own count of the blocks you wrote at the core's `## Convergence` record step). Emit it as a log line and fall straight through — do **not** treat it as a stopping point. Emit the mandatory `📌 Run mode: …` disclosure line too, as its own line beside the `📌 Dispatch additions: …` line and never merged into it, in the exact form `${CLAUDE_PLUGIN_ROOT}/instructions/run_mode_instructions.md` → `## The disclosure line` gives it — including its `none` form (a prompt carrying no such section at all, a normal outcome) and its ignored-directive suffix; the core's `## Convergence` owns that obligation and the form, and this fork-held hand-off value is where it is emitted.

## Override 2 — resumability

On **(re-)entry**, before dispatching the writer, detect prior state and continue from where the previous run parked rather than restarting. This mirrors how the implement phase is already resumable via the Phase 2 Readiness checkboxes. This section is the `<existing_artifact_decision>` value the core's `## Setup` step 5 applies — the precedent shape is that step's "If a story index already exists", but note this variant resumes **non-interactively**: it never asks the user "extend / rewrite / stop", it decides purely from the presence of clarification answers and the state of the story index. Mapped onto the three outcomes that step names: **(a)** is **extend** (the pending questions + answers are passed to the writer), **(b)** is **skip** (this loop has nothing left to do), **(c)** is **proceed fresh**.

Decide as follows:

- **(a) Story index exists AND clarification answers are pending consumption.** If `<state_dir>/story_plans/<branch>_story_plan.md` exists AND answered pairs sit at the **top level** of `<state_dir>/clarifications/<branch>/` (not under `answered/`) — each `answer_<n>.md` beside its matching `question_<n>.md`, per the clarification-channel format below, and **every** such pair, which are the ones the resume prompt names — **resume the writer with every such question file and its answer appended** to its prompt — this is how the answer content is fed back to the agent that parked. Do NOT restart the loop from scratch and do NOT re-ask an answered question; a question the answers leave unaddressed is re-parked per the clarification-channel section, never assumed. Then continue the loop normally from that point. Per the **consume-then-archive contract** in the clarification-channel section, the watcher deliberately leaves the answered pairs at the top level for this re-entry detection and archives them only **after** this resumed run exits — so a top-level `answer_<n>.md` is precisely the resume signal, and an answer already moved to `answered/` has already been consumed and must not be re-processed.
- **(b) Story index exists with a complete Phase 2 Readiness list and no pending clarification.** Skip the task-plan write loop and proceed to the **UI-test-plan loop** (or, if that is also complete or not enabled, fall through to implementation per `<terminal_handoff>`). This is the "continue from where it parked" behavior.
- **(c) No story index exists.** Run the loop **fresh** (the writer's first-iteration prompt, exactly as in the core's `## Loop` step 1).

## Override 3 — commit the UI-test plan after it converges

**Autonomous fork only.** This override exists nowhere in the core, in the semi-autonomous fork over it, or in the supervised flow — they deliberately leave the UI-test plan (index **and** the per-test detail dir) uncommitted for the human review/merge step. Only the autonomous flow self-commits it, so a watcher-driven run ends with a clean `git status`. Do **not** propagate this step into the core.

**Why a commit is needed here.** The Phase E `mode: ui_test_pass` committer stages **only** the index (`<state_dir>/ui_test_plans/<branch>_ui_test_plan.md`) and only one `**Test N**` checkbox flip at a time, and it never stages the per-test detail dir (`<state_dir>/ui_test_plans/<branch>/`) at all. So on any branch where QA is skipped, where some tests never pass, or where the run halts before Phase E, the index and/or the whole detail dir dangle uncommitted and are lost at PR time. This override commits the **as-written** plan once, at planning convergence, so both the index and the detail dir are tracked from the planning phase forward.

**Trigger (when it fires).** Exactly when the core's **`## UI-test-plan write loop` converges with a plan written** — i.e. its step 3 parsed `verdict: PASS` from the `ui-tests-plan-reviewer`. It runs **after** that PASS and **before** `<terminal_handoff>`'s fall-through to implementation. Run it once, at that single convergence point.

**`no_ui: true` short-circuit (when it does nothing).** When the `ui-tests-plan-writer` returned `no_ui: true`, no UI-test plan file was written — there is **nothing to commit**. Skip this commit entirely: do **not** create an empty commit, do **not** error. This mirrors the existing `no_ui` handling in `<terminal_handoff>` and in the core's `## UI-test-plan write loop`, and the convergence summary still reports `ui_test: no-UI (QA skipped)` unchanged. **When `phases.qa` is `false`** the core's UI-test-plan write loop never ran at all, so there is likewise no plan and nothing to commit: this override does not fire.

**Run-mode skip (a second, separate do-nothing path).** When the core's `## UI-test-plan write loop` never ran at all because `qa` is among the recorded skipped ids, no UI-test plan file was written either — again there is **nothing to commit**. Skip this commit and its push entirely: do **not** create an empty commit, do **not** error. Keep this clause **separate** from the `no_ui` one above rather than folding the two together: `no_ui` is the writer's own finding that there is nothing to test, this is an authored exclusion decided before the run began with no writer dispatched, and the convergence summary reports them in different words (see `<terminal_handoff>`).

**Commit mechanism (via the `commit-on-branch.sh` wrapper in the fork, not a committer dispatch).** Stage and commit through the `<scripts_dir>/commit-on-branch.sh` wrapper — never a direct `git add` / `git commit` here, because a `git commit` carrying a `${branch}` expansion is what stalls a headless run on the `Bash(git commit:*)` branch-guard; the `bash <scripts_dir>/commit-on-branch.sh …` invocation is auto-allowed and never matches that guard even with the expansion in its args. That allow is withheld, though, when **anything in the command** — subject included — carries `$(…)`, a backtick, `|` (hence `||`), `>`, `<` (hence a subject naming a `<placeholder>`) or a braced expansion other than a bare `${IDENT}`; the guard scans the whole string. This is **not** a `committer` agent dispatch (the existing `committer` modes do not fit: `review_plan_file` is locked to a different fixed subject; `task` / `review_item` / `ui_test_pass` each flip a `## Phase 2 Readiness` checkbox, but a "plan produced" commit flips nothing) — the fork calls the wrapper directly, exactly as the watcher commits the copied prompt directly.

**Exact staging + commit.** Pass **both** targets to the wrapper as explicit paths only — the wrapper stages them with `git add -- <path>` and never `git add -A` / `git add .` (matches the committer's no-blanket-add rule):

- `<state_dir>/ui_test_plans/<branch>_ui_test_plan.md` — the index
- `<state_dir>/ui_test_plans/<branch>/` — the per-test detail dir (holds the index's `ui_test_<N>.md` siblings)

This Override has **no idempotency guard** (it is reached only when a plan was written — the `no_ui: true` short-circuit exits before it), so the wrapper call replaces the `git add … ; git commit -m "$(cat <<EOF …)"` directly. Fixed subject `chore: Add UI-test plan for <branch>`, no `Co-Authored-By:` / trailer, no `--no-verify` / hook-skip flag — the wrapper enforces both: it builds the message from the positional args after `--` only (subject only here) and never passes `--no-verify`. Push the worktree branch immediately after the commit lands (see "Push after the commit" below). The whole block — commit **and** push — sits inside Override 3, which the `no_ui: true` short-circuit already exits before reaching here (per the short-circuit note above), so both the commit and the push are co-located in one block that runs only when a plan was written. Mirroring Override 4's structure, the push is part of the same block as the commit so nothing is pushed on the `no_ui` path:

```zsh
bash <scripts_dir>/commit-on-branch.sh --repo "$REPO_ROOT" \
  "<state_dir>/ui_test_plans/${branch}_ui_test_plan.md" \
  "<state_dir>/ui_test_plans/${branch}/" \
  -- "chore: Add UI-test plan for ${branch}"
bash <scripts_dir>/push-branch.sh "$REPO_ROOT"
```

If a hook fails, surface the error — do not bypass it with a hook-skip flag and do not create a partial commit; the wrapper returns a loud non-zero on a hook failure, which the fork surfaces.

**Push after the commit.** The `<scripts_dir>/push-branch.sh` call above runs in the same block as the commit, so it pushes the worktree branch to its upstream — tracking this planning-convergence commit — exactly when the commit ran, and not at all on the `no_ui: true` short-circuit (which exits Override 3 before this block, so neither the commit nor the push is reached). It uses the `$REPO_ROOT` the calling command (`/autonomous-sdlc-harness:branch-start-plan-autonomous`) derived at session start. The helper is best-effort (it exits 0 and logs on any failure — non-git dir, detached HEAD, protected branch, transient push failure) and reaches only the run's own non-protected branch; it never extends the flow or fails the planning phase. The shared rationale for this post-commit push is the clean-tree invariant cited under "Shared rationale" below — not restated here.

**Interaction with Phase E's `mode: ui_test_pass` commits (complementary, not conflicting).** Phase E later flips the index's `**Test N**` readiness checkboxes one at a time and commits the index alone (`committer.md` `ui_test_pass`). That is **unchanged and complementary**: this override commits the *initial* plan (index + details) at planning convergence so the detail dir and the as-written index are tracked from the planning phase; Phase E commits the per-test checkbox flips on top later. The two never contend for the same change — one is the initial plan, the others are subsequent checkbox-flip commits.

**Shared rationale.** This commit is one of the autonomous-fork commit points that collectively keep the clean-tree precondition honest — see **Autonomous-fork commit points — the clean-tree invariant** in `${CLAUDE_PLUGIN_ROOT}/instructions/plan_orchestration_instructions_autonomous.md`.

## Override 4 — commit the task plan after it converges

**Autonomous fork only.** This override exists nowhere in the core, in the semi-autonomous fork over it, or in the supervised flow — they deliberately leave the task plan (the story index **and** the per-task detail dir) uncommitted for the human review/merge step. Only the autonomous flow self-commits it, so a watcher-driven run ends with a clean `git status`. Do **not** propagate this step into the core. This is the task-plan analogue of Override 3's UI-test-plan commit.

**Why a commit is needed here.** No flow step otherwise commits the as-written task-plan family. The story index (`<state_dir>/story_plans/<branch>_story_plan.md`) lands later, opportunistically, on the first Phase A `task`-mode checkbox flip, and a per-task file (`<state_dir>/task_plans/<branch>/task_<N>_plan.md`) lands **only if** the implementer appended a `**Deviations from plan:**` note to it (the `committer.md` `task` / `review_item` modes stage `<task_file>` *conditionally* on that note). A per-task file with **no** deviation note is therefore never staged and dangles untracked through to "branch ready for review." This override commits the **as-written** plan once, at planning convergence, so both the index and every per-task file are tracked from the planning phase forward — mirroring how Override 3 commits the durable UI-test detail dir.

**Scope — durable planning artifacts only.** This commits the durable planning artifacts: the story index + the per-task detail dir (analogous to Override 3's per-test detail dir), **and** the four plan-review findings folders the planning loop's reviewers write (enumerated in the staging list below). Those folders are durable in the same sense — they are the evidence of what the plan loop found and what the writer had to fix, they are read at PR time, and no other flow step claims them. Keep the two directory families distinct **by name, not by glob** — a `…_point_reviews/` directory also ends in `_reviews`, so no `<state_dir>/*_reviews/` pattern separates them: only the four folders enumerated below are staged here, and every `<state_dir>/*_point_reviews/` file is **not** committed — those remain out of scope and uncommitted, exactly as before.

**Trigger (when it fires).** At **planning convergence** — the same single point Override 3 fires at: when the core's `## Convergence` condition is met (the `## Loop` returned `verdict: PASS`, and the `## UI-test-plan write loop` either returned `verdict: PASS`, short-circuited on `no_ui: true`, or never ran because `phases.qa` is `false`, **or** never ran, because `qa` is among the recorded skipped ids — an authored exclusion rather than a writer's finding, equally not an error), **before** `<terminal_handoff>`'s fall-through to implementation. Run it once. The story index always exists at convergence, so — unlike Override 3 — there is no `no_ui`-style short-circuit; the idempotency guard below is the only skip condition.

**Idempotency / empty-commit guard.** Under Override 2 resumability the story index may already be tracked from a prior run, so **skip the commit when nothing is staged** — now satisfied by the wrapper's dedicated **nothing-to-commit status (exit 3)** rather than a `git diff --cached --quiet`: the staged explicit set produces no diff and the wrapper returns exit 3, which skips the commit. This makes the override safe to re-run at convergence on a resumed run. After this commit, Phase A's later `task`-mode commits just **modify** the already-tracked story index (checkbox flips) — they do not re-add it.

**Commit mechanism (via the `commit-on-branch.sh` wrapper in the fork, not a committer dispatch).** Stage and commit through the `<scripts_dir>/commit-on-branch.sh` wrapper — never a direct `git add` / `git commit` here, because a `git commit` carrying a `${branch}` expansion is what stalls a headless run on the `Bash(git commit:*)` branch-guard; the `bash <scripts_dir>/commit-on-branch.sh …` invocation is auto-allowed and never matches that guard even with the expansion in its args. That allow is withheld, though, when **anything in the command** — subject included — carries `$(…)`, a backtick, `|` (hence `||`), `>`, `<` (hence a subject naming a `<placeholder>`) or a braced expansion other than a bare `${IDENT}`; the guard scans the whole string. This is **not** a `committer` agent dispatch (the existing `committer` modes do not fit a "plan produced" commit — it flips no `## Phase 2 Readiness` checkbox) — the fork calls the wrapper directly, exactly as Override 3 does and as the watcher commits the copied prompt directly.

**Exact staging + commit.** Pass **all six** targets to the wrapper as explicit paths only — the wrapper stages them with `git add -- <path>` and never `git add -A` / `git add .` (matches the committer's no-blanket-add rule):

- `<state_dir>/story_plans/<branch>_story_plan.md` — the story index
- `<state_dir>/task_plans/<branch>/` — the per-task detail dir (holds the `task_<N>_plan.md` files)
- `<state_dir>/task_plan_reviews/<branch>/` — plan-review findings, when the reviewer wrote any
- `<state_dir>/business_parity_reviews/<branch>/` — plan-mode parity findings, when any
- `<state_dir>/architecture_reviews/<branch>/` — plan-mode architecture findings, when any
- `<state_dir>/ui_test_plan_reviews/<branch>/` — UI-test-plan-review findings, when any

**Pass all six unconditionally — never add an existence guard.** The wrapper's staging policy is that "A path that does not exist is skip-with-warning … NOT a hard error" (`<scripts_dir>/commit-on-branch.sh`, STAGING POLICY header), so a reviewer that returned PASS created no folder and its path is simply skipped; and if all six are absent or unchanged the wrapper returns exit 3 and the commit is skipped whole, exactly as the idempotency guard above describes. An `if …; then` existence check would buy nothing and would reintroduce the headless trap the note below warns about.

Make **one** commit with the fixed subject `chore: Add task plan for <branch>`, no `Co-Authored-By:` / trailer, no `--no-verify` / hook-skip flag — the wrapper enforces both: it builds the message from the positional args after `--` only (subject only here) and never passes `--no-verify`. Rely on the wrapper's nothing-to-commit code (exit 3) to skip the commit, then push as a **separate plain statement**:

```zsh
bash <scripts_dir>/commit-on-branch.sh --repo "$REPO_ROOT" \
  "<state_dir>/story_plans/${branch}_story_plan.md" \
```

> ⚠️ **No exit-code gate — deliberate.** Do **not** wrap the push in `if [ "$?" -eq 0 ]; then … fi`. Per `${CLAUDE_PLUGIN_ROOT}/instructions/autonomous_pause_and_ledger.md` §1.6 that control-flow block is a headless trap (the ` then bash …` piece defeats `allow-safe-compounds.sh`, nothing else matches the command, and the run **stalls on a permission prompt it cannot answer headlessly** — **the commit silently does not land**). `$?` is unreliable across Bash calls anyway — each runs in a fresh shell. No gate is needed: `push-branch.sh` is non-fatal and only fast-forwards already-committed work, so an unconditional push is a harmless no-op ("Everything up-to-date") on the exit-3 path.

If a hook fails, surface the error — do not bypass it with a hook-skip flag and do not create a partial commit; the wrapper returns a loud non-zero on a hook failure, which the fork surfaces.

**Push after the commit.** The `<scripts_dir>/push-branch.sh` call above is **unconditional**, per the ⚠️ note above: it pushes the worktree branch to its upstream whenever a commit landed and is a harmless "Everything up-to-date" no-op when the wrapper returned its nothing-to-commit status (exit 3 — nothing staged, e.g. a resumed run whose story index is already tracked). Do **not** add an exit-code gate — `$?` is unreliable across separate Bash calls, and the `if …; then` compound is the headless trap the note describes. It uses the `$REPO_ROOT` the calling command (`/autonomous-sdlc-harness:branch-start-plan-autonomous`) derived at session start. The helper is best-effort (exits 0 and logs on any failure — non-git dir, detached HEAD, protected branch, transient push failure) and reaches only the run's own non-protected branch; it never extends the flow or fails the planning phase. The shared rationale for this post-commit push is the clean-tree invariant cited under "Shared rationale" below — not restated here.

**Interaction with the `task` / `review_item` `<task_file>` staging (complementary, not conflicting).** This override commits the as-written per-task files at convergence; the later Phase A `task`-mode committer (and Phase C `review_item` mode) still stages a per-task file **only when a Deviations note was appended during implementation** — those are subsequent diffs on top of an already-tracked file, so the two never contend (mirror of Override 3's interaction with Phase E `ui_test_pass`). Likewise the first `task`-mode checkbox flip now just modifies the already-tracked story index instead of first-adding it.

**Shared rationale.** This commit is one of the autonomous-fork commit points that collectively keep the clean-tree precondition honest — see **Autonomous-fork commit points — the clean-tree invariant** in `${CLAUDE_PLUGIN_ROOT}/instructions/plan_orchestration_instructions_autonomous.md`.

## Override 5 — pause/resume + flow-progress ledger (planning half)

**Autonomous fork only.** The mechanism — ledger schema, flip/commit contract, resume-from-ledger, pause protocol — is canonical in `${CLAUDE_PLUGIN_ROOT}/instructions/autonomous_pause_and_ledger.md` and is **not** restated here. This override names only the *planning-phase* points where it applies; the orchestrator fork's Override G owns the Implementation half.

**Create the ledger at Setup.** As the planner fork's **first Setup act** (during the core's `## Setup`, before the first `task-plan-writer` dispatch), create `<state_dir>/flow_progress/<branch>_progress.md` from the **task-engine template** (canonical-doc §1.3) and commit it via `<scripts_dir>/commit-on-branch.sh` (subject `chore: Add flow-progress ledger for <branch>`), **idempotently**: if it already exists (a resume) read it and skip creation — the wrapper returns exit 3 (nothing to commit) and nothing is pushed. This is the task-engine analogue of the user-review engine's ledger creation (owned by the fix-plan fork).

**Record the run mode in that same write.** The creation act above also writes the ledger's `## Run mode` block, including its `phases:` line, and marks a `[-]`-eligible entry `[-]` rather than `[ ]` when **either** a `skipped:` id names it **or** the `phases.*` flag gating it is `false` — **one write, one commit**, with the subject and the wrapper mechanics above unchanged. This creation act is the fork's **first Setup act**, and the configuration is readable there, so both provenances are resolved before that single write; neither waits on a later act. The block's shape, the three markers, the `[-]`-eligible set and the seeding rule are canonical-doc §1.3–§1.5's and none of them is restated here; what a directive id is, and what makes a directive ignored, is `${CLAUDE_PLUGIN_ROOT}/instructions/run_mode_instructions.md`'s.

**Who reads first.** This creation is the fork's *first* Setup act, so it can run **before** the core's `## Setup` step 6 — the ordering rule is that step's, copied here verbatim so the two files cannot disagree (its "this step" is that step): "The rule: the run mode is obtained by whichever participant reaches it first — the engine entry command's confirm-and-establish step where the session has one, otherwise this step, otherwise the creating fork performing the same grep-first check itself immediately before its creation write — and **the creation write never happens without a resolved run mode**, an absent `### Run mode` section resolving to "no run mode", which is a value, not a missing one." So where this fork reaches the write first, it performs that same grep-first check itself immediately before writing: the block is never written empty, and a prompt with no such section records `skipped: none`.

**What the idempotency rule then buys.** It is unchanged — but its consequence is now load-bearing: on a resume the ledger is **read, not reset**, so the block recorded at creation governs the branch from then on and a task prompt edited mid-branch does **not** silently change the run. The divergence is reported instead, per canonical-doc §1.4's tie-break.

**Flip the `## Planning` entries** — each a direct `<scripts_dir>/commit-on-branch.sh` + `<scripts_dir>/push-branch.sh` flip, **never** a committer dispatch (canonical-doc §1.6):
- `P1` — when the core's `## Loop` converges (`task-plan-reviewer` returns `verdict: PASS` at its step 5, i.e. the architecture gate — and, when `phases.parity` is `true`, the business-parity gate — also passed on the final revision).
- `P2` — on the runs whose UI-test loop actually ran, and only those: flip when the core's `## UI-test-plan write loop` converges (`ui-tests-plan-reviewer` PASS) or short-circuits on `no_ui: true`. A `P2` seeded `[-]` at creation — **whether by a run mode carrying `qa` or by `phases.qa` being `false`** — is **already resolved and is never flipped** (canonical-doc §1.5's never-flip-a-`[-]` rule); the loop never ran, so this bullet reaches nothing.
- `P3` — right after **Override 3 + Override 4** have committed the durable plan artifacts (UI-test plan, then story index + per-task dir). Flip `P3` as the **last planning action** before `<terminal_handoff>`'s fall-through to implementation.

**Resume-from-ledger (planning).** Override 2's resumability is unchanged and composes: on re-entry, if `P1` is `[x]` skip the task-plan loop; if `P2` is `[x]` **or `[-]`** skip the UI-test loop; if all three `## Planning` entries are **resolved — `[x]` or `[-]`** — planning is done — fall straight through to implementation (`<terminal_handoff>`). A `[-]` is resolved, not pending (canonical-doc §1.7 step 2): reading it as pending would land every re-entry on a phase excluded before the run began — the loop a run mode carrying `qa`, or `phases.qa` being `false`, switched off. The clarification-answer resume (Override 2(a)) still fires independently. The ledger's `## Planning` entries are the durable, **computed** form of Override 2(b)'s "story index exists with a complete readiness list" heuristic (canonical-doc §1.7).

**Honoring a PAUSE during planning.** The core's `## Safety contract` checks `<state_dir>/STOP` before every dispatch; **immediately after** it, apply canonical-doc §2.2 — if `<state_dir>/PAUSE` is present, pause at the next clean tracked-tree boundary (the in-progress story index / per-task files are untracked until Override 3/4 commit, so they are tolerated): append `<state_dir>/PAUSE_PROGRESS.md`, write `<state_dir>/PAUSE_ACK`, emit `PAUSED: <branch> — planning`, and **end the session**. The watcher classifies `paused` and resumes on `<state_dir>/RESUME`; re-entry uses resume-from-ledger + Override 2.

**Self-pause on API overload during planning.** When a `task-plan-writer` / reviewer dispatch dies on an API-infrastructure error rather than on anything the sub-agent did (`Agent terminated early due to an API error: API Error: 529 Overloaded`, likewise `500` / `503`), apply canonical-doc **§2.5**: it is not a reviewer `FAIL` and does **not** advance the `>= 5` convergence cap — re-dispatch immediately, then once more after a backoff of **at most 60 s**, and on the third consecutive failure **self-pause** (append `<state_dir>/PAUSE_PROGRESS.md` with the reason + the undelivered dispatch, write `<state_dir>/PAUSE_ACK`, emit `PAUSED: <branch> — planning (API overload)`, end the session). ⚠️ Never schedule a `Monitor`, never sleep for minutes, and never end the turn intending to continue after a backoff: the headless process is torn down at end of turn, so that exit is `rc=0` with no `PAUSE_ACK` and the watcher stamps the run **`completed`** and notifies **success** for planning that never converged.

## Clarification channel — file format (canonical, single source of truth)

This section is the **one** authoritative definition of the async file-based clarification channel. The implementation fork (`${CLAUDE_PLUGIN_ROOT}/instructions/plan_orchestration_instructions_autonomous.md` → `## Mode contract — bindings` → ``### `<escalate>` — the clarification reroute``) and the watcher (`<scripts_dir>/autonomous-watcher.sh`) both **reference this section** — they do not restate the format.

- **Directory:** `<state_dir>/clarifications/<branch>/`, inside the run's own worktree (so it is per-worktree exactly like the rest of `<state_dir>/…`). `clarifications/` **is** a directory of the run-artifact tree `init` materializes, on every run regardless of which phases are on, and `init` writes it with a committed `README.md` stating this channel's contract; the `<branch>/` subdirectory beneath it is created on that branch's first question. The question, answer and archived files themselves are **machine-local** — the generated ignore rules ignore the directory's contents and except only that README, so no exchange file ever reaches a commit. What does survive the working copy is the exchange's **content**: at Phase D the run digests each resolved pair into the committed `<state_dir>/clarification_digests/<branch>.md`, canonical in `${CLAUDE_PLUGIN_ROOT}/instructions/clarification_digest_instructions.md`.
- **Question file:** `question_<n>.md`, **one file per park**, holding every question that park raises, where `<n>` is a 1-based index unique across the **whole branch directory, its `answered/` archive included**, and never reused: take the next index above the highest `question_<n>.md` present in **either** location, never merely the next free name at the top level, and never overwrite an existing `question_<n>.md`. The archive is why the distinction matters — the consume-then-archive bullet below moves an answered pair out of the top level once its resumed run exits, so a top-level-only scan frees index `1` again, and the index is the identity the branch's committed clarification digest keys its blocks on (`${CLAUDE_PLUGIN_ROOT}/instructions/clarification_digest_instructions.md` → `## The entry format`). Each file is **self-contained**: it must carry enough context for the user to answer cold, with no access to the live session. It opens with which agent/phase raised the park (e.g. `task-plan-writer`, or `Phase A1.5 business-parity-reviewer`) and the latest findings path where one applies, then carries one `## Q<k> — <decision needed>` section per question, `<k>` counting from 1, each self-contained and stating at minimum:
  - why it is high-stakes / irreversible / unresolvable-from-source (per the ask-vs-assume policy below — a question is only written when the policy says *ask*),
  - the concrete decision needed and any options the run is choosing between.
- **Answer file:** the user answers the whole park by dropping one sibling `answer_<n>.md` in the same directory. **Pairing is by index `<n>`** — `answer_3.md` answers `question_3.md`. Rulings address questions by `Q<k>`; a park of one question needs no label, and text addressed to no label answers every question in the park. A question the answer does not address stays open: the resumed run parks it again in a **new** question file, at the next index, rather than assuming.
- **Why one file per park:** every site that writes a question does so at the moment it parks and then ends the session — this fork's headless reroute and the matching reroute in each of the other three autonomous forks — so no question is ever written while its run keeps going, and a park's questions are known together. One file per question would let a watcher consume part of a park.
- **Parks written before this layout:** several one-question files form one park; every rule here applies to them unchanged.
- **The run never deletes its own `question_<n>.md`.** It writes the question and yields; it does not clean up.
- **Consume-then-archive (single ordering contract for resume).** The watcher resumes a parked run only when **every** top-level `question_<n>.md` has its `answer_<n>.md`. It then **re-launches the engine first, leaving every answered `question_<n>.md` / `answer_<n>.md` pair at the top level of `<state_dir>/clarifications/<branch>/`** — it does NOT archive before re-launching — and its resume prompt names every one of those answer files. The re-launched engine consumes **all** of them, each paired by index with its question (Override 2(a) above). **Only after** the resumed run exits — once the answers have been consumed — does the watcher archive **exactly the set the prompt named** (moving each `question_<n>.md` + `answer_<n>.md` to `<state_dir>/clarifications/<branch>/answered/`); a pair written during the resumed session stays at the top level for the next resume. This ordering is what lets Override 2(a)'s top-level `answer_<n>.md` detection fire on re-entry while still guaranteeing a stale answer is never reprocessed and a resumed run never re-detects an already-answered question as still-outstanding. A run whose resumes make no progress is held by the watcher under the status `park_loop` until an operator clears it (the harness repository's `docs/watcher.md` §4). The watcher comment (`autonomous-watcher.sh`) and the `<escalate>` clarification reroute (`plan_orchestration_instructions_autonomous.md` → ``### `<escalate>` — the clarification reroute``) reference this same contract; they do not restate it.

## Ask-vs-assume policy

So the autonomous flow does not degrade into babysitting:

- **Low-stakes / reversible ambiguity:** make a reasonable **documented assumption** and proceed. Do NOT park. Record the assumption in the plan (a `> Assumption:` note in the story index `## Context` or in the relevant per-task file) and surface it in the convergence summary so the user can correct it at review.
- **Park-and-ask only for:** high-stakes / irreversible / security choices, or — when `phases.parity` is `true` — business-logic parity the writer cannot resolve from the `<parity_vocabulary>` source. These go through the headless clarification reroute above.

Every assumption is recorded in the story plan and rolled up in the Done summary; nothing is silently decided.
