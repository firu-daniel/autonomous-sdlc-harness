# scripts/

The five helper scripts an instruction or agent body invokes **by path**, as `${CLAUDE_PLUGIN_ROOT}/scripts/<name>.sh`. All five ship in this directory, and the list below is their declaration — the generated permission profile's interactive-test fragment sends an adopter here for the names rather than repeating them:

- **`find-free-port.sh [base]`** — prints the first free port at or above `base`, so two runs on one machine never serve on the same one. Takes the caller's `qa.portSeed` as that base; prints the chosen port and nothing else.
- **`poll-dev-server.sh <port> [timeout_seconds]`** — polls `http://localhost:<port>` until it answers, rather than sleeping a fixed interval and hoping. Takes the port and an optional timeout; exits 0 on the first answer, 1 on timeout.
- **`kill-dev-server.sh [port]`** — tears that server down, killing only what is *listening* on the port and never a client still holding a connection to it. Takes the port; a no-op with exit 0 when nothing is listening.
- **`reserve-qa-user.sh [slot]`** — parks one test account, so parallel interactive-test sessions never drive the same account at once. Takes the slot number the caller wants, or none for the first free slot; prints the reserved slot, and exits 1, 2 or 3 for an environment problem, an unconfigured slot and a busy one — an exit-code contract callers branch on.
- **`release-qa-user.sh <slot>`** — releases a slot the reserve half parked. Takes that slot number; a no-op with exit 0 when the lock is already gone, so "release on every exit" never turns a passing test into a failing dispatch.

Each script's own header carries the rest: what it does, what it deliberately never does, why it is a script rather than an inline loop or pipe the permission layer cannot express, and a REPRO block that reproduces each of its outcomes by hand.

Note the split deliberately: **outer-loop** scripts — the run watcher and its restart wrapper, the notifier, the commit / push / worktree wrappers and the daemon unit templates — are not plugin assets, because none of them is ever resolved from the plugin root: the instruction corpus names three of them by their `<scripts_dir>/` destination in the adopting repository, and the rest are the CLI's, the watcher's or an operator's to run. They belong to the CLI package — the daemon unit templates at `cli/scripts/daemon/`, the rest under `cli/templates/scripts/`, which `init` copies into the configured `scriptsDir`.

**One adopter step these scripts need, and `init` does not take it.** After enabling the plugin, add one `permissions.allow` entry per helper above, in the same unquoted form the generated profile's wrapper entries use — `Bash(bash <resolved plugin root>/scripts/<name>.sh:*)` — naming a **resolved** plugin root — both of them, where the two differ, per the split below — and the script **file** rather than the directory holding it, because a directory-prefix entry was measured not to match even when the command carried a literal path. Keeping the token in the entry rescues nothing: matching is against the raw command string, and a `${…}` anywhere in that string defeats it however the entry is worded. You do not look a root up by hand: `doctor`'s `plugin-permissions` check resolves them on every run and prints the exact lines to paste (`docs/cli.md` §7). The generated permission profile states the same requirement and the same entry form in its interactive-test fragment's `_README` (`cli/templates/claude/settings.autonomous.qa.json`), and that file is written create-if-absent, so entries added by hand survive every later `init` run — **`--force` included**, which re-reads the profile before replacing it and carries forward every entry naming a plugin root this machine still resolves (`docs/cli.md` §3). An entry naming a root that has moved is dropped rather than carried, and named by the run that dropped it and by `doctor` afterwards — on a machine where the plugin **does** resolve. Where none of its roots resolve there, nothing can tell such an entry from one pasted a minute ago, so the forced run carries every absolute entry outside the checkout forward **unverified** and says so rather than dropping any. What a missing entry costs is a **silent stall**, not a refusal: a run that reaches one of these helpers with nothing matching parks with no error.

**Why the step is manual, and it is not that the root is unknowable.** The root is knowable: the agent runner's own `installed_plugins.json` — under `<claude home>/plugins/` — records an `installPath` per plugin and per scope, which is where `doctor` reads it from; and a machine-local absolute path in a generated file is nothing new — the profile `init` writes is full of them, in the identical `Bash(bash <absolute path>/scripts/<name>.sh:*)` shape as the entry above. Two obstacles are real. `init` may run **before** the plugin is enabled, leaving no row to read — conditional rather than fatal, and the generator already carries that pattern (`extraKnownMarketplaces` is written only when the owner slug resolves, and the closing step says so when it did not). And the install path carries the plugin **version**, so an entry generated once goes silently stale on the next upgrade — which is the argument for re-deriving the root on every run rather than writing it once, and is what the `doctor` check does.

**What the call site does and does not decide, measured 2026-08-26.** What an entry meets is the **command string an agent issues**, and an agent issues a resolved one whether the runtime substituted the path into what it read or it resolved the root itself — so the call site does not decide whether an entry *matches*. What it does decide is **which root** that resolved path names, and where the two roots differ that is the difference between an entry that matches and one that never can:

- A helper named in an **instruction file** — `find-free-port.sh`, `poll-dev-server.sh`, `kill-dev-server.sh` — arrives as bytes, and the agent resolves the root itself. The adoption rehearsal's unattended run invoked all three with the resolved **cache** install root, under hand-added entries of exactly the form above, and nothing stalled. Which root a future agent resolves for this class is not fixed by that run.
- A helper named in an **agent definition body** — the QA-user pair, in `plugin/agents/qa-tester.md` — has `${CLAUDE_PLUGIN_ROOT}` substituted by the runtime. On a `directory`-sourced marketplace that substitution was measured to yield the **source tree** rather than the cache (`docs/development.md` §1). Neither of the pair was invoked in that run, so this class's stall is unexercised rather than disproved.

So: on a machine where the two roots differ, add the entry form above **once per helper per root**, and `doctor`'s `plugin-permissions` prints both sets (`docs/cli.md` §7). Where the two coincide — every git-sourced adoption — they are the same five lines. The one qualification that survives is the probe's, not this document's: the session behind the block results could not be isolated from the measuring machine's own hooks, and §3 of that same document states it.

**A decision this makes available, and it is not taken here.** Generating these entries is blocked by neither the call site nor an unknowable root. What remains is the install-before-enable ordering and the version-carrying path going stale, and the second is already answered for the *checking* half — `plugin-permissions` re-resolves the root every run and prints what is missing. Whether `init` should also **write** the entries is an owner decision that is now open. It is open, not resolved, and the generator is unchanged. A forced run **preserving** an entry an adopter pasted does not take it: preserving is not generating, and it leaves both obstacles standing — the forced run still writes no entry on a machine where the plugin is not yet enabled, and still names no version-carrying path of its own.

The alternative — re-homing these helpers into the adopter's own `scriptsDir` at `init` time, where a generated rule could name them and the manual step would disappear — was settled against when this directory was filled: roadmap item 5's own task prompt fixed the destination as the `${CLAUDE_PLUGIN_ROOT}/scripts/` form above, so the invocation form stands unchanged in every instruction that calls them and the documented hand-add step is carried rather than waited on.
